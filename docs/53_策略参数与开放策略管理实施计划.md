# 策略参数与开放策略管理实施计划

## 1. 计划状态

本计划落实《策略参数声明与开放策略管理设计方案》。当前状态为“待执行确认”；在用户确认本计划前不修改业务代码、数据库迁移、前端行为或使用手册中的现有功能说明。

实施目标是以最小必要改动完整交付以下能力：

- 自定义策略参数声明与单次回测覆盖；
- 开放 API 的完整策略读取、创建、修改、发布、版本查询、归档和恢复；
- API Key 新 Scope、通用幂等、revision 乐观锁和审计；
- 网页参数输入与 API Key 权限页面；
- Bar、L2、历史恢复、公开读取和文档兼容。

## 2. 受影响服务与发布边界

| 服务或模块 | 影响 |
| --- | --- |
| Backend | 新增策略生命周期接口、参数解析、鉴权、幂等、审计和快照构造 |
| Frontend | 参数输入、保存/实验脏状态拆分、API Key Scope 展示 |
| Bar Worker | 读取冻结后的最终策略参数，兼容新快照字段 |
| L2 Runner | 读取冻结后的最终策略参数，兼容新快照字段 |
| PostgreSQL migrate | 扩展通用开放写入幂等记录 |
| 使用手册与开放接口文档 | 同步全部用户可见行为和请求示例 |

以上服务存在接口依赖，必须由 `scripts/deploy-server.sh` 同批发布，不能只重启 Backend 或 Frontend。

## 3. 实施顺序

### 3.1 建立变更前基线

1. 记录当前工作区状态，保护用户已有未提交修改。
2. 运行与策略保存、API Key、公开回测、Bar 和 L2 参数传递相关的现有测试。
3. 核对当前 `/api/v1` 错误格式、Scope 列表、策略保存 revision 和回测幂等行为。
4. 记录现有公开接口兼容样例，作为实施后的回归基线。

### 3.2 增加参数声明解析

修改 `backend/strategies/scripted.py`：

1. 增加 `strategy_parameters_for_script(code)`，与预热声明解析共用一次 AST 解析能力。
2. 实现顶层唯一字典、标量类型、参数名、数量、字符串长度和总大小校验。
3. 返回规范化且保持声明顺序的参数定义，不执行用户代码。
4. 将保留字段集中为一个后端常量，避免路由和 Worker 各自维护。

新增或扩展 `backend/tests/test_scripted_strategy.py`：

- 覆盖合法类型、空声明、未声明、重复声明；
- 覆盖函数调用、表达式、变量引用、嵌套对象和非法名称；
- 覆盖 `bool` 与 `int` 区分、非有限浮点值和所有大小上限；
- 证明解析过程不会执行代码。

### 3.3 抽取统一完整策略生命周期模块

新增 `backend/services/strategy_lifecycle.py`，作为网页和开放接口共同调用的深模块。其接口只暴露完整策略操作，不暴露脚本与配置的分离写入细节：

- `list_strategies`；
- `get_strategy`；
- `save_strategy`；
- `publish_strategy`；
- `archive_strategy`；
- `restore_strategy`；
- `list_versions`；
- `get_version`。

模块内部负责：

1. 复用现有代码安全校验、预热声明和时间周期校验。
2. 解析 `STRATEGY_PARAMETERS` 并协调声明值、旧保存值和本次值。
3. 把公开 snake_case 模型与现有完整策略持久化模型互相转换。
4. 调用 `state_store` 的事务实现，保持脚本、方案和版本原子一致。
5. 将数据库冲突转换为稳定的领域错误，供两个 HTTP 适配器映射。

修改 `backend/app.py` 中网页完整策略保存接口，使其调用该模块。完成替换后删除路由层重复的保存校验组合，避免网页和开放接口规则漂移。

### 3.4 完善完整策略持久化能力

修改 `backend/services/state_store.py`：

1. 将完整策略写入主体提取为可在调用方事务中执行的内部函数。
2. 保留现有一对一所有权、不可变版本复用和 revision 乐观锁。
3. 增加包含归档状态的所有者限定读取与分页列表。
4. 增加带 `expected_revision` 的发布、归档和恢复。
5. 恢复时检查活动策略名称唯一约束；冲突时不自动改名。
6. 归档和恢复同时维护 `strategy_config.archived_at`、`published`、`revision` 与 `user_strategy.status`。
7. 不删除或改写历史 `strategy_config_version`、`user_strategy_version` 和 `backtest_run` 快照。

扩展 `backend/tests/test_strategy_ownership.py`，覆盖跨用户不可见、过期 revision、同内容版本复用、归档、恢复和名称冲突。

### 3.5 扩展通用开放写入幂等

新增幂等迁移 `db/migrations/042_public_strategy_lifecycle.sql`：

1. 为 `api_idempotency_record` 增加操作类型、资源类型、资源 ID、响应状态和最小响应 JSON 字段。
2. 将现有回测记录幂等回填为 `backtest.submit` 操作，保留 `run_id` 和原唯一约束。
3. 增加字段类型和状态约束，不改变现有 RLS 所有者策略。
4. 迁移使用 `IF NOT EXISTS`、确定性回填和约束存在性检查，保证重复执行安全。

修改 `backend/services/state_store.py`，实现一个通用开放写入幂等事务接口：

- 先锁定 API Key 并读取现有记录；
- 相同摘要重放已保存响应；
- 不同摘要返回冲突；
- 首次请求在同一事务内执行资源写入、保存最小响应和写入审计；
- 回测提交继续沿用现有并发与每日限额。

新增迁移结构测试和事务单元测试，覆盖首次执行、重放、冲突、异常回滚及旧回测幂等兼容。

### 3.6 扩展 API Key Scope

修改：

- `backend/services/auth.py`；
- `backend/schemas.py`；
- `frontend/src/api/client.ts`；
- `frontend/src/components/ApiKeyPage.tsx`。

新增 `strategy:read`、`strategy:write`、`strategy:publish`、`strategy:delete`。已有 Key 数据不变，不自动增加权限。

API Key 页面把读取、写入、发布和归档分组说明；写入、发布和归档默认不勾选。创建中禁止重复提交，错误在当前页面显示并保留选择。

扩展 `backend/tests/test_auth.py` 和前端 API Key 页面测试，覆盖合法 Scope、非法 Scope、旧 Key 兼容、缺少 Scope 和管理员 Key 不继承管理员能力。

### 3.7 增加公开完整策略接口

修改 `backend/schemas.py`，增加公开完整策略请求、响应、分页和版本模型。公开模型使用 snake_case，不返回数据库字段结构。

修改 `backend/app.py`，增加：

```text
GET  /api/v1/strategies
GET  /api/v1/strategies/{config_id}
POST /api/v1/strategies
PUT  /api/v1/strategies/{config_id}
POST /api/v1/strategies/{config_id}/publish
POST /api/v1/strategies/{config_id}/archive
POST /api/v1/strategies/{config_id}/restore
GET  /api/v1/strategies/{config_id}/versions
GET  /api/v1/strategies/{config_id}/versions/{version_id}
```

实现要求：

1. 路由只做 API Key Scope、幂等键、字段转换和稳定错误响应。
2. 所有写接口调用统一生命周期模块。
3. 写请求限制为回测模式，不接受实盘账户和执行凭据。
4. 跨用户访问与不存在统一返回 `404`。
5. `409` 区分 revision、名称和幂等冲突，不再把全部冲突映射为同一错误码。
6. 策略源码和完整参数不进入访问审计或集中日志。

新增 `backend/tests/test_public_strategy_api.py`，从 HTTP 契约层覆盖每个路由、Scope、错误码、所有权、幂等和 revision。

### 3.8 实现单次策略参数覆盖

修改 `backend/schemas.py`，为 `PublicBacktestOverrides` 增加 `strategy_params`。

修改统一回测准备链路：

1. 从已发布策略版本读取参数声明和已保存默认值。
2. 校验覆盖名称与类型。
3. 生成 `savedStrategyParams`、`strategyParamOverrides` 和 `effectiveStrategyParams`。
4. 将最终值写入现有 `strategyParams`，供 Bar 和 L2 执行链路读取。
5. 将覆盖纳入现有请求摘要。
6. 校验失败时不创建 `backtest_run` 或队列任务。

扩展：

- `backend/tests/test_public_backtest_api.py`；
- `backend/tests/test_bar_strategy_session.py`；
- `backend/tests/test_l2.py`；
- 回测历史与共享读取相关测试。

至少覆盖默认值、局部覆盖、未知参数、类型错误、旧策略无声明、幂等摘要变化、保存后立即运行和任务提交后策略再次保存不影响已冻结任务。

### 3.9 调整网页回测配置

修改 `frontend/src/components/BacktestPage.tsx` 和相关类型、测试：

1. 从完整策略读取参数声明及当前默认值。
2. 在现有“策略参数与信号”区域生成基础输入框。
3. 将草稿状态明确拆为 `versionDirty` 和 `experimentDirty`。
4. 只有结构或代码变更阻止运行；日期、资金、成本、执行算法和已声明策略参数允许直接运行。
5. 回测提交明确携带单次覆盖，运行操作不调用保存策略接口。
6. 提供恢复默认参数操作和“本次覆盖”提示。
7. 创建请求使用兼容的 UUID v4 生成方式，同一次网络重试复用幂等键。
8. 失败信息显示在当前回测配置区域并保留用户输入。

回归测试必须包含“保存后立即运行不被判为未保存修改”。

## 5. 验证矩阵

### 5.1 后端自动化验证

1. 参数 AST 解析和安全限制。
2. 完整策略创建、修改、版本复用和 revision 冲突。
3. 活动/归档列表、归档、恢复和名称冲突。
4. 每个 Scope 的允许与拒绝矩阵。
5. API Key 所有权与数据库 RLS 双重隔离。
6. 所有公开写接口的首次执行、相同请求重放和不同请求冲突。
7. 公开错误码、请求 ID 和无资源枚举差异。
8. 单次覆盖的校验、合并、快照和幂等摘要。
9. Bar 与 L2 接收最终有效参数。
10. 历史任务、共享回测和旧快照读取兼容。

### 5.2 前端自动化验证

1. 参数声明生成整数、小数、布尔和文本控件。
2. 实验参数变化不触发 `versionDirty`，结构参数变化仍触发。
3. 保存后立即运行不被判定为未保存修改。
4. 运行只提交覆盖，不隐式保存策略。
5. `crypto.randomUUID` 不存在时仍生成合法 UUID v4。
6. 提交中重复点击只发出一次请求。
7. 失败提示显示在当前操作区域并保留输入。
8. 新增高权限 Scope 默认不勾选。

### 5.3 静态与构建验证

- 后端 pytest 目标测试与完整测试；
- 前端 Vitest 目标测试与完整测试；
- TypeScript `tsc --noEmit`；
- 前端正式构建；
- 迁移在空库、现有库和重复执行场景验证。

未实际执行的检查不得写成已通过。

### 5.4 远程普通用户样本回归

本次变更涉及回测提交、策略执行、历史恢复和权限隔离。完成本地自动化验证后，交付前必须：

1. 只读取得远程服务器普通用户最近两条回测任务的保存代码和运行快照。
2. 不把用户代码、参数或快照写入仓库、文档、对话或持久日志。
3. 通过隔离的正常回测和 Worker 链路验证提交、排队、领取、执行和最终结果。
4. 分别覆盖 Bar 和实际受影响的 L2 链路；行情不足时如实记录限制。
5. 验证历史任务仍按原快照读取，不被新默认值重算。
6. 验证后清理临时副本。

远程不可访问、样本不足或行情缺失时，明确标记“远程普通用户样本回归待验证”及原因。

## 6. 发布步骤

1. 发布前检查排队和运行中的 L2 任务。
2. 若重建 L2 Runner 会中断任务，则等待完成、由用户取消，或取得明确中断确认。
3. 使用 `scripts/deploy-server.sh` 同批执行迁移并发布 Backend、Bar Worker、L2 Runner 和 Frontend。
4. 不覆盖服务器 `deploy/.env`；本方案预期不新增环境变量。
5. 发布后检查健康状态和 Runner 能力摘要。
6. 创建一个最小权限新 API Key，验证策略读取、创建、修改、发布、归档、恢复和回测覆盖。
7. 验证旧 API Key 不获得新增权限且旧回测接口仍可用。
8. 检查代表性历史策略和历史任务读取。

## 7. 回滚策略

1. 应用回滚到旧版本时，新增数据库字段保持可空且不影响旧代码读取。
2. 不删除已经由新版本创建的策略、版本或审计记录。
3. 若公开策略写接口出现问题，先通过配置关闭整个开放 API，避免部分写能力继续暴露。
4. 回滚后验证网页策略保存、旧公开回测提交和历史读取。
5. 数据修复只能使用独立、幂等迁移，不修改已执行的 `042` 迁移。

## 8. 自审结论

计划已检查以下风险：

- 没有把内部脚本与配置分离写接口直接暴露给调用方；
- 没有因 API Key 属于管理员而放宽所有权；
- 没有把归档实现为不可恢复删除；
- 没有把参数文件、批量循环或特定调用工具纳入系统职责；
- 没有让单次覆盖修改策略默认值或版本；
- 没有为网页和开放接口复制两套保存规则；
- 已包含幂等、乐观锁、RLS、审计、历史兼容和运行快照；
- 已包含使用手册、开放接口文档和服务器同批发布要求；
- 已包含项目规定的远程普通用户样本回归。

当前未发现必须新增第三方依赖或修改依赖清单的需求。
