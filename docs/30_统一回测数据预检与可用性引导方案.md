# 统一回测数据预检与可用性引导方案

> 历史方案说明：本文关于保存、提交前行情完整性预检的决定已由 `docs/adr/0004-unified-preflight-and-loading.md` 的 2026-09-22 修订取代；现行行为只展示元数据范围，实际行情错误在 Worker 执行期统一处理。

## 一、背景与结论

当前回测页面将“周期受引擎支持”与“当前标的、日期范围的数据完整可用”混为一谈。尤其在 L2 模式下，前端把支持周期直接标为可用，并将数据检查延后至 `l2-runner`（L2 任务执行器）。因此用户可能保存了不可执行的完整策略文件，或任务进入队列后才得到“系统异常”。

以任务 `c0f7fded-85bb-46e6-948e-e0f93a3770bc` 为例，`688126.SH` 在 2026-08-01 至 2026-08-24 缺少 QMT 1 分钟行情，L2 快照临时聚合也未找到数据；异常发生于 `l2.bar_load`（L2 Bar 加载），但未被映射为数据问题，最终显示为通用系统异常。

本方案的结论如下：

1. 所有回测模式必须在保存完整策略文件和创建回测任务前完成权威数据预检。
2. 策略源码、参数、标的、周期与回测区间共同构成完整可执行策略文件；任一必需数据不完整时，禁止保存该文件。
3. 页面必须先向用户展示各周期与各交易日的可用性，避免通过保存或运行反复试错。
4. 普通用户只需要知道“缺少哪类数据”和“哪些日期不可用”：日期在日历中置灰，文案不逐条罗列日期。
5. `bar-runner`（标准 Bar 任务执行器）和 `l2-runner` 仍保留运行前的最终校验，防止预检结果过期或数据源状态变化。

## 二、目标、范围与不变量

### 2.1 目标

1. 用户选择标的、日期范围、周期与成交模式时，可直接看见可用周期和不可用交易日。
2. 数据缺失时，前端以数据问题展示，不显示“系统异常”、SQL、表名、容器名或堆栈。
3. 数据缺失时，不保存策略代码与参数构成的完整策略文件，不创建回测任务，也不占用队列。
4. 标准 Bar 与 L2 盘口回放复用同一预检入口，依据模式增加各自的数据依赖。
5. 预检只进行覆盖元数据或按日聚合查询，不读取完整快照明细；不显著增加 ClickHouse 压力。

### 2.2 本轮范围

- 后端统一预检服务、网页预检接口、保存/提交权威拦截和结构化错误契约。
- QMT Bar、L2 十档快照、需要逐笔成交时的逐笔成交的逐交易日完整性判定。
- 周期可用性矩阵、缺失日期置灰、保存/运行操作拦截和右下角提示。
- `l2.bar_load`（L2 Bar 加载）及相关 L2 数据异常的安全分类。
- 后端、前端与 Runner 的自动化测试和服务器发布验证。

### 2.3 非目标

- 不导入、修复、去重、补齐或删除任何原始行情数据。
- 不改变策略撮合、成交、交易时段、L2 队列调度或历史任务结果语义。
- 不新增依赖，不修改 `package.json`、`pyproject.toml` 或 `requirements.txt`。
- 不向普通用户公开 ClickHouse 表结构、源地址、SQL 或原始异常。

### 2.4 必须保持的不变量

1. 预检通过不替代 Runner 的最终校验；Runner 的结果仍是执行时的权威结论。
2. 只有当前完整策略文件所引用的标的、周期、日期和成交模式决定预检结果；不得使用其他方案或旧缓存的结果。
3. 历史任务按保存时的数据与参数快照展示，不因新增预检逻辑被重算、改写或隐藏。
4. 数据可用性缓存失效最多增加查询，不得将不完整数据误判为完整。

## 三、数据完整性规则

### 3.1 通用规则

预检先按交易日历计算所选范围内应存在的交易日，再逐日比对可用性；禁止仅根据“查询到了若干覆盖记录”判定完整，避免中间交易日无记录时被误判为完整。

预检结果包含三种状态：

| 状态 | 含义 | 保存与回测 |
| --- | --- | --- |
| `available`（可用） | 所有必需交易日和数据类型均完整 | 允许 |
| `incomplete`（不完整） | 已确定存在缺失日期或缺失数据类型 | 禁止 |
| `unknown`（待确认） | 参数不完整、预检请求中或数据源暂不可确认 | 暂不允许保存/运行，并提示等待检查或重试 |

### 3.2 模式依赖

| 模式 | 必需数据 | 说明 |
| --- | --- | --- |
| 标准 Bar 回放 | 可用且完整的 Bar | 根据统一 Bar 来源解析规则确认一个任务级来源；不能跨日期静默混用来源。 |
| L2 盘口回放 | 完整 Bar + 有效十档快照 | 十档快照须覆盖实际 Bar 对应的全部交易日。 |
| 需要逐笔成交的 L2 配置 | 完整 Bar + 有效十档快照 + 有效逐笔成交 | 逐笔成交仅在当前策略/执行配置确实依赖时纳入必需项。 |

周期可用不等于数据来源相同。比如 15 分钟与 30 分钟可由完整 1 分钟数据派生；页面应展示最终可用性，而不是要求用户理解数据源回退细节。

## 四、前端交互方案

### 4.1 数据可用性面板

在标的、日期范围、周期和成交模式附近增加“数据可用性”面板。用户每次修改标的、模式或有效日期后，前端经过短暂防抖请求一次批量预检。

面板按当前模式展示所有支持周期：

| 周期 | 状态 | 原因示例 |
| --- | --- | --- |
| 1m | 可用 | 数据完整 |
| 5m | 不可用 | 缺少 L2 十档快照 |
| 1d | 不可用 | 缺少 QMT Bar |

不可用周期保持可见但置灰，原因只显示缺失数据类型，不展示日期列表。用户切换为 L2 模式后，不能再把“引擎支持”误解为“当前数据可运行”。

### 4.2 日期选择与置灰

日期选择器按当前标的、模式与周期使用预检返回的缺失交易日置灰：

1. 置灰日期不可作为开始日期或结束日期选择。
2. 已选区间因参数切换而包含置灰交易日时，明确标记为不完整；保存与运行均不能通过。
3. 非交易日沿用当前页面语义，不与数据缺失交易日混淆。
4. 普通用户看到日期已置灰即可知某日不可用；不在右下角提示或周期说明中重复列出日期。

### 4.3 保存与运行拦截

完整策略文件保存与回测运行复用相同的 `PreflightResult`（预检结果）：

- `available`：允许保存和运行。
- `unknown`：显示“正在检查数据可用性”，不执行保存或运行。
- `incomplete`：不保存、不创建任务；按钮呈不可用状态，但保留受控点击入口以展示原因。

由于原生 `disabled` 按钮不能接收点击事件，前端应使用无障碍语义的不可用样式和操作守卫：点击时不触发保存/提交 API，仅在右下角显示安全提示。

提示文案示例：

```text
当前日期范围缺少 L2 十档快照，无法保存完整策略。
```

文案按缺失类型组合，最多展示必要类别；不得写入缺失日期、表名、内部数据源、SQL 或异常原文。

## 五、后端预检与任务链路

### 5.1 统一预检服务

新增独立的预检服务，作为网页预检接口、完整策略保存接口、网页回测提交接口与开放 API 回测提交接口的共同依赖。调用方不得各自实现日期或模式判断。

输入为经过规范化的：

```text
symbol、timeframe、startDate、endDate、fillModel、executionAlgorithm、executionParameters
```

输出为结构化结果，至少包含：

```text
status、timeframeAvailability、missingDataTypes、missingDates、dataSourceVersion、checkedAt
```

`missingDates`（缺失日期）仅服务于网页置灰和服务端诊断；普通用户提示只使用 `missingDataTypes`（缺失数据类型）。

### 5.2 批量可用性查询

一次网页预检应同时返回当前模式下全部支持周期的可用状态，避免为每个下拉选项发起独立请求。

查询应遵循下列成本边界：

1. QMT Bar 优先读取 `qmt_kline_coverage`（QMT 覆盖记录）和交易日历，不读取完整 K 线。
2. L2 十档快照与逐笔成交仅按标的、日期范围做 `GROUP BY trade_date`（按交易日聚合）或等价的覆盖元数据查询，不拉取逐条快照或成交记录。
3. 同一预检结果使用 `symbol + timeframe + startDate + endDate + fillModel + 数据映射版本` 作为缓存键，并采用短 TTL；映射版本变化立即失效。
4. 后端保存/提交前的权威预检可复用仍有效的缓存结果；缓存未命中时重新执行轻量查询。

精确 TTL、缓存容量和查询延迟以服务器压测结果确定，不在本方案中预设未经验证的数值。

### 5.3 权威保存与提交校验

在写入完整策略代码/参数快照之前，后端必须调用统一预检服务：

1. 预检不通过，返回 HTTP `422` 和安全的结构化数据错误，不写入策略版本或方案快照。
2. 预检通过，才允许保存当前完整策略文件。
3. 回测提交前再次调用同一服务；预检不通过时不得插入 `backtest_run`、`bar_backtest_job` 或 `l2_backtest_job`。
4. 网页 Cookie 提交与 `/api/v1` 提交必须共用该校验，避免开放 API 绕过规则。

### 5.4 Runner 最终校验

Runner 在领取任务后仍执行来源选择与覆盖校验：

- 标准 Bar 任务验证保存时选择的数据源当前仍完整；
- L2 任务依次验证 Bar、十档快照和必要的逐笔成交；
- 运行期发现数据缺失时，任务以 `data`（数据）类别安全失败，并保存内部诊断供管理员排查。

这层校验只防御数据变动、缓存失效或旧任务兼容，不能替代提交前反馈。

## 六、错误契约与前端展示

数据缺失属于用户可理解、不可重试的 `data`（数据）问题，而不是未知系统故障。预检接口和异步任务失败都应使用稳定错误码，例如：

| 代码 | 对外消息 | 用途 |
| --- | --- | --- |
| `data.bar_missing` | 当前日期范围缺少 Bar 数据。 | QMT 或选定 Bar 来源不完整。 |
| `data.l2_quote_missing` | 当前日期范围缺少 L2 十档快照。 | L2 Quote 覆盖不足。 |
| `data.l2_trade_missing` | 当前日期范围缺少 L2 逐笔成交。 | 需要逐笔成交的配置覆盖不足。 |
| `data.l2_quote_duplicate_timestamp` | L2 十档快照时间数据不满足回放要求。 | 已存在数据但质量不合格。 |

`l2.bar_load` 中由 QMT 缺失、临时聚合无快照等原因引发的 `L2DataError`（L2 数据错误）必须在异常创建处保留数据类别和安全上下文，不能仅靠中文异常文本匹配。错误摘要与错误详情应使用分类器真实返回的 `category`（类别），避免再写死为 `system_error`（系统错误）。

管理员系统日志可记录标的、缺失日期、阶段和受控原始诊断；普通用户接口及前端不得泄露这些内部详情。

## 七、实施步骤

1. 梳理当前完整策略保存、方案保存、网页提交、开放 API 提交和 Runner 的数据校验入口，确定统一接入点与现有接口兼容边界。
2. 定义预检结果模型、交易日历逐日比对规则、模式依赖和覆盖查询适配器；为 QMT、Quote、Trade 数据返回统一缺失类型。
3. 实现批量预检服务与网页接口，加入短时缓存、映射版本失效和输入校验。
4. 将完整策略保存和所有回测提交接入权威预检；不完整时返回结构化 `422`，不产生版本、方案快照或任务。
5. 改造回测页面：展示周期可用性矩阵、置灰缺失日期、保存/运行守卫和右下角安全提示。
6. 完善 L2 Bar/Quote/Trade 运行期错误分类与 `errorDetail`（结构化错误详情）透传，保持管理员诊断可用。
7. 补充测试并按服务器发布约束发布全部相互依赖服务；发布前检查排队与运行中的 L2 任务。

## 八、验证计划

### 8.1 后端测试

1. QMT 覆盖记录为空、部分交易日缺失、状态为 `partial`（部分）和完整覆盖的逐交易日判定。
2. L2 Quote 与 Trade 的单日、跨日和全部缺失；断言只进行聚合/覆盖查询，不读取完整行情明细。
3. 标准 Bar、L2 立即成交与依赖逐笔成交的 L2 配置返回各自正确的缺失类型。
4. 完整策略保存和网页/API 回测提交在预检失败时均返回 `422`，且数据库没有新增策略版本、方案快照或任务。
5. Runner 在预检通过后数据发生变化时仍安全拒绝，并返回 `data.*`，不返回 `internal.unexpected`（未知内部错误）。
6. 缓存命中、失效、映射版本变化和数据源查询异常的行为符合不变量。

### 8.2 前端测试

1. 周期矩阵正确展示可用、不可用与缺失类别；L2 模式不再将支持周期一律展示为可用。
2. 缺失交易日被置灰且不可选；非交易日与数据缺失日的视觉/语义正确区分。
3. 预检中的保存与运行被守卫，不会发送保存/提交请求。
4. 数据不完整时点击保存或运行只展示右下角安全提示，不写入、不入队、不显示日期列表。
5. 数据补齐后刷新预检结果，周期、日期、保存与运行状态恢复可用。
6. 历史失败任务的 `data.*` 错误详情显示数据问题，旧任务仍按兼容逻辑显示。

### 8.3 性能与服务器验证

1. 对代表性标的、短区间和长区间分别记录预检的查询次数、响应时间、ClickHouse 读取行数与缓存命中情况。
2. 确认预检不拉取完整 Quote 或 Trade 明细，且相同参数的重复页面操作命中短时缓存。
3. 服务器发布前检查排队和运行中的 L2 任务；按 `scripts/deploy-server.sh` 同批发布后端、前端、Bar Runner、L2 Runner 与 Strategy Worker。
4. 在服务器使用缺 QMT、缺 Quote、缺 Trade、完整数据四类样本验证：日期置灰、保存拦截、提交拦截、运行期兜底和管理员日志。

## 九、验收标准

1. 用户无需先保存或运行，即可知道当前标的、日期范围、成交模式下哪些周期可用。
2. 缺失数据交易日在日期选择器置灰；不可用周期显示缺失数据类别但不展示日期列表。
3. 数据不完整时，完整策略文件无法保存，回测任务无法入队，且右下角显示安全、可理解的原因。
4. 网页与开放 API 无法绕过预检；Runner 仍可拦截预检后发生的数据变化。
5. `l2.bar_load` 等数据缺失场景对用户显示 `data.*` 数据错误，不再显示“回测服务发生内部错误”。
6. 预检不读取完整 L2 明细；性能验证证明其查询成本远低于实际 L2 回放，并具有有效缓存。
7. 现有交易语义、历史任务读取、数据源原始内容和部署私有配置均不被改变。

## 十、风险与自审

| 风险 | 控制措施 |
| --- | --- |
| 仅看已有覆盖记录，遗漏中间缺失交易日 | 使用交易日历构造期望日期集合并逐日比对。 |
| 前端结果过期后仍允许保存 | 保存和提交始终由后端重新进行权威预检。 |
| 预检扫完整快照导致页面变慢 | 强制覆盖元数据或按日聚合查询；记录读取行数并使用短时缓存。 |
| 原生禁用按钮无法解释原因 | 采用可访问的操作守卫，拦截点击并显示右下角提示。 |
| 数据异常仍被误分类为系统异常 | 在领域异常与错误目录中按类型分类，测试禁止 `data.*` 回退到 `internal.unexpected`。 |
| 新规则影响历史方案或任务 | 新规则只限制新保存和新提交；历史任务不重算、不回写。 |

## 十一、执行前确认

本方案获得执行确认后，改动将涉及后端预检与错误分类、网页回测页面、完整策略保存/方案保存接口、网页与开放 API 提交链路、Bar/L2 Runner 二次校验和相关测试；不修改原始行情数据、交易规则、依赖清单或服务器私有 `deploy/.env`。
