# 自动化回测逻辑计划配额移除方案

## 一、文档状态

- 状态：待实施
- 适用范围：标准 Bar 自动化实验的预览、创建、Trial 生成、任务物化、恢复、重试、数据库迁移、前端提示和公开 API 文档
- 基线：`develop` 分支 `b71a786`
- 不包含：提高实际回测并发、提高 Runner 副本数、开放自动化 L2、改变实验结果和评价口径

## 二、背景与问题

当前自动化实验同时存在三类由部署环境变量控制的逻辑计划硬上限：

```text
TREND_GRID_EXPERIMENT_MAX_TRIALS
TREND_GRID_EXPERIMENT_MAX_USER_PLANNED_TRIALS
TREND_GRID_EXPERIMENT_BAR_MAX_ESTIMATED_BARS
```

它们分别限制单个实验 Trial 总数、单用户未完成实验的计划 Trial 总数和预计 Bar 总量。这些限制会直接决定预览能否通过、实验能否创建以及运行阶段能否继续物化任务。

该设计把“逻辑计划规模”和“当前实际资源消耗”混为一体。参数网格的笛卡尔积很容易超过固定阈值，但计划规模大并不等于系统会同时执行同等数量的任务。真正需要保护的是并发执行槽位、待物化缓冲窗口、数据库与磁盘压力，而不是用部署变量拒绝一个有限且可暂停的逻辑计划。

更直接的业务问题是：如果用户的一次完整参数验证超过固定上限，当前系统会要求用户手工删减候选值，或者把同一个搜索空间拆成两个甚至更多实验。这样虽然绕过了上限，却破坏了“一个实验代表一次完整验证意图”的边界：候选结果无法在同一 Revision 内统一评价和排序，进度、暂停、恢复、取消及审计被拆散，人工分段还可能遗漏或重复组合。用户为了验证完整参数空间，不应承担这种由部署配额造成的实验拆分成本。

因此本方案取消上述三项业务配额，改为：

> Trial 总数和预计总工作量不再由 `.env` 决定是否允许创建；`.env` 只负责实际运行容量和技术安全保护。

同时坚持：

> 一个完整参数搜索空间应当保存在一个 Experiment Revision 中；资源容量只影响完成速度和暂时能否继续推进，不改变用户实验的逻辑边界。

## 三、现状核对与必要补充

### 3.1 当前限制链路

现有实现中的限制并非只存在于 `backend/settings.py`，而是贯穿完整生命周期：

1. `backend/settings.py` 读取三个变量，并在实验开关开启时校验单实验上限和用户计划上限的关系；
2. `backend/experiments/application.py` 在预览中以 Trial 总数和预计 Bar 总量形成硬阻塞；
3. 创建事务通过 `reserved_planned_trial_count` 串行预留用户计划额度，超限返回 `experiment.plan_limit_exceeded`；
4. 运行阶段根据当前配置、历史预算快照和已预留计划量再次阻塞实验；
5. 实验终结、恢复和失败重试会释放或重新预留计划额度；
6. `experiment_budget_v2` 快照固化三个旧上限并参与 `budgetDigest`；
7. 前端、测试、使用手册和 API 文档均依赖旧门禁语义。

删除三个设置读取但保留其余链路，会形成启动错误、运行时属性不存在、历史实验永久阻塞或配额缓存漂移，因此必须按完整契约改造。

### 3.2 当前“分批生成”不是滚动缓冲

当前 `TREND_GRID_EXPERIMENT_GENERATION_BATCH_SIZE` 只限制单次事务写入的 Trial 数量。Stage 仍需先生成全部 `backtest_experiment_trial` 记录，才从 `preparing` 进入 `queued`，任务物化也要求：

```text
generated_trial_count == planned_trial_count
```

因此只删除总量上限会把问题从“创建被拒绝”转移为“协调器持续预生成全部 Trial 并占满 PostgreSQL”。这不满足“不限制逻辑计划规模、只限制实际资源”的目标。

本方案必须同时把生成与执行改为滚动补充：逻辑计划可以很大，但未执行的已生成 Trial 数量始终有界；已完成 Trial 作为实验结果仍会累积保存，并由磁盘高水位机制决定是否暂停继续生成。

### 3.3 当前预览会遍历全部组合

当前预览在门禁允许时会编译全部 Trial，只在门禁拒绝时才抽取首尾样例。取消总量门禁后，该行为会使大网格预览占用与 Trial 总量线性增长的 CPU 和内存。

预览必须改成：完整校验输入维度和每个候选值，但只编译固定数量的代表性组合。预览耗时和内存不得随笛卡尔积总量线性增长。

### 3.4 磁盘高水位现状

当前仓库可以确认存在分批生成和在途并发门禁，但未发现自动化实验专属的磁盘高水位暂停实现。实施阶段必须先核对服务器或外部运维层是否已有统一磁盘高水位控制：

- 若已有，应记录信号来源、触发阈值和恢复条件，并补充协调器暂停/恢复验证；
- 若没有，本方案上线前必须补齐可测试的存储压力门禁，不能把尚不存在的能力写成“已保留”；
- 存储压力只暂停新 Trial 生成和新任务物化，不改写计划规模，不删除结果，也不把实验错误地标记为失败。

## 四、目标与非目标

### 4.1 目标

1. 删除三个逻辑计划上限环境变量的读取、校验、示例配置和服务器私有配置；
2. 用户的一次完整参数验证可以作为单个 Experiment Revision 创建，不需要为绕过上限手工删减或拆分参数；
3. Trial 总数只受有限网格定义和数据库数值类型可表示范围约束，不受业务配额约束；
4. 预计 Bar 总量只用于资源等级和耗时提示，不参与预览、创建或运行准入；
5. 删除用户计划额度的预留、释放、修复和重试恢复逻辑；
6. 生成、物化和执行形成有界滚动窗口，避免大计划一次性写入全部 Trial；
7. 保留实际并发、公平调度、手工任务保留容量和用户在途上限；
8. 历史 `experiment_budget_v2` 快照继续可读，但旧字段不再影响调度；
9. 保持暂停、恢复、取消、重试和结果评价对大计划有效；
10. 删除 `experiment.plan_limit_exceeded` 公开错误契约。

### 4.2 非目标

1. 不把“取消计划配额”解释为无限并发；
2. 不调整 `BACKTEST_BASE_CONCURRENCY`、突发并发或 Runner 副本；
3. 不删除 `TREND_GRID_EXPERIMENT_MAX_VALUES_PER_DIMENSION`；
4. 不删除请求体数组长度、字段长度、数据类型或 `bigint` 溢出保护；
5. 不改变 Trial 指纹、随机种子、回测请求、成交、收益或评价语义；
6. 不自动清理历史 Trial、运行结果或评价产物；
7. 不由服务端自动截断、抽样或拆分用户提交的完整参数搜索空间；
8. 不在本次改造中开放自动化 L2。

## 五、目标约束

改造后的系统必须同时满足以下不变量：

1. **逻辑计划有限但不设业务总量上限**：`planned_trial_count` 必须大于 0，且不得超过 PostgreSQL `bigint` 最大值 `2^63 - 1`；超过时返回 `experiment.validation_failed`；
2. **完整验证意图不拆分**：一次提交的全部候选组合保存在同一 Experiment Revision 中，由同一评价、进度和生命周期管理；
3. **单维度输入有界**：继续使用 `TREND_GRID_EXPERIMENT_MAX_VALUES_PER_DIMENSION` 限制异常单维度和请求体放大；
4. **预览复杂度有界**：预览只生成固定的首尾代表样例，不遍历全部组合；
5. **待执行窗口有界**：尚未终结的已生成 Trial 数不得无限领先于实际执行进度；
6. **实际并发有界**：统一调度器、实验级在途上限、用户级在途上限和普通任务保留容量继续生效；
7. **存储压力可暂停**：达到磁盘高水位时暂停生成和物化，恢复后从持久化游标继续；
8. **身份确定性不变**：同一冻结 Stage 的 `trialIndex`、维度赋值、指纹和种子不因批次或暂停恢复而变化；
9. **历史只读兼容**：旧预算字段可以展示或导出，但不能重新成为门禁；
10. **取消不依赖预生成**：取消大计划时，未生成区间通过 `cancelled_before_generation` 计入终态，不要求补生成 Trial 行。

## 六、详细改造方案

### 6.1 设置与部署配置

从 `backend/settings.py` 删除：

```text
EXPERIMENT_MAX_TRIALS
EXPERIMENT_MAX_USER_PLANNED_TRIALS
EXPERIMENT_BAR_MAX_ESTIMATED_BARS
```

同时删除 `validate_experiment_configuration()` 中以下启动校验：

- 用户计划 Trial 上限必须为正数；
- 单实验 Trial 上限不能大于用户计划 Trial 上限。

从 `deploy/.env.example` 删除对应三行及其注释。不得保留已废弃变量并静默忽略，因为这会让运维继续误认为修改它们可以改变准入行为。

以下配置继续保留：

- `TREND_GRID_EXPERIMENT_MAX_VALUES_PER_DIMENSION`：输入结构保护；
- `TREND_GRID_EXPERIMENT_GENERATION_BATCH_SIZE`：单次生成事务的批量大小；
- `TREND_GRID_EXPERIMENT_MAX_IN_FLIGHT_PER_EXPERIMENT`：实验实际在途任务上限；
- `TREND_GRID_EXPERIMENT_MAX_IN_FLIGHT_PER_USER`：用户实际在途任务上限；
- `TREND_GRID_EXPERIMENT_MANUAL_RESERVED_PERMITS`：普通手工回测保留容量；
- 统一回测调度容量及公平调度配置。

### 6.2 预览与输入校验

`backend/experiments/application.py` 的预览逻辑调整为：

1. `_limit_decision()` 只保留单维度候选值数量门禁；
2. 删除 `trial_limit_exceeded` 和 `bar_budget_exceeded`；
3. `estimatedBarCount` 无论大小都不进入 `blockingReasons`；
4. `resourceClass=heavy` 继续返回 `high_resource_estimate` 警告，并明确它只是耗时/资源提示；
5. `_examples()` 始终使用固定首尾样例索引，不再因 `allowed=true` 遍历 `range(planned_trial_count)`；
6. 每个维度及每个候选值仍由生成器完整规范化和校验；跨维度组合只编译固定样例，实际批次生成时继续执行权威编译；
7. `_safe_product()` 继续检查 `2^63 - 1` 溢出，并返回 `experiment.validation_failed`，该保护属于数据类型安全而非用户配额。

创建和创建新 Revision 时，如果预览因单维度输入保护不允许创建，统一返回现有的 `422 experiment.validation_failed` 并携带 `blockingReasons`，不再返回 `429 experiment.plan_limit_exceeded`。

### 6.3 预算快照版本

新预览和新 Revision 使用：

```text
budgetVersion = experiment_budget_v3
```

新的 `capacityPolicy` 只保存仍影响运行的字段：

```json
{
  "maxValuesPerDimension": 50,
  "maxInFlightPerExperiment": 1,
  "maxInFlightPerUser": 1,
  "schedulerCapacity": 16
}
```

不得再写入：

```text
maxTrials
maxUserPlannedTrials
maxEstimatedBars
```

兼容规则：

1. 历史 `experiment_budget_v2` JSON 原样保留，不做数据重写；
2. 读取历史快照时忽略三个旧字段；
3. 运行阶段只比较实际容量字段，不因旧 Trial 总数或预计 Bar 值阻塞；
4. 部署前生成但尚未创建的旧预览允许因 `budgetDigest` 变化返回 `experiment.preview_stale`，用户重新预览即可；
5. 已创建 Revision 的 `resource_budget`、`specHash` 和历史导出不得被新默认值重算。

### 6.4 删除用户计划额度

从 `backend/experiments/repository.py` 删除：

- `_reserve_user_plan()`；
- `_release_plan_quota()`；
- 创建实验和创建 Revision 时的计划额度预留；
- 实验终结时的计划额度释放；
- 失败重试时的重新预留；
- 聚合修复中对计划额度的重算；
- 运行门禁对 `reserved_planned_trial_count` 的判断；
- `plan_quota_released_at` 的状态维护。

`backtest_experiment_user_quota` 表继续保留，因为它仍负责：

- `experiment_in_flight_count`；
- `manual_reserved_permits`；
- 用户实际在途容量的串行化和漂移修复。

### 6.5 滚动 Trial 生成与物化

目标状态不再要求“全部生成后才能执行”。协调器按以下顺序推进：

```text
计算当前窗口余量
  → 按 generation_cursor 生成一个有限批次
  → 提交 Trial 行与增量集合摘要
  → 立即允许物化已生成 Trial
  → 执行终结后释放在途容量
  → 窗口出现余量时继续生成
```

核心规则：

1. Stage 在首批 Trial 成功提交后即可进入可物化状态，不等待 `generated_trial_count == planned_trial_count`；
2. `_can_materialize()` 删除“必须全部生成”的条件，只要求目标 Trial 已持久化、未取消、未终结且容量允许；
3. 生成候选查询必须比较当前已生成未终结数量和滚动窗口，不允许协调器无限领先；
4. 滚动窗口属于实际资源保护，可由现有生成批量和在途容量派生；若实现阶段证明需要独立配置，只能新增明确命名的缓冲容量变量，不能重新引入逻辑计划总量上限；
5. `generation_cursor` 仍是下一逻辑 Trial 索引，租约、CAS 和增量摘要语义不变；
6. `trial_collection_digest` 在全部逻辑 Trial 已生成后才冻结；在此之前使用 `incremental_collection_digest` 恢复；
7. 计划执行完毕的判断同时要求逻辑生成完成、无在途任务且所有已生成 Trial 终结；
8. 取消时不生成剩余 Trial，直接将未生成数量计入 `cancelled_before_generation`；
9. 暂停只停止新生成和新物化，不取消已经运行的普通回测；
10. 恢复从原 `generation_cursor` 和未终结 Trial 继续，不重复生成或跳号。

需要同步校正详情接口中的计数语义：

- `plannedTrialCount`：逻辑总数；
- `generatedTrialCount`：已经持久化的 Trial 数；
- `inFlightTrialCount`：已物化且未终结的实际任务数；
- `queuedTrialCount`：尚未终结的逻辑工作量，必须在文档中明确其中可包含尚未生成的 Trial。

### 6.6 运行阶段门禁

`_budget_capacity_gate()` 只允许以下变化阻塞新物化：

- 实验级在途容量收紧；
- 用户级在途容量收紧；
- 统一调度有效容量收紧；
- 普通手工任务保留容量和等待时间门禁；
- 用户被冻结、资产不可用、功能关闭或存储高水位。

以下内容不得再阻塞：

- 计划 Trial 总数；
- 用户所有未完成实验的计划总数；
- 预计 Bar 总量；
- 历史 `budget_v2` 中上述字段比当前值大。

### 6.7 数据库迁移

数据库收缩采用两阶段发布，避免新版本启动失败时无法回退到旧代码。

#### 阶段 A：停止使用并清零

新增幂等迁移，完成：

1. 将 `backtest_experiment_user_quota.reserved_planned_trial_count` 清零；
2. 新代码停止读取和写入该字段；
3. 新代码停止读取和写入 `backtest_experiment_revision.plan_quota_released_at`；
4. 保留列一个短观察周期，仅用于回退兼容；
5. 通过数据库统计确认两个字段不再变化。

#### 阶段 B：删除字段

确认仓库代码、运维查询、报表和外部只读消费者均无依赖后，新增后续幂等迁移：

```sql
ALTER TABLE backtest_experiment_user_quota
  DROP COLUMN IF EXISTS reserved_planned_trial_count;

ALTER TABLE backtest_experiment_revision
  DROP COLUMN IF EXISTS plan_quota_released_at;
```

`plan_quota_released_at` 仅服务于计划额度释放；若只删除额度字段而保留该列，会留下无业务含义的死状态，因此一并删除。

阶段 B 完成前不得把数据库清理写成“已完成”。阶段 B 完成后，旧版本代码不再具备直接回退兼容性，回退必须使用包含兼容迁移的前向修复版本，不能直接切回读取旧列的镜像。

### 6.8 前端行为

前端保留 Trial 总数、预计 Bar、资源等级和首尾样例展示，但调整语义：

1. 将“预览通过资源边界检查”改为“预览完成，可创建实验”；
2. 资源等级显示为耗时和资源提示，不暗示达到某个等级会拒绝创建；
3. 删除针对 `trial_limit_exceeded`、`bar_budget_exceeded` 和 `experiment.plan_limit_exceeded` 的提示或测试；
4. 单维度异常仍在当前预览区域展示并阻止创建；
5. 超大计划的创建按钮行为、幂等键和错误展示继续满足浏览器运行环境兼容要求；
6. 页面应提示大计划可能长时间排队，可随时暂停或取消，但不得用前端阈值重新实现隐藏上限。

## 七、实施步骤

7. 新增滚动生成、边生成边物化、窗口耗尽、终结补充、暂停恢复和取消未生成区间测试；

## 八、验证计划

### 8.1 后端单元与契约测试

- 设置模块在完全不存在三个旧变量时可正常启动实验功能；
- 设置模块不再暴露三个旧配置属性，应用代码也不再引用对应环境变量名；
- 单维度候选值超限仍被阻止；
- 1001、10000 及更大但未溢出的 Trial 计划可以预览和创建；
- 超过旧上限的完整参数空间只创建一个 Experiment Revision，`plannedTrialCount` 等于完整笛卡尔积，不被截断、抽样或拆分；
- 预计 Bar 超过原阈值仍 `allowed=true`，并保留资源等级提示；
- `experiment.plan_limit_exceeded` 不再由任何公开接口返回；
- 预览样例数量固定且首尾索引稳定；
- 历史 `budget_v2` 快照不会触发计划规模阻塞；
- 现有并发、公平调度和手工任务保留门禁继续生效。

### 8.2 PostgreSQL 集成测试

- 同一用户并发创建多个大计划均能成功，不出现计划额度竞争；
- 幂等创建仍只生成一个 Experiment；
- Trial 只在滚动窗口内提前生成；
- 首批生成后即可物化，不需要等待全部计划生成；
- 运行终结后窗口继续补充；
- 暂停后生成游标不前进，恢复后无重复 Trial；
- 取消时未生成部分正确计入 `cancelled_before_generation`；
- 聚合修复只修复实际在途计数；
- 阶段 A/B 迁移均可重复执行；
- 删除字段后所有查询、RLS 策略和协调器循环正常。

### 8.3 前端测试

- 大计划预览成功后可以创建；
- 预计 Bar 和资源等级以提示而非阻塞显示；
- 单维度超限仍在当前操作区域显示错误；
- 创建中的重复点击只发送一次请求；
- 不支持 `crypto.randomUUID()` 的内网 HTTP 浏览器仍可提交；
- TypeScript 检查、Vitest 和正式构建通过。

### 8.4 远程普通用户样本回归

本次修改涉及实验提交、调度、执行和结果生成。按仓库规则，本地自动化测试完成后必须：

1. 只读取得服务器普通用户最近两条相关回测的保存代码和运行快照；
2. 在隔离的正常实验/Worker 链路验证预览、创建、滚动生成、排队、领取、执行和结果生成；
3. 验证历史实验详情与 `budget_v2` 快照仍可读取；
4. 不修改原生产任务，不把用户代码或快照写入仓库、文档或对话；
5. 条件不满足时明确标记“远程普通用户样本回归待验证”，不得声称已通过。

## 九、服务器发布顺序

该改造影响后端、实验协调器、前端接口展示和数据库结构，必须同批发布相互依赖的服务，不能只重启后端。

推荐顺序：

1. 检查排队和运行中的普通 Bar/L2 任务以及自动化实验；
2. 暂停实验协调器，阻止继续生成和物化新 Trial；
3. 等待现有运行任务完成，或由用户明确取消；
4. 使用 `scripts/deploy-server.sh` 发布阶段 A 代码和迁移；
5. 验证健康检查、预算 v3、新大计划、历史实验和真实并发；
6. 手动从服务器私有 `deploy/.env` 删除三个旧变量；
7. 观察字段不再变化并核对外部依赖；
8. 后续发布阶段 B 删除数据库字段；
9. 再次执行历史兼容和普通用户样本回归。

如果一键发布仍被自动化实验持续产生的任务阻塞，应先停止实验协调器并让现有任务排空，不得绕过迁移只重建单个服务。

## 十、风险与控制

### 10.1 超大计划长期占用存储

取消逻辑总量上限后，已完成 Trial 和结果仍会长期累积。滚动窗口只能限制提前生成和同时执行，不能消除历史结果增长。必须配合存储监控、高水位暂停、用户主动取消以及既有归档/清理能力。

### 10.2 协调器忙循环

当窗口已满、调度容量耗尽或存储高水位触发时，候选查询必须返回无工作并遵循现有轮询间隔，不能持续领取同一 Stage 形成忙循环。

### 10.3 状态机和聚合计数偏差

生成与执行交错后，`generated_trial_count < planned_trial_count` 将成为正常运行状态。所有完成判断、恢复修复、详情计数和前端进度都必须移除“未全部生成等于异常”的隐含假设。

### 10.4 数据库字段删除后的回退

阶段 B 是收缩性迁移。执行后不能直接回退到读取旧字段的版本，因此必须先完成阶段 A 观察，并准备前向修复方案。

### 10.5 旧变量残留造成运维误判

仓库示例和服务器私有 `.env` 都必须删除三行。只在代码中忽略而保留配置会继续制造“改了上限为什么没生效”的问题。

## 十一、验收标准

全部满足以下条件后，本方案才算完成：

1. 仓库代码和 `deploy/.env.example` 不再读取或声明三个旧变量；
2. 服务器私有 `deploy/.env` 已删除三个旧变量；
3. 大于旧阈值的完整有限计划能够作为一个 Experiment Revision 预览和创建，不需要用户拆分参数；
4. 创建后的 `plannedTrialCount` 与完整笛卡尔积一致，没有静默截断、抽样或自动拆分；
5. 同一 Revision 内可以对全部候选结果执行统一评价和排序；
6. 预计 Bar 总量只影响资源等级与提示；
7. `experiment.plan_limit_exceeded` 已从实现、测试、使用手册和 API 文档删除；
8. 预览编译次数与 Trial 总量无关并保持固定上界；
9. Trial 生成和物化采用有界滚动窗口，不再预生成完整计划后才执行；
10. 实际并发、用户在途、公平调度和普通任务保留容量仍有效；
11. 数据类型溢出和单维度异常输入仍被拒绝；
12. 历史 `experiment_budget_v2` 和历史实验可以读取且不被旧上限阻塞；
13. 用户计划额度预留、释放、重试恢复和修复逻辑全部删除；
14. `reserved_planned_trial_count` 与 `plan_quota_released_at` 完成两阶段下线并最终删除；
15. 存储高水位暂停机制的真实来源和恢复行为已验证；
16. 本地后端、PostgreSQL 集成、前端检查和正式构建通过；
17. 远程普通用户两条样本回归通过，或如实记录待验证原因；
18. 发布后健康检查、新功能回测、历史兼容检查和任务恢复验证均有真实结果。

## 十二、完成定义

“删除三个环境变量”不是本方案的完成定义。最终完成状态是：

- 用户可以提交任意未发生数据类型溢出的有限笛卡尔积计划；
- 一次完整参数验证由一个 Experiment Revision 承载，不需要人为拆分成多个实验；
- 系统不会因为 Trial 总数、用户计划总量或预计 Bar 总量拒绝创建；
- 系统通过有界预览、有界滚动生成、实际并发门禁和存储压力暂停保护资源；
- 历史快照仍可解释，新旧语义不会互相污染；
- 运维界面和 `.env` 中不再存在看似可调、实际无效的逻辑计划配额。
