# 自动化回测逻辑计划配额移除方案

## 一、文档状态

- 状态：待实施
- 适用范围：标准 Bar 自动化实验的预览、创建、Trial 生成、任务物化、暂停、恢复、取消、重试、结果评价、数据库迁移、存储探针、前端提示和公开 API 文档
- 基线：`develop` 分支 `b71a786`
- 不包含：提高实际回测并发、提高 Runner 副本数、开放自动化 L2、改变实验结果和评价口径

## 二、背景与问题

当前自动化实验同时存在三类由部署环境变量控制的逻辑计划硬上限：

```text
TREND_GRID_EXPERIMENT_MAX_TRIALS
TREND_GRID_EXPERIMENT_MAX_USER_PLANNED_TRIALS
TREND_GRID_EXPERIMENT_BAR_MAX_ESTIMATED_BARS
```

它们分别限制单个实验 Trial 总数、单用户未完成实验的计划 Trial 总数和预计 Bar 总量。这些限制会直接决定预览能否通过、实验能否创建以及运行阶段能否继续物化任务。

该设计把“逻辑计划规模”和“当前实际资源消耗”混为一体。参数网格的笛卡尔积很容易超过固定阈值，但计划规模大并不等于系统会同时执行同等数量的任务。真正需要保护的是并发执行槽位、待物化缓冲窗口、数据库与磁盘压力，而不是用部署变量拒绝一个有限且可暂停的逻辑计划。

更直接的业务问题是：如果用户的一次完整参数验证超过固定上限，当前系统会要求用户手工删减候选值，或者把同一个搜索空间拆成两个甚至更多实验。这样虽然绕过了上限，却破坏了“一个实验代表一次完整验证意图”的边界：候选结果无法在同一 Revision 内统一评价和排序，进度、暂停、恢复、取消及审计被拆散，人工分段还可能遗漏或重复组合。用户为了验证完整参数空间，不应承担这种由部署配额造成的实验拆分成本。

因此本方案取消上述三项业务配额，改为：

> Trial 总数和预计总工作量不再由 `.env` 决定是否允许创建；`.env` 只负责实际运行容量和技术安全保护。

同时坚持：

> 一个完整参数搜索空间应当保存在一个 Experiment Revision 中；资源容量只影响完成速度和暂时能否继续推进，不改变用户实验的逻辑边界。

## 三、现状核对与必要补充

### 3.1 当前限制链路

现有实现中的限制并非只存在于 `backend/settings.py`，而是贯穿完整生命周期：

1. `backend/settings.py` 读取三个变量，并在实验开关开启时校验单实验上限和用户计划上限的关系；
2. `backend/experiments/application.py` 在预览中以 Trial 总数和预计 Bar 总量形成硬阻塞；
3. 创建事务通过 `reserved_planned_trial_count` 串行预留用户计划额度，超限返回 `experiment.plan_limit_exceeded`；
4. 运行阶段根据当前配置、历史预算快照和已预留计划量再次阻塞实验；
5. 实验终结、恢复和失败重试会释放或重新预留计划额度；
6. `experiment_budget_v2` 快照固化三个旧上限并参与 `budgetDigest`；
7. 前端、测试、使用手册和 API 文档均依赖旧门禁语义。

删除三个设置读取但保留其余链路，会形成启动错误、运行时属性不存在、历史实验永久阻塞或配额缓存漂移，因此必须按完整契约改造。

### 3.2 当前“分批生成”不是滚动缓冲

当前 `TREND_GRID_EXPERIMENT_GENERATION_BATCH_SIZE` 只限制单次事务写入的 Trial 数量。Stage 仍需先生成全部 `backtest_experiment_trial` 记录，才从 `preparing` 进入 `queued`，任务物化也要求：

```text
generated_trial_count == planned_trial_count
```

因此只删除总量上限会把问题从“创建被拒绝”转移为“协调器持续预生成全部 Trial 并占满 PostgreSQL”。这不满足“不限制逻辑计划规模、只限制实际资源”的目标。

本方案必须同时把生成与执行改为滚动补充：逻辑计划可以很大，但未执行的已生成 Trial 数量始终有界；已完成 Trial 作为实验结果仍会累积保存，并由磁盘高水位机制决定是否暂停继续生成。

### 3.3 当前预览会遍历全部组合

当前预览在门禁允许时会编译全部 Trial，只在门禁拒绝时才抽取首尾样例。取消总量门禁后，该行为会使大网格预览占用与 Trial 总量线性增长的 CPU 和内存。

预览必须改成：完整校验输入维度和每个候选值，但只编译固定数量的代表性组合。预览耗时和内存不得随笛卡尔积总量线性增长。

### 3.4 存储压力不能由单一数据库大小代表

当前仓库可以确认存在分批生成和在途并发门禁，但没有自动化实验专属的存储压力聚合门禁。`pg_database_size()` 只能说明 PostgreSQL 的逻辑占用，不能代表 PostgreSQL 数据卷剩余空间，也不能覆盖 `OUTPUT_ROOT` 等结果产物卷；把它单独当作磁盘权威信号会在逻辑大小尚未越线时耗尽物理卷，或者在卷仍有充足空间时误停系统。

因此本方案补建统一的 `StoragePressureGate` 模块和专用只读 `storage-probe` Sidecar。Sidecar 只暴露挂载卷标识、可用字节数、总字节数和采样时间，不持有数据库账号，也不提供文件读取接口；门禁聚合 PostgreSQL 逻辑占用、PostgreSQL 数据卷可用空间、结果产物卷可用空间和信号新鲜度，使用高低水位形成迟滞控制。存储压力只暂停新 Trial 生成和新任务物化，不改写计划规模、不删除结果，也不把实验标记为失败；取消、查询、归档和清理能力必须始终可用。

### 3.5 当前取消链路存在但命令契约不足

当前系统已经提供实验取消接口、前端“取消实验”按钮和后端收敛逻辑。取消会停止继续生成 Trial，将未物化 Trial 标记为取消，并通过普通回测取消链路处理已提交任务；已完成结果继续保留。

现有实现仍有以下缺口：

1. 前端点击后直接发送请求，没有不可逆操作确认；
2. 请求只携带 Experiment ID，没有 `expectedRevisionId` 和独立的生命周期版本，旧页面可能误取消后来创建的 Revision；
3. 没有记录用户取消原因；
4. 浏览器每次点击生成新的幂等键，网络结果不明确时不能用同一键安全重放；
5. 接口没有明确区分“已接受取消”和“全部任务已经取消完成”。

当前详情中的 `snapshotVersion` 会随 Trial 生成、任务终结和聚合刷新递增，不能作为暂停或取消的乐观并发条件，否则用户仅因正常进度推进就会频繁冲突。本方案引入只在生命周期命令和当前 Revision 替换时递增的 `lifecycleVersion`，并通过新的版本化命令契约补齐确认、稳定幂等、审计和异步状态展示。现有公开 `/api/v1` 接口只作为有期限的兼容桥，不把弱契约永久延续到新能力。

### 3.6 当前恢复接口不等于用户暂停/恢复

现有 `/resume` 只允许解除 `experiment.execution_blocked` 执行熔断，系统没有用户主动暂停命令，也没有 `pausing`、`paused` 生命周期。方案原文所称“暂停后恢复”目前并不存在，不能继续把系统熔断恢复描述成用户暂停恢复。

大计划取消配额后，用户需要一种不丢弃当前 Revision、也不取消已运行结果的临时止流能力。本方案因此新增正式的用户暂停/恢复语义，并继续保留执行熔断解除语义。暂停、系统阻塞、执行阶段和终态结果不能继续挤进同一个 `status` 字段；新契约使用正交状态轴表达，旧 `status` 仅在兼容期作为派生投影。

### 3.7 冻结容量不应成为运行硬门禁

当前 `resource_budget.capacityPolicy` 会保存创建时的并发容量，运行阶段再与当前设置比较。只要当前容量低于创建时快照，Revision 就可能进入 `experiment.capacity_blocked`。这种行为会把正常的运维缩容变成需要人工恢复的实验阻塞。

并发容量、用户在途容量和手工任务保留容量都是动态运行资源，应在每次领取和物化时按当前值计算可用许可。容量缩小只会降低推进速度或暂时不发放新任务，不得写入持久化阻塞原因，也不得要求用户恢复。创建时容量如需留作诊断，只能作为不参与 `budgetDigest` 和准入判断的观测信息。

### 3.8 资源估算失败不能继续阻止创建

当前估算器在行情覆盖元数据不足或周期无法可靠换算时返回 `experiment.capacity_unavailable`，使预览直接失败。既然预计 Bar 和资源等级在新语义下只用于提示，估算不可用也不能继续充当隐藏准入门禁。

新契约必须允许估算结果为 `unavailable`：预览仍完成输入校验和固定样例编译，返回“暂时无法估算耗时”的警告；实际执行继续受真实并发和存储压力保护。只有数据快照本身无法解析、回测请求无法编译等真实执行前置条件失败时，才阻止创建。

### 3.9 计划总数还受跨端精确整数边界约束

数据库 `bigint` 可以表示到 `2^63 - 1`，但当前 JSON 和 TypeScript 契约使用 `number`，只能精确表示到 `2^53 - 1`。若只保留数据库边界，前端展示、快照版本比较和请求回传会发生静默舍入。

本方案不在本次改造中把所有计数字段迁移为十进制字符串，因此计划总数的技术上限统一为 `Number.MAX_SAFE_INTEGER`，即 `9,007,199,254,740,991`。该边界用于保证跨端精确表达，不是业务配额；未来若确有更大规模需求，必须通过版本化 API 将计数字段迁移为十进制字符串后再提高边界。

### 3.10 评价完整性仍会展开整个逻辑计划

当前评价完整性构建会对 `range(planned_trial_count)` 逐项查找缺失 Trial，并为每个未生成索引生成一条异常。取消总量配额后，取消或部分完成的大计划会在评价阶段重新产生与逻辑总量线性相关的 CPU、内存和响应体开销。评价执行还会一次性载入 Trial 结果，规模增大后同样可能耗尽 Worker 内存。

因此滚动化不能只改生成协调器。完整性统计必须改为数据库聚合，未生成逻辑区间必须压缩表达；评价执行集合和行级结果必须进入规范化表，由数据库冻结、Worker 流式读取、接口分页输出，不能继续把全部执行集合或结果塞进单个 JSON。仓库中所有按 `planned_trial_count` 全量展开的调用都必须完成审计。

### 3.11 活动实验不能依靠停机后自然消失

发布时可能同时存在已全部生成、部分生成、窗口占用超出新阈值、旧容量阻塞、暂停中或取消中的 Revision。若不定义迁移矩阵，新代码会把历史正常状态误判为损坏，或要求用户重建实验，违背历史快照兼容原则。

本方案必须为每类活动 Revision 定义可重复执行的接管规则：已生成数据不删除，部分生成从原游标继续，窗口超量只停止补充等待自然回落，旧瞬时阻塞原因清除后重新计算，取消中的任务继续收敛，所有 Trial 身份、摘要和结果保持不变。

### 3.12 长期方案需要稳定的深模块

配额删除会同时触及生命周期、生成容量、存储压力和评价执行。若这些规则继续散落在路由、协调器循环和仓库方法中，每次新增状态都会形成新的组合分支。本方案把复杂度集中到四个深模块：

1. `ExperimentLifecycleCommands`：统一暂停、恢复、取消的授权、幂等、并发控制、状态转换和审计；
2. `RollingTrialWindow`：内部选择公平候选，原子生成 Trial，并管理实验、用户和全局滚动窗口、终态释放、重试重开与漂移修复；
3. `StoragePressureGate`：聚合多种存储信号、迟滞判断、故障安全和可观测状态；
4. `EvaluationDataset`：冻结评价输入、流式计算、持久化行级结果和分页导出。

路由、协调器和 Worker 只能调用这些模块的窄接口，不得复制内部判断。测试以模块接口为主要验证面，避免未来实现重构时反复改写大量调用方测试。

## 四、目标与非目标

### 4.1 目标

1. 删除三个逻辑计划上限环境变量的读取、校验、示例配置和服务器私有配置；
2. 用户的一次完整参数验证可以作为单个 Experiment Revision 创建，不需要为绕过上限手工删减或拆分参数；
3. Trial 总数只受有限网格定义和当前跨端精确整数范围约束，不受业务配额约束；
4. 预计 Bar 总量只用于资源等级和耗时提示，不参与预览、创建或运行准入；
5. 删除用户计划额度的预留、释放、修复和重试恢复逻辑；
6. 生成、物化和执行形成有界滚动窗口，避免大计划一次性写入全部 Trial；
7. 保留实际并发、公平调度、手工任务保留容量和用户在途上限；
8. 历史 `experiment_budget_v2` 快照继续可读，但旧字段不再影响调度；
9. 补齐用户暂停/恢复和取消命令契约，保持重试和结果评价对大计划有效；
10. 评价统计和异常明细不展开尚未生成的逻辑尾部，成功结果分批处理且仍统一评价；
11. 删除 `experiment.plan_limit_exceeded` 公开错误契约；
12. 以正交状态轴取代不断扩张的单一状态枚举，避免暂停、系统阻塞、执行进度和终态结果互相污染；
13. 通过四个深模块收口生命周期、滚动容量、存储压力和评价数据集复杂度；
14. 为活动 Revision、旧公开接口和历史评价结果提供明确、可退出的兼容路径。

### 4.2 非目标

1. 不把“取消计划配额”解释为无限并发；
2. 不调整 `BACKTEST_BASE_CONCURRENCY`、突发并发或 Runner 副本；
3. 不删除 `TREND_GRID_EXPERIMENT_MAX_VALUES_PER_DIMENSION`；
4. 不删除请求体数组长度、字段长度、数据库数值类型或跨端精确整数保护；
5. 不改变 Trial 指纹、随机种子、回测请求、成交、收益或评价口径；允许为可扩展性升级评价异常明细的传输结构，但必须版本化并兼容历史结果；
6. 不自动清理历史 Trial、运行结果或评价产物；
7. 不由服务端自动截断、抽样或拆分用户提交的完整参数搜索空间；
8. 不在本次改造中开放自动化 L2；
9. 不把实验取消自动扩散到已经冻结的评价或导出任务；评价和导出拥有独立生命周期及取消命令；
10. 不以永久兼容为理由继续扩展 `/api/v1`，新生命周期能力只进入版本化的新契约。

### 4.3 业务目标追踪与防跑偏规则

| 原始业务目标 | 必须落地的设计 | 验收入口 |
| --- | --- | --- |
| 用户无需为了固定上限删参数或拆成多个实验 | 删除三个总量门禁；完整有限网格保存为一个 Revision；禁止自动拆分、截断或抽样 | 11.3—11.10 |
| 计划规模不等于同时消耗的资源 | `RollingTrialWindow`、真实执行并发和动态容量只控制推进速度 | 11.11—11.13、11.20 |
| 参数填错后不会让旧实验长期堵住新工作 | 用户暂停/恢复、不可逆取消、取消后复制为新实验、旧任务按真实占用自然收敛 | 11.15—11.18 |
| 同一次完整验证仍能统一评价和排序 | 同一 Revision 保存全部结果；`EvaluationDataset` 流式处理全部符合条件结果 | 11.5、11.21—11.23 |
| 不把无限逻辑计划风险转移成数据库、内存或磁盘事故 | 有界预览、三级滚动窗口、多信号存储门禁、分页/流式评价 | 11.9、11.20—11.22、11.28 |
| 历史任务和公开调用方不因改造失效 | 预算快照兼容、活动 Revision 接管、v1 限期桥接、分波次发布 | 11.24—11.29、11.33 |

实施过程中出现以下任一变化，均视为偏离本方案，必须停止实施并重新取得业务确认：

1. 以新的环境变量、数据库字段或前端阈值限制单实验 Trial 总数、单用户计划总量或预计 Bar 总量；
2. 为降低实现难度而自动截断、抽样或拆分用户提交的参数笛卡尔积；
3. 只删除创建门禁，却保留运行阶段旧预算阻塞、计划额度预留或全量预生成；
4. 以“暂停/取消可用”为理由减少应参与同一 Revision 评价的成功结果；
5. 把动态容量等待、系统存储压力和用户暂停重新合并成一个含义不清的持久状态；
6. 未满足当前发布波次的退出条件就提前删除兼容字段、旧接口或服务器回退材料。

## 五、目标约束

改造后的系统必须同时满足以下不变量：

1. **逻辑计划有限但不设业务总量上限**：`planned_trial_count` 必须大于 0，且不得超过当前 JSON/TypeScript 精确整数上限 `2^53 - 1`；超过时返回 `experiment.validation_failed`，该技术边界不得配置成业务阈值；
2. **完整验证意图不拆分**：一次提交的全部候选组合保存在同一 Experiment Revision 中，由同一评价、进度和生命周期管理；
3. **单维度输入有界**：继续使用 `TREND_GRID_EXPERIMENT_MAX_VALUES_PER_DIMENSION` 限制规范化去重后的单维度候选值数量；请求模型现有数组长度和字段长度限制继续独立保护原始请求体，二者都不得按笛卡尔积总量判断；
4. **预览复杂度有界**：预览只生成固定的首尾代表样例，不遍历全部组合；
5. **待执行窗口有界**：按实验、用户和全局三个作用域限制“已生成但未终结”的 Trial；已终结结果不占滚动窗口，逻辑上尚未生成的 Trial 不占任何运行额度；
6. **实际并发有界**：统一调度器、实验级在途上限、用户级在途上限和普通任务保留容量继续生效；
7. **存储压力可暂停**：达到磁盘高水位时由系统自动停止生成和物化，降至恢复水位后自动继续；系统存储门禁与用户暂停使用不同原因码和审计事件；
8. **身份确定性不变**：同一冻结 Stage 的 `trialIndex`、维度赋值、指纹和种子不因批次或暂停恢复而变化；
9. **历史只读兼容**：旧预算字段可以展示或导出，但不能重新成为门禁；
10. **取消不依赖预生成**：取消大计划时，未生成区间通过 `cancelled_before_generation` 计入终态，不要求补生成 Trial 行；
11. **用户暂停可恢复**：暂停不取消运行中的普通回测，停止新生成和新物化，待在途任务自然终结后进入 `lifecycleState=paused`；恢复后从原游标继续；
12. **取消不可恢复但保留证据**：取消当前 Revision 后不得恢复该 Revision，已完成结果、参数快照、取消原因和审计记录必须保留；
13. **运行容量动态生效**：当前实际容量只控制下一次是否发放工作，不与创建时容量快照比较，不形成需要人工解除的持久化阻塞；
14. **状态正交**：生命周期、执行阶段、系统阻塞和终态结果分别存储；兼容 `status` 必须由统一投影函数计算，调用方不得自行拼接优先级；
15. **命令并发稳定**：暂停、恢复和取消使用独立 `lifecycleVersion`，普通进度更新不得制造生命周期命令冲突；
16. **窗口占用原子**：生成前必须先原子预留三级窗口，批次提交时在同一事务把预留转换为开放 Trial 并推进游标；Trial 从开放进入终态、失败重试重新开放时，Trial 状态和三级账本必须原子提交；
17. **存储信号完整**：逻辑占用、数据库卷和产物卷均有权威信号；必需信号缺失或过期时停止新工作但不影响取消和清理；
18. **评价数据有界**：冻结输入、计算和导出的内存及单次响应上界由批量或分页大小决定，不由完成 Trial 总数决定；
19. **兼容路径可退出**：所有双写、旧接口桥接和旧列保留都有观测指标、下线条件和最终删除步骤。

### 6.1 设置与部署配置

从 `backend/settings.py` 删除：

```text
EXPERIMENT_MAX_USER_PLANNED_TRIALS
EXPERIMENT_BAR_MAX_ESTIMATED_BARS
```

以下配置继续保留：

- `TREND_GRID_EXPERIMENT_MAX_VALUES_PER_DIMENSION`：输入结构保护；
- `TREND_GRID_EXPERIMENT_GENERATION_BATCH_SIZE`：单次生成事务的批量大小；
- `TREND_GRID_EXPERIMENT_MAX_IN_FLIGHT_PER_EXPERIMENT`：实验实际在途任务上限；
- `TREND_GRID_EXPERIMENT_MAX_IN_FLIGHT_PER_USER`：用户实际在途任务上限；
- `TREND_GRID_EXPERIMENT_MANUAL_RESERVED_PERMITS`：普通手工回测保留容量；
- 统一回测调度容量及公平调度配置。

新增服务器实际存储容量配置，名称明确区分“逻辑占用阈值”和“物理剩余空间阈值”：

- `TREND_GRID_EXPERIMENT_POSTGRES_LOGICAL_HIGH_WATER_BYTES` 与 `TREND_GRID_EXPERIMENT_POSTGRES_LOGICAL_LOW_WATER_BYTES`：数据库逻辑占用高水位和恢复水位；
- `TREND_GRID_EXPERIMENT_POSTGRES_VOLUME_MIN_FREE_BYTES` 与 `TREND_GRID_EXPERIMENT_POSTGRES_VOLUME_RESUME_FREE_BYTES`：PostgreSQL 数据卷进入压力和恢复所需的可用空间；
- `TREND_GRID_EXPERIMENT_ARTIFACT_VOLUME_MIN_FREE_BYTES` 与 `TREND_GRID_EXPERIMENT_ARTIFACT_VOLUME_RESUME_FREE_BYTES`：`OUTPUT_ROOT` 结果产物卷进入压力和恢复所需的可用空间；
- `TREND_GRID_EXPERIMENT_STORAGE_SIGNAL_MAX_AGE_SECONDS`：`storage-probe` 存储信号允许的最大陈旧时间。

这些配置属于部署容量，不是逻辑工作量配额。逻辑水位满足 `0 < LOW < HIGH`，物理卷水位满足 `0 < MIN_FREE < RESUME_FREE`。未配置、数值非法或必需探针过期时采用故障安全行为，仅关闭自动化实验的新生成和新物化，并通过健康检查和运维指标报告具体缺失信号，不影响服务启动、普通回测、取消命令、归档清理和历史读取。不得用一个看似通用的 `STORAGE_HIGH_WATER_BYTES` 同时解释逻辑大小和物理剩余空间。现有 `TREND_GRID_EXPERIMENT_EXPORT_MIN_FREE_BYTES` 继续保护单次导出写入；产物卷聚合门禁使用新全局阈值，导出时取两者中更严格者，避免两个设置互相绕过。

### 6.2 预览与输入校验

`backend/experiments/application.py` 的预览逻辑调整为：

1. `_limit_decision()` 只保留规范化后单维度候选值数量门禁；请求模型已有的原始数组长度、字段长度和类型校验继续在进入生成器前执行；
2. 删除 `trial_limit_exceeded` 和 `bar_budget_exceeded`；
3. 预计 Bar 无论大小都不进入 `blockingReasons`；为避免预计值本身超过 JavaScript 精确整数范围，新增权威十进制字符串 `estimatedBarCountExact`，旧 `estimatedBarCount` 仅在安全整数范围内返回数值，否则返回 `null`；
4. `resourceClass=heavy` 继续返回 `high_resource_estimate` 警告，并明确它只是耗时/资源提示；
5. 估算器因覆盖元数据不足而无法可靠估算时，不再抛出阻止创建的 `experiment.capacity_unavailable`，而是返回 `estimateStatus=unavailable`、`estimatedBarCount=null`、`estimatedBarCountExact=null`、`resourceClass=unknown` 和 `resource_estimate_unavailable` 警告；
6. `_examples()` 始终使用固定首尾样例索引，不再因 `allowed=true` 遍历 `range(planned_trial_count)`；
7. 每个维度及每个候选值仍由生成器完整规范化和校验；跨维度组合只编译固定样例，实际批次生成时继续执行权威编译；
8. `_safe_product()` 将常量改为 `2^53 - 1` 并在每次乘法前执行除法式溢出判断，避免先构造超大整数；超过时返回 `experiment.validation_failed`，错误详情说明这是跨端精确整数边界而非业务配额；
9. `dimension_counts` 使用规范化去重后的数量；`dimension_normalization.submitted` 继续展示提交数量，使用户可以看到重复值被折叠，但单维度门禁不得把笛卡尔积总数当成某个维度数量。

创建和创建新 Revision 时，如果预览因单维度输入保护不允许创建，统一返回现有的 `422 experiment.validation_failed` 并携带 `blockingReasons`，不再返回 `429 experiment.plan_limit_exceeded`。

### 6.5 滚动 Trial 生成与物化

目标状态不再要求“全部生成后才能执行”。候选选择、Trial 生成和三级窗口规则全部收口到 `RollingTrialWindow` 模块；协调器只负责触发一次推进并处理返回结果，不得传入指定 Stage 绕过公平性，也不得自行读取几个计数后拼装判断。

模块提供三个核心接口：

```text
generateNextBatch(batchLimit, now) -> GeneratedBatch | NoWork
settleTrial(trialId, terminalTransition, eventId, now) -> SettlementResult
requestRetry(trialId, eventId, now) -> RetryDecision
```

`generateNextBatch` 隐藏一个带超时令牌的两段式实现，避免在数据库锁内执行编译：第一段事务选择下一公平用户和 Experiment，校验候选、按固定顺序加锁并原子预留三级窗口；随后在事务外编译有限批次；第二段事务重新校验令牌、生命周期和游标，把预留占用转换为 Trial 行、推进游标并更新摘要。编译失败、取消竞争或令牌过期时幂等释放预留；协调器崩溃后的过期预留由回收器释放。`NoWork` 属于正常等待，并携带可观测原因而不是抛出错误。`settleTrial` 只允许把非终态 Trial 转为终态并同步扣减账本，`eventId` 保证重复终结幂等。`requestRetry` 在同一事务内重新取得窗口许可并重开失败 Trial；取得失败时返回等待决定，不得先改 Trial 再补计数。

协调器推进顺序为：

```text
调用 RollingTrialWindow.generateNextBatch
  → 原子预留三级窗口并取得生成令牌
  → 事务外编译有限批次
  → 原子将预留转换为 Trial、游标、摘要和开放占用
  → 立即允许物化已生成 Trial
  → Trial 终结时原子释放窗口占用
  → 窗口出现余量时继续生成
```

滚动窗口使用以下权威计数：

```text
open_generated_trial_count = 已生成且当前不处于 succeeded / failed / cancelled 的 Trial 数
reserved_generation_count  = 已由有效生成令牌预留但尚未提交 Trial 的数量
window_occupancy           = open_generated_trial_count + reserved_generation_count
```

未生成且未预留的逻辑尾部不占窗口；已经终结但为了结果和审计继续保存的 Trial 行也不占窗口。窗口上限不新增逻辑计划配额变量，而是由现有实际资源参数确定：

```text
experiment_window = generation_batch_size + max_in_flight_per_experiment
user_window       = generation_batch_size + max_in_flight_per_user
global_window     = generation_batch_size + current_automation_execution_capacity
```

其中 `current_automation_execution_capacity` 是统一调度有效容量扣除普通手工任务保留许可后的非负值。每次生成数量为单批上限、逻辑剩余量以及实验、用户、全局三个窗口剩余量的最小值。

账本至少持久化 Stage、用户和全局三个层级的开放占用与生成预留，并保存生成令牌、预留数量和过期时间。所有事务固定按“全局 → 用户 → Stage”加锁，避免多协调器发生锁顺序反转；Trial 行与有效生成令牌是最终事实，账本是受约束的快速索引。后台对账器按相同定义从 Trial 和有效令牌聚合修复漂移，并记录修复前后差值，不能静默覆盖。

公平性不能只依赖 `created_at`。账本维护持久化的用户轮转序号和用户内 Experiment 轮转序号：先在有余量的用户之间轮转，再在该用户的活动 Experiment 之间轮转。进程重启或多个协调器切换后仍应延续次序，单个超大计划不得通过更频繁轮询独占全局窗口。

核心规则：

1. Stage 在首批 Trial 成功提交后即可进入可物化状态，不等待 `generated_trial_count == planned_trial_count`；
2. `_can_materialize()` 删除“必须全部生成”的条件，只要求目标 Trial 已持久化、未取消、未终结且容量允许；
3. 生成候选按持久化用户和 Experiment 序号公平轮转，单个超大计划不得连续填满全局窗口；
4. 领取生成令牌和增加预留占用在第一段事务完成；写入 Trial、推进 `generation_cursor`、更新摘要以及从预留占用转换为开放占用在第二段事务完成；
5. 当前容量为零、窗口无余量、用户暂停、取消中、系统存储门禁开启或执行熔断时，本轮不生成且遵循正常轮询退避，不能形成忙循环；
6. `generation_cursor` 仍是下一逻辑 Trial 索引，租约、CAS 和增量摘要语义不变；
7. `trial_collection_digest` 在全部逻辑 Trial 已生成后才冻结；在此之前使用 `incremental_collection_digest` 恢复；
8. 计划执行完毕的判断同时要求逻辑生成完成、无在途任务且所有已生成 Trial 终结；
9. 取消时不生成剩余 Trial，直接将未生成数量计入 `cancelled_before_generation`；
10. 暂停只停止新生成和新物化，不取消已经运行的普通回测；
11. 恢复从原 `generation_cursor` 和未终结 Trial 继续，不重复生成或跳号；
12. 手工重试使失败 Trial 重新进入非终结状态前，必须先由账本原子取得窗口许可；没有许可时等待而不是超发；
13. Trial 终态转换、账本释放和实际执行槽释放使用同一幂等事件标识，重复投递不能重复扣减；生成令牌回收同样必须幂等；
14. `RollingTrialWindow` 直接通过 PostgreSQL 集成测试验证同一公开接口，不为唯一数据库实现额外暴露浅层仓库接口；公平时钟等可变依赖使用模块内部测试缝替换。

需要同步校正详情接口中的计数语义：

- `plannedTrialCount`：逻辑总数；
- `generatedTrialCount`：已经持久化的 Trial 数；
- `inFlightTrialCount`：已物化且未终结的实际任务数；
- `readyTrialCount`：已生成但尚未物化的 Trial 数；
- `remainingLogicalTrialCount`：`plannedTrialCount - generatedTrialCount`，表示尚未生成的逻辑尾部；
- `queuedTrialCount`：仅表示已经物化并处于普通回测排队状态的 Trial，不再混入尚未生成的逻辑工作量。

### 6.6 运行阶段门禁

删除“创建时预算与当前容量比较”的 `_budget_capacity_gate()` 语义。运行状态改为四个正交轴：

```text
lifecycleState: active | pausing | paused | cancelling | terminal
executionPhase: preparing | queued | running | blocked | settled
systemBlockCode: null | storage_pressure | automation_disabled | execution_circuit | ...
terminalOutcome: null | completed | partially_completed | failed | cancelled
```

Revision 是生命周期状态的唯一写入源，Stage 保存执行阶段和 Revision 级持久阻塞，Experiment 只缓存当前 Revision 的查询投影；全局存储压力保留在门禁单例表，不复制到每个 Stage。v2 的 `systemBlockCode` 由 Revision 级阻塞、全局门禁和管理员开关统一投影，新前端只使用四个状态轴生成展示文案。

兼容 `status` 必须严格限制在旧客户端已经认识的枚举集合，不得返回新增的 `pausing` 或 `paused`：终态结果映射到旧终态，`cancelling` 映射到旧 `cancelling`，有在途任务的 `pausing` 暂按旧执行阶段显示，`paused` 映射为旧 `generation_blocked` 并附带只读原因，系统阻塞按既有可识别阻塞状态映射，其余使用 `executionPhase` 对应旧值。该映射只为旧读契约服务，旧 `/resume` 仍不能解除用户暂停。路由、前端和协调器不得各自复制映射。存储压力不会把用户的 `lifecycleState` 改成 `paused`，用户恢复也不能清除系统阻塞。

运行阶段按以下三类处理：

1. **瞬时等待**：实验级/用户级/全局在途容量耗尽、普通手工任务保留、手工任务等待优先级或滚动窗口已满。本轮不发放工作，但不写 `blocked_reason_code`，容量释放后自动继续；
2. **系统自动暂停**：存储高水位或管理员暂时关闭自动化执行。停止新生成和新物化，保留持久化游标和已有结果；恢复信号满足后自动继续，并记录系统暂停/恢复审计；
3. **需要人工处理的阻塞**：用户被冻结、资产不可用或连续系统性错误触发执行熔断。记录明确 `systemBlockCode`；只有原因消除且用户发出对应的解除熔断命令后才继续。

动态容量收紧属于第一类，不能设置 `experiment.capacity_blocked`。现有 `experiment.capacity_blocked` 若仅由旧冻结预算比较产生，部署迁移后清除；若来自其他真实阻塞来源，映射到上述明确原因码，不能继续使用含义混杂的通用原因。

`StoragePressureGate` 提供单一查询接口：

```text
evaluate(now) -> open | pressured(reasons, observedAt) | unknown(missingSignals)
```

其内部 Adapter 读取 PostgreSQL 逻辑大小，并通过内部网络调用专用只读 `storage-probe` Sidecar 获取 PostgreSQL 数据卷和 `OUTPUT_ROOT` 产物卷的文件系统可用空间。Sidecar 以只读方式挂载两个卷，使用最小权限运行，只返回 `statvfs` 类容量数据。模块将最新观测持久化到单例状态表，使多个协调器读取相同门禁结论，并对每个信号独立应用迟滞。任一必需信号进入压力状态时整体为 `pressured`；信号缺失或超过最大陈旧时间时整体为 `unknown`，对新生成和新物化按关闭处理。只有所有信号回到恢复区间且保持最新，整体才重新开放。

存储门禁自动恢复只代表允许继续推进，不代表空间问题已经解决。取消不会删除已完成结果；当压力来自累计历史数据时，运维必须通过独立的归档/保留期清理或扩容解除。门禁健康状态必须同时报告每个信号的值、阈值、采样时间和最终决定，避免只返回一个无法定位原因的布尔值。

以下内容不得再阻塞：

- 计划 Trial 总数；
- 用户所有未完成实验的计划总数；
- 预计 Bar 总量；
- 历史 `budget_v2` 中上述字段比当前值大。

### 6.7 用户暂停、恢复与取消

暂停、恢复和取消统一由 `ExperimentLifecycleCommands` 模块实现。内部页面路由和公开版本化路由只是传输 Adapter，必须调用同一模块，不能维护两套状态转换。模块对外只暴露：

```text
pause(command)  -> LifecycleCommandResult
resume(command) -> LifecycleCommandResult
cancel(command) -> LifecycleCommandResult
```

模块内部封装所有者校验、幂等记录、Revision 锁、`lifecycleVersion` CAS、状态转换、生成租约清理、子任务取消派发和审计。调用方不需要知道锁表顺序或状态列组合。

#### 6.7.1 用户暂停

新增内部命令路由和公开 v2 路由：

```text
POST /api/backtest/experiments/{experimentId}/commands/pause
POST /api/v2/experiments/{experimentId}/commands/pause
```

请求必须包含 `expectedRevisionId`、`expectedLifecycleVersion`、非空 `reason` 和 `Idempotency-Key`。`lifecycleVersion` 只在生命周期命令、当前 Revision 替换或终态收敛时递增，Trial 生成、运行进度和详情聚合不得递增它。允许在非终态且 `lifecycleState=active` 时发起：

1. 事务锁定 Experiment、当前 Revision 和 Stage；
2. 校验所有者、预期 Revision 和生命周期版本；不一致返回 `409 experiment.revision_conflict` 或 `409 experiment.lifecycle_conflict`；
3. 写入 `pause_requested_at` 和 `pause_reason`，清理尚未提交的生成租约；
4. 从该事务提交起，生成和物化候选查询必须排除该 Revision；
5. 已经运行或排队的普通回测不取消，继续自然终结；
6. 有在途任务时 `lifecycleState=pausing`，在途归零后由生命周期收敛器改为 `lifecycleState=paused`；若本来没有在途任务，可直接返回 `lifecycleState=paused`。

重复请求使用同一幂等键返回原结果。`paused` Revision 保留滚动窗口中已生成 Trial、逻辑游标、结果和重试信息，不释放或重算 Trial 身份。`snapshotVersion` 仍用于详情增量刷新，但不参与命令 CAS。

#### 6.7.2 用户恢复与执行熔断恢复

新客户端使用：

```text
POST /api/backtest/experiments/{experimentId}/commands/resume
POST /api/v2/experiments/{experimentId}/commands/resume
```

请求包含 `expectedRevisionId`、`expectedLifecycleVersion`、`resumeMode` 和 `Idempotency-Key`。`resumeMode` 为：

```text
user_pause | execution_circuit
```

- `user_pause` 只允许恢复 `lifecycleState=paused` 或 `lifecycleState=pausing`，清除用户暂停字段并从原 `generation_cursor` 继续；
- `execution_circuit` 只允许解除 `experiment.execution_blocked`，继续执行现有运行能力检查；
- 新客户端必须显式传递 `resumeMode`；
- 存储高水位和管理员关闭属于系统自动暂停，不接受用户 `/resume` 绕过；
- 已请求取消或已终结的 Revision 均不能恢复。

现有内部和公开 `/resume` 路径在兼容期只桥接到 `execution_circuit`，保持旧语义，不接受 `user_pause`。响应加入标准 `Deprecation`、`Sunset` 和替代链接信息，服务端记录旧接口调用量；达到文档声明的下线日期且连续一个观察周期无调用后删除。不得长期依靠“缺少字段时猜测模式”。

#### 6.7.3 取消确认与接口契约

新客户端使用：

```text
POST /api/backtest/experiments/{experimentId}/commands/cancel
POST /api/v2/experiments/{experimentId}/commands/cancel
```

请求体为：

```json
{
  "expectedRevisionId": "当前页面对应的 Revision ID",
  "expectedLifecycleVersion": 3,
  "reason": "参数配置有误"
}
```

`reason` 为去除首尾空白后的非空文本，最长 500 字符。响应至少包含 `experimentId`、`revisionId`、`lifecycleState`、`lifecycleVersion`、兼容 `status`、`acceptedAt` 和 `replayed`。

前端点击“取消实验”后必须先打开确认窗口，并使用确认时最新 `revisionId` 和 `lifecycleVersion`。详情轮询可以继续更新进度数字，但不得偷偷替换确认窗口绑定的生命周期版本；若版本变化，关闭提交并要求用户重新确认。窗口展示计划、已生成、已完成、排队、运行和尚未生成数量，并明确说明：取消对当前 Revision 不可恢复；停止生成和物化新 Trial；已提交任务按普通回测取消语义收敛；已有结果继续保留。

后端在一个事务中：

1. 锁定 Experiment、当前 Revision 和 Stage，校验所有者、预期 Revision 和生命周期版本；
2. 以 CAS 写入 `cancel_requested_at` 和 `cancel_reason`，清理生成租约；
3. 将逻辑未生成尾部计入 `cancelled_before_generation`；
4. 将已生成但未物化的 Trial 标记为 `cancelled_before_materialization`；
5. 对已物化且未终结的任务调用普通回测取消命令；
6. 记录包含原因、请求 ID、Revision 和数量快照的 `experiment.cancel_requested` 审计事件；
7. 返回 `202 Accepted` 和 `lifecycleState=cancelling`；若事务内已无待收敛工作，可直接返回 `lifecycleState=terminal`、`terminalOutcome=cancelled`。

允许从任意非终态生命周期状态取消。进入 `lifecycleState=cancelling` 后按钮禁用，页面继续轮询并展示仍在退出的排队/运行数量；最终写入 `lifecycleState=terminal`、`terminalOutcome=cancelled`。终态重复取消返回当前终态，不重复写审计或重复发送普通回测取消命令。

生命周期主路径为：

```text
active → pausing → paused → active
active / pausing / paused → cancelling → terminal(cancelled)
active → terminal(completed | partially_completed | failed)
```

取消优先级高于用户暂停、系统存储暂停和执行熔断：这些状态都不得阻止所有者发出取消。暂停与取消并发时依靠同一事务锁串行化；一旦 `cancel_requested_at` 写入，后到的暂停或恢复命令必须返回 `experiment.command_invalid`。

前端对一次用户确认只生成一个幂等键，并保存到收到确定响应为止。超时或网络结果不明确时，“重试取消”必须复用原键；发生 Revision/生命周期冲突时丢弃旧键，刷新详情并要求用户重新确认。

现有公开 `POST /api/v1/experiments/{id}/cancel` 在兼容期继续接受旧请求，但只作为调用同一模块的桥接 Adapter：服务端在事务中绑定当时的当前 Revision，返回旧响应形状并附带弃用信息。它不能支持“确认后长时间停留再提交”的强并发保证，因此新前端和新接入方不得继续使用。旧接口调用量归零并经过公告观察期后删除；不能把请求体永久做成可选来维持两套语义。

#### 6.7.4 更正参数后的新实验

取消请求被接受后，页面提供“复制参数为新实验”。新 Experiment 可以立即创建，不等待旧实验完全取消；旧任务仍占用的实际并发槽会使新实验短暂排队，槽位释放后由公平调度自动推进。

同一 Experiment 继续保持“一次只有一个活动 Revision”的不变量。只有旧 Revision 收敛到 `lifecycleState=terminal` 且 `terminalOutcome=cancelled` 后，才允许在原 Experiment 内创建新 Revision。这样既避免两个 Revision 共用同一实验身份并发推进，也不迫使用户等待才能通过“复制为新实验”修正参数。

取消不是删除。参数、代码和数据快照、已有结果、取消原因、审计记录及评价产物继续保留；物理清理由独立的归档和保留期流程负责。

#### 6.7.5 与评价、导出生命周期的边界

实验生命周期命令只控制 Trial 生成、物化和普通回测执行。已经冻结输入的评价运行和已经创建的导出任务是独立作业，不因实验暂停或取消而自动停止；它们各自通过评价/导出取消命令管理，并在产物中继续指向原 Revision。这样可以保留取消前已经形成的可审计结果，也避免一次实验命令跨越多个作业类型产生部分成功。

实验进入 `lifecycleState=cancelling` 后不得再创建新的评价或导出；收敛到终态后，允许用户基于已完成的部分结果显式创建评价或导出，界面必须标注覆盖率和取消数量。此规则与自动化删除无关，历史评价和导出仍由独立保留期管理。

### 6.8 评价、异常明细与导出

评价口径保持不变，但由 `EvaluationDataset` 模块统一管理冻结、读取、写入和导出。模块隐藏表结构和流式游标，对评价 Worker 提供“冻结执行集、迭代输入批次、写入结果批次、读取分页结果”四类窄接口。

新增规范化持久化结构：

- `backtest_experiment_evaluation_execution`：保存某次评价冻结的 Trial/Execution 身份、稳定顺序和必要版本引用；
- `backtest_experiment_evaluation_result_row`：保存每个执行的指标、排名键、分组键和可分页展示字段；
- `backtest_experiment_evaluation_group_result`：保存增量聚合后的分组结果；
- `backtest_experiment_evaluation_run`：只保存状态、`bigint` 计数、摘要、算法版本和数据集摘要，不再内嵌无界 `execution_set` 或完整 `output_snapshot`。

执行规则：

1. `planned`、`generated`、`succeeded`、`failed`、`cancelled` 和 `missing` 由数据库聚合与 `cancelled_before_generation` 计算，不为统计构造每个逻辑 Trial；
2. 删除 `_completeness_exceptions()` 中的 `range(planned_trial_count)`；未生成部分使用 `startTrialIndex`、`endTrialIndexExclusive`、`count` 和 `status` 的区间表示；
3. 评价启动时在一个可重复读事务中用数据库端 `INSERT ... SELECT` 冻结执行集，不先把所有行加载到应用内存；冻结顺序和资格规则带明确版本；
4. 冻结集摘要使用版本化的确定性流式算法，并保存算法版本、行数和摘要；相同输入与版本必须得到相同摘要；
5. Worker 使用服务端游标或 `fetchmany` 读取固定批次，行级结果批量写入规范化表，分组聚合增量更新；全局排名由数据库索引或外部排序完成，不能一次性加载全部结果；
6. 已生成的失败、取消和缺失明细通过稳定游标分页，评价运行只保存分类计数和有限样例，不内嵌无界异常数组；
7. 排名、分组和覆盖率仍覆盖同一 Revision 的全部符合条件结果，不得因为内存保护而抽样、截断或只评价滚动窗口；
8. CSV/XLSX/报告导出从规范化结果表分页或流式读取，不从超大 JSON 重新全量反序列化；
9. 新评价详情输出使用 `evaluation_output_v2`，返回摘要、计数和分页链接；历史 `v1` JSON 继续只读反序列化，但不再作为新运行的写入格式；本项不额外扩大评价接口的公开范围；
10. 所有计数字段在数据库使用 `bigint`，跨 JSON 安全整数边界时按版本化十进制字符串返回；
11. 新表具备与所属 Experiment/Revision 一致的 RLS、所有者索引、唯一约束、级联/保留策略和清理顺序；
12. 任何步骤都不得与尚未生成的逻辑尾部逐项线性相关；对实际结果的遍历允许线性耗时，但峰值内存和单次响应由批次或分页大小决定。

### 6.9 数据库迁移

数据库演进采用“加法迁移 → 双读投影 → 活动数据接管 → 停止旧写入 → 观察 → 收缩迁移”，避免一次发布同时改变状态、数据和接口而无法回退。所有 DDL 均通过新的幂等迁移由 migrate 服务执行，不修改已执行迁移。

#### 阶段 A：建立长期模型

新增幂等迁移，完成：

1. 在 `backtest_experiment_revision` 增加 `lifecycle_state`、`lifecycle_version`、`terminal_outcome`、`pause_requested_at`、`paused_at`、`pause_reason`、`cancel_requested_at` 和 `cancel_reason`；
2. 在 Stage 增加或规范化 `execution_phase` 和 Revision 级持久阻塞字段，并为状态组合建立 CHECK 约束；全局存储压力只保存在门禁单例表；终态必须有 `terminal_outcome`，非终态不得有终态结果；
3. 旧 `status` 暂时保留为兼容投影，继续使用旧枚举集合；索引和数据库约束同步支持映射后的迁移期读写，不能只改 Python 枚举或向旧列塞入 `pausing/paused`；
4. 建立三级生成窗口账本、全局单例行、生成预留令牌及过期索引、持久化公平轮转序号、唯一约束和对账索引；
5. 建立存储压力观测/决策单例表，保存每个信号的值、采样时间、阈值版本和聚合结论；
6. 建立规范化评价执行集、行级结果和分组结果表，计数使用 `bigint`，补齐 RLS、索引和清理关系；
7. 建立单例 `backtest_experiment_rollout_state`，以单调 `contract_epoch` 记录 `legacy`、`lifecycle_v2`、`evaluation_v2`、`rolling_window_v1` 的语义激活点和审计信息；
8. 本阶段不清零、不改变旧额度字段和旧调度行为，保证 `contract_epoch=legacy` 时仍能完整运行并直接回退应用版本。

#### 阶段 B：活动 Revision 接管

接管任务使用可重复执行的迁移命令或后台管理作业，不依赖一次性进程内脚本。处理矩阵为：

| 旧状态 | 新模型接管规则 |
| --- | --- |
| 已全部生成且未终态 | 保留全部 Trial，以真实非终态 Trial 数初始化三级账本，继续物化和执行 |
| 部分生成 | 保留 `generation_cursor`、Trial、摘要和身份，从原游标按滚动窗口继续 |
| 开放 Trial 数超过新窗口 | 不删除、不取消；停止补充，待自然终结降到窗口内后继续 |
| 仅因旧冻结容量产生阻塞 | 清除旧原因，按当前动态容量重新计算，不写新的持久化阻塞 |
| `experiment.capacity_blocked` 等含义不明 | 根据审计和字段来源分类；无法证明安全映射时保留并列入人工清单 |
| `manual_queue_reserved`、`manual_wait_blocked` 等瞬时等待 | 清除持久化原因，改由本轮许可计算表达 |
| 用户执行熔断 | 映射为明确 `system_block_code=execution_circuit`，不得自动解除 |
| 暂停或取消中 | 映射到相应 `lifecycle_state`，继续自然排空或取消收敛 |
| 已终态 | 只生成兼容投影，不重算结果、摘要或历史预算 |

接管前后必须核对每个 Revision 的计划数、生成数、终态数、开放数和游标守恒关系。发现不守恒时隔离该 Revision 并报告，不能为了继续发布而自动删除行。

#### 阶段 C：停止兼容写入并观察

1. 所有新代码先以 `contract_epoch=legacy` 暗部署；只有同波次服务和前端均验证就绪后，才在单独事务单调推进语义纪元；
2. `contract_epoch` 达到 `evaluation_v2` 后，新评价运行只写规范化 v2 表，历史 v1 结果保持只读；必须先完成该纪元，才能推进 `rolling_window_v1`；
3. `contract_epoch` 达到 `rolling_window_v1` 后，新建 Revision 才写入 `generation_policy_version=rolling_window_v1`；
4. `contract_epoch` 达到 `rolling_window_v1` 且所有旧实例退出后，新代码停止读写 `reserved_planned_trial_count` 和 `plan_quota_released_at`，再由幂等清理作业把旧预留值清零；两个字段继续保留用于观察，不能在暗部署阶段提前清零；
5. 所有生命周期命令只修改新字段，旧 `status` 由统一投影维护；
6. 监控旧接口调用量、旧额度列写入量、账本对账差异、兼容投影差异和活动 Revision 接管异常；
7. 任一差异未归零时停止收缩迁移，使用前向修复版本处理。

#### 阶段 D：收缩迁移

确认仓库代码、运维查询、报表、外部只读消费者和旧版本回退均无依赖后，新增后续幂等迁移：

```sql
ALTER TABLE backtest_experiment_user_quota
  DROP COLUMN IF EXISTS reserved_planned_trial_count;

ALTER TABLE backtest_experiment_revision
  DROP COLUMN IF EXISTS plan_quota_released_at;
```

`plan_quota_released_at` 仅服务于计划额度释放；若只删除额度字段而保留该列，会留下无业务含义的死状态，因此一并删除。

随后在独立发布中删除已经结束公告期的 v1 命令桥接和不再被任何消费者读取的旧状态列；不得把“删除旧状态列”和首次启用新状态模型放在同一发布。暂停恢复时可以清除当前活动暂停字段，但每次暂停、恢复和取消的原因及时间必须写入审计表，不能依赖可变状态列保存完整历史。阶段 D 完成前不得把数据库清理写成“已完成”。阶段 D 完成后，旧版本代码不再具备直接回退兼容性，回退必须使用包含兼容迁移的前向修复版本，不能直接切回读取旧列的镜像。

### 6.12 目标代码组织与写入所有权

新增实现按职责固定落在以下模块，避免实施阶段把规则重新散回路由和大仓库文件：

| 模块 | 固定位置 | 唯一写入职责 | 允许的调用方 |
| --- | --- | --- | --- |
| `ExperimentLifecycleCommands` | `backend/experiments/lifecycle.py` | 生命周期轴、`lifecycleVersion`、命令幂等和生命周期审计 | 内部/公开路由 Adapter |
| `RollingTrialWindow` | `backend/experiments/rolling_window.py` | 公平候选、生成令牌、三级账本、Trial 批次、游标、终态释放和重试重开 | 协调器、结果终结处理 |
| `StoragePressureGate` | `backend/experiments/storage_pressure.py` | 存储观测快照、迟滞状态和聚合决定 | `RollingTrialWindow`、健康检查 |
| `EvaluationDataset` | `backend/experiments/evaluation_dataset.py` | 评价冻结集、行级/分组结果和稳定分页 | 评价 Worker、读取/导出 Adapter |
| 兼容状态投影 | `backend/experiments/lifecycle.py` 内部 | 从正交状态生成旧 `status`，自身不持久化第二套事实 | 详情读取和 v1 Adapter |

`backend/app.py`、公开路由、前端和 Worker 不得直接拼装这些模块的内部 SQL 或状态组合。旧 `backend/experiments/repository.py` 中相关方法在迁移期可以作为兼容 Adapter，但新接口稳定后必须删除被替代的浅层方法，不能让新旧写路径永久并存。

暂停和取消需要同时失效生成令牌、终结未物化 Trial 并释放窗口账本。为保持同一 PostgreSQL 事务，`ExperimentLifecycleCommands` 是命令事务的编排者，`RollingTrialWindow` 提供包内私有事务参与者完成令牌和账本变化；该参与者不是路由可见接口。两者共享同一连接和锁顺序，任何一项失败则整个命令回滚。除该受控协作外，生命周期模块不得直接更新滚动账本，滚动窗口模块不得自行修改生命周期轴。

`StoragePressureGate` 与远程自有的 `storage-probe` 之间定义内部容量查询 port：生产使用内部 HTTP Adapter，测试使用内存 Adapter。其他三个模块以 PostgreSQL 集成测试覆盖其公开接口，不为测试额外暴露仓库细节。

### 8.2 PostgreSQL 集成测试

- 同一用户并发创建多个大计划均能成功，不出现计划额度竞争；
- 幂等创建仍只生成一个 Experiment；
- Trial 只在滚动窗口内提前生成；
- 多协调器并发竞争时，实验、用户和全局窗口均不超发；
- 账本事务始终按全局、用户、Stage 顺序加锁，压力并发测试无死锁；
- Trial 终结重复投递只释放一次窗口，手工重试必须重新取得窗口许可；
- 生成编译期间协调器崩溃或令牌过期后，预留占用可被幂等回收且不会跳过 Trial 索引；
- 对账器能够发现并修复三级账本漂移，同时留下可观测修复记录；
- 多个用户和多个 Experiment 公平轮转，单个大计划不能独占全局窗口；
- 首批生成后即可物化，不需要等待全部计划生成；
- 运行终结后窗口继续补充；
- 暂停请求与生成/物化并发时，事务提交后游标不再前进，已有任务自然终结后进入 `lifecycleState=paused`；
- 恢复后从原游标继续且无重复 Trial；
- 暂停中再次暂停幂等，暂停中取消能够转入 `lifecycleState=cancelling`；
- 取消与生成批次提交竞争时，未生成部分只计数一次，已提交批次不会丢失或重复；
- 取消时未生成部分正确计入 `cancelled_before_generation`，未物化部分进入 `cancelled_before_materialization`；

- 相同幂等键重放返回相同取消结果，不重复审计或重复发出子任务取消；
- 旧 Revision 已终态前不能在原 Experiment 创建新 Revision，但允许复制创建新的 Experiment；
- PostgreSQL 逻辑大小、数据库卷和产物卷任一进入压力状态后停止生成和物化，全部恢复后自动继续且不跳号；
- 任一必需存储信号过期时故障安全停止新工作，取消和清理仍可执行；
- 取消一个未生成逻辑尾部很大的实验时，完整性统计耗时不随尾部数量逐项增长；
- 评价执行集冻结、摘要、批量读取、全局排名和分页输出在相同输入下确定；
- 评价成功结果分批读取，峰值内存由批量大小而不是已完成 Trial 总数决定；
- 异常明细区间和分页合计数与聚合统计一致；
- 活动 Revision 的每种接管情形均保持计数和游标守恒，超窗口数据不会被删除；
- 聚合修复只修复实际在途和滚动账本计数；
- 阶段 A 至 D 迁移及接管作业均可重复执行；
- `contract_epoch` 只能单调推进，相关服务构建 ID 或支持范围不一致时推进事务失败；
- 删除字段后所有查询、RLS 策略和协调器循环正常。

- Revision/生命周期版本冲突会刷新详情并要求重新确认，不会继续发送旧请求；
- 详情进度刷新不会改变已打开确认窗口绑定的生命周期版本；
- `lifecycleState=cancelling` 显示收敛进度，`terminalOutcome=cancelled` 保留已有结果并提供复制为新实验入口；
- 系统存储压力、用户暂停、执行熔断和瞬时容量等待显示为不同原因；
- 已生成待物化、普通回测排队和尚未生成的逻辑尾部分别展示；
- 评价异常先展示汇总和压缩区间，具体已生成异常按页加载；
- 不支持 `crypto.randomUUID()` 的内网 HTTP 浏览器仍可提交；
- TypeScript 检查、Vitest 和正式构建通过。

### 8.4 远程普通用户样本回归

本次修改涉及实验提交、调度、执行和结果生成。按仓库规则，本地自动化测试完成后必须：

1. 只读取得服务器普通用户最近两条相关回测的保存代码和运行快照；
2. 在隔离的正常实验/Worker 链路验证预览、创建、滚动生成、排队、领取、执行、暂停恢复、取消收敛和结果生成；
3. 验证历史实验详情与 `budget_v2` 快照仍可读取；
4. 不修改原生产任务，不把用户代码或快照写入仓库、文档或对话；
5. 条件不满足时明确标记“远程普通用户样本回归待验证”，不得声称已通过。

## 九、服务器发布顺序

该改造影响后端、实验协调器、评价/导出 Worker、`storage-probe`、前端接口展示和数据库结构，必须按波次同批发布相互依赖的服务，不能只重启后端。

推荐按“先暗部署、再单独激活语义”的发布波次执行。每一波仍使用 `scripts/deploy-server.sh` 同批发布该波相互依赖的 migrate、后端、协调器、Worker、`storage-probe` 和前端：

1. 发布前检查普通 Bar/L2 任务、自动化实验、评价和导出作业；需要停协调器时先让现有运行任务排空，不能静默中断；
2. 第一波只发布加法迁移、`contract_epoch=legacy`、影子状态投影和观测指标，不切换调度语义；
3. 根据 PostgreSQL 逻辑预算、数据库数据卷和产物卷真实容量，在服务器私有 `deploy/.env` 配置各自阈值和探针陈旧时间；验证所有信号后暗部署 `StoragePressureGate`；
4. 第二波暗部署生命周期 v2、前端确认交互和 v1 兼容桥；通过退出条件后单独推进 `contract_epoch=lifecycle_v2`；
5. 第三波暗部署评价数据集 v2、流式导出和前端分页；通过退出条件后单独推进 `contract_epoch=evaluation_v2`；
6. 执行活动 Revision 接管预检并输出守恒报告；存在无法解释的状态时停止第四波，不自动清理；
7. 第四波暗部署 `RollingTrialWindow`、预算 v3、无配额预览/创建和动态容量；确认评价 v2 已生效并通过退出条件后，单独推进 `contract_epoch=rolling_window_v1`；
8. 删除仓库示例变量前，先把服务器三个旧值保存到受控发布回退记录，禁止写入仓库、普通日志或对话；滚动纪元激活并验证后从服务器私有 `.env` 删除三行。若在语义激活前回退旧版本，先从受控记录恢复三行；
9. 持续观察旧额度字段、v1 调用、投影和账本差异，并核对运维查询、报表及外部消费者；
10. 仅在下线条件满足后以独立第五波执行阶段 D 收缩迁移和后续旧接口/旧状态删除；
11. 每一波都执行健康检查、代表性新功能回测、历史任务兼容和普通用户样本回归，不能把最后一波验证代替前几波验证。

#### 语义激活线与回退规则

- `contract_epoch` 不得由应用启动或迁移自动推进；在 `scripts/deploy-server.sh` 增加显式激活子命令，先核对后端、协调器、相关 Worker 的健康响应和前端构建标签，再以“预期旧纪元 → 目标新纪元”的数据库 CAS 写入激活记录；禁止运维直接执行无审计 SQL 跳过检查；
- 新代码暗部署但 `contract_epoch` 尚未推进时，可以直接回退到上一版本；
- 语义纪元推进前，必须确认同波次所有依赖服务均已更新，旧实例已退出，迁移已完成，退出条件已满足；
- 纪元推进后，一旦产生该纪元的新命令、新 Revision 或新评价数据，禁止直接启动不理解该纪元的旧镜像；紧急处理必须先关闭对应新入口和协调器，再发布兼容的前向修复版本；
- 只有能够通过审计证明纪元推进后没有产生任何新语义数据时，才允许回退纪元并回滚应用；
- 阶段 D 收缩迁移后永远只允许前向修复，不允许恢复旧镜像。

#### 各波次 Go/No-Go 条件

| 波次 | 激活条件 | 退出条件 | No-Go/处置 |
| --- | --- | --- | --- |
| 第一波：加法模型 | 迁移可重复执行；旧接口和协调器特征测试通过 | 全部活动 Revision 守恒；影子投影连续 24 小时零差异 | 任一差异未解释：保持 `legacy`，直接回退应用或前向修复迁移 |
| 第二波：生命周期 v2 | 所有存储信号新鲜；暂停/恢复/取消并发测试通过；前端已切换 v2 | 代表性普通用户实验完成暂停、恢复、取消和复制新实验；v1 兼容投影一致 | 命令重复审计、状态漂移或存储门禁误判：不推进纪元 |
| 第三波：评价 v2 | 冻结集、摘要、全局排名、分页和导出确定性测试通过 | 新旧评价读取一致；批量内存上界符合测试；历史 v1 结果只读正常 | 结果数量、排名或摘要不一致：不推进纪元，保留 v1 新写入 |
| 第四波：滚动无配额 | `evaluation_v2` 已激活；活动 Revision 接管报告守恒；多协调器压力测试无超发、死锁和令牌泄漏 | 新建大计划不受旧总量门禁；至少覆盖生成、终结、重试、暂停和取消；账本对账连续 24 小时零差异 | 任一计数不守恒或身份摘要变化：关闭新建入口和协调器，保持上一纪元或前向修复 |
| 第五波：收缩 | 旧额度列连续 7 天零写入；投影和账本差异连续 7 天为零；v1 已公告至少 30 天且连续 30 天调用量为零 | 删除后完整测试、历史读取和普通用户样本回归通过 | 任一依赖或调用仍存在：延期删除，不以人工豁免绕过 |

如果一键发布仍被自动化实验持续产生的任务阻塞，应先停止实验协调器并让现有任务排空，不得绕过迁移只重建单个服务。

## 十、风险与控制

### 10.1 超大计划长期占用存储

取消逻辑总量上限后，已完成 Trial 和结果仍会长期累积。滚动窗口只能限制提前生成和同时执行，不能消除历史结果增长。必须配合存储监控、高水位暂停、用户主动取消以及既有归档/清理能力。

### 10.2 协调器忙循环

当窗口已满、调度容量耗尽或存储高水位触发时，候选查询必须返回无工作并遵循现有轮询间隔，不能持续领取同一 Stage 形成忙循环。

### 10.3 状态机和聚合计数偏差

生成与执行交错后，`generated_trial_count < planned_trial_count` 将成为正常运行状态。所有完成判断、恢复修复、详情计数和前端进度都必须移除“未全部生成等于异常”的隐含假设。

### 10.4 数据库字段删除后的回退

语义纪元激活后若已写入新语义数据，旧版本即使字段仍在也可能错误处理新状态；阶段 D 删除字段后风险更高。每波必须把“暗部署前回退”和“激活后前向修复”写入发布记录，阶段 D 前完成投影、调用量和旧列写入观察，并准备经过验证的前向修复路径。

### 10.5 旧变量残留造成运维误判

仓库示例和服务器私有 `.env` 都必须删除三行。只在代码中忽略而保留配置会继续制造“改了上限为什么没生效”的问题。

### 10.6 暂停、取消与批次提交竞争

暂停或取消可能与生成租约、Trial 批次提交和普通回测物化同时发生。所有命令必须锁定同一 Revision/Stage，并让候选查询检查暂停和取消标记；未提交批次回滚，已提交批次按真实状态计数，禁止通过进程内标志推测结果。

### 10.7 取消收敛不是瞬时完成

已运行任务可能正在执行不可中断区段，取消请求只能先进入 `lifecycleState=cancelling`。前端不得在收到受理响应后立即显示“已取消”，调度器也不得在子任务仍占用执行槽时提前扣减在途计数。

### 10.8 精确整数边界被误解为新配额

`2^53 - 1` 是现有 JSON/TypeScript 数字契约的精确表达边界。错误提示、文档和变量命名不得把它描述成可由运维调整的 Trial 配额，也不得新增对应 `.env` 开关。

### 10.9 存储门禁配置缺失

任一必需存储阈值缺失、数值不合法、探针不可达或观测过期时采用故障安全行为：自动化实验停止新生成和新物化，健康检查明确报告具体信号；取消、查询、归档清理和普通回测不受影响。发布前必须按服务器真实容量配置并验证，不能用 `pg_database_size()` 或任意默认字节数猜测物理卷容量。

### 10.10 评价结果规模转移

滚动窗口只约束未终结工作，不能减少最终成功结果总量。如果评价仍一次性加载全部结果或在快照中内嵌全部异常，系统会把生成阶段的规模风险转移到评价 Worker 和 API 响应。必须以数据库聚合、分批计算、持久化排序结果和分页明细保持内存与响应体有界。

### 10.11 新旧状态双写漂移

兼容期同时存在正交状态轴和旧 `status` 投影。任何调用方绕过 `ExperimentLifecycleCommands` 直接更新旧状态都会制造漂移。数据库写入路径必须集中，持续比较投影差异；差异未归零不得删除旧列，也不得掩盖为自动修复成功。

### 10.12 三级账本死锁或重复释放

多个协调器、终态事件和重试命令会并发修改三级账本。所有写事务必须使用固定锁顺序和幂等事件标识；压力测试覆盖死锁、重复投递和事务重试。对账器是故障检测与修复保险，不能替代主事务原子性。

### 10.13 v1 兼容桥无限期存在

旧接口缺少强生命周期并发语义，只适合过渡。如果没有调用量指标、公告日期和删除条件，系统会永久维护两套外部契约。v1 桥接必须从发布当天开始计量和弃用，只有完成公告观察期才可删除，但不得以仍有桥接为由让新前端继续使用。

### 10.14 生成预留泄漏

批次编译在事务外执行，协调器退出可能留下尚未转换的窗口预留。生成令牌必须具有数据库时间定义的过期时间和幂等回收路径；回收前重新校验令牌未被成功提交，不能仅凭进程心跳缺失扣减。健康检查需暴露过期令牌数量和最老年龄，避免预留泄漏使大计划永久停止推进。

### 10.15 语义纪元与运行实例不一致

若旧实例仍在运行时推进 `contract_epoch`，同一数据库会被两套语义并发修改。推进纪元的发布步骤必须先验证所有相关服务的构建 ID 和支持的最大纪元，迁移事务只允许在全部实例已就绪时执行；健康检查必须返回当前纪元和进程支持范围，不匹配的实例拒绝领取新工作并报告不健康。

## 十一、验收标准

全部满足以下条件后，本方案才算完成：

1. 仓库代码和 `deploy/.env.example` 不再读取或声明三个旧变量；
2. 服务器私有 `deploy/.env` 已删除三个旧变量；
3. 大于旧阈值的完整有限计划能够作为一个 Experiment Revision 预览和创建，不需要用户拆分参数；
4. 创建后的 `plannedTrialCount` 与完整笛卡尔积一致，没有静默截断、抽样或自动拆分；
5. 同一 Revision 内可以对全部候选结果执行统一评价和排序；
6. 预计 Bar 总量只影响资源等级与提示；
7. 资源估算不可用只产生警告，不阻止合法计划创建；
8. `experiment.plan_limit_exceeded` 已从实现、测试、使用手册和 API 文档删除；
9. 预览编译次数与 Trial 总量无关并保持固定上界；
10. `plannedTrialCount` 在 `2^53 - 1` 内跨后端、JSON 和前端精确一致，超过边界明确拒绝；
11. Trial 生成和物化采用实验、用户、全局三层有界滚动窗口，不再预生成完整计划后才执行；
12. 实际并发、用户在途、公平调度和普通任务保留容量仍有效；
13. 动态容量收紧只影响推进速度，不产生需要人工恢复的冻结容量阻塞；
14. 数据类型溢出、请求结构和单维度异常输入仍被拒绝；
15. 用户可以暂停并从原游标恢复，且执行熔断恢复不能误解除用户暂停或系统存储压力；
16. 暂停、取消使用独立 `lifecycleVersion`，普通进度刷新不会制造命令冲突；
17. 取消具有确认、乐观并发、稳定幂等、原因审计和异步收敛；已完成结果继续保留；
18. 取消受理后可立即复制为新实验，旧任务只按真实在途容量短暂影响新实验调度；
19. 生命周期、执行阶段、系统阻塞和终态结果分别存储，旧 `status` 只由统一投影生成且不超出旧枚举集合；
20. `RollingTrialWindow` 内部选择公平候选并原子维护三级预留/开放占用、令牌回收、终态释放和重试重开，多协调器不超发、不重复释放且公平次序可持续；
21. 评价统计不展开尚未生成的逻辑尾部，异常使用区间与分页表达，全部成功结果仍参与统一评价和排序；
22. 新评价输入和行级结果使用规范化表，Worker 峰值内存由批量上界决定，历史评价输出继续可读；
23. 实验暂停或取消不自动终止已冻结评价和导出，其独立生命周期与取消语义已验证；
24. 历史 `experiment_budget_v2` 和历史实验可以读取且不被旧上限或冻结容量阻塞；
25. 活动 Revision 按接管矩阵迁移，计划数、生成数、开放数、终态数和游标保持守恒；
26. 用户计划额度预留、释放、重试恢复和修复逻辑全部删除；
27. `reserved_planned_trial_count` 与 `plan_quota_released_at` 完成加法、观察和收缩阶段后最终删除；
28. PostgreSQL 逻辑大小、数据库卷和产物卷的权威信号、陈旧判定、故障安全和自动恢复行为已验证；
29. v2 生命周期命令成为前端和新接入方唯一入口，v1 桥接有调用量、公告期和删除记录；
30. 四个深模块均通过接口级测试，路由、协调器和 Worker 不复制其内部状态判断；
31. 本地后端、PostgreSQL 集成、前端检查和正式构建通过；
32. 远程普通用户两条样本回归通过，或如实记录待验证原因；
33. 每个发布波次的健康检查、新功能回测、历史兼容、暂停恢复和取消收敛验证均有真实结果；
34. `contract_epoch` 的暗部署、单独激活、实例兼容检查和激活后前向修复规则已验证；
35. 4.3 中每个原始业务目标均能由实现变更、自动化测试和发布证据追溯，不存在新的总量门禁、自动拆分或结果抽样。

## 十二、完成定义

“删除三个环境变量”不是本方案的完成定义。最终完成状态是：

- 用户可以提交任意不超过当前跨端精确整数边界的有限笛卡尔积计划；
- 一次完整参数验证由一个 Experiment Revision 承载，不需要人为拆分成多个实验；
- 系统不会因为 Trial 总数、用户计划总量或预计 Bar 总量拒绝创建；
- 系统通过有界预览、三层滚动窗口、实际并发门禁和存储压力自动暂停保护资源；
- 用户可以暂停后继续同一 Revision，也可以取消错误实验并立即复制参数创建新实验；
- 生命周期命令、生成窗口、存储压力和评价数据集分别由稳定的深模块承载，新增状态或容量信号不需要散改路由和协调器；
- 全部已完成结果仍在同一 Revision 中统一评价，规范化评价数据集和分页传输不会展开尚未生成的逻辑尾部或一次性加载全部结果；
- 历史快照仍可解释，新旧语义不会互相污染；
- 活动 Revision 能够无损接管，兼容接口和旧列都有可观测、可退出的下线路径；
- 运维界面和 `.env` 中不再存在看似可调、实际无效的逻辑计划配额。
