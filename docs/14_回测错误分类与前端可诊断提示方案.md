# 回测错误分类与前端可诊断提示方案

## 1. 背景与结论

当前回测失败大多以一段原始异常字符串返回前端。该字符串可能来自策略脚本、行情读取、撮合引擎、worker 通信或基础设施；前端既难以判断使用者能否自行修复，也可能暴露内部服务地址、数据查询细节或堆栈信息。

首版采用两类对外错误：

| 类别 | 适用范围 | 前端展示原则 |
| --- | --- | --- |
| `strategy_error`（策略错误） | 脚本校验、脚本运行、策略返回非法指令 | 展示可定位的回调、时间、标的、原因和修复建议 |
| `system_error`（系统错误） | 数据源、存储、网络、worker、撮合基础设施及未知异常 | 仅展示安全的中文提示、是否可重试和任务编号，不展示原始异常 |

其中，“所选范围没有可用行情”属于系统侧的数据可用性问题，但可以给出安全且可操作的提示；它不能暴露表名、SQL、服务地址或底层异常。

## 2. 目标与边界

### 2.1 目标

1. 使用者遇到策略问题时，能在前端直接定位到发生位置并修改脚本。
2. 系统问题对普通使用者保持脱敏，同时保留可供运维排查的任务编号和服务端日志。
3. Bar 回测、L2 订单驱动回测和 L2 连续行情回放使用同一套错误契约。
4. 已有历史任务中仅保存 `error` 字符串的结果仍可展示，不因升级而无法读取。

### 2.2 非目标

1. 不在本次向普通前端展示 Python 堆栈、SQL、容器名称、内网地址或第三方服务返回体。
2. 不改变策略交易规则、行情读取逻辑或任务调度方式。
3. 不引入新的依赖、队列或数据库表；优先复用现有任务结果摘要字段。

## 3. 对外错误契约

任务结果新增可选的 `errorDetail`（结构化错误详情）对象。失败任务保留既有 `error`（兼容旧客户端的简短文本）字段，但前端优先使用 `errorDetail`。

```json
{
  "error": "策略执行失败",
  "errorDetail": {
    "category": "strategy_error",
    "code": "strategy.runtime_error",
    "message": "条件判断中使用了未定义变量 entry_price。",
    "hint": "请在使用 entry_price 前从 state（跨回调临时状态）读取，或先为它赋值。",
    "callback": "on_quote",
    "eventTime": "2026-06-01 09:31:03",
    "symbol": "688981.SH",
    "retryable": false,
    "taskId": "任务 UUID"
  }
}
```

字段约束如下：

| 字段 | 含义 | 展示规则 |
| --- | --- | --- |
| `category`（错误类别） | `strategy_error` 或 `system_error` | 必填，用于选择前端样式 |
| `code`（稳定错误码） | 机器可读的错误类型 | 必填，用于前端文案和测试，不直接替代中文说明 |
| `message`（安全原因） | 已清洗的中文原因 | 必填，可展示 |
| `hint`（修复建议） | 使用者下一步应做什么 | 可选；策略错误通常应提供 |
| `callback`（策略回调） | `on_bar`、`on_quote` 或 `on_order_event` | 仅策略错误可用 |
| `eventTime`（事件时间） | 发生错误的 Bar、快照或订单回报时间 | 仅策略错误且上下文可得时可用 |
| `symbol`（标的） | 发生错误的回测标的 | 仅策略错误且上下文可得时可用 |
| `retryable`（是否可重试） | 重试当前任务是否有合理可能 | 必填 |
| `taskId`（任务编号） | 回测任务唯一标识 | 必填，可复制给维护人员 |

原始异常仅写入服务端日志，并通过 `taskId`（任务编号）关联；不得写入普通用户可访问的任务结果、HTTP 响应或前端控制台。

## 4. 错误分类规则

### 4.1 策略错误

只有明确的策略领域异常才归为 `strategy_error`（策略错误），包括：

1. 策略源码编译或校验失败。
2. `on_bar`、`on_quote`、`on_order_event` 内运行时异常。
3. 策略返回的动作、数量、方向或字段不符合策略接口约定。
4. 策略调用约定中的上下文值不合法，例如把不支持的时间格式传给策略自身逻辑。

策略执行包装层必须在异常发生点捕获上下文，并构造受控异常对象。回调名、时间和标的由引擎传入，不能信任策略脚本自行填写的内容。

订单因资金不足、可用数量不足、最小交易单位或涨跌停限制而被拒绝，不应使整个任务失败；它们应继续作为订单/信号明细中的拒绝结果展示。只有策略指令本身不合法时才归为策略错误。

### 4.2 系统错误

下列情况归为 `system_error`（系统错误）：

1. ClickHouse、PostgreSQL、Redis 或 worker 的连接、协议和超时异常。
2. 行情适配、数据读取、缓存读写、任务租约和持久化异常。
3. worker 重启、会话中断或未知内部异常。
4. 所选标的、日期或周期没有可用行情数据。

系统错误由后端映射为白名单安全文案。例如，数据为空显示“所选区间没有可用行情数据，请检查标的、日期和周期后重试”；其它未知异常显示“回测执行异常，请稍后重试或联系管理员”。

## 5. 后端改造方案

### 5.1 统一错误模型

新增独立的回测错误模块，负责：

1. 定义 `StrategyExecutionError`（策略执行错误）和 `BacktestErrorDetail`（回测结构化错误详情）。
2. 将策略异常、数据异常和未知异常映射为受控的 `errorDetail`（结构化错误详情）。
3. 生成对外安全文本；原始异常只用于结构化日志。

未知异常必须默认映射为 `system_error`（系统错误），不能因为异常字符串看起来像脚本错误就推断为策略错误，避免错误归类和信息泄露。

### 5.2 策略脚本上下文

`ScriptedBarStrategy`（脚本策略适配器）在调用三个入口时统一包装：

| 入口 | 应附带的上下文 |
| --- | --- |
| `on_bar` | `callback=on_bar`、Bar 时间、标的 |
| `on_quote` | `callback=on_quote`、快照时间、标的 |
| `on_order_event` | `callback=on_order_event`、订单回报时间（如有）、标的 |

脚本加载、编译和接口校验失败也使用同一对象，但没有行情事件时允许省略 `eventTime`（事件时间）与 `symbol`（标的）。

### 5.3 worker 与任务链路

L2 worker 的 HTTP 响应当前不能再把异常压扁为 `detail`（原始字符串）后转发。改造为传递受控的结构化错误对象：

1. worker 捕获领域异常并返回安全的 `errorDetail`（结构化错误详情）。
2. 调度端还原为对应的领域异常，避免二次拼接或丢失回调上下文。
3. `l2_runner`（L2 任务执行器）及普通 Bar 回测入口最终调用统一映射器。
4. 任务完成/失败写入结果摘要时保存安全的 `error`（兼容文本）与 `errorDetail`（结构化错误详情）。
5. 服务端使用 `logger.exception`（带堆栈日志）记录原始异常，并始终带上 `taskId`（任务编号）。

### 5.4 历史兼容

历史任务只有 `error`（旧字符串）而没有 `errorDetail`（结构化错误详情）时，后端或前端统一按遗留系统错误处理：展示“历史任务未保存可定位错误信息”和任务编号，不回显旧字符串中的潜在敏感信息。

## 6. 前端展示方案

失败任务在“概览”和“历史回测”使用同一错误卡片组件；运行中轮询失败也复用这套解析逻辑。

### 6.1 策略错误卡片

展示下列内容：

1. 标题：“策略执行失败”。
2. `callback`（策略回调）、`eventTime`（事件时间）和 `symbol`（标的），有值才显示。
3. `message`（安全原因）。
4. `hint`（修复建议）。
5. 可复制的 `taskId`（任务编号）。

示例：

> 策略执行失败：`on_quote`，688981.SH，2026-06-01 09:31:03。  
> 原因：条件判断中使用了未定义变量 `entry_price`。  
> 建议：请在使用前初始化该变量，或从 `state`（跨回调临时状态）读取它。  
> 任务编号：`...`

### 6.2 系统错误卡片

展示受控标题、受控原因、是否建议重试和任务编号；不显示技术细节、回调、Python 异常、服务名或堆栈。

示例：

> 回测未完成。所选区间没有可用行情数据，请检查标的、日期和周期后重试。  
> 任务编号：`...`

未知系统错误示例：

> 回测执行异常，请稍后重试；如持续出现，请提供任务编号给维护人员。  
> 任务编号：`...`

## 7. 实施步骤

1. 梳理普通 Bar、L2 引擎、worker 和任务持久化中现有的异常出口，确定统一接入点。
2. 实现结构化错误模型、错误码白名单和安全文案映射。
3. 为脚本策略适配器的 `on_bar`、`on_quote`、`on_order_event` 增加上下文捕获与领域异常包装。
4. 改造 worker 与调度端之间的错误响应，完整保留结构化详情但不传递原始异常。
5. 改造任务结果保存和查询接口，兼容旧的 `error`（旧字符串）结果。
6. 扩展前端 API 类型，新增统一失败任务错误卡片，并在概览、历史回测和轮询失败处接入。
7. 更新使用手册中的策略排错章节，明确普通用户可见信息与任务编号的作用。

## 8. 验证计划

### 8.1 后端测试

1. `on_bar`、`on_quote`、`on_order_event` 分别抛出异常时，验证类别、回调、时间、标的、原因和建议。
2. 策略返回非法动作或数量时，验证归为 `strategy_error`（策略错误）。
3. 行情为空、数据源异常、worker 连接失败和未知异常时，验证归为 `system_error`（系统错误），且响应不含原始异常片段。
4. worker 端结构化错误经过 HTTP 往返后，验证字段没有丢失或被字符串化。
5. 订单拒绝仍写入订单明细，不会把任务标为失败。
6. 历史 `error`（旧字符串）任务能安全展示。

### 8.2 前端测试

1. 策略错误卡片展示回调、时间、标的、原因、建议和任务编号。
2. 系统错误卡片不渲染技术字段，即使后端意外附带未知字段也不得展示。
3. 数据不可用文案可见且不含内部表名、地址或 SQL。
4. 遗留任务结果显示兼容提示而不回显旧原始异常。

### 8.3 验收标准

1. 使用者仅凭前端信息可以定位并修复常见策略异常。
2. 普通前端页面、任务查询 API 和浏览器控制台均不包含服务端堆栈、SQL、内网地址或连接凭据。
3. 每个失败任务都有可复制的 `taskId`（任务编号），可与服务端日志准确关联。
4. 不改变成功任务、订单拒绝明细及历史回测列表的既有行为。

## 9. 自审与风险控制

1. **误分类风险**：仅由明确的策略领域异常生成 `strategy_error`（策略错误）；其它异常一律按系统错误处理。
2. **泄露风险**：安全消息只允许由后端白名单模板生成；测试中应断言响应不包含原始异常、URL、SQL 或堆栈。
3. **上下文缺失风险**：订单回报没有可靠时间或标的时允许字段缺省，前端不以缺省字段判定错误类别。
4. **兼容风险**：保留 `error`（兼容文本），并对历史任务走安全降级展示，避免改造后历史页面空白。
5. **可维护性风险**：错误码由后端集中定义，前端只依赖稳定字段与安全文案，不根据英文异常字符串分支。

## 10. 执行前确认

本方案获得确认后，实施范围包括后端错误模型、策略适配器与 worker 错误传递、任务结果接口、前端失败卡片、测试及使用手册更新；不涉及交易逻辑、数据表结构或依赖升级。
