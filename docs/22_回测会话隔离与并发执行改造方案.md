# 回测会话隔离与并发执行改造方案

日期：2026-08-20  
状态：已实施并完成本地五任务队列验证，待服务器四并发压测

## 1. 背景与问题

当前 L2 回测任务由单个 `l2-runner（L2 回测执行器）` 消费。用户提交多个任务时，后续任务只能等待前一任务完成，无法利用服务器的多核 CPU 与充足内存。

现有回测主链路还依赖共享的 `strategy-worker（策略脚本执行服务）`：L2 runner 通过 HTTP 调用它执行策略的 `on_bar()`、`on_quote()` 与 `on_order_event()`。该设计实现了服务级隔离，但引入了内部 HTTP 和 JSON 编解码开销；多个并发回测也会竞争同一个共享策略服务。若共享服务异常，等待其回调的多个任务可能同时超时或失败。

服务器具备 96 核 / 192 线程、约 377 GiB 内存与 NVMe 存储，但同时运行 ClickHouse、Kafka、Flink、Spark、GitLab 等服务。因此目标不是取消队列或无限并发，而是在明确资源上限下提升多用户回测吞吐，并将故障限制在单个回测任务内。

## 2. 目标、边界与不做事项

### 2.1 目标

1. L2 回测支持 4 个任务并行执行，第 5 个及后续任务可靠排队。
2. 每个回测任务拥有独立的 `StrategySession（策略会话）` 子进程；策略异常、超时或子进程崩溃只影响该任务。
3. L2 回测主链路不再通过共享 `strategy-worker` 执行策略，消除内部 HTTP 与共享执行瓶颈。
4. 保持现有策略脚本接口、L2 撮合、无前视、底仓、T+0、费用、信号明细与历史任务展示语义不变。
5. 保持 PostgreSQL 任务状态可追溯、Redis 缓存可淘汰且不影响结果、ClickHouse 查询受控。
6. 为超时、取消、异常退出、缓存并发未命中和发布回滚提供明确处理方式。

### 2.2 不做事项

1. 不以“无限并发”替代排队；并发槽位必须受配置和容器资源限制。
2. 不改变首次从 ClickHouse 读取大量盘口数据的固有耗时；本次重点是提升多任务吞吐和隔离性。
3. 不改变普通用户看到的安全错误展示，也不将容器堆栈直接暴露到前端。
4. 不主动收紧策略脚本的可导入模块、网络访问或环境变量访问规则；安全权限治理另行设计。
5. 不重算或修改历史回测任务、策略快照、缓存结果与收益统计。
6. 首轮不扩容标准 Bar runner；标准 Bar 与 L2 队列保持隔离，待 L2 四并发稳定后另行评估。

## 3. 总体架构

### 3.1 目标执行链路

```text
前端 / API
  ↓ 创建任务
PostgreSQL（任务队列、状态真相、结果与审计）
  ↓ 原子领取任务
L2 runner × 4（每个 runner 同时处理一个任务）
  ├─ 读取 Redis 缓存与 ClickHouse 行情
  ├─ 续租、取消、超时、进度与结果持久化
  ↓ Pipe
StrategySession 子进程（一个任务一个会话）
  ├─ 批量回放 Bar / 盘口、撮合、费用、仓位与策略状态
  └─ 返回受限结果、会话控制响应与策略错误
  ↓
L2 runner 写入 PostgreSQL 并释放执行槽位
```

`strategy-worker` 在本次改造后不再位于 L2 回测主链路。其可暂时保留用于策略编辑页的语法检查、预览或其他低频功能，避免将服务移除与回测架构改造耦合。

### 3.2 组件职责

| 组件 | 改造后职责 | 是否共享 |
| --- | --- | --- |
| PostgreSQL | 保存 `backtest_run（回测记录）`、任务状态、结果、事件和审计信息；原子分配任务。 | 全系统共享。 |
| L2 runner | 领取单个任务、读取行情、创建和监管策略子进程、处理取消与超时、持久化结果。 | 一个副本一个执行槽位。 |
| StrategySession | 批量回放已标准化数据、运行策略、维护撮合/费用/仓位状态并返回结果。 | 仅属于当前任务。 |
| Redis | Bar、盘口或数据块缓存；缓存未命中协调。 | 可共享，缓存可淘汰。 |
| ClickHouse | 原始 Bar 与 L2 行情数据查询。 | 可共享，需控制并发查询。 |
| strategy-worker | 非回测主链路的策略编辑辅助能力。 | 共享，但不阻塞 L2 回测。 |

## 4. 会话隔离方案

### 4.1 隔离粒度

以“单个回测任务”为进程隔离粒度，不以单根 Bar、单条 Quote 或单次策略回调为粒度。

每个 L2 runner 同时只运行一个 `StrategySession` 子进程，因此子进程共享所在 runner 容器的 CPU、内存和 PID 上限，但不会与其他任务共享 Python 解释器、策略状态、异常栈或进程生命周期。

不为每次 `on_bar()` 或 `on_quote()` 启动进程，避免高频进程创建抵消回测性能。

### 4.2 父子进程通信

L2 runner 与 StrategySession 使用本机 Pipe 或等价的受控进程通信，不使用 HTTP。父 runner 发送已标准化的 Bar/Quote/Trade 数据块和任务控制消息；子进程在块内完成策略回调与撮合，返回控制响应、受限结果和策略错误。通信消息限定为：

1. `chunk（数据块）`：父 runner 发送按时间排序的 Bar、Quote 与 Trade 集合；不得按单条 Quote 往返通信。
2. `barBatch（K线批次）`、`quote（盘口）` 与 `dayControl（日控制）`：订单驱动模式所需的受控补充消息。
3. `demand（盘口需求）`、`result（结果）`：子进程返回下一步数据需求或既有受限结果结构。
4. `error（错误）`：包含受控错误编码、阶段、异常类型、脱敏上下文和原始正文索引。

子进程不直接写任务状态表、不读取 Redis 或 ClickHouse、不持有 PostgreSQL、Redis 与 ClickHouse 的连接配置；父 runner 是唯一数据访问和状态写入方。撮合仅使用父 runner 传入的数据块和任务参数，在子进程内存中执行。这样即使子进程崩溃，父 runner 仍能依据退出码、最后心跳和已接收消息，将任务收敛到 `failed（失败）`、`cancelled（已取消）` 或 `succeeded（成功）`。

### 4.3 策略运行时复用

StrategySession 在同一任务子进程内直接组合现有 L2 撮合引擎与脚本运行时。父 runner 只决定数据读取边界和任务控制，不参与块内回调与撮合，保留以下外部契约：

| 契约 | 改造要求 |
| --- | --- |
| `on_bar(bar, state)` | 调用时机、字段、返回信号格式不变。 |
| `on_quote(quote, state)` | L2 的可见性、严格后续快照成交语义不变。 |
| `on_order_event(event, state)` | 账本更新后的回调顺序与字段不变。 |
| `action（交易动作）`、`quantity（数量）`、`reason（原因）` | 现有校验和错误提示不变。 |
| 策略快照 | 仍以任务创建时保存的脚本与参数执行。 |

策略脚本抛出的业务错误应继续归类为策略错误并向普通用户展示可诊断提示；会话进程崩溃、IPC 中断、行情源不可用等归类为系统错误并写管理员诊断日志。

## 5. 并发、资源与队列

### 5.1 首轮资源配置

服务器首轮目标配置如下：

| 配置项 | 当前 | 目标 | 说明 |
| --- | ---: | ---: | --- |
| `TREND_GRID_L2_RUNNER_REPLICAS（L2 runner 副本数）` | 1 | 4 | 允许 4 个 L2 任务并行。 |
| 单个 `l2-runner` CPU | 2 | 4 | 保障回放、撮合和策略执行的 CPU 配额。 |
| 单个 `l2-runner` 内存 | 3 GiB | 6 GiB | 为行情块、策略状态和结果明细留出边界。 |
| L2 总资源上限 | 2 CPU / 3 GiB | 16 CPU / 24 GiB | 四个副本的资源总和。 |
| `strategy-worker` | 2 CPU / 2 GiB | 保持现状 | 不再承担 L2 主链路，不为其扩容。 |

`TREND_GRID_L2_RUNNER_REPLICAS（L2 runner 副本数）` 属于服务器私有 `deploy/.env` 配置，不提交到仓库。Compose 配置中的单副本资源限制属于项目配置，需随代码发布。

### 5.2 任务领取与公平性

PostgreSQL 任务表是可靠队列，不是额外的消息中间件。每个 runner 使用事务内原子领取，必须满足：

1. 多个 runner 不会领取到同一条任务。
2. 已取消任务不会被领取。
3. 已领取但 runner 意外退出的任务有明确恢复策略，不会永久停留在 `running（运行中）`。
4. 任务按提交时间保持尽力而为的公平顺序；不同用户不需要为每人维护独立任务库。
5. 状态更新仅在领取、开始、周期性进度、完成、失败和取消时写入，禁止按每条 Quote 更新 PostgreSQL。

现有 L2 领取 SQL 已使用 `FOR UPDATE SKIP LOCKED`、`attempt_token（尝试令牌）` 与租约续期。改造必须保持这些语义，并补充多副本领取、旧尝试令牌无法覆盖新结果、取消与租约过期接管的回归测试；不得重新实现或弱化现有原子领取逻辑。

### 5.3 为什么不使用消息队列

当前回测是低频、长耗时、强状态任务。PostgreSQL 已保存任务、结果、取消状态和审计记录，能够可靠支持四个并发消费者。引入 RabbitMQ、Kafka 或 Redis 队列仍需 PostgreSQL 保存最终状态，还会新增确认、重复投递、死信、重试一致性和运维复杂度。

Redis 在本项目用于可淘汰缓存，不作为任务可靠性来源。只有未来达到多机大规模 worker、每秒大量任务提交或跨系统任务分发时，才评估增加专用消息队列作为分发层；PostgreSQL 仍保留任务状态真相。

## 6. 缓存与 ClickHouse 并发保护

并发执行会放大同一标的、同一交易日、同一周期的缓存未命中问题。若四个任务同时回源，会产生重复 ClickHouse 扫描，降低吞吐。

### 6.1 缓存击穿协调

1. Redis 缓存键继续按数据源、标的、交易日、周期与缓存版本区分。
2. 缓存未命中时，以相同维度申请短期互斥锁。
3. 获得锁的会话负责查询 ClickHouse 并写入缓存；其他会话等待缓存完成后读取。
4. 加锁者失败或锁超时时，等待者可重新竞争或降级为独立查询，避免永久阻塞。
5. 缓存变更必须递增命名空间或版本；缓存失效只能影响性能，不得改变结果语义。

### 6.2 查询边界

1. 单个会话同一时刻最多一个在途 ClickHouse 查询。
2. 继续使用 Docker 内部网络 `quant-clickhouse:8123`，不经宿主机 IP 或公网链路。
3. 为查询保留连接、超时和可重试分类，但禁止无上限重试。
4. 监控 ClickHouse 查询时长、读取行数、磁盘 I/O 与并发数，确认四并发不会使单任务时延显著恶化。

## 7. 取消、超时与错误处理

### 7.1 取消

用户取消后，父 runner 设置任务取消标记并通知策略子进程。父 runner 在数据块与策略回调边界检查取消状态；超过短暂宽限时间仍未退出时，父 runner 终止子进程并将任务标为 `cancelled（已取消）`。

### 7.2 超时与无心跳

1. 每个任务有整任务上限和可配置的心跳超时。
2. 父 runner 必须以独立定时器续写 PostgreSQL 租约；续租不能依赖策略子进程是否返回消息，避免策略阻塞时任务被另一副本重复领取。
3. 长时间没有心跳的子进程按异常退出处理，父 runner 回收其资源。
4. 策略执行异常、会话进程异常、数据源异常和取消超时必须映射到既有的受控错误分类。
4. 管理员系统日志保留任务编号、用户、发生时间、阶段、错误编码、异常类型和脱敏正文索引；普通用户仅看到安全提示与任务编号。

### 7.3 进程隔离边界

会话级进程隔离能防止任务互相污染和单个任务崩溃扩散，但不等同于安全沙箱。策略子进程不得继承数据库、Redis 和 ClickHouse 连接配置，且只接收父 runner 传入的市场与账户上下文；但它仍与父进程共享容器网络命名空间。当前策略脚本的模块导入和网络访问规则不主动收紧；如后续需要处理不受信任脚本，应另行设计容器级或沙箱级权限隔离。

### 7.4 IPC 背压与结果规模

1. 策略子进程不得对每条 Quote 额外发送进度、日志或完整状态快照；心跳与前端进度按固定时间间隔发送。
2. 父 runner 必须持续读取 Pipe，并对 `intent（交易意图）`、错误和控制消息设置有界队列或等价背压，避免子进程因 Pipe 缓冲区写满而阻塞。
3. 信号明细与成交明细由子进程在内存中按数据块聚合，最终以既有受限结果结构一次返回；父 runner 禁止在高频回放中逐条写 PostgreSQL。
4. 超出既有结果明细上限时沿用现有受限结果规则，并在管理员诊断中记录截断原因，不得造成会话无限占用内存。

## 8. 实施阶段

### 阶段一：执行前审查与运行时抽取

1. 审查 L2 任务领取、租约、取消和重启恢复逻辑的原子性。
2. 抽取与 HTTP 无关的策略运行时模块，使用现有 L2 任务构造等价输入输出测试。
3. 设计并实现父子进程消息协议、退出码处理、父进程独立续租、IPC 背压与受控错误转换。
4. 不改变现有线上执行路径，完成单元测试和本地单任务对照。

### 阶段二：L2 会话化与兼容验证

1. 将 L2 runner 改为“领取任务 + 数据读取 + 策略会话监管”，由 StrategySession 子进程批量完成回放、撮合和策略状态维护。
2. 维持 `strategy-worker` 服务可用，但从 L2 runner 的运行依赖和 HTTP 调用中移除。
3. 使用相同脚本、标的、时间区间和参数运行新旧链路，逐项比对信号、委托、成交、费用、收益和错误分类。
4. 验证取消、策略异常、会话崩溃、ClickHouse 异常、Redis 异常与历史任务读取。

### 阶段三：并发与缓存验证

1. 将单副本 L2 runner 资源调整为 4 CPU / 6 GiB。
2. 本地先以 4 个副本完成并发与第 5 条排队测试，再部署服务器。
3. 服务器确认 Swap 没有持续换入/换出、可用内存充足后，将 `TREND_GRID_L2_RUNNER_REPLICAS（L2 runner 副本数）` 设置为 4，通过 `scripts/deploy-server.sh` 同批发布。
4. 同时提交 5 个代表性 L2 任务，确认前 4 个运行、第 5 个排队；验证缓存命中与同键未命中协调。
5. 观察任务吞吐、单任务时长、ClickHouse 查询、CPU、内存、Swap、Redis 内存和错误率。

### 阶段四：稳定化与后续扩展

1. 若四并发下单任务时长、错误率或 ClickHouse 延迟明显恶化，降低副本数或优化数据读取后再扩容。
2. L2 稳定后，单独评估标准 Bar runner 的会话化与独立副本数，不与 L2 扩容同时上线。
3. 在所有回测路径迁移完成并稳定后，再决定是否缩减或替换仅用于编辑辅助的 `strategy-worker`。

## 9. 验证与验收标准

### 9.1 正确性

1. 新旧 L2 链路在相同输入下，策略回调顺序、信号、委托、成交、费用、仓位、做 T 收益和总收益结果一致。
2. `on_quote()` 产生的订单仍严格从后续可见快照开始撮合，不引入前视。
3. 策略快照、参数快照、错误展示和历史任务读取保持兼容。
4. Redis 缓存命中与未命中不会改变结果，只改变读取耗时。

### 9.2 并发与隔离

1. 同时提交五条 L2 任务时，四条任务状态为 `running（运行中）`，第五条保持 `queued（排队中）`。
2. 任意一个策略故意抛出异常、无限等待或耗尽会话资源时，仅该任务失败或取消，其他任务继续执行；父 runner 的租约仍持续有效，不会重复领取该任务。
3. 任意 L2 runner 容器重启时，只影响该副本正在处理的任务；其他副本继续消费队列。
4. 多个 runner 不重复领取任务，取消任务不会在取消后开始执行。

### 9.3 性能与资源

1. 四并发下总完成任务数相较单 runner 串行模式有可测量提升。
2. 同一任务单独运行时，新链路不因移除 HTTP 而出现明显性能回退。
3. ClickHouse、Redis、PostgreSQL 不出现持续错误、连接耗尽或不可恢复积压。
4. 服务器 CPU、内存、磁盘 I/O 与 Swap 在可接受范围内；若 Swap 持续增长，停止继续增加副本数并先排查内存压力。

### 9.4 发布验证

受影响服务包括 `backend`、`l2-runner`、`strategy-worker` 依赖关系、Redis 缓存逻辑及部署 Compose 配置。必须通过 `scripts/deploy-server.sh` 同批发布，不可只重启某一个服务。

发布前检查排队和运行中的 L2 任务；若重建 runner 会中断任务，等待其完成、由用户取消，或经明确确认后标记为发布中断。发布后执行健康检查、单任务回归、四并发任务验证、缓存命中/回源验证和历史任务读取检查。

## 10. 回滚方案

1. 发布异常时回退到上一稳定 Git 提交，并将 `TREND_GRID_L2_RUNNER_REPLICAS（L2 runner 副本数）` 恢复为 `1`。
2. Redis 缓存键采用版本化命名；新旧代码不共用不兼容缓存结构。
3. PostgreSQL 任务和历史结果不因架构切换重算。发生会话异常的任务按失败记录保留，可由用户重新提交。
4. 不删除 `strategy-worker`，直至 L2 直接运行时经过完整服务器验证；因此回滚不依赖临时重建该服务。

## 11. 自审与结论

### 11.1 方案合理性

本方案将“任务调度、行情读取”和“回放、撮合、用户策略执行”从共享 HTTP 服务改为每任务独占的一对父子进程：L2 runner 负责可靠领取、数据读取、监管和持久化，StrategySession 在内存中完成回放、撮合和策略运行。这样既消除共享策略服务单点，也避免按每条 Quote 进行 Pipe 往返，同时不将 PostgreSQL、Redis 和 ClickHouse 数据访问职责交给用户策略进程。

### 11.2 性能判断

消除内部 HTTP 只有在 IPC 保持数据块粒度时才会减少回调开销；逐 Quote Pipe 会因大量上下文切换造成明显回退，已排除。真正解决排队的是四个受限 runner 副本；缓存击穿协调可避免并发后重复读取抵消收益。因此验收必须同时看总吞吐与单任务时延，不能只看容器 CPU 利用率。

### 11.3 风险控制

最大风险包括：多 runner 重复领取任务、子进程异常后状态悬挂、策略进程 Pipe 阻塞、缓存击穿导致重复扫描、四并发争抢 ClickHouse、以及服务器已有 Swap 占用扩大。方案通过保留现有原子领取与尝试令牌、父进程独立续租和统一落库、IPC 背压、缓存锁、固定并发上限和分阶段压测逐项控制。

### 11.4 结论

推荐按“先会话隔离，再四并发上线，最后评估标准 Bar 扩容”的顺序实施。该顺序在不改变策略语义和历史结果的前提下，优先解决多用户排队，并保留对资源、故障和回滚的明确控制。
