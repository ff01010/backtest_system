# 策略代码声明预热与连续历史数据校验方案

## 1. 背景

标准 Bar 自定义策略可能依赖 MA、均线斜率、ATR、MACD 等历史指标。现有方式由用户在回测页面手动填写 `warmupTradingDays（预热交易日）`，存在两份配置不一致、保存与运行类型不一致、用户难以判断合理取值的问题。

以日线方向性策略为例，`MA120` 与其历史斜率需要约 140 根日线。正式回测区间只有 58 根日线时，策略会持续返回空信号，结果表现为订单、成交和收益均为 0。

同时，预热不能为凑足数量而跳过历史交易日缺口。若 2025-09-01 至 2025-09-08 缺少行情，指标序列出现断档，继续计算会降低回测可信度。

## 2. 目标与边界

### 2.1 目标

- 由策略代码声明预热需求，取消前端手工维护。
- 预热需求与策略代码、策略配置和回测快照绑定，保证历史重跑可复现。
- 仅加载回测开始日前连续、完整的历史交易日；预热不足时在提交运行阶段返回可定位异常。
- 预热区只初始化策略状态，不产生订单、成交、费用、收益或正式净值记录。

### 2.2 非目标

- 不自动推导任意 Python 策略实际需要的指标窗口。
- 不修改用户具体的 MA、ATR、止损或开平仓逻辑。
- 不自动修复、补录或跨来源拼接缺失历史行情。
- 不在前端展示或编辑预热天数。

## 3. 设计决策

### 3.1 代码常量是唯一的当前配置来源

标准 Bar 自定义策略可在模块顶层声明：

```python
WARMUP_TRADING_DAYS = 140


def on_bar(bar, state):
  # 策略逻辑
  return []
```

规则：

- 未声明时按 `0` 处理。
- 只接受模块顶层的整数常量，范围为 `0–250`。
- 不接受布尔值、浮点数、字符串、表达式、函数调用或运行时计算值。
- 后端使用 AST 读取，不执行用户策略代码。
- `l2_quote（L2 盘口回放）` 声明大于 0 时拒绝保存；预热仅适用于标准 Bar 回测。

选择代码声明而非统一自适应预热，原因是任意 Python 代码无法可靠推导真实的历史依赖。统一默认值可能不足、过度加载，或掩盖历史数据缺口。

### 3.2 前端不配置、不展示

- 移除“预热交易日数”输入框、可用预热天数、预热风险提示及相关前端传参。
- 不新增只读展示项。
- 用户通过策略代码中的 `WARMUP_TRADING_DAYS` 维护该策略的历史窗口需求。

### 3.3 保存、提交与运行的职责

| 阶段 | 行为 |
| --- | --- |
| 保存策略 | 校验常量语法和值域；将解析值写入当前策略配置及版本快照。正式回测区间继续按现有规则预检。 |
| 提交回测 | 从已保存策略代码重新解析常量；不信任前端的预热字段。 |
| 运行前加载 | 校验正式区间前是否存在数量足够且连续完整的历史交易日。 |
| 数据不足 | 拒绝任务并返回结构化数据异常，不创建成功结果。 |
| Worker | 仅接收经后端确定的预热 Bar 数与数据快照，不自行推导。 |

预热数据不足时，错误应包含策略声明需求和实际连续可用数量，例如：

```text
策略声明需要 140 个预热交易日，实际连续完整数据只有 132 个。
```

## 4. 连续完整数据判定

### 4.1 判定原则

- `qmt_kline_coverage.status = complete` 是行情完整性的权威状态。
- 交易日历只用于给出回测开始日前的预期交易日序列，不作为行情完整性的替代来源。
- 从正式开始日前一天向前倒推，逐个交易日检查覆盖状态；遇到首个非 `complete` 日期即停止。
- 不得通过“取最近 N 个 complete 日期”的方式跨越缺口凑足预热数量。
- 日线优先使用原始 `1d`；原始日线不可用时，必须使用完整 `1m` 派生日线，并对同一预热日期使用同一来源决策。

### 4.2 缺口示例

688981.SH 在 2025-09-01 至 2025-09-08 缺少原始日线和分钟线。若正式回测从 2026-04-01 开始，缺口之后仅有 132 个连续完整交易日，则策略声明 `WARMUP_TRADING_DAYS = 140` 时必须拒绝运行，不能跳过该缺口后继续计算 MA120 或斜率。

## 5. 数据模型与历史兼容

- 新保存策略：将 AST 解析出的预热天数保存至配置参数和策略版本快照。
- 新回测任务：将实际预热日期、来源周期、派生规则和预热 Bar 数写入 `marketDataSnapshot（行情数据快照）`。
- 历史任务：保持原有快照与结果不变。
- 旧策略配置：继续读取既有 `warmupTradingDays（预热交易日）` 以保证历史重跑兼容；策略重新保存后，以代码常量为准。
- 未声明常量的旧策略：当前策略运行按 `0` 个预热日处理，除非使用其历史任务快照重跑。

## 6. 实施步骤

1. 增加策略源码 AST 解析器，读取并校验 `WARMUP_TRADING_DAYS`。
2. 调整保存完整策略、更新策略与提交回测链路，使其使用代码声明值。
3. 移除前端预热输入、预检传参、保存参数和运行参数的手工预热逻辑。
4. 改造行情解析器：按交易日历倒推连续完整预热日期，检测缺口后返回实际连续可用数量。
5. 将统一解析结果传入预检、Runner、Worker 和快照构建，避免来源或预热日期不一致。
6. 调整错误映射，预热不足返回明确的数据异常，不写作系统异常。
7. 更新使用手册，加入常量语法、最长回看窗口计算方法和 MA120/斜率示例。

## 7. 测试计划

- 未声明常量时使用 0 个预热日。
- 合法常量、边界值 0 与 250、非法类型和值域均有保存校验。
- L2 策略声明正数预热被拒绝。
- 保存、提交、Runner 与 Worker 使用同一解析值。
- 连续完整历史足够时，预热 Bar 只初始化状态，不产生订单、成交、费用、收益或正式净值。
- 历史缺口存在时，即使缺口前存在更多完整日期，也不能跨越缺口凑足预热数量。
- 日线原始数据和分钟派生日线两条来源均覆盖连续性判定。
- 旧策略及历史任务快照保持可读取、可重跑。
- 前端不再存在预热输入框、预检参数或手工运行参数。

## 8. 验收标准

1. 用户只需在策略代码中声明 `WARMUP_TRADING_DAYS`，无需在页面填写预热参数。
2. 未声明时策略按 0 个预热日运行；声明非法时保存失败并给出准确提示。
3. 预热不足时运行被拒绝，错误包含声明需求与实际连续可用数量。
4. 预热区不影响正式区间的订单、成交、费用、收益和净值结果。
5. 任意预热数据缺口不会被跳过或静默忽略。
6. 策略版本、回测任务和历史快照均能追溯实际使用的预热配置与数据范围。
