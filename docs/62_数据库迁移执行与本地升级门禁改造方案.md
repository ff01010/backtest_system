# 数据库迁移执行与本地升级门禁改造方案

## 一、文档状态

- 状态：待实施
- 适用范围：PostgreSQL 数据库迁移、服务器发布脚本、本地后端测试入口
- 不涉及：前端功能、回测运行时、策略执行语义、业务依赖升级
- 当前生产基线构建：`6483efebcb183605be69d4453bc2d11f6780e0a1`
- 当前生产基线迁移：`001` 至 `056`
- 当前待应用迁移：`057` 至 `059`

## 二、背景与问题

当前生产和测试环境的迁移服务都会遍历 `db/migrations/*.sql`，并在每次发布时重新执行全部历史迁移：

```bash
for file in /migrations/*.sql; do
  psql ... -f "$file"
done
```

该实现把所有历史迁移都隐式要求为“在任意未来数据库状态下永久可重放”。这比正常的数据库迁移契约更严格，也与包含数据回填、触发器、RLS 策略和约束收紧的迁移不兼容。

本次发布已经连续暴露两个问题：

1. `057_strategy_complete_version_baseline.sql` 在 `SET ROLE quant_backtest_owner` 后没有管理员 RLS 会话上下文，迁移查询看不到受 `FORCE ROW LEVEL SECURITY` 保护的数据，将有效记录误判为孤立记录。
2. 补齐管理员 RLS 会话上下文后，重放 `037_shared_backtest_status_audit.sql` 时，历史回填仍被旧的审计表写入策略拒绝。首次执行 `037` 时先回填、后启用 RLS，因此能够成功；再次执行时表已经启用 `FORCE RLS`，回填中的 `actor_user_id` 是历史记录所有者，而当前迁移身份是系统管理员，两者不相等，触发 RLS 拒绝。

`ON CONFLICT DO NOTHING` 不能规避该问题，因为 PostgreSQL 会在冲突处理前执行 RLS 校验。

现有本地测试只覆盖空数据库首次安装，没有构造“上一生产版本结构 + 普通用户数据 + 已启用 FORCE RLS”的升级场景，因此无法在合并前发现该问题。

## 三、改造目标

### 3.1 功能目标

1. 每个数据库迁移只执行一次，发布时只执行尚未应用的迁移。
2. 已应用迁移文件不可修改；内容发生变化时，迁移执行器必须在写数据库前失败。
3. 生产与本地测试调用同一个迁移执行模块，避免两套实现漂移。
4. 发布停服前执行只读迁移计划，提前发现基线、校验和和顺序问题。
5. 本地真实 PostgreSQL 测试必须覆盖上一生产版本升级路径。
6. 保留现有 RLS 隔离，不授予迁移角色 `BYPASSRLS`，不关闭 `FORCE ROW LEVEL SECURITY`。
7. 首次切换新机制时，安全登记生产库已完成的 `001` 至 `056`，实际只执行 `057` 至 `059`。

### 3.2 非目标

1. 不修改已经执行过的 `001` 至 `056`，包括 `037`。
2. 不通过永久放宽审计策略解决迁移问题。
3. 不把 PostgreSQL 超级用户作为业务迁移身份。
4. 不在应用启动过程中执行 DDL。
5. 不引入 Flyway、Liquibase 等外部依赖。
6. 不在本次改造中接入尚未确定的远程 CI 平台。

## 四、核心设计决策

### 4.1 建立统一迁移模块

新增统一迁移执行脚本，建议路径：

```text
scripts/run-database-migrations.sh
```

该模块只暴露两个外部接口：

```bash
scripts/run-database-migrations.sh plan
scripts/run-database-migrations.sh apply
```

`plan` 为只读操作，负责发现并验证计划；`apply` 负责取得迁移锁并应用计划。生产 Compose、测试 Compose、服务器发布脚本和本地升级测试都必须通过这两个接口调用迁移，不再自行实现文件遍历、角色切换或会话变量设置。

模块内部统一负责：

- 迁移文件发现、编号解析和排序；
- 重复编号、非法命名和历史插队检查；
- SHA-256 校验；
- 已应用迁移查询；
- 生产历史基线接管；
- PostgreSQL advisory lock；
- `SET ROLE quant_backtest_owner`；
- 管理员 RLS 会话上下文；
- 待应用迁移执行；
- 迁移结果登记；
- 可诊断的失败输出。

### 4.2 增加迁移记录表

新增迁移基础设施表 `app_schema_migration`，建议字段如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `version` | integer | 迁移编号，主键 |
| `filename` | text | 完整文件名，唯一 |
| `sha256` | char(64) | 应用时文件校验和 |
| `applied_build_id` | char(40) | 执行或登记迁移的构建 |
| `application_kind` | varchar(16) | `baseline` 或 `migration` |
| `applied_at` | timestamptz | 完成时间 |

该表由 `quant_backtest_owner` 拥有，不向应用数据库角色授予任何权限，也不承载用户数据。建表 SQL 放入独立的迁移执行器基础设施目录，由 migrate 服务管理，不混入业务应用启动流程。

记录表只保存已经成功完成的迁移。失败迁移不得写入成功记录。

### 4.3 迁移文件不可变与校验和

迁移执行器对每个已应用文件计算 SHA-256，并与 `app_schema_migration.sha256` 比较：

- 文件不存在：失败；
- 文件名或编号冲突：失败；
- 已应用文件校验和变化：失败；
- 新迁移编号小于或等于已应用最大编号：失败；
- 待应用文件连续且合法：进入执行计划。

这项校验使“不得修改已执行迁移”从人工约定变成可执行契约。

### 4.4 生产历史基线接管

现有生产数据库尚无迁移记录表，不能通过猜测表结构直接判定历史版本。首次切换采用“激活构建 + 固定校验和清单”接管：

1. 读取 `app_deployment_state.current_build_id`。
2. 当前生产激活构建必须等于 `6483efebcb183605be69d4453bc2d11f6780e0a1`。
3. 读取该构建对应的历史基线清单。
4. 清单包含 `001` 至 `056` 的文件名和 SHA-256。
5. 验证当前工作区的 `001` 至 `056` 与清单完全一致。
6. 验证生产数据库存在 `056` 所要求的关键结构和语义纪元记录。
7. 所有验证通过后，在一个事务中将 `001` 至 `056` 登记为 `baseline`。
8. `057` 至 `059` 保持待应用状态，由迁移执行器正常执行。

已通过 Git 历史确认：生产激活构建只包含到 `056`，当前分支相对该构建仅新增 `057`、`058` 和 `059`，没有修改 `001` 至 `056`。

如果数据库当前激活构建、历史清单或关键结构任一不匹配，`plan` 必须失败，不得自动提高基线版本，也不得开始停服。

完成首次接管后，后续发布以 `app_schema_migration` 为唯一迁移事实来源，不再依赖构建映射。

### 4.5 RLS 执行身份

每个待应用迁移继续使用以下身份：

```sql
SET ROLE quant_backtest_owner;
SELECT set_config(
  'app.current_user_id',
  '00000000-0000-0000-0000-000000000001',
  false
);
SELECT set_config('app.current_is_admin', 'true', false);
```

设计约束如下：

- 不给 `quant_backtest_owner` 增加 `BYPASSRLS`；
- 不在迁移执行器中全局关闭 RLS；
- 普通用户数据迁移必须在真实 RLS 下通过；
- 合法的跨用户历史回填如果与现有策略冲突，必须在该迁移自己的事务中显式调整并恢复策略，失败时由事务整体回滚；
- 本地升级测试必须使用相同角色和会话变量，不能使用超级用户成功作为正确性证明。

### 4.6 事务契约

历史迁移 `001` 至 `059` 保持原文件不变。生产首次接管时 `001` 至 `056` 只登记、不重放；`057` 至 `059` 按现有事务边界执行，成功后登记。

从 `060` 开始采用新的迁移契约：

1. 迁移文件本身不再写 `BEGIN` 和 `COMMIT`。
2. 迁移执行器使用 `psql --single-transaction` 包裹迁移 SQL 和迁移记录写入。
3. 业务结构变化和 `app_schema_migration` 记录在同一事务中提交。
4. 任一语句失败时，两者同时回滚。
5. 契约测试禁止新迁移自行提交事务。

历史迁移在空数据库初始化时仍按原事务执行；此时尚无用户流量，执行成功后逐条登记。生产切换只涉及已确认幂等且尚未应用的 `057` 至 `059`。

### 4.7 并发控制

`apply` 必须在 PostgreSQL 中取得固定 advisory lock，并在整个迁移执行期间持有。另一个迁移进程只能等待或以明确错误退出，不能并发执行不同文件。

锁必须由数据库会话持有，不能只使用宿主机文件锁，因为未来可能从不同宿主机连接同一数据库。

进程退出、连接断开或容器被终止后，PostgreSQL 自动释放会话锁。

## 五、发布流程改造

当前发布脚本在停服后才运行迁移，因此迁移计划错误会直接造成业务停机。调整后的流程如下：

```text
检查仓库状态并拉取代码
  → 启动并检查 PostgreSQL
  → migrate plan（只读）
  → 校验 Compose 和发布配置
  → 关闭新回测提交门禁
  → 等待运行中任务和执行槽位归零
  → 停止提交与辅助服务
  → 取得发布屏障
  → migrate apply
  → 构建并启动同批服务
  → 健康检查和兼容性检查
  → 激活发布版本
  → 开放提交门禁
```

`plan` 必须输出：

- 当前数据库是否已经启用迁移记录；
- 当前历史基线或已应用最大版本；
- 当前构建标识；
- 待应用迁移列表；
- 校验和检查结果；
- 最终 `ready` 或明确失败原因。

`plan` 失败时不得关闭门禁、停止服务或写数据库。

`apply` 失败时保持门禁关闭并输出精确失败文件。不得在数据库状态未验证的情况下自动开放门禁。

## 六、本地升级测试设计

### 6.1 当前测试缺口

`scripts/test-backend.ps1` 当前只创建空 PostgreSQL，再运行全部迁移和后端测试。该路径可以验证首次安装，但无法验证：

- 历史迁移已经启用 RLS 后的升级；
- 普通用户数据存在时的数据回填；
- 已执行迁移是否被错误重放；
- 已应用文件是否被篡改；
- 两个迁移进程是否会并发执行。

### 6.2 新增升级场景

增加独立的 PostgreSQL 17 升级测试数据库，执行以下流程：

1. 初始化与生产一致的数据库角色。
2. 只执行 `001` 至 `056`。
3. 写入完全合成的普通用户、策略、策略版本、回测、共享回测和审计记录。
4. 确认相关表已经启用 `FORCE ROW LEVEL SECURITY`。
5. 写入上一生产构建对应的 `app_deployment_state`。
6. 运行统一迁移执行器 `plan`。
7. 断言计划只包含 `057` 至 `059`。
8. 运行 `apply`。
9. 验证 `057` 的完整策略基线、`058` 的搜索投影结构和 `059` 的回填结果。
10. 验证 `037` 没有被重放，原审计记录数量和内容没有异常变化。
11. 再次运行 `plan` 和 `apply`，断言 `pending=0` 且数据库业务事实不变。

所有样本必须是测试环境生成的合成数据，不读取或保存生产用户代码和参数。

### 6.3 必须覆盖的测试矩阵

| 场景 | 验收结果 |
| --- | --- |
| 空数据库首次安装 | `001` 至当前版本全部成功且均有记录 |
| 上一生产版本升级 | 只执行 `057` 至 `059` |
| 升级后重复执行 | `pending=0`，无数据变化 |
| 普通用户与管理员 RLS | 隔离策略在升级前后保持有效 |
| 已应用文件校验和变化 | `plan` 在写数据库前失败 |
| 重复迁移编号 | 本地契约测试失败 |
| 历史编号插队 | 本地契约测试失败 |
| 并发运行两个 `apply` | 只有一个进程执行迁移 |
| 故意失败的新格式迁移 | DDL 和迁移记录同时回滚 |
| 未知生产构建首次接管 | `plan` 失败，不自动登记基线 |
| 基线结构缺失 | `plan` 失败，不自动登记基线 |

### 6.4 本地统一入口

继续使用现有入口：

```powershell
.\scripts\test-backend.ps1
```

该命令必须同时执行：

1. 生产兼容的上一版本升级测试；
2. 空数据库首次安装；
3. 后端单元与 PostgreSQL 集成测试；
4. 迁移契约测试。

只运行普通 pytest、未运行升级数据库场景，不能作为本次改造的完整验收结果。

仓库当前没有远程 CI 配置，因此本次先建立确定性的本地门禁和服务器停服前门禁。若要在代码托管平台强制阻止未验证合并，需要在确认实际使用的 Git 平台后，将同一命令接入必需检查；不能另写一套简化迁移测试。

## 九、风险与控制措施

### 9.1 错误登记生产基线

风险：把未实际执行的历史迁移登记为完成，导致缺失结构被永久跳过。

控制：基线必须同时绑定激活构建、固定校验和和结构验证；未知构建一律失败，不提供自动猜测或强制跳过参数。

### 9.2 历史迁移曾被修改

风险：当前工作区中的历史 SQL 与生产激活构建不一致。

控制：基线清单固定 `001` 至 `056` 的 SHA-256；首次接管和后续发布都检查不可变性。

### 9.3 新迁移绕过 RLS

风险：迁移使用超级用户成功，但生产所有者角色失败，或意外放宽普通用户隔离。

控制：升级测试使用真实所有者角色和 GUC；RLS 必须由 PostgreSQL 集成测试验证；禁止使用 Fake 或 Mock 代替。

### 9.4 并发迁移

风险：两个发布流程同时判断同一迁移为待执行并重复运行。

控制：在数据库中持有全程 advisory lock，锁外不得执行 DDL 或写迁移记录。

### 9.5 新事务契约与历史文件不兼容

风险：历史文件自带事务，直接由执行器再次包裹会产生提前提交。

控制：`001` 至 `059` 走明确标识的 legacy 路径；`060` 起执行器统一事务；契约测试禁止两类格式混用。

### 9.6 本地通过但生产数据仍有新边界

风险：合成数据不能覆盖所有生产数据组合。

控制：迁移应包含只读前置断言；服务器 `plan` 在停服前运行；涉及普通用户数据的改动继续遵守远程普通用户样本回归要求，但不得将生产样本写入仓库或测试固件。

## 十、验收标准

1. 生产和测试 Compose 不再包含 `for file in /migrations/*.sql`。
2. 生产和测试均调用同一个迁移执行脚本。
3. `plan` 在生产停服前完成且不写数据库。
4. 生产首次接管只把 `001` 至 `056` 登记为基线。
5. 首次接管的待执行列表严格为 `057`、`058`、`059`。
6. 未修改 `037` 及其他已执行历史迁移。
7. 执行完成后再次运行显示 `pending=0`。
8. 修改任一已应用迁移后，`plan` 因校验和不一致失败。
9. 上一生产版本升级测试在本地稳定通过，并能在旧实现下稳定复现当前 `037` 错误。
10. 空数据库首次安装测试通过。
11. 并发、失败事务和 RLS 集成测试通过。
12. 完整 `scripts/test-backend.ps1` 实际执行通过。
13. 服务器发布成功后，健康检查、历史任务兼容检查和代表性新功能验证通过。
14. 提交门禁只在应用健康、版本激活和迁移状态一致后开放。

## 十一、回退原则

1. 代码尚未执行 `apply` 时，可直接回退迁移执行器和发布脚本，不影响数据库。
2. `plan` 失败不产生数据库变更，无需数据库回退。
3. 基线登记只写迁移元数据，不改业务数据；如果登记事务失败则整体回滚。
4. 已成功执行的前向业务迁移不通过删除表、删除列或重写历史迁移回退。
5. 发布失败时保持提交门禁关闭，先确认迁移记录与实际结构一致，再决定恢复旧服务或继续前向修复。
6. 任何生产回退都不得清理用户策略、回测、审计记录或迁移记录。
