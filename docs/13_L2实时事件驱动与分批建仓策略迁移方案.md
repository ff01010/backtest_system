# L2 实时事件驱动与分批建仓策略迁移方案

## 1. 背景与结论

当前基础 L2 回测采用 `order_driven_quote（订单驱动盘口回放）`：策略只在 `on_bar（Bar 回调）` 时运行；没有待成交订单时，runner 不读取 3 秒快照。这对纯 Bar 策略是正确且高效的，但不能等价迁移 QMT 的 `on_tick（实时行情回调）` 策略。

`分批建仓做多 V2_1` 同时依赖两类事件：

- 已完成 1 分钟 Bar 用于确认三根收盘价形成的顶/底结构；
- 实时行情用于开盘建仓、止盈止损、14:56 收盘处理，以及“分钟内先跌破触发价、该分钟收盘仍在触发价下方”这一反手确认条件。

推荐结论：为 L2 自定义脚本增加可选的 `on_quote（3 秒盘口快照回调）` 与 `on_order_event（委托回报）`，仅对声明连续快照需求的策略启用全量 3 秒行情回放；纯 `on_bar` 策略继续使用现有订单驱动模式。该策略以 `directional_holding（方向性持仓策略）` 接入，避免当前 `core_position_overlay（底仓增强策略）` 的收盘恢复底仓规则改变原脚本的持仓语义。

本方案只使用现有 3 秒十档快照。它能重现“在可见 3 秒采样点发生”的实时判断，不能声称重现原 QMT 一秒 Tick 之间不可见的价格路径。

## 2. 目标、边界与不变量

### 2.1 目标

1. 让一个 L2 脚本同时接收完成 Bar 与时间有序的 3 秒快照。
2. 保持 `on_bar` 策略的查询量、成交时点和性能优化不变。
3. 使分批建仓策略只在实际成交回报后推进阶段、均价和反手状态。
4. 保存事件模式、快照粒度、脚本版本和性能计数，保证结果可追溯。

### 2.2 本次范围

- 数据：`quant.tick_quote` 适配后的 3 秒十档盘口和由其聚合的 1 分钟 Bar。
- 事件：`on_bar`、`on_quote`、`on_order_event`。
- 委托：沿用现有主动吃单、十档深度、部分成交、手续费和无前视撮合。
- 策略：将给定 QMT 的 V6 分批建仓、止盈、第四阶段止损、反手确认、反手部分退出及 14:56 处理迁移为系统脚本。

### 2.3 不在本次范围

- 一秒 Tick、逐笔成交/委托/撤单和被动限价排队模拟；
- 融券券源、保证金、借券费率、强平等真实信用账户规则；
- 让底仓增强策略保留隔夜反手残仓；
- 改变原脚本的仓位比例、拐点条件、止盈止损阈值或反手条件；
- Redis Bar 缓存格式变更或远端 ClickHouse 表结构调整。

## 3. 事件协议与时间语义

### 3.1 新脚本协议

脚本仍必须定义 `on_bar(bar, state)`，并可选定义：

```python
def on_quote(quote, state):
  return []

def on_order_event(event, state):
  return None
```

`quote（3秒盘口快照）` 提供 `time（时间）`、`tradeDate（交易日）`、`symbol（标的）`、`lastPrice（最新价）`、`bids（十档买盘）`、`asks（十档卖盘）`。每档含 `price（价格）` 与 `volume（可见量）`；缺失或零价盘口保持为不可成交，不能伪造价格。

`on_order_event` 接收 `accepted（已受理）`、`partial_fill（部分成交）`、`filled（完全成交）`、`cancelled（已撤销）`、`rejected（已拒绝）`。成交事件包含 `quantity（本次成交量）`、`cumulativeQuantity（累计成交量）`、`price（成交价）`、`commission（手续费）`、`time（时间）` 和策略提交的 `clientOrderKey（客户订单键）`。

`clientOrderKey` 由策略在 action 中填入，用于把异步成交回报稳定关联到某一阶段目标；引擎不允许该键覆盖其他未终结订单。

### 3.2 严格无前视顺序

同一时间点按以下顺序处理：

1. 先用当前快照撮合此前已经生效的订单；
2. 将因此产生的委托回报交给 `on_order_event`；
3. 再调用当前快照的 `on_quote`；
4. `on_quote` 新产生的订单只能从严格晚于当前快照的下一条快照开始成交。

已完成 Bar 与同时间快照仍遵循现有 Bar 完成边界：Bar 的信号不得使用该 Bar 结束后才出现的盘口。策略在 `on_quote` 中记录的“分钟内跌破”标记，只有该分钟完成 Bar 的正式收盘价仍满足条件时才允许反手，避免用中间快照直接前视收盘。

### 3.3 回放模式声明

策略版本增加 `quoteMode（盘口模式）`：

- `order_driven`：默认。仅在有待成交订单或日终结算需要时读取下一条盘口；仅需要 `on_bar`。
- `continuous`：要求 `on_quote`。交易时段内按时间顺序回放全部有效 3 秒快照，即使当前没有订单。

后端保存脚本时校验：`continuous` 必须定义 `on_quote`；`order_driven` 不得依赖它。历史版本未提供该字段时一律按 `order_driven` 处理，保证兼容。

## 4. 回测链路改造

### 4.1 runner 与数据源

`l2_runner` 根据 `quoteMode` 选择路径：

1. `order_driven` 保留现有 `next_quote_after` 按需查询逻辑，不回归为全量扫描。
2. `continuous` 用 keyset 分页顺序读取交易时段内的快照，与当天 Bar 合并为单一时间线后分块发送 worker；不得把整日快照一次性载入内存。
3. Bar 与 Quote 使用稳定的 `datetime（时间）+ sequence（序号）` 排序。数据源没有稳定序号时，适配器必须明确拒绝同时间多条记录，不能以数据库偶然返回顺序撮合。
4. 午间休市不合成跨时段 Bar；连续回放只覆盖 09:30 至 11:30、13:00 至 15:00 的有效快照。

连续模式会读取更多数据，这是实时策略语义的必要成本。常用周期 Bar 仍优先使用 Redis 缓存；缓存只减少 Bar 聚合开销，不替代连续盘口事件。

### 4.2 worker、引擎与订单回报

worker 会话新增单条 Quote 处理与委托事件队列。L2 引擎在每次订单状态变化后，先完成账本更新，再同步投递不可变的事件快照；脚本不能修改账本、订单对象或引擎内部状态。

动作扩展 `clientOrderKey`，其余 `action（动作）`、`quantity（数量）`、`reason（原因）` 维持既有约束。对于“先平现有多头，余额再开空”的反手，迁移脚本生成顺序相关的两笔动作：先 `sell_close（平多）`，收到对应完成/部分成交回报后，才按实际已平数量决定 `sell_open（开空）`。不得直接把不同方向净额写入一个持仓变量。

所有任务结果增加：`quoteMode（盘口模式）`、`quoteGranularitySeconds（快照粒度秒数）`、`eventProtocolVersion（事件协议版本）`、行情源/适配器版本、脚本哈希，以及 Bar 数、读取快照数、查询耗时、worker 耗时和回调次数。

### 4.3 分批建仓策略迁移

新增系统策略模板 `staged_entry_long_v6_l2`，保留原始默认常量和计算方法：总目标 18,000 股、开盘 1%、后续 2%/4%/8%/16% 分批、100 股取整、基于三个已完成 1 分钟 Bar 的顶底确认、1% 固定止盈、第四阶段后以第四阶段信号价止损、第三阶段后反手监控、33% 反手仓位与 16% 反手退出数量。

迁移时移除 QMT 账户、订阅、`passorder`、文件持久化和平台日志调用，改为 `state（策略状态）` 与标准 action。阶段推进、方向锁定、平均成本和反手状态只在 `on_order_event` 的成交事件中更新；订单被拒绝、取消或部分成交必须保留可恢复状态，不能假定下单即成交。

该脚本的反手后“手动接管残仓”原语义与底仓增强策略的日终恢复冲突。因此首版固定标记为 `directional_holding`：常规前向仓位仍由策略在 14:56 通过 Quote 主动退出；原脚本明确手动接管的反手残仓不由引擎擅自恢复或强平。运行该策略需明确开启 `allowShort（允许做空）`。

源策略中的 `600584.SH`、账户号、QMT 订阅、下单接口、文件持久化和监控目录均属于运行环境配置，不属于交易执行逻辑。迁移模板不得绑定标的，始终使用回测请求和事件上下文中的 `symbol（标的）`；分批数量、顶底确认、止盈止损、反手条件和尾盘处理保持原有交易逻辑。

## 5. 实施步骤

1. 扩展脚本元数据、语法校验与运行时适配器，支持 `quoteMode`、`on_quote`、`on_order_event` 和 `clientOrderKey`。
2. 扩展 worker API 与 L2 引擎，按“先撮合旧单、再回报、后回调”的顺序处理快照；保留旧 Bar/Quote 接口兼容层。
3. 为连续模式实现分页事件合流和稳定排序；订单驱动模式代码路径与性能指标保持独立。
4. 扩展任务快照、结果适配器和错误信息，记录事件协议、行情粒度和性能数据。
5. 编写并注册 `staged_entry_long_v6_l2` 模板，使用填充/拒单回报推进其状态机。
6. 更新 `docs/玄龄回测系统使用手册.md`，准确说明新增回调、字段、成交时点、连续回放成本和 3 秒采样限制。
7. 使用固定小样本、真实短区间和前端任务结果分别回归验证。

## 6. 验证与验收

### 6.1 协议与无前视

- `on_quote` 的新订单不能被同一快照成交，下一条快照才可成交。
- 一次部分成交先触发 `partial_fill`，完全成交再触发 `filled`；回报数量、均价、现金与账本一致。
- 同时存在 Bar、旧订单成交和 Quote 回调时，顺序严格符合第 3.2 节。
- 纯 `on_bar` 脚本不读取无订单区间快照，现有订单驱动测试全部保持通过。

### 6.2 V6 行为

- 开盘基线、四级递进建仓、后续低点限制及方向锁定与源脚本的固定样例一致。
- 第三阶段后只有“快照内已跌破且同分钟 Bar 收盘仍跌破”才反手；任一条件缺失均不得反手。
- 固定止盈、第四阶段止损、反手 16% 退出、拒单和部分成交后的状态均可复现。
- 14:56 的常规前向仓位按当时及之后有效盘口平仓；手动接管残仓按方向性持仓规则保留。

### 6.3 性能与可追溯

- 对同一数据，`order_driven` 的实际读取快照数不因本改造增加。
- `continuous` 结果展示总快照数、分页次数、数据源耗时、worker 耗时和回调次数；不以预估速度代替实测。
- 以任一有完整 L2 数据的标的运行真实短区间连续回放，记录实际耗时、结果哈希和数据源版本；前端概览、收益、回撤、信号及成交明细均可显示。

## 7. 自审与前置风险

| 风险 | 处理 |
| --- | --- |
| 3 秒数据遗漏一秒级触发 | 结果明确标注 3 秒采样；不将其描述为逐 Tick 精确回放。 |
| 阶段在提交时推进导致假成交 | 只以 `on_order_event` 成交回报推进状态。 |
| 同快照成交产生前视 | 采用新单严格在下一快照生效的边界测试。 |
| 连续回放拖慢纯 Bar 回测 | 以显式 `quoteMode` 隔离两条路径，默认仍为订单驱动。 |
| 原脚本反手残仓与底仓做 T 冲突 | 首版固定方向性持仓；禁止把它误配为底仓增强。 |
| 开盘价字段不完整 | 实施前核验 Quote 适配器能提供首个有效快照价格；若不能代表官方开盘价，任务需告警并以首个可见 `lastPrice（最新价）` 作为明确的降级规则，不能静默替换。 |
| 做空被误解为真实融券 | 明确为价格方向模拟；融券库存、成本和保证金不在本期。 |

## 8. 执行前确认

推荐按本方案实施，并以 `directional_holding` 承载该策略。实施前仅需确认两项业务边界：

1. 原脚本反手后的“手动接管残仓”是否按原意允许跨日保留；本方案默认允许，因其比尾盘强平更符合“不改变逻辑”。
2. 已确认源策略的标的限制属于运行环境配置，模板使用当前回测标的，不再保留该限制。
