# 订单驱动日内盘口流游标优化方案

日期：2026-08-17  
状态：实验结束，未采纳

## 实验结论（2026-08-17）

以 `688126.SH`（标的）、`5m`（周期）、2026-06-04 至 2026-07-09 的相同策略和参数对比：`day_stream`（日内盘口流）将盘口查询次数从 235 次降至 50 次，但顺序读取了 93,489 条快照，远高于 `prefetch`（固定窗口预读）的 25,347 条；总耗时 12.221 秒，仅比最快的 `prefetch` 基线 12.591 秒改善约 3%。

原因是订单驱动策略在无订单区间会一次处理多个 Bar；后续出现订单时，流游标必须顺序消费此前所有空档快照才能到达目标时点，查询次数减少却放大了实际扫描与解码量。因此该方案不适合当前稀疏信号的回测路径。

同时发现旧 `prefetch` 的尾盘结算会误用预读窗口中的旧快照，已改为查询 `14:57:00` 前真实最后一条连续竞价快照。为避免两条路径的结果差异，现已移除 `day_stream` 的配置、客户端流接口、游标、指标和测试，仅保留修复后的 `prefetch`。本文件作为未采纳实验记录保留；后续应聚焦 ClickHouse 实际扫描量、物理排序/投影和针对性预读优化。

## 1. 背景与结论

当前 L2 回测已将临时 Bar 缓存到专用 Redis。相同标的、日期区间和周期的第二次回测可直接命中 Bar 缓存，Bar 读取耗时已显著下降；但盘口读取仍是主要瓶颈。

本机测试中，同一策略、标的、区间连续运行两次，第二次已命中全部 25 个交易日的 Bar 缓存：

| 指标 | 首次 | 第二次（Bar 缓存命中） |
| --- | ---: | ---: |
| `barReadMs`（Bar 读取耗时） | 1333.745 ms | 67.287 ms |
| `sourceReadMs`（盘口源数据读取耗时） | 6559.781 ms | 5542.205 ms |
| `quoteQueries`（盘口查询次数） | 235 | 235 |
| `quoteRowsPrefetched`（预读盘口行数） | 25347 | 25347 |
| `quotesFetched`（实际交给撮合的盘口数） | 314 | 314 |
| `totalElapsedMs`（任务总耗时） | 14754.163 ms | 12590.723 ms |

结论：Bar 缓存已生效，但当前“每次待成交订单预读固定 128 条盘口”的模式存在明显过读。多数预读盘口随后被跳过，且同一交易日会产生多次 ClickHouse 查询。下一步应优化回测内的盘口读取路径，而不是将原始 L2 全量复制到 Redis。

推荐实现“订单驱动日内盘口流游标”：在一个交易日首次出现待成交订单时，仅建立一条该交易日连续竞价时段的有序盘口流；后续订单共用游标顺序读取、按需跳过，不再为每个信号重新执行固定窗口预读。

## 2. 目标、范围与不变量

### 2.1 目标

- 将订单驱动模式下的 ClickHouse 盘口查询次数由“每次待成交信号一次”降低为“每个活跃交易日一条流”，外加必要的每日时间唯一性校验。
- 在 Bar Redis 已命中的前提下，实测降低 `sourceReadMs`（盘口源数据读取耗时）和 `totalElapsedMs`（任务总耗时）。
- 保持现有 L2 撮合语义、策略信号、成交结果与资金曲线不变。

### 2.2 本次范围

- 仅优化 L2 的订单驱动盘口读取路径。
- 保留现有 `_QuotePrefetchBuffer`（固定窗口预读缓冲）实现，作为可配置的回退路径。
- 使用现有 ClickHouse HTTP 长连接和 gzip 压缩；查询结果改为顺序可读取的 `JSONEachRow` 格式。
- 增加可观测指标、自动化测试和同口径性能对比。

### 2.3 不在本次范围

- 不将原始 3 秒十档盘口全量写入 Redis。
- 不修改 ClickHouse 表结构、排序键或历史数据。
- 不新增 Python 依赖，不切换 ClickHouse 原生 TCP 驱动。
- 不改变 `continuous`（连续回放）模式；该模式仍按完整盘口序列回放。
- 不改变策略 API、前端参数、成交规则或历史回测结果展示。

### 2.4 必须保持的正确性边界

- Bar 仍是回测调度器：没有待成交订单时不得读取或向策略 worker 发送盘口。
- 订单只可使用其生效时间之后的第一条可用盘口；不得将未来盘口提前暴露给 worker。
- 若下一条盘口时间晚于下一根 Bar 的处理时间，必须先处理该 Bar，再继续盘口回放。
- 保持连续竞价时段过滤、涨跌停单边盘口处理、部分成交、尾盘处理、撤销和失败语义。
- 任务取消、异常、日切换后必须关闭流连接，不得保留泄漏连接或后台读取。

## 3. 当前问题定位

当前订单驱动路径使用 `_QuotePrefetchBuffer`（固定窗口预读缓冲）：每次缓冲为空时，按“订单生效时间之后”向 ClickHouse 查询固定数量的盘口，默认一次 128 条。

这种方式有两个相反的目标：

1. 预读窗口较大时，单次查询次数减少，但会读取大量最终不会参与撮合的盘口；
2. 预读窗口较小时，额外数据减少，但会因频繁查询而增加 HTTP、ClickHouse 解析和结果反序列化开销。

现有实测中，`quoteRowsPrefetched`（预读盘口行数）为 25347，而 `quotesFetched`（实际交给撮合的盘口数）仅为 314，说明大部分读取的数据在游标推进时被丢弃。即使 ClickHouse 与项目部署在同一台服务器，仍需要经过 Docker 网络、HTTP 协议、ClickHouse 查询执行、JSON 解码及 Python 调度；瓶颈不是单纯的“硬盘读数据”。

现有 HTTP 客户端已经复用线程内 `HTTPConnection`（HTTP 连接），因此改用 WebSocket 不会消除主要问题；原生 TCP 驱动需要引入新依赖，也不应在未验证查询次数优化收益前提前实施。

## 4. 目标架构

```text
Bar 回放器
  │
  ├─ 无待成交订单 ──────────────────────────────── 不读取盘口
  │
  └─ 首次出现待成交订单
       │
       ├─ 当日时间唯一性校验（每日一次）
       │
       └─ 建立当日连续竞价盘口流（每日最多一条）
            ClickHouse HTTP 长连接 + gzip + JSONEachRow
                         │
                         ▼
                  日内流游标
                  ├─ 顺序跳过早于订单生效时间的行
                  ├─ 仅将合格盘口发送给策略 worker
                  ├─ 无订单时暂停消费
                  └─ 日终 / 取消 / 异常时关闭
```

流游标仅在当前任务内存中存在，不跨任务、不写 Redis。Redis 继续只缓存可复用的聚合 Bar；原始 L2 盘口保持在 ClickHouse，避免 Redis 内存被高频明细数据挤占，也避免数据版本和失效策略复杂化。

## 5. 详细设计

### 5.1 日内流查询

为 `ClickHouseL2Adapter`（ClickHouse L2 数据适配器）增加顺序读取接口，按标的、交易日、连续竞价时间段排序返回 `JSONEachRow` 行流。

- 查询条件与现有 `quotes_after`（指定时间后查询）保持一致，包括标的、交易日和连续竞价过滤。
- 排序保持时间优先；若源表存在同一时间多条记录，继续使用现有序列字段作为次序，确保与旧路径一致。
- 继续使用现有 HTTP 长连接和 `Accept-Encoding: gzip`（gzip 压缩响应）。
- 不一次性将全天盘口反序列化为 Python 列表；按行解码并由游标逐条消费。
- 时间唯一性校验继续保留，每个交易日最多一次，并复用现有校验结果。

### 5.2 订单与游标时序

新增 `DayQuoteStreamCursor`（日内盘口流游标），由回测 runner 按“标的 + 交易日”维护。

处理顺序如下：

1. Bar 完成并调用策略；策略产生订单后，订单携带现有的生效时间。
2. 当天首次出现待成交订单时，惰性创建该日流游标；此前不读取任何盘口。
3. 游标顺序读取盘口：早于或等于订单生效时间的盘口只推进游标，不传给 worker。
4. 第一条晚于订单生效时间、且满足连续竞价过滤的盘口，按当前撮合规则交给 worker。
5. 若该盘口时间已晚于下一个 Bar 的处理边界，则先处理下一根 Bar；盘口仍保留在游标中，不能被提前发送。
6. 没有待成交订单时暂停消费流；后续订单到来后从当前位置继续。
7. 日切换、回测完成、取消或异常时关闭游标与连接。

这样仍是严格的“订单驱动”，并非完整 `on_quote`（逐盘口回放）。流连接可以顺序准备数据，但 worker 永远只收到订单在当时可见的盘口。

### 5.3 失败恢复与资源释放

- 流在读取过程中出现可恢复的连接异常时，从 `lastConsumedTime`（最后已消费盘口时间）之后重新建立流；同一时间多条记录时使用序列字段或等价游标保证不重复、不遗漏。
- 无法可靠续接时，按现有任务失败机制结束任务，并记录可定位的系统错误日志。
- 取消请求优先终止流读取并关闭连接；不得等待整日数据传输完成。
- 每个任务、每个交易日同时最多保留一个盘口流；多任务之间互不共享内存游标。

### 5.4 配置与回退

新增 `TREND_GRID_L2_QUOTE_READ_MODE`（L2 盘口读取模式）配置：

| 配置值 | 含义 |
| --- | --- |
| `prefetch` | 沿用现有固定窗口预读缓冲。 |
| `day_stream` | 使用本方案的订单驱动日内盘口流游标。 |

初始发布保留 `prefetch` 作为默认安全回退模式；通过测试和线上同口径数据验证后，再单独决定是否将默认值切换为 `day_stream`。任何异常均可仅改配置回退，无需回滚数据库或历史缓存。

### 5.5 性能指标

在现有 `performance`（性能统计）中补充：

| 指标 | 含义 |
| --- | --- |
| `quoteReadMode`（盘口读取模式） | 本任务实际使用的读取模式。 |
| `quoteStreamQueries`（盘口流查询次数） | 创建及重连盘口流的次数。 |
| `quoteRowsStreamed`（盘口流读取行数） | 从流中解码的盘口总行数。 |
| `quoteRowsSkipped`（盘口流跳过行数） | 因早于有效订单时间或空档被推进的行数。 |
| `quoteReadMs`（盘口读取耗时） | 盘口流建立、接收与解码累计耗时。 |
| `quoteStreamReconnects`（盘口流重连次数） | 因临时连接故障的续接次数。 |

保留 `quoteQueries`（盘口查询次数）、`quoteRowsPrefetched`（预读盘口行数）等旧指标，便于同任务基线对比。

## 6. 实施步骤

1. 为 ClickHouse 客户端增加可关闭的 `JSONEachRow`（逐行 JSON）读取能力，复用现有连接、鉴权、gzip 和错误包装逻辑。
2. 在 L2 数据适配器中实现按交易日、连续竞价范围读取的有序盘口流，并复用时间唯一性校验。
3. 实现 `DayQuoteStreamCursor`（日内盘口流游标），负责惰性创建、时间边界、暂停消费、日切换、关闭和断线续接。
4. 在订单驱动 runner 中接入游标模式；保留 `_QuotePrefetchBuffer`（固定窗口预读缓冲）并通过配置选择。
5. 补充性能指标、结构化错误日志和配置说明。
6. 完成结果一致性测试、异常测试及固定口径性能对比后，再决定默认读取模式。

## 7. 测试与验收

### 7.1 正确性测试

至少覆盖以下场景，并将 `prefetch` 与 `day_stream` 的订单、成交、持仓、现金、净值结果逐项比较：

- 无订单的 Bar 区间：不创建流、不读取盘口。
- 订单在 Bar 结束后生效：首条可用盘口必须严格晚于生效时间。
- 盘口位于下一根 Bar 之后：先执行该 Bar，再将盘口交给 worker。
- 部分成交、连续多笔订单、涨跌停单边盘口、日末未成交订单。
- 同一时间多条盘口的顺序一致性。
- 流连接中断后续接：无重复成交、无漏成交。
- 任务取消、worker 异常、日切换：连接正确关闭。
- `continuous`（连续回放）模式：行为和性能路径均不受影响。

### 7.2 性能验证

使用固定的标的、策略、日期区间、周期和参数执行：

1. 确认临时 Bar 已全部命中 Redis 缓存。
2. 使用 `prefetch` 连续执行 3 次，记录中位数。
3. 使用 `day_stream` 连续执行 3 次，记录中位数。
4. 比较 `sourceReadMs`（盘口源数据读取耗时）、`quoteReadMs`（盘口读取耗时）、`totalElapsedMs`（任务总耗时）及查询次数。

验收条件：

- 业务结果与旧模式一致，新增指标除外。
- 在当前 25 个交易日样本中，物理盘口查询目标不高于“活跃交易日流数 + 每日校验数”；即理论上约不高于 50 次，对比现有 235 次。
- `sourceReadMs` 或 `totalElapsedMs` 在三次热态样本的中位数上有可复现的实际下降；若无实际下降，不保留该模式为默认实现。

## 8. 风险与应对

| 风险 | 处理方式 |
| --- | --- |
| 单日流可能顺序经过比实际成交更多的盘口 | 仅在有订单时惰性创建；无订单暂停消费；以实测总耗时和读取行数决定是否保留。 |
| 长连接中断 | 使用最后已消费游标续接；无法安全续接则明确失败并记录正文。 |
| 同时间多条盘口导致续接重复或遗漏 | 使用现有唯一性校验及序列次序，测试覆盖边界。 |
| 实现改变无前视时序 | 以 Bar 边界、订单生效时间和结果一致性测试作为硬性门槛。 |
| 新路径在线上异常 | 通过 `TREND_GRID_L2_QUOTE_READ_MODE`（L2 盘口读取模式）立即回退 `prefetch`。 |
| ClickHouse / JSON 解析仍为主要瓶颈 | 本方案验证后再评估原生 TCP 驱动、表排序键与分区、服务端部署拓扑；不在本次提前引入。 |

## 9. 后续决策

本方案完成后，根据真实对比数据决定：

1. 是否将 `day_stream`（日内盘口流）设为订单驱动回测的默认读取模式；
2. 是否保留或移除 `_QuotePrefetchBuffer`（固定窗口预读缓冲）；
3. 若流游标已显著减少查询次数但耗时仍高，再单独评估 ClickHouse 原生 TCP、表排序与分区优化，不与本次改动混合实施。
