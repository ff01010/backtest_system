# 公平调度与 L2 八并发扩容方案

日期：2026-08-22
状态：待实施

## 1. 背景与结论

当前 L2 回测使用 PostgreSQL 任务表和 4 个 `l2-runner（L2 回测执行器）` 副本。任务领取按全局提交顺序进行，不区分所属用户。一个用户提交大量任务后，可以同时占满全部执行槽位；其他用户之后提交的任务只能排在该批任务之后。

服务器最近的实际使用数据显示，2026-08-22 在 13:45 至 13:50 的五分钟内有 73 条 L2 任务提交，均来自同一用户。当天共 90 条任务、2 名用户，4 个槽位达到峰值并发；64 条任务等待超过 30 秒，排队中位数约 143 秒、P95 约 371 秒。该现象主要是单用户突发批量提交造成，而不是常态多用户计算资源不足。

本方案同时完成两项改造：

1. L2 runner 从 4 个副本扩展到 8 个副本。
2. 将全局先进先出领取升级为“工作守恒的公平调度”：有多个用户排队时优先均衡用户的运行任务数；只有一个用户有任务时，该用户可以使用全部空闲槽位。

方案不设置“单用户固定只能运行一条”的硬限制，不降低单用户独占时的吞吐，也不抢占已经运行的回测任务。

## 2. 目标、范围与不做事项

### 2.1 目标

1. L2 同时运行任务上限由 4 提升至 8。
2. 多用户同时排队时，避免一个用户的大批量任务长期占满所有槽位。
3. 单用户独自使用时，允许其并发使用全部 8 个槽位，避免资源闲置。
4. 保持 PostgreSQL 的原子领取、租约、取消、尝试令牌和失败恢复语义。
5. 保持策略执行、行情读取、撮合、费用、收益和历史任务结果不变。
6. 通过真实服务器压测确认扩容后没有持续 Swap 换页、ClickHouse 拥塞或显著单任务性能退化。

### 2.2 本期范围

- `l2_backtest_job（L2 回测任务）` 的公平领取排序与并发安全实现。
- L2 runner 副本数、容器资源和部署配置。
- 公平性、单用户吞吐、八并发、取消、租约和任务恢复测试。
- 服务器发布前后运行状态、资源、排队等待和吞吐监控。

### 2.3 不做事项

1. 不限制用户可提交的任务总数，也不删除已排队任务。
2. 不抢占或迁移已开始的任务；公平性只在领取下一条任务时生效。
3. 不改变标准 Bar runner 的副本数或其队列逻辑。
4. 不改用 Redis、Kafka 或其他消息队列替代 PostgreSQL 任务队列。
5. 不改变单个任务的 CPU、内存、PID 上限：每个 L2 runner 继续为 4 CPU、6 GiB、256 PID。
6. 不把 8 并发理解为无限扩容；若资源或数据源出现持续压力，必须可回退。

## 3. 当前状态与容量判断

### 3.1 已验证运行状态

| 项目 | 当前值 |
| --- | ---: |
| L2 runner 副本数 | 4 |
| 单副本资源限制 | 4 CPU / 6 GiB 内存 / 256 PID |
| L2 总资源上限 | 16 CPU / 24 GiB 内存 |
| Bar runner 资源限制 | 2 CPU / 3 GiB 内存 |
| 服务器可用内存（审查时） | 约 261 GiB |
| 服务器 Swap 已用（审查时） | 约 7.9 / 8 GiB |

8 月 21 日和 8 月 22 日均已实际达到 4 个 L2 任务并发。当前 4 并发对日常少量多用户使用基本足够；但在单用户短时间提交数十条任务时，吞吐无法及时消化突发队列。

### 3.2 八并发资源边界

扩容后 L2 runner 的容器上限为 32 CPU、48 GiB 内存；加上 Bar runner 为 34 CPU、51 GiB 内存。该上限低于服务器物理资源，但服务器已有较高 Swap 占用，因此不能只依据空闲内存判断安全性，必须观察实际 `pswpin（Swap 换入）`、`pswpout（Swap 换出）`、容器 RSS、ClickHouse 延迟和任务失败率。

## 4. 公平调度模型

### 4.1 核心规则

每次有 L2 runner 空闲并领取下一条任务时：

1. 计算每个有排队任务用户的 `activeCount（运行中任务数）`。
2. 优先选择 `activeCount（运行中任务数）` 最少的用户。
3. 同一优先级内，选择该用户最早排队的任务；用户间再按最早排队时间排序。
4. 当只有一个用户有排队任务时，该用户持续领取空闲槽位，直至跑满全局 8 槽位。
5. 当新用户进入队列且其 `activeCount（运行中任务数）` 低于正在占用槽位的用户时，在下一个可用槽位优先启动新用户任务。

该规则是“工作守恒”的：不会因为等待某个用户而让 runner 空闲；也是“非抢占”的：正在运行的任务不被中断或暂停。

### 4.2 示例

#### 仅用户 A 排队

```text
用户 A：73 条排队任务
全局：8 个空闲槽位

结果：用户 A 的前 8 条任务同时运行，其余 65 条排队。
```

#### 用户 B 在 A 满载后提交

```text
用户 A：8 条运行，65 条排队
用户 B：1 条排队，0 条运行

任一 A 任务结束后：优先启动 B 的任务。
```

#### 多用户持续提交

```text
用户 A、B、C 均有大量排队任务
全局：8 个槽位

结果：调度器优先使三名用户的运行数量接近，
例如 A=3、B=3、C=2；而不是 A=8、B=0、C=0。
```

## 5. 原子领取与并发安全

### 5.1 保持既有可靠性语义

现有 PostgreSQL 队列的 `FOR UPDATE SKIP LOCKED`、`attemptToken（尝试令牌）`、租约续期和取消检查是防止重复执行与错误覆盖的基础。本次改造必须复用，不得以普通“先查询、后更新”的两步逻辑替代。

公平排序需要在同一领取事务中完成：选择候选任务、锁定任务、写入 `running（运行中）` 状态、生成新的尝试令牌和 worker 标识必须原子提交。取消任务、过期租约接管和旧 worker 回写结果仍须以尝试令牌校验。

### 5.2 多副本公平性

8 个 runner 会同时请求下一条任务。若每个副本独立读取用户运行数，空闲瞬间可能同时把多个任务分给同一用户，破坏第一轮的公平性。

为避免该竞争，领取事务应使用 PostgreSQL 事务级调度锁或等价的短临界区：

```text
获取短期调度锁
  ↓
计算各用户运行任务数并选择公平候选
  ↓
FOR UPDATE SKIP LOCKED 锁定该候选任务
  ↓
写入 running、worker、attemptToken 和租约
  ↓
提交事务并释放调度锁
```

调度锁只包围毫秒级领取 SQL，不包围回测、ClickHouse 查询或策略执行，因此不会将 8 个任务重新串行化。锁竞争时 runner 短暂重试；若锁持有者异常，事务结束后数据库自动释放事务级锁。

实施前需以现有表结构和查询计划确认采用 `pg_advisory_xact_lock（事务级咨询锁）` 还是等价机制；不得持有会话级永久锁。

### 5.3 查询与索引审查

公平领取会查询 `status（状态）`、`owner_user_id（用户归属）`、`created_at（创建时间）` 和运行中任务。实施前使用 `EXPLAIN ANALYZE` 检查现有索引是否覆盖。只有确认缺失且会造成领取退化时，才新增幂等迁移创建必要索引；不因猜测创建冗余索引。

## 6. 并发配置

### 6.1 项目与服务器配置

项目 Compose 配置继续通过环境变量读取副本数，并提供安全默认值。服务器私有 `deploy/.env` 在部署时设置：

```text
TREND_GRID_L2_RUNNER_REPLICAS=8
```

`deploy/.env` 不提交到仓库，也不得被 `.env.example` 覆盖。若项目的 Compose 默认值需要从 4 调整为 8，应同步检查启动校验、部署脚本和文档，但不将服务器私有地址、账号或口令写入仓库。

### 6.2 资源与限流

每个 L2 runner 保持 4 CPU / 6 GiB / 256 PID，上限清晰且任务隔离。8 个副本仍从同一个 PostgreSQL 队列领取任务，并共享 ClickHouse、Redis 与网络磁盘，因此全局并发数必须保持可配置，允许紧急回退为 4。

本次不为单用户设置固定运行上限。若未来出现恶意或失控批量提交，再单独设计可配置的“每用户排队上限”和提交频率限制；不与本次公平调度耦合。

## 7. 实施步骤

1. 审查当前 L2 任务领取 SQL、状态流转、租约续期、取消、尝试令牌和现有索引。
2. 抽取或重写公平候选选择逻辑，定义同一事务内的调度锁、用户运行数排序和任务锁定顺序。
3. 保留 `SKIP LOCKED`，实现原子公平领取；处理候选任务在锁定前被取消、完成或被其他 worker 领取时的重选逻辑。
4. 按查询计划决定是否新增幂等索引迁移，并补充迁移验证。
5. 增加单元/集成测试：单用户填满 8 槽位、多用户均衡、突发新用户优先、取消、租约接管、旧尝试令牌拒绝回写和无任务空闲。
6. 将副本参数与部署校验扩展至 8，保持单副本资源限制。
7. 本地启动 8 个 L2 runner，使用可控任务集验证领取顺序、结果一致性和第 9 条任务排队。
8. 服务器发布前检查 queued/running L2 任务；通过 `scripts/deploy-server.sh` 同批发布 backend、L2 runner、迁移及前端相关任务状态契约。
9. 服务器以分阶段压测验证 4、6、8 并发，记录队列等待、吞吐、单任务时长、ClickHouse、Redis、PostgreSQL、CPU、内存和 Swap。
10. 根据验收阈值决定长期保留 8 或回退为 4/6，不以一次压测的峰值 CPU 判断结论。

## 8. 测试与验收标准

### 8.1 调度正确性

1. 单用户提交至少 9 条任务、系统空闲时，前 8 条可并发运行，第 9 条保持排队。
2. 两个用户各自有排队任务时，第二个用户在下一个可用槽位获得优先，不被第一个用户的历史任务压住。
3. 三个用户持续排队时，任一用户运行任务数不得在其他用户有待执行任务时长期显著高于其他用户；允许一个槽位的瞬时差异。
4. 无其他用户排队时，单用户可继续领取所有空闲槽位，不发生人为闲置。
5. 多 runner 下同一任务只被一个 worker 领取，取消任务不启动，旧尝试令牌不能覆盖新尝试结果。

### 8.2 结果与兼容

1. 公平调度只影响开始顺序，不改变单个任务的策略快照、行情、信号、成交、费用和收益结果。
2. 排队、运行、取消、失败和成功状态及其前端展示保持兼容。
3. 历史任务不因新的排序规则被重算或改写。

### 8.3 性能与资源

1. 8 并发下，单用户批量任务的总完成时间相较 4 并发有可测量改善。
2. 多用户并发时，后提交用户的等待时间显著低于原全局 FIFO 队列。
3. 调度锁不成为瓶颈：领取操作耗时保持毫秒级，runner 不因锁长期空闲。
4. 8 并发时 ClickHouse、Redis、PostgreSQL 无连接耗尽、持续错误或不可恢复积压。
5. 观察期间无持续 `pswpin（Swap 换入）` 或 `pswpout（Swap 换出）`；若持续换页或单任务 P95 时长明显恶化，停止扩容。

## 9. 发布、监控与回滚

### 9.1 发布要求

受影响服务为 backend、l2-runner、数据库 migrate 和可能引用任务状态的前端。必须经 `scripts/deploy-server.sh` 同批发布；不得只修改服务器 `deploy/.env` 后单独扩容容器。

发布前应检查正在运行的 L2 任务。重建 4 个现有 runner 会中断它们，应等待完成、由用户取消，或经明确确认后标记为发布中断。发布后执行健康检查、历史任务读取、单用户 8 并发、多用户公平领取和代表性回测结果回归。

### 9.2 监控指标

发布后至少记录：

- 每日提交任务数、独立用户数、峰值并发和每用户运行数分布。
- 队列中位数、P95、最大等待时间和等待超过 30 秒的任务占比。
- 单任务运行时长的中位数、P95 和失败率。
- 8 个 runner 的 CPU、RSS、PID、容器重启次数。
- ClickHouse 查询时长、读取行数、失败/重试次数。
- PostgreSQL 领取耗时、锁等待和连接数。
- Redis 内存、命中率、延迟。
- 主机 `pswpin（Swap 换入）`、`pswpout（Swap 换出）`、可用内存与磁盘 I/O。

### 9.3 回滚策略

1. 若公平领取出现异常，回退到现有全局 FIFO 原子领取逻辑；任务状态、租约和尝试令牌不迁移、不重算。
2. 若 8 并发导致数据源拥塞、持续换页或错误率升高，将 `TREND_GRID_L2_RUNNER_REPLICAS（L2 runner 副本数）` 恢复为 4，并通过一键部署脚本重建相关服务。
3. 若新索引或持久化字段已迁移，保留向后兼容读取；应用回滚不得依赖删除迁移或删除历史数据。
4. 缓存不参与任务可靠性；扩缩容或回滚不得清空 Redis 作为常规步骤。

## 10. 自审结论

本方案针对已观察到的真实问题：单用户的突发批量任务使 4 个全局槽位饱和，而非一般多用户负载持续超过资源上限。单纯扩容到 8 会缩短该用户批处理时间，但无法保证后来用户及时获得服务；单纯设置“每用户最多一条”又会在单用户使用时浪费资源。

“按运行数量优先 + 无其他用户时填满空闲槽位”同时满足公平和吞吐。通过短事务级调度锁配合现有 `SKIP LOCKED`，避免 8 个 runner 在空闲瞬间竞态地把任务都发给同一用户，同时不把耗时回测过程串行化。

8 并发在容器资源配额上可行，但服务器已有较高 Swap 占用。因此本方案将实际 `pswpin（Swap 换入）`/`pswpout（Swap 换出）`、单任务 P95 时延、ClickHouse 延迟和错误率设为上线后是否长期保留 8 并发的判断依据，而不是仅以一次空闲资源快照作结论。
