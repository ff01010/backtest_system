# 玄龄回测系统使用手册

> 版本：1.4
> 适用对象：在策略代码编辑器中编写、回测或维护 K 线策略的使用者和维护者。

## 1. 先读这一页

策略代码编辑器采用“已完成 K 线触发、返回委托列表”的方式运行。系统在每根指定周期 K 线结束后调用策略函数，策略读取当前 K 线和账户快照，再返回本根 K 线需要执行的委托。

### 1.1 先记住这 6 条

1. 只使用**已完成**的 Bar；不能把未收盘价格当作确认信号。
2. 每次回调必须返回委托列表；没有委托时返回 `[]`，不能省略 `return`。
3. 默认“标准 Bar 回放（快速）”在本 Bar 收盘生成信号，并在下一根可交易 Bar 的开盘价加 `slippage（滑点）` 成交；这不等于实盘成交价。
4. L2 订单只能使用**严格晚于**信号 Bar 或信号快照的后续十档盘口成交；同一时间戳绝不成交。
5. 当天买入不会增加 L2 的当日可卖数量；科创板 `688/689` 标的开仓至少 200 股。
6. 策略错误会给出可修改提示；系统错误和需维护的数据异常会展示任务编号，由维护人员在回测诊断日志或容器日志中定位。

### 1.2 普通 Bar 回测

- `on_bar(bar, state)`（K线回调函数）会在每根**已完成**的当前所选周期 K 线上调用一次。
- 默认标准模式中，信号在本 Bar 收盘时生成；买入在下一根可交易 Bar 开盘价基础上上调滑点，卖出在该开盘价基础上下调滑点。午间信号会在下午首根 Bar 开盘成交；最后一根 Bar 的新开仓信号不会跨任务成交。
- `bar_close（Bar 收盘成交）` 已废止。历史任务仍按原始结果展示，但重新运行时统一使用标准 Bar 回放，不能按旧规则复现。
- `bar`（当前K线及账户数据）可读取 `time`、`datetime`、`tradeDate`、`hhmm`、OHLC、`volume`、`cash`、`equity`、`position`、`strategyPosition`、`basePosition`、`sellableQuantity`、`t0AvailableQuantity` 和 `params`。
- `time` 固定为 `YYYYMMDDHHMMSS`；`tradeDate` 固定为 `YYYY-MM-DD`；交易时段判断使用 `hhmm`，例如 `931`。

### 1.2.2 研究信号联动回测

- 研究信号不是独立策略。信号驱动脚本必须勾选“研究信号驱动策略”，并在代码中显式读取 `bar['researchSignal']`；这类策略运行前必须选择已发布信号数据集。普通策略不选择信号时保持原行为，也不能附加研究信号。
- 提交时回测系统按当前用户权限读取信号数据集，冻结原始行、数据集版本、来源分区哈希与快照哈希；Worker 读取正式区间 Bar 后再生成 effectiveAt 到第一根可执行 Bar 的对齐计划，并随结果保存。运行期间不会再请求研究平台。
- 首期仅支持标准 Bar 回放。信号周期可以等于或粗于回测周期；细于回测周期会被拒绝，避免把多个细粒度信号压缩到一根粗粒度 Bar。
- 信号首次对齐到可执行 Bar 后，会作为“当前有效信号”持续注入后续 Bar，直到下一条信号替换；首条信号生效前 `researchSignal` 为 `None`。字段包含 `action`（long / short / flat）、信号时间、可用时间、生效时间、信号 ID 和来源哈希。
- 信号只表达方向，不能自动下单。策略代码必须显式读取 `researchSignal`，再结合当前持仓、资金、底仓、交易方向与风控规则返回委托和数量。
- 在“历史回测”中可查看本次运行保存的策略、行情与研究信号快照；重新运行同一不可变信号数据集时仍会创建一份新的回测快照。


### 1.2.1 指标预热与连续历史数据

标准 Bar 自定义策略如需在正式区间开始前初始化指标，应在代码模块顶层声明整数常量，例如 `WARMUP_TRADING_DAYS = 140`。系统不会在前端显示或允许编辑该值；保存策略时写入版本快照，运行时重新从代码解析。

预热 Bar 仅用于更新策略内部状态，不产生订单、成交、费用或收益。Worker 从正式回放使用的同一 Bar 来源中，选取正式开始日期前最近 `N` 个状态完整且实际可加载的行情日期；没有 Bar 的周末、休市日或停牌日不消耗预热数量。来源不足 `N` 个日期时任务失败，不会跨来源拼接补足。系统不在保存或提交阶段扫描原始 Bar。标准 Bar 回放只处理所选来源实际读到的已定稿 Bar，不按行级质量状态筛选，也不会为没有 Bar 的日期生成 `on_bar` 回调；整段无可回放 Bar、字段无法解析或来源读取失败时，任务仍统一提示“行情数据异常，请联系管理员”。未声明时默认不预热。`l2_quote（基础L2盘口回测）` 不支持声明大于 `0` 的预热交易日。

### 1.2.3 自定义策略参数声明

自定义策略可以在模块顶层声明可调参数。系统只解析字面量，不执行声明代码：

```python
STRATEGY_PARAMETERS = {
  "window": 20,
  "stopLoss": 0.08,
  "enableVolumeFilter": True,
  "signalLabel": "breakout",
}

def on_bar(bar, state):
  params = state["params"]
  window = int(params["window"])
  stop_loss = float(params["stopLoss"])
  return []
```

- 支持整数、有限小数、布尔值和字符串；网页分别生成整数、小数、开关和文本控件。
- 只允许模块顶层唯一一次 `STRATEGY_PARAMETERS` 字典赋值。键必须匹配 `^[A-Za-z][A-Za-z0-9_]{0,63}$`，并且不能使用系统保留运行参数名。
- 最多 64 个参数；单个字符串最长 1024 个字符；规范化后的声明最大 64 KiB。函数调用、表达式、变量引用、`None`、列表和嵌套对象均会被拒绝。
- `STRATEGY_PARAMETERS` 声明的参数在回调中通过 `state["params"]` 或 `bar["params"]` 读取，建议统一使用 `state["params"]` 并将参数视为只读。`strategyParams` 只是请求载荷和运行快照中的内部字段名，不是 `bar` 的回调字段；读取 `bar["strategyParams"]` 会因字段不存在而失败。
- 未声明该字典的旧策略按“没有自定义参数”运行，原有 `bar["params"]` 和 `state["params"]` 读取方式保持兼容。
- 保存完整策略时，请求明确值优先；未明确提供时保留同名同类型的已保存值；新增参数或类型变化使用代码声明值；代码删除的参数会从当前默认值移除。

### 1.3 L2 回放与成交

- 选择 `l2_quote（基础L2盘口回测）` 后，`on_bar` 仍在已完成 Bar 结束时调用，但订单不再按本 Bar 收盘价直接成交。
- L2 Worker 先加载所选单一 Bar 来源，再仅对实际回放 Bar 日期核对 `l2_quote_daily_availability` 日级摘要；没有 Bar 的日期不要求 Quote 摘要，也不会生成回放事件。策略或撮合实际需要时再读取连续竞价盘口，不会用旧盘口、收盘价或零价替代。有 Bar 的日期若摘要缺失、非完整或实际读取失败，任务按行情数据异常结束，详细技术原因只记录在服务端诊断日志中。
- `slippage（滑点）` 仅用于标准 Bar 的虚拟成交；L2 以十档最优可成交价和可用深度撮合，不再额外叠加固定滑点，避免重复计入买卖价差。
- L2 十档盘口的实际成交价只用于成交现金变化、手续费和已实现收益；当天全部模拟成交完成后，剩余持仓与日终净值统一按当天实际回放的最后一根有效 Bar 收盘价结算。底仓收益与增强未实现收益使用同一结算价；当天没有有效 Bar 时任务失败，不使用盘口价兜底。
- 结果中的“有效委托数”是撮合接受的订单数；“成交笔数”是实际成交记录数。同一 L2 委托分次成交时，成交笔数可能大于有效委托数。
- 市价单和可立即成交的限价单，按后续十档盘口逐档撮合；允许部分成交、继续等待后续快照或日终撤单。
- 定义 `on_quote(quote, state)`（3秒盘口回调函数）后，脚本自动使用 `continuous（连续快照）`：每条可见 3 秒快照依时间顺序回放，先处理旧订单与成交回报，再调用当前 `on_quote`。
- `on_quote` 新产生的订单只能从**下一条**快照开始成交。未定义 `on_quote` 时保持 `order_driven（订单驱动）`，无待成交订单的区间不会读取盘口。
- `on_order_event(event, state)`（委托回报回调函数）用于根据部分成交、完全成交、拒绝或撤单更新状态；不要在提交订单时假定已成交。
- 3 秒快照只表达可见采样点，不能替代一秒 Tick 或逐笔成交 `tick_data`。

### 1.4 执行方式：立即成交与 TWAP

- `immediate（立即成交）` 是默认方式。策略产生委托后，标准 Bar 使用下一根可交易 Bar 的开盘价加滑点成交；L2 使用严格晚于信号时点的第一条可成交盘口撮合。
- `twap（时间加权执行）` 仅可在 L2 盘口回放中使用。系统将一条策略委托拆为等时间间隔的子单，并且每个子单只可使用其计划时点之后的 3 秒盘口成交。
- TWAP 参数位于回测参数的“执行方式”，不传给策略脚本：执行时长、子单间隔（必须为 3 秒倍数）、最小子单数量。执行窗口结束未成交部分会撤销，不会进入后续时段。
- “信号明细”会保留实际子单成交，并在“执行追溯”中显示每个母单的申请、成交、撤销和拒绝数量。图表仍按实际成交绘制。

### 1.5 Bar 聚合、价格与缓存

- “运行标的”和“基准标的”搜索目录来自 ClickHouse `xl_derived.stock_directory`，仅同步 `type=CS` 且 `status=Active` 的沪、深、北交所股票。目录可搜索只代表证券主数据存在；页面另行显示对应标的和周期的可回测范围。
- 标的输入框支持按六位代码、完整代码或名称搜索；只有点击候选项、用键盘确认候选或提交唯一匹配的完整代码后，才会更新实际标的并刷新可回测范围。未确认的搜索文字在失焦或按 `Esc` 时恢复为原标的，历史方案恢复后统一显示“完整代码 · 证券名称”。
- 沪、深、北交所统一从 `qmt_history_dev` 的 `1m/5m/15m/30m/1h/1d` 周期表读取不复权（`none`）且已经定稿的数据，不按原始行的 `quality_status` 筛选；该数据库是标准 QMT Bar 的唯一来源。平台 `60m` 对应物理 `1h`，`3m`、`45m` 由同库的 `1m` 数据派生。Bar 范围只依据 `qmt_ingest_runs` 与 `qmt_universe_snapshot` 发布元数据计算，不扫描原始 Bar 表。范围查询会对超时和临时网络错误进行有限重试；没有覆盖、请求越界、预热不足、重试失败或发生确定性查询错误时提示行情数据异常，不切换其他 QMT 数据库。Worker 再次校验请求起止日期都位于来源的 `firstDate/lastDate` 闭区间内；超出边界会失败，不会静默截断。交易日历不参与正式日期、预热日期或行情缺失判断。使用旧 QMT 数据库来源快照且尚未执行的任务不再受支持，发布前应先排空或处理。
- L2 模式的可回测范围只读取 `l2_quote_daily_availability` 日级摘要，不在页面、保存或提交阶段回填摘要或扫描 L2 原始表；L2 首版不计算基准曲线，因此页面不展示基准标的范围。
- 选择或切换运行标的、周期或成交模式后，日期区域仅在范围请求进行中显示“正在读取”；有可用范围时显示起止日期，查询完成但该标的无覆盖数据时显示“暂无可回测数据”，查询失败时显示“可回测范围暂不可用”。无数据或失败不会沿用前一标的的范围；用户点击“应用”时才校验草稿并显示对应原因，不额外查询行情。
- Bar 来源按“正式映射 Bar 表 → QMT 原生或派生 K 线 → `quant.tick_quote（L2三秒十档快照表）` 临时聚合”选择；一个任务只使用其中一个来源。临时聚合支持 `1m/3m/5m/15m/30m/45m/60m/1d`。
- 分桶只覆盖连续竞价 `09:30–11:30` 与 `13:00–14:57`；上午、下午分别从时段起点对齐。`14:57–15:00` 集合竞价不使用十档盘口撮合或聚合。
- `45m` 保留时段尾部 Bar；日线合并上午和下午连续竞价时段。仅已收盘历史交易日可运行。
- Bar 无有效价格或出现负量额会明确失败，不会退回为收盘价成交；快照间隔仅作观测，不决定 Bar 是否可用。
- 聚合 Bar 按规则和映射版本隔离缓存到 Redis；缓存淘汰或不可用时自动从 ClickHouse 重建，回测语义不变。
- `last_price（最新价）` 使用元价格；十档 `bid_price_*（买价）`、`ask_price_*（卖价）` 使用万分之一元整数，适配器会统一换算为元。

### 1.6 策略类别与账户规则

- `directional_holding（方向性持仓策略）` 使用单一净仓；启用初始持仓时，初始持仓就是该净仓的一部分，不存在“脚本仓卖不出时改卖隐藏底仓”的回退。完整交易从持仓建立开始，到该方向持仓归零时结束；未归零持仓不进入交易胜率。
- `core_position_overlay（底仓增强策略）` 围绕 `baseQuantity（目标底仓数量）` 调整实际持仓。可选择 `intraday_restore（日内恢复）` 或 `cross_day_carry（允许跨日）`；后者日终不自动补回，增强仓延续至下一交易日。
- `allowShort（允许做空）` 同时决定策略能否产生开空信号，以及 L2 撮合是否接受开空委托。
- 底仓增强策略中，`initialCapital（初始资金）` 是独立可用现金；底仓成本不从其中扣除，但总收益和回撤起点会计入底仓初始市值。
- `actualPosition（实际净仓）` 是账户真实持仓；底仓增强中的 `overlayQuantity（增强仓位） = actualPosition - baseQuantity`。增强仓可正可负，负值只表示实际持仓低于目标底仓，不表示真实融券空头。
- 标准 Bar 与 L2 都执行 A 股 T+1：回测开始前的初始持仓首日可卖，当日买入不增加当日 `sellableQuantity（可卖数量）`；委托超过可卖量时只按实际可卖量成交。允许跨日不会放宽 T+1、资金或实际持仓约束。
- 只有 `intraday_restore（日内恢复）` 会在尾盘尝试恢复目标底仓。标准 Bar 使用既定尾盘结算价；L2 若封板、盘口缺边或深度不足，则保留带明确标识的强制结算假设与告警。`cross_day_carry（允许跨日）` 日终不制造恢复成交。
- 模拟成交价记录撮合事实，并决定现金变化、费用和已实现收益；成交入账后账户会暂时按该成交价标记持仓，不代表最终日终估值。
- 所有当前及未来策略类别都在日终成交完成后，由统一结算流程使用当天最后一根有效 Bar 收盘价重新估值剩余持仓并生成唯一日终快照。策略只能决定日终订单或结算策略，不能提供估值价格；当天没有有效 Bar 时任务失败，不使用成交价或盘口价兜底。

### 1.7 结果、日期与错误处理

- 当前费用使用全局“默认 A 股费用”：佣金 `0.008%`（单笔委托最低 5 元）、过户费 `0.001%`（双边）、印花税 `0.05%`（仅卖出）。成交明细会记录实际费用；L2 同一委托分次成交时，最低佣金只在该委托的累计佣金不足时补收。
- L2 回测是异步任务：页面自动轮询，成功后自动打开概览和信号明细。明细会保留成交、方向限制跳过、撮合拒绝、日终撤单及部分成交的剩余数量。
- 标准 Bar 与 L2 回测共用平台执行槽位。页面中的“排队中”表示任务尚未取得槽位，“运行中”表示正在执行，“取消中”表示系统已收到取消请求并正在终止执行；页面刷新后仍会继续读取数据库中的真实状态。
- 当指定类型的回测执行器全部异常或心跳超时时，新任务不会被写入为无限期“排队中”，页面会提示“回测执行服务暂不可用，请稍后重试”。已入队任务仍保留在数据库中，执行器恢复后继续调度。
- 每位有等待任务的用户会优先获得一个槽位；没有其他用户等待时，单个用户可以使用其余空闲槽位。该规则只影响开始顺序，不改变策略、撮合或回测结果。
- L2 首版不计算基准曲线，超额收益显示为 `--` 并在结果告警中说明。
- `directional_holding` 展示实际持仓、组合收益、基准收益与超额收益；`core_position_overlay` 展示总账户收益、底仓持有收益和做 T 超额收益。
- 收益详情默认筛选本次回测起止日期，并展示初始总资产与期末总资产。方向性持仓策略的初始总资产等于初始资金；底仓增强策略则等于初始资金加底仓初始市值。
- 新任务使用 `resultSchemaVersion（结果结构版本） = 3`。底仓增强结果分别展示 `accountPnl（账户总收益）`、`baseBenchmarkPnl（底仓基准收益）` 与 `overlayPnl（增强收益）`，并满足“账户收益 = 底仓基准收益 + 增强收益”。
- 增强仓从 0 变为非 0 后，直到再次回到 0 才形成一个完整周期。分批恢复在各自成交日确认 `realizedOverlayPnl（已实现增强收益）`；任务结束仍未归零的部分进入 `unrealizedOverlayPnl（未实现增强收益）`，不进入周期胜率。
- 成交明细中的 `accountRealizedPnl（账户会计已实现损益）` 按账户库存成本计算，不等同于一次增强周期收益。周期表通过 `fillId（成交编号）` 关联组成成交，避免同一成交重复记账。
- 历史任务保持原结果不变；没有结果结构版本 3 的任务显示“历史收益口径”。只有主动重新运行才按新口径生成周期和指标。
- `strategy_error（策略错误）` 会展示回调、事件时间、标的、安全原因和修改建议；应据此检查字段、变量、盘口档位、返回值和下单动作。
- `system_error（系统错误）` 不回显服务地址、SQL 或 Python 堆栈，只给出安全提示和 `taskId（任务编号）`；管理员可在“回测诊断日志”按任务编号查看每次 `Attempt（执行尝试）` 的 Worker、最后阶段、退出码、终止原因、脱敏错误摘要和安全时间线。同一任务重试时，各次 Attempt 独立展示，不会由后一次覆盖前一次。
- 集中日志属于有期限的运维证据，默认保留 30 天，不记录用户身份、策略源码、完整参数或请求载荷。集中日志不可用或已经过期时，管理员页面仍展示 PostgreSQL 中的 Attempt 和错误摘要，并明确标记“暂不可用”或“已过期”；普通用户、共享回测和公开接口均不能读取这些内部诊断。
- `runtime.contract_missing（运行时契约缺失）` 和 `runtime.version_mismatch（运行时版本不一致）` 属于平台问题。页面会明确提示无需修改策略；请把任务编号提供给管理员。
- `strategy.undefined_name（名称未定义）`、`strategy.local_unbound（局部变量未初始化）` 和 `strategy.runtime_policy_blocked（运行时规则禁止）` 属于策略可修改问题，页面会显示可安全公开的名称、回调与行号。
- `data（数据错误）` 对用户统一显示“行情数据异常，请联系管理员”，不再公开超时、缺失日期、表名或底层查询信息。服务端仍保留独立错误码、任务编号、执行阶段和原始异常堆栈，供管理员定位。
- 标准 Bar 回测不执行行级行情质量判定、逐日完整性扫描或自动修复。页面范围只反映行情发布元数据；生产行情清洗和修复由数据维护流程完成。L2 行情质量规则本次不变。
- 回测日期区域先显示当前标的和周期的可回测范围，并提供“近1月”“近3月”“今年”“全部数据”和“从最早日期开始”。日期本身保持“开始 `YYYY-MM-DD`”“结束 `YYYY-MM-DD`”两个横向日期框；点击年份、月份或日期数字，会在原位置展开带上下候选的纵向滚轮长列表，中间高亮项为当前值，可以滚动列表或点击可见候选值进行选择，不会打开日历。改变年份或月份后，目标月份不存在原日期时自动使用该月最后一天。开始、结束日期彼此独立，滚动任一端点不会自动改动另一端；滚轮和快捷操作只修改本次草稿且不提前报错，点击“取消”可恢复原区间。用户点击“应用”时，系统才检查开始日期不晚于结束日期，并按闭区间校验所选范围完整落在当前可回测起止日期内；两个范围端点均可选取。校验失败时保留草稿并提示，不更新正式参数。该校验只比较覆盖元数据边界，不扫描行情或判断逐日完整性；实际读取失败仍由回测任务统一报告行情数据异常。
- 保存完整策略时，系统只校验标的、周期、日期格式和策略配置契约，不查询行情完整性。策略编辑器不再单独保存或切换脚本。

## 2. 系统使用流程

回测日期统一填写为 `YYYY-MM-DD（ISO交易日格式）`，例如 `2026-06-01`。历史记录中的旧 `YYYYMMDD（紧凑交易日格式）` 会在读取时自动兼容转换；策略、接口和任务结果均以 ISO 格式显示。

### 2.1 编写前

1. 明确交易周期。当前契约示例为 5 分钟 K 线；若编辑器的周期配置改变，先确认回调频率与成交规则是否同步变化。
2. 明确策略只做多、只做空还是双向。最小示例只覆盖多头。
3. 明确每笔数量、最大持仓、止损和交易时段。没有写出的风控规则不会由示例自动补上。

### 2.2 编写与运行

1. 在策略代码编辑器中定义 `on_bar(bar, state)`（K线回调函数）。
2. 只读取当前契约明确提供的 `bar`（当前K线及账户数据）字段。
3. 根据条件返回一条或多条委托字典；没有信号时返回 `[]`。
4. 运行回测后，逐笔检查信号 K 线、成交价、仓位变化和委托原因。
5. 确认结果符合预期后，再评估是否进入实盘流程。

若需要盘中盘口触发：

- 增加 `on_quote(quote, state)`；`quote` 可读取时间、标的、`lastPrice`、`bids`、`asks` 及与 `bar` 相同的账户字段，每档盘口含 `price（价格）` 与 `volume（可见量）`。
- 使用 `on_order_event(event, state)` 根据 `accepted（已受理）`、`partial_fill（部分成交）`、`filled（完全成交）`、`cancelled（已撤销）`、`rejected（已拒绝）` 更新状态；成交事件含数量、累计成交量、价格、手续费和 `clientOrderKey（客户订单键）`。
- 从 QMT 迁移时，移除账户号、固定标的、订阅、`passorder`、文件持久化和监控目录；只保留已确认的交易判断、仓位规则和风控条件，并改用当前回测请求的标的、账户字段、方向权限与行情事件。

### 2.2.1 管理完整策略

- 一个完整策略由策略名称、独立代码、回测参数和当前不可变版本共同组成。即使两个策略的代码相同，它们也不会共享可变脚本记录。
- 同一用户的有效策略名称不可重复。新建、复制或重命名时如名称已存在，系统会自动追加 `-1`、`-2` 等数字后缀，并在保存后显示最终名称。
- 将当前策略代码恢复为以前保存过的内容时，系统会通过内容指纹复用对应的历史不可变版本，不创建重复代码版本；本次恢复仍会保留在方案发布记录中。
- 策略管理右侧的“回测配置”按“回测范围、策略与仓位、成交与执行、策略参数与信号、资金与成本”分组折叠；默认展开回测范围和策略与仓位，分组标题会显示当前关键值摘要。
- 选择 `core_position_overlay（底仓增强策略）` 后，`baseQuantity（目标底仓数量）`、底仓成本价与 `overlaySettlementPolicy（增强仓结算规则）` 会紧跟策略类别显示。运行前校验失败时，页面自动展开并定位到对应参数组。
- 回测配置内容可独立滚动，“运行回测”和参数恢复按钮固定在配置栏底部，不需要滚动到全部参数末尾。
- “保存策略”会在同一事务中保存代码和参数。代码或运行语义变化时创建新的不可变脚本版本；只改回测参数时复用当前脚本版本。
- 已声明的自定义参数在“策略参数与信号”中显示。页面区分“已保存默认值”和“本次覆盖值”：点击“保存策略”会更新默认值与 revision；直接点击“运行回测”只冻结本次覆盖，不会隐式保存策略或修改默认值。
- 日期、资金、成本、执行算法和已声明参数属于本次实验配置，可以不保存直接运行；代码、标的、周期、持仓语义等结构变更仍需先保存。参数区可点击“恢复默认参数”放弃本次覆盖。策略保存提示使用红黄绿状态：红色表示新建未保存或策略内容已修改、暂不可运行；黄色表示仅修改本次实验参数、仍可直接运行且不影响已保存策略；绿色表示策略内容已保存且可直接运行。
- “复制策略”会复制当前内容，但创建新的策略、独立脚本身份和独立版本链。之后修改原策略或副本不会互相影响。
- 页面只选择完整策略，不提供独立脚本选择器。每次回测绑定保存时的确切方案版本和脚本版本，排队期间再修改策略也不会改变已提交任务。
- 平台检测到新版本时会显示更新通知。若当前策略存在未保存修改，刷新前会明确提醒，可先点击“保存策略后刷新”；强制兼容升级期间需保存或放弃未保存内容后才能刷新，避免静默丢失代码和参数。
- 两个页面同时编辑同一策略时，后保存的页面会提示“该策略已在其他会话中更新，请刷新后重试”，不会静默覆盖先保存的内容。
- 删除策略采用归档方式：策略不再出现在当前列表中，但历史发布版本、脚本版本和已有回测快照继续保留。
- 归档策略可通过开放 API 恢复；恢复时如果已有同名活动策略会明确失败，不会自动改名。归档和恢复都不会删除或改写历史版本、历史回测和共享快照。

### 2.2.2 自动化回测预览

- 平台能力开关开放后，顶部“自动化回测”用于为当前用户可运行的已发布策略配置有限网格；策略回测页也提供“自动化预览”快捷入口。快捷入口仅在能力已开放、策略结构已保存、存在发布版本且发布版本的成交模型为“标准 Bar 回放”时可用。未保存的代码、标的、周期、持仓语义等结构变化不能带入自动化预览，应先保存并发布。
- 自动化页面冻结发布版本中的策略代码、标的、周期、账户与仓位语义、标准 Bar 成交模型和平台费用档案。费用档案不能伪装成佣金候选；首期执行算法固定为 `immediate（立即成交）`，不开放 L2 盘口回放。
- “策略参数候选”只显示策略代码通过 `STRATEGY_PARAMETERS（策略参数声明）` 暴露的参数。候选值、初始资金和滑点使用英文逗号分隔；候选值会按类型规范化并去重，服务端按参数名、日期、资金、成本和执行场景的固定顺序生成笛卡尔积，不会静默截断。
- 每个日期场景必须同时填写名称、用途、开始日期和结束日期。日期区间作为一个原子维度处理；服务端依据实际 Bar 覆盖冻结数据查询定义，不使用交易日历推测可用日期。
- 点击“生成预览”后，页面展示服务端权威的 Trial 总数、各维度数量、预计 Bar 数、资源等级、预算阻塞项以及首尾 Trial 样例。浏览器不提交可信 Trial 总数或完整 Trial 数组；同一输入会得到相同的规范摘要、顺序和 Trial 指纹，但每次预览都会签发新的短期令牌。
- 修改任一实验输入都会立即使已有预览令牌失效。草稿按“当前用户 + 策略 + 发布版本 + 草稿结构版本”保存在本机；恢复草稿后必须重新预览，以重新确认行情数据、平台能力和资源预算没有漂移。
- 预览允许创建时，可以点击“确认创建并开始”。服务端会再次校验当前用户、发布版本、底层资产、数据快照、能力和硬上限；任一依据变化都会返回 `experiment.preview_stale` 并要求重新预览。创建事务只冻结 Experiment、首个 Revision、Stage、权威计划数、预算、资产保留和生成游标，不在页面请求中同步插入全部 Trial。
- 创建成功后页面立即显示 `preparing（准备中）` 及“已生成数 / 计划数”。独立协调器按稳定 `trialIndex` 分块生成 Trial，关闭或刷新浏览器不会暂停；网络响应不确定时页面使用原 `Idempotency-Key` 找回同一个 Experiment，不会盲目重复创建。
- Trial 全部生成且集合摘要校验通过后进入 `queued（已排队）`。协调器按配置的有限在途窗口逐个创建 TrialExecution 和普通标准 Bar 回测任务；每个首次执行的 Trial 只创建一个普通任务，继续使用既有 Worker、行情加载、撮合、账本和结果保存链路。Experiment 自身不占用回测执行槽位，也不会一次把全部 Trial 灌入普通任务队列。
- 同一用户的全部 Experiment 共享实验在途硬上限，创建多个 Experiment 不会获得更多额度；多个 Experiment 在剩余额度内按持久化顺序轮转。不同用户的任务继续由统一回测调度器按用户当前占用数公平领取。
- 同一用户存在普通手工回测时，协调器会为手工任务保留配置额度；手工任务等待超过门禁时间后，暂停为该用户补充新的实验 Trial。统一 Runner 在选定用户后优先领取其普通任务，避免大实验长期压后手工回测。
- 系统容量低于 Experiment 创建时冻结的预算，或当前统一调度容量已经用尽时，详情页显示 `experiment.capacity_blocked` 等可恢复原因。系统不会删除已生成 Trial、缩小网格、终止正在运行的任务或把阻塞记为失败；容量恢复后会从同一 Revision 继续。改变 Experiment 自身预算必须创建新 Revision，不能改写历史预算。
- 自动化回测功能默认关闭。容量与统一调度门禁未在目标服务器完成验证前，顶部入口保持隐藏；直接打开页面会明确显示“自动化回测能力尚未启用”，不能创建实验。
- 原策略后续更新、重新发布、重命名或归档不会改变已经冻结的实验。尚未物化的 Trial 仍使用创建时的策略代码、参数默认值、FeeProfile、Bar 来源与正式/预热日期、执行配置和确定性种子；若冻结运行能力已经不可用，系统停止新增物化并保留稳定原因，不改用当前版本顶替。
- 自动化首页显示最近实验及准备、排队、运行、成功、失败和取消数量。详情页以游标分页显示 Trial；已物化 Trial 可点击“查看单次结果”进入现有回测结果视图，实验页不复制交易明细或 K 线图。
- 普通 Worker 完成后，协调器从普通回测记录冻结结果 schema、结果摘要 hash 和实际行情 hash，更新 Trial 与实验聚合状态并释放在途 permit。重复对账不会重复释放；成功 Trial 的单次回测记录受实验历史保留约束，不能从历史列表单独删除。
- 实验详情页的“结果评价”读取不可变 Trial 结果。用户可以选择 MetricCatalog/DimensionCatalog 中的稳定字段，配置安全派生公式、行过滤、分组、聚合、分组公式、多级排序和高级分析，并保存不可变 EvaluationSpec。修改评价只改变结果分析，不会重新提交普通回测、修改 Trial 或覆盖原始回测结果。
- 点击“保存版本并运行”时，系统先保存评价版本，再创建 EvaluationRun。EvaluationRun 会同时冻结成功项的 `trialExecutionId`、`runId`、`resultHash` 映射和全部 Trial 的完成性快照，以及参与集合摘要、指标/维度目录版本、结果适配器版本和评价流水线版本；独立评价 Worker 校验每份原始结果的 SHA-256 后执行评价。后续 Trial 重试或新的评价版本不会改写已有评价输出。
- 评价顺序固定为“基础指标 → 行公式 → 行过滤 → 分组 → 聚合 → 分组公式 → 排序”。安全公式只接受数值、已声明指标、`+ - * /`、括号及 `abs`、`min`、`max`、`coalesce`；属性访问、下标、任意代码、未知字段、除零和非有限结果会明确失败。缺失值保持为空，普通算术传播空值，只有 `coalesce` 可以提供替代值。
- 聚合支持计数、均值、中位数、最小值、最大值、样本标准差和最近秩分位数。全部为空时结果为空；样本少于两个时样本标准差为空；升序和降序都把空值放在非空值之后，最终并列按 Stage、Trial 顺序稳定排列。若本金、日期窗口、年化日历、基准、运行路径、结果 schema 等可比较口径不同且没有冻结 Normalizer，运行会以 `experiment.metric_not_comparable` 明确失败。
- 参数曲线和二维热力图只展示实际运行的离散网格点，不插值；存在第三个及更多变化参数时，必须先固定或将其配置为系列/分面。成本压力只比较不同 Slippage 场景下独立运行的真实 Trial，不会在页面二次扣减收益。时间稳定性按创建 Revision 时冻结的日期顺序、用途、行情查询、复权和数据集摘要展示。
- `development`、`validation` 和 `reference` 只是研究用途标签。对全部候选运行过的 `reference` 不会显示为真正最终测试；真正 `test` 仍要求在候选冻结后的下游 Stage 解锁，首期评价不能据此宣称无偏最终测试结果。
- 默认完整评价要求全部 Trial 成功。开启 provisional 部分评价时，用户必须冻结最低完成率，并可逐项配置日期、参数、资金、成本或执行场景等关键维度的最低覆盖率；结果会显式显示成功、失败、取消、缺失、完成率和 `isPartial`，并完整列出异常项。provisional 输出不能被标记为最终报告，也不能驱动未来最终候选选择。未达到完成率或关键维度覆盖门槛时分别返回 `experiment.evaluation_partial_gate_failed` 或 `experiment.evaluation_dimension_coverage_failed`。
- 评价版本列表可以把旧版本载入为副本，也可以在同一旧版本上重复创建 EvaluationRun。相同评价版本、冻结执行与完整性集合和流水线版本会产生相同结果顺序与输出摘要。失败的 EvaluationRun 可以重试评价计算；重试仍使用原冻结事实，不触发回测。未分组排名行中的“查看结果”继续进入已有单次回测页面。
- 已完成的 EvaluationRun 下方提供“异步导出”。用户可以选择当前评价输出中的字段，生成 CSV 结果表、XLSX 结果表或 HTML 研究报告；创建请求只登记作业，不会在页面请求内同步生成大文件。关闭或刷新页面不影响独立导出 Worker 继续处理。
- 导出记录显示排队、生成、完成、失败、取消中、已取消和已过期状态，以及已处理行数、尝试次数、文件大小和 SHA-256。排队或生成中的作业可以取消；失败、取消或过期的记录可点击重新创建，新作业继续绑定原 EvaluationRun 的 `outputHash`、字段、语言和版本证据，不会改用后续评价结果。
- 下载前会重新校验当前登录用户、作业状态、有效期、文件大小和 SHA-256。评价导出文件默认保留 7 天；过期下载返回 `410 experiment.export_expired`，需要重新创建导出。下载链接不是公开分享链接，不能用于读取其他用户制品。
- CSV 和 XLSX 会对以 `= + - @` 开头的用户可控文本执行公式注入防护。研究报告只包含脱敏的实验对象、资产版本、固定结构摘要、搜索空间、评价规则、指标口径、完整成功/失败/取消/缺失清单、结果表和单次回测链接，不包含策略源码、私有路径、令牌、数据库连接或其他用户信息。
- 研究报告会明确说明用户自定义评分和排序不构成系统投资建议。provisional EvaluationRun 导出的报告仍标记为“部分评价”，完整显示失败、取消与缺失项，不能被表述为最终报告或真正最终测试。
- `experiment.evaluation_result_set_incomplete` 表示完整评价存在失败、取消、未生成、未完成或没有成功选定执行的 Trial；`experiment.evaluation_result_hash_mismatch`、`experiment.evaluation_data_hash_mismatch` 分别表示冻结后原始结果或实际行情摘要不一致；`experiment.evaluation_formula_invalid`、`experiment.evaluation_formula_division_by_zero` 表示公式不安全或计算非法；`experiment.evaluation_field_unknown`、`experiment.evaluation_metric_unknown` 表示请求引用了目录外字段。
- 准备、排队或运行中的 Experiment 均可取消。取消请求会立即停止新的 Trial 生成和任务物化，并对已经提交的普通任务沿用现有取消语义：排队任务直接取消，运行中任务进入取消中并等待 Worker 收敛；取消完成后不会再创建新的 run。已成功结果、冻结定义、已提交 Trial 分块和审计记录都会保留。
- 取消与任务完成并发时，以普通回测任务已经接受的真实终态为准：成功先被接受时实验仍可聚合为完成；取消先被接受后到达的成功回报不会覆盖取消事实。详情页在收敛期间显示 `cancelling（取消中）`，最终按成功、失败和取消的实际数量区分 `completed（已完成）`、`partially_completed（部分完成）`、`failed（失败）` 或 `cancelled（已取消）`。
- 单个 Trial 失败不会中止其他 Trial。详情页按稳定错误分类和指纹汇总失败；系统只对策略允许的可重试系统错误执行有限自动重试，并同时受次数、观察窗口和冷却时间约束，不会无限重试。相同系统性错误按持久化终态顺序连续出现并达到阈值时，Experiment 进入 `execution_blocked（执行阻塞）`，停止新的任务物化。
- `generation_blocked` 和 `execution_blocked` 会显示稳定原因与阻塞范围。对可恢复的执行阻塞，用户可在详情页点击“恢复原 Revision”；服务端会重新校验用户权限、冻结资产、运行能力和当前容量，通过后从原 Revision 的未完成 Trial 继续，并记录恢复审计。修改冻结输入或预算仍须创建新 Revision，恢复不会改写历史定义。
- 协调器、Backend 或 Worker 重启后以数据库中的生成游标、租约、普通任务终态和执行事实继续处理；已成功 Trial 不会重跑。中断的普通任务仍按现有任务租约规则恢复，策略执行从该 Trial 起点重新开始，不从策略进程内存中的中间位置续跑。
- 若页面返回 `auth.csrf_invalid`，刷新页面后重新预览；`experiment.preview_expired` 或 `experiment.preview_stale` 需要重新预览，`idempotency.conflict` 表示同一请求键被用于不同创建内容，`experiment.plan_limit_exceeded` 表示用户未完成实验的计划总量超过上限。创建事务失败不会留下半成品实验、计划额度或审计记录。

开放 API Key 页面按回测和策略管理分组展示权限。`strategy:read` 用于读取策略和版本，`strategy:write` 用于创建、修改和恢复，`strategy:publish` 用于显式发布，`strategy:delete` 只执行可恢复归档。写入、发布和归档属于高权限操作，默认不勾选；已有 API Key 不会自动获得新增权限。API Key 即使属于管理员账号，也只能按 Key 的 Scope 和所属用户访问资源，不继承管理员能力。

开放策略写接口要求 `Idempotency-Key`。修改、发布、归档和恢复还要求当前 `expected_revision`；过期 revision 返回 `strategy.revision_conflict`。相同幂等键和相同请求重放首次响应，不同请求复用同一键返回 `idempotency.conflict`。不存在和无权访问统一返回 `strategy.not_found`，不会暴露其他用户资源。

浏览器登录会话的所有写操作都使用页面统一维护的 CSRF Token，并同时校验请求来源；登录本身除外。页面刷新后会自动轮换 Token，登出、策略保存与归档、Bar/L2 回测提交与取消、共享、信号明细导出以及评价导出均使用同一保护。若页面显示 `auth.csrf_invalid`，说明 Token 已过期或请求来源不受信任，应刷新当前页面后重试；失败请求不会进入业务事务。开放 API Key 调用不使用浏览器 CSRF Token，仍按各自 Scope、限流与审计规则执行。

### 2.3 管理历史回测

- “历史回测”会保存每次任务的代码、参数、行情数据与结果快照；可查看结果、复制参数重新运行或保存备注和标签。
- 历史列表按页从服务器读取，可通过页码访问全部历史记录；每页可显示 10、20 或 50 条。关键词和标的筛选作用于全部历史记录，不限于当前页。
- 单条勾选、多条勾选和表头复选框使用同一个“已选择记录”操作条。表头复选框只选择或取消当前页可操作记录，不会清除其他页已选记录；当前页全部选中后，还可以继续选择当前筛选条件下的全部可操作记录。修改搜索、标的、方案或收藏筛选会清空旧选择，翻页不会清空。
- 可点击每条历史回测编号前的星标进行收藏或取消收藏；收藏状态会跨刷新和重新登录保留。“只看收藏”可与关键词、标的筛选组合使用，并按最近收藏时间显示。收藏不阻止永久删除，历史回测删除后其收藏状态一并消失。
- 对比对象可按回测编号、标的、策略、方案或标签搜索；已选回测及对比对象在主列表翻页后仍会保留。
- 已成功、失败或取消的历史回测可在列表的操作区域点击“删除”。确认后，系统会永久删除数据库中的该回测记录及其关联任务、事件和错误记录，无法恢复。
- 平台默认独立保留 180 天的运行环境错误聚合，只含错误码、固定运行时版本、标准内置名称、时间和次数，不能关联或恢复已删除任务，也不包含用户、源码和参数。
- 可勾选当前页中的多条已结束回测，再点击“删除所选”批量删除。系统会先校验所有选中记录；只要其中有排队、运行中或无权限记录，整批不会删除。
- 排队、运行中或取消中的任务不能删除；应先取消并等待任务进入“已取消”终态。
- 取消排队任务会直接进入“已取消”；取消运行中的标准 Bar 用户策略会终止该任务的独立策略子进程，释放其 CPU、内存和执行槽位。取消是幂等操作，任务已结束时页面会显示数据库中的实际终态。
- 删除历史回测不会删除策略脚本、策略方案或其发布版本。

### 2.3.1 批量导出信号明细

- 在历史回测列表选择一条或多条记录后，点击“批量导出信号明细”。单选、多选、本页全选、跨页手动选择和当前筛选结果全选都使用同一入口，不限制为当前页或 50 条。
- 系统在服务端异步生成 ZIP，关闭页面不影响任务继续执行。点击历史回测页面顶部的“信号明细导出记录”可以查看等待、准备、生成、取消、失败、完成和过期状态；生成过程中可以取消，瞬时失败或已过期任务可以重新导出。
- ZIP 中每条符合条件的回测对应一个 CSV，全部保存在同一个“信号明细”目录中，文件名为“标的_回测冻结的策略方案名称_回测编号.csv”。方案后续改名或删除不会改变文件名。CSV 的类型、字段、顺序、编码和内容规则与单条回测“信号明细”中各筛选项均为“全部”时的现有导出一致；ZIP 不包含额外报表或清单。
- 只有成功完成、结果结构兼容且至少包含一条成交或跳过信号的回测会写入 ZIP。准备完成后，导出记录会分别显示实际导出数量和被排除数量，避免静默遗漏。
- 任务成功后，在“信号明细导出记录”中点击“下载信号明细 ZIP”。文件默认保留 24 小时；过期后需要重新导出。下载必须通过当前登录会话完成，不提供外部公开链接。

### 2.3.2 共享回测与策略广场

“策略广场”用于在本系统的内部登录用户之间共享一份已经成功完成的回测。它不是匿名公开站点，也不会让外部 API Key 获得跨用户读取能力。

- 只有回测所有者可以从“历史回测”的操作区点击“共享到策略广场”。可共享的任务必须已经成功完成，并且保存了完整的代码、业务参数和结果快照；较早的历史任务如缺少其中任一项，需要按当前配置重新运行后再共享。
- 共享前填写标题、说明和标签。系统会创建独立、不可变的共享快照，并展示作者姓名、策略代码、业务参数、数据范围、结果指标以及用于复现的结果明细和依赖摘要。账户关联、用户与任务标识、服务器路径、原始请求和系统诊断不会进入公开读取契约。
- 策略代码本身会完整展示。发布者应先检查代码、说明和参数中是否手工写入了口令、令牌、账号或其他敏感文字；系统无法判断业务文本中每一段内容是否适合内部共享。
- 所有正常状态的内部登录用户都可以在“策略广场”按标题、作者姓名、标的或标签搜索，按策略类别和周期筛选，按最新发布或复制次数排序，并收藏仍在展示的共享回测。
- 详情页分别展示上下文、代码、参数、收益曲线和分页结果明细。共享结果只用于内部交流和复现参考，不代表实盘收益承诺；行情版本、费用、滑点、成交模型或依赖数据不同，重新运行的结果可能不同。
- 点击“复制为我的策略”只会创建当前用户独立拥有的普通策略、脚本和不可变版本，不会自动发起回测，也不会复制作者的账户关联、历史任务或收藏关系。复制完成后必须检查代码和参数、选择自己的账户，再手动保存或运行。连续重复点击同一共享回测会返回同一份副本，不会重复创建或重复累计复制次数。
- 研究信号等必要附件会复制到接收者自己的隔离空间，并在副本中换成新的依赖标识；副本仍保留来源共享记录，便于追溯。附件复制受数量、单文件大小和总大小限制，缺失或摘要不一致时系统会拒绝复制，不会创建不完整副本。
- 发布者可以在“我的共享”中修改标题、说明和标签，可以撤回后重新上架。撤回会立即停止普通用户发现、收藏和新复制，但不会删除共享记录、历史收藏或已经复制的独立策略；重新上架沿用原共享编号、首次发布时间和统计数据。
- 管理员可以在“共享管理”中填写原因后下架内容，也可以恢复展示。管理员下架后，发布者不能自行重新上架；下架原因仅在作者和管理员的管理界面显示，普通访问统一提示“该共享回测已不可用”。
- 原历史回测、原策略或作者账号之后被删除或归档，不会删除已经创建的共享快照和策略副本。作者账号删除后，既有共享内容仍按冻结的作者姓名展示，但不再提供作者管理入口。
- 当前版本不提供直接运行他人共享任务、点赞、评论、关注或收益排行榜；复制后的策略必须在自己的权限和风控边界内运行。

### 2.4 发布前检查

- 确认不会在空仓时发送平仓动作。
- 确认平仓数量不超过实际持仓。
- 确认多头和空头的动作没有写反。
- 确认每一个分支都返回列表，而不是返回单个字典或 `None`。
- 确认策略对连续多根满足条件的 K 线不会重复开仓，除非这正是设计目标。
- 确认回测中的“下一根 Bar 开盘虚拟成交”或 L2 后续盘口成交与 `slippage（滑点）` 配置符合策略预期；该规则不代表实盘一定能以同样价格成交。

## 3. 策略编写指南

### 3.0 提供给 AI 的完整指南地址

系统在当前部署主机下提供不需要登录的只读 Markdown 地址：`/strategy-guide.md`。例如服务器地址为 `http://192.168.251.1:28601` 时，完整地址为 `http://192.168.251.1:28601/strategy-guide.md`。

- 在策略编辑器的“策略编写指南”中，可使用“打开 Markdown”查看原文，或使用“复制公开链接”将地址提供给可访问该服务器的 AI。
- 该地址只提供本手册，不提供任意项目文件、用户策略、回测记录或系统配置。
- 要求 AI 生成策略时，应明确要求其完整阅读本手册，并只使用当前文档定义的回调、字段和委托动作。

### 3.1 先选择回调场景

| 场景 | 必须定义的函数 | 何时使用 | 成交时点 |
| --- | --- | --- | --- |
| 标准 Bar 回放（快速） | `on_bar(bar, state)`；可选 `on_order_event(event, state)` | 只依赖已完成 K 线的策略 | 下一根可交易 Bar 开盘价加滑点；虚拟成交后发送完全成交回报。 |
| L2 订单驱动 | `on_bar(bar, state)` | 信号只依赖 Bar，但希望用十档盘口模拟主动成交 | 严格晚于信号 Bar 的后续快照。 |
| L2 连续快照 | `on_bar(bar, state)`、`on_quote(quote, state)` | 盘中止盈止损、开盘触发、盘口条件、分批下单 | `on_quote` 新订单严格从下一条快照开始成交。 |

新用户应从“普通 Bar 回测”开始。记住以下边界：

- 普通 Bar 策略看不到未完成 K 线。
- 标准 Bar 会执行 `on_bar` 与成交后的 `on_order_event`，但不会执行 `on_quote`；写在 `on_quote` 中的盘口止损、止盈和开平仓逻辑不参与标准 Bar 结果。
- L2 订单驱动策略不会每 3 秒调用一次。
- 只有定义 `on_quote` 才会启用连续快照回放。

### 3.2 最小模板：普通 Bar、单标的、只做多

适用范围：无底仓、普通股票、只做多、按当前所选周期的已完成 Bar 产生信号，并在下一根 Bar 开盘成交。

```python
# on_bar 会在每根已完成的 Bar 调用一次；周期由回测页面选择。
# bar['time'] 为 YYYYMMDDHHMMSS，bar['tradeDate'] 为 YYYY-MM-DD。
# 本模板只使用已完成 Bar 的 OHLC 和当前策略净仓位。
def on_bar(bar, state):
  if bar['position'] == 0 and bar['close'] > bar['open']:
    return [{'action': 'buy_open', 'quantity': 100, 'reason': '阳线开多'}]
  if bar['position'] > 0 and bar['close'] < bar['open']:
    return [{'action': 'sell_close', 'quantity': bar['position'], 'reason': '阴线平多'}]
  return []
```

这段代码只是最小示例，不是通用策略模板：

- 科创板开仓至少 200 股。
- L2 底仓增强策略还受 T+1 与做 T 额度限制。
- 资金不足、未启用方向或数量不合规则会被拒绝并写入明细。

### 3.2.1 最小模板：研究信号驱动

适用范围：标准 Bar 回放、按研究信号决定目标方向、由策略自行决定数量。保存前必须勾选“研究信号驱动策略”，运行前必须选择研究信号数据集。

```python
SIGNAL_QUANTITY = 200


def on_bar(bar, state):
  signal = bar.get('researchSignal')
  if signal is None:
    return []

  action = signal['action']
  position = bar['strategyPosition']

  if action == 'flat':
    if position > 0:
      return [{'action': 'sell_close', 'quantity': position, 'reason': '研究信号转为空仓'}]
    if position < 0:
      return [{'action': 'buy_close', 'quantity': abs(position), 'reason': '研究信号转为空仓'}]
    return []

  if action == 'long':
    if position < 0:
      return [{'action': 'buy_close', 'quantity': abs(position), 'reason': '研究信号转多，先平空'}]
    if position == 0:
      return [{'action': 'buy_open', 'quantity': SIGNAL_QUANTITY, 'reason': '研究信号开多'}]
    return []

  if action == 'short':
    if position > 0:
      return [{'action': 'sell_close', 'quantity': position, 'reason': '研究信号转空，先平多'}]
    if position == 0:
      return [{'action': 'sell_open', 'quantity': SIGNAL_QUANTITY, 'reason': '研究信号开空'}]
  return []
```

`SIGNAL_QUANTITY（信号目标数量）` 由策略代码定义；示例使用 200 股，实际策略应替换为自己的仓位和风控计算。

这个模板有四个重要语义：

- 当前有效信号会在后续 Bar 持续提供，因此平掉反向仓位后，下一根 Bar 仍可按同一信号建立目标方向，不需要等待新信号。
- 使用 `strategyPosition（当前脚本净持仓数量）`，只调整策略形成的仓位，不会把 `basePosition（初始底仓数量）` 当成信号仓位平掉。
- 每次回调最多返回一条委托；方向反转时先平后开，避免依赖同一根 Bar 多委托的未定义撮合顺序。
- 使用 `short` 信号前必须在回测配置中启用做空方向；只做多策略可把 `short` 分支改成平多后保持空仓。

### 3.3 最小模板：L2 盘口内止盈

适用范围：入场信号仍由已完成 Bar 确认，但持仓后需要在每条 3 秒快照检查止盈。定义 `on_quote` 后自动启用连续回放；标准 Bar 模式会忽略该函数，但仍可执行 `on_bar` 信号和 `on_order_event` 回报。

```python
def on_bar(bar, state):
  if bar['position'] == 0 and bar['close'] > bar['open']:
    return [{'action': 'buy_open', 'quantity': 100, 'reason': 'Bar 确认开多', 'clientOrderKey': 'entry'}]
  return []

def on_quote(quote, state):
  entry_price = state.get('entryPrice', 0.0)
  if quote['position'] > 0 and entry_price > 0 and quote['lastPrice'] >= entry_price * 1.01:
    return [{'action': 'sell_close', 'quantity': quote['position'], 'reason': '3秒快照止盈', 'clientOrderKey': 'take-profit'}]
  return []

def on_order_event(event, state):
  if event['type'] == 'filled' and event.get('clientOrderKey') == 'entry':
    state['entryPrice'] = event['price']
  if event['type'] == 'filled' and event.get('clientOrderKey') == 'take-profit':
    state.pop('entryPrice', None)
```

不要在 `on_bar` 提交订单时就写入成交价或推进分批阶段：

- 订单可能部分成交、被拒绝或被撤销。
- 应在 `on_order_event` 的 `partial_fill（部分成交）`、`filled（完全成交）` 事件中更新状态。

### 3.4 `state（策略状态）` 的正确使用

`state` 是当前一次回测会话内的可读写字典：

- 会跨同一任务中的 Bar、Quote 与委托回报回调保留。
- 任务结束、重跑或 worker 重启后不承诺恢复。
- 适合保存已成交均价、阶段序号、待处理 `clientOrderKey（客户订单键）` 和当日标记。
- 不应用它替代系统账户、持仓或现金。

### 3.5 下单前检查清单

1. `quantity（下单数量）` 是大于 0 的整数；普通股票通常按 100 股，科创板开仓至少 200 股。
2. `buy_open（买入开多）` 受现金限制；`sell_open（卖出开空）` 要求回测方案启用 `allowShort（允许做空）`。
3. `sell_close（卖出平多）` 不得超过可平仓位；L2 中当天买入不增加当日可卖数量。
4. 底仓增强策略的 `position（净持仓）` 不等于可自由交易仓位；应使用 `strategyPosition（策略净持仓）`、`basePosition（底仓数量）`、`sellableQuantity（当日可卖数量）` 和 `t0AvailableQuantity（当日做T剩余额度）`。
5. L2 中任何新订单都不能使用产生该订单的同一条快照成交；这是无前视规则。

### 3.6 从 QMT 迁移策略

迁移时请按下面边界处理：

- 保留交易判断、仓位比例、风控阈值和开平仓顺序。
- 删除账户号、固定标的、订阅、`passorder`、QMT 回调对象、文件持久化、监控目录和平台日志。
- 改用当前回测的 `bar['symbol']`、`quote['symbol']`、账户字段、标准 action 和委托回报。
- QMT 一秒 Tick 在本系统中只能映射为可见的 3 秒 `on_quote` 快照；不能假定两次快照之间的价格路径存在。

### 3.7 Python 运行时能力与禁止项

新回测使用版本化的 Python 3.12 策略运行时。可以直接使用该版本的标准内置能力，例如 `tuple`、`enumerate`、`zip`、`reversed`、`slice`、`list`、`dict`、`set`、`sorted` 和数值转换函数，无需等待平台逐项开放；也可以导入运行镜像中已经安装的模块，但不能在回测过程中安装依赖。

平台当前承诺支持以下量化计算库：

| 发行包 | 导入名 | 固定版本 | 典型用途 |
| --- | --- | --- | --- |
| `numpy` | `numpy` | `2.5.2` | 数组与数值计算 |
| `pandas` | `pandas` | `2.2.3` | 时间序列与滚动窗口 |
| `scipy` | `scipy` | `1.18.1` | 统计、信号处理与优化 |
| `TA-Lib` | `talib` | `0.7.1` | SMA、EMA、RSI、MACD 等技术指标 |
| `statsmodels` | `statsmodels` | `0.15.0` | 回归、统计检验与时间序列模型 |

策略仍需通过 `state` 自行积累指标输入。标准 Bar 可以使用 `WARMUP_TRADING_DAYS` 预热；L2 不支持非零系统预热，只能在正式区间前部积累且在窗口形成前保持不交易。量化结果应先用 `math.isfinite()` 或 `numpy.isfinite()` 检查，订单数量需显式转换为 Python `int`。`scikit-learn`、`numba`、外部数据源、交易客户端和第三方回测框架不属于当前支持范围。

标准 Bar 的 TA-Lib 最小示例：

```python
import numpy as np
import talib

WARMUP_TRADING_DAYS = 30


def on_bar(bar, state):
  closes = state.setdefault("closes", [])
  closes.append(float(bar["close"]))
  values = np.asarray(closes, dtype=float)
  sma = talib.SMA(values, timeperiod=20)[-1]
  if not np.isfinite(sma):
    return []
  if bar["strategyPosition"] == 0 and bar["close"] > float(sma):
    return [{"action": "buy_open", "quantity": int(100), "reason": "收盘价上穿 SMA20"}]
  if bar["strategyPosition"] > 0 and bar["close"] < float(sma):
    return [{"action": "sell_close", "quantity": int(bar["strategyPosition"]), "reason": "收盘价跌破 SMA20"}]
  return []
```

标准 Bar 的预热回调可用于形成指标，但预热区间不会成交；正式区间产生的信号仍在下一根可交易 Bar 开盘撮合。L2 策略必须将 `WARMUP_TRADING_DAYS` 保持为 `0` 或不声明，并在正式区间的 `on_bar` 中使用相同方式积累窗口；`np.isfinite()` 返回 `False` 时必须返回 `[]`，形成指标后产生的新订单仍只能使用严格后续盘口成交。

导入未安装且不在上述承诺清单中的模块时，保存或运行会返回 `strategy.module_unavailable`，应修改策略或申请平台增加依赖。若返回 `runtime.dependency_missing`、`runtime.dependency_load_failed` 或 `runtime.version_mismatch`，属于平台镜像或发布一致性问题，用户无需修改正确策略。

保存策略失败时，错误详情显示在代码编辑区上方，右侧参数栏和当前未保存的参数保持可见，便于对照修改。失败的保存不会生成新版本；修正代码后需再次点击“保存策略”。

为保证可复现性和交互安全，策略不得直接调用 `open`、`input`、`breakpoint`、`eval`、`exec`、`compile`、`help`、`exit` 或 `quit`。保存或运行时会返回 `strategy.runtime_policy_blocked`，不会再误报为“变量未定义”。这些规则定义策略产品契约；进程、容器、只读文件系统和资源限制才是运行隔离边界。

## 4. 最小可运行策略

```python
# 此示例等同于 3.2 的普通 Bar、单标的、只做多模板。
def on_bar(bar, state):
  if bar["position"] == 0 and bar["close"] > bar["open"]:
    return [{"action": "buy_open", "quantity": 100, "reason": "阳线开多"}]
  if bar["position"] > 0 and bar["close"] < bar["open"]:
    return [{"action": "sell_close", "quantity": bar["position"], "reason": "阴线平多"}]
  return []
```

这段代码的行为是：

1. `position`（当前持仓数量）为 `0` 且收盘价高于开盘价时，返回 100 股开多委托。
2. `position`（当前持仓数量）大于 `0` 且收盘价低于开盘价时，返回全部平多委托。
3. 其他情况不产生委托。

### 5.1 `on_bar(bar, state)`（K线回调函数）

| --- | --- |

### 5.2 `bar`（当前K线及账户数据）字段

| 字段 | 含义 | 使用提示 |

| `high` | 最高价 | 可用于基于已完成 K 线的止损、突破或波动计算。 |

### 5.3 委托字典

每条委托至少使用以下字段：

| 字段 | 含义 | 要求 |
| --- | --- | --- |
| `action`（交易动作） | 下单方向与开平含义 | 必须是下表中的一个值。 |
| `quantity`（下单数量） | 本次委托数量 | 应为正数；平仓不得超过可平持仓。最小单位与是否允许零股由系统规则决定。 |
| `reason`（下单原因） | 供日志和结果分析使用的说明 | 推荐填写简短中文说明，例如“均线上穿开多”。 |
| `clientOrderKey`（客户订单键） | 策略自定义的未终结订单标识 | 可选；同一键未终结时不可重复下单，回报用它关联状态。 |

## 6. 编写规则与示例

### 6.1 无信号必须返回空列表

```python
def on_bar(bar, state):
  return []
```

不要省略 `return`。Python 默认返回 `None`，而编辑器要求的是委托列表。

### 6.2 只在确认后的条件下下单

```python
def on_bar(bar, state):
  is_bullish = bar["close"] > bar["open"]
  if bar["position"] == 0 and is_bullish:
    return [{"action": "buy_open", "quantity": 100, "reason": "阳线确认开多"}]
  return []
```

变量 `is_bullish`（本根K线是否为阳线）只基于已完成 K 线的数据判断，因此不会使用未收盘价格。

### 6.3 多条委托前先确认系统语义

当前最小契约尚未定义以下语义：

- 同一根 K 线返回多条委托时的执行顺序；
- 多条委托之间的部分成交关系；
- 多条委托的资金占用顺序。

在这些规则确认前，每次回调推荐只返回一条委托，避免依赖未定义的撮合顺序。

## 7. 常见问题

### 为什么策略没有交易？

先检查：

1. 当前 K 线是否已经完成。
2. 条件是否真的满足，例如 `close > open`。
3. `position`（当前持仓数量）是否符合分支条件。
4. 返回值是否为列表，且 `action`（交易动作）拼写正确。
5. `quantity`（下单数量）是否为正数并符合系统最小数量要求。

### 为什么一段时间内连续开仓？

可能原因：

- 策略扩展后删除了 `position == 0` 的开仓限制；
- 持仓更新、部分成交或未完成委托与策略预期不一致；
- 同一触发条件连续成立，但策略没有防重入状态。

处理方法：先确认委托回报、部分成交和挂单占用的系统语义，再用 `state` 记录待处理订单或阶段，避免重复开仓。

### 可以在 `state`（策略状态）保存开仓价或止损价吗？

可以在当前一次回测会话内保存开仓价、止损价、阶段序号和待处理订单标识。`state` 会跨同一任务中的 Bar、Quote 与委托回报回调保留。

注意：任务结束、重跑或 worker 重启后不承诺恢复。因此，`state` 不能替代系统账户、持仓、现金或跨任务持久化存储。

### 回测结果能直接等同于实盘结果吗？

不能。

- 普通 Bar 回测以信号后的下一根可交易 K 线开盘价为基础，并按配置滑点虚拟成交。
- L2 回测使用可见十档盘口模拟成交，但仍只覆盖 3 秒采样点。
- 实盘还受行情跳动、撮合、资金、券源、涨跌停和交易时段影响。

回测用于验证规则，不保证实际成交价格。

### 能否同时做多和做空？

方向性持仓可以使用 `buy_open（买入开多）`、`sell_close（卖出平多）`、`sell_open（卖出开空）`、`buy_close（买入平空）` 四类动作；是否接受开空还受 `allowShort（允许做空）` 控制。

底仓增强不是融券多空账。引擎把策略买卖统一落实到实际股票持仓，再用相对目标底仓的有符号偏离解释正增强或负增强；实际净仓不得因负增强降到零以下。

### 为什么某笔成交收益与增强周期收益不同？

两者回答的问题不同：

- `accountRealizedPnl（账户会计已实现损益）` 解释账户按库存成本卖出后确认了多少损益；
- `realizedOverlayPnl（本次已实现增强收益）` 解释该成交恢复了多少增强仓，以及相对增强开仓成本实现了多少收益；
- `completedCyclePnl（完整周期收益）` 汇总同一增强仓从离开 0 到回到 0 期间的所有已实现增强收益。

因此，跨日分批补回时，每个交易日可以有已实现增强收益，但只有最后恢复到目标底仓的那一笔成交会把周期标记为完成。未完成周期按最后行情估值，不进入胜率。
