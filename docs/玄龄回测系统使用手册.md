# 玄龄回测系统使用手册

> 版本：1.0  
> 适用对象：在策略代码编辑器中编写、回测或维护 K 线策略的使用者和维护者。

## 1. 先读这一页

策略代码编辑器采用“已完成 K 线触发、返回委托列表”的方式运行：系统在每根指定周期 K 线结束后调用策略函数，策略读取当前 K 线和账户快照，返回本根 K 线需要执行的委托。

当前编辑器给出的契约为：

- `on_bar(bar, state)`（K线回调函数）会在每根**已完成**的 5 分钟 K 线上调用一次。
- 信号在本根 K 线收盘时生成，并以本根收盘价为基础虚拟成交；配置非零 `slippage（滑点）` 后，买入价上调、卖出价下调。
- `bar`（当前K线及账户数据）可读取 `time`、`datetime`、`tradeDate`、`hhmm`、`open`、`high`、`low`、`close`、`volume`、`cash`、`equity`、`position`、`strategyPosition`、`basePosition`、`sellableQuantity`、`t0AvailableQuantity`、`params`。`time` 固定为 `YYYYMMDDHHMMSS`；`tradeDate` 固定为 `YYYY-MM-DD`；交易时段判断使用 `hhmm`，例如 `931`。
- 每次调用必须返回委托列表；无委托时返回 `[]`。

这意味着：策略不能把尚未收盘的价格当作已确认信号，也不能假设能在一根 K 线内部再次被调用。

选择 `l2_quote（基础L2盘口回测）`（基础L2盘口回测）后，`on_bar(bar, state)`（K线回调函数）仍只在已完成 Bar 的结束时调用一次，但委托不会按本根收盘价直接成交：订单只可使用**严格晚于**该 Bar 结束时间的十档盘口撮合。即使 `l2LatencyMs（L2模拟延迟毫秒数）` 为 `0`，同一时间戳的盘口也不会用于成交该订单。市价单与可立即成交的限价单按后续十档盘口逐档、可部分成交。

L2 脚本可额外定义 `on_quote(quote, state)`（3秒盘口回调函数）和 `on_order_event(event, state)`（委托回报回调函数）。定义 `on_quote` 后，该脚本自动使用 `continuous（连续快照）`：连续竞价时段内所有可见 3 秒快照依时间顺序回放；先撮合已生效旧订单并发送成交回报，再调用当前 `on_quote`。`on_quote` 新产生的订单只能使用**下一条**快照成交。未定义 `on_quote` 的脚本保持 `order_driven（订单驱动）`，不会读取无订单区间的盘口。3 秒快照只能表达可见采样点，不能替代一秒 Tick 或逐笔成交路径。

正式 L2 Bar 表尚未配置时，系统会临时从 `quant.tick_quote（L2 三秒十档快照表）` 聚合 `1m/3m/5m/15m/30m/45m/60m/1d` Bar。分桶只覆盖连续竞价 `09:30–11:30` 与 `13:00–14:57`，上午、下午分别从时段起点对齐；`14:57–15:00` 的收盘集合竞价不按十档盘口撮合或聚合。`45m` 保留时段尾部 Bar，日线合并两个连续竞价时段。仅已收盘的历史交易日可运行；Bar 无有效价格或存在负量额会明确失败，不回退为收盘价成交。快照间隔仅作为观测指标，不影响 Bar 可用性。聚合后的历史 Bar 以规则和映射版本隔离缓存到 Redis，缓存被淘汰或不可用时会自动从 ClickHouse 重建，不影响回测语义。

L2 回测以异步任务执行。提交后页面会自动轮询；任务成功时自动打开概览和信号明细，无需重新运行或手动刷新。信号明细会保留已成交、策略方向限制跳过、撮合拒绝以及日终撤单的信号；部分成交会分别列出实际成交数量和未成交的剩余数量。L2 首版不计算基准曲线，因此超额收益显示为 `--`，并在结果告警中说明。

回测失败时，页面将区分两类错误。`strategy_error（策略错误）` 会展示发生的 `callback（策略回调）`、`eventTime（事件时间）`、`symbol（标的）`、安全原因与修改建议；应据此检查脚本字段、变量、盘口档位、返回值或下单动作。`system_error（系统错误）` 只展示安全提示和 `taskId（任务编号）`，不显示服务地址、SQL 或 Python 堆栈；持续出现时将任务编号提供给维护人员。历史任务若没有保存结构化错误详情，会显示兼容提示，不会回显旧的原始异常文本。

临时快照表中 `last_price（最新价）` 使用元价格，而十档 `bid_price_*（买价）`、`ask_price_*（卖价）` 使用万分之一元整数；适配器会分别换算，策略和撮合均使用元价格。`allowShort（允许做空）` 同时决定策略是否产生开空信号及 L2 撮合是否接受开空委托。科创板 `688/689` 标的的开仓委托最小数量为 200 股，之后可按 1 股递增。

基础 L2 回测以订单驱动方式回放：没有待成交订单时，系统只推进已完成 Bar，不读取两根 Bar 之间的 3 秒盘口；`on_bar` 产生待成交订单后，才按时间顺序读取后续十档快照，直到订单完全成交、撤单或收盘。市价单和主动限价单按当时可见盘口逐档成交，盘口不足时会继续读取后续快照并部分成交或日终撤单；不读取逐笔成交 `tick_data`。涨停或跌停封板时，价格为 0 的档位表示该侧没有挂单：另一侧有效盘口仍可用于成交；需要空侧对手盘的委托保持未成交，不回填上一笔价格。

L2 回测可选择 `1m`、`3m`、`5m`、`15m`、`30m`、`45m`、`60m` 和 `1d`；这些 Bar 均按交易时段起点从十档快照临时聚合并缓存，策略方案保存时按 L2 周期白名单校验，不依赖 QMT 分钟数据覆盖。

回测必须选择 `strategyCategory（策略类别）`。`directional_holding（方向性持仓策略）` 在信号时开多、开空或平仓后跨日持有真实仓位，概览和“持仓收益”用于评价方向判断、买入持有和未来选股组合。`core_position_overlay（底仓增强策略）` 围绕固定底仓进行日内做 T，固定使用基础 L2 盘口并在日终恢复底仓，概览和“底仓增强收益”用于评价相对底仓的增厚收益。

底仓增强策略可设置 `baseQuantity（底仓数量）` 与 `baseCostPrice（底仓成本价）`。`initialCapital（初始资金）` 始终是独立可用现金，底仓成本不从其中扣除；但收益、回撤的起点会计入底仓成本市值。账户内部将 `baseQuantity（底仓数量）`、`longQty（策略开多仓位）`、`shortQty（策略开空仓位）` 分账记录。`t0Enabled（启用底仓做T）` 时，`t0AvailableQuantity（当日做T剩余额度）` 从 `baseQuantity（底仓数量）` 开始，策略 `BUY_OPEN（开多）` 或 `SELL_OPEN（开空）` 的实际成交都会消耗同一额度；余额小于标的最小下单量时，后续开仓信号会被跳过，平仓不会恢复额度。尾盘强制将策略多仓、策略空仓分别清零，只保留底仓数量。

底仓增强策略概览会展示总账户收益率、底仓持有收益率和做 T 超额收益。总账户收益以 `initialCapital（初始资金）+ 底仓初始市值` 为起点；底仓持有收益假设现金不动、底仓始终持有到期末收盘；做 T 超额收益为实际期末权益减去该底仓持有基准，做 T 超额收益率以底仓初始市值为分母。方向性持仓策略不显示底仓与做 T 指标，而是展示实际持仓、组合收益、基准收益和超额收益。

“持仓收益”或“底仓增强收益”详情默认筛选本次回测的起止日期，并同时展示初始总资产与期末总资产。方向性持仓策略的初始总资产等于初始资金；底仓增强策略的初始总资产等于初始资金加底仓初始市值。

`core_position_overlay（底仓增强策略）` 固定使用 `intraday（日内）`：尾盘目标是恢复至底仓数量，先按 `14:57` 前最后有效十档盘口完成差额；若封板、盘口缺边或深度不足仍有差额，系统按最后可观察最优价生成“尾盘涨跌停强制结算”或“尾盘盘口深度不足强制结算”成交。该成交是回测结算假设，不代表实盘可成交订单，并会在明细与告警中明确标识；必要时可使可用现金为负。`directional_holding（方向性持仓策略）` 固定使用 `overnight（允许跨日）`，不执行尾盘恢复，保留实际仓位至下一交易日；早期没有策略类别的历史记录仍按其原 `holdingPolicy（持仓规则）` 解释。

## 2. 系统使用流程

回测日期统一填写为 `YYYY-MM-DD（ISO交易日格式）`，例如 `2026-06-01`。历史记录中的旧 `YYYYMMDD（紧凑交易日格式）` 会在读取时自动兼容转换；策略、接口和任务结果均以 ISO 格式显示。

### 2.1 编写前

1. 明确交易周期。当前契约示例为 5 分钟 K 线；若编辑器的周期配置改变，先确认回调频率与成交规则是否同步变化。
2. 明确策略只做多、只做空还是双向。最小示例只覆盖多头。
3. 明确每笔数量、最大持仓、止损和交易时段。没有写出的风控规则不会由示例自动补上。

### 2.2 编写与运行

1. 在策略代码编辑器中定义 `on_bar(bar, state)`（K线回调函数）。
2. 只读取当前契约明确提供的 `bar`（当前K线及账户数据）字段。
3. 根据条件返回一条或多条委托字典；没有信号时返回 `[]`。
4. 运行回测后，逐笔检查信号 K 线、成交价、仓位变化和委托原因。

若策略需要盘中盘口触发，可增加 `on_quote(quote, state)`；`quote` 可读取 `time`、`datetime`、`tradeDate`、`hhmm`、`symbol`、`lastPrice`、`bids`、`asks` 及与 `bar` 相同的账户字段。每一档 `bids/asks` 为含 `price（价格）`、`volume（可见量）` 的字典。`on_order_event(event, state)` 可根据 `accepted（已受理）`、`partial_fill（部分成交）`、`filled（完全成交）`、`cancelled（已撤销）`、`rejected（已拒绝）` 更新状态；成交事件包含数量、累计成交量、价格、手续费与 `clientOrderKey（客户订单键）`。

从 QMT 迁移策略时，账户号、固定标的、订阅、`passorder`、文件持久化和监控目录属于原平台运行环境，必须移除；策略应使用当前回测请求的 `symbol（标的）`、账户资金、方向权限和行情事件。仅保留已确认的交易判断、仓位规则和风控条件。
5. 确认结果符合预期后，再评估是否进入实盘流程。

### 2.3 发布前检查

- 确认不会在空仓时发送平仓动作。
- 确认平仓数量不超过实际持仓。
- 确认多头和空头的动作没有写反。
- 确认每一个分支都返回列表，而不是返回单个字典或 `None`。
- 确认策略对连续多根满足条件的 K 线不会重复开仓，除非这正是设计目标。
- 确认回测中的“本 Bar 收盘虚拟成交”和 `slippage（滑点）` 配置与策略预期一致；该规则不代表实盘一定能以同样价格成交。

## 3. 策略编写指南

### 3.1 先选择回调场景

| 场景 | 必须定义的函数 | 何时使用 | 成交时点 |
| --- | --- | --- | --- |
| 普通 Bar 回测 | `on_bar(bar, state)` | 只依赖已完成 K 线的策略 | 当前 Bar 收盘价加滑点。 |
| L2 订单驱动 | `on_bar(bar, state)` | 信号只依赖 Bar，但希望用十档盘口模拟主动成交 | 严格晚于信号 Bar 的后续快照。 |
| L2 连续快照 | `on_bar(bar, state)`、`on_quote(quote, state)` | 盘中止盈止损、开盘触发、盘口条件、分批下单 | `on_quote` 新订单严格从下一条快照开始成交。 |

新用户从第一类开始。不要在普通 Bar 策略中假设能看到未完成 K 线，也不要在 L2 订单驱动策略中期待每 3 秒调用一次；只有定义 `on_quote` 才会启用连续快照回放。

### 3.2 最小模板：普通 Bar、单标的、只做多

适用范围：无底仓、普通股票、只做多、按当前所选周期的已完成 Bar 收盘成交。

```python
# on_bar 会在每根已完成的 Bar 调用一次；周期由回测页面选择。
# bar['time'] 为 YYYYMMDDHHMMSS，bar['tradeDate'] 为 YYYY-MM-DD。
# 本模板只使用已完成 Bar 的 OHLC 和当前策略净仓位。
def on_bar(bar, state):
  if bar['position'] == 0 and bar['close'] > bar['open']:
    return [{'action': 'buy_open', 'quantity': 100, 'reason': '阳线开多'}]
  if bar['position'] > 0 and bar['close'] < bar['open']:
    return [{'action': 'sell_close', 'quantity': bar['position'], 'reason': '阴线平多'}]
  return []
```

这段代码是最小示例，不是通用策略模板：科创板开仓至少 200 股；L2 底仓增强策略还会受 T+1 与做 T 额度限制；资金不足、未启用方向或数量不合规则会被拒绝并写入明细。

### 3.3 最小模板：L2 盘口内止盈

适用范围：入场信号仍由已完成 Bar 确认，但持仓后需要在每条 3 秒快照检查止盈。定义 `on_quote` 后自动启用连续回放。

```python
def on_bar(bar, state):
  if bar['position'] == 0 and bar['close'] > bar['open']:
    return [{'action': 'buy_open', 'quantity': 100, 'reason': 'Bar 确认开多', 'clientOrderKey': 'entry'}]
  return []

def on_quote(quote, state):
  entry_price = state.get('entryPrice', 0.0)
  if quote['position'] > 0 and entry_price > 0 and quote['lastPrice'] >= entry_price * 1.01:
    return [{'action': 'sell_close', 'quantity': quote['position'], 'reason': '3秒快照止盈', 'clientOrderKey': 'take-profit'}]
  return []

def on_order_event(event, state):
  if event['type'] == 'filled' and event.get('clientOrderKey') == 'entry':
    state['entryPrice'] = event['price']
  if event['type'] == 'filled' and event.get('clientOrderKey') == 'take-profit':
    state.pop('entryPrice', None)
```

不要在 `on_bar` 提交订单时就写入成交价或推进分批阶段。订单可能部分成交、被拒绝或被撤销；应在 `on_order_event` 的 `partial_fill（部分成交）`、`filled（完全成交）` 事件中更新状态。

### 3.4 `state（策略状态）` 的正确使用

`state` 是当前一次回测会话内的可读写字典，会跨同一任务中的 Bar、Quote 与委托回报回调保留；任务结束、重跑或 worker 重启后不承诺恢复。适合保存已成交均价、阶段序号、待处理 `clientOrderKey（客户订单键）` 和当日标记，不应用它替代系统账户、持仓或现金。

### 3.5 下单前检查清单

1. `quantity（下单数量）` 是大于 0 的整数；普通股票通常按 100 股，科创板开仓至少 200 股。
2. `buy_open（买入开多）` 受现金限制；`sell_open（卖出开空）` 要求回测方案启用 `allowShort（允许做空）`。
3. `sell_close（卖出平多）` 不得超过可平仓位；L2 中当天买入不增加当日可卖数量。
4. 底仓增强策略的 `position（净持仓）` 不等于可自由交易仓位；应使用 `strategyPosition（策略净持仓）`、`basePosition（底仓数量）`、`sellableQuantity（当日可卖数量）` 和 `t0AvailableQuantity（当日做T剩余额度）`。
5. L2 中任何新订单都不能使用产生该订单的同一条快照成交；这是无前视规则。

### 3.6 从 QMT 迁移策略

只保留交易判断、仓位比例、风控阈值和开平仓顺序。删除账户号、固定标的、订阅、`passorder`、QMT 回调对象、文件持久化、监控目录和平台日志；改用当前回测的 `bar['symbol']`、`quote['symbol']`、账户字段、标准 action 和委托回报。QMT 的一秒 Tick 在本系统中只能映射为可见的 3 秒 `on_quote` 快照，不能假定两次快照之间的价格路径存在。

## 4. 最小可运行策略

```python
# 此示例等同于 3.2 的普通 Bar、单标的、只做多模板。
def on_bar(bar, state):
  if bar["position"] == 0 and bar["close"] > bar["open"]:
    return [{"action": "buy_open", "quantity": 100, "reason": "阳线开多"}]
  if bar["position"] > 0 and bar["close"] < bar["open"]:
    return [{"action": "sell_close", "quantity": bar["position"], "reason": "阴线平多"}]
  return []
```

这段代码的行为是：

1. `position`（当前持仓数量）为 `0` 且收盘价高于开盘价时，返回 100 股开多委托。
2. `position`（当前持仓数量）大于 `0` 且收盘价低于开盘价时，返回全部平多委托。
3. 其他情况不产生委托。

## 5. 函数与字段参考

### 5.1 `on_bar(bar, state)`（K线回调函数）

| 项目 | 说明 |
| --- | --- |
| `bar`（当前K线及账户数据） | 当前已完成 K 线与账户快照。只应读取当前契约提供的字段。 |
| `state`（策略状态） | 当前回测会话内可读写的字典；跨同一任务的回调保留，不承诺跨任务或 worker 重启恢复。 |
| 返回值 | 委托字典组成的列表，例如 `[{...}]`；无委托时为 `[]`。 |

### 5.2 `bar`（当前K线及账户数据）字段

| 字段 | 含义 | 使用提示 |
| --- | --- | --- |
| `time` | 当前已完成 K 线的完成时刻 | 固定紧凑格式 `YYYYMMDDHHMMSS`，例如 `20260727093000`；存量策略可继续切片，新策略不应依赖字符串位置。 |
| `datetime` | 当前已完成 K 线的完成时刻 | 固定 ISO 格式 `YYYY-MM-DD HH:MM:SS`，例如 `2026-07-27 09:30:00`。 |
| `tradeDate` | 当前交易日 | 固定 ISO 格式 `YYYY-MM-DD`；用于跨交易日重置策略状态。 |
| `hhmm` | 当前完成时刻的时分 | 整数，例如 `931`、`1300`、`1457`；用于交易时段和尾盘规则。日线为 `None`。 |
| `open` | 开盘价 | 与 `close`（收盘价）比较可判断阳线或阴线。 |
| `high` | 最高价 | 可用于基于已完成 K 线的止损、突破或波动计算。 |
| `low` | 最低价 | 可用于基于已完成 K 线的止损、突破或波动计算。 |
| `close` | 收盘价 | 当前契约下，信号与虚拟成交均以该价格为基准；实际成交价会受 `slippage（滑点）` 调整。 |
| `volume` | 成交量 | 可用于成交量过滤。单位以编辑器实际数据定义为准。 |
| `cash` | 账户可用资金或资金快照 | 具体口径未在最小契约中定义；下单前不可据此臆测冻结资金规则。 |
| `equity` | 账户权益快照 | 可用于记录或风控计算；具体口径未在最小契约中定义。 |
| `position` | 当前净持仓数量 | 包含底仓和脚本成交仓位；多头为正、空头为负。 |
| `strategyPosition` | 当前脚本净持仓数量 | 仅当前脚本以自身委托形成的仓位，不含底仓。 |
| `basePosition` | 初始底仓数量 | L2 回测配置的底仓；未设置时为 `0`。 |
| `sellableQuantity` | 当日可卖数量 | L2 中按 T+1 计算；当天买入不增加该数值。非 L2 时为 `null`。 |
| `t0AvailableQuantity` | 当日做T剩余额度 | 仅启用底仓做 T 时为非负整数；未启用或非 L2 时为 `null`。 |
| `params` | 策略参数 | 参数结构、默认值和编辑方式需以编辑器实际配置为准。 |

### 5.3 委托字典

每条委托至少使用以下字段：

| 字段 | 含义 | 要求 |
| --- | --- | --- |
| `action`（交易动作） | 下单方向与开平含义 | 必须是下表中的一个值。 |
| `quantity`（下单数量） | 本次委托数量 | 应为正数；平仓不得超过可平持仓。最小单位与是否允许零股由系统规则决定。 |
| `reason`（下单原因） | 供日志和结果分析使用的说明 | 推荐填写简短中文说明，例如“均线上穿开多”。 |
| `clientOrderKey`（客户订单键） | 策略自定义的未终结订单标识 | 可选；同一键未终结时不可重复下单，回报用它关联状态。 |

### 5.4 `action`（交易动作）对照表

| 值 | 含义 | 常见用途 |
| --- | --- | --- |
| `buy_open` | 买入开多 | 建立或增加多头仓位。 |
| `sell_close` | 卖出平多 | 减少或平掉多头仓位。 |
| `sell_open` | 卖出开空 | 建立或增加空头仓位。 |
| `buy_close` | 买入平空 | 减少或平掉空头仓位。 |

## 6. 编写规则与示例

### 6.1 无信号必须返回空列表

```python
def on_bar(bar, state):
  return []
```

不要省略 `return`。Python 默认返回 `None`，而编辑器要求的是委托列表。

### 6.2 只在确认后的条件下下单

```python
def on_bar(bar, state):
  is_bullish = bar["close"] > bar["open"]
  if bar["position"] == 0 and is_bullish:
    return [{"action": "buy_open", "quantity": 100, "reason": "阳线确认开多"}]
  return []
```

变量 `is_bullish`（本根K线是否为阳线）只基于已完成 K 线的数据判断，因此不会使用未收盘价格。

### 6.3 多条委托前先确认系统语义

当前最小契约没有说明同一根 K 线返回多条委托时的执行顺序、部分成交和资金占用规则。因此，在这些规则未确认前，每次回调推荐只返回一条委托，避免依赖未定义的撮合顺序。

## 7. 常见问题

### 为什么策略没有交易？

先检查：

1. 当前 K 线是否已经完成。
2. 条件是否真的满足，例如 `close > open`。
3. `position`（当前持仓数量）是否符合分支条件。
4. 返回值是否为列表，且 `action`（交易动作）拼写正确。
5. `quantity`（下单数量）是否为正数并符合系统最小数量要求。

### 为什么一段时间内连续开仓？

最小示例仅在 `position == 0` 时开多。若系统的持仓更新有延迟、允许多条未完成委托，或策略扩展后删除了该判断，则可能出现重复开仓。需要先确认委托回报、部分成交和挂单占用的系统语义，再设计防重入状态。

### 可以在 `state`（策略状态）保存开仓价或止损价吗？

当前最小契约没有说明 `state`（策略状态）能否写入、是否跨 K 线保存、策略重启后是否恢复。因此，尚不能把它作为关键交易状态的可靠存储。系统补充该契约后，手册会给出正式示例。

### 回测结果能直接等同于实盘结果吗？

不能。当前规则是以信号 K 线收盘价为基础、按配置滑点调整后虚拟成交；实盘还会受到行情跳动、撮合、资金、券源、涨跌停和交易时段等影响。回测用于验证规则，不保证实际成交价格。

### 能否同时做多和做空？

动作表提供了开空和平空动作，但最小契约没有定义 `position`（当前持仓数量）在双向持仓下的表示方式，也没有定义多空能否同时存在。使用双向策略前，应先确认系统的持仓模型。
