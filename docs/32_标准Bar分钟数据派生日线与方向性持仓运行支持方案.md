# 标准 Bar 分钟数据派生日线与方向性持仓运行支持方案

> 现行决策说明：本文的日线派生与预热隔离仍有效；其中保存、提交前行情预检的描述已由 `docs/adr/0003-warmup-execution-isolation.md` 和 `docs/adr/0004-unified-preflight-and-loading.md` 的 2026-09-22 修订取代。

## 1. 背景与问题

方向性持仓类自定义策略通常在交易日收盘后，以日线 MA（移动平均线）、MA 斜率、MACD 等指标生成信号，并在下一交易日开盘成交、跨日持有。

当前系统的 `directional_holding（方向性持仓）` 已具备跨日持仓、下一根可交易 Bar 开盘成交、费用与收益核算能力；但标准 QMT 数据链路仅将 `15m`、`30m` 由 `1m` 派生，`1d` 需要原始日线覆盖。已有完整分钟数据而未导入原始日线时，用户策略不能以日线 Bar 直接运行。本期只改造标准 QMT Bar 链路，不改变 L2 映射链路。

本方案补齐通用运行能力，使用户自行编写的日线策略无需在脚本中重复处理分钟聚合与指标预热。

## 2. 目标与边界

### 2.1 目标

1. 完整 `1m` QMT 数据可派生为标准 `1d` Bar，并可被自定义 `on_bar` 策略选择和运行。
2. 日线策略在 T 日收盘后才接收 T 日 Bar；T 日委托仅可在 T+1 日开盘成交。
3. 为 MA、EMA、MACD 等状态型指标提供不产生交易结果的预热交易日。
4. 预检、日期可用性、数据快照、历史记录和页面提示一致表达日线来源与预热区间。

### 2.2 不在范围内

- 不编写 MA、斜率、MACD 或任何具体交易策略代码。
- 不新增预测准确率、每日预测明细、方法比较、参数寻优等研究功能。
- 不新增真实券源、融券费率、保证金或原子反手机制。
- 不重构 QMT 分钟数据导入和原始数据清洗规则；本方案依赖导入器已有的每日完整度结果。

## 3. 设计原则

1. **全区间来源优先级明确**：先确定预热与正式区间合并后的目标范围；完整原始 `1d` 优先，原始日线不足时仅在完整 `1m` 覆盖整个范围时才派生。
2. **不跨来源拼接**：单次回测的预热与正式 Bar 必须来自一个确定来源；快照必须记录来源和派生规则。
3. **完整度先于聚合**：某日 `1m` 覆盖不是 `complete` 时，不得派生日线，也不得以缓存状态替代原始完整度。
4. **预热无交易副作用**：预热 Bar 会调用用户 `on_bar` 以更新 `state`，但其订单不得被接纳、成交或计入结果。
5. **不引入未来函数**：正式 Bar 的收盘数据只能在该 Bar 完成后可见；成交严格使用正式区间内的后续可交易 Bar 开盘价。
6. **预检与执行同源**：日期可用性、保存、提交和 Worker 必须调用同一个来源解析器，禁止分别推断数据可用性。

## 4. 数据来源与日线派生

### 4.1 日线来源决策

对标准 QMT Bar 的 `timeframe=1d`，按以下顺序解析。来源解析器的输入范围是“实际预热区间 + 正式回测区间”：

1. 查询原始 `qmt_kline` 的 `1d` 覆盖；目标范围内所有所需交易日均为 `complete` 时，使用原始 `1d`。
2. 原始 `1d` 不能完整覆盖目标范围时，查询 `1m` 覆盖；目标范围内所有所需交易日均为 `complete` 时，整体使用 `1m` 派生日线。
3. 两类来源均不能完整覆盖时，预检返回不可用及对应缺失日期；不得提交回测，也不得缩短预热或跨来源拼接。

完整度唯一以 `qmt_kline_coverage` 的 `complete` 状态判断；交易日历仅用于页面日期展示。`15m`、`30m` 的既有派生逻辑保持不变。本方案为 `1d` 设计专用聚合逻辑，不复用会按上午、下午交易时段分桶的分钟聚合函数。

### 4.2 日线聚合规则

以 `Asia/Shanghai（上海时区）` 的交易日为分组键，对每个已确认完整交易日聚合：

| 字段 | 聚合规则 |
| --- | --- |
| `open` | 时间序列首根分钟 Bar 的开盘价 |
| `high` | 全交易日最高价 |
| `low` | 全交易日最低价 |
| `close` | 时间序列末根分钟 Bar 的收盘价 |
| `volume` | 全交易日成交量之和 |
| `time` | 当日最后一根分钟 Bar 的结束时间戳，供日线 `on_bar` 使用 |

午间休市不是日线分界；非交易日不生成 Bar。分钟数据最后一根 Bar 的时间戳已表示结束时间，日线不强制改写为固定 `15:00`。分钟数据质量由 `qmt_kline_coverage` 的 `complete` 状态保证，聚合层不以行数猜测完整度。

### 4.3 数据快照

任务沿用分钟回测的 `marketDataSnapshot` JSON 快照与 `backtest_run.market_data_snapshot` 存储字段，不新增数据库迁移。除既有快照字段外，至少记录：

- `provider（数据提供方）`：`qmt_kline`；
- `timeframe（运行周期）`：`1d`；
- `sourcePeriod（原始周期）`：`1d` 或 `1m`；
- `derivation（派生规则）`：原始日线为空，分钟派生日线时记录版本；
- 正式区间、Bar 数、覆盖记录最后更新时间或版本和快照哈希；
- `warmupTradingDays（预热交易日数）` 与实际取得的预热日期范围。

来源变化或派生规则版本变化必须改变快照哈希，禁止历史记录误显示为同一输入。

## 5. 预检与日期可用性

1. 抽取单一的“Bar 来源解析与覆盖查询”服务，保存策略、提交回测、日期可用性和 Worker 实际加载均调用该服务。
2. `1d` 周期预检按完整目标范围先检查原始日线；失败后再检查分钟完整度是否允许整体派生。
3. `1m` 完整但原始 `1d` 缺失时，周期仍应显示可选，并标记“由完整 1m 数据派生日线”。
4. `1m` 某日缺失、部分覆盖或读取异常时，对应日线日期置为不可用；原因明确为分钟数据不完整。
5. 预热区间也必须检查完整性，但不改变用户正式回测区间的日期可用性显示；数据不足时返回可用预热天数和数据类型，不重复罗列日期。

## 6. 预热交易日

### 6.1 配置

回测请求与策略方案增加 `warmupTradingDays（预热交易日数）`：

- 类型：`0–250` 的整数；默认 `0`。
- 语义：正式开始日前，向前取得指定数量的完整交易日 Bar。
- 适用：标准 Bar 自定义策略；L2 与其他运行模式不展示、不接受该字段。日线方向策略推荐配置 MA／EMA 所需窗口。

### 6.2 运行语义

1. 先加载预热 Bar，再加载正式区间 Bar，时间顺序连续。
2. 对每根预热 Bar 调用用户 `on_bar(bar, state)`，使 `state（策略状态）` 完成指标初始化。
3. 执行器将预热视为显式无交易阶段：丢弃预热回调返回的全部订单；不得接纳订单，也不得产生订单事件、成交、费用、资金、持仓、净值、每日持仓或结果明细。
4. 首根正式 Bar 保留预热后的 `state`，正式区间才开始接受委托和生成结果。
5. 请求的预热天数无法从来源完整度记录中取得时，预检以 `data.warmup_insufficient（预热数据不足）` 阻止提交，并明确返回可用预热天数。

## 7. 方向性持仓执行语义

本方案不改变用户脚本接口，仍使用：

```python
def on_bar(bar, state):
  return []
```

运行约束如下：

1. 日线 `on_bar` 在 T 日收盘完成后调用；用户脚本此时可读取 T 日 OHLCV 和既有 `state`。
2. 标准 `bar_next_open` 模式下，T 日产生的委托在 T+1 首根可交易 Bar 开盘执行，并计入滑点和费用。
3. `directional_holding` 默认不设置初始底仓；启用时该持仓作为账户初始状态参与收益，正式区间仓位可跨日保留，且不会日终恢复底仓。
4. `sell_open（卖出开空）` 与 `buy_close（买入平空）` 仅在启用 `allowShort（允许做空）` 时模拟执行；不表示真实可融券。
5. 正式区间最后一根 Bar 的下一开盘委托不得跨出用户选择的结束日期成交；将其记录为“区间结束未执行委托”，不计入成交、费用或收益。
6. 同一根日线内多委托的原子顺序不作为本方案能力；反向信号应先平当前仓位，后续信号才可开反向仓。原子反手由后续专项实现。

## 8. 前端与接口

### 8.1 前端

- `1d` 周期显示实际来源：`QMT 原始日线` 或 `由完整 1m 派生`；历史页面以实际运行周期为主，在追溯位置展示来源与预热信息。
- 自定义策略回测增加 `预热交易日数` 输入及不足时的阻止提示。
- 方向性持仓区域说明“日线收盘发信号、下一交易日开盘成交”。
- 历史记录和回测对比展示周期来源、预热参数与实际预热范围。

### 8.2 接口与兼容性

- `BacktestRunRequest（回测运行请求）`、策略方案参数、版本快照和历史回测参数增加 `warmupTradingDays`。
- 未传该字段的历史方案按 `0` 处理，保持兼容。
- 结果 JSON 增加来源和预热元数据；现有汇总、成交、持仓字段不改名。
- 不新增数据库迁移：请求与结果快照使用既有 JSON 字段保存新增元数据。

## 9. 实施步骤

1. 扩展标准 QMT Bar 来源解析，按预热与正式区间统一选择原始 `1d` 或 `1m` 派生 `1d`；不改动 L2 映射链路。
2. 实现专用日线聚合器、来源快照和统一来源解析服务，接入日期可用性、保存/提交校验、Worker 与数据预检。
3. 实现预热交易日解析、请求校验、执行器无交易阶段、末尾未执行委托记录和正式结果区间隔离。
4. 更新回测接口、策略方案快照、前端周期提示与预热配置。
5. 补充单元、集成和前端回归测试，使用确定性分钟样本验证时序、来源降级和预热隔离。

## 10. 验收标准

1. 仅有完整 `1m` 数据时，用户可选择 `1d` 并运行自定义日线 `on_bar` 策略。
2. 派生日线 OHLCV 与分钟数据按交易日聚合结果逐字段一致，午间休市不拆分日线。
3. `1m` 不完整的日期不能派生日线，预检提示具体数据缺失原因。
4. 预热 Bar 可初始化策略状态，但预热期不产生任何订单、成交、费用、净值或持仓结果。
5. T 日收盘信号只能在 T+1 开盘成交；自动化测试证明不存在未来函数。
6. 日线来源、派生规则、预热参数和实际范围均可在任务快照及历史页面追溯。
7. 既有原始 `1d`、`1m`、`15m`、`30m` 标准 Bar 回测行为保持兼容。
8. 页面、保存/提交校验与 Worker 对同一请求返回相同的数据来源和可用性结论。
9. 正式区间最后一根 Bar 的待执行委托被记录为未执行，不扩大成交区间。

## 11. 风险与前置条件

主要风险与前置条件：

- 目标标的必须先导入完整 `1m` QMT 数据；数据源缺失不能由聚合补齐。
- 原始 `1d` 与分钟派生日线可能存在供应商口径差异，必须在结果中明确来源。
- 本方案不解决同 Bar 原子反手；用户策略应避免依赖未定义的多委托顺序。
- 本期只覆盖历史回测；实时与仿真盘的日线完成确认另立需求评审。
