# 标准 Bar 与 L2 策略回调兼容改造方案

## 1. 背景与问题

当前自定义策略以 `on_bar(bar, state)` 为最小入口，L2 策略可以额外定义 `on_quote(quote, state)` 和 `on_order_event(event, state)`。

任务 #90 选择“标准 Bar 回放（快速）”后没有产生任何委托：策略的首笔开仓只写在 `on_quote()`，而标准 Bar 引擎只调用 `on_bar()`；同时，标准 Bar 成交后未回调 `on_order_event()`。因此，依赖成交回报维护阶段状态的策略即使把首笔信号迁移到 `on_bar()`，仍不能可靠地跨模式运行。

本次目标不是把 L2 行情回调引入标准 Bar 回放，也不将两种成交价格强行统一；目标是让一个以 `on_bar()` 为主、可选 `on_quote()` 增强的策略在两种模式下均能正确运行。

## 2. 目标、边界与不做事项

### 2.1 目标

1. 标准 Bar 模式始终执行 `on_bar()`，并按既有规则在下一根可交易 Bar 开盘价加滑点虚拟成交。
2. 标准 Bar 虚拟成交后向策略发送与 L2 语义对齐的 `on_order_event()` 回报。
3. 允许同一脚本同时定义 `on_bar()`、`on_quote()` 和 `on_order_event()`；选择标准 Bar 时仅跳过 `on_quote()`，不拒绝任务。
4. 将 `staged_entry_long_v6_l2.py` 调整为“Bar 决策、L2 实时风控增强”的结构：首笔和阶段建仓由 `on_bar()` 发出，盘口止损/止盈保留在 `on_quote()`。
5. 明确手册中的跨模式契约，使新用户不会得到“任务成功但零成交”的误导。

### 2.2 不做事项

1. 不在标准 Bar 模式读取 3 秒十档快照，不增加 ClickHouse 或 Redis 读取压力。
2. 不让标准 Bar 模式模拟部分成交、盘口深度、撤单排队或 3 秒内价格路径。
3. 不修改历史任务的结果、策略快照或收益；仅影响新发起任务。
4. 不改变 L2 的无前视规则：L2 中 `on_quote()` 产生的新订单仍只能从下一条快照成交。
5. 不把 Bar 内止损伪装为 L2 盘口止损；标准模式下 `on_quote()` 风控自然不执行。

## 3. 目标回调契约

| 回调 | 标准 Bar 回放 | L2 盘口回放 | 主要职责 |
| --- | --- | --- | --- |
| `on_bar(bar, state)` | 每根已完成 Bar 调用 | 每根已完成 Bar 调用 | 开仓、加仓、常规平仓等 Bar 级信号。 |
| `on_quote(quote, state)` | 不调用 | 每条可见 3 秒快照调用（连续模式） | 盘口止损、止盈、突破、盘口条件等实时增强。 |
| `on_order_event(event, state)` | 已接受委托、虚拟完全成交、系统强平后调用 | 已接受、部分成交、完全成交、拒绝/撤单等状态变化后调用 | 只依据真实成交回报更新均价、阶段、待处理订单。 |

标准 Bar 的单笔虚拟成交是原子成交：只会产生 `accepted（已接受）` 后的 `filled（完全成交）`，不会产生 `partial_fill（部分成交）`。L2 维持现有的部分成交、撤单与盘口深度语义。

所有成交回报均在账本更新之后发送，故回调读取到的账户/持仓与该事件一致。下一次 `on_bar()` 调用前，前一根 Bar 的成交回报必须已完成。

## 4. 实施方案

### 4.1 标准 Bar 引擎补齐可选委托回报

修改 `backend/backtesting/engine.py`：

1. 保持 `BarStrategy` 的最小接口仍只有 `on_bar()`；通过 `getattr(strategy, "on_order_event", None)` 识别可选回调，避免影响既有内置策略和第三方策略。
2. 为标准 Bar 内部待成交订单维护稳定的内部订单标识和原始 `signalTime（信号时间）`，不改变对外 `OrderIntent` 数据结构。
3. `on_bar()` 返回订单并通过现有资格检查后，发送 `accepted` 回报；被 T+0 额度、日终不隔夜等既有资格检查过滤的订单不得伪造为已接受。
4. 下一根 Bar 虚拟成交成功后，先写入账本、更新做 T 额度，再发送 `filled` 回报；回报带有 `symbol（标的）`、`action（交易动作）`、`quantity（成交数量）`、`price（成交价）`、`reason（原因）`、`clientOrderKey（客户订单键）`、`signalTime（信号时间）` 与 `executionTime（成交时间）`。
5. 虚拟成交模型返回空成交时，发送可诊断的未成交/拒绝事件，不允许策略状态永久保留待处理订单。
6. 日内尾盘系统强平在账本更新后同样发送系统来源的成交回报；策略可按 `source（来源）= system` 或缺少自身 `clientOrderKey` 忽略它。
7. `bar_close` 等非下一开盘成交路径沿用同一事件顺序：`accepted` 后同 Bar `filled`。

### 4.2 策略运行时与隔离 worker 保持统一

1. `ScriptedBarStrategy.on_order_event()` 已具备隔离执行和错误包装能力，复用该实现，不新增脚本权限或可导入模块。
2. 标准 Bar 的 strategy-worker 仍只传入 Bar 数据；不增加 L2 连接、网络调用或容器间新接口。
3. 发生回调异常时，沿用现有 `StrategyExecutionError`，错误定位为 `on_order_event` 并携带事件时间/标的；前端继续按策略错误显示。

### 4.3 V6 分批建仓策略迁移

修改 `backend/strategies/staged_entry_long_v6_l2.py`：

1. 每个交易日的首笔与阶段建仓由 `on_bar()` 的已完成 1 分钟 Bar 判断并发出，使用现有 `clientOrderKey` 防重。
2. 首笔理由改为“首根 Bar 建仓”，不再声称在开盘快照成交；这是标准 Bar 与 L2 都可复现的信号时点。
3. `on_quote()` 仅保留需要 3 秒级响应的止盈、止损、反手触发和盘口条件，不负责初始开仓。
4. `on_order_event()` 继续仅以 `accepted`、`partial_fill`、`filled` 更新挂单、均价和阶段状态；标准 Bar 的 `accepted`/`filled` 事件可直接驱动该逻辑。
5. 不改变策略的仓位上限、反手顺序、尾盘处理和风控阈值；仅迁移触发位置与更新来源。

### 4.4 页面与手册提示

1. 运行参数区域在脚本定义 `on_quote()` 且选择标准 Bar 时显示非阻塞提示：实时盘口回调不会执行，结果不包含盘口止损/止盈；`on_bar()` 信号仍正常回测。
2. 不改变模式可选性，不阻断含 `on_quote()` 的脚本使用标准 Bar。
3. 更新 `docs/玄龄回测系统使用手册.md`：明确三类回调在两种模式下的调用/不调用规则、标准 Bar 的 `accepted`/`filled` 回报语义，以及“主信号写在 `on_bar()`、实时增强写在 `on_quote()`”的编写准则。

## 5. 兼容性与数据影响

| 维度 | 处理方式 |
| --- | --- |
| 历史任务 | 仅按已保存结果展示，不重算、不追加事件。 |
| 现有仅 `on_bar()` 策略 | 可选回调不存在，行为与当前保持一致。 |
| 现有 `on_bar()` + `on_quote()` 策略 | 标准模式继续只执行 `on_bar()`，新增提示；L2 行为不变。 |
| 现有依赖 `on_order_event()` 的标准策略 | 新任务会收到完整虚拟成交回报，属于修复性增强。 |
| 回测结果结构 | 不新增数据库字段；标准结果中的成交明细、费用和收益字段保持现有格式。 |
| 缓存 | 不变更 Bar/L2 数据读取和 Redis 键，不需要缓存版本迁移。 |

## 6. 验证计划

### 6.1 单元测试

1. 仅 `on_bar()` 的既有策略：成交时间、价格、数量、费用、收益与改造前基线一致。
2. 定义 `on_order_event()` 的标准策略：验证事件顺序为 `accepted → filled`，且 `filled` 时账本已更新。
3. 下一开盘成交：验证信号时间为前一根 Bar 完成时刻、成交时间为下一根 Bar 时刻。
4. 当日最后一根 Bar 新开仓：验证不会接受跨日订单，也不会留下未清理的策略待处理状态。
5. 日内尾盘强平：验证系统事件在账本更新后发送，且不影响底仓保留。
6. T+0 额度过滤、资金不足、方向限制：验证不发送错误的 `accepted`，既有跳过明细保持正确。
7. L2 回归：验证 `on_quote()` 的严格下一快照成交、部分成交和撤单语义无变化。

### 6.2 集成验证

1. 使用迁移后的 V6 策略分别发起相同参数的标准 Bar 与 L2 任务：两者均必须有首笔委托和成交。
2. 验证标准模式成交为下一根开盘价加滑点；L2 为严格后续十档盘口价。
3. 验证 L2 才会产生盘口止损/止盈事件；标准模式页面提示该差异。
4. 验证历史 #90 仍保持原结果，新任务不改写历史。
5. 运行后端相关 pytest、前端 TypeScript 检查；不把未实际发起的服务器回测写为已验证。

## 7. 发布与回滚

受影响服务为 `backend`、`strategy-worker`、`bar-runner`、`l2-runner`（共享策略契约）、前端和使用手册。必须通过 `scripts/deploy-server.sh` 同批发布，不可仅重启其中一个容器。

发布前检查排队和运行中的 L2 任务；若需要重建 l2-runner，等待完成或由用户明确取消，避免静默中断。发布后执行健康检查、一个标准 Bar 代表任务、一个 L2 代表任务及一条历史任务读取检查。

本改造不涉及数据库迁移、环境变量和缓存结构。若发现标准 Bar 事件回报改变既有策略结果，回滚应用代码即可；历史任务不受影响。

## 8. 自审与结论

### 8.1 正确性

方案将“信号产生”与“成交确认”分离：`on_bar()` 不预先写入成交状态，所有状态推进由账本更新后的回报驱动，消除 #90 的零委托根因，也避免 L2 部分成交时提前推进阶段。

### 8.2 无前视与时间语义

标准 Bar 仍只在下一根 Bar 虚拟成交；L2 仍只在严格后续快照成交。新增事件不改变订单发生时间或价格来源，只把已发生的账本状态通知给策略，因此不存在前视数据泄漏。

### 8.3 兼容性

不修改最小 `on_bar()` 接口，`on_order_event()` 为可选扩展；旧策略不会因缺少回调而变化。历史结果按快照展示。此方案优于“存在 `on_quote()` 就禁止标准模式”，因为后者会错误限制具有可选实时风控的 Bar 策略。

### 8.4 风险控制

最大风险是错误地对被过滤/未成交订单发送 `accepted`，使策略永久等待。方案通过在既有资格检查之后再发接受事件，并在无法虚拟成交时发送终态事件规避。另一个风险是系统尾盘强平被脚本误当成自身交易，因此系统事件必须携带来源标识。

### 8.5 性能、并发与资源

标准 Bar 每笔虚拟成交新增一次本地 Python 回调，不增加远程 ClickHouse、Redis、PostgreSQL 查询或 Docker 通信。常规分钟级策略成交数远少于 Bar 数，对任务吞吐影响应很小；以现有并发设置压测并记录耗时差异，若无可测量负担则不额外调整 worker 数。

### 8.6 方案结论

推荐按本方案实施。它同时修复标准 Bar 的成交回报缺口、保留模式选择自由、明确 L2 专属实时逻辑边界，并通过可选回调和全量回归测试避免影响现有正常回测。
