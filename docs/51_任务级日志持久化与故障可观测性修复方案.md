# 任务级日志持久化与故障可观测性修复方案

日期：2026-09-23
状态：本地实施与隔离验证完成；服务器发布、缩短周期的 Compactor 实效删除及远程普通用户样本回归待验证
范围：标准 Bar 与 L2 回测的执行尝试、结构化日志、容器异常关联、管理员诊断和服务器日志基础设施

## 一、背景与问题结论

当前系统并不是“每个任务启动一个 Docker 容器，任务结束后删除容器”。`bar-runner` 与 `l2-runner` 是常驻容器和常驻 Runner 进程，持续从 PostgreSQL 队列领取任务；每个回测任务会创建独立的策略子进程，任务结束、取消或异常后销毁该子进程。

现有诊断链路已经具备以下能力：

1. `backtest_run` 保存任务 UUID、状态、安全错误摘要和结果。
2. `system_error_log` 按任务 UUID 保存错误分类、阶段、异常类型、安全上下文和内部原始异常。
3. Runner 使用 `attemptToken（执行尝试令牌）` 和租约避免迟到结果覆盖新执行。
4. `backtest_runner_health` 保存 Runner 心跳、当前任务和最后错误码。
5. 管理员页面可以按任务 UUID 查询 `system_error_log`，但只展示安全诊断和文本形式的 `rawLogRef（原始日志索引）`。

因此，正常抛出并被 Runner 捕获的 Python 异常通常不会完全丢失。当前真正的结构性问题是：

1. 策略子进程被强杀、段错误或异常退出时，可能来不及通过进程间通信返回 traceback。
2. Runner 进程、Runner 容器或宿主机退出时，可能来不及执行任务失败落库。
3. 任务因租约过期重新领取时，任务表中的 `attempt_token` 和 `worker_id` 会被新尝试覆盖，旧尝试现场没有独立持久化记录。
4. `rawLogRef` 只是检索提示，不对应一个保证可用的持久化日志存储。
5. Docker Compose 未配置集中日志、明确保留期限和跨容器检索；容器重建、日志轮转或宿主机清理后，`docker logs` 不能作为可靠证据。
6. 管理员只能看到最终错误摘要，无法判断任务经历了几次尝试、在哪个阶段中断、是否由 OOM、信号、超时、租约丢失或容器重启引起。

本方案的核心结论是：保留 PostgreSQL 中的业务状态和安全错误摘要，引入按执行尝试持久化的诊断事实，并使用结构化日志与 Loki 集中存储保存有期限的运维证据。两条链路通过任务 UUID 和执行尝试令牌关联，但互不成为对方的同步依赖。

## 二、既有方案继承关系

本方案不替代既有错误分类和运行时方案，而是在其上补齐日志持久化与异常退出现场。

| 既有方案 | 本方案继承的决定 | 本方案补充内容 |
| --- | --- | --- |
| `14_回测错误分类与前端可诊断提示方案` | 普通用户只看到安全提示和任务编号 | 不向普通用户增加原始日志或内部上下文 |
| `19_系统错误分类与管理员诊断日志改造方案` | `system_error_log`、错误分类、`rawLogRef` 和管理员查询 | 将文本索引升级为可验证的执行尝试和集中日志关联 |
| `22_回测会话隔离与并发执行改造方案` | 每个任务使用隔离策略子进程 | 记录子进程退出码、信号、超时和强杀结果 |
| `27_数据错误分类与原始异常留存完善方案` | 内部原始异常保存在数据库，接口过滤 `__internal_*` | 不把无限制日志正文继续堆入 PostgreSQL；集中日志承担过程证据 |
| `37_统一回测并发调度与任务状态改造方案` | `attemptToken`、租约、统一执行槽位和迟到结果保护 | 为每次领取建立不可覆盖的执行尝试记录 |
| `40_策略运行时兼容与脱敏错误留存修复方案` | 任务删除后不保留可反查用户的长期运行时诊断 | 集中日志不写用户身份、源码和参数，并执行固定短期保留 |
| `41_L2日终估值与通用错误诊断修复方案` | 实际 `workerId` 和阶段进入诊断上下文 | 将 Worker、容器和尝试关系结构化 |
| `49_回测执行性能全链路分阶段指标方案` | Attempt 是执行和性能归因的基本单位 | 复用 Attempt 标识和阶段目录；性能明细仍输出为 49 号方案规定的本地测试产物 |

若本方案与既有文档中的“原始堆栈仅保留在容器日志中”表述冲突，以本方案实施后的集中日志语义为准，并在同批改动中更新使用手册和管理员页面说明。

## 三、目标与不做事项

### 3.1 目标

1. 管理员只凭任务 UUID 即可定位全部执行尝试、Worker、容器、阶段、终止原因和相关日志。
2. 容器重建后，保留期内仍可查询已采集日志。
3. 正常异常、子进程异常退出、Runner 进程退出、租约过期、容器 OOM、容器重启和宿主机中断均有明确或可解释的诊断结果。
4. 同一个任务被多次领取时，每次 Attempt 独立保存，不由后一次覆盖前一次。
5. 日志系统不可用时，回测提交、执行、结果落库和取消仍按原语义工作。
6. 日志字段、错误摘要和页面输出有明确脱敏边界，不记录账户、凭据、策略源码或请求载荷。
7. 日志采集有容量上限、轮转、保留期限、健康检查和降级状态，不能无限占用服务器磁盘。
8. Bar、L2 和后续异步 Runner 复用同一个任务诊断模块和事件契约。

### 3.2 不做事项

1. 不修改撮合、费用、仓位、收益、行情读取和策略回调语义。
2. 不把 Loki 作为任务状态、回测结果或错误分类的事实来源。
3. 不把所有 INFO/DEBUG 日志复制到 PostgreSQL。
4. 不记录每根 Bar、每条 Quote 或每次订单簿变化；高频循环只保留聚合性能指标和异常。
5. 不将任务 UUID、执行尝试令牌、Worker ID、容器 ID 或用户 ID 配置为 Loki 标签。
6. 不允许浏览器直接访问 Loki，也不允许前端提交任意 LogQL。
7. 不在本方案中自动更新 Loki、Alloy、Grafana或其他镜像版本；实施时固定经验证的明确版本和镜像摘要，升级另行执行。
8. 不承诺单机本地磁盘能够抵抗宿主机磁盘损坏；需要该等级时再迁移到独立对象存储或独立日志主机。

## 四、术语与强制不变量

### 4.1 术语

| 术语 | 定义 |
| --- | --- |
| Run | 用户提交的一次回测，对应 `backtest_run.id`，即任务 UUID |
| Attempt | Runner 对 Run 的一次实际领取和执行，以 `attempt_no + attempt_token` 唯一识别 |
| Runner 进程 | 领取任务、读取行情、管理租约并启动策略子进程的进程 |
| 策略子进程 | 单个任务内运行用户策略和回测引擎的受限 Python 子进程 |
| 业务摘要 | PostgreSQL 中的状态、错误码、安全原因和结果，是产品行为的事实来源 |
| 运维事件 | Runner、容器和日志采集器产生的结构化诊断记录 |
| 日志关联键 | `runId + attemptToken`；在保留期内用于检索同一次执行尝试的日志 |

### 4.2 强制不变量

1. PostgreSQL 始终是任务状态和执行尝试状态的唯一事实来源。
2. Loki、Alloy 或容器事件观察器不可用时，不得阻塞或改变回测终态。
3. 只有持有当前 `attempt_token` 的 Runner 才能完成对应任务；诊断改造不得削弱现有迟到结果保护。
4. 每次领取都必须产生新的 Attempt；旧 Attempt 的关联字段不可变，只允许从 `running` 原子转换到一个终态，不能被新领取覆盖。
5. 普通用户接口不得返回 Worker、容器、内部路径、SQL、Python 堆栈或日志查询表达式。
6. 产品管理员页面只展示安全时间线；完整运维日志只在受控服务器或受控运维入口查询。
7. 日志写入失败最多产生本地告警或采集缺口，不得把本来成功的回测改成失败。
8. 所有新增数据库结构都通过新建的幂等迁移执行，不修改已执行迁移。

## 五、总体架构

```text
提交任务
  │
  ▼
PostgreSQL: backtest_run / *_backtest_job
  │ 领取任务，创建 Attempt
  ▼
Bar/L2 Runner ───────────────► PostgreSQL: backtest_run_attempt
  │                                  │
  │ 启动、阶段、终态、安全错误摘要   │ 管理员时间线与降级查询
  │                                  ▼
  ├─► 策略子进程                 Backend 管理员诊断接口
  │      │ 异常诊断/退出码             │
  │      └──────────────► Runner       ▼
  │                                管理员诊断页面
  │ 结构化 JSON stdout                ▲
  ▼                                   │ 有界、安全查询
Docker 本地轮转日志                    │
  │                                   │
  ▼                                   │
Grafana Alloy ───────────────► Grafana Loki
  ▲                               ▲
  │ Docker 日志与读取位置          │ 有期限运维证据
  │                               │
容器事件观察器 ─────────────────────┘
  OOM / die / restart / destroy
```

### 5.1 三层职责

| 层级 | 保存内容 | 可用性语义 |
| --- | --- | --- |
| PostgreSQL 业务层 | Run 状态、Attempt 状态、错误分类、安全摘要、Worker/容器关联、终止原因 | 必须成功；决定产品状态 |
| Docker 本地缓冲层 | 各服务 stdout/stderr 的有限轮转副本 | Loki 暂时不可用时提供短期缓冲，不作为长期存储 |
| Loki 运维层 | 结构化阶段事件、受控异常、Runner/容器生命周期和采集状态 | 尽力采集；故障时不影响业务 |

### 5.2 部署级别

当前单服务器环境先采用 Loki 单体模式、TSDB 索引和持久 Docker 卷。该配置能够抵抗 Loki 或 Runner 容器重建，但不能抵抗宿主机磁盘损坏。

当系统提出“服务器磁盘损坏后仍须保留日志”的恢复目标时，再把 Loki chunk 与索引迁移到独立对象存储。迁移前不得把单机 Docker 卷描述为异地备份或灾难恢复。

## 六、任务诊断深模块

### 6.1 模块职责

新增单一 `task_diagnostics（任务诊断）` 模块，隐藏以下实现复杂度：

1. 构造统一事件信封。
2. 校验阶段名、事件名和终止原因枚举。
3. 注入 Run、Attempt、Worker、容器、构建和运行时字段。
4. 对消息、异常和附加字段执行白名单、脱敏、长度限制和换行归一化。
5. 输出结构化 JSON 日志。
6. 将异常转换为现有 `SystemErrorLogRecord` 或兼容的新诊断记录。
7. 生成安全时间线事件和日志关联键。

Runner 只学习一个小接口，不得继续分别拼接 Bar、L2 和子进程日志字段。建议接口形状如下，具体命名可在实现时按项目风格调整：

```python
attempt = task_diagnostics.start_attempt(context)
attempt.stage("l2.market_replay")
attempt.record_exception(error, termination_reason="exception")
attempt.finish("failed")
```

`AttemptDiagnostics` 内部可以使用多个 Adapter：生产环境写标准日志和 PostgreSQL，测试环境使用内存 Adapter。Adapter 是内部 seam，不向 Runner 暴露 Loki、LogQL 或存储细节。

### 6.2 上下文

每个 Attempt 在领取成功后固定以下上下文：

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `runId` | `backtest_run.id` | 任务 UUID |
| `attemptNo` | 任务表 | 从 1 开始递增 |
| `attemptToken` | 任务表 | 本次领取的随机 UUID |
| `jobKind` | 调度器 | `bar` 或 `l2` |
| `workerId` | Runner | 当前为 `<container-hostname>:<pid>` |
| `containerId` | 容器 hostname | 与 Docker 事件关联，保存稳定前缀 |
| `processId` | Runner PID | 同容器多 Runner 进程时区分实例 |
| `applicationBuildId` | 构建配置 | 定位实际镜像代码 |
| `runtimeVersion` | 运行时契约 | 定位策略运行环境 |
| `capabilityDigest` | 运行时契约 | 检查调度与 Runner 能力一致性 |

上下文一旦创建不得从可变全局状态重新推断。租约线程、策略会话和结果处理必须显式使用同一个 Attempt 上下文。

## 七、执行尝试持久化

### 7.1 新表

新增幂等迁移 `db/migrations/041_backtest_run_attempt_diagnostics.sql`，创建 `backtest_run_attempt`：

| 字段 | 约束与含义 |
| --- | --- |
| `run_id` | 外键指向 `backtest_run`，任务删除时级联删除 |
| `owner_user_id` | 用于 RLS，与 Run 所有者一致 |
| `job_kind` | `bar` 或 `l2` |
| `attempt_no` | 该 Run 内递增编号，与 `run_id` 组成主键 |
| `attempt_token` | 全局唯一 UUID，日志主要关联键 |
| `worker_id` | 实际领取任务的 Runner 进程 |
| `container_id` | 容器 ID 前缀或明确的本机进程标识 |
| `status` | `running/succeeded/failed/cancelled/interrupted` |
| `stage` | 最后确认的稳定阶段名 |
| `started_at` | 领取成功时间 |
| `heartbeat_at` | 最近一次成功租约续期时间 |
| `finished_at` | Attempt 终止时间 |
| `exit_code` | 子进程或 Runner 已知退出码；未知为空 |
| `termination_reason` | 受控终止原因枚举 |
| `error_code` | 已分类错误码；没有为空 |
| `log_correlation_id` | 默认等于 `attempt_token` 的规范字符串，便于未来替换日志实现 |

建议索引：

1. `PRIMARY KEY (run_id, attempt_no)`；
2. `UNIQUE (attempt_token)`；
3. `(run_id, started_at DESC)`；
4. 部分索引 `(status, heartbeat_at)`，仅覆盖 `running`；
5. 管理员排查所需的 `(container_id, started_at DESC)`。

该表启用并强制 RLS。普通用户不直接读取 Attempt 行；普通历史页面继续读取 `backtest_run`。管理员诊断接口可读取 Attempt 安全字段。

该表只保存领取、心跳、阶段和终止等生命周期事实，不保存每个性能阶段的耗时明细、Bar/Quote 数量或容量测试样本。性能数据继续按 49 号方案输出到隔离测试产物，避免把在线诊断表扩展成长期 trace 表。

### 7.2 `system_error_log` 扩展

在同一迁移中为 `system_error_log` 增加以下可空字段：

- `attempt_no`；
- `attempt_token`；
- `worker_id`；
- `container_id`；
- `termination_reason`；
- `exit_code`；
- `log_correlation_id`。

既有 `context_json.workerId` 和 `raw_log_ref` 继续读取，保持历史兼容；新记录使用独立列作为查询契约，同时保留 `rawLogRef` 兼容字段。历史记录不回填不存在的 Attempt 信息。

### 7.3 事务规则

1. 领取任务、递增 `attempt_no`、生成 `attempt_token`、获取执行槽位和插入 Attempt 必须处于同一事务。
2. 任务心跳续租成功时，同事务更新 Attempt 的 `heartbeat_at` 和最后阶段；限频规则与 Runner 健康心跳一致，不能每根 Bar 写数据库。
3. 任务正常结束时，任务终态、结果、执行槽位释放、Attempt 终态和 `system_error_log` 必须处于同一事务。
4. 过期任务重新领取前，先将旧 Attempt 标记为 `interrupted/lease_expired`，再创建新 Attempt。
5. 旧 Attempt 的迟到日志可以进入 Loki，但不得再修改 Run 或新 Attempt。
6. 数据库暂时不可用时，Runner 继续按现有退避策略处理；不能声称未落库的 Attempt 已持久化。

## 八、结构化日志契约

### 8.1 事件信封

所有任务级运维事件输出为单行 JSON，固定 `schemaVersion`。首期字段如下：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `timestamp` | 是 | UTC RFC 3339 时间 |
| `schemaVersion` | 是 | 首期为 `task-log-v1` |
| `level` | 是 | `info/warning/error/critical` |
| `service` | 是 | `backend/bar-runner/l2-runner/runner-supervisor` 等 |
| `event` | 是 | 稳定事件名，例如 `attempt.started` |
| `message` | 是 | 经过脱敏和长度限制的中文说明 |
| `runId` | 任务事件必填 | 任务 UUID |
| `attemptNo` | Attempt 事件必填 | 执行尝试序号 |
| `attemptToken` | Attempt 事件必填 | 执行尝试令牌 |
| `jobKind` | Attempt 事件必填 | `bar/l2` |
| `workerId` | Runner 事件必填 | Runner 标识 |
| `containerId` | 可取得时必填 | 容器关联字段 |
| `stage` | 阶段事件必填 | 稳定阶段枚举 |
| `status` | 终态事件必填 | Attempt 状态 |
| `errorCode` | 失败事件选填 | 稳定错误码 |
| `exceptionType` | 异常事件选填 | 根异常类型 |
| `exitCode` | 异常退出选填 | 进程退出码 |
| `terminationReason` | 终止事件必填 | 受控终止原因 |
| `durationMs` | 阶段/终态选填 | 单调时钟计算的持续时间 |
| `applicationBuildId` | 是 | 构建标识 |
| `runtimeVersion` | 任务事件必填 | 策略运行时版本 |

### 8.2 事件范围

首期只记录低频状态变化：

- `attempt.claimed`；
- `attempt.started`；
- `attempt.stage_changed`；
- `strategy_process.started`；
- `strategy_process.exited`；
- `attempt.succeeded`；
- `attempt.failed`；
- `attempt.cancelled`；
- `attempt.interrupted`；
- `runner_process.exited`；
- `container.oom`；
- `container.died`；
- `container.restarted`；
- `log_pipeline.degraded/recovered`。

禁止在 Bar、Quote、Trade、订单簿或策略回调循环内逐条打印事件。阶段事件必须与 49 号性能方案使用同一阶段目录，避免诊断阶段和性能阶段名称分叉。

### 8.3 脱敏与大小限制

日志字段采用允许列表，不接受任意 `payload` 直接展开。以下内容禁止进入集中日志：

1. 策略源码、源码行正文和完整策略参数；
2. 账户号、用户名、邮箱、显示名和用户 ID；
3. 数据库、ClickHouse、Redis、对象存储和外部接口凭据；
4. Cookie、Authorization、API Key、密码、令牌和完整连接 URL；
5. 完整 SQL、请求体、行情原始行和回测结果 JSON；
6. 宿主机非必要绝对路径。

异常日志在进入 stdout 前执行结构化脱敏。普通消息默认不超过 4 KiB；异常堆栈默认不超过 64 KiB，超限时记录 `truncated=true`、原始字符数和内容摘要。策略子进程优先保留异常类型、脱敏原因及 `文件名:行号:函数名` 帧摘要，不记录用户源码行正文。

数据库中现有 `__internal_raw_*` 继续受数据库权限保护；本方案不要求将其直接复制到前端或长期统计表。

## 九、Loki 与 Alloy 设计

### 9.1 采集链路

生产采用 Grafana Alloy 的 `discovery.docker` 与 `loki.source.docker` 发现并读取 Docker 日志，转发到内部 Loki。Alloy 的数据目录使用持久卷保存读取位置，使 Alloy 重启后可以从已确认位置继续采集。

Loki 使用单体模式、TSDB 索引、持久卷和 ingester WAL。Loki 与 Alloy 不暴露公网端口，只加入受控内部网络。浏览器和普通用户不能直接连接 Loki。

Alloy 读取 Docker API 时必须经过限制为只读发现、日志和事件接口的 Docker socket proxy，不能把直接挂载 `/var/run/docker.sock:ro` 描述为权限隔离；文件系统只读挂载不会限制通过 Docker API 发起写操作。socket proxy 只加入运维网络，不加入前端网络，并设置最小 Linux capabilities、只读根文件系统和资源限制。

### 9.2 标签与高基数字段

Loki 标签只使用有界、低基数字段：

- `environment`；
- `compose_project`；
- `service`；
- `job_kind`。

`runId`、`attemptToken`、`workerId`、`containerId`、错误消息和异常类型均不得成为标签。首期保留在 JSON 日志正文，通过 `| json` 查询；若查询性能确有证据不足，再评估 Loki structured metadata，仍不创建高基数 stream。

典型查询由后端或维护脚本生成，不能由浏览器自由拼接：

```logql
{compose_project="quant-backtest-platform"}
  | json
  | runId="<validated-run-uuid>"
  | attemptToken="<validated-attempt-uuid>"
```

### 9.3 本地轮转与故障缓冲

所有长期运行服务显式配置 Docker `local` 日志驱动或等价的有限轮转配置，设置单文件大小、文件数量上限和非阻塞投递模式。日志缓冲区溢出时允许丢弃运维日志并记录采集缺口，不得反向阻塞 Runner。具体容量值在实施前按服务器磁盘预算计算，不能依赖 Docker daemon 未知默认值。

Alloy 到 Loki 短暂中断时，Docker 本地轮转日志和 Alloy 持久读取位置承担恢复窗口。首期不依赖 Alloy 实验性日志 WAL；恢复窗口必须通过“停止 Loki、继续产生测试日志、启动 Loki、确认日志补采”验证。超过本地轮转窗口的日志允许丢失，并产生明确采集缺口告警。

### 9.4 保留策略

首期运维日志默认保留 30 天，可通过服务器私有环境变量缩短，但不得配置为无限期。Loki 必须显式启用 Compactor retention、持久化 Compactor 工作目录并配置删除请求存储；不能只填写 `retention_period` 就声称过期删除有效。

任务删除仍会立即级联删除 PostgreSQL 中的 Run、Attempt 和 `system_error_log`。集中日志属于短期安全运维记录，不写用户身份、源码或参数，任务删除不会同步发起高成本逐行 Loki 删除；相关日志在固定保留期后自动删除。这与当前 Docker 日志独立轮转的语义一致，但必须在管理员文档和隐私边界中明确。

如未来出现必须立即删除某任务运维日志的合规要求，应独立设计 Loki deletion outbox 和受控删除流程，不能在用户删除事务中同步调用 Loki。

## 十、异常退出与中断归因

### 10.1 终止原因枚举

| `terminationReason` | 含义 |
| --- | --- |
| `completed` | 正常成功 |
| `exception` | Runner 捕获到异常 |
| `strategy_exit_nonzero` | 策略子进程非零退出 |
| `strategy_signal` | 策略子进程由信号终止 |
| `timeout` | 平台超时终止 |
| `cancelled_by_user` | 用户取消 |
| `lease_lost` | 当前 Attempt 不再持有租约 |
| `lease_expired` | 心跳停止并由调度器确认过期 |
| `runner_exit_nonzero` | Runner 进程异常退出 |
| `container_oom` | Docker 明确报告 OOM |
| `container_died` | 容器退出，但没有更精确原因 |
| `host_interrupted` | 可确认宿主机关机或重启 |
| `unknown_interruption` | 只能确认 Attempt 中断，不能可靠判断原因 |

不得仅凭“最后心跳时间接近容器重启”推断 OOM。没有 Docker OOM 证据时必须记录为 `container_died` 或 `unknown_interruption`。

### 10.2 策略子进程

Bar 与 L2 策略会话在未收到结构化响应时必须读取 `multiprocessing.Process.exitcode`：

- 正数表示进程返回的退出码；
- 负数表示 POSIX 信号编号；
- `None` 表示当时仍在运行，不能伪造退出原因。

子进程异常退出时，父 Runner 生成稳定错误码、记录 Attempt 退出字段并保留原有安全用户提示。超时或取消由父 Runner 主动终止时，必须区分平台超时和用户取消，不能统一显示“子进程异常退出”。

### 10.3 Runner 进程

`runner_supervisor` 已能发现被管理 Runner 进程的退出码。实施时应使用容器 hostname 与退出进程 PID 重建同格式 `workerId`，写入 `runner_process.exited` 事件，并尝试把该 Worker 当前运行的 Attempt 标记为 `runner_exit_nonzero`。如果数据库不可用，只写日志，后续由租约过期兜底。

Supervisor 重启 Runner 进程后，新进程使用新 PID 和 `workerId`，不能继续冒用旧 Attempt。

### 10.4 容器与宿主机

增加只读容器事件观察器，订阅本 Compose 项目的 `oom/die/restart/destroy` 事件并输出结构化事件。它只补充运维证据，不直接把 Run 标记为最终失败。

容器事件通过 `containerId` 与正在运行的 Attempt 关联；同容器包含多个 Runner 进程时，所有活跃 Attempt 都要标记为可能受影响。只有明确 `oom` 事件才能写 `container_oom`。

宿主机断电时，观察器通常也来不及写日志。系统恢复后，调度器根据租约过期把旧 Attempt 标记为 `unknown_interruption`；如果能从系统启动标识或受控宿主机事件确认重启，再提升为 `host_interrupted`。

## 十一、故障场景矩阵

| 场景 | PostgreSQL 结果 | Loki 证据 | 最终诊断 |
| --- | --- | --- | --- |
| 普通策略异常 | Run 失败或策略错误；Attempt 失败；安全错误摘要 | 异常类型、阶段、脱敏帧摘要 | 可按任务 UUID 完整定位 |
| 策略子进程崩溃 | Attempt 记录退出码或信号 | 子进程启动、失联和退出事件 | `strategy_exit_nonzero` 或 `strategy_signal` |
| 用户取消 | Run/Attempt 取消 | 取消请求和终止阶段 | `cancelled_by_user` |
| 平台超时 | Run/Attempt 失败 | 超时阈值和终止事件 | `timeout` |
| Runner 进程退出，Supervisor 存活 | 尽力立即标记；失败时由租约兜底 | Supervisor 退出码事件 | `runner_exit_nonzero` |
| Runner 容器 OOM | 租约过期后 Attempt 中断 | Docker `oom/die` 事件 | 有证据时 `container_oom` |
| Runner 容器重启 | 租约过期后 Attempt 中断并可重领 | Docker `die/restart` 事件 | `container_died` 或更精确原因 |
| 宿主机断电 | 恢复后由租约标记中断 | 可能只有日志时间断点 | `unknown_interruption`，不伪造 OOM |
| PostgreSQL不可用 | 不能确认新的业务状态 | Runner 数据库错误与重试事件 | 恢复后按真实租约和任务状态处理 |
| Loki 不可用 | 回测状态不受影响 | Docker 本地日志暂存；超窗可能丢失 | 页面显示“集中日志暂不可用” |
| Alloy 不可用 | 回测状态不受影响 | Docker 本地日志继续轮转 | 恢复后从持久位置补采 |
| 同一 Run 多次领取 | 每次 Attempt 独立保存 | 每次使用不同 `attemptToken` | 管理员按 Attempt 查看，不混合证据 |

## 十二、管理员查询与页面

### 12.1 后端接口

保留现有 `/api/admin/system-errors`，新增受控任务诊断接口：

```text
GET /api/admin/backtest-runs/{run_id}/diagnostics
```

接口返回：

1. Run 基本信息和最终安全错误摘要；
2. 按时间排序的 Attempt 列表；
3. 每个 Attempt 的 Worker、容器、阶段、终止原因、退出码和错误分类；
4. 集中日志状态：`available/unavailable/expired/disabled`；
5. 有界的安全事件时间线；
6. 可复制的任务和 Attempt 日志关联键。

Backend 使用固定查询模板和经过 UUID 校验的参数访问 Loki。查询时间范围优先使用 Attempt 起止时间并增加小幅缓冲；没有时间信息时使用受限默认窗口。单次查询设置短超时、最大时间跨度、最大行数和响应大小，Loki 超时只影响日志区，不影响数据库诊断信息。

不得接受前端传入任意 LogQL、标签选择器或无上限时间范围。

### 12.2 页面行为

现有“回测诊断日志”页面增加任务详情抽屉：

1. 顶部显示 Run 最终状态和安全原因；
2. 中部按 Attempt 展示领取、阶段、异常、中断、重试和终态时间线；
3. 明确区分“平台已确认原因”和“只能确认执行中断”；
4. Loki 不可用或日志已过期时仍展示 PostgreSQL Attempt 与错误摘要；
5. 原始运维日志不直接渲染在普通用户页面；受控管理员页面也只返回脱敏字段；
6. 保留可复制关联键，供服务器维护脚本或内部 Grafana Explore 查询。

前端不得以“没有 Loki 日志”等同于“任务没有错误”。

### 12.3 维护查询入口

新增只读维护脚本，接收完整任务 UUID，可选 Attempt UUID，在服务器受控环境调用 Loki 查询并输出脱敏后的完整事件序列。脚本必须：

- 校验 UUID；
- 自动限制时间范围和最大行数；
- 不读取或打印 `.env`；
- 不接受任意 LogQL；
- 不把查询结果写入仓库；
- 默认隐藏内部地址和凭据模式。

如后续部署 Grafana，Grafana只在内网或经认证的运维入口开放，不复用普通产品登录会话，也不直接对公网暴露。

## 十三、部署与配置

### 13.1 新增服务

在 `deploy/compose.infrastructure.yml` 中按需增加：

1. `loki`：单体 Loki，内部端口、持久数据卷、健康检查和资源限制；

- `TREND_GRID_OBSERVABILITY_ENABLED`；
- `TREND_GRID_LOKI_URL`；
- `TREND_GRID_LOG_RETENTION_HOURS`；
- `TREND_GRID_LOG_QUERY_TIMEOUT_SECONDS`；
- `TREND_GRID_LOG_QUERY_MAX_LINES`；
- `TREND_GRID_LOG_LOCAL_MAX_SIZE`；
- `TREND_GRID_LOG_LOCAL_MAX_FILES`。

### 13.3 容量与健康

日志基础设施必须设置 CPU、内存、PID 和磁盘预算。至少监控：

- Loki 写入失败、查询失败、WAL 重放和磁盘占用；
- Compactor 最近一次成功执行时间；
- Alloy 活跃 target、解析失败、发送失败和 positions 持久化；
- Docker 本地日志目录大小；
- 日志丢弃、截断和脱敏计数；
- 容器事件观察器最后事件时间和连接状态。

日志服务异常不得让 `/api/health` 把业务后端标记为完全不可用；健康结果应分别报告 `backtest` 与 `observability`。

## 十六、测试与验收

### 16.1 单元测试

1. 事件信封完整、时间格式稳定、未知字段被拒绝。
2. 任务 UUID、Attempt、Worker 和阶段正确注入。
3. 密码、令牌、连接 URL、源码行和超长文本被脱敏或截断。

### 16.2 集成测试

5. 在隔离环境停止并删除 Runner 容器，重建后仍可查询停止前日志。
6. 在隔离环境触发受控 OOM 或使用等价 Docker 事件夹具，只有明确 OOM 证据才显示 `container_oom`。
7. 停止 Loki 后执行任务，业务结果正常；恢复 Loki 后在轮转窗口内补采日志。
8. 停止 Alloy 后产生日志，恢复后按 positions 继续采集且不产生不可接受重复。
9. 任务删除后 PostgreSQL Attempt 和错误记录级联删除，Loki 日志只按固定保留期存在且不能反查用户身份或源码。
10. 30 天保留配置经过缩短周期的测试环境验证，不能只检查配置文件文本。

### 16.3 前端测试

1. 输入完整任务 UUID 可加载 Attempt 时间线。
2. 多次 Attempt 按时间排序并明确标记中断与重试。
3. Loki 不可用时仍展示 PostgreSQL 诊断，并给出可理解的降级说明。
4. 日志过期与任务没有错误是两种不同状态。
5. 页面不渲染内部原始堆栈、连接地址和隐藏字段。
6. 相关 Vitest、TypeScript 检查和正式构建实际通过。

### 16.4 性能与容量

1. 任务事件只发生在领取、阶段切换、异常和终态，不随 Bar/Quote 数量线性增长。
2. 使用 49 号方案的固定用例比较改造前后热态耗时和日志量。
3. 日志格式化或采集异常不得持有回测关键锁或延长数据库事务。
4. 日志磁盘占用、Loki WAL、chunk、Compactor 和 Docker 本地轮转总量均有预算和硬上限。
5. 在代表性并发下验证 Loki 故障不会降低可用回测槽位或造成任务失败。

### 16.5 验收标准

1. 任一新失败任务可通过任务 UUID定位至少一个 Attempt、最后阶段、Worker 和终止原因。
2. 正常异常具备分类后的数据库摘要和保留期内的集中日志证据。
3. 子进程异常退出具备真实退出码或信号；未知时明确标记未知，不伪造原因。
4. Runner 容器删除并重建后，保留期内仍能查询删除前日志。
5. 同一任务多次领取的 Attempt 不互相覆盖。
6. Loki/Alloy 停止时，回测提交、执行、取消和结果落库语义不变。
7. 普通用户、共享回测和公开接口均不泄露内部诊断。
8. 日志中不出现测试凭据、策略源码、账户信息或完整请求载荷。
9. Compactor 实际执行保留删除，不能无限占用磁盘。
10. 本地自动化测试通过；远程普通用户样本回归真实完成，或明确标记待验证及原因。

## 十七、发布、回滚与降级

### 17.1 发布顺序

1. 部署幂等数据库迁移；
2. 启动 Loki、Alloy、socket proxy 和事件观察器，验证内部健康；
3. 先保持应用日志查询功能关闭，验证采集与保留；
4. 检查并处理运行中的 L2 任务；
5. 同批重建 backend、Bar Runner、L2 Runner 和 frontend；
6. 验证 Attempt 写入、错误摘要和历史读取；
7. 开启管理员日志查询并执行代表性任务；
8. 观察磁盘、Loki、Alloy 和任务成功率后完成发布。

### 17.2 回滚

1. 管理员 Loki 查询通过配置开关关闭，页面回退为数据库摘要，不需要回滚数据库。
2. 停止 Alloy、Loki和事件观察器不影响任务运行；Docker 本地轮转继续受上限保护。
3. 041 迁移是加法迁移，旧版本可忽略新表和新字段；不得删除已执行迁移或生产诊断数据。
4. 若结构化日志格式导致运行异常，回滚 Runner 镜像并保留新表；历史任务仍按原接口读取。
5. 若日志磁盘快速增长，先关闭采集和查询，再按 Loki 正常保留/删除流程处理，禁止直接删除未知索引目录。

### 17.3 可接受降级

| 故障 | 产品行为 |
| --- | --- |
| Loki 不可用 | 回测正常；管理员看到数据库摘要和“日志暂不可用” |
| Alloy 不可用 | 回测正常；本地轮转保留有限恢复窗口 |
| 事件观察器不可用 | 回测正常；OOM 等容器原因可能降级为未知中断 |
| Attempt 写入失败 | 视为数据库业务故障，任务不得假装已被可靠领取 |
| 日志查询超时 | 终止查询，不扩大时间范围重试；数据库诊断继续可用 |

## 十八、安全与隐私审查

1. Loki、Alloy、socket proxy 和事件观察器只在内部网络通信。
2. Docker socket proxy 使用最小只读 API，不允许容器创建、执行、删除、挂载或镜像管理。
3. 产品管理员权限与服务器原始日志权限分离；拥有产品管理员角色不自动获得 Docker 或 Loki 全量访问权。
4. 后端只提供预定义、安全、有界的任务诊断查询，不提供通用日志搜索代理。
5. 日志保留 30 天，数据库错误摘要随任务生命周期存在；独立运行时统计继续遵循 40 号方案的脱敏和 180 天规则。
6. 日志配置、查询结果和测试夹具不得进入 Git；自动化测试只使用合成凭据与合成策略。
7. 对脱敏规则本身编写反例测试，避免只覆盖理想字段。

## 十九、方案自审

### 19.1 为什么不只加 Docker volume

Docker volume 只能持久化容器内文件，无法统一处理多 Runner 检索、日志轮转、标签约束、保留和查询权限。继续让每个任务写独立日志文件还会引入文件数量、清理、并发写入和路径安全问题。

### 19.2 为什么不把完整日志写入 PostgreSQL

PostgreSQL 适合保存小而稳定的业务事实，不适合保存高吞吐、多行、按时间检索的日志正文。把日志正文写入任务事务还会放大数据库故障并影响回测完成。数据库只保存 Attempt 和错误摘要，日志系统保存过程证据，职责更清晰。

### 19.3 为什么需要 Attempt 表

只使用 Run UUID 无法区分租约过期后的多次执行。当前任务表会覆盖 `attempt_token` 和 `worker_id`，导致管理员看到最终任务却无法重建旧 Runner 现场。Attempt 是调度、性能和诊断共同需要的稳定事实，不是日志系统的重复数据。

### 19.4 为什么任务 UUID 不能做 Loki 标签

每个任务 UUID 都是唯一值，会为每个任务创建新的日志 stream，导致索引和小 chunk 快速膨胀。任务 UUID 应保留在 JSON 字段或 structured metadata 中，通过固定低基数标签先缩小服务范围再解析查询。

### 19.5 为什么日志系统必须可降级

可观测性用于解释业务系统，不应成为业务系统的新单点故障。业务数据库写入失败需要阻止不可靠执行；Loki 写入失败只应减少诊断证据并触发告警，两者故障语义不能混同。

### 19.6 已知限制

1. 单机 Loki 持久卷不能抵抗宿主机磁盘损坏。
2. 宿主机瞬时断电可能没有 Docker 终止事件，只能通过租约推断中断。
3. 日志经过强制脱敏和大小限制，不等同于无约束内存转储。
4. 任务删除不会同步删除 Loki 行；日志只保留不含用户身份和源码的短期运维事件，并按固定期限删除。
5. 容器事件观察器故障时，精确 OOM 归因会降级，但任务状态和租约恢复不受影响。

这些限制必须在交付说明中保留，不得把“保留期内可通过任务编号排查”宣传为无限期或灾备级日志归档。

## 二十、官方实现依据

- Grafana Alloy `loki.source.docker` 官方说明：支持读取 Docker 日志，并使用 positions 文件在重启后恢复读取位置：<https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.docker/>
- Grafana Loki 标签最佳实践：动态标签必须保持低基数，不应将请求 ID、订单 ID等唯一值设为标签：<https://grafana.com/docs/loki/latest/get-started/labels/bp-labels/>
- Grafana Loki 保留策略：保留由 Compactor 执行，默认不会自动启用，marker 工作目录需要持久化：<https://grafana.com/docs/loki/latest/operations/storage/retention/>
- Grafana Loki 日志删除：新部署应使用 TSDB，定向删除依赖 Compactor 且带行过滤的删除成本较高：<https://grafana.com/docs/loki/latest/operations/storage/logs-deletion/>
