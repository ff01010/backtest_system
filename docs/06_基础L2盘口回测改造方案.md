# 基础 L2 盘口回测改造方案

## 1. 背景与结论

现有回测以固定周期 K 线驱动策略，并按 Bar 成交模型处理订单。该模式适合快速研究，但不能表达买卖价差、盘口深度、部分成交和委托等待。

已只读核验远程 ClickHouse 中的相关数据表：

- `quant.tick_quote`：名义 3 秒采样的十档盘口快照，含最新价、累计成交量/额、买卖十档价格与数量。快照并非绝对连续，存在 6 秒及以上间隔，且覆盖集合竞价和收盘后时段。
- `quant.tick_data`：逐笔事件流，含委托新增、撤单与成交；具备 `trade_id`、`exchange_order_id`、买卖方向及买卖委托序号等字段。
- `quant.market_bars`：已有 Bar 数据，但当前 `timestamp` 字段全部落在 1970 年，不能用于日内顺序回测。
- `raw_historical_data.qmt_kline`：现有 QMT K 线回测数据源，继续保持不变。

上游将以 `tick_quote` 拟合常用周期并写入新的 Bar 表，表名待定。本项目只读取该表，不承担 Bar 物化、回填或重算职责。

本方案采用“预聚合策略 Bar + L2 事件确认成交”的基础 L2 模式。它显著优于 Bar 收盘价立即成交，但不宣称复现完整交易所队列优先级。

## 2. 目标与边界

### 2.1 目标

- 接入上游预聚合的 `1m`、`3m`、`5m`、`15m`、`30m`、`45m`、`60m`、`1d` 固定周期 Bar。
- 对未预聚合的低频周期，支持从 `tick_quote` 按需聚合并缓存派生 Bar。
- 保留 `on_bar` 策略接口：策略仍在 Bar 收盘后产生订单。
- 支持基于十档盘口的市价单、可成交限价单、部分成交和盘口冲击成本。
- 使用逐笔成交事件为被动限价单提供无前视的保守成交确认。
- 第一阶段即支持内置策略与自定义 `on_bar` 脚本的 L2 回测。
- 保持 QMT K 线快速回测、已有回测记录和现有策略脚本兼容。

### 2.2 非目标

- 第一阶段不重建完整订单簿，不计算真实排队位置。
- 第一阶段不模拟隐藏流动性、自身订单对市场的冲击或真实网络传输延迟。
- 不修改远程原始表 `quant.tick_quote`、`quant.tick_data`、`quant.market_bars` 和既有 QMT 表。
- 不由本项目创建、物化或维护上游的 L2 Bar 表。
- 不把 `market_bars` 作为 L2 模式的数据来源，除非其时间字段被上游修复并重新核验。
- Redis 不作为行情真源、回测任务真源或最终回测结果存储。

## 3. 数据规则

### 3.1 交易时段

常规连续竞价只读取 `09:30:00–11:30:00` 与 `13:00:00–15:00:00`。集合竞价和收盘后快照不进入基础 L2 回测，除非后续单独增加竞价模式。

所有分钟周期按上午、下午两个时段分别分桶，禁止跨越午休。`45m` 在每个时段末尾可能出现不足 45 分钟的尾部 Bar；第一阶段保留该 Bar，并记录实际时长与质量标记。

### 3.2 价格与量额

适配器必须在运行时验证并统一以下单位，不允许在策略或撮合器内混用原始值：

- `tick_data.price` 作为规范成交价格候选；
- `tick_quote` 的盘口价格、`last_price`、累计量额的缩放规则；
- `cum_volume`、`cum_amount` 的区间增量规则，以及交易日开始时的基准值。

验证失败时拒绝该日期的 L2 回测，不以猜测的缩放系数继续运行。

### 3.3 快照完整度

`tick_quote` 的 3 秒采样存在间隔缺口，因此上游 Bar 表不应仅以“每分钟恰有 20 条”作为唯一完整度标准。上游需为每根 Bar 输出快照数量、最大间隔、有效价格数量和质量状态，供本项目校验。

默认情况下，目标区间存在 `partial` 或 `empty` Bar 时拒绝 L2 回测；后续若开放降级模式，必须在请求与结果中明确标记。

### 3.4 公司行为与交易规则

L2 Bar、十档快照与逐笔成交必须使用同一未复权价格基准。跨越除权除息日的隔夜持仓，只有在存在已验证的公司行为调整数据时才允许回测；否则该范围拒绝 L2 回测，不以复权 Bar 与未复权盘口混算。

`L2ExecutionEngine` 读取标的规则快照，校验最小变动价位、交易单位、涨跌停、停牌与账户卖空权限。A 股现货默认启用 T+1 可卖数量约束；卖空只有在账户和标的规则均明确允许时才可用。`intraday（当日持仓）` 模式在最后有效盘口尝试平仓，未平部分标记失败原因；所有日内未成交订单在收盘时撤销。

## 4. 目标架构

```text
上游 L2 Bar 表 ──> L2BarProvider ──┐
quant.tick_quote ──> L2QuoteProvider ─┼─> l2-runner ──> strategy-worker
quant.tick_data  ──> L2EventProvider ─┘       │              on_bar 策略
                                               │              L2ExecutionEngine
PostgreSQL 任务队列 / 租约 ───────────────────┤              账户 / 状态 / 未成交订单
Redis 低频周期 Bar 缓存 ──────────────────────┘
```

### 4.1 数据源适配器

新增统一市场数据协议，并实现三个只读适配器：

- `L2BarProvider（L2 Bar 数据源）`：读取并校验上游预聚合 Bar 与覆盖信息；具体表名由部署配置提供。
- `L2QuoteProvider（L2 快照数据源）`：读取、规范化和校验三秒十档快照。
- `L2EventProvider（L2 事件数据源）`：按时间顺序读取逐笔委托、撤单和成交事件。

原有 QMT ClickHouse 读取逻辑保留为独立 Provider。上层 `market_data` 门面维持当前函数签名，避免前端和既有回测流程直接依赖具体表名。

适配器的输出固定为 `NormalizedBar（标准化 K 线）`、`QuoteSnapshot（十档快照）`、`TradeEvent（逐笔成交事件）` 和 `CoverageSnapshot（覆盖快照）`。外部表的字段名、周期编码、时间语义、价格缩放与质量列仅存在于 `SourceMappingProfile（数据源映射配置）`，不得散落到回测代码。

`SourceMappingProfile` 仅可由受控部署配置提供。表名和列名必须先通过 `DESCRIBE TABLE` 校验为白名单标识符，值条件使用参数化查询；不得将用户请求中的字符串直接拼接为 ClickHouse 标识符或 SQL 片段。

### 4.2 上游预聚合 Bar 输入表

上游负责创建和维护常用周期 Bar 表，本项目不对其执行写入。表名待定；接入前需确认其至少提供：

- 标的、周期、交易日、Bar 起止时间；
- `open/high/low/close/volume/amount`；
- 快照数量、最大快照间隔、有效价格数量、质量状态；
- 源快照版本、聚合规则版本和生成时间或等效可追溯标识。

上游原始快照更新后，由上游重建受影响的 Bar。项目侧根据源版本或等效标识使已有 L2 回测范围校验与结果快照失效。

### 4.3 Bar 接入规则

- 上游 Bar 必须以连续竞价时段为边界，禁止跨越午休。
- 上游需要明确 `open/high/low/close/volume/amount` 的单位与累计量额计算规则。
- 无有效成交价的时间桶必须标记为 `empty`，不得伪造为可交易价格。
- `L2BarProvider` 将拒绝缺少日内时间、周期、质量状态或版本标识的记录。

### 4.4 低频周期 Bar 缓存

上游未预聚合的周期由 `L2QuoteProvider` 在 ClickHouse 端从 `tick_quote` 按交易时段聚合；项目不将大批三秒快照拉入 Python 进程后再聚合。聚合结果按“标的、交易日、目标周期、源版本、聚合规则版本”写入 Redis。

缓存键采用 `l2bar:v1:{source_version}:{symbol}:{trade_date}:{period}`。缓存值包含标准化 Bar、质量状态和生成元数据；缓存丢失或过期时可从 ClickHouse 重新生成。缓存以单日为粒度、设置 TTL 与内存淘汰策略，不保存跨年范围或原始逐笔数据。

常用周期始终优先读取上游 Bar 表；Redis 仅服务于低频或临时周期。

`source_version（源数据版本）` 是启用缓存的前提。上游不能提供可信版本或等效批次标识时，低频周期直接回源 ClickHouse 且不写 Redis，避免缓存失效不完整导致结果不可追溯。

## 5. 自定义脚本 L2 会话

### 5.1 职责边界

独立 `l2-runner` 服务负责连接 ClickHouse、解析 `SourceMappingProfile`、校验覆盖范围和按交易日读取标准化数据。`strategy-worker` 不持有 ClickHouse 凭据、不挂载原始数据目录，也不接受任意表名或任意查询。

worker 负责执行用户脚本、维护 `state`、账户、持仓和未成交订单，并在同一会话中运行 `L2ExecutionEngine`。因此自定义脚本在每根 Bar 上看到的账户状态，始终是此前 L2 撮合后的真实模拟状态。

### 5.2 会话协议

L2 模式新增仅供后端调用的会话接口：

1. `create_l2_session`：提交已验证的脚本快照、账户参数、撮合参数和请求范围，创建隔离会话。
2. `begin_day`：声明交易日、该日数据版本和预期块数量，校验日期连续性。
3. `process_chunk`：`l2-runner` 按最大事件数和最大字节数发送有界、已排序的 Bar、十档快照与逐笔成交事件；worker 在内存中持续回放。
4. `finish_day`：确认当日数据流完整，并保留跨日策略状态、账户、持仓和未成交订单。
5. `finish_l2_session`：返回完整成交、权益、订单事件、警告和会话快照。
6. `discard_l2_session`：在取消、超时或异常时释放会话资源。

单次 `process_chunk` 不得携带跨日数据或超过资源上限。worker 重启、会话超时、输入日期不连续或块序号缺失时，本次任务标记失败；第一阶段从头重跑，不尝试恢复内存中的策略状态。

### 5.3 无前视时间线

同一交易日中，worker 以 `(time, event_priority, event_sequence)` 作为唯一时间线。形成 Bar 的数据可以用于该 Bar 的 `on_bar`；订单即使 `l2_latency_ms=0`，也只能匹配严格晚于 Bar 收盘时间的事件，不能使用同一时间戳的盘口或成交。

对后续同一时间戳，先更新十档快照，再按 `trade_id` 升序处理逐笔成交；已生效主动订单先使用该快照，随后被动订单才消费该时间戳的成交量。缺少稳定事件序号的输入日期拒绝 L2 回测。

### 5.4 第一阶段资源边界

第一阶段保留现有自定义脚本的导入能力，不新增导入白名单或脚本网络策略，避免破坏既有脚本体验。资源保护在脚本语言之外实施：限制并发 L2 会话数、设置 worker 容器 CPU、内存与 PID 上限，并对单个数据块和整项任务设置宽松但有限的运行时限。

`strategy-worker` 不保存 ClickHouse、PostgreSQL、Redis 或 runner 凭据；runner 的数据源权限不传入脚本执行上下文。导入白名单、网络出口限制和更严格的脚本沙箱列为后续可选加固项，需在评估现有脚本兼容性后单独启用。

## 6. 基础 L2 撮合规则

### 6.1 订单生效时间

策略仅能基于已结束的 Bar 生成订单。订单生效时间为 Bar 收盘时间加 `l2_latency_ms（L2 模拟延迟毫秒数）`；撮合器只读取生效时间之后的盘口快照和逐笔事件，禁止使用未来数据。

### 6.2 主动订单

市价单和会立即穿透盘口的限价单，在生效时间之后的首个有效十档快照上，按对手方档位逐档成交：

- 买入使用卖一至卖十；卖出使用买一至买十；
- 每档按可见数量限制成交量；
- 同一快照维护共享的可用量预算，按订单生效时间和创建顺序分配，禁止多个模拟订单重复使用同一档显示量；
- 数量不足时产生部分成交，剩余订单继续等待或按订单有效期撤销；
- 记录每档成交明细、成交均价、盘口冲击和未成交原因。

### 6.3 被动限价订单

被动限价单不以快照触及就直接成交。撮合器读取订单生效后的 `tick_data` 成交事件：只有成交价触及委托价，且可用成交量满足保守参与率限制时才确认成交。

第一阶段不计算订单真实队列位置；结果中必须标注“保守成交确认”。后续在撤单关联和委托序号规则完全验证后，再增加队列消耗模型。

### 6.4 权益与日终规则

每根 Bar 收盘使用该 Bar 的有效 `close` 计算权益；不存在有效收盘价时拒绝该区间，不用未知价格估值。日终成交、撤单、强制平仓和持仓调整都记录为订单事件，避免回测结果与账户快照不一致。

## 7. 回测接口与结果

### 7.1 回测模式

在现有回测方案中新增成交模式：

- `bar_close`：现有 K 线快速回测，默认兼容模式；
- `l2_quote`：基础 L2 十档盘口回测，支持内置策略和自定义 `on_bar` 脚本。

选择 `l2_quote` 时，回测作为异步任务执行。界面只展示 L2 覆盖完整、且 Bar、十档快照与逐笔事件交集完整的日期范围。没有 L2 数据时不回退至 K 线收盘价成交。

### 7.2 可追溯性

L2 回测结果保存：

- Bar 源版本、L2 快照源版本和逐笔事件源版本；
- 撮合模式、延迟、参与率等运行参数；
- 订单生效时间、快照时间、逐档成交明细、部分成交与撤销原因；
- 数据质量告警和覆盖检查结果。

### 7.3 结果体积预算

最终结果只保存成交、订单状态变化、每日权益、必要的 Bar 级账户快照和汇总指标；不保存原始十档快照、逐笔事件或每个快照的账户状态。诊断明细作为可过期产物保存，并设置单任务字节数、事件数和保留期上限；超过上限时保留摘要并写入截断告警。

### 7.4 任务与失败语义

PostgreSQL 是任务状态与租约的唯一真源。`l2-runner` 使用原子领取、租约过期和心跳机制获取任务，并遵守用户并发额度。每次领取生成 `attempt_token（执行尝试令牌）`；只有持有当前令牌的 runner 才能写入心跳、最终结果或终态，避免租约过期的旧 runner 覆盖新尝试。任务状态应反映排队、运行、完成、取消和失败。

仅在 `finish_l2_session` 成功后保存最终结果；worker 或 `l2-runner` 异常时保存失败原因，不保存部分成交结果为成功回测。租约超时的任务自动回到待执行状态，第一阶段从头重跑。任务取消时调用 `discard_l2_session`，并释放 runner 与 worker 的会话资源。

## 8. 实施步骤

1. 定义标准化领域模型、`SourceMappingProfile` 与模拟数据夹具；该步骤不依赖上游 Bar 表最终字段。
2. 新建 L2 Provider 接口及其三个只读适配器，保留 QMT Provider 行为不变；待表名和字段确定后只新增映射配置与集成验证。
3. 实现 L2 Bar 覆盖校验、版本快照读取和映射失败错误提示；不创建或写入上游 Bar 表。
4. 增加 Redis 低频周期 Bar 缓存与 ClickHouse 按需聚合路径，设置版本化缓存键、TTL、容量控制和无版本禁用策略。
5. 增加 PostgreSQL 任务租约与 `attempt_token` 结构、独立 `l2-runner` 服务；runner 按块供数并管理任务心跳、取消和重试。
6. 在 `strategy-worker` 实现 L2 会话协议、分块校验与跨日状态保持；runner 调用会话接口。
7. 实现 `L2ExecutionEngine` 的主动订单逐档撮合、部分成交和无前视订单时间线。
8. 加入逐笔成交驱动的被动限价单保守确认规则。
9. 接入异步回测任务、任务快照、结果查询和前端成交模式选择。
10. 更新 `docs/玄龄回测系统使用手册.md` 中已确认的 `on_bar` 成交语义与错误提示。

## 9. 验证标准

- Provider 单元测试：时段过滤、价格单位、快照缺口、累计量额增量和数据版本。
- Bar Provider 单元测试：全部固定周期、午休边界、45 分钟尾部 Bar、空桶、质量标记与版本读取。
- 撮合单元测试：十档逐档成交、买卖方向、部分成交、限价拒绝、固定延迟和无前视约束。
- 时间线测试：同时间戳 Bar、快照、成交和零延迟订单均不产生未来函数。
- 容量预算测试：多个订单在同一快照竞争深度时不重复成交。
- 交易规则测试：T+1、涨跌停、最小价位、交易单位、停牌、日终撤单和公司行为范围拒绝符合规则。
- Worker 会话测试：自定义脚本跨日 `state`、持仓、未成交订单和异常清理均符合预期。
- 资源边界测试：单块超时、整任务超时、会话并发上限与容器终止均能将任务安全标记失败并清理资源。
- 异步任务测试：取消、worker 重启、日期不连续和会话超时均不能产生成功的部分结果。
- 任务租约测试：多 runner 竞争、心跳续租、租约超时、旧令牌提交和从头重跑均不会重复提交成功结果。
- Redis 缓存测试：单日键隔离、版本失效、无版本禁用、TTL 过期、缓存丢失回源和低频周期聚合结果一致。
- 结果预算测试：大规模回测不会持久化原始 L2 数据，产物截断和告警可追溯。
- 集成测试：以小标的、小日期范围同时读取 `tick_quote` 与 `tick_data`，验证结果可复现。
- 回归测试：现有 QMT K 线回测、策略脚本、用户隔离和历史记录查询保持通过。

## 10. 风险与待确认事项

- 上游 L2 Bar 表名与最终字段契约尚未确定；这不阻塞通用适配器、会话协议和撮合内核实现，但会阻塞真实数据的端到端接入验证。
- `tick_quote` 的盘口价格和累计字段缩放规则必须先验证；不满足契约的日期不得进入回测。
- `tick_data` 的撤单事件与 `exchange_order_id`、`ask_order_seq`、`bid_order_seq` 的关联语义需在实现队列模型前验证。
- L2 数据量远大于 QMT K 线；回放必须按交易日流式读取，禁止一次加载多年事件到进程内存。
- 同时间戳事件需具备稳定 `trade_id` 或等效序号；缺失时不得以数据库物理顺序替代。
- 公司行为和标的规则数据尚未确认；在该数据契约就绪前，相关范围或订单类型必须拒绝 L2 回测。
- worker 会话为内存态；第一阶段不提供断点续跑，重启或超时后从头重跑，避免策略状态与账本状态不一致。
- 第一阶段保留现有脚本导入能力；资源限制在容器与任务层实施，脚本导入白名单和网络限制延后评估。
- Redis 缓存只影响低频周期的响应时间；缓存失效、淘汰或重启不得改变回测结果。
- `l2-runner` 需要独立于 API 后端部署，并仅由它持有 ClickHouse 与 PostgreSQL 的运行凭据；`strategy-worker` 的无凭据隔离边界保持不变。
- L2 可用历史与 QMT K 线可用历史并不完全重叠；系统应按所选成交模式展示各自可用范围。
- 本方案只覆盖模拟回测，不增加实盘下单能力。
