# 统一 Bar 数据层与标准 Bar 回放方案

## 1. 背景与结论

当前系统存在两条彼此独立的 Bar 链路：

- 普通 bar_close 回测直接读取 raw_historical_data.qmt_kline 中的 QMT K 线，当前按 Bar 收盘价成交。
- L2 盘口回测在未配置正式 L2 Bar 表时，从 quant.tick_quote 三秒十档快照临时聚合 Bar，并将派生 Bar 写入 Redis。

这导致两种成交模式无法稳定共享同一份 Bar，也使 QMT 原生表未提供的 3m、45m 等周期不能用于普通回测。当前 QMT 表的已导入数据在覆盖记录和基础质量检查中均通过，但仅覆盖 6 个标的：1m、5m、60m 数据区间为 2023-07-31 至 2026-07-30，不能视为全市场数据源。

本方案建立统一的 BarProvider（Bar 数据提供器）适配层，以“正式 Bar 表 > QMT 原生或派生 Bar > 三秒 quote 临时聚合 Bar”的优先级，为两种回放模式输出相同的标准化 Bar。新建任务默认采用“标准 Bar 回放（快速）”：已完成 Bar 触发信号，下一根可交易 Bar 的开盘价叠加滑点成交；保留“L2 盘口回放（真实）”：使用相同 Bar 触发信号，但继续读取三秒十档盘口逐档撮合。

本轮只处理 Bar 数据与标准 Bar 成交时序。十档盘口跨任务 Redis 缓存、L2 盘口查询扫描优化、逐笔成交和排队模拟均不在本轮范围。

## 2. 目标、范围与不变量

### 2.1 目标

1. 为标准 Bar 回放和 L2 盘口回放提供统一、可追溯的 Bar 输入。
2. 使 1m、3m、5m、15m、30m、45m、60m、1d 均能按数据源可用性运行。
3. 复用现有 Redis 派生 Bar 缓存，避免同一标的、交易日、周期重复从三秒 quote 聚合。
4. 将普通回测成交语义改为“已完成 Bar 信号 → 下一根 Bar 开盘价 ± 滑点成交”。
5. 在历史任务和结果中记录 Bar 来源、版本、质量与缓存命中。

### 2.2 本轮范围

- 统一 BarProvider 协议、数据源选择和标准化数据契约。
- QMT K 线 Provider、正式映射 Bar Provider、quote 临时聚合 Provider 的接入和回退规则。
- Redis 版本化 Bar 缓存的复用、元数据和失效边界。
- bar_close 到 bar_next_open 的标准 Bar 回放演进，以及前后端模式文案、参数校验和历史兼容。
- 单元、集成、回归与真实性能验证。

### 2.3 非目标

- 不缓存原始十档盘口，不调整 Redis 内存上限、LFU/LRU 策略或持久化方式。
- 不优化 L2 成交阶段的 quant.tick_quote 查询次数、扫描量、HTTP/TCP 协议或容器架构。
- 不修改 ClickHouse 原始行情表、导入任务和历史数据。
- 不改变 L2 逐档撮合、部分成交、底仓做 T、尾盘结算和 on_quote 事件语义。
- 成交模式与策略类别解耦；方向性持仓策略和底仓增强策略均可选择标准 Bar 回放或 L2 盘口回放。
- 底仓、做 T、最小下单数量、可卖数量和尾盘结算等业务约束不因成交模式切换而取消；差别仅在订单的成交数据与时点。

### 2.4 必须保持的不变量

1. 分钟周期从上午 09:30:00、下午 13:00:00 分别对齐，禁止跨午休连续切桶。
2. on_bar(bar, state) 只在 Bar 完成后调用；策略可见 time 固定表示 Bar 完成时点。
3. 标准 Bar 回放的订单只能在严格后续、可交易的 Bar 开始时成交。
4. L2 回放订单仍只使用严格晚于订单生效时点的十档快照成交。
5. 单个任务不能混用多个 Bar 来源；首选来源覆盖不足时，须为整个任务选择同一回退来源或明确失败。

## 3. 目标架构

~~~text
正式 Bar 表（字段适配器）
          │ 不可用时回退
QMT K 线（原生 / 1m 派生）
          │ 不可用时回退
quant.tick_quote ──交易时段聚合──► Redis 版本化派生 Bar
                                      │
                                      ▼
                          统一 BarProvider 输出
                          ┌───────────┴───────────┐
                          ▼                       ▼
            标准 Bar 回放（快速）       L2 盘口回放（真实）
            下一根 Bar 开盘 ± 滑点       后续三秒十档逐档撮合
~~~

### 3.1 Provider 优先级与任务级选择

每次回测在启动前由 BarSourceResolver（Bar 来源解析器）选择唯一 Provider：

1. 已配置且覆盖完整的正式 Bar 映射表。
2. 覆盖完整的 QMT 原生或派生 Bar。
3. 覆盖完整的三秒 quote 临时聚合 Bar。
4. 三者均不可用时，明确返回缺失日期和原因。

解析器只在任务开始时决策，避免一条资金曲线中部分日期使用 QMT、部分日期静默使用 quote 聚合。正式表、QMT 和 quote 聚合均必须映射为统一字段；quote 聚合只接受质量为 complete 的 Bar。

### 3.2 统一 Bar 数据契约

所有 Provider 输出 NormalizedBar（标准化 Bar），至少包含：

~~~text
symbol、trade_date、period、start_time、end_time、
open、high、low、close、volume、amount、quality、source_version
~~~

可选质量字段包括 snapshot_count、max_gap_ms、valid_price_count、actual_duration_seconds。QMT Provider 没有的 quote 质量指标必须显式为空，不得伪造。

每个任务保存以下快照：

- barSource（Bar 来源）：正式表、QMT 或 quote 临时聚合。
- barSourceVersion（来源版本）和 mappingVersion（字段映射版本）。
- aggregationVersion（聚合版本）：仅 quote 聚合适用。
- barCache（Bar 缓存）：命中和未命中交易日统计。
- barQualitySummary（Bar 质量汇总）。

## 4. 三类 Bar Provider

### 4.1 正式 Bar 表 Provider

后续正式 L2 Bar 表通过 SourceMappingProfile（数据源映射配置）映射字段、单位和时间语义。适配器启动时校验字段存在性，并在任务中保存映射和来源版本。时间戳必须明确是 Bar 开始还是完成；适配器统一输出 start_time 和 end_time，策略可见 time 使用 end_time。未知时间语义不得接入。

### 4.2 QMT Bar Provider

继续使用 raw_historical_data.qmt_kline FINAL 和 raw_historical_data.qmt_kline_coverage FINAL：

- 1m、5m、60m、1d 直接读取。
- 15m、30m 由 1m K 线按交易时段聚合。
- 周期或日期未被 QMT 覆盖时，由 Resolver 判断是否整体回退 quote 聚合。

现有 ensure_cached 仅表示覆盖检查，不负责下载或 Redis 缓存。QMT 来源版本以覆盖记录的最后导入时间、行数和周期构成可追溯快照。

### 4.3 quote 临时聚合 Provider

复用 quant.tick_quote 的三秒快照聚合和现有 Redis 键：

~~~text
l2bar:v2:{aggregation_version}:{mapping_version}:{symbol}:{trade_date}:{period}
~~~

支持 1m、3m、5m、15m、30m、45m、60m、1d。1d 汇总上午和下午连续竞价时段；非日线的尾部不足周期 Bar 保留 actual_duration_seconds。Redis 继续只缓存派生 Bar 与质量元数据，TTL 保持 30 天；缓存丢失或 Redis 重启仅触发回源重建，不影响回测语义。映射、价格缩放、分桶或质量规则变化时递增版本，自动使用新键。

## 5. 两种回放模式

### 5.1 标准 Bar 回放（快速）

该模式内部值为 bar_next_open，替代新任务的 bar_close 默认行为：

~~~text
Bar N 完成 → 调用 on_bar → 生成订单并进入待执行队列
Bar N+1 开始 → 以 open 价格和滑点生成成交
Bar N+1 完成 → 再调用 on_bar
~~~

价格规则：

~~~text
买入成交价 = 下一根 Bar.open × (1 + slippage)
卖出成交价 = 下一根 Bar.open × (1 - slippage)
~~~

成交价按标的最小价格单位处理，继续应用资金、可卖数量、最小下单数量和手续费规则。跨午休时，上午尾 Bar 的订单使用下午首根 Bar 开盘；回测结束后没有后续 Bar 的普通订单记录为未成交。日内尾盘强平仍按既有独立规则处理。

bar_close 保留为历史任务兼容值，不改变既有记录或结果；新建任务默认 bar_next_open。历史页面展示保存时的原始成交模式，不将旧记录重命名为新规则。

### 5.1.1 A 股费用档案

当前单一手续费率改为按方向计算的费用档案。后端全局默认值为：

~~~text
commissionRate（佣金率） = 0.00008
transferFeeRate（过户费率） = 0.00001
stampDutyRate（印花税率） = 0.0005，仅卖出
minimumCommission（最低佣金） = 5.00 元
~~~

买入费用为佣金加过户费，卖出费用为佣金加过户费加印花税。每个有实际成交的委托按订单累计成交额收取一次最低佣金；完全未成交、被拒绝的委托不收费。L2 部分成交时，首笔成交先计入最低佣金，后续成交仅在累计应收佣金超过已收佣金时补差额；过户费和印花税随每笔实际成交额累加。

前端只显示“默认 A 股费用”，例如买入 0.009%、卖出 0.059%、最低佣金 5 元；本期不提供高级设置、个人费用档案或任务级费用覆盖。费用档案由管理员维护为系统全局配置，后续新任务统一使用该值。

每次任务将实际采用的全局费用档案版本和每笔订单的费用拆分写入结果快照。管理员后续调整全局默认值只影响新任务；历史任务继续按保存时的旧费用口径展示和复现，不自动重算。

### 5.2 L2 盘口回放（真实）

该模式内部值继续使用 l2_quote。它与标准模式共享 Resolver 选出的 Bar，但 on_bar 后仍读取后续三秒十档快照逐档撮合。L2 模式不默认额外叠加普通 Bar 滑点，避免对点差和深度冲击重复计价。

### 5.3 前端呈现与限制

成交模式下拉框调整为：

- 标准 Bar 回放（快速）。
- L2 盘口回放（真实）。

L2 模式说明为“基于三秒十档快照，更接近真实成交，不模拟逐笔排队优先级”。标准模式说明为“已完成 Bar 产生信号，下一根 Bar 开盘价加滑点成交”。周期列表由 Resolver 的可用性结果驱动；quote 聚合可用时可展示其支持的三秒整数倍周期。

成交模式选择对所有策略类别开放。底仓增强策略在标准 Bar 模式下，仍按下一根 Bar 开盘价、滑点和费用处理其订单；在 L2 模式下，仍按后续三秒十档盘口撮合。两种模式均沿用底仓、做 T、可卖数量、最小下单数量和尾盘结算校验；前后端不得以策略类别强制改写用户选择的成交模式。

### 5.4 信号执行账本

两种模式在首次仅依赖 OHLCV 的 on_bar 信号上可以相同，但后续信号不保证相同：标准模式在下一根 Bar 开盘一次成交；L2 模式可能部分成交、未成交或撤单。策略若读取 position、cash、equity，或定义 on_quote、on_order_event，后续状态和信号都可能分叉。

不新增独立页面，页面名称继续保持“信号明细”。其内部数据与展示模型升级为统一的信号执行账本，从当前“成交记录 + 跳过信号”拼接演进为可追溯的三层关系：

~~~text
策略信号 → 委托 → 一笔或多笔成交
~~~

每条账本记录至少展示：

- 信号时间和触发来源：Bar 或 L2 事件。
- 动作、请求数量、原因和成交模式。
- 委托状态：已接受、跳过、拒绝、部分成交、已成交、撤单或未成交。
- 计划执行时点：标准模式为下一根 Bar 开始；L2 模式为后续首个可用盘口。
- 实际成交时间、成交数量、平均成交价和未成交数量。
- 跳过、拒绝、撤单或未成交原因。

标准 Bar 订单通常只有一笔成交；L2 订单可以汇总展示成交数量和成交均价，并允许展开查看多笔部分成交。K 线标注继续使用实际成交时间和价格，不能用信号时间替代实际成交点。

## 6. 实施步骤

1. 定义 BarProvider、BarSourceResolver 与统一快照元数据，梳理现有 QMT 与 L2 Provider 的重复逻辑。
2. 将 QMT K 线读取封装为 Provider，补齐标准化 start_time/end_time、来源版本和覆盖状态。
3. 让正式映射 Bar Provider、quote 临时聚合 Provider 实现同一协议，实现“单任务单来源”的选择和失败说明。
4. 复用 VersionedBarCache 缓存 quote 派生 Bar，补充跨模式命中统计和来源元数据，不写入原始盘口。
5. 在 Bar 回测内核和脚本 worker 实现待执行订单队列，使新模式按下一根 Bar 开盘、滑点和费用成交；保留 bar_close 兼容路径。
6. 将单一手续费率升级为订单级 A 股费用档案，实现管理员维护的全局默认、最低佣金与 L2 部分成交补差；本期不提供前端自定义覆盖。
7. 扩展统一信号、委托和成交结果模型；保持页面名称为“信号明细”，支持状态、计划执行时点、部分成交展开和原因展示。
8. 更新 API schema、任务快照、历史记录与前后端参数校验，切换模式名称、周期可用性、费用档案和说明；所有策略类别均可选择成交模式，不得因类别重写用户选择。同步移除现有请求模型中“底仓增强仅支持 l2_quote”和“标准模式不得设置底仓或做 T”的旧校验。
9. 同步更新 docs/玄龄回测系统使用手册.md，明确 on_bar 时机、Bar 时间语义、标准成交时序、两种模式差异、费用规则和账本字段。
10. 编写测试并进行真实数据回测验证和性能对比。

## 7. 验证与验收

### 7.1 数据与缓存

1. 同一标的、日期、周期首次 quote 聚合与再次 Redis 命中，逐字段 Bar 和质量元数据完全一致。
2. 3m、45m 从 09:30:00、13:00:00 分别分桶，午间不跨桶；1d 仅汇总连续竞价时段。
3. 三类 Provider 均输出完整来源快照；覆盖不足不得混源。
4. 映射或聚合版本变化后，不命中旧 Redis 键。

### 7.2 标准 Bar 成交时序

1. Bar N 收盘触发买入时，成交价来自 Bar N+1 的 open，不能使用 Bar N 的 close。
2. 买卖滑点方向正确，手续费、最小下单数量、资金和可卖校验保持有效。
3. 上午末尾订单在下午首 Bar 开盘处理；回测结束无后续 Bar 时普通订单不成交。
4. 新 bar_next_open 任务与历史 bar_close 任务可分别回放，历史结果不改变。
5. 标准模式账本同时展示信号时间、下一根 Bar 的计划执行时间和实际成交时间。
6. L2 部分成交、撤单和拒绝均能从信号追溯到委托和成交明细；汇总数量不得掩盖未成交余额。
7. 默认费用档案下，买入费用为 0.009%，卖出费用为 0.059%；有成交的订单最低佣金为 5 元，未成交订单费用为 0。
8. 全局费用调整只影响后续新任务；任务快照能够精确复现其创建时采用的费用档案。

### 7.3 L2 回归与性能

1. 相同 Bar 来源、策略和参数下，L2 的 on_bar 时间和信号内容不因 Provider 抽象变化而改变。
2. L2 订单仍仅使用严格晚于生效时间的十档快照成交。
3. 首次和第二次 quote 聚合运行均记录 barReadMs、缓存命中交易日和总耗时。
4. L2 只比较 Bar 读取耗时，不将盘口成交读取耗时归因于本方案。

## 8. 风险、自审与回滚

| 风险 | 处理方式 |
| --- | --- |
| 新旧 Bar 时间语义混淆 | Provider 强制输出 start_time/end_time，策略 time 固定为完成时点，并以成交时序测试约束。 |
| 下一根开盘成交仍发生前视 | 成交置于下一根 Bar 开始、on_bar 之前；不得在 Bar N 完成时直接成交。 |
| QMT 与 quote 价格不同 | 任务级单来源选择并记录来源快照；不在单任务中混用。 |
| quote 缓存过期或 Redis 重启 | 仅影响性能，回源 ClickHouse 重建；Redis 不作为真源。 |
| 正式 Bar 表字段未定 | 通过适配器隔离，字段和时间语义未验证前不启用。 |
| 历史 bar_close 记录失真 | 保留旧值和旧执行路径，仅新任务默认 bar_next_open。 |
| L2 读取仍然慢 | 明确不纳入本方案，后续独立处理。 |

发布采用分步方式：先接入统一 Provider 并保持旧 bar_close 行为进行来源回归；再启用 bar_next_open 默认模式；最后更新前端默认值。若新链路异常，可恢复新任务默认值为 bar_close，不需迁移或重算历史任务。

## 9. 服务器发布与兼容性

### 9.1 数据库与历史任务

现有 backtest_run.fill_model 为 varchar，requested_params、params_snapshot、market_data_snapshot 和 result_json 均为 JSON 类型；新增 bar_next_open 可以直接保存，不需要修改或迁移旧的 bar_close、l2_quote 历史数据。服务端必须同时兼容三种值：

- bar_close：仅用于既有历史任务的结果读取和复现。
- bar_next_open：新标准 Bar 回放。
- l2_quote：L2 盘口回放。

若实现过程中确需增加数据库字段，必须新建幂等迁移文件并通过既有 migrate 服务执行；不得修改已执行迁移，也不得以应用启动时 DDL 代替迁移。

### 9.2 容器发布顺序

本方案会同时修改 backend、strategy-worker、l2-runner 和 frontend。服务器发布必须使用既有 deploy-server.sh，由该脚本执行迁移并重建上述四个服务；不得只重启 backend 或只更新前端。Redis 的容器配置本轮不变，部署脚本不会主动重启 quant-backtest-l2-redis，既有 Bar 缓存可保留。

发布前应检查 l2_backtest_job 中是否存在 queued 或 running 任务。running L2 任务会因重建 l2-runner 中断，不得在未知任务状态下直接发布；应等待完成、由用户取消，或明确标记为发布中断后再执行部署。

### 9.3 配置与缓存兼容

全局 A 股费用档案使用后端默认值并允许由服务器 deploy/.env 覆盖；启动时校验所有费率非负、最低佣金非负。实际生效值必须写入任务快照。deploy/.env 是服务器私有文件，发布不得用仓库的 .env.example 覆盖它。

若统一 Bar 缓存的值结构、来源标识或分桶规则变化，必须递增 aggregationVersion 或调整缓存命名空间。旧 Redis 键保留至 TTL 或淘汰，不得以新代码读取旧结构。

### 9.4 发布后验收与回滚

发布后依次执行：

1. 健康检查：backend、strategy-worker、l2-runner、frontend 均为 healthy。
2. 标准模式：运行一个 QMT 覆盖完整的 1m 或 5m 回测，确认下一根 Bar 开盘成交、费用和信号明细正确。
3. quote 聚合：运行一个 3m 或 45m 回测两次，确认首次回源、第二次 Bar 缓存命中且结果一致。
4. L2 模式：运行一个小区间回测，确认 Bar 来源快照、严格后续盘口成交和既有结果未退化。
5. 历史兼容：打开一条 bar_close 和一条 l2_quote 历史任务，确认结果和详情仍可读取。

若标准模式异常，可先将前端默认成交模式恢复为 bar_close，并保留新 Provider 代码供定位；若缓存协议异常，递增版本使其回源重建；若 L2 出现回归，恢复前一版本镜像并按任务状态审计中断任务。
