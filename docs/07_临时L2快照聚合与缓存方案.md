# 临时 L2 快照聚合与缓存方案

## 1. 背景与结论

正式 L2 Bar 表尚未建立，导致 `l2-runner` 无法配置 `L2BarProvider（L2 Bar 数据源）`，L2 任务会在读取数据前失败。等待正式表会阻塞基础 L2 回测验证。

临时方案直接读取 `quant.tick_quote` 的三秒十档快照，在 ClickHouse 内按交易时段聚合策略 Bar；`quant.tick_data` 仍只读取 `type='trade'` 的逐笔成交，用于被动限价成交确认。聚合 Bar 是确定性重复计算，按标的、交易日和周期写入 Redis 缓存。

该方案只面向已收盘的历史交易日。基于“历史 L2 数据只增量追加、通常不修订”的业务约束，已收盘日期可视为稳定输入；Redis 只是可淘汰的派生物，不是行情真源或回测结果真源。

## 2. 目标与边界

### 2.1 目标

- 在正式 Bar 表就绪前，使 `l2_quote` 能直接基于 `quant.tick_quote` 运行。
- 支持 `1m`、`3m`、`5m`、`15m`、`30m`、`45m`、`60m`、`1d`。
- 仅在 ClickHouse 端聚合，不把整日三秒快照拉入 Python 后聚合。
- 对已收盘交易日缓存聚合结果；缓存丢失可无副作用地回源重建。
- 保留现有 L2 成交时间线：Bar 结束触发 `on_bar`，订单仅使用严格晚于 Bar 结束时间的快照和成交。
- 不修改远程原始表，也不改变后续正式 L2 Bar 表的接入契约。

### 2.2 非目标

- 不把 Redis 当作原始行情、任务状态或最终结果存储。
- 不缓存 `tick_data` 原始事件，也不在 Redis 保存完整十档快照。
- 不为交易中的当日数据提供正式回测；当日请求明确拒绝或后续单独设计短 TTL 模式。
- 不以此替代正式 Bar 表；正式表就绪后，临时 Provider 仅作为回退或调试路径。

## 3. 数据契约与聚合规则

### 3.1 输入与顺序

- 快照源为 `quant.tick_quote`；适配器读取时间、最新价、累计量额、买卖十档价格与数量。
- 成交源为 `quant.tick_data`；适配器强制过滤 `type='trade'`，委托新增和撤单不得进入成交确认。
- `tick_quote` 没有独立快照序号时，先逐日校验 `(symbol, trade_date, datetime)` 唯一；仅在唯一时使用毫秒时间作为稳定快照序号。发现重复时间戳即拒绝该日期，不以数据库物理行顺序撮合。
- 所有价格、数量、金额的缩放系数由受控 `SourceMappingProfile（数据源映射配置）` 提供，并在接入时抽样校验；未知单位不得猜测。

### 3.2 时段分桶

只处理连续竞价时段：`09:30:00–11:30:00`、`13:00:00–15:00:00`。上午、下午各自从时段起点分桶，禁止跨午休：

- 上午桶锚点为 `09:30:00`；下午桶锚点为 `13:00:00`。
- `45m` 的时段尾部保留不足周期的 Bar，并记录 `actual_duration_seconds（实际时长秒数）`。
- `1d` 由两个连续竞价时段共同构成，且不包含集合竞价或收盘后快照。

### 3.3 OHLCV、量额与质量

- `open/high/low/close` 使用桶内有效 `last_price` 的首值、最大值、最小值、末值。
- `volume/amount` 以交易日累计字段的相邻快照增量求和；窗口函数必须带入桶前一个快照，避免只用桶内 `max-min` 漏掉首个快照前的成交增量。
- 每根 Bar 输出 `snapshot_count（快照数量）`、`max_gap_ms（最大快照间隔毫秒）`、`valid_price_count（有效价格数量）`、`actual_duration_seconds` 和 `quality（质量状态）`。
- 无有效价格为 `empty`；存在非正增量、快照间隔超过阈值或价格缺失则为 `partial`；其余为 `complete`。
- 默认 L2 回测只接受 `complete`。`partial`/`empty` 必须失败，不降级为 Bar 收盘价成交。

## 4. Redis 缓存策略

### 4.1 缓存键和值

缓存键：

```text
l2bar:v2:{aggregation_rule_version}:{mapping_version}:{symbol}:{trade_date}:{period}
```

缓存值包含标准化 Bar 列表、质量指标、输入表名、聚合规则版本、映射版本、生成时间和“已收盘且仅增量追加”的来源说明。

`aggregation_rule_version（聚合规则版本）` 在任何分桶、量额、质量规则变化时递增；`mapping_version（映射版本）` 在字段映射或缩放变化时递增。二者变化会自动使用新键，不复用旧派生结果。

### 4.2 写入、命中与失效

1. 仅允许交易日早于当前交易日的请求读写缓存。
2. 命中后直接返回 Bar 与质量元数据；缓存被 Redis 淘汰、过期或不可用时回源 ClickHouse 聚合。
3. 聚合成功且质量元数据完整后才写入缓存；失败、`partial` 或 `empty` 结果不写入可交易缓存。
4. 初始 TTL 设置为 30 天，并沿用 `allkeys-lru` 容量淘汰；缓存淘汰只影响速度，不影响结果语义。
5. 极少数历史订正时，由管理员执行“标的 + 交易日”精准失效；同时递增临时聚合规则或映射版本，避免旧键误命中。

### 4.3 可审计性

每次 L2 回测结果保存缓存是否命中、缓存键、输入表、`aggregation_rule_version`、`mapping_version`、Bar 质量汇总和运行时间。该信息能解释结果所用的聚合逻辑；严格历史复现仍以“历史日不修订”的业务承诺为前提，正式表上线后应改用其批次版本。

## 5. 运行流程

```text
l2-runner 按交易日处理
  ├─ 判断日期是否已收盘
  ├─ Redis 读取临时聚合 Bar
  │   ├─ 命中：校验质量后发送 worker
  │   └─ 未命中：ClickHouse 聚合 → 校验 → 写 Redis → 发送 worker
  ├─ 分页读取 tick_quote 与 type='trade' 的 tick_data
  ├─ 按 (time, priority, sequence) 合并为有界块
  └─ strategy-worker 会话执行 on_bar 与 L2ExecutionEngine
```

按日缓存只缓存 Bar；十档快照与逐笔成交仍按块流式读取，以保证盘口成交和被动成交确认使用原始顺序数据。

## 6. 实施步骤

1. 补充临时 `tick_quote` / `tick_data` 映射配置，并以 `DESCRIBE TABLE` 和抽样数据验证字段、缩放、时间与唯一性。
2. 在 `L2QuoteProvider` 增加 ClickHouse 时段对齐聚合查询，输出 `NormalizedBar（标准化 K 线）` 与质量元数据。
3. 增加日内前序累计量额窗口、快照间隔计算、午休边界和 `45m` 尾部 Bar 的单元测试。
4. 将 `VersionedBarCache` 调整为临时缓存键策略，增加已收盘日期保护、30 天 TTL、命中/回源元数据和精准失效接口。
5. 让 `l2-runner` 在正式 Bar 映射缺失时选择临时聚合 Provider；正式映射存在时仍优先正式 Bar 表。
6. 在任务结果和前端历史记录中展示 Bar 来源为“临时快照聚合”、缓存命中状态、质量汇总与失败原因。
7. 使用一个标的、2026-06-01 至 2026-06-03 的范围完成真实集成验证，再扩展日期和标的规模。

## 7. 验证标准

- 所有固定周期的分桶均从 `09:30:00` 或 `13:00:00` 对齐，午休不跨桶。
- 45 分钟尾部 Bar 的结束时间和实际时长正确。
- 桶前累计量额增量被计入，结果不因首个快照位置而少算。
- 相同请求首次回源、再次命中缓存得到逐字段相同的 Bar。
- 变更聚合规则或映射版本后，不会命中旧缓存键。
- 当日请求、重复快照时间、价格单位异常、`partial`/`empty` Bar 都被明确拒绝。
- `tick_data` 中 `order`、`cancel` 事件不会进入被动成交数量。
- 三日单标的集成回测记录缓存命中、原始读取量、聚合耗时和总耗时；不预设性能结论，以实测作为后续容量参数依据。
- 现有 `bar_close` 回测与正式 L2 Bar Provider 回归通过。

## 8. 自审与风险

- 当前三秒快照并非完全连续，质量阈值需以实测分布确定；若阈值过严会拒绝过多历史日，过松会降低撮合可信度。
- 将毫秒时间当作快照序号只能在唯一性验证通过时成立；重复时间戳必须拒绝，不能静默排序。
- 累计量额字段的重置和盘中异常需通过样本验证；错误的量额计算会影响策略指标，即使 OHLC 正确。
- Redis 的 30 天 TTL 与 LRU 是性能策略，不是数据保留策略；淘汰后必须可回源重建。
- 若未来发生历史订正，管理员必须精准失效缓存或递增版本；该临时方案不声称在无版本原表上自动识别订正。
- 正式 Bar 表建立后，应以其质量状态和版本为主，临时聚合结果不得与正式表混用在同一任务内。
