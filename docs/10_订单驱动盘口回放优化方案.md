# 订单驱动盘口回放优化方案

## 1. 背景与结论

当前基础 L2 回测仅使用 `quant.tick_quote` 的十档盘口快照和 Bar，不再默认读取 `quant.tick_data`。在本地结果中，2026-06-01 至 2026-06-03 的基础 L2 回测耗时约 2.9 秒；此前同时读取逐笔数据的版本耗时约 35 至 38 秒，主要瓶颈是逐笔数据读取，而不是撮合计算。

即使移除逐笔数据，现有实现仍会将交易日内的全部 3 秒快照逐条发送给 L2 worker。以每个交易日约 4,740 条快照估算，三年回测仍会读取和跨进程传递数百万条无交易意义的盘口记录。

本方案将基础 L2 模式改为**订单驱动的盘口回放**：策略没有待成交订单时，只触发 Bar，不读取中间盘口；策略产生主动订单后，才严格按时间顺序读取该订单生效后的盘口，直至订单完全成交、被取消或到达下一个 Bar / 收盘边界。

推荐结论：首版只覆盖市价与可成交的主动委托，以 `tick_quote` 作为成交依据。逐笔成交、被动限价单和盘口排队模型保留给后续独立的精细撮合模式，不能在本次改造中以不完整语义混入基础模式。

## 2. 目标、边界与不变量

### 2.1 目标

1. 在不改变基础 L2 主动成交语义的前提下，避免回放无待成交订单期间的盘口快照。
2. 保持 Bar 策略的 `on_bar` 时机、严格无前视、十档盘口吃单、部分成交和日终处理不变。
3. 保持前端 API、任务状态、结果结构与现有策略脚本兼容。
4. 输出可量化的性能指标，使每次回测能说明耗时发生在哪里、跳过了多少盘口。

### 2.2 本次范围

- 数据源：`quant.tick_quote` 的 3 秒十档盘口快照。
- 委托类型：市价单及可立即成交的主动委托。
- 成交模型：订单在 Bar 完成后生效，严格使用其后第一条及后续有效盘口；可跨多个快照部分成交。
- 策略触发：按既有 Bar 周期调用 `on_bar`。
- 强平：保持日内模式的收盘前平仓规则，按需要读取最后一条有效盘口。

### 2.3 明确不在本次范围

- `quant.tick_data` 的逐笔成交、委托、撤单驱动回放。
- 被动限价单的挂单、排队位置、撤单优先级与撮合概率。
- 开盘集合竞价、午间休市、涨跌停特殊成交规则的精细微观模拟。
- 新增 Redis 缓存、ClickHouse 表、数据源适配器字段改造或前端交互改造。

后续若启用被动限价单，必须单独引入逐笔事件及队列模型；不能复用本方案的“跳过无订单盘口”逻辑来宣称真实排队撮合。

## 3. 回放时序与成交语义

### 3.1 时间顺序

交易日内事件必须遵循以下顺序：

1. 处理当前 Bar 结束时间之前、且仍有待成交订单所需的盘口。
2. 将完成的 Bar 传入 worker，触发策略 `on_bar`。
3. 该次 `on_bar` 产生的订单以 Bar 结束时间为严格排他边界生效。
4. 仅在有待成交订单时，读取 `datetime > effective_at` 的后续盘口；盘口与下一个 Bar 的先后关系仍按时间排序。
5. 到收盘边界后执行既有日终取消或强平规则。

例如 09:31 完成的 1 分钟 Bar 产生买入订单，09:31:00 的盘口不得成交该订单；只能从严格晚于该时间的下一条有效盘口开始撮合。若 09:31:03 的盘口不足以完成成交，则继续读取 09:31:06、09:31:09 等快照，直到订单完成、失效，或先到达下一根 Bar 的时间边界。

### 3.2 跳过盘口的正确性

没有待成交订单时，中间盘口不会改变持仓、现金、已成交订单或策略输入（策略只由 Bar 触发），因此可以不读取。下一根 Bar 仍从预聚合或适配后的 Bar 数据触发，不依赖被跳过的逐条盘口。

以下场景不得跳过盘口：

- 有尚未完成的订单，包括十档深度不足导致的部分成交订单。
- 收盘前需要按盘口执行日终强平，且账户仍有持仓。
- 后续引入依赖逐快照策略回调或被动限价单时；该模式将改为全量事件回放，不适用本方案。

### 3.3 订单状态

worker 对每次 Bar 或盘口处理后返回一个明确的订单需求状态：

- `idle`：没有待成交订单，runner 不再查询下一条盘口。
- `waiting_quote`：存在待成交订单，runner 继续查询严格晚于当前游标的下一条有效盘口。
- `day_end_required`：日内收盘前仍有持仓，需要读取收盘前最后一条有效盘口用于强平。

订单驱动状态只描述是否需要行情，不把 ClickHouse 连接、查询凭证或数据源细节传入策略 worker。

## 4. 架构设计

### 4.1 数据源层

在 L2 行情提供器中增加按时间游标读取的接口，替代基础 L2 运行路径中的整日分页扫描：

- `next_quote_after(symbol, trade_date, cursor_exclusive, before_exclusive)`：返回指定区间内时间最早的一条有效盘口。
- `last_quote_before(symbol, trade_date, before_exclusive)`：仅供日终强平取得收盘边界前最后一条有效盘口。

查询必须采用 keyset 条件，而非 `OFFSET`：以交易日、标的、时间作为过滤与排序条件，只选择撮合所需字段。`quant.tick_quote` 当前排序键为 `(trade_date, symbol, datetime)`，该访问方式可以利用现有主键顺序。

临时快照表仍需保持“同一标的、交易日、时间唯一”的约束。若未来上游出现相同时间戳的多条快照，则适配器必须提供稳定的序列字段；在该字段未定义前，基础 L2 模式应明确拒绝该数据，而不是用不确定顺序撮合。

### 4.2 L2 runner

runner 成为唯一的时间调度方，按“Bar 事件 + 按需盘口事件”推进单个交易日：

1. 读取当天已适配的 Bar 序列，不预读整日盘口。
2. 到达一根 Bar 时，先处理该 Bar 结束前因旧订单而需要的盘口；随后调用 worker 的 Bar 处理接口。
3. worker 返回 `waiting_quote` 时，runner 使用时间游标查询下一条盘口；如果该盘口位于下一根 Bar 之前，则发送给 worker 并继续判断订单状态。
4. 若下一条盘口不早于下一根 Bar，则先处理下一根 Bar；未成交订单继续保留，之后仍按全局时间顺序读取盘口。
5. 没有待成交订单时，runner 直接推进到下一根 Bar，不查询被跳过区间的盘口。
6. 收盘时仅在确有仓位需要日终处理时读取最后一条有效盘口；无仓位时不额外查询。

该循环不会为了性能调整事件顺序。特别是部分成交订单必须连续消费后续盘口，不能因为中间没有新的 Bar 信号而跳过。

### 4.3 Worker 与撮合引擎

现有批量 `process_l2_chunk` 内部会合并 Bar 和盘口后排序。本次拆分为语义更明确的会话接口：

- `process_l2_bar(session_id, bar)`：调用策略、提交新订单、返回订单需求状态。
- `process_l2_quote(session_id, quote)`：只处理仍待成交的主动订单、更新成交与账户状态、返回订单需求状态。
- `finish_l2_day(session_id, final_quote)`：执行收盘取消或强平，并记录当天权益。

撮合引擎新增只读状态方法，例如 `has_pending_orders()` 与 `requires_day_end_quote()`，由服务层转换为订单需求状态；策略脚本不直接访问内部订单集合。

保留现有撮合不变量：

- `allow_short` 直接取前端传入值，不使用隐式默认值覆盖。
- 十档买卖价继续按数据适配器确定的比例换算；不能将盘口整数价与成交价比例混用。
- 科创板 `688`、`689` 标的开仓最小数量为 200 股，后续数量按既有规则处理。
- 同一行情快照可按可见十档深度产生部分成交；未成交余量保留至后续盘口或日终处理。

### 4.4 权益、结果与兼容性

当前逐 Bar 保存权益曲线会使长周期 L2 结果无谓膨胀。本方案将权益持久化粒度收敛为每日收盘权益与最终权益；净值、收益、最大回撤继续据此计算。结果适配器需继续兼容历史任务中已有的逐 Bar 权益数组。

成交明细、信号明细和拒单原因仍完整保存，因为它们是验证回测行为所必需的数据，不能为了性能被省略。前端接口与页面不修改；它们继续从既有任务结果字段读取概览、权益曲线和明细。

结果快照新增以下可追溯字段：

- `executionMode`：固定为 `order_driven_quote`。
- `quoteSource`：实际使用的快照表、适配器版本及价格比例版本。
- `performance`：Bar 数、实际读取盘口数、盘口查询次数、worker 调用次数、Bar/盘口数据源耗时与 worker 耗时。为避免重新全表扫描，未读取盘口不额外计算全量计数。

## 5. 实施步骤

1. 为 L2 行情提供器增加时间游标读取与收盘最后盘口读取接口；保留旧分页接口供历史诊断使用，不再由基础 L2 路径调用。
2. 在 worker 服务协议中增加 Bar、盘口、日终三个会话操作及订单需求响应结构，并为异常、无有效盘口和会话结束定义明确错误码。
3. 将 L2 撮合引擎的批量事件处理拆为 Bar 和盘口处理入口，保持现有委托、成交、费用、做空权限、最小交易单位与价格比例规则。
4. 重写 L2 runner 的日内事件循环，以 Bar 为主时钟、以订单状态决定盘口查询，并在 Bar 与盘口边界执行严格时间排序。
5. 将权益曲线写入调整为日终粒度，更新结果归一化逻辑以兼容旧任务记录。
6. 记录并持久化性能快照，在任务完成与失败时均保留已知计数和耗时，方便定位数据源或 worker 瓶颈。
7. 更新使用手册中的基础 L2 模式说明、主动成交范围、无前视边界、已不支持的被动限价行为及性能指标释义。

## 6. 验证方案与验收标准

### 6.1 单元测试

- 09:31 Bar 下单时，09:31:00 盘口不能成交，09:31:03 盘口可以成交。
- 无待成交订单的两个 Bar 之间不调用盘口读取接口。
- 十档不足时订单部分成交并继续请求下一条盘口；全部完成后停止读取。
- 下一条盘口晚于下一根 Bar 时，下一根 Bar 必须先触发，不能为了成交而打乱时间。
- 收盘有仓位时仅查询一次最后有效盘口并强平；无仓位时不查询。
- 多空权限、科创板最小 200 股、价格比例、费用和拒单原因保持现有行为。
- 旧任务的逐 Bar 权益结果经归一化后仍能展示概览、回撤与历史曲线。

### 6.2 集成与回归测试

- 构造一个小型固定数据集，同时以“全量快照回放参考实现”和“订单驱动回放”运行；在只含主动订单的策略下，订单、成交、现金、持仓、日终权益、收益与回撤必须完全一致。
- 对 688981.SH、2026-06-01 至 2026-06-03 运行基础 L2 回测，记录实际耗时和性能快照；不以预估时间代替真实基准。
- 验证前端概览、历史任务、权益回撤、成交明细、信号明细均可正常显示。
- 分别验证有交易、无交易、部分成交、拒单、允许做空与日终强平的任务结果。

### 6.3 性能验收

性能验收以同一策略、同一时间范围、同一数据版本的实测结果为准，而非固定秒数承诺。必须同时满足：

- 无订单区间的 `quotesFetched` 为 0，且不会发起盘口查询。
- 有订单时只读取完成该订单所需的连续盘口，以及必要的日终盘口。
- 与全量快照参考实现在主动订单范围内的结果一致。
- 任务结果包含足以解释耗时的性能快照。

## 7. 风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 时间边界错误导致前视成交 | 使用严格排他条件 `quote_time > effective_at`；将边界案例固化为单元测试。 |
| 部分成交订单被错误跳过 | 只要订单余量存在，就连续按时间游标读取后续盘口。 |
| 盘口与下一根 Bar 的顺序被打乱 | runner 比较下一条盘口与下一根 Bar 时间，始终先处理较早事件。 |
| 相同时间戳快照顺序不稳定 | 要求数据源提供稳定序列；没有序列时拒绝该数据源用于基础 L2 撮合。 |
| 结果缩减后影响页面 | 只收敛权益曲线到日终；信号与成交明细完整保留，并对旧结果兼容。 |
| 被误解为真实挂单撮合 | 前端模式说明和使用手册明确标注“主动成交盘口回放”，被动限价单另行实现。 |
| 行情读取仍异常缓慢 | 性能快照分离数据源耗时与 worker 耗时；再依据实测决定是否增加 ClickHouse projection 或物化视图。 |

## 8. 不在本次提前实施的优化

若本方案完成后的实测仍无法满足长周期回测需求，再基于性能快照评估以下后续事项：

1. 对已确认的 `symbol + trade_date + datetime` 查询模式，在远程 ClickHouse 上评估 projection 或物化视图；先用 `EXPLAIN indexes = 1` 和真实数据验证，再决定是否写入远端数据库。
2. 将常用周期 Bar 的离线聚合表接入数据适配器，避免回测时重复从快照生成 Bar。
3. 建立独立的逐笔事件 / 被动限价撮合模式，定义成交、委托、撤单字段与队列假设后再实施。

这些事项不包含在本计划的代码改动中，避免将基础主动成交性能优化与真实排队撮合混为一项不可验证的改造。
