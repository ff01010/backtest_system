# 执行算法层与 L2-TWAP 一期方案

日期：2026-08-22  
状态：已实施（本地验证通过，待真实行情回测与服务器发布验证）

## 1. 背景与结论

当前策略脚本在 `on_bar(bar, state)` 或 `on_quote(quote, state)` 中直接返回买卖动作和数量，回测引擎随即按当前成交模式完成撮合。该方式只能表达“何时、买卖多少”，无法复用地表达“如何在一段时间内执行一笔较大委托”。若将 TWAP、VWAP 等拆单逻辑写入策略脚本，会导致策略作者重复处理交易时段、最小交易单位、部分成交、未完成订单和 L2 撮合，且相同策略难以公平比较不同执行方式。

本期引入独立的 `ExecutionAlgorithm（执行算法）` 层：策略只产生 `ParentOrder（母单）`，执行算法将母单拆成 `ChildOrder（子单）`，再交由现有撮合器处理。首期实现 `immediate（立即成交）` 与 `twap（时间加权平均价格）`，并只对 L2 盘口回放开放 TWAP。标准 Bar 回放首期继续使用立即成交，避免在低频 OHLCV 数据上制造 L2 级拆单精度的假象。

VWAP、POV、Iceberg、Adaptive 和 QMT 实盘适配不在本期实施范围，但必须能够以新增算法实现的方式接入，而不修改策略脚本接口或核心回测状态机。

## 2. 目标、范围与非目标

### 2.1 目标

1. 建立可注册、可配置、可追溯的执行算法公共框架。
2. 将既有“一次性立即成交”收敛为 `immediate` 算法，保持现有结果语义。
3. 在 L2 盘口回放中实现无前视的 TWAP 子单计划与十档盘口撮合。
4. 前端将执行算法作为单次回测的执行条件配置，不与策略逻辑参数混淆。
5. 保存算法与参数快照，并在信号明细中追溯“策略信号 → 母单 → 子单 → 成交”。
6. 为 VWAP、POV、Iceberg、Adaptive 及 QMT 实盘适配提供稳定扩展点。

### 2.2 本期范围

- 新增执行算法领域模型、注册表、参数校验和执行运行时。
- 实现 `immediate` 和 L2 `twap`。
- 在 L2 回放中处理子单计划、部分成交、撤销、交易时段、午休、收盘和异常盘口。
- 前端回测参数增加“执行方式”及 TWAP 动态参数。
- 任务参数快照、结果明细、信号可视化和历史任务展示兼容。
- 单元、回归、前视、性能和服务器发布验证。

### 2.3 非目标

1. 不在策略脚本中开放任意自定义拆单代码或新增策略回调。
2. 不在标准 Bar 回放中提供所谓“精确 TWAP/VWAP”；本期标准 Bar 仅支持立即成交。
3. 不实现 VWAP、POV、Iceberg、Adaptive 或 QMT 实盘下单。
4. 不改变 Bar 信号产生时机、现有 L2 十档盘口撮合规则、底仓/T+0、费用、持仓或收益统计语义。
5. 不用三秒 Quote 快照重建交易所订单排队、逐笔成交路径或真实市场 VWAP。
6. 不修改 ClickHouse 原始行情表、Redis 容量策略或服务器私有 `deploy/.env`。

## 3. 概念与职责边界

### 3.1 订单层级

```text
策略信号
  ↓
ParentOrder（母单：方向、目标数量、产生时间、原因）
  ↓
ExecutionAlgorithm（执行算法）
  ↓
ChildOrder（子单：计划时点、目标数量、价格约束）
  ↓
标准 Bar 撮合器 / L2 十档盘口撮合器
  ↓
Fill（实际成交）与订单状态
```

`ParentOrder` 是用户策略一次交易意图的唯一载体；`ChildOrder` 是系统执行算法产生的内部委托。策略不能直接控制子单时间表，也不能绕过引擎调用撮合器。

### 3.2 组件职责

| 组件 | 职责 | 不负责 |
| --- | --- | --- |
| 策略脚本 | 判断开平仓时机、方向、目标数量和原因。 | TWAP 拆单、盘口轮询、部分成交和撤单。 |
| 执行算法层 | 创建母单执行计划，按市场事件生成子单，管理剩余数量和完成状态。 | 直接读取 ClickHouse、Redis 或写 PostgreSQL。 |
| L2 回测运行时 | 提供严格有序的后续 Quote，调用执行算法并送入撮合器。 | 改写策略交易意图。 |
| 撮合器 | 使用现有十档盘口规则处理子单成交、费用、持仓和订单事件。 | 决定何时拆单。 |
| 前端 | 选择执行算法并填写其参数，展示任务快照与结果。 | 实现拆单或计算成交结果。 |

## 4. 目标架构

建议新增以下后端模块，不将实现放入 `backend/strategies/`：

```text
backend/
  execution/
    contract.py          # 母单、子单、计划、上下文和统一接口
    registry.py          # 算法注册、参数 schema 与校验
    runtime.py           # 计划创建、推进、完成、取消和序列化
    algorithms/
      immediate.py       # 立即成交
      twap.py            # L2-TWAP
```

运行链路如下：

```text
策略 on_bar / on_quote
  ↓ 返回 action、quantity、reason
回测运行时转换为 ParentOrder
  ↓
ExecutionRuntime（执行算法运行时）
  ├─ immediate：生成一个立即可撮合子单
  └─ twap：按时间计划生成多笔子单
  ↓
L2 Matcher（十档盘口撮合器）
  ↓
订单事件、成交、账本、结果与信号明细
```

执行算法层必须被标准 Bar runner 与 L2 runner 共用接口，但本期仅允许 L2 runner 实例化 `twap`。这样后续增加标准 Bar 的近似执行规则时，不需要重做数据模型或前端任务快照。

## 5. 公共契约

### 5.1 策略接口保持不变

策略仍返回现有格式：

```python
return [{
  "action": "buy_open",
  "quantity": 10000,
  "reason": "突破入场",
}]
```

策略可选返回 `executionHint（执行偏好）`，但该字段仅作为兼容未来策略的提示，不得覆盖用户本次回测选择的执行算法。首期不要求、也不依赖策略返回该字段。

### 5.2 执行算法接口

`ExecutionAlgorithm` 至少提供以下职责：

```python
class ExecutionAlgorithm:
  algorithm_id: str
  parameter_schema: dict[str, object]

  def create_plan(self, parent_order, context):
    """信号产生后创建执行计划。"""

  def on_market_event(self, plan, market, context):
    """在 Bar 或 Quote 到来时返回本次应提交的子单。"""

  def on_fill(self, plan, fill, context):
    """依据成交更新计划状态和剩余数量。"""
```

实际代码必须补全 Python 类型注解；上述片段仅用于说明接口职责。

### 5.3 算法参数与任务快照

任务请求新增：

```text
executionAlgorithm（执行算法）：immediate / twap
executionParameters（执行算法参数）：按算法 schema 校验
```

新字段与成交模式独立：

- `fillModel（成交模式）`：标准 Bar 或 L2 盘口，决定可用行情和撮合器。
- `executionAlgorithm（执行算法）`：立即成交或拆单计划，决定母单如何生成子单。

创建任务后，实际生效的算法编号、参数、算法版本和默认值必须写入任务快照。历史任务没有该字段时按保存的旧即时成交语义读取，不能因新默认值改变结果。

## 6. 首期算法设计

### 6.1 immediate（立即成交）

`immediate` 为既有行为的显式算法化表示：母单生成一个可立即进入对应撮合队列的子单。它必须保持当前 L2 严格后续 Quote 撮合和标准 Bar 下一根开盘撮合语义，不得因为抽象改造改变成交价、费用、可卖校验或信号顺序。

### 6.2 twap（时间加权平均价格）

TWAP 目标是在有效执行窗口内尽量均匀完成目标数量，不保证每一笔都成交，也不承诺等同于真实市场 VWAP。

首期参数：

| 参数 | 含义 | 约束 |
| --- | --- | --- |
| `durationSeconds（执行窗口）` | 从母单生效起持续执行的秒数。 | 正整数，最小 3 秒。 |
| `intervalSeconds（拆单间隔）` | 相邻子单计划时点的间隔。 | 必须为 3 秒倍数，且不大于执行窗口。 |
| `minChildQuantity（最小子单数量）` | 单笔子单的最小数量。 | 必须符合标的最小下单数量及整数倍约束。 |
| `completionPolicy（未完成处理）` | 窗口结束的处理方式。 | 首期固定为 `cancel_remaining（取消剩余）`，前端只读展示。 |

计划规则：

1. 母单仅在严格晚于信号生效时点的首条可交易 Quote 后开始执行；不得使用产生信号的同一条或更早 Quote 成交。
2. 将目标数量按计划触发次数均匀分配；为避免尾单大量偏差，最后一笔承接舍入余数。
3. 每次触发仅生成一个子单，并由现有十档盘口撮合器决定全成、部分成交或未成交。
4. 部分成交只扣减实际成交数量；未成交数量继续作为母单剩余数量，不得假定已成交。
5. 执行窗口结束后，未完成余额标记为已取消，不进行收盘强制追价，不得擅自改变为立即成交。
6. 子单数量必须遵守 A 股最小交易单位、科创板规则、可用现金、可卖数量、底仓和 T+0 既有校验；校验失败原因写入明细。

### 6.3 交易时段与异常行情

1. 只允许连续竞价时段生成和撮合子单；午休期间暂停计时或跳过至下午连续竞价，具体选择必须固定为“按有效交易秒计时”，并保存到算法版本说明。
2. 母单在收盘前不足一个完整执行窗口时，按可用交易秒缩短计划；不能生成收盘后的子单。
3. 涨跌停、无有效买卖盘、价格为零或盘口深度不足时，沿用现有 L2 撮合拒绝/部分成交语义，并保留子单原因。
4. 取消任务、策略异常、数据源异常或回测结束时，所有未完成执行计划收敛为明确终态，不得遗留运行中母单。

## 7. 前端设计

### 7.1 配置位置

在策略代码编辑页右侧“回测设置”区域，置于“成交模式”之后：

```text
成交模式：标准 Bar 回放 / L2 盘口回放
执行方式：立即成交 / TWAP
```

选择 L2 盘口回放与 TWAP 时展示：执行窗口、拆单间隔、最小子单数量，以及只读的“窗口结束后取消剩余数量”说明。选择标准 Bar 回放时，只显示立即成交；若任务快照请求 TWAP，前端和后端均应拒绝并说明“TWAP 仅支持 L2 盘口回放”。

执行方式不放入策略参数区域。策略参数改变信号逻辑；执行方式改变信号后的成交路径，两者必须在界面与结果中分开呈现。

### 7.2 历史与结果展示

1. 历史回测列表和详情显示 `成交模式 · 执行算法`，例如“L2 盘口 · TWAP（10 分钟）”。
2. 概览继续显示最终成交与收益汇总，不因拆单展示大量技术细节。
3. 页面名称保持“信号明细”。每条记录可以追溯策略信号、母单状态、子单数量、实际成交数量、均价、剩余数量及取消/拒绝原因。
4. 信号可视化默认按实际成交聚合显示；展开明细后可查看同一母单对应的多笔子单成交，避免 K 线图被拆单点位淹没。

## 8. 数据库、缓存与兼容性

### 8.1 持久化

优先将 `executionAlgorithm`、`executionParameters`、算法版本及结果摘要写入现有 JSON 快照字段；若现有数据结构无法满足母单/子单的可追溯性，必须新增幂等迁移文件并由 `migrate` 服务执行，禁止修改已执行迁移或在应用启动时执行 DDL。

高频子单和 Quote 回放过程中不得逐条写 PostgreSQL。运行时在内存中聚合，任务完成、取消或失败时一次性写入受限结果；必要进度更新沿用现有固定间隔机制。

### 8.2 Redis 与 ClickHouse

本期不引入新的原始 L2 快照缓存，也不改变已有 Redis 缓存的 TTL、淘汰策略或键结构。TWAP 只复用 L2 runner 已经为待成交订单读取的 Quote 数据，禁止为了每个子单重复从 ClickHouse 发起同一区间查询。

如后续为执行算法新增 Redis 计划缓存或结果缓存，必须采用独立版本化命名空间；缓存失效只能影响性能，不能改变回测结果。

### 8.3 历史兼容

1. 历史任务缺少执行算法字段时，按其原有即时成交语义展示。
2. 既有信号明细、收益和可视化必须可读取；新增母单/子单字段不存在时以兼容视图展示。
3. 新增请求参数必须有服务器安全默认值 `immediate`，且前后端同时校验。

## 10. 验证与验收

### 10.1 正确性

1. 相同策略、参数和行情下，`immediate` 改造前后的信号、成交、费用、持仓和收益结果一致。
2. TWAP 母单只在信号生效后的严格后续 Quote 开始产生子单，不存在前视成交。
3. `intervalSeconds（拆单间隔）` 不是 3 秒倍数时，前端与后端均拒绝任务。
4. 子单全成、部分成交、无盘口、涨跌停、资金不足、可卖不足、午休、收盘和取消均有确定终态与可读原因。
5. 母单请求数量 = 实际成交数量 + 已取消数量 + 已拒绝数量，数量守恒。
6. 历史任务和现有立即成交新任务仍可正常读取、运行和展示。

### 10.2 性能

1. 空闲执行计划不触发额外 Quote 扫描；仅在存在待执行 TWAP 母单时推进算法。
2. 相同 L2 数据、无 TWAP 订单的任务相较改造前不得出现明显性能回退。
3. 同一 TWAP 母单不得因每笔子单重复读取相同 Quote 区间。
4. 信号明细增量不会导致按 Quote 逐条 PostgreSQL 写入或无界内存增长。

### 10.3 前端与可追溯性

1. 用户能明确区分“成交模式”和“执行方式”，且标准 Bar 不能误选 TWAP。
2. 历史详情可展示本次实际采用的算法、参数和版本。
3. 信号明细可从策略信号追溯到母单、子单和最终成交/未完成原因。

## 11. 发布、回滚与风险

### 11.1 发布范围

受影响服务包括 `backend`、`l2-runner`、前端，以及可能的 `strategy-worker` 接口契约和数据库迁移。必须通过 `scripts/deploy-server.sh` 同批发布；不得只重启单个容器。

发布前检查排队和运行中的 L2 任务。重建 `l2-runner` 会中断正在执行的任务，因此应等待任务完成、由用户取消，或经明确确认后标记发布中断。发布后应完成健康检查、立即成交回归、代表性 TWAP 回测、历史任务读取及错误日志检查。

### 11.2 回滚

1. 前端默认执行算法保持 `immediate`；新功能异常时可隐藏 TWAP 入口并拒绝新 TWAP 任务，不影响旧任务读取。
2. 代码回滚时保留任务快照兼容解析；已创建的 TWAP 任务不可被旧代码静默按立即成交重算。
3. 新增持久化字段或缓存结构必须版本化；回滚代码不得读取未知新结构。
4. 任务失败保留原始受控错误、任务编号和管理员诊断信息，用户可以重新提交，不自动重复执行。

### 11.3 主要风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 将策略信号与执行参数混淆 | 前端分区展示，策略接口不变，任务快照独立保存。 |
| TWAP 在低频 Bar 上产生伪精度 | 首期仅允许 L2 盘口回放使用 TWAP。 |
| 高频 Quote 造成额外扫描或数据库写入 | 订单驱动推进、数据块读取、内存聚合和限频持久化。 |
| 部分成交导致数量或费用错误 | 以实际 Fill 驱动母单余额和既有费用账本，增加数量守恒测试。 |
| 引入前视 | 强制使用严格后续 Quote，测试覆盖信号时点和首笔子单时点。 |
| 历史任务被新默认值改写 | 任务快照优先、缺失字段按旧即时语义读取。 |

## 12. 后续扩展与前置条件

### 12.1 VWAP

VWAP 需要区分“按量能曲线拆单”和“真实市场 VWAP 评估”。前者至少需要可靠历史分时成交量；后者必须使用含逐笔成交价格与成交量的 `tick_data`。三秒十档 Quote 只能表示盘口快照，缺少快照间的真实成交路径、排队顺序和完整成交量，不能严谨重建市场 VWAP。

在实施 VWAP 前必须确认：

1. `tick_data` 的每一类记录可区分成交、委托与撤单。
2. 成交价格、成交量、时间戳和单位经原始数据抽样验证。
3. 量能曲线仅使用此前交易日，或当日截至当前时点的已知数据；不得使用当日收盘后的完整成交量规划，避免前视。

### 12.2 其他算法

后续 POV、Iceberg、Adaptive 和 QMT 实盘适配均以新增 `ExecutionAlgorithm` 实现方式接入：

- POV：根据真实成交量和 `participationRate（参与率）` 决定子单数量。
- Iceberg：维护有限可见子单，成交后再补充。
- Adaptive：根据价差、盘口深度、波动和剩余时间动态调整。
- QMT 适配：将系统母单转换为 QMT 智能算法委托，仅用于实盘；历史回测仍由本系统可复现的算法执行，不能以券商黑盒结果代替。

## 13. 自审结论

本方案将“何时交易”的策略逻辑与“如何成交”的执行逻辑分离，避免让每个策略脚本重复实现高频状态机。首期选择 L2-TWAP，是因为三秒 Quote 足以提供受限但可解释的时间拆单与十档盘口撮合；同时明确排除真实 VWAP、排队优先级和 Bar 内伪精度，避免把数据能力不足包装为高真实性。

方案通过任务快照、历史兼容、订单驱动 Quote 推进、数量守恒、严格后续快照和同批发布要求控制正确性与上线风险。VWAP 被明确作为依赖 `tick_data` 质量核验的二期工作，不以不完整 Quote 数据仓促实现。
