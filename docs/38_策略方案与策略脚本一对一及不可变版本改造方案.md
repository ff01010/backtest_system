# 策略方案与策略脚本一对一及不可变版本改造方案

日期：2026-09-03
状态：已实施，待服务器迁移与发布验收

## 1. 背景与问题结论

系统页面把“策略方案”表现为一个可以编辑、保存、发布和回测的完整策略，但当前数据模型将其拆成了可变且可共享的两层：

- `strategy_config（策略方案）` 保存标的、周期、资金、回测日期和策略参数。
- `user_strategy（策略脚本）` 保存脚本身份，`user_strategy_version（脚本版本）` 保存 Python 代码。
- `strategy_config.strategy_id` 没有一对一约束，多个方案可以指向同一个脚本。
- 完整策略保存时，前端传入当前 `scriptId`，后端原地更新这份脚本的当前版本。

因此，修改任一方案的代码，会改变所有引用同一 `strategy_id` 的方案。只有拥有独立脚本的方案不受影响。

2026-09-03 对远程服务器的只读核对结果为：

- 服务器运行 `main` 分支的 `66d6c20`。
- 共有 514 条方案记录，方案 ID 和同一用户内的方案名称均唯一，不存在接口重复返回同一方案的问题。
- 514 个方案只对应 348 份非空脚本，其中 26 组存在脚本共享，另有 1 个方案的脚本引用为空。
- 最大的共享组由 22 个方案指向同一份脚本。若全部按一对一拆分，共享组需要新建 165 份独立脚本；空引用方案需先确认其应绑定的实际代码，不能在迁移中猜测。

这不是前端下拉框的 React `key`、浏览器缓存或 Nginx 问题，而是完整策略的数据归属模型错误。

## 2. 核心决策

系统将以下列关系作为强制契约：

> 一个完整策略 = 一份策略方案 + 一份独立策略脚本 + 一个明确的不可变脚本版本。

具体规则：

1. 一份脚本身份同一时刻只能归属一个方案。
2. 两个方案即使代码完全相同，也必须拥有不同的 `strategy_id`。
3. “复制策略”只复制内容，不共享可变数据库记录。
4. 修改方案 A 的代码、脚本元数据或参数，不得改变方案 B。
5. 脚本版本一旦创建就不再原地更新；任何有效变更都创建新版本。
6. 发布版本和回测任务绑定确切脚本版本，不在运行时追踪“当前最新代码”。

## 3. 目标、范围与不做事项

### 3.1 目标

1. 彻底消除“修改一个方案，其他方案代码跟着变”的行为。
2. 使页面概念、API 契约与数据库关系统一为“完整策略”。
3. 使历史发布版本和历史回测继续读取当时的快照，不被新代码改写。
4. 将远程已有共享关系幂等拆分，不删除方案、历史回测或发布快照。
5. 保留批量创建参数实验的能力，但每个实验方案都获得自己的脚本副本。

### 3.2 本期范围

- `strategy_config`、`user_strategy` 和 `user_strategy_version` 的归属、版本及唯一性契约。
- 新建、保存、另存为、复制、发布、回测和删除完整策略的链路。
- 远程服务器已有共享数据的审计、拆分与验证。
- 历史策略版本和历史回测的兼容读取。
- 策略管理页和《玄龄回测系统使用手册》中的交互及语义调整。

### 3.3 不做事项

1. 不改变 `on_bar`、`on_quote`、`bar`、`state` 或交易动作契约。
2. 不改变行情读取、撮合、费用、仓位、收益或调度规则。
3. 不重算、改写或删除任何历史回测结果。
4. 不将相同代码做物理去重后再共享可变脚本身份。
5. 不依赖前端判断保证数据隔离；后端与数据库必须能独立阻止重新共享。

## 4. 目标数据模型

### 4.1 完整策略归属

`strategy_config` 保留 `strategy_id`，但将其定义从“可共享脚本”改为“本方案独占脚本”。新增部分唯一索引：

```sql
CREATE UNIQUE INDEX ... ON strategy_config (strategy_id)
WHERE strategy_id IS NOT NULL;
```

对可供回测的完整策略，`strategy_id` 必须非空。不允许通过旧接口、批量工具或直接 SQL 把已绑定脚本再指派给第二个方案。

### 4.2 方案绑定确切脚本版本

`strategy_config` 新增 `strategy_version_id`，指向本方案当前已保存的 `user_strategy_version.id`。同时为 `user_strategy_version (id, strategy_id)` 建立候选键，并用 `strategy_config (strategy_version_id, strategy_id)` 到该候选键的复合外键保证“版本必须属于同行脚本”。后端再做同样的业务校验，用于返回可理解的错误。

```text
strategy_config
  id
  strategy_id             # 本方案独占的脚本身份
  strategy_version_id     # 本方案当前确切脚本版本
  params                  # 方案参数
  ...
```

不再通过 `user_strategy.current_version_no` 间接推测方案应使用哪份代码。

### 4.3 不可变脚本版本

当前 `_write_strategy_script` 会直接 `UPDATE user_strategy_version`。改造后：

1. 对代码、`entryType`、`signalRequired` 和其他影响运行的脚本元数据计算统一内容指纹。
2. 指纹与当前版本相同时复用当前版本，避免无意义增版。
3. 指纹不同时，插入新的 `user_strategy_version`，并递增 `current_version_no`。
4. 任何代码或运行元数据都不得再原地更新旧版本。
5. 现有 `UNIQUE (strategy_id, source_checksum)` 只能识别代码，无法区分“代码相同但运行元数据不同”。需改为覆盖完整运行语义的版本指纹约束，`source_checksum` 仍保留为纯代码校验值。

### 4.4 发布与回测快照

- 发布方案时，`strategy_config_version.strategy_version_id` 必须等于当前方案明确绑定的脚本版本。
- 运行回测时，从已发布方案版本读取代码，并继续写入 `backtest_run.script_snapshot`。
- 已提交任务始终使用提交时快照，即使用户随后保存新版本，排队中和运行中任务也不变。
- 读取旧数据时，若 `strategy_config.strategy_version_id` 为空，在过渡期内可回退到原 `current_version_no`；迁移验收后不再为新数据允许该回退。

## 5. 保存、复制与删除契约

### 5.1 新建完整策略

后端在同一事务中：

1. 创建新 `user_strategy`。
2. 创建第 1 个不可变 `user_strategy_version`。
3. 创建 `strategy_config`，同时绑定新的 `strategy_id` 和 `strategy_version_id`。
4. 任一步失败则整个事务回滚，不产生孤立脚本或半完成方案。

新建接口可以接受“从某个完整策略复制内容”，但不再允许客户端自由指定一个已被占用的 `scriptId`。

### 5.2 修改完整策略

修改时以 `configId` 为唯一资源身份：

1. 后端锁定当前方案，并从数据库解析其所属 `strategy_id`。
2. 不信任前端传入的 `scriptId` 来改变归属；若保留该字段，只用于一致性校验。
3. 代码有变化时为本方案的独占脚本创建新版本。
4. 在同一事务内更新方案参数和 `strategy_version_id`。
5. 数据库唯一约束作为最后防线，即使发生并发保存也不能产生脚本共享。

### 5.3 另存为与复制

前端明确区分：

- “保存”：更新当前完整策略并生成必要的新代码版本。
- “另存为”或“复制策略”：用当前参数和代码内容创建全新方案、全新脚本身份和第 1 个脚本版本。

前端方案选择器只展示完整策略，不再把“可共享脚本”表现为可与多个方案自由组合的独立资产。

### 5.4 删除

- 删除方案时由后端在事务内处理归属脚本，不再由前端先删方案再猜测脚本是否还被使用。
- 已被历史发布版本或回测引用的脚本版本保留，或将脚本身份转为 `archived`，不因删除当前方案破坏历史读取。
- 删除完整策略不删除历史回测中已保存的 `script_snapshot`。

## 6. 现有数据迁移

### 6.1 迁移方式

新建幂等迁移 `023_strategy_config_script_ownership.sql`，不修改已执行的历史迁移。迁移采用“扩展 → 回填 → 验证 → 加约束”顺序：

1. 新增可空 `strategy_config.strategy_version_id` 和脚本完整内容指纹字段。
2. 统计空脚本、孤立脚本、无当前版本、共享脚本和版本引用异常；存在不可判定数据时终止迁移，不猜测。
3. 对每个共享组按方案创建独立 `user_strategy`。一个确定方案可保留原脚本，其余方案使用新脚本。
4. 每份新脚本从迁移当时的有效代码和运行元数据创建自己的第 1 个版本。
5. 将每条当前 `strategy_config` 更新为独立 `strategy_id` 和相应 `strategy_version_id`。
6. 为未共享方案回填其当前脚本版本 ID。
7. 验证不存在共享、空绑定和跨脚本版本后，再建立唯一约束和非空业务校验。

新脚本名称优先使用方案名称。若与已有脚本名称冲突，使用可重复执行的确定性后缀，不使用随机名称造成重试时重复克隆。

### 6.2 历史数据保护

迁移只改变“当前方案以后编辑哪份脚本”，不改变历史事实：

- 不更新已有 `strategy_config_version.strategy_version_id`。
- 不更新已有 `strategy_config_version.snapshot`。
- 不更新 `backtest_run.strategy_version_id`、`script_snapshot`、`requested_params` 或结果字段。
- 不删除原共享脚本及其历史版本，因为旧发布记录可能仍然引用它们。

需要如实承认：如果旧系统已经将某个 `user_strategy_version` 原地覆盖，而该旧代码没有保存在任何回测 `script_snapshot` 或外部备份中，单靠现有数据库无法无损恢复被覆盖前的代码。实施前应生成审计报告，尝试用可确认的回测快照补充缺失版本，但不得自动猜测或改写历史。

### 6.3 幂等与事务安全

- 迁移为每个“方案 + 原脚本”记录确定性迁移标识，重复执行不会重复克隆。
- 拆分、回填和约束建立在可控事务内完成；任一校验失败则回滚。
- 迁移脚本不记录策略源码，只输出数量、ID 和安全错误摘要。
- 对远程数据首先在恢复的数据库副本中演练，记录迁移前后计数和耗时，不直接以生产库作为首次试运行环境。

## 7. 后端与 API 改造

### 7.1 完整策略服务作为唯一写入入口

将新建、修改、复制和发布的数据库操作集中到完整策略服务。现有脚本和方案独立写接口按以下方式收敛：

- 前端策略编辑器不再分两步调用“保存脚本”和“保存方案”。
- 修改必须携带 `configId`和服务端版本号或 `updatedAt`，用于检测两个页面同时编辑的乐观锁冲突。
- 后端根据 `configId` 解析脚本归属，不允许用客户端 `scriptId` 将当前方案改绑到其他脚本。
- 旧写接口在兼容期内返回明确错误或仅支持不改变归属的操作，不得继续创建共享关系。

### 7.2 读取契约

完整策略读取至少返回：

```text
configId
strategyId
strategyVersionId
name
code
entryType
signalRequired
paramsJson
publishedVersion
updatedAt
```

页面用一份返回对象同时填充方案参数和代码，避免同时请求脚本列表与方案列表后在浏览器内再次组合。

### 7.3 公开回测 API 兼容

公开 API 仍以已发布 `config_id` 提交回测，请求字段无需改变。后端必须从该方案的已发布版本获取确切代码版本，不得改用脚本的全局最新版本。

## 8. 前端改造

1. 方案选择器仍使用唯一 `configId`，显示方案名称，不再另外让用户选择可共享 `scriptId`。
2. 选择方案时一次加载完整策略，参数和代码共用同一个版本身份。
3. 将主操作收敛为“保存策略”；如果保留“保存代码”，其也必须通过当前 `configId` 调用完整策略服务，不再直接更新脚本 ID。
4. 新建或复制策略后，页面立即切换到新 `configId`、新 `strategyId` 和新 `strategyVersionId`。
5. 保存成功后使用后端返回的完整策略替换本地状态，不使用保存前的旧脚本引用继续组合。
6. 策略名称和版本状态只展示一次，页面不再使用“方案”与“脚本”两套名称让用户猜测二者关系。
7. 如果发生并发修改，页面明确提示“该策略已在其他会话中更新，请刷新后重试”，不静默覆盖。

## 9. 历史兼容与不可恢复边界

### 9.1 必须保持的兼容性

- 旧方案 ID 保持不变，用户的方案列表、收藏、公开 API 调用和历史回测关联不丢失。
- 历史回测依旧按已保存的 `script_snapshot` 和参数快照展示，不用迁移后的当前策略重算。
- 旧 `strategy_config_version` 可以继续引用原共享脚本版本；新发布版本必须引用拆分后的独立脚本版本。
- 新代码读取历史任务时必须兼容空 `strategy_version_id`，不将旧数据当作损坏记录。

### 9.2 旧代码覆盖的限制

本次改造可以保证从上线时点开始的一对一与版本不变性，但不能凭空恢复过去已被原地覆盖且没有快照的代码。发布前审计应将记录分为：

1. 可由回测 `script_snapshot` 唯一还原。
2. 存在多份候选快照，需人工确认。
3. 没有可用快照，只能保留当前可见代码并标记旧版本不可恢复。

任何自动恢复都必须以完整哈希和唯一对应为前提，不用“时间最近”或“名称相似”猜测历史代码。

## 10. 实施阶段

### 阶段一：审计与兼容读取

1. 生成本地和远程只读审计报告，统计共享组、待克隆数、空引用和可恢复历史。
2. 增加新字段的兼容读取和契约测试，但先不切换写入路径。
3. 在恢复的生产数据副本上演练迁移并核对计数。

### 阶段二：一对一拆分与不可变版本

1. 执行幂等迁移，拆分当前共享脚本。
2. 回填每个方案的确切 `strategy_version_id`。
3. 建立一对一唯一约束。
4. 将脚本保存改为追加新版本，禁止原地覆盖。

### 阶段三：完整策略 API 与前端收敛

1. 新建、保存、复制和删除改为完整策略事务。
2. 前端不再独立组合方案与脚本列表。
3. 接入并发编辑冲突保护。
4. 更新使用手册和页面文案。

### 阶段四：本地验收与服务器发布

1. 用多个内容相同的完整策略做独立编辑回归。
2. 校验发布版本、新回测、排队任务和历史回测快照。
3. 按服务器发布规则检查活动回测，然后同批发布 `migrate`、`backend`、`bar-runner`、`l2-runner`、`strategy-worker` 和 `frontend`。
4. 发布后对共享统计、代表性方案、新旧回测和公开 API 进行验收。

## 11. 测试与验收标准

### 11.1 数据库契约

1. 任意非空 `strategy_id` 最多被一条 `strategy_config` 引用。
2. 每个可回测方案均有 `strategy_id` 和 `strategy_version_id`。
3. 每个 `strategy_version_id` 都属于同行 `strategy_id`。
4. 迁移重复执行不新增多余脚本或改变已完成关系。
5. 数据库直接尝试将同一脚本绑定第二个方案时失败。

### 11.2 独立编辑

1. 从同一代码复制方案 A 和 B，二者的 `strategy_id` 和 `strategy_version_id` 均不同。
2. 修改 A 的代码后，B 的代码、指纹、版本号、参数和发布状态均不变。
3. 修改 A 的参数但不改代码时，不为 A 生成多余代码版本，B 仍不变。
4. 代码未变但 `entryType` 或 `signalRequired` 改变时，生成新的完整运行语义版本。
5. 两个会话同时修改同一方案时，后提交者收到冲突提示，不覆盖先提交者。

### 11.3 版本与回测

1. 发布版本精确引用保存当时的脚本版本。
2. 新代码保存后，旧发布版本和旧回测仍显示原代码快照。
3. 保存后立即运行不被误判为“存在未保存修改”。
4. Bar、L2、研究信号、公开 API 与历史重新运行均使用确切代码版本。
5. 改造前后使用同一快照回测，交易信号、成交、费用、持仓、净值和摘要一致。

### 11.4 迁移数据对账

远程发布前后至少对比：

```text
方案数                         不变
方案唯一 ID 数                 不变
方案唯一名称数                 不变
共享 strategy_id 组数            26 -> 0
需拆分的额外引用数             165 -> 0
空 strategy_id 方案数             1 -> 0（需先确认实际代码）
历史回测数、状态与结果哈希     不变
历史方案版本数                 不变
```

再从原最大共享组、4 方案共享组、2 方案共享组和原本独立的方案中各抽样验证。

## 12. 发布、观测与回滚

### 12.1 发布前

1. 备份 PostgreSQL 业务库，并实际验证备份可恢复到隔离环境。
2. 保存共享关系审计结果、当前 Git 提交和关键表计数。
3. 选择无人编辑和无活动回测的发布窗口，暂停新策略保存，避免迁移中产生新共享。
4. 用生产备份恢复的副本执行完整迁移演练和验收 SQL。

### 12.2 发布顺序

1. 发布可兼容新旧字段的后端。
2. 执行幂等数据库迁移和强制约束。
3. 发布新前端和所有使用策略快照的执行服务。
4. 先进行数据库对账，再开放策略编辑和新回测。

依赖服务必须通过 `scripts/deploy-server.sh` 同批发布，不得只更新前端或 backend。

### 12.3 回滚

- 迁移以新增脚本和新增版本为主，不删除原共享记录，便于审计和必要时软件回退。
- 软件回退后必须保留新表、新字段和已克隆数据，不执行破坏性逆向迁移。
- 一对一唯一约束默认保留，因为它能阻止旧代码再制造共享；若回退版本不兼容该约束，应停止策略写入而不是删除约束。
- 只有数据校验确认迁移结果错误且无法前向修复时，才使用发布前数据库备份整库恢复。这会丢失备份后的新写入，因此发布窗口必须停止新写入。

## 13. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 克隆后脚本名称冲突 | 优先使用方案唯一名称，冲突时加确定性方案 ID 后缀。 |
| 大批量方案迁移时部分成功 | 迁移幂等、事务化，约束建立前完成全量验证。 |
| 旧发布版本指向原共享脚本 | 保留旧引用和原脚本，只切换当前方案。 |
| 旧版本代码已被覆盖 | 仅在快照唯一可验证时恢复；否则记录不可恢复边界。 |
| 迁移时仍有人保存策略 | 发布窗口暂停策略写入，迁移完成并对账后再开放。 |
| 前端修复但旧 API 继续制造共享 | 数据库唯一约束和后端归属校验作为最终防线。 |
| 两个编辑会话相互覆盖 | 使用 `updatedAt` 或显式版本号实现乐观锁。 |
| 脚本数增长导致存储增加 | 接受完整策略隔离所需的存储成本；只可去重不可变内容块，不去重可变脚本身份。 |

## 14. 自审结论

只在前端去重、修改 React `key` 或在保存时刷新列表，都无法解决该问题；它们不会改变多个方案指向同一可变脚本的数据库事实。

仅在保存时做“写时复制”可以防止将来的联动修改，但会继续留下已有共享关系，也无法防止独立脚本接口原地覆盖历史版本。因此推荐一次完成三个强约束：

1. 当前方案与脚本身份一对一。
2. 当前方案显式绑定确切脚本版本。
3. 脚本版本只追加、不覆盖。

该方案能使“策略方案 + 策略代码 = 一个完整策略”成为数据库、后端、前端和回测运行时共同遵守的契约，不再仅是页面文案上的概念。
