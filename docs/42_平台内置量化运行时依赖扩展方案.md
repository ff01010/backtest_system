## 1. 背景与问题结论

当前自定义策略运行时已经允许使用 Python `import` 语法导入运行镜像中已安装的模块，不维护模块导入白名单。实际限制来自固定容器镜像：`backend`、`strategy-worker`、标准 Bar Runner 和 L2 Runner 均只安装 `backend/requirements.txt` 中声明的依赖，因此策略只能导入标准库、`pandas` 及其传递依赖等现有模块。

当前正在运行的 `strategy-worker`、Bar Runner 和 L2 Runner 均无法找到 `talib`。这不是语法校验拒绝，而是镜像内没有安装对应发行包。

完整的“用户自选依赖、按任务构建环境”方案需要依赖解析、隔离构建、制品存储、任务级沙箱和运行环境回收等新基础设施，改造范围较大。现阶段推荐建设固定、版本化的“平台内置量化运行时”：由平台统一选择、固定和发布一组常用量化计算库，策略可以直接导入这些库，但不能在运行期间安装依赖。

本方案扩展的是通用计算能力，不内置交易策略、指标参数或投资结论，继续遵守 `docs/adr/0001-runtime-capability-not-strategy-implementation.md` 的既有决策。

## 2. 目标、范围与不做事项

### 2.1 目标

1. 为自定义策略提供稳定、可文档化的常用量化计算库。
2. Bar、L2 和 `strategy-worker` 使用完全一致的 Python、依赖版本和运行时标识。
3. 固定直接依赖和传递依赖，避免同一运行时版本因重新构建而得到不同计算环境。
4. 新任务冻结策略运行时版本，历史结果继续按保存时的快照展示。
5. 在保存或运行阶段明确区分“用户导入未支持模块”与“平台承诺的模块在镜像中缺失”。
6. 通过真实指标计算验证数值、预热、空值和订单类型转换，不以“可以 import”代替功能验收。
7. 不改变行情、撮合、费用、仓位、日终结算、收益归因和调度语义。

### 2.2 本期范围

- 固定 Python 3.12 Linux 运行镜像中的量化依赖集合。
- 集中的策略运行时 manifest、能力摘要和启动一致性检查。
- `SCRIPT_RUNTIME_VERSION` 的升级及新任务快照写入。
- 保存校验、Bar、L2、`strategy-worker` 的模块错误归类。
- Runner 心跳、任务入队和任务领取的运行时版本匹配。
- 新运行时错误码对应的前端提示与脱敏统计扩展。
- 策略使用手册中的支持库、限制和示例。
- 镜像构建测试、后端自动化测试、本地容器验证及远程普通用户样本回归。

### 2.3 不做事项

1. 不允许用户提交自己的 `requirements.txt`、包名、版本或安装源。
2. 不允许策略运行期间执行 `pip install`、源码编译或下载依赖。
3. 不建设按用户或按任务生成动态镜像的依赖构建平台。
4. 不开放 Git URL、本地路径、私有包、CUDA、GPU 或特殊硬件依赖。
5. 不为策略开放外部行情、网络爬取或第三方交易接口。
6. 不引入自带回测、撮合或账户模型的第三方回测框架。
7. 不内置 MA、MACD、RSI 等具体交易规则或默认参数。
8. 不改变现有禁止内置函数、双下划线名称规则和策略回调接口。
9. 不重算、改写或补写历史回测结果。
10. 不把本次依赖扩展描述为任务级完整安全沙箱升级。

## 3. 核心决策

### 3.1 采用固定平台量化运行时

平台维护一套统一的策略运行环境，策略作者只需要知道支持的导入名和行为限制，不需要了解镜像构建细节。运行环境的实现继续集中在现有策略运行时契约模块后面，避免 backend、Bar、L2 和 Worker 分别维护支持清单。

运行时接口至少包含以下信息：

```text
runtimeVersion
pythonVersion
platform
supportedPackages
packageVersions
```

同一 `runtimeVersion` 必须始终对应同一组受支持包、精确版本、基础镜像摘要和策略契约。只要 Python 版本、依赖集合、依赖版本、基础镜像、禁止能力或回调契约发生兼容性变化，就必须创建新的运行时版本，不得静默修改旧版本含义。

运行时版本不能只依赖代码常量。仓库必须提交不可变的运行时 manifest，包含预期 Python 版本、平台、基础镜像摘要、受支持发行包、导入名、精确版本和完整依赖锁摘要；对规范化 manifest 计算 `capabilityDigest（能力摘要）`。backend、Worker、Bar 和 L2 只有在运行时版本与能力摘要同时一致时，才属于同一执行环境。

### 3.2 首批支持库

首批只加入覆盖指标、数值、统计和时间序列分析的基础库。

| 发行包 | 策略导入名 | 用途 | 本期决策 |
| --- | --- | --- | --- |
| `numpy` | `numpy` | 数组、向量和基础数值计算 | 新增显式固定版本；不得只依赖 pandas 间接安装 |
| `pandas` | `pandas` | 时间序列、滚动窗口和表格计算 | 保留并纳入正式支持契约 |
| `scipy` | `scipy` | 统计、信号处理、插值和优化 | 新增 |
| `TA-Lib` | `talib` | SMA、EMA、RSI、MACD 等常用技术指标 | 新增 |
| `statsmodels` | `statsmodels` | 回归、统计检验和时间序列模型 | 新增 |

具体版本不得在未构建、未测试的情况下由方案文档猜测。实施第一步必须在与生产一致的 `python:3.12-slim`、Linux CPU 架构和 NumPy 主版本下解析一组精确兼容版本，随后将完整版本组合固定到依赖文件。

`TA-Lib` 官方从提供自包含底层 C 库的二进制 wheel 后，已覆盖 Python 3.12 和 Linux x86_64；本期仍必须通过生产同构的干净镜像确认选定版本确实命中 wheel，禁止在正式执行镜像中临时编译。参考：<https://pypi.org/project/TA-Lib/>。

SciPy 应使用官方二进制 wheel，避免把 C、C++、Fortran、BLAS/LAPACK 编译工具链带入运行镜像。参考：<https://docs.scipy.org/doc/scipy/building/index.html>。

### 3.3 明确排除的库类型

| 类型 | 示例 | 排除原因 |
| --- | --- | --- |
| 自带回测或撮合模型 | `backtrader`、`vectorbt`、`zipline` | 容易绕过或混淆平台现有成交、费用、仓位和结算契约 |
| 外部行情或爬取库 | `akshare`、`yfinance` | 依赖运行期网络和变化中的外部数据，破坏行情冻结与可复现性 |
| 交易客户端 | 券商、QMT 或交易所客户端 | 可能接触账户、下单和凭据，超出历史回测职责 |
| 机器学习与 JIT 加速库 | `scikit-learn`、`numba` | 当前没有对应业务需求，且会增加镜像、LLVM/JIT、资源治理与验证复杂度 |
| 绘图库 | `matplotlib`、`plotly` | 当前策略回调没有图形制品输出契约，加入后没有稳定用户出口 |
| GPU 与硬件库 | CUDA、专用加速运行时 | 当前容器和调度没有硬件声明、隔离与资源分配契约 |

排除指“不作为平台承诺的内置量化库”，不是通过模块名白名单阻断 Python 导入。若某个模块因其他平台依赖偶然存在，也不得视为受支持能力或写入使用手册。

### 3.4 不建立模块导入白名单

本方案继续保持导入语法开放。策略可以导入标准库和镜像中已安装模块；平台只对“正式支持的量化包”提供版本、文档和回归承诺。

不得在前端、AST 校验、Bar Runner、L2 Runner 或 Worker 新增不同的模块白名单。受支持能力由集中运行时契约声明，安全隔离仍由进程身份、容器、网络、文件系统和资源限制承担。

## 4. 依赖锁定与镜像构建

### 4.1 依赖源与版本规则

1. 所有直接依赖使用精确版本，不使用范围、通配符或自动升级。
2. 生成并保存完整传递依赖锁定结果；仅固定直接依赖不足以保证重复构建一致。
3. 保存安装制品的 SHA-256 哈希，构建时启用哈希校验。
4. 只从项目配置的可信 Python 包源取得依赖，不接受策略代码提供的安装源。
5. 首批库必须命中与生产 Python、操作系统和 CPU 架构兼容的二进制 wheel。
6. 构建阶段执行 `pip check`，存在依赖冲突立即失败。
7. 不执行自动包升级；后续升级必须建立新运行时版本并完成完整回归。

### 4.2 建议的依赖文件职责

依赖文件需要区分“人维护的直接依赖”与“机器锁定的完整环境”，但不要求在首期拆分 backend、Runner 和 Worker 的基础镜像。

建议职责如下：

```text
backend/requirements.in
  人工维护的直接依赖与精确版本意图

backend/requirements.lock
  完整传递依赖、环境标记和制品哈希

backend/strategies/runtime_manifest.json
  由锁文件生成的预期 Python、平台、基础镜像、受支持包精确版本和能力摘要输入

backend/requirements.txt
  兼容现有开发流程的入口；具体是否转为引用 lock 文件在实施时统一决定
```

`runtime_manifest.json` 必须由锁文件和固定构建配置确定性生成，不允许人工分别维护两套版本。CI/构建测试负责验证 manifest、锁文件和实际安装环境一致。

若不引入新的锁定工具，也必须提交等价的完整锁文件和可重复生成脚本。不得只依赖某次本地 `pip freeze`，也不得更新与本需求无关的包。

### 4.3 镜像构建规则

现有 `deploy/Dockerfile.backend` 同时用于 backend、Bar Runner 和 L2 Runner，`deploy/Dockerfile.worker` 用于 `strategy-worker`。本期保持这一结构，两个 Dockerfile 必须安装同一份锁定依赖，避免新增多个运行时变体。

镜像构建必须：

1. 从固定 digest 的 Python 3.12 基础镜像构建；可读标签只用于说明，不能代替 digest。
2. 安装锁定且校验哈希的依赖。
3. 禁止因缺少 wheel 自动回退到源码构建。
4. 不保留编译器、头文件、包缓存或无关构建产物。
5. 构建完成后运行依赖一致性和运行时能力测试。
6. 记录最终镜像摘要，用于发布审计。

### 4.4 运行时能力清单

在 `backend/strategies/runtime_contract.py` 或其同职责模块中读取已提交的运行时 manifest。预期版本来自 manifest，实际版本通过 `importlib.metadata` 从当前镜像读取；两者必须逐项比较，不能让错误镜像把实际版本自报为正确的 `v3`。

建议接口：

```python
def runtime_capabilities() -> dict[str, object]:
  """校验并返回固定运行时版本、能力摘要和受支持包版本。"""
```

调用方只依赖该接口，不直接解析 requirements 文件。模块内部必须检查：

- 所有承诺包均已安装；
- 实际 Python 主次版本与 manifest 一致；
- 每个发行包的实际版本与 manifest 精确一致；
- 导入名能够被发现；
- 规范化 manifest 计算出的能力摘要与提交值一致；
- 能力清单字段可安全返回，不包含文件路径、镜像内部信息或凭据。

能力检查分为父进程轻量检查和独立深度探针。Runner 父进程只读取 manifest、包元数据和 `find_spec`，避免提前加载 NumPy/BLAS；但每个实际部署容器在报告健康或 Runner 写入 `ready` 之前，必须启动一个短生命周期探针子进程，真实导入全部承诺包并执行最小计算。探针成功后退出，不污染 Runner 父进程；探针失败则容器不健康、Runner 不领取任务。构建期使用同一探针，但构建期成功不能替代部署节点启动检查。

### 4.5 资源与数值线程门禁

首批依赖引入 NumPy/SciPy 计算栈后，必须固定数值线程数，避免多个 Runner 各自创建 BLAS 线程造成 CPU 过量竞争。线程变量需要分两段设置：先在 Dockerfile 或容器配置中于 Python 解释器启动前设置，覆盖 backend、`strategy-worker`、Bar 和 L2；再在策略子进程清空继承环境后，由集中运行时模块恢复同一组受控变量。

```text
OPENBLAS_NUM_THREADS=1
OMP_NUM_THREADS=1
MKL_NUM_THREADS=1
NUMEXPR_NUM_THREADS=1
```

不能只在策略子进程目标函数中设置：`multiprocessing spawn` 会先启动解释器并重新导入模块，NumPy/BLAS 可能在进入目标函数之前初始化；`strategy-worker` 也可能直接在服务进程执行策略。也不能只配置父容器环境，因为现有 Bar/L2 策略子进程会主动清空环境变量。两段式设置必须同时存在。

首批默认发布门禁：

- 压缩镜像体积相对当前基线增加不超过 300 MiB；
- Runner 父进程空闲 RSS 增加不超过 25 MiB；
- 代表性策略子进程峰值 RSS 相对 pandas 基线增加不超过 256 MiB；
- 首次导入首批全部量化库的 P95 不超过 2 秒；
- 不导入新增库的固定回测样本总耗时回归不超过 10%；
- 不提高现有 Runner 并发数或容器内存上限来掩盖超标。

若任一门禁超标，应缩减首批依赖或另行评审资源配置，不能在本方案实施中自行放宽阈值。

## 5. 运行时版本与历史兼容

### 5.1 新运行时版本

本次依赖集合变化属于运行时兼容性变化，建议将：

```text
python3.12-runtime-v2
```

升级为：

```text
python3.12-runtime-v3
```

只有在最终依赖组合、测试和文档均确定后才能固定 `v3`。同一 `v3` 标识不得在不同环境指向不同包版本。

### 5.2 新任务

新提交任务继续在 `versionScriptSnapshot`、`savedConfigSnapshot`、任务载荷和实验清单中冻结 `runtimeVersion`。所有提交入口，包括页面回测、公开回测 API、研究信号联动、标准 Bar 和 L2，必须写入同一版本。

提交前应确认至少一个对应类型的健康 Runner 报告当前 `runtimeVersion` 和 `capabilityDigest`，且均与 backend 完全一致。若 backend 已升级但 Runner 仍为旧版本或能力摘要不同，必须拒绝新任务，不能让任务排队后再以版本不一致失败。

任务入队时将已冻结的 `runtimeVersion` 和 `capabilityDigest` 同时写入 Bar/L2 作业表的独立列。Runner 领取时必须传入自身运行时版本和能力摘要，SQL 候选查询和原子状态更新均按两者过滤；不能先领取为 `running`，再到策略会话阶段发现不一致。队首任务版本或摘要不兼容时，后续兼容任务仍应按既有公平调度规则正常领取。

### 5.3 历史任务

1. 已完成历史任务继续读取保存结果和原始 `runtimeVersion`，不重算、不修改为 `v3`。
2. 历史详情缺少版本时继续显示 `legacy`，不得补写当前版本。
3. “复制参数重新运行”创建新任务时使用当前 `v3`，并明确这是当前环境下的新实验，不承诺与旧依赖环境逐位一致。
4. 发布前必须处理所有排队、运行中和取消中的 `v2` 或 `legacy` Bar/L2 任务；推荐先停止 backend 接收请求，再让 Runner 自然排空。
5. 若业务要求发布期间仍保留 `v2` 执行能力，需要另行实现多版本 Runner；本期不默认承担该复杂度。
6. 策略定义本身不是可执行环境快照。已保存但尚未运行的 TA-Lib 策略在回滚期间继续保留，新的运行请求因当前平台不具备 `v3` 而暂时拒绝，不得提示用户删除或修改正确策略。

### 5.4 数据库影响

本期不新增用户依赖选择字段，但为了在提交、健康检查、任务领取和回滚阶段真正按运行时匹配，需要新建幂等迁移。按当前迁移编号建议新增 `026_strategy_runtime_capability_routing.sql`；实施时若已有新的 `026`，必须使用当时下一个编号，不得复用或修改既有迁移。

迁移至少包含：

1. `backtest_runner_health.runtime_version`，记录 Runner 可执行的运行时版本。
2. `backtest_runner_health.capability_digest`，记录实际能力摘要。
3. `bar_backtest_job.runtime_version`，供标准 Bar 原子领取过滤。
4. `bar_backtest_job.capability_digest`，供标准 Bar 原子领取过滤。
5. `l2_backtest_job.runtime_version`，供 L2 原子领取过滤。
6. `l2_backtest_job.capability_digest`，供 L2 原子领取过滤。
7. 两类任务按 `status + runtime_version + capability_digest + created_at` 建立适合领取的部分索引；沿用现有 `created_at` 公平排序，不引用不存在的 `queued_at`。
8. 扩展 `strategy_runtime_error_stat` 的允许错误码，并增加受控的 `missing_module` 字段，用于记录平台承诺模块缺失；不得保存用户任意模块名。

迁移对已有排队任务按任务载荷中的脚本快照版本和能力摘要回填，无法确定时分别标记为 `legacy` 和对应的受控哨兵值。新任务必须同时写入列和 JSON 快照，并由测试保证两者一致。现有 RLS 与删除语义保持不变。

## 6. 保存校验与错误归责

### 6.1 保存阶段

现有语法、回调和订单字面量校验保持不变。在集中运行时能力清单基础上增加模块可用性预检：

1. 使用 AST 收集静态可识别的 `import` 与 `from ... import ...` 顶层模块名。
2. 标准库以运行时 manifest 中经过构建验证的模块集合为准；不能假定 slim 镜像包含所有可选标准库扩展。
3. 平台承诺的量化包必须在运行镜像中可发现，否则属于平台运行时缺陷。
4. 其他未安装模块在保存阶段返回用户可修改错误，并列出公开支持库入口。
5. 动态导入无法完全静态判定，运行期保留相同错误归责。

保存预检不得为了验证导入而在 backend 进程直接执行整段用户策略源码。若需要真实导入检查，应由无数据库凭据的 `strategy-worker` 完成受控验证。

### 6.2 错误码

| 场景 | 类别 | 建议错误码 | 用户提示 |
| --- | --- | --- | --- |
| 用户导入未安装且未承诺支持的模块 | `strategy_error` | `strategy.module_unavailable` | 当前运行时不提供该模块，请使用支持清单中的库 |
| 平台承诺支持的模块在某镜像缺失 | `system_error` | `runtime.dependency_missing` | 平台运行环境不完整，用户无需修改策略 |
| 依赖存在但二进制扩展加载失败 | `system_error` | `runtime.dependency_load_failed` | 平台依赖与系统环境不兼容，用户无需修改策略 |
| 任务快照与 Runner 运行时不一致 | `system_error` | `runtime.version_mismatch` | 平台发布或调度不一致，用户无需修改策略 |
| 策略对库函数传入非法参数 | `strategy_error` | 复用或细化 `strategy.runtime_error` | 检查策略行号、参数形状、类型和空值 |

`ModuleNotFoundError` 不能统一归责用户。必须根据用户请求的导入、缺失模块、受支持顶层包和异常链共同判断责任：

1. `import missing_pkg`：顶层包未承诺，属于 `strategy.module_unavailable`。
2. `import talib` 且整个承诺包缺失：属于 `runtime.dependency_missing`。
3. `import talib.nonexistent`：`talib` 存在但用户指定的子模块不存在，属于 `strategy.module_unavailable`。
4. `from talib import nonexistent`：包已正确加载但用户请求的符号不存在，属于用户策略错误。
5. 导入 `talib`、`scipy` 等承诺包期间缺少其锁定的传递模块：属于 `runtime.dependency_missing`。
6. `.so`、共享库、ABI 或符号加载失败产生的 `ImportError`、`OSError`：属于 `runtime.dependency_load_failed`。

诊断结构新增 `requestedModule`、`missingModule` 和 `supportedPackage`。模块名允许受控的点分标识符格式，不能复用只允许单个 Python 名称的 `missingName`。只有平台承诺包及其锁定传递依赖可以进入长期脱敏统计；用户任意输入的模块名不写入长期统计。

保存阶段的响应语义固定为：

- 用户导入未知模块：HTTP 422，返回结构化 `strategy.module_unavailable`。
- 平台承诺依赖缺失或加载失败：HTTP 503，返回结构化平台错误，提示用户无需修改策略。
- 创建脚本、更新脚本和完整策略保存三个入口使用同一转换逻辑。

### 6.3 健康检查

backend、`strategy-worker`、Bar Runner 和 L2 Runner 启动时均应调用同一个运行时能力接口。能力检查失败时：

- `strategy-worker` 健康检查返回失败；
- Runner 不得报告 `ready`，不得领取新任务；
- backend 不得接受需要该运行时的新任务；
- 日志记录受控包名、预期运行时和异常类型，不记录用户源码或参数。

`/api/health` 和 Worker `/health` 可安全返回运行时版本、能力摘要及受支持包版本。Runner 心跳写入相同版本与摘要；backend 聚合健康状态时只统计与自身完全匹配的 Runner。对外响应不得包含 site-packages 路径、wheel 文件名、内部镜像地址或构建凭据。

## 7. 指标使用与数据契约

### 7.1 输入转换

量化库通常接收 NumPy 数组、pandas Series 或连续浮点序列，而当前 `bar`/`quote` 只提供当前事件。策略仍需通过 `state` 保存历史值，再构造指标输入。

使用手册必须说明：

1. 指标不会自动获得完整历史数据。
2. 标准 Bar 策略可以声明足够的 `WARMUP_TRADING_DAYS`，并在 `state` 中积累所需字段；预热阶段只更新状态，不产生订单。
3. L2 当前不支持非零 `WARMUP_TRADING_DAYS`。L2 指标策略只能在正式回测区间前部积累窗口，并在指标形成前保持不交易；本方案不扩展 L2 系统预热语义。
4. 指标输入统一使用明确的浮点类型，不依赖对象类型或字符串隐式转换。
5. 指标结果尚未形成时必须返回空订单。

### 7.2 `NaN` 与不稳定期

TA-Lib、pandas、SciPy 和 statsmodels 在窗口不足、输入缺失或模型不可估计时可能返回 `NaN`、无穷值或抛出异常。平台不替策略猜测交易含义。

策略必须显式判断结果是否为有限数值。计划中的示例和测试不得在 `NaN` 上产生订单，也不得用零值自动替代未形成的指标。

### 7.3 Python 与 NumPy 标量

当前订单契约要求 `quantity` 是大于零的 Python `int`。NumPy 计算可能得到 `numpy.int64` 等标量，策略应在返回前显式转换：

```python
quantity = int(calculated_quantity)
```

本期不放宽订单契约接受任意 NumPy 标量，避免布尔值、溢出值和不可序列化类型进入撮合链路。价格、原因和订单列表继续按现有契约验证。

### 7.4 状态与结果可序列化性

策略可以在单次任务内的 `state` 中保存数组和模型对象，但不得假定这些对象可跨任务、跨进程或跨运行时版本持久化。当前未定义的状态序列化与恢复能力不因增加量化库而自动获得支持。

如未来需要保存训练模型或跨任务恢复指标状态，应另行定义制品格式、大小、版本和安全检查，不纳入本期。

## 9. 分阶段实施计划

### 阶段零：建立可回滚的 v2 路由基线

运行时路由迁移不能与量化依赖 `v3` 第一次同时上线，否则部署前原始 `v2` 镜像不理解新字段，无法作为安全回滚目标。因此先发布一个仍使用当前依赖和 `python3.12-runtime-v2` 语义的路由兼容版本：

1. 从当前生产 `v2` 镜像核对实际直接及传递依赖，不输出私有配置。
2. 在不升级、降级或替换任何包的前提下，为当前环境生成包含全部传递依赖和制品哈希的完整 `v2` 锁文件。
3. 由完整 `v2` 锁文件生成 runtime manifest 和能力摘要。
4. 使用锁文件重新构建路由兼容 `v2` 镜像，验证锁文件、manifest、实际安装版本和镜像摘要一致。
5. 新增 Runner 心跳、作业版本、作业能力摘要及领取索引迁移。
6. 所有新任务同时冻结 `v2` 版本和 `v2` 能力摘要。
7. Bar/L2 Runner 按版本与能力摘要原子领取。
8. backend 只把版本与摘要匹配的 Runner 计入可用容量。
9. 扩展发布脚本，区分正常发布门禁与回滚门禁。
10. 在不增加量化依赖的情况下完成依赖复现、调度、迁移和历史兼容测试。
11. 同批发布该路由兼容 `v2`，验证后记录镜像摘要，作为后续 `v3` 唯一允许的回滚目标。

退出条件：生产当前运行在理解新字段和版本化领取的 `v2` 兼容版本；原始、不理解路由字段的旧镜像不再列为 `v3` 回滚目标。

### 阶段一：兼容矩阵与依赖锁定

1. 确认生产服务器 CPU 架构、Python 3.12 补丁版本和基础镜像发行版。
2. 在干净的生产同构镜像中解析首批库的候选版本组合。
3. 强制只安装二进制 wheel，确认没有源码构建回退。
4. 执行 `pip check` 和逐包导入。
5. 运行最小数值样本，记录 NumPy、pandas、SciPy、TA-Lib 和 statsmodels 的实际版本。
6. 生成完整锁文件和制品哈希。
7. 生成运行时 manifest 和能力摘要，并验证其与锁文件、实际安装版本一致。
8. 生成 SBOM，核对各直接及传递依赖许可证。
9. 对已知高危漏洞进行扫描；未修复高危漏洞默认阻止发布，例外必须由项目负责人记录原因、影响和到期时间。
10. 对镜像体积、冷启动时间、空闲内存和首次导入耗时建立基线，并按 4.5 门禁判断。

退出条件：形成一组可在生产同构镜像重复构建的固定版本，不存在依赖冲突或源码编译。

### 阶段二：运行时契约与错误分类

1. 增加集中运行时能力清单及一致性检查。
2. 将运行时版本升级为 `python3.12-runtime-v3`。
3. 统一 backend、Worker、Bar 和 L2 对运行时能力的读取。
4. 增加 `strategy.module_unavailable`、`runtime.dependency_missing` 和 `runtime.dependency_load_failed`。
5. 静态预检可识别的导入；动态导入在运行期按相同规则分类。
6. 在阶段零已经上线的路由结构上增加 `v3` manifest，不重复创建第二套路由字段。
7. 验证 Bar/L2 入队和领取逻辑能够按 `v3` 版本和能力摘要原子筛选任务。
8. 扩展脱敏运行时错误统计，只记录平台承诺模块相关的安全字段。
9. 更新前端错误类型、责任提示和管理员统计展示。
10. 在每个实际容器启动时运行真实导入和最小计算的短生命周期深度探针；失败时阻止服务报告可接任务状态。

退出条件：故意删除一个受支持包时所有执行路径均判定为平台错误；导入未支持包时稳定判定为用户策略错误。

### 阶段三：指标契约与自动化测试

1. 为每个首批库增加导入和版本测试。
2. 增加 TA-Lib SMA、EMA、RSI、MACD 的确定性计算样本；预期值来自人工推导或独立固定夹具，不能在测试中调用被测库即时生成 expected。
3. 增加 NumPy 数组、pandas 滚动窗口、SciPy 统计函数和 statsmodels 最小回归样本。
4. 覆盖窗口不足、`NaN`、无穷值、空序列、常数序列和非法参数。
5. 覆盖 NumPy 标量转换为 Python `int` 后提交订单。
6. 在 `ScriptedBarStrategy`、标准 Bar 子进程、L2 子进程和 `strategy-worker` 中分别运行代表性脚本。
7. 验证相同输入在 Bar、L2 和 Worker 中得到一致指标值。
8. 验证依赖扩展不改变无量化库策略的订单、成交、费用、净值和结果结构。
9. 验证数值线程变量在解释器启动前已设置，并在 Bar/L2 策略子进程清空环境后恢复为 1；测试还应通过实际线程池检查或并发压力测试确认 NumPy/SciPy 计算线程数确为 1，不能只断言环境变量文本。

退出条件：量化库不只是可以导入，而是在全部执行链路中通过真实计算和失败场景测试。

### 阶段四：手册与用户提示

1. 更新唯一策略编辑器手册 `docs/玄龄回测系统使用手册.md`。
2. 列出受支持发行包、导入名和实际版本。
3. 增加基于 `state` 积累收盘价并调用 TA-Lib 的标准 Bar 最小示例。
4. 增加 L2 正式区间内先积累、不下单，指标形成后才交易的示例或说明；不得使用非零系统预热。
5. 明确预热、`NaN`、Python `int` 转换、无网络和不可运行期安装规则。
6. 明确排除的库类型以及如何申请平台增加新库。
7. 更新错误提示，使用户能区分策略依赖问题与平台镜像问题。

退出条件：用户只阅读手册即可编写可运行的 TA-Lib 策略，并能理解窗口未形成时为何不下单。

### 阶段五：本地容器与完整回归

1. 全量重建 backend、`strategy-worker`、Bar Runner 和 L2 Runner 镜像。
2. 在每类运行容器中查询能力清单并实际导入首批库。
3. 执行后端受影响测试和完整 pytest。
4. 启动本地完整环境，验证 backend 与 Runner 报告相同 `runtimeVersion` 和包版本。
5. 提交代表性标准 Bar 与 L2 回测，覆盖指标积累、生成信号、订单提交和最终结果。标准 Bar 使用系统预热区间；L2 在正式区间内先积累窗口且不交易，形成指标后再产生信号。
6. 读取历史成功、失败和取消任务，验证不因新运行时无法展示。
7. 比较改造前后不使用新增库的固定样本，确认结果未变化。

退出条件：本地代码、镜像、任务链路和历史读取全部通过，且实际结果有记录可复核。

### 阶段六：远程普通用户样本回归与发布

1. 通过只读查询取得远程服务器普通用户最近两条回测任务的保存代码和运行快照，不输出或持久化用户源码。
2. 在预发布隔离环境或隔离测试租户中，使用修改后的代码通过正常 Worker/Runner 链路执行两条样本，不在 Codex 进程或宿主机直接执行用户策略。
3. 隔离回归只复用只读行情和冻结快照；验证记录只保存任务编号、源码哈希、快照哈希和结果摘要，临时任务及源码副本在验证后清理。
4. 至少增加一条 TA-Lib 标准 Bar 样本和一条 TA-Lib L2 样本，覆盖提交、排队、领取、执行和结果生成。L2 样本使用正式区间内积累，不使用系统预热。
5. 完成发布门禁和 go/no-go 决策后，停止生产 backend 容器，使页面和公开 API 无法继续提交任务；frontend 可以保留静态页面，但所有写请求应明确不可用。
6. 检查排队、运行中和取消中的 Bar/L2 任务，等待 `v2` 任务自然完成；不得静默中断。
7. 检查并处理无法确定版本的 `legacy` 队列任务，队列和运行中任务全部清零后才能重建 Runner。
8. 通过 `scripts/deploy-server.sh` 同批发布迁移、backend、`strategy-worker`、全部 Bar Runner、全部 L2 Runner 和 frontend。
9. 发布后核对健康检查、运行时版本、能力摘要、受支持包版本、代表性新任务和历史任务读取。
10. 验证服务器私有 `deploy/.env` 未被覆盖。

远程不可访问、普通用户有效样本不足两条或行情条件不足时，必须标记“远程普通用户样本回归待验证”并说明原因，不得声称已通过。是否允许带着该待验证状态发布，必须由用户或项目负责人明确决定，实施者不得自行放行。

## 10. 测试计划

### 10.1 依赖与镜像测试

1. 锁文件能够在无本地缓存的干净镜像重复安装。
2. 所有制品通过哈希校验，安装不访问未配置的包源。
3. 所有首批依赖使用二进制 wheel，没有编译器回退。
4. `pip check` 无冲突。
5. backend、Worker、Bar、L2 的包版本完全一致。
6. 镜像内没有遗留编译器、pip 缓存和临时构建文件。
7. manifest 中的预期版本、锁文件和实际安装版本完全一致。
8. 基础镜像 digest、依赖锁摘要和能力摘要可重复生成。
9. SBOM、许可证核验和高危漏洞处置记录完整。
10. 镜像体积、RSS、首次导入和固定回测耗时满足 4.5 门禁。
11. 通过实际线程池检查或并发压力测试确认 NumPy/SciPy 计算线程数为 1，不以环境变量字符串代替验证。

### 10.2 运行时能力测试

1. `runtime_capabilities()` 返回固定结构和安全字段。
2. 所有承诺包实际存在且可导入。
3. 每个实际容器启动时的深度探针真实导入并执行最小计算；缺少承诺包或二进制加载失败时服务不健康，Runner 不领取任务。
4. 未承诺模块缺失返回 `strategy.module_unavailable`。
5. 承诺模块缺失返回 `runtime.dependency_missing`。
6. 二进制扩展加载失败返回 `runtime.dependency_load_failed`。
7. 旧运行时任务与新 Runner 不兼容时继续返回 `runtime.version_mismatch`。
8. `talib.nonexistent` 和不存在的导入符号归类为用户错误，不误报平台缺依赖。
9. 支持包内部锁定传递依赖缺失归类为平台错误。
10. 创建、更新和完整保存入口分别验证 422 与 503 的结构化错误响应。
11. 前端对新增平台错误显示“平台运行环境异常”，对未知模块显示用户可修改提示。
12. 脱敏统计只记录平台承诺模块，不记录用户任意模块名。

### 10.3 量化计算测试

1. NumPy 数组生成、切片、有限值判断和标量转换。
2. pandas Series、rolling、shift 和缺失值处理。
3. SciPy 最小统计与信号函数的确定性结果。
4. TA-Lib SMA、EMA、RSI、MACD 的窗口形成前后结果。
5. statsmodels 最小回归的系数和异常场景。
6. 同一固定输入重复执行得到相同结果。
7. 不把 `NaN`、无穷值、NumPy 布尔值或 NumPy 整数直接作为订单契约字段。
8. 指标预期值使用独立固定夹具或人工推导值，不由被测库生成。

测试断言应使用与浮点算法相称的误差范围，不以字符串化结果或过度严格的逐位比较制造跨平台脆弱测试。

### 10.4 Bar、L2 与 Worker 集成测试

1. 标准 Bar 使用预热数据形成指标，正式区间前不产生订单。
2. 标准 Bar 的信号仍在下一根可交易 Bar 开盘成交。
3. L2 拒绝非零系统预热的既有契约保持不变。
4. L2 `on_bar` 在正式区间积累指标且形成前不交易，信号仍只能使用严格后续盘口成交。
5. L2 `on_quote` 使用状态内窗口计算时保持事件顺序。
6. `strategy-worker` 与本地 Bar/L2 子进程使用同一运行时版本、能力摘要和依赖版本。
7. 无新增库策略的既有固定样本结果保持不变。
8. 取消、超时和子进程异常退出行为保持不变。

### 10.5 快照与历史兼容测试

1. 页面提交、公开 API、研究信号联动、Bar 和 L2 新任务均冻结 `v3`。
2. 保存后立即运行不被误判为未保存修改。
3. 历史 `v2` 和 `legacy` 任务按原快照展示。
4. 历史复制参数重新运行生成新的 `v3` 任务，不改写原任务。
5. backend 与 Runner 版本不一致时提交被提前拒绝。
6. 回滚到阶段零路由兼容 `v2` 镜像后，不会执行已排队的 `v3` 任务。
7. 入队列与 JSON 快照中的运行时版本、能力摘要始终一致。
8. `v3` Runner 不领取版本或摘要不匹配的任务，路由兼容 `v2` Runner 不领取 `v3` 任务。
9. 同版本但不同能力摘要的 Runner 不得领取任务。
10. 队首是不兼容版本或摘要时，不阻塞后续兼容任务的公平领取。
11. Runner 心跳过期、版本不符或能力摘要不符时均不计入可用容量。

## 11. 发布计划

### 11.1 发布前门禁

必须全部满足：

1. 首批依赖版本和哈希已经固定。
2. 干净镜像重复构建通过。
3. backend、Worker、Bar、L2 的运行时版本、能力摘要和包版本一致。
4. 受影响测试和完整 pytest 已实际执行并通过。
5. 本地标准 Bar、L2 和历史读取已验证。
6. 镜像体积、启动时间、内存增量、首次导入和固定样本耗时满足 4.5 的量化门禁。
7. 远程普通用户两条样本已通过，或已如实标记待验证并取得发布决策。
8. 服务器没有将被静默中断的排队或运行任务。
9. 阶段零的路由兼容 `v2` 已在生产验证，其镜像摘要已记录为唯一回滚目标。

### 11.2 发布步骤

1. 先停止 backend 容器，阻断页面和公开 API 新提交；不得只检查一次队列后继续接受请求。
2. 保持 Bar/L2 Runner 运行，等待 queued、running 和 cancelling 任务全部进入终态。
3. 核对并记录阶段零已经验证的路由兼容 `v2` 镜像摘要；不得使用不理解新字段的原始旧镜像。
4. 使用增强后的 `scripts/deploy-server.sh` 再次检查所有任务均已排空，并同批执行迁移、构建和发布相关服务。
5. 检查 backend 和 Worker 健康接口。
6. 检查所有 Bar/L2 Runner 心跳、运行时版本和能力摘要。
7. 执行 TA-Lib 标准 Bar 冒烟回测。
8. 执行 TA-Lib L2 冒烟回测。
9. 读取至少一个历史 `v2` 成功任务。
10. 恢复新任务提交并观察首批任务。

本期包含运行时路由和错误统计的幂等数据库迁移，并使用现有发布脚本保证迁移及相互依赖服务同批更新。若排空、迁移、健康检查或冒烟任一步失败，保持提交入口关闭，进入回滚或向前修复，不能带病恢复新任务。

### 11.3 发布后观察

重点观察：

- `runtime.version_mismatch`；
- `runtime.dependency_missing`；
- `runtime.dependency_load_failed`；
- `strategy.module_unavailable`；
- Runner 启动失败和反复重启；
- 单任务峰值内存、任务耗时和镜像拉取耗时；
- TA-Lib 指标窗口与 `NaN` 导致的用户策略错误。

任何平台承诺包在部分 Runner 缺失都视为发布阻断问题，不得要求用户修改策略规避。

## 12. 回滚计划

### 12.1 软件回滚

1. 停止 backend，阻断新的页面和公开 API 任务提交。
2. 检查是否存在运行或取消中的 `v3` 任务，并让现有 Runner 完成这些活动任务；回滚不强制排空仍为 queued 的 `v3` 任务。
3. 确需中断运行任务时必须取得用户明确确认并标记为发布中断；未确认时不得通过停止 Runner 强制终止。
4. 活动任务清零后停止 Runner，并使用回滚模式同批回退 backend、`strategy-worker`、全部 Bar Runner、全部 L2 Runner 和 frontend 到阶段零已验证的路由兼容 `v2` 镜像摘要。
5. 验证所有服务重新报告 `v2`，并检查历史任务读取。

### 12.2 `v3` 任务处理

路由兼容 `v2` Runner 不得执行 `v3` 任务。回滚时尚未执行的 `v3` 任务可以保持 queued，但必须因版本和能力摘要过滤而不可领取，等待向前修复恢复 `v3`，或者在取得明确确认后取消并由用户重新提交；不得把快照版本或摘要改写为 `v2`。

回滚脚本与正常发布使用不同门禁：正常发布要求 queued、running、cancelling 全部清零；回滚只要求 running、cancelling 清零，并允许不兼容的 queued `v3` 留存。回滚后的 `v2` backend 继续为新任务写入 `v2` 版本和能力摘要，兼容 Runner 能跳过旧的 queued `v3` 并领取后续 `v2` 任务。

### 12.3 数据回滚

已执行的新增迁移不做破坏性逆迁移；新增列、索引和扩展后的统计约束由阶段零路由兼容 `v2` 继续使用。已成功完成的 `v3` 结果继续按保存结果展示；不得因软件回滚删除、重算或降级其运行时快照。

## 13. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| NumPy 与 TA-Lib ABI 不兼容 | 导入失败或容器崩溃 | 固定兼容版本、只用官方 wheel、构建期真实导入和计算 |
| 只固定直接依赖 | 重建时传递依赖漂移 | 完整锁定传递依赖和制品哈希 |
| 依赖升级改变指标结果 | 相同策略重新运行结果变化 | 新版本对应新 runtimeVersion，不静默更新 v3 |
| 镜像体积明显增长 | 发布、扩容和冷启动变慢 | 只加入首批库、使用 slim 镜像、清理缓存并设体积门禁 |
| SciPy/statsmodels 增加内存 | 高并发 Runner 内存压力 | 固定 BLAS 线程，执行量化资源门禁；超标时缩减首批依赖并另行评审并发 |
| 指标窗口不足返回 `NaN` | 策略误下单或运行失败 | 手册与测试要求显式有限值判断 |
| NumPy 标量不符合订单契约 | `quantity` 被拒绝 | 示例使用 `int()`，保留严格订单验证 |
| 不同服务镜像依赖不一致 | 同一任务在不同路径表现不同 | 同一锁文件、集中能力检查、同批发布 |
| 新错误仍被归责用户 | 用户反复修改正确策略 | 按承诺集合区分平台缺失和用户未知模块 |
| 增加第三方代码扩大攻击面 | 漏洞或供应链风险 | 固定版本、哈希、可信源、漏洞审查、禁止运行期安装 |
| Runner 领取错误版本任务 | 任务先进入 running 再失败 | 作业列冻结版本，领取 SQL 按版本原子过滤并覆盖队首不兼容测试 |
| 错误镜像自报为 v3 | 不同节点计算环境漂移 | 提交 manifest、精确预期版本和能力摘要，启动时对照实际环境 |
| 发布检查后又进入新任务 | Runner 重建时中断任务 | 先停 backend，再排空全部任务，发布脚本二次阻断检查 |
| 误把本期视为完整沙箱 | 安全承诺超过实际实现 | 文档明确只是固定依赖扩展，继续披露现有隔离限制 |

## 14. 验收标准

1. 标准库及现有正常导入不受影响，不新增模块白名单。
2. `numpy`、`pandas`、`scipy`、`talib` 和 `statsmodels` 在 backend、`strategy-worker`、全部 Bar Runner 和全部 L2 Runner 中版本一致。
3. 每个首批库均通过真实计算测试，不只验证导入成功。
4. TA-Lib 的 SMA、EMA、RSI 和 MACD 以独立固定预期值验证，并在标准 Bar 与 L2 路径得到一致结果。
5. 标准 Bar 预热期和 L2 正式区间积累期均不产生错误订单；L2 非零系统预热仍被拒绝；`NaN` 处理在手册与测试中明确。
6. NumPy 标量不会绕过或破坏现有订单类型契约。
7. 新任务完整冻结 `python3.12-runtime-v3`，所有提交入口一致。
8. 历史 `v2` 和 `legacy` 任务可以正常查看，不重算、不改写。
9. 用户导入未支持模块时返回 `strategy.module_unavailable`。
10. 平台承诺模块缺失或加载失败时返回平台错误，并明确用户无需修改策略。
11. backend 与 Runner 的运行时版本或能力摘要不一致时提前阻止新任务，不产生不可执行队列积压。
12. 不修改成交、费用、仓位、日终结算、收益归因和结果结构。
13. 本地自动化、容器、Bar、L2、历史兼容及远程普通用户样本回归均有真实验证记录；未执行项如实标记。
14. 策略使用手册列出支持库、实际版本、预热、`NaN`、类型转换和禁止运行期安装规则。
15. Runner 心跳保存版本和能力摘要，任务入队保存运行时版本，领取 SQL 只领取兼容任务。
16. 前端正确区分新增的平台依赖错误与用户未知模块错误，管理员统计不保存用户任意模块名。
17. 发布流程能够实际停止提交、排空队列、同批发布并在失败时保持入口关闭。

10. SBOM、许可证和漏洞处置记录。
11. 本地验证记录、远程普通用户样本回归记录和发布检查结果。
12. 可回滚镜像摘要及回滚验证记录。

## 16. 方案自审

1. 方案解决了当前 `talib` 等常用库不可用的问题，但没有引入用户自选依赖平台的基础设施复杂度。
2. 支持集合聚焦通用计算能力，不把具体策略、数据源或撮合框架纳入平台职责。
3. 依赖集合通过运行时版本、精确 manifest、基础镜像 digest 和能力摘要共同管理，不会在相同版本下静默漂移。
4. 集中能力接口为 backend、Worker、Bar 和 L2 提供同一个测试 seam，避免支持清单散落。
5. 保存校验和运行期错误按平台承诺集合判断责任，不再把镜像缺包统一归责用户。
6. 保留现有订单、撮合、结算和历史结果语义；为保证版本路由闭环，本期明确包含心跳、任务表、领取逻辑、前端错误展示和幂等迁移，未继续低估影响范围。
7. 本期仍使用固定公共镜像，不能解决用户任意第三方依赖需求；该能力如有必要应另立动态依赖与任务沙箱方案。
8. 当前 Bar/L2 子进程仍共享父 Runner 的容器文件系统和网络命名空间，本方案不得被表述为完整安全隔离。
9. 首批版本必须通过生产同构构建矩阵确定，方案不虚构未经验证的版本组合。
10. 发布采用“先停 backend、再排空 Runner、然后同批发布”的可执行流程，不依赖当前不存在的维护开关。
11. L2 继续不支持非零系统预热，指标只在正式区间内积累，不暗含扩大行情和撮合契约。
12. 发布、回滚、版本化领取和远程样本验证均已纳入计划，不把“镜像能构建”当作完成标准。
