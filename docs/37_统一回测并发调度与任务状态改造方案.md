# 统一回测并发调度与任务状态改造方案

日期：2026-09-03
状态：已实施，待服务器发布验收

## 1. 背景与结论

当前系统已经将标准 Bar 回测和 L2 回测都改为 PostgreSQL 异步任务，但两类任务仍使用彼此独立的执行能力：

- 标准 Bar 回测由单个 `bar-runner（标准 Bar 回测执行器）` 串行消费，实际并发为 1。
- L2 回测由多个 `l2-runner（L2 回测执行器）` 消费，项目代码支持 1 至 8 个副本，但服务器私有 `deploy/.env` 当前配置为 4，实际并发为 4。
- `fb65f4f feat: 公平调度并扩展L2八并发` 已实现 L2 公平领取、8 副本配置上限和默认模板，但没有修改不纳入 Git 的服务器私有 `deploy/.env`，因此生产环境没有自动从 4 切换为 8。
- 原 L2 八并发方案明确排除了标准 Bar runner，因此它表达的是“L2 最多 8 并发”，不是“整个回测平台合计 8 并发”。

服务器最近 14 天共有 687 个 L2 任务，历史峰值确实达到 4 个任务同时运行，证明当前四并发已经生效。服务器现有 192 逻辑 CPU、约 377 GiB 内存，但 Swap 约 7.8/8 GiB 已占用，扩容仍需以 ClickHouse 延迟、容器 RSS、Swap 换入换出和失败率作为上线依据。

当前还存在任务状态展示与取消语义不一致的问题：

1. 前端提交任务后保存了最初的 `queued（排队中）` 快照；轮询到 `running（运行中）` 时没有同步更新任务列表，可能在任务已经执行甚至已经成功后仍显示“排队中”和取消按钮。
2. 取消接口只匹配队列表中的 `queued/running`；任务刚好已经结束时返回 404，前端却没有立即重新读取真实终态，用户容易误认为取消失败或任务仍在运行。
3. 标准 Bar runner 在同一进程中同步等待整个回测返回。取消线程只能写入或发现取消标记，无法可靠停止死循环、CPU 密集计算或阻塞调用。
4. 标准 Bar 取消任务的过期收尾发生在 runner 下一次领取任务之前；单 runner 被当前任务阻塞时，无法进入下一次领取，任务可能长时间停留在 `running`。
5. 任务成功提交没有把 `cancel_requested（取消请求）`作为拒绝条件，存在取消与成功同时发生时成功结果覆盖取消意图的竞争窗口。

本方案将平台能力统一定义为：

> 标准 Bar 与 L2 回测共享 8 个基础执行槽位；每个有任务的用户默认先获得 1 个槽位，没有其他用户等待时可借用全部空闲基础槽位。基础槽位被单一或少数用户占满后，新到且当前没有运行任务的用户可使用受控的公平突发槽位，默认最多临时扩展至 12。所有状态以 PostgreSQL 为唯一真源，标准 Bar 策略以独立子进程运行并可被真正终止。

## 2. 目标、范围与不做事项

### 2.1 目标

1. 将“并发 8”定义为整个回测平台的全局基础并发，而不是某一种回测模式的副本数。
2. 标准 Bar 与 L2 任务可以任意组合占用 8 个基础槽位，第 9 条任务仅在满足公平突发条件时运行，否则可靠等待。
3. 每个有等待任务的用户默认先获得 1 个执行槽位；没有其他用户等待时，单用户可以工作守恒地使用全部空闲基础槽位。
4. 避免 8 个基础槽位被同一用户占满后，新用户只能等待全部长任务自然结束；为当前没有运行任务的新用户提供有界、公平、可审计的临时突发容量。
5. 标准 Bar 回测按任务使用独立策略子进程，取消时能够真正停止策略计算并回收 CPU、内存和执行槽位。
6. PostgreSQL 统一记录排队、执行、取消和终态；前端展示必须与数据库当前状态一致。
7. 保持策略快照、行情快照、回调顺序、撮合、费用、仓位、收益、错误分类和历史任务读取语义不变。
8. 提供自动公平突发和管理员限时手动扩容两种能力，扩容到期后自动停止分配新增突发任务。

### 2.2 本期范围

- 标准 Bar 与 L2 任务共享的全局执行槽位、租约和公平调度。
- 用户默认 1 槽位、空闲借用、新用户突发救援和非抢占规则。
- 基础 8、突发上限 12、限时人工覆盖和自动回落配置。
- 标准 Bar 策略进程隔离、超时、真正取消与迟到结果保护。
- `queued/running/cancelling/succeeded/failed/cancelled` 状态契约。
- 前端实时状态、执行时长和取消反馈。
- 数据库幂等迁移、历史兼容、部署、压测、监控和回滚。

### 2.3 不做事项

1. 不设置无限并发，不保证任意数量的新用户都能立即运行；突发容量到达 12 后，后续任务仍需排队。
2. 不抢占、暂停或迁移已经运行的正常任务；新用户通过突发槽位或下一可用基础槽位获得服务。
3. 不改变任一历史回测的参数快照、结果快照、收益或成交记录。
4. 不以 Redis、Kafka 或浏览器状态替代 PostgreSQL 的任务状态真相。
5. 不把进程隔离描述为完整安全沙箱；策略导入白名单、网络出口和操作系统权限隔离另行设计。
6. 不因扩容清空 Redis、删除任务或重算历史结果。

## 3. 统一并发定义

### 3.1 基础容量与突发容量

| 配置 | 推荐默认值 | 含义 |
| --- | ---: | --- |
| `TREND_GRID_BACKTEST_BASE_CONCURRENCY` | 8 | Bar 与 L2 合计可长期占用的基础槽位数。 |
| `TREND_GRID_BACKTEST_BURST_MAX_CONCURRENCY` | 12 | 自动或人工临时扩容后的总并发硬上限。 |
| `TREND_GRID_BACKTEST_USER_GUARANTEED_CONCURRENCY` | 1 | 有等待任务的用户优先保证的运行槽位数。 |
| `TREND_GRID_BACKTEST_CAPACITY_OVERRIDE_MAX_TTL_SECONDS` | 3600 | 人工临时扩容允许的最长有效期，默认 60 分钟。 |
| `TREND_GRID_BACKTEST_CANCEL_GRACE_SECONDS` | 5 | 取消后等待策略子进程正常退出的宽限时间。 |

`TREND_GRID_BACKTEST_BASE_CONCURRENCY=8` 是对外承诺的基础能力。`TREND_GRID_BACKTEST_BURST_MAX_CONCURRENCY=12` 是保护其他用户等待体验的应急上限，不是日常吞吐目标，也不能被单个已经占用多个基础槽位的用户继续借用。

### 3.2 统一槽位的业务含义

一个处于 `running（正在回测）` 或 `cancelling（取消处理中）` 且执行进程尚未退出的任务占用一个全局槽位。标准 Bar 与 L2 均按一个任务占用一个槽位计数：

```text
8 个 L2                         = 8 个基础槽位
8 个标准 Bar                   = 8 个基础槽位
3 个标准 Bar + 5 个 L2         = 8 个基础槽位
8 个既有任务 + 1 个新用户任务 = 8 个基础槽位 + 1 个公平突发槽位
```

虽然 Bar 与 L2 的资源成本不同，首期仍按任务数计槽位，便于用户理解和验收。服务器验收以“12 个全部为 L2”的最坏资源组合为上限。如果后续数据显示不同模式资源差异导致明显失衡，再单独评估加权槽位，不在本期引入难以解释的权重。

## 4. 用户公平与空闲借用规则

### 4.1 默认一用户一槽位

调度器每次分配任务时，先统计标准 Bar 与 L2 两类任务中每个用户当前持有的有效全局槽位数 `activeCount`，再按以下顺序选择：

1. 优先选择 `activeCount=0` 且有等待任务的用户。
2. 若所有等待用户都至少有一个运行任务，优先选择 `activeCount` 最少的用户。
3. 同一运行数量下，选择最早进入统一队列的任务。
4. 同一用户内按提交时间领取，除非任务已取消、不可执行或等待指定执行器。

该规则保证用户默认先获得一个槽位，但不是“每个用户永远最多只能运行一个任务”。

### 4.2 空闲槽位借用

系统必须保持工作守恒：

- 只有用户 A 有任务时，A 可以依次使用全部 8 个基础槽位。
- A 使用 8 个基础槽位后，用户 B 到达时，不抢占 A 已经运行的任务。
- 如果某个基础任务很快结束，释放出的下一个基础槽位优先分配给 B。
- 如果基础任务都不会很快结束，并且满足突发条件，B 可以获得第 9 个临时槽位。

不能同时满足“单用户随时使用全部 8 个基础槽位”“不抢占已经运行的任务”和“后来用户必定立即使用基础槽位”。本方案用有界突发容量解决这一矛盾，而不是长期闲置保留槽位或终止其他用户任务。

### 4.3 多用户示例

#### 单用户独占空闲系统

```text
用户 A：20 条等待任务
基础槽位：8 个空闲

结果：A 的前 8 条任务运行，其余等待。
```

#### 新用户进入已满系统

```text
用户 A：8 条运行
用户 B：1 条等待，0 条运行
基础槽位：已满
突发槽位：4 个空闲

结果：B 获得第 9 个公平突发槽位；A 不能继续占用该突发槽位。
```

#### 多名新用户连续进入

```text
用户 A：8 条运行
用户 B、C、D、E：各有任务等待，均为 0 条运行
突发上限：12

结果：B、C、D、E 各获得 1 个突发槽位，总运行数达到 12。
后续用户 F 等待下一基础或突发槽位释放。
```

#### 基础容量恢复

当总运行数高于 8 时，调度器不为已获得服务的用户补充已结束任务。随着任务自然结束，总并发逐步回落；降至 8 以下后，再按统一公平规则领取基础任务。

## 5. 临时扩容设计

### 5.1 自动公平突发

只有同时满足以下条件时，调度器才能自动使用第 9 至第 12 个槽位：

1. 8 个基础槽位全部占用。
2. 存在 `activeCount=0` 的等待用户。
3. 等待任务对应类型的执行器可用。
4. 当前总运行数小于突发硬上限。
5. 数据源、数据库和主机没有进入人工设置的容量保护状态。

自动突发槽位只用于让当前没有运行任务的用户获得第一条运行任务。已经持有一个或多个槽位的用户不能借用自动突发槽位。这样既避免单用户长期独占，也不会把“临时扩容”变成常态 12 并发。

### 5.2 管理员限时扩容

提供受审计的管理命令或管理员接口，允许将有效并发上限临时设置为 9 至 12，例如持续 30 或 60 分钟。每次操作必须记录：

- 操作人；
- 原容量与目标容量；
- 生效时间和自动过期时间；
- 扩容原因；
- 当时的运行数、等待数、CPU、内存、Swap 和数据源状态。

限时扩容到期时：

1. 不终止已经运行的任务。
2. 不再领取超过基础并发 8 的新任务。
3. 等待现有任务自然完成并回落至 8。
4. 管理页面和日志显示“扩容已到期，容量正在回落”。

### 5.3 执行器容量准备

全局槽位是调度许可，Runner 副本或子进程是实际执行能力，两者必须同时满足。仅提高数据库容量但没有对应执行器，不会产生真实并发。

推荐部署方式：

1. L2 runner 保持一个副本同时处理一个任务，部署副本上限按突发上限准备。
2. 标准 Bar runner 移除固定 `container_name`，支持多副本；每个任务再由独立策略子进程执行。
3. PostgreSQL 全局槽位保证所有 Bar 与 L2 活跃任务合计不超过有效容量，即使两类 Runner 都有空闲副本，也不能绕过总上限。
4. 首期不让应用容器直接访问 Docker Socket，避免扩大生产控制权限。
5. 可以预启动低资源占用的空闲 Runner，由数据库槽位控制实际任务数；也可以由管理员扩容脚本同时调整 Runner 副本和限时容量。

短期人工扩容通过受控脚本完成，长期若需要自动增减容器，应交由专门的部署编排或系统服务执行，不在后端 Web 进程中直接调用 Docker。

## 6. 统一调度与数据库模型

### 6.1 保留现有任务表

首期保留：

- `backtest_run（回测主记录）`
- `bar_backtest_job（标准 Bar 任务）`
- `l2_backtest_job（L2 任务）`

避免为了统一并发而重写全部历史任务。新增全局执行槽位和运行时容量表，并由共享调度模块同时读取两类任务。

建议新增：

```text
backtest_execution_slot
  slot_no
  run_id
  owner_user_id
  job_kind            # bar / l2
  attempt_token
  worker_id
  is_burst
  acquired_at
  lease_expires_at

backtest_scheduler_capacity
  id                  # 固定单行或版本化记录
  base_limit
  burst_limit
  override_limit
  override_expires_at
  burst_enabled
  updated_by_user_id
  update_reason
  updated_at
```

新增或修改数据库字段、约束和索引必须使用新的幂等迁移，不修改已经执行的迁移文件，也不在应用启动阶段执行 DDL。

### 6.2 原子领取

Bar 与 L2 Runner 调用同一个调度服务领取任务。领取必须在同一数据库事务和短期全局调度锁内完成：

```text
获取事务级全局调度锁
  ↓
清理已确认退出且租约过期的槽位
  ↓
读取基础、突发和限时覆盖容量
  ↓
统计两类任务的用户 activeCount
  ↓
在 Bar + L2 等待任务中选出全局公平候选
  ↓
检查调用方是否能执行该任务类型
  ↓
锁定任务、写 running、attemptToken、worker 和任务租约
  ↓
同时占用全局槽位并提交事务
```

全局调度锁只覆盖毫秒级任务分配事务，不覆盖行情读取、策略执行或结果写入。原有 `FOR UPDATE SKIP LOCKED`、任务租约和 `attempt_token（尝试令牌）` 必须保留。

### 6.3 内部等待原因与日志

全局存在空闲槽位但目标类型 Runner 不可用时，任务仍为 `queued`。普通用户界面统一只显示“排队中”，不展示队列位置、容量、公平调度、执行器类型或其他内部等待原因。

后台仍应为管理员诊断区分以下内部原因码：

- `capacity_wait`：全局基础槽位已满，且当前任务不满足突发条件；
- `fairness_wait`：其他当前尚未获得执行机会的用户优先；
- `bar_executor_wait`：有全局容量，但暂时没有可领取任务的 Bar 执行器；
- `l2_executor_wait`：有全局容量，但暂时没有可领取任务的 L2 执行器；
- `burst_limit_wait`：基础容量和突发容量均已达到上限。

等待原因由当前队列、全局槽位和执行器可用状态动态计算，只写入管理员日志和监控指标，不返回普通用户任务接口，也不作为历史回测结果语义保存。日志记录原因码、当时容量、对应执行器数量和调度决策，但不得记录策略正文、令牌或其他敏感信息。任务开始后保存实际 `started_at`、`worker_id` 和槽位信息用于审计。

## 7. 标准 Bar 进程隔离与真正取消

### 7.1 目标结构

```text
Bar runner 父进程
  ├─ 领取任务与占用全局槽位
  ├─ 加载、校验并传递不可变任务快照
  ├─ 独立定时续写任务和全局槽位租约
  ├─ 启动单任务 StrategySession 子进程
  ├─ 监听结果、错误、退出码、超时和取消
  └─ 原子提交终态并释放槽位

StrategySession 子进程
  ├─ 执行用户策略与 Bar 撮合
  ├─ 不持有 PostgreSQL、Redis 或 ClickHouse 凭据
  └─ 返回受限结果或受控错误
```

标准 Bar 不再依赖共享 `strategy-worker /run` 完成整项 CPU 密集型策略执行，避免多个 Bar 任务在同一个 Python 解释器和共享服务中竞争。`strategy-worker` 是否继续保留给编辑器预览或低频校验，应依据现有调用点单独确认，不能在本方案中直接删除。

### 7.2 取消顺序

排队任务取消：

1. 原子将任务和主记录标记为 `cancelled`。
2. 不分配全局槽位，不启动策略子进程。
3. 重复取消返回当前 `cancelled`，保持幂等。

运行任务取消：

1. 原子写入 `cancel_requested=true`，主记录与任务进入 `cancelling`。
2. 父 runner 向策略子进程发送正常退出信号。
3. 在 `TREND_GRID_BACKTEST_CANCEL_GRACE_SECONDS` 内等待子进程退出。
4. 宽限时间到期仍未退出时，终止子进程；必要时升级为强制结束。
5. 只有确认子进程退出后，才将任务标记为 `cancelled` 并释放全局槽位。
6. 迟到的成功、失败或旧尝试结果不能覆盖 `cancelling/cancelled`。

`cancelling` 期间仍占用槽位，因为其计算进程可能尚未退出。否则在旧进程仍占用 CPU 时提前释放槽位，会造成实际资源并发超过数据库记录。

### 7.3 异常和租约恢复

- 父 runner 崩溃时，其容器退出必须同时结束所属策略子进程。
- 任务租约与全局槽位租约使用同一个 `attempt_token`，避免任务被重新领取而旧进程仍能提交结果。
- 租约过期后，由任何正常 Runner 或独立轻量收尾循环处理，不能只依赖原阻塞 Runner 的下一次领取。
- `cancel_requested=true` 的过期任务只能收敛为 `cancelled`，不得重新排队。
- 非取消的异常退出任务按现有重试上限决定重新排队或失败；必须记录尝试次数和原始诊断。

## 8. 统一任务状态契约

### 8.1 状态定义

| 数据库状态 | 前端文案 | 定义 | 是否占用槽位 | 是否显示取消按钮 |
| --- | --- | --- | --- | --- |
| `queued` | 排队中 | 已提交，但尚未被执行器原子领取。 | 否 | 是 |
| `running` | 正在回测 | 已取得槽位，执行器和任务租约有效。 | 是 | 是 |
| `cancelling` | 取消处理中 | 已接受取消请求，正在等待或强制结束执行进程。 | 是 | 否，改为状态提示 |
| `succeeded` | 已完成 | 结果已经原子持久化。 | 否 | 否 |
| `failed` | 已失败 | 任务已结束并保存受控错误。 | 否 | 否 |
| `cancelled` | 已取消 | 任务未启动或执行进程已经确认退出。 | 否 | 否 |

普通用户只需要区分“排队中”和“正在回测”：只有 `started_at` 已写入且持有有效槽位时才能显示“正在回测”，其余尚未领取的任务统一显示“排队中”。

### 8.2 状态接口

任务详情和列表至少返回：

```text
status
queuedAt
startedAt
finishedAt
cancelRequested
```

普通用户任务接口不返回队列位置、内部等待原因、全局容量或突发容量状态。上述调度数据仅进入管理员监控接口和日志。前端根据稳定的 `status` 枚举映射中文状态，不依赖后端返回可变文案。

### 8.3 前端同步规则

1. 提交成功后立即保存任务 ID，但不永久保留首次返回的 `queued` 快照。
2. 每次轮询任务详情都更新任务列表中的同一记录，包括 `queued → running → terminal`。
3. 列表和顶部运行条使用同一个最新任务对象，不分别维护互相漂移的状态。
4. 收到终态后先更新本地状态，再刷新列表和结果详情；列表刷新失败不能把任务退回旧状态。
5. 取消返回“任务已经结束”时立即读取真实终态，不显示笼统的 404 取消失败。
6. 页面重新打开后，主动轮询当前用户所有 `queued/running/cancelling` 任务，不能只轮询本页面刚提交的任务。

## 9. 配置与部署

### 9.1 项目默认配置

项目 `.env.example`、本地启动脚本和服务器部署脚本统一校验：

```ini
TREND_GRID_BACKTEST_BASE_CONCURRENCY=8
TREND_GRID_BACKTEST_BURST_MAX_CONCURRENCY=12
TREND_GRID_BACKTEST_USER_GUARANTEED_CONCURRENCY=1
TREND_GRID_BACKTEST_FAIRNESS_BURST_ENABLED=true
TREND_GRID_BACKTEST_CAPACITY_OVERRIDE_MAX_TTL_SECONDS=3600
TREND_GRID_BACKTEST_CANCEL_POLL_SECONDS=1
TREND_GRID_BACKTEST_CANCEL_GRACE_SECONDS=5
TREND_GRID_BAR_RUNNER_REPLICAS=12
TREND_GRID_L2_RUNNER_REPLICAS=12
```

Runner 副本数表示某类型执行器的最大可用数量，全局实际运行任务数仍由 PostgreSQL 槽位控制。若要求任意模式都能独占 8 个基础槽位，则 Bar 和 L2 两种执行器都必须至少准备 8 个执行能力。仅提高数据库容量不会自动产生执行能力；突发至 12 前，必须先通过预热副本或管理员扩容脚本补足目标模式的执行器，否则任务会以 `bar_executor_wait` 或 `l2_executor_wait` 继续等待。

服务器私有 `deploy/.env` 不进入 Git，也不得被 `.env.example` 覆盖。代码提交和服务器拉取不会自动改变现有生产值；发布步骤必须明确列出服务器侧需要人工写入或由受控脚本更新的非敏感容量配置。

### 9.2 分阶段上线

1. 先上线统一状态契约和前端实时同步，不改变并发数。
2. 完成标准 Bar 子进程隔离、取消和单任务结果对照，保持 Bar 单并发。
3. 上线全局槽位调度，先以总并发 4 验证 Bar/L2 混合领取和公平性。
4. 扩展到基础 8，执行单用户、多用户及 Bar/L2 混合压测。
5. 开启自动公平突发，先验证第 9 个救援槽位，再逐步验证最大 12。
6. 最后开放管理员限时扩容入口和自动到期回落。

每个阶段均应通过 `scripts/deploy-server.sh` 同批发布相互依赖的 `migrate`、`backend`、`bar-runner`、`l2-runner`、必要的 `strategy-worker` 和 `frontend`，不得只重启其中一个服务。

### 9.3 发布前检查

- 查询 Bar 与 L2 两类 `queued/running/cancelling` 任务。
- 发布需要重建 Runner 时，等待任务完成、由用户取消，或经明确确认标记为发布中断；不得静默中断。
- 记录当前服务器私有容量配置、容器副本数和 Git 提交，确保可以恢复。
- 执行数据库迁移演练，确认历史任务和旧状态可以读取。
- 检查 ClickHouse、Redis、PostgreSQL 连接数以及主机 CPU、内存、Swap 和磁盘 I/O。

## 10. 测试与验收标准

### 10.1 全局并发

1. 同时提交 9 个标准 Bar 任务时，前 8 个运行，第 9 个等待；不存在 L2 任务时，Bar 可以使用全部 8 个基础槽位。
2. 同时提交 9 个 L2 任务时，前 8 个运行，第 9 个等待；不存在 Bar 任务时，L2 可以使用全部 8 个基础槽位。
3. 同时提交 4 个 Bar 和 5 个 L2 任务时，任意时刻基础运行总数不超过 8，第 9 个等待或按突发规则运行。
4. 多 Runner 竞争时同一任务只被领取一次，旧 `attempt_token` 不能续租、释放槽位或写入终态。
5. 任务失败、取消和进程崩溃后槽位均能可靠释放，不产生永久占用。

### 10.2 用户公平与突发

1. 用户 A 单独提交 9 条任务时可以占满 8 个基础槽位，第 9 条等待。
2. A 已占满 8 个基础槽位后，零运行任务的用户 B 提交任务，B 获得第 9 个突发槽位。
3. A 不得继续获得第 9 至第 12 个自动公平突发槽位。
4. B、C、D、E 在 A 满载后依次到达时，各自最多先获得 1 个突发救援槽位；达到 12 后用户 F 可靠等待。
5. 任一基础槽位释放后，优先分配给运行数更少且有等待任务的用户。
6. 临时扩容到期时不杀运行任务，总并发自然回落；回落至基础 8 前不再领取新任务。
7. 人工扩容、延期、提前结束和禁用突发均有操作审计。

### 10.3 状态与前端

1. Runner 尚未领取时统一显示“排队中”，不展示队列位置或内部等待原因。
2. Runner 原子领取后，在下一次轮询内显示“正在回测”和真实开始时间。
3. 快速任务在取消按钮点击前已经完成时，页面显示“已完成”，不显示取消失败或继续显示排队。
4. 页面重新打开后能够恢复轮询已有活动任务。
5. 取消请求后状态依次收敛为 `cancelling → cancelled`，终态后不再显示取消按钮。
6. 列表、顶部状态条、结果详情和数据库对同一任务的状态一致。

### 10.4 真正取消与隔离

1. 正常策略收到取消后在宽限期内退出并释放槽位。
2. 包含无限循环的标准 Bar 策略在宽限期后被终止，只影响当前任务。
3. 阻塞调用、CPU 密集计算、策略异常和子进程崩溃均不会卡死 Bar runner 父进程。
4. 子进程确认退出前槽位不提前释放，实际进程数不会超过数据库有效容量。
5. 取消与成功同时发生时，数据库按原子顺序得到唯一终态；已接受取消的任务不能被迟到成功覆盖。

### 10.5 结果兼容与性能

1. 相同标准 Bar 任务在改造前后逐项比对信号、成交、费用、仓位、净值、收益和警告，结果一致。
2. L2 历史任务继续按保存时快照和语义展示，不被新调度规则重算。
3. Redis 缓存命中与回源只影响性能，不改变回测结果。
4. 8 基础并发和 12 最坏突发并发下，ClickHouse、Redis、PostgreSQL 无连接耗尽或持续错误。
5. 记录单任务 P50/P95 时长、排队 P50/P95、吞吐、CPU、RSS、Swap 换入换出和失败率；出现持续恶化时关闭突发并回退容量。

## 11. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| Bar 与 L2 两类 Runner 同时领取导致总并发超限 | 使用同一数据库事务锁和全局槽位表原子分配。 |
| 单用户先占满基础槽位，新用户长时间等待 | 新用户优先 + 第 9 至第 12 个公平突发槽位。 |
| 突发扩容变成单用户常态扩容 | 自动突发仅允许 `activeCount=0` 用户取得第一槽位。 |
| 临时扩容忘记恢复 | 所有人工覆盖必须带过期时间，到期停止新领取并自然回落。 |
| 取消后旧进程仍占 CPU | 子进程退出确认前保持 `cancelling` 和槽位占用，超时后强制终止。 |
| 迟到结果覆盖取消 | 终态更新同时校验状态、取消标记、尝试令牌和槽位归属。 |
| Runner 副本充足但数据源成为瓶颈 | 以 ClickHouse 延迟、缓存击穿、I/O 和错误率控制突发开关。 |
| 服务器空闲内存多但 Swap 持续换页 | 监控 `pswpin/pswpout`，不能只看一次可用内存快照。 |
| 两类任务资源成本不一致 | 首期按最坏 12 个 L2 任务验收，必要时后续引入加权槽位。 |
| 前端再次显示旧状态 | 任务详情轮询结果直接替换列表记录，数据库状态为唯一真源。 |

## 12. 回滚方案

1. 关闭自动公平突发，将有效容量恢复为基础 8；不终止已运行任务，等待自然回落。
2. 若统一调度异常，将基础容量临时降为 1，并停止新增领取；保留任务、槽位和审计数据用于排查。
3. 应用回退到上一兼容版本时，新迁移表和新增字段保留，不删除迁移、不删除历史任务。
4. 若标准 Bar 子进程链路异常，回退到旧 Bar 执行路径前必须确认没有运行中的新链路任务，并保持新旧结果结构兼容。
5. Runner 扩缩容必须通过部署脚本或受控扩容脚本完成；服务器私有 `.env` 恢复到发布前备份值。
6. Redis 不作为任务可靠性来源，回滚不得依赖清空缓存。

## 13. 实施顺序

### 阶段一：状态真源与取消竞争修复

1. 增加 `cancelling` 状态或等价的明确持久化状态。
2. 修复成功提交与取消标记竞争，补充幂等取消。
3. 前端轮询实时更新列表、顶部状态和取消按钮。
4. 增加活动任务恢复轮询；所有尚未领取的任务统一展示“排队中”。

### 阶段二：标准 Bar 子进程隔离

1. 抽取可在子进程执行的标准 Bar StrategySession。
2. 实现父子进程协议、退出码、结果限制、超时和取消。
3. 移除标准 Bar 整项回测对共享 `strategy-worker /run` 的依赖。
4. 完成新旧链路结果对照、死循环取消和异常隔离测试。

### 阶段三：统一全局槽位与公平调度

1. 新增幂等数据库迁移和共享调度服务。
2. 将 Bar、L2 领取接入同一全局槽位和用户运行数统计。
3. 增加仅供管理员使用的槽位、容量和内部等待原因监控接口。
4. 在总并发 4 下先完成混合任务验证。

### 阶段四：基础八并发上线

1. 调整 Bar 与 L2 执行器副本配置，确保任一模式具备 8 个执行能力。
2. 将服务器基础容量设置为 8，同批发布相关服务。
3. 验证 8 Bar、8 L2、4 Bar + 4 L2、多用户公平和第 9 条等待。
4. 观察至少一个完整高峰时段的吞吐与资源指标。

### 阶段五：公平突发与临时扩容

1. 开启第 9 个自动公平突发槽位，验证新用户救援语义。
2. 分阶段验证 10、11、12 并发及全部为 L2 的最坏负载。
3. 上线带 TTL、原因和审计的管理员临时扩容命令或接口。
4. 验证到期不抢占、停止新领取和自然回落。

## 14. 自审结论

原 L2 八并发提交没有丢失，但它只扩展了 L2 执行器能力；服务器私有配置仍为 4，因此生产环境目前只有 L2 四并发和 Bar 单并发。若业务要求是“整个回测平台八并发”，仅把 `TREND_GRID_L2_RUNNER_REPLICAS` 从 4 改成 8 不能满足要求，也无法解决标准 Bar 的真正取消与状态漂移。

本方案保留 Bar 与 L2 各自适配资源和数据源的执行器，同时用 PostgreSQL 全局槽位统一限制总并发、统一用户公平和统一状态，不要求把两种执行引擎强行合并到同一个进程。基础 8 保证稳定容量；默认一用户一槽位并允许空闲借用保证公平与吞吐；第 9 至第 12 个突发槽位解决单用户已经占满基础容量后新用户无槽位的问题；非抢占和自动回落避免破坏已运行任务。

推荐严格按“状态修复 → Bar 进程隔离 → 统一四并发验证 → 基础八并发 → 公平突发至十二”的顺序实施。不得直接在生产环境把某一类 Runner 扩到 8 或 12 后将其称为全平台并发改造完成。
