# 回测交易日历运行依赖移除方案

## 1. 背景与结论

任务 `#171` 请求 `600000.SH`、`1m`、`2024-03-07` 至 `2026-09-24` 的标准 Bar 回测。ClickHouse 已声明 `2026-09-24` 行情完整，但 PostgreSQL 中 SSE 交易日历只同步到 `2026-09-23`，Worker 在读取实际 Bar 前因“交易日历未覆盖本次回测区间”终止，最终对用户显示 `data.bar_load_failed`。

该故障不是行情缺失，而是两个日期事实来源更新不同步造成的误拒绝：

- 行情覆盖已经证明所选标的、周期和日期存在可用数据；
- 交易日历只比行情覆盖落后一天，却拥有更高的运行否决权；
- 当前系统是单标的、实际 Bar 事件驱动，不生成独立于 Bar 的市场时钟；
- 当前标准 Bar、L2 回放和预热均可从实际 Bar 或覆盖元数据取得所需日期；
- 当前页面预检已经不展示或消费逐日交易日历，公开预检接口固定返回空 `calendarDays`。

本方案决定：**将交易日历从回测运行、预热、L2 可用性摘要和服务器发布链路中退出，以版本化行情覆盖和实际加载的 Bar 日期作为唯一运行事实来源。**

本轮不删除 `market_trade_calendar` 表，不修改已执行迁移，不清理历史数据。该表保留为兼容结构，但不再影响新任务能否提交、领取、执行或发布。

## 2. 决策依据

### 2.1 当前系统不具备独立市场时钟

当前策略按单标的 Bar 推进：有 Bar 才调用 `on_bar`，没有 Bar 就没有该时点的策略事件。系统没有组合级分钟网格、无 Bar 日事件、跨标的同步回调、停牌价格延用或组合收盘估值时钟。

因此，交易日历目前只能提供“某自然日是否开市”，不能让没有 Bar 的日期或时点产生策略事件，也不能构成多标的组合所需的统一市场时钟。保留交易日历不会为当前执行模型增加实际能力。

### 2.2 行情覆盖已经承担可执行性判断

新版 QMT 历史来源只有满足以下条件的日期才被解析为 `complete`：

- 导入批次处于 `PUBLISHED`；
- 校验结果为 `PASS`；
- 预期路由数与实际路由数一致；
- 无缺失标的、重复键等批次级异常；
- 目标周期和复权路径属于本次发布；
- 标的在对应股票池快照中有效。

旧版 QMT 来源则使用 `qmt_kline_coverage.status = complete`。实际 Bar 读取后仍会执行数据格式、非空结果和允许日期过滤。交易日历不提供价格、行数、周期、来源版本或批次质量信息，不能替代上述判断。

### 2.3 日历没有实现其理论上的缺口识别价值

交易日历理论上可以区分休市日、停牌日和行情漏采日，但当前接受的行为已经明确：标准 Bar 不比较交易日历、覆盖记录和实际 Bar 的逐日集合来推断行情缺失；只要任务范围内存在可回放 Bar，就按所选单一来源的完整覆盖日期执行。

L2 回放也会在 Bar 加载后，以实际 Bar 日期检查十档快照摘要。若某日没有 Bar，现有交易日历并不会单独生成回放事件。因此，当前交易日历的严格区间覆盖检查只增加前置失败点，没有兑现逐日缺口识别能力。

### 2.4 保留日历硬依赖的持续成本

- 维护新浪和东方财富交易日历接口、编码解析、重试与回退。
- 维护一次性同步容器、每日调度、失败告警和部署校验。
- 维护 PostgreSQL 日历表、同步游标及相关单元测试。
- 行情覆盖与日历形成两个事实来源，任一方滞后都会产生误拒绝。
- 普通重启不会运行 Compose profile 中 `restart: no` 的 `calendar-sync`，形成隐藏运维前置条件。
- 发布脚本必须等待外部日历源成功，即使本次发布功能与交易日历无关。

在当前执行模型下，这些成本高于交易日历带来的收益。

`market_trade_calendar` 当前仅有数千条自然日记录，存储成本不是本次决策依据；保留历史表也不会形成显著负担。本方案要消除的是双事实来源、外部同步和发布耦合，而不是为了节省数据库空间删除数据。

## 3. 目标、范围与非目标

### 3.1 目标

1. 有完整行情覆盖的标准 Bar 和 L2 任务不再因交易日历缺失、滞后或数据库日历查询失败而终止。
2. 正式回放日期只由任务选定的单一 Bar 来源决定。
3. 预热日期只由同一 Bar 来源在正式开始日前的完整覆盖决定。
4. L2 十档摘要和执行校验只围绕实际 Bar 日期进行。
5. 页面与开放 API 仍不能通过超出行情可用边界的开始、结束日期制造静默截断。
6. 任务快照继续记录实际使用日期、来源和版本，使历史结果可解释。
7. 服务器发布不再依赖外部交易日历接口。

### 3.2 本轮范围

- 标准自定义策略的 Worker Bar 加载。
- 内置/兼容标准策略的统一 Bar 加载。
- L2 Runner 的标准化 Bar 加载和 Quote 日期校验。
- `WARMUP_TRADING_DAYS` 的日期解析语义。
- L2 十档日级摘要预热工具的候选日期来源。
- 交易日历同步服务、部署调用和健康校验的退出。
- 相关错误分类、运行快照、测试、ADR 和使用手册。

### 3.3 非目标

- 不建设多标的组合市场时钟。
- 不引入新的定时任务、第三方日历源或 Python 依赖。
- 不删除 `market_trade_calendar` 表或历史记录。
- 不修改 ClickHouse 原始行情、导入批次或既有 Redis 数据。
- 不恢复已经失败的任务；失败任务保持不可变，修复后通过新任务验证。
- 不重新引入保存或提交阶段的全量行情预检。
- 不把任务范围内每个工作日都强制解释为应有行情日。

## 4. 新的唯一事实来源

### 4.1 日期来源优先级

每个任务仍只选择一个 Bar 来源，禁止跨来源拼接。选定来源后，正式回放日期按以下规则确定：

1. 新版 QMT 来源：取符合已发布、校验通过、路由完整、标的有效条件的覆盖日期。
2. 旧版 QMT 来源：取 `qmt_kline_coverage.status = complete` 的日期。
3. 正式映射 Bar 来源：取该 Provider 声明完整并实际返回 Bar 的日期。
4. 临时 Quote 聚合来源：取能够完成聚合且质量合格的实际 Bar 日期。

日期过滤、Bar 查询、来源选择和快照必须来自同一个 Provider 决策。不得先用 QMT 日期，再静默从其他来源加载缺失部分。

### 4.2 正式区间边界

删除交易日历后，不能把“有部分 Bar”误当成“任意请求范围都合法”。后端必须以选定来源的覆盖边界约束请求：

```text
sourceFirstDate <= startDate <= endDate <= sourceLastDate
```

页面继续使用覆盖元数据校验日期草稿；Worker 或共享解析器必须保留同等的服务端边界校验，覆盖网页、开放 API 和历史恢复入口，不能只信任前端。

边界内的周末、法定休市日、停牌日和未产生 Bar 的日期不单独制造回调，也不作为缺失日期阻断任务。实际回放日期是该区间内由选定来源声明完整且实际可加载的日期。

### 4.3 空区间和读取失败

以下情况继续失败：

- 请求范围完全超出来源覆盖边界；
- 范围内没有任何完整覆盖日期；
- 完整覆盖记录存在，但实际 Bar 查询结果为空；
- Bar 字段、时间、价格或格式不满足标准化要求；
- 来源读取超时或连接失败且有限重试耗尽；
- 任务要求的预热数据不足。

错误继续进入 `data.*` 分类，但内部原因必须区分“范围越界”“无完整覆盖”“实际 Bar 为空”和“来源读取失败”，避免统一包装掩盖诊断。

## 5. 正式 Bar 与预热日期语义

### 5.1 正式回放日期

`market_data.resolve_backtest_data()` 在调用方未提供历史任务已冻结的 `formalDates` 时，直接从候选来源覆盖记录生成正式日期，不再调用 `required_trade_dates()`。

历史任务或共享任务已经保存合法 `formalDates` 时，继续优先使用快照日期，并按快照中的 `provider`、`sourceDatabase`、`sourceTable`、`sourcePeriod` 和 `derivation` 约束来源；不得只冻结日期却重新选择另一个当前优先来源，也不得用新规则重算并覆盖历史快照。

### 5.2 预热日期

`WARMUP_TRADING_DAYS = N` 调整为：从正式开始日期之前，按同一来源取最近 `N` 个状态完整的行情日。停牌且没有 Bar 的日期不消耗预热数量。

预热必须满足：

- 与正式区间使用相同来源和来源周期；
- 日期严格早于正式开始日期；
- 结果按日期递增并恰好包含 `N` 个完整行情日；
- 实际加载后至少产生对应来源的预热 Bar；
- 预热 Bar 只初始化策略状态，不产生正式订单、收益和净值记录。

如果来源在开始日前不足 `N` 个完整行情日，按预热不足失败。系统不再承诺依据交易所日历识别“某个开市日完全漏采”；完整性的含义明确收敛为“所选来源发布并标记完整的行情日期序列”。这一语义变化必须写入使用手册并覆盖原方案中依赖交易日历连续性的描述。

### 5.3 快照字段

新任务的 Bar 快照至少保留：

- `provider`；
- `sourceDatabase`、`sourceTable`、`sourcePeriod`；
- `formalDates`、`warmupDates`；
- `warmupTradingDays`、`barCount`；
- `derivation`、来源/清单哈希和最后导入时间等既有字段。

不新增 `calendarValidated` 一类字段，避免在退出交易日历后继续制造无业务价值的兼容负担。历史快照中已存在的未知字段继续按 JSON 向后兼容读取。

## 6. 标准 Bar、L2 与摘要工具改造

### 6.1 标准自定义策略

调整 `backend/services/backtest_runner.py`：

- `_load_user_script_bars()` 不再在空快照时调用 `market_data.required_trade_dates()`；
- 无冻结日期时由 `resolve_backtest_data()` 使用覆盖元数据解析；
- 有历史冻结日期时继续使用快照；
- 将范围越界、无覆盖和实际读取失败保留为不同内部原因。

任务 `#171` 的回归用例必须模拟“行情覆盖至结束日、日历缺少结束日”，并证明任务仍可加载 `2026-09-24` 的完整 Bar。

### 6.2 内置/兼容标准策略

调整 `backend/services/bar_data.py`：

- `load_bars_with_snapshot()` 删除对 `_required_trade_dates()` 的依赖；
- QMT 路径直接使用覆盖解析结果；
- 正式映射表和临时聚合 Provider 按各自实际可用日期工作；
- 保持单任务单来源和现有回退边界，不因删除日历扩大跨源拼接。

### 6.3 L2 回放

`load_normalized_bars_with_snapshot()` 同样不再先查交易日历。L2 Runner 加载 Bar 后，继续以 `_bars_by_day(bars)` 的实际日期集合调用 `require_summarized_quote_dates()`。

这意味着 L2 完整性合同为：

```text
实际回放 Bar 日期 ⊆ Quote 摘要状态为 complete 的日期
```

若某日有 Bar 但 Quote 摘要不存在或不完整，L2 任务仍失败；若某日没有 Bar，则该日不进入 L2 回放，也不要求 Quote 摘要。

### 6.4 L2 Quote 摘要预热工具

`backend/l2_quote_coverage_sync.py` 不再通过 `list_open_trade_dates()` 构造候选日期。工具应增加或复用周期参数，从与 L2 回放一致的 Bar 来源取得范围内实际可用日期，再调用 `rebuild_quote_availability()`。

工具必须记录所用 Bar 来源和周期；不能退化为按周一至周五猜测交易日，也不能扫描与本次标的、周期无关的全部 Quote 明细。

## 7. 交易日历组件退出边界

### 7.1 运行链路退出

完成调用方迁移后，移除以下运行依赖：

- `market_data.required_trade_dates()`；
- 预热日期中的 `is_trade_calendar_range_covered()` 和 `list_open_trade_dates()`；
- `bar_data._required_trade_dates()`；
- L2 摘要预热对 `list_open_trade_dates()` 的调用；
- 已不被公开预检调用的 `_calendar_days()`、`_unknown_calendar_days()` 及相关死代码。
- `state_store` 中仅为该历史日历运行链路服务的写入、最新日期、范围覆盖和开市日期查询函数。

若最终静态搜索仍发现回测执行、预热、摘要或页面预检引用这些函数，视为退出未完成。

### 7.2 部署链路退出

调整 `deploy/compose.infrastructure.yml` 和 `scripts/deploy-server.sh`：

- 删除 `calendar-sync` 一次性服务；
- 删除发布过程中的日历同步调用；
- 删除 `verify_trade_calendar()` 发布门禁；
- 不以新的定时器、Cron 或常驻 Scheduler 替代；
- 保留 ClickHouse 连通性和实际服务健康检查。

部署脚本不再访问外部日历接口，发布成功与否只由迁移、服务健康、ClickHouse 连通性及改动范围内的回归决定。

### 7.3 代码与数据库兼容

`backend/trade_calendar_sync.py`、`backend/services/trade_calendar.py` 及其专用测试在所有调用方退出后删除，避免留下无人运行但仍需维护的半废弃组件。

保留：

- 已执行迁移中的 `market_trade_calendar` 表定义；
- 表内现有历史数据；
- 数据库角色对该历史表的既有权限。

本轮不新增“删除表”迁移。若未来有独立数据质量系统需要交易所日历，应在其上下文中重新定义来源、更新责任和可用性合同，不得重新把该历史表直接接回 Worker。

## 8. API、页面与历史兼容

### 8.1 API 与页面

- 日期范围和周期状态接口继续展示 Bar/L2 覆盖元数据，不增加交易日历字段。
- 现有页面日期选择器继续按 `firstDate`、`lastDate` 校验闭区间。
- 后端对网页和开放 API 使用相同的来源边界校验，防止绕过页面提交未来结束日期。
- 本轮不恢复逐日保存/提交预检，也不新增交易日灰显交互。
- 用户可见错误继续保持脱敏；管理员诊断应能看到准确内部原因。

若实施不修改前端接口结构和提示契约，则不改前端代码；不得为了“顺手清理”重构日期组件。

### 8.2 历史任务

- 已成功任务的结果、行情快照和正式日期不重算。
- 已失败任务保持失败，不原地补跑或修改错误记录。
- 历史任务保存了 `formalDates` 时继续按冻结日期读取。
- 历史任务没有冻结日期且被明确重新运行时，使用新规则，并生成新的运行事实；不得修改原任务结果。
- 公开共享回测继续读取保存时的结果和快照，不因当前覆盖范围变化而改写展示。

### 8.3 ADR 与使用手册

实施时新增 ADR 取代 `docs/adr/0004-unified-preflight-and-loading.md` 中“Worker 使用交易日历识别开市日和预热候选日”的决定，说明：

- 覆盖元数据和实际 Bar 日期是当前执行模型的唯一日期事实；
- 当前系统不提供独立市场时钟；
- 未来多标的组合若需要市场时钟，应作为新的领域能力设计。

同步更新 `docs/玄龄回测系统使用手册.md`，明确正式日期、预热日期、无 Bar 日期、范围越界和 L2 Quote 日期的实际语义。

`docs/30_统一回测数据预检与可用性引导方案.md`、`docs/31_统一回测数据预检实施纰漏修正方案.md` 和 `docs/33_策略代码声明预热与连续历史数据校验方案.md` 保留为历史方案，但应在文件开头增加“相关交易日历决定已被本方案及新 ADR 取代”的说明，避免实施者继续引用旧语义；不得重写历史方案正文伪造当时决策。

## 9. 实施步骤

1. 为 `resolve_backtest_data()` 补充来源边界校验和覆盖日期解析测试，先锁定无日历条件下的正式日期合同。
2. 改造预热日期查询，直接从同一来源取得开始日前最近 `N` 个完整行情日，并补齐不足、停牌和来源一致性测试。
3. 改造标准自定义策略加载，移除 `required_trade_dates()`，保留历史冻结日期优先级和错误根因。
4. 改造统一 `bar_data` 的标准与标准化加载函数，使内置策略和 L2 Runner 使用相同的覆盖驱动规则。
5. 改造 L2 Quote 摘要预热工具，以 Bar 来源的实际日期作为候选集合；验证 Worker 仍拒绝实际 Bar 日缺少 Quote 的任务。
6. 删除交易日历在预检中的未使用代码、`state_store` 专用访问函数，以及同步服务、专用测试和部署门禁；保留数据库历史表。
7. 更新错误诊断、ADR 和使用手册，不修改无关前端交互或依赖文件。
8. 运行本地单元、集成和真实行情回归；通过后执行远程普通用户样本回归。
9. 使用 `scripts/deploy-server.sh` 同批发布 backend、bar-runner 和 l2-runner，完成新任务与历史任务兼容检查。

## 10. 测试与验收

### 10.1 单元测试

1. 日历表为空、落后或数据库日历查询不可用时，覆盖完整的标准 Bar 任务仍能解析并加载。
2. 任务结束日等于 Bar 来源 `lastDate` 时可运行；结束日晚于 `lastDate` 时明确拒绝。
3. 范围内存在多个完整日期时只回放这些日期，不生成无 Bar 日期事件。
4. 范围内没有完整日期或实际 Bar 为空时仍返回数据错误。
5. 预热取同一来源开始日前最近 `N` 个完整行情日，数量不足时拒绝。
6. 历史快照提供 `formalDates` 时不调用当前日期解析覆盖它。
7. L2 只检查实际 Bar 日期的 Quote 摘要，有 Bar 无 Quote 时仍拒绝。
8. L2 摘要预热工具不读取 PostgreSQL 交易日历。
9. 部署合同测试确认发布脚本和 Compose 不再包含 `calendar-sync` 或日历校验门禁。

### 10.2 集成回归

至少覆盖以下三条实际链路：

- 标准自定义策略：复现任务 `#171` 的日期状态，确认 `2026-09-24` Bar 被加载并进入策略回调。
- 内置/兼容标准策略：相同区间完成回放，来源快照和实际日期正确。
- L2 策略：实际 Bar 日 Quote 完整时成功，故意缺少某个实际 Bar 日 Quote 时仍按 L2 数据缺失失败。

每条链路检查任务状态、Attempt 阶段、内部错误分类、`marketDataSnapshot`、正式日期、预热日期和结果可读取性。

### 10.3 历史兼容

- 打开并读取至少一条已有标准 Bar 成功任务和一条 L2 成功任务。
- 读取包含既有 `formalDates`/`warmupDates` 的历史快照，确认不被当前覆盖重算。
- 读取任务 `#171`，确认仍显示原始失败事实，不被迁移或修复代码改写。

### 10.4 远程普通用户样本回归

本改动涉及回测提交后的执行、结果生成和历史恢复。本地自动化测试通过后，必须只读取得远程服务器普通用户最近两条回测任务的保存代码和运行快照，并通过隔离的正常 Worker 链路验证：

- 标准 Bar 的领取、执行和最终结果生成；
- L2 或历史恢复中受本次改动影响的日期解析链路；
- 任务快照未泄漏或改写生产样本。

生产样本代码、参数和快照不得写入仓库、测试固件、文档、对话或持久日志。无法访问远程、样本不足或缺少对应行情时，必须标记“远程普通用户样本回归待验证”并说明原因。

### 10.5 验收标准

1. 任务 `#171` 所代表的“行情已完整、日历滞后”场景不再失败。
2. 停止或删除交易日历同步服务后，标准 Bar 和 L2 回测仍可正常执行。
3. 网页和开放 API 均不能提交超出来源覆盖边界后被静默截断的成功任务。
4. 正式日期、预热日期和 L2 Quote 校验均来自同一任务实际使用的 Bar 来源。
5. 任务快照能够说明实际回放日期、预热日期、来源、周期和版本。
6. 没有实际 Bar、有 Bar 无 Quote、预热不足和来源读取失败仍分别得到正确结果。
7. 发布脚本不再同步或校验交易日历，且无需新增定时运维任务。
8. 历史任务、共享结果和既有失败事实保持可读取且不被重算。

## 11. 风险、自审与控制

| 风险 | 控制措施 |
| --- | --- |
| 删除日历后，API 请求未来结束日期但仍回放此前 Bar | 在服务端以选定来源 `firstDate/lastDate` 校验请求边界，不能只依赖页面。 |
| 行情覆盖漏掉整日时无法区分休市与漏采 | 明确接受覆盖发布状态为当前执行事实；批次完整性由行情导入链路负责，不由 Worker 二次推断。 |
| 预热“连续交易日”语义变化 | 手册明确改为同一来源最近 N 个完整行情日，并用快照保存实际日期。 |
| L2 同时缺 Bar 和 Quote 的日期被跳过 | 明确 L2 只对实际 Bar 日期负责；未来若要求市场级逐日完整性，应在导入质量域实现。 |
| 删除同步服务后其他隐含调用失败 | 合入前对全仓执行静态搜索，并覆盖部署合同、CLI 和 Worker 集成测试。 |
| 回滚到旧版本时旧代码仍要求日历 | 回滚前临时执行旧版日历同步命令补齐当天，再恢复旧镜像；本轮不删表以支持该回滚。 |
| 修改范围扩张到日期组件或行情导入 | 本轮不修改前端交互和 ClickHouse 导入逻辑，仅调整日期事实消费方。 |

### 11.1 方案自审结论

- **是否真正消除维护成本**：是。方案不是新增日历 Scheduler，而是删除运行和发布调用方及同步组件。
- **是否出现新的隐式事实来源**：否。正式日期、预热日期和 L2 校验均收敛到任务选定的 Bar 来源。
- **是否放开未来日期**：否。来源边界校验替代日历区间校验，并覆盖开放 API。
- **是否改变历史结果**：否。历史快照和结果只读兼容，失败任务不原地修复。
- **是否掩盖真实数据错误**：不掩盖。空 Bar、范围越界、预热不足、Quote 缺失和读取失败继续阻断并保留内部根因。
- **是否为未来组合回测预埋错误抽象**：否。当前明确不把交易日历等同于市场时钟；组合市场时钟未来单独设计。

## 12. 发布、观察与回滚

本改动影响 backend、bar-runner、l2-runner、部署脚本和策略运行时行为。服务器必须通过 `scripts/deploy-server.sh` 同批发布相互依赖的服务；不得只重启其中一个服务。

发布前：

1. 检查排队和运行中的标准 Bar/L2 任务。
2. 等待运行中 L2 任务完成、由用户取消，或经明确确认后标记为发布中断。
3. 确认本地测试和远程普通用户样本回归状态。
4. 确认部署脚本不再调用 `calendar-sync`，且私有 `deploy/.env` 未被覆盖。

发布后：

1. 检查 backend、bar-runner、l2-runner 和前端健康状态。
2. 运行一个结束日在最新行情日的标准 Bar 任务。
3. 运行一个小区间 L2 任务并检查 Quote 日期校验。
4. 打开标准 Bar、L2 和共享历史任务各一条。
5. 查询任务 Attempt 和集中日志，确认不再出现“交易日历未覆盖本次回测区间”。

本轮无数据库迁移、无缓存结构变更。若出现回归，可恢复前一版本镜像；由于历史日历表仍保留，回滚前补齐旧代码要求的日历范围即可恢复旧运行合同。不得通过修改历史任务或结果数据完成回滚。
