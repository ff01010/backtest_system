## 2. Bug 一：不同回测模式缺少统一日终估值契约

### 2.1 根因与同源表现

账户账本在每笔成交后会用成交价更新持仓标记价。该行为适合保留成交事实和盘中账户状态，但日终结算完成后若直接生成账户快照，就会把最后一笔成交价误当成日终估值价。

L2 与标准 Bar 的具体触发方式不同，但根因一致：

- L2：尾盘按真实盘口价恢复底仓，盘口成交价覆盖账户标记价；
- 标准 Bar：尾盘恢复成交包含滑点，带滑点的成交价覆盖账户标记价；
- 收益归因：底仓持有收益和增强未实现收益继续使用当天最后一根有效 Bar 收盘价。

因此差额近似为：

```text
日终剩余持仓数量 ×（最后成交价 - Bar 收盘价）
```

并触发：

```text
增强收益与账户收益无法对账
```

### 2.2 统一日终结算契约

所有当前及未来回测模式必须通过同一个日终结算模块生成每日最终快照。该模块提供稳定的日终结算接口，并固定执行顺序：

1. 接收当日最后一根有效 Bar、账户账本和该回测模式生成的日终结算指令。
2. 按该模式既有撮合规则完成撤单、平仓、底仓恢复等日终成交。
3. 所有日终成交完成后，统一使用最后一根有效 Bar 收盘价重新标记剩余持仓。
4. 重新估值后，由模块生成并返回当日唯一的最终账户快照。
5. 最终快照进入收益归因与严格对账，禁止调用方在模块外再次生成另一份日终快照。

职责边界如下：

- 策略类别或执行引擎只负责提供日终结算策略及订单，不得决定日终估值价格；
- 撮合层继续决定真实成交价、滑点、现金变化、手续费和已实现收益；
- 日终结算模块统一决定剩余持仓估值价和最终账户快照；
- 收益归因只消费统一快照，不再自行推导另一套账户日终价值；
- 新增策略类别必须接入该接口，不得复制一套独立的“成交后生成快照”分支。

统一后保持以下关系：

```text
账户总收益
= 底仓持有收益
+ 增强已实现收益
+ 增强未实现收益
```

当天没有有效 Bar 时任务失败，不使用最后成交价、盘口价或其他价格兜底。本次信任现有 Bar 数据完整度，不增加约定收盘时刻校验；数据被错误标记为完整时，按独立数据质量问题处理。

### 2.3 已完成：L2 日终估值修复

Ticket 01 已在 L2 日终路径完成以下修复：

1. 按现有逻辑撤销未完成订单。
2. 按真实 L2 盘口完成增强仓结算和底仓恢复。
3. 结算后用最后一根有效 Bar 收盘价重新标记剩余持仓。
4. 重新标记后生成每日账户净值。
5. 保留现有严格收益对账和 0.05 元舍入容差。

该修复解决了已知 L2 任务，但目前仍属于 L2 路径内实现。Ticket 03 需要将其收敛到统一日终结算接口，避免后续模式再次遗漏。

### 2.4 待实施：标准 Bar 与未来策略类别接入

标准 Bar 至少存在两条独立日终路径，均可能在尾盘成交后直接生成快照：

- 带事件回传的日终路径；
- 普通批量或流式执行使用的日终路径。

Ticket 03 实施时需要：

1. 提取与具体策略类别无关的日终结算模块和小型接口。
2. 将标准 Bar 的事件、批量和流式执行路径全部接入该接口。
3. 将 L2 已有修复接入同一接口，消除重复的重新标记逻辑。
4. 保留账户账本“成交后按成交价标记”的现有盘中行为，不全局修改成交入账语义。
5. 用一个仅用于测试的未来策略类别证明：只提供日终订单策略并接入接口，即可自动获得统一估值，无需新增估值分支。
6. 在实际行为修改时同步更新 `docs/玄龄回测系统使用手册.md`，明确成交价与日终结算价的职责。

## 3. Bug 二：任务编号错误信息不完整

### 3.1 原因

原错误记录虽然包含任务编号、来源和阶段，但普通 `ValueError` 会被统一转换为：

```text
errorCode=internal.unexpected
reason=发生未预期内部错误，需要维护人员处理
```

同时，日志索引使用 Runner 通配符，没有指出实际执行任务的实例，管理员仍需扫描容器并对照代码推导原因。

### 3.2 已完成修复

Ticket 02 已复用现有 `system_error_log` 和 `context_json` 完成以下改造，未增加数据库字段：

1. 使用受控异常 `ResultReconciliationError` 表示结果收益对账失败。
2. 映射稳定错误码 `result.overlay_reconciliation_failed`。
3. 管理员原因保存明确结论“增强收益与账户收益无法对账”。
4. Runner 将实际 `workerId` 写入错误上下文和日志索引；可直接取得时同时记录 `tradeDate`。
5. 错误分类为 `result`，标记为不可直接重试。
6. 普通用户只看到安全提示：平台结果生成失败，无需修改策略，请提供任务编号联系管理员。
7. 不保存用户源码、完整计算现场或敏感运行数据。

任务编号的目标是让管理员快速得到稳定错误分类、发生阶段和准确日志位置，而不是在普通用户页面直接展示内部诊断。

### 3.3 通用错误兼容规则

- 所有错误继续共用任务编号、错误码、分类、来源、阶段、异常类型、是否可重试和发生时间；
- `context_json` 只保存快速定位所必需的少量安全字段，不要求还原完整错误现场；
- 未分类的新错误继续使用 `internal.unexpected`，首次排查清楚后再增加稳定错误码，无需修改数据库表结构；
- 容器删除后原始 Docker 日志可能丢失，集中日志属于独立运维能力，不纳入本次修复。

## 5. 测试计划

### 5.1 统一契约测试

1. 验证日终结算固定执行“完成成交 → Bar 收盘价重新估值 → 生成唯一快照”。
2. 验证调用方无法用最后成交价替代日终结算价，也不在模块外生成第二份最终快照。
3. 验证无有效 Bar 时明确失败，不回退到成交价。
4. 用测试专用的未来策略类别接入接口，确认无需新增估值条件分支。

### 5.2 标准 Bar 回归

1. 覆盖任务 323 的触发形态：非零滑点、卖出底仓、尾盘买回。
2. 覆盖事件、批量和流式执行路径。
3. 验证成交价、现金、手续费和已实现收益仍使用原撮合结果。
4. 验证日终剩余持仓与账户净值使用最后一根有效 Bar 收盘价。
5. 覆盖多交易日及真实账目差异，确认合法任务可对账、真实差异仍被阻断。

### 5.3 L2 与错误诊断回归

1. 保留尾盘盘口成交价与 Bar 收盘价不同的 L2 回归用例。
2. 验证 L2 成交事实不变，日终净值继续按 Bar 收盘价结算。
3. 对账失败继续返回 `result.overlay_reconciliation_failed`。
4. 管理员通过任务编号可看到明确原因、实际 `workerId` 和精确日志索引。
5. 普通用户响应不包含内部计算数据、源码或堆栈。

### 5.4 完整与远程普通用户回归

1. 执行受影响模块测试和后端完整 pytest。
2. 验证历史成功、失败任务仍按保存时的快照和语义读取。
3. 按仓库规则，只读取得远程服务器普通用户最近两条任务的冻结代码和运行快照。
4. 通过隔离的正常 Worker/Runner 链路使用修改后代码运行，不在宿主机直接执行用户源码。
5. 验证任务提交、排队、领取、执行及最终结果生成，并至少覆盖一条本次受影响的日终恢复场景。
6. 远程条件不足时明确标记“远程普通用户样本回归待验证”。

## 8. 方案自审

1. 修复边界已从 L2 特例提升为统一领域契约，可覆盖标准 Bar 和未来策略类别。
2. 成交层负责成交事实，日终结算模块负责结束时点估值，职责边界清晰。
3. 保留成交后按成交价标记的盘中行为，避免为修复日终问题改变既有盘中语义。
4. 统一模块拥有最终快照生成权，消除多个路径各自修补造成的再次遗漏风险。
5. 保留严格收益对账，不通过放宽容差或隐藏错误换取任务成功。
6. 数据库、前端、历史结果重算、集中日志和收盘数据质量治理均未扩大到本次范围。
