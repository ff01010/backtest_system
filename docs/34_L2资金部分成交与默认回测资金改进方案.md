# L2 资金部分成交与默认回测资金改进方案

日期：2026-08-31  
状态：待实施  
关联问题：L2 市价开多订单在资金不足时跳过整档盘口，之后出现延迟的 1、2 股成交。

## 1. 背景与结论

任务 4a38e0cb-ea3b-446c-8c69-1b6ce304f8a1 证明了当前 L2 撮合存在资金处理缺陷。

该任务的实际执行算法为 immediate（立即成交），并非 twap（时间加权平均价格）。其中一笔 1200 股市价开多信号产生于 2026-04-16 09:32:05，后续先后仅成交 137、48、10、2、1、1 股，余量 1001 股日终撤单。

现有撮合器对每个盘口档位先取“订单剩余量与档位量”的较小值，再整体判断该数量是否可负担。若可用资金不足以买入该整档数量，则整个档位不成交，也不缩小为可负担数量。因此，订单会跳过本可部分成交的深度，持续等待后续恰好较小的档位，表现为数十分钟后仍成交 1、2 股。

本方案的结论如下：

1. 保持 immediate（立即成交）的语义：订单在严格后续 Quote 进入撮合；首个 Quote 不足时继续等待，不因部分未成自动撤单。
2. 对 L2 开多订单，按“订单剩余量、盘口档位量、可负担数量”三者最小值成交。
3. 将资金不足原因写入订单与成交明细，明确区分资金不足、盘口不足和日终撤单。
4. 将新建回测策略的 initialCapital（初始资金）默认值由 1,000,000 调整为 10,000,000，但绝不改写已有策略或历史任务快照。

## 2. 目标与边界

### 2.1 目标

1. 资金不足时不再整档跳过，应执行资金允许的部分成交。
2. 保留未成交订单的后续 Quote 等待能力，符合实盘中未撤单委托的持续成交逻辑。
3. 用户能在成交明细中看出某笔成交或未完成订单受可用资金限制。
4. 降低默认资金过低导致的无意资金约束，同时保持策略和历史结果可复现。

### 2.2 范围

- backend/l2/engine.py 的主动十档盘口开多撮合。
- L2 订单事件、成交元数据、结果适配与前端成交明细展示。
- 新建回测页面与新建策略的默认 initialCapital（初始资金）。
- 相关单元、回归和前端类型测试。

### 2.3 非目标

1. 不把 immediate（立即成交）改成首个 Quote 后自动撤余量。
2. 不改变策略主动撤单、日终撤单、涨跌停、T+0、可卖数量或十档价格优先级规则。
3. 不改变已保存策略配置、已创建账户或历史任务的 initialCapital（初始资金）快照。
4. 不在本项中处理“界面选择 TWAP、实际任务保存为 immediate”的参数链路问题；该问题需独立复现、定位和验收。
5. 不修改原始 L2 行情表、ClickHouse 数据或 Redis 缓存。

## 3. 现状根因

当前主动盘口撮合的核心逻辑等价于：

候选数量 = min(订单剩余量, 当前档位量)  
若候选数量整体买得起：成交候选数量  
否则：本档完全跳过

例如，订单还剩 1200 股、卖一有 1707 股、账户只能买 900 股时，当前实现会尝试买 1200 股并失败，随后继续尝试其他完整档位。它不会买入可负担的 900 股。

在关联任务中，信号后的 09:32:08 卖一深度为 1707 股。若资金允许完整买入，理论上应在卖一一笔完成 1200 股；若资金仅允许部分买入，理论上应成交可负担数量。当前结果没有在该快照成交，而是在后续 09:32:35 的卖一仅有 137 股时才成交，符合“整档买不起即跳过”的缺陷特征。

同日另一笔 1200 股订单在 09:32:02 已按四个价格档成交 332 + 300 + 190 + 378 = 1200。这说明十档跨档遍历本身有效，问题限定在资金约束的整档判定方式。

## 4. 目标成交语义

### 4.1 L2 开多逐档数量计算

对每一个严格后续且可撮合的 Quote 档位，计算：

depthQuantity（档位可用量） = 当前档位可用数量  
candidateQuantity（候选数量） = min(remainingQuantity（订单剩余量）, depthQuantity（档位可用量）)  
affordableQuantity（可负担量） = 当前可用现金在该价格与费用下可买入的最大数量  
fillQuantity（实际成交量） = min(candidateQuantity（候选数量）, affordableQuantity（可负担量）)

其中：

- 仅对 OPEN_LONG（开多）计算 affordableQuantity（可负担量）；平仓、开空保持既有规则。
- 费用计算必须与实际成交费用模型共用，包含最低佣金、过户费和其他已配置费用，避免预估与落账不一致。
- 原始委托已在提交时完成 A 股最小下单量与数量步长校验；部分成交沿用现有 L2 成交语义，可接受盘口中出现的非整手剩余量，不对部分成交再次按新委托规则拒绝。
- 若资金成为限制因素，affordableQuantity（可负担量）必须按 InstrumentRules.order_quantity_step（标的开仓数量步长，通常为 100 股）向下取整；不足最低开仓数量时为 0，不发起零股买入。
- 上述取整只约束“资金限制下新增可买数量”，不改变盘口已导致的零股部分成交：若订单剩余量或当前档位量本身为 137 股，且资金足以覆盖该 137 股，则仍可按 137 股成交；若订单已因真实部分成交仅余 63 股，且资金足够覆盖该全部余量，也允许完成该 63 股余量。

### 4.2 等待、取消与终态

| 场景 | 目标行为 |
| --- | --- |
| 当前档位深度不足 | 吃完当前可成交深度，剩余订单等待后续 Quote。 |
| 当前档位整档买不起但可买部分 | 成交可负担部分，保留余量等待后续 Quote。 |
| 当前可负担量为 0 | 不成交、不改变订单状态，保留订单等待后续 Quote、策略撤单或日终撤单。 |
| 策略显式撤单 | 按既有策略订单事件和撤单规则终结。 |
| 日终 | 按既有日终撤单规则撤销普通未完成订单；日内模式的系统强平规则保持不变。 |

immediate（立即成交）的“立即”指订单在严格后续 Quote 获得撮合资格，不代表保证全成，也不代表系统替用户撤单。

### 4.3 资金不足说明

资金不足说明必须可追溯但不能为每条 Quote 重复生成大量事件。

1. 发生“可负担量小于候选档位量且大于 0”的部分成交时，在成交元数据记录 fundingLimited（受资金限制）、depthQuantity（档位量）、affordableQuantity（可负担量）、remainingQuantity（成交后剩余量）和 availableCashBefore（成交前可用现金）。
2. 前端成交明细将该笔显示为“资金不足限制，已成交可负担部分”，同时保留实际成交价格和数量。
3. 首次出现“可负担量为 0”时，订单事件记录一次 funds_insufficient（资金不足）诊断；同一订单后续 Quote 不重复写入。去重标记写入 L2Order.metadata（订单运行时元数据）。
4. 若订单最终因日终撤单且曾被资金限制，撤单原因显示“日终撤单；期间受可用资金限制”，避免用户误判为单纯盘口不足。
5. 历史任务缺少上述字段时按原结果展示，不补造资金不足说明。
6. funds_insufficient（资金不足）仅是结果诊断，不属于订单状态迁移；不得传入策略 on_order_event（订单事件回调），以免策略误判为成交、撤单或拒单。

## 5. 实现方案

### 5.1 后端撮合改造

在 backend/l2/engine.py 中新增可测试的最大可负担数量计算函数。该函数输入订单、档位价格和候选数量，基于现有费用预览逻辑返回从 0 到候选数量之间的最大可成交整数数量。

建议使用二分查找或等价单调求解，不复制费用公式；每次候选量都复用现有费用预览逻辑，确保最低佣金等阶梯费用也正确。

按盘口深度撮合的逐档数量由当前的两项最小值改为“候选数量、可负担数量”的两步计算。_apply_fill（执行成交）必须返回实际成交量：未成交时返回 0，成交时返回实际成交数量。盘口 budget（档位预算）只能扣减该返回值，不能扣减 candidateQuantity（候选数量）；否则资金不足的前序订单会错误占用盘口，影响同一 Quote 的后续订单。

当可负担量为 0 时，不调用实际成交方法，也不让订单进入终态；同时通过 L2Order.metadata（订单运行时元数据）的订单级去重状态记录资金不足诊断。此状态仅用于解释结果，不调用策略 on_order_event（订单事件回调）。

### 5.2 结果与前端展示

后端在 Fill（成交）元数据及订单事件中新增资金限制字段；backend/l2/result_adapter.py 必须将 fundingLimited（受资金限制）、affordableQuantity（可负担量）和 availableCashBefore（成交前可用现金）映射为 BacktestTrade（回测成交明细）的可选字段。不得只写入 Fill 元数据，因为现有结果适配会丢弃未映射的元数据。

前端在信号/成交明细中：

- 对 fundingLimited（受资金限制）的部分成交，在保留策略原始说明的前提下追加展示“资金不足限制，已成交可负担部分”；
- 对最终日终撤单且有资金限制记录的订单展示对应原因；
- 不将资金不足标为系统异常，也不影响正常的已成交收益计算。

### 5.3 默认初始资金

将回测页面 DEFAULT_PARAMS.initialCapital（默认参数的初始资金）由 1000000 调整为 10000000。

同时检查并统一所有“新建但尚未保存”的默认来源，包括新建策略、恢复缺少快照的旧草稿及新建账户预填。运行请求、策略配置和账户实体均继续使用用户实际填写或已保存的数值，不以服务端强制覆盖。

| 数据来源 | 改造后行为 |
| --- | --- |
| 新开回测页面 | 默认显示 10,000,000。 |
| 新建策略并保存 | 保存用户当前值；未修改时保存 10,000,000。 |
| 已保存策略 | 加载其原 initialCapital（初始资金），不迁移。 |
| 历史任务/重新运行 | 优先使用任务快照；快照存在时绝不替换为新默认值。 |
| 已创建回测账户 | 使用账户自身资金，不修改账户记录。 |
| 外部 API | 继续要求显式传入 initial_capital（初始资金），不新增隐式默认。 |

## 6. 验证方案

### 6.1 后端单元与回归测试

1. 单档深度足够且资金足够：订单一次成交，结果与现有行为一致。
2. 首档不足、后续档位补足：按价格优先跨档成交，成交量守恒。
3. 整档买不起但可买部分：成交按标的交易单位向下取整后的可负担数量，不整档跳过。
4. 可用资金不足以买入最低开仓数量：订单保持等待状态，记录一次资金不足诊断，不重复写事件。
5. 后续 Quote 价格下降或账户资金释放：剩余订单可继续成交。
6. 资金受限后日终撤单：撤单原因包含资金限制说明，数量满足“请求量 = 成交量 + 取消量 + 拒绝量”。
7. 最低佣金、过户费、卖出印花税等费用配置下，可负担量不超出真实可用资金。
8. 同一 Quote 存在两笔买单：前一笔资金不足时只扣其实际成交量，后一笔仍可使用剩余盘口；前一笔未成交时不得消耗盘口预算。
9. funds_insufficient（资金不足）仅写入结果 orderEvents（订单事件），不触发策略 on_order_event（订单事件回调）。
10. 资金只够买 99 股时不成交；资金够买 199 股时最多成交 100 股；计算均包含手续费。
11. 当前盘口为 137 股且资金足够时可成交 137 股；订单因既有部分成交仅余 63 股且资金足够时可完成 63 股。
12. TWAP 子单经过相同 L2 撮合器时，同样遵守部分可负担成交和执行窗口取消规则。
13. L2 订单事件和策略 on_order_event（订单事件回调）的 accepted、partial_fill、filled、cancelled 时序不回退。

### 6.2 前端验证

1. 新开回测页面默认初始资金为 10,000,000。
2. 已保存策略加载其历史初始资金，不被新默认值覆盖。
3. 历史任务重新运行保留任务快照资金。
4. 资金限制字段从 Fill 元数据经结果适配后可到达成交明细；策略原始说明仍保留。
5. 资金限制部分成交、资金不足未成和日终撤单均展示可读说明。
6. TypeScript 类型检查通过。

### 6.3 真实回测复核

使用 688008.SH 的关联日期复核：

- 对应信号在资金受限时不再跳过整档；
- 订单明细能说明资金限制；
- 未撤单余额仍仅在后续 Quote、策略撤单或日终时发生状态变化；
- 结果中不再出现由“整档买不起”造成的无解释延迟零股成交。

## 7. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 费用存在最低收费，简单除法高估可买数量 | 使用现有费用预览函数进行单调求解，并以实际落账断言兜底。 |
| 资金不足订单错误消耗盘口预算 | _apply_fill（执行成交）返回实际成交量，撮合循环仅扣减该数量；覆盖同一 Quote 多订单回归。 |
| 每条 Quote 写资金不足事件导致结果膨胀 | 同一订单只记录首次不可负担诊断，部分成交信息写入实际成交元数据。 |
| 资金不足诊断改变策略状态机 | 诊断仅进入结果 orderEvents（订单事件），不回调策略 on_order_event（订单事件回调）。 |
| 修改部分成交影响策略脚本状态机 | 保持既有订单事件类型与顺序，仅补充元数据；覆盖连续订单事件回归。 |
| 新默认资金误改历史结果 | 只改新建默认值；已保存配置、账户和历史任务始终以快照优先。 |
| 将资金问题误认为 TWAP 问题 | 结果详情始终展示实际 executionAlgorithm（执行算法）与参数快照；TWAP 参数链路作为独立问题跟踪。 |
