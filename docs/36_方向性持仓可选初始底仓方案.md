# 方向性持仓可选初始底仓方案

## 1. 背景与问题

现有回测体系将 `directional_holding（方向性持仓策略）` 定义为“不得设置底仓”，将 `core_position_overlay（底仓增强策略）` 定义为“必须设置底仓、仅日内做 T、日终恢复底仓”。该排他规则与新的业务需求冲突：方向性策略也需要能够从已有持仓状态开始回测，并由 A 股 `T+1` 可卖约束决定实际订单是否可执行。

同时，底仓不能成为方向性策略的默认部分。大量只做多策略应从全现金、零持仓开始回测；若遗留底仓参数，底仓价格波动会混入策略收益并造成结果解释错误。

本方案将“初始底仓”定义为可选的账户初始状态，而不再作为区分方向性持仓和底仓增强策略的唯一条件。

## 2. 目标与边界

### 2.1 目标

1. 允许方向性持仓策略显式配置初始底仓。
2. 默认无底仓，确保只做多或普通方向性策略以全现金、零持仓开始。
3. 初始底仓进入统一账户、持仓和 `T+1` 可卖数量管理，不绕过撮合规则。
4. 保留底仓增强策略必须日终恢复底仓、只做日内增强的既有业务语义。
5. 不以是否存在底仓自动推断策略类别，历史任务按自身快照展示。

### 2.2 不在本期范围内

- 自动根据 `long / short / flat` 信号换算目标股数；
- 改写策略对下单数量、止损或仓位比例的决定权；
- 真实融券券源、保证金、借券费用与强平；
- 多标的底仓、组合权重和跨标的资金分配。

## 3. 已确认设计决策

### 3.1 初始底仓是可选账户状态

方向性持仓中的底仓表示回测开始时账户已持有的多头股票，不代表策略必须长期保留该仓位，也不代表信号自动产生任何股数。

```text
未启用初始底仓：现金起跑，初始持仓为 0
启用初始底仓：现金 + 用户填写的初始持仓起跑
```

底仓开启后，其市值和价格波动参与账户权益和收益；关闭后，回测请求、策略快照和运行上下文中的底仓数量与成本必须均为 0，避免历史表单残留影响收益。

### 3.2 策略类别与初始底仓解耦

保留以下两种业务语义，但不再通过底仓字段推断：

| 策略类别 | 初始底仓 | 日终规则 | 业务语义 |
| --- | --- | --- | --- |
| `directional_holding` | 可选 | 保留真实实际仓位 | 策略可跨日持仓，并可从已有仓位开始。 |
| `core_position_overlay` | 必填 | 恢复为配置底仓 | 围绕固定底仓做日内增强。 |

方向性持仓中设置底仓，不会自动切换为底仓增强策略，也不会启用尾盘恢复或做 T 限额。

### 3.3 策略决定订单，账户执行 T+1 约束

方向性策略继续根据行情、账户、可选研究信号和自身逻辑输出订单数量。底仓仅作为初始持仓进入账户；撮合引擎依据真实持仓、可卖数量和 `T+1` 规则接纳、部分成交或拒绝卖出订单。

前端不增加 `long / flat / short` 到目标股数的换算预览。研究信号只作为策略输入，不能绕过策略或 `T+1`。

## 4. 数据与账户语义

### 4.1 请求字段

在保留既有 `baseQuantity（底仓数量）` 与 `baseCostPrice（底仓成本价）` 的基础上，新增显式字段：

```text
initialPositionEnabled（启用初始底仓）: boolean
```

新任务校验：

| 条件 | 规则 |
| --- | --- |
| `initialPositionEnabled=false` | `baseQuantity=0` 且 `baseCostPrice=0`。 |
| `initialPositionEnabled=true` | `baseQuantity>0` 且 `baseCostPrice>0`。 |
| `strategyCategory=core_position_overlay` | 初始底仓必须启用，并沿用既有日终恢复和做 T 约束。 |
| `strategyCategory=directional_holding` | 可启用或关闭初始底仓；不得因底仓存在改变为底仓增强。 |

`strategyCategory（策略类别）` 必须由用户显式选择并写入快照，禁止再按 `baseQuantity` 或 `t0Enabled` 自动推断新任务类别。

### 4.2 初始权益与成本

启用初始底仓时：

- `initialCapital（初始资金）` 表示可用现金；
- 初始账户权益为初始现金加初始底仓市值；
- `baseCostPrice` 用于建立初始持仓成本、已实现和未实现盈亏基准；
- 初始底仓视为回测开始日前已持有的库存，首个交易日可按 `T+1` 规则作为可卖数量参与撮合；
- 方向性持仓不要求收盘恢复到底仓，实际仓位随策略订单跨日延续。

关闭初始底仓时，账户以初始现金和零持仓开始，收益不应包含任何底仓持有收益。

### 4.3 策略上下文与结果

无论是否启用初始底仓，策略均可从既有账户上下文读取当前净持仓、现金、权益和可卖数量。方向性策略允许底仓后，不增加新的强制交易字段；底仓增强策略特有的做 T 额度和恢复指标继续仅在其类别下提供。

每条新回测结果和历史快照必须记录：

- `strategyCategory`；
- `initialPositionEnabled`；
- 底仓数量、成本价和初始权益口径；
- 持仓规则、成交模型和策略快照。

## 5. 前端设计

### 5.1 方向性持仓配置

复用现有回测页面，不新增页面。在方向性持仓配置中增加：

```text
[ ] 启用初始底仓
```

- 默认关闭。
- 关闭时隐藏底仓数量和成本价，保存与提交时强制写入 `0`。
- 开启时显示底仓数量、成本价及“初始持仓受 T+1 可卖规则约束”的简短说明。
- 用户关闭开关时立即清空页面状态中的底仓数量与成本价，防止从旧方案或类别切换带入残留值。
- 不显示额外的目标仓位推演表，不新增复杂交互。

### 5.2 底仓增强配置

底仓增强策略保持已有强制配置：初始底仓必填、做 T 启用、日终恢复底仓。页面继续按其业务语义展示相关设置与结果指标。

切换策略类别时：

- 切至底仓增强：要求填写或确认初始底仓，并显示日终恢复说明；
- 切至方向性持仓：保留“启用初始底仓”开关，由用户决定是否保留；不再强制清零；
- 切至方向性持仓且关闭开关：清零底仓字段。

### 5.3 历史与结果展示

历史回测和结果详情应明确展示“无初始底仓”或“初始底仓：数量、成本价”。方向性策略有底仓时，仍展示方向性持仓的总收益、基准收益、超额收益、实际仓位和跨日盈亏；不得改用底仓增强的做 T 超额收益指标。

## 6. 后端与执行器改造

1. 扩展请求 schema、前端参数、策略方案、版本快照、任务负载和结果快照，支持 `initialPositionEnabled`。
2. 修改现有前后端校验，允许 `directional_holding` 在开关开启时携带有效底仓。
3. 修改类别归一化和历史读取逻辑：新任务只信任显式 `strategyCategory`；旧任务按保存参数回退推断，且不回写历史数据。
4. 在标准 Bar 与 L2 执行器中统一初始化初始底仓、成本、现金、可卖数量和 `T+1` 库存。
5. 确保方向性持仓不会执行底仓增强的尾盘恢复、系统结算或做 T 额度逻辑。
6. 若策略运行时、Worker 请求模型、缓存序列化或结果 JSON 结构变化，递增对应版本或命名空间，并保持旧任务读取兼容。

## 7. 与既有方案的关系

本方案替代 `docs/12_策略类别与持仓回测体系改造方案.md` 中“方向性持仓策略不得设置底仓”的规则，并修正 `docs/32_标准Bar分钟数据派生日线与方向性持仓运行支持方案.md` 中“方向性持仓不设置底仓”的约束。

除上述规则外，既有方案中关于：

- 底仓增强策略的日终恢复和做 T 语义；
- 历史任务不重算；
- 方向性持仓的跨日真实持仓和收益口径；
- `T+1`、费用和成交明细的可追溯要求；

均继续有效。

实施完成后，应在第 12、32 号方案的文首或相关章节补充“已由本方案替代”的引用，避免后续读者按旧规则实现。

## 8. 验收标准

1. 新建方向性持仓方案默认无初始底仓，回测从全现金和零持仓开始。
2. 方向性持仓可显式启用初始底仓，并以该仓位、成本和可卖数量开始回测。
3. 关闭初始底仓后，任何残留底仓参数都不能影响请求、快照、账户权益或收益。
4. 方向性持仓有底仓时，不触发日终恢复底仓或底仓做 T 额度逻辑。
5. 底仓增强策略仍要求底仓，仍执行既有日终恢复和做 T 语义。
6. 新任务类别不由底仓数量自动推断；旧任务仍按历史快照正确展示。
7. 覆盖前端开关清理、请求校验、首日可卖数量、跨日持仓、类别切换、历史兼容和收益口径的自动化测试。

## 9. 发布与风险

- 本方案影响前端、后端、标准 Bar Worker、L2 Runner、策略运行时和历史结果读取；发布必须使用 `scripts/deploy-server.sh` 同批部署相互依赖服务。
- 发布前检查排队和运行中的 L2 任务；如重建 L2 Runner 会中断任务，必须等待完成、由用户取消或经明确确认后标记为发布中断。
- 不修改已执行迁移；如新增持久化列、约束或索引，必须新增幂等迁移并由 migrate 服务执行。
- 未实际完成的服务器回测、真实行情或真实融券验证不得写为已通过。
