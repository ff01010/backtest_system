# 单标的/多标的回测与投研因子、策略资产接入建设方案

## 一、建设目标与边界

### 1.1 建设背景

投研平台已经形成因子库、策略库和组件中心；回测系统负责验证这些投研资产在历史行情中的交易表现。

为避免行业术语混淆，本方案统一使用“因子系统交易回测”，产品界面可简称“因子回测”。它特指：用户选择股票池、开仓、普通退出、止盈、止损、时间退出和仓位等不同职责的因子，由回测系统组成一套可执行的单标的或多标的因子系统，计算目标持仓并完成模拟成交。它不是只计算 IC、RankIC、分组收益等统计指标的因子有效性分析。

根据《策略中心与组件中心架构设计方案 V1.2》，投研平台的交付形态不是一个包含全部业务逻辑的单体 SDK，而是以下五类资产：

- **股票池与 UniverseSnapshot**：固定成员、不可变版本和成分生效规则；
- **quantflow-contract**：唯一共享的契约包，只定义数据模型、模块接口和兼容版本，不承载业务实现；
- **quant-comp-\***：按 Selector、Condition、Signal、MoneyManager、ExitRule 等职责独立发布的可执行 Wheel；其中 ExitRule 以独立角色区分 Stoploss、TakeProfit、TimeExit 和普通退出；
- **策略 YAML**：冻结模块包名、版本、参数、调度、运行时和因子数据版本的组合定义；
- **数据与模型制品**：Feature Store 中的版本化因子数据，以及模型仓库中的版本化模型文件。

组件注册中心仍然负责资产发现、元数据、参数定义、发布状态和制品定位；内部 PyPI 或 Artifactory 负责保存不可变 Wheel。因而本方案不是在 SDK 与远程接口之间二选一，而是由注册与治理接口管理资产，由组件包承载执行逻辑，由 YAML 承载策略组合，由 Feature Store 承载预计算因子数据。

一期建设采用“契约先冻结、多标的闭环先跑通、投研平台适配后接入”的顺序。回测系统先使用本地 Adapter 和测试制品验证完整多标的链路；通过前置验收后，再把本地资产来源替换为投研平台真实 Adapter。多标的核心不能依赖投研平台在线状态，投研接入也不能改变已经验证的组合决策、撮合和账户语义。

### 1.2 一期建设目标

一期原生建设单标的与多标的标准 Bar 回测。单标的是单成员股票池的产品形态，多标的是共享资金、共享持仓和统一决策时钟的组合形态；两者复用同一套新增因子系统与策略 YAML 运行链路，并提供两条资产来源路径：

| 运行路径 | 用户输入 | 回测系统职责 | 引擎执行接口 |
| --- | --- | --- | --- |
| 因子系统交易回测 | 版本化股票池，以及按职责选择的一组因子 | 解析资产、批量计算因子、选股、形成目标组合、生成调仓订单 | 批次 OrderIntent |
| 策略回测 | 一个已发布策略 YAML，以及 YAML 冻结或明确允许覆盖的股票池 | 解析 YAML、加载精确版本组件、构造 System、形成组合决策 | 批次 OrderIntent |

runPath（factor_system 或 strategy）与 scopeType（single 或 portfolio）是正交维度；“组合回测”只表示 scopeType = portfolio，不代表第三种策略来源。

strategyCategory（策略类别）同样与 runPath、scopeType 正交。一期支持以下矩阵：

| 策略类别 | 单标的 | 多标的 | 一期核心语义 |
| --- | --- | --- | --- |
| directional_holding（方向持仓） | 支持 | 支持 | 根据目标权重建仓、调仓和退出 |
| core_position_overlay（底仓＋长期 T0） | 支持 | 支持 | 每个标的维护独立底仓基准与 T0 叠加层，共享组合现金，分别核算底仓和 T0 |

底仓在核算上是稳定的目标基准，不等同于一份永远不能参与成交的物理锁仓。实际持仓可因 T0 交易暂时偏离底仓，overlayQuantity = actualQuantity - baseTargetQuantity；T0 盈亏、费用和退出单独归因。是否日内恢复到底仓或允许跨日保留叠加层，由版本化 overlaySettlementPolicy 明确，禁止隐式推断。

一期核心是建立共享资金、共享持仓和统一决策时钟的多标的组合回测能力，而不是并行运行 N 个互相独立的单标的回测。系统先以本地股票池、因子数据、测试组件和测试 YAML 验证因子计算、选股、目标组合、批次订单、结果和性能，再接入投研真实资产来源；两阶段使用同一契约、组合语义和执行链路。

一期的产品粒度是“一次显式提交生成一个回测任务”：该任务可以是单成员或多成员股票池。现有调度器仍可并发处理不同用户或不同请求提交的普通任务，但一期不把参数空间、股票池、周期或费用场景自动展开为多个 Trial，不新增批次、搜索、评分或自动淘汰流程。

一期最终交付物为：

| 交付项 | 一期范围 |
| --- | --- |
| 多标的内核 | 同一账户下的多标的事件调度、估值、目标组合、调仓订单和逐标的成交路由 |
| 因子系统 | 股票池、基础选股、职责因子组、等权聚合、方向组合等权/T0 容量等比例分配和最低组合校验 |
| 策略执行 | 解析版本化策略 YAML，加载兼容组件并接入同一多标的运行时 |
| 持仓类别 | 单标的与多标的方向持仓；单标的与多标的底仓＋长期 T0；逐标的底仓、T0 容量和叠加层核算 |
| 退出组件 | 独立可选的 Stoploss、TakeProfit、TimeExit 和普通退出，按固定优先级在每根已完成 Bar 上评估 |
| 产品入口 | 单标的与组合回测入口、股票池选择、覆盖元数据展示、配置保存和运行摘要 |
| 方案与快照 | 完整配置、股票池成员、选择结果、资产制品和数据版本的不可变快照 |
| 结果与追溯 | 组合净值、持仓演变、标的贡献、交易明细和精简决策追溯 |
| 真实投研接入 | 注册中心、股票池来源、组件 Wheel、策略 YAML、Feature Store 和模型制品的生产 Adapter |
| 性能与兼容 | 固定规模基准、资源限额，以及既有单标的策略和历史结果兼容 |
| 单次回测正确性 | T1-T4 基础门禁、未来数据检查、黄金样例对拍、状态往返、事件去重、账本/归因对账、确定性重放和运行快照 |

一期不是从零重写回测引擎。建设内容按“直接复用、扩展、新增、二期”分类：

| 分类 | 能力范围 |
| --- | --- |
| 直接复用 | BarStrategy.on_bar 与 BarBacktestEngine 的单标的执行基础、OrderIntent、PortfolioLedger、PortfolioSnapshot、标准 Bar/L2 撮合、T+1、费用与滑点、运行时隔离、任务快照、既有绩效指标、单标的 T0 与底仓/叠加层归因、现有队列和多 Runner 任务并发 |
| 一期扩展 | 多标的统一事件时钟、逐标的待成交队列、逐标的底仓与 T0 容量、共享现金竞争、结构化退出原因、组合级快照与结果 |
| 一期新增 | 组件契约与策略 YAML 运行路径、FactorComputeSession、股票池/Selector、因子职责组合、TargetPortfolio 和 RebalancePlanner |
| 二期建设 | Ray、网格搜索、批量实验、参数与样本外自动验证、实验级自动归因、自动评分淘汰和报告生成 |

现有任务队列和多 Runner 并发属于运行调度能力，一期继续使用；它不等同于 Ray，也不等同于用户一次提交参数矩阵后自动展开、比较和淘汰大量策略的“回测实验自动化”。

### 1.3 一期建设里程碑

一期内部划分为三个顺序明确的里程碑：

一期完成表示 A、B、C 全部完成；B 是真实接入前必须通过的本地产品门禁，只有 C 通过后才形成一期最终交付。

| 里程碑 | 建设内容 | 完成标志 |
| --- | --- | --- |
| A：契约冻结 | 冻结投研资产、股票池、因子结果、组合决策和版本快照契约 | 固定契约版本、样例制品、预期结果和契约一致性测试经双方评审确认 |
| B：本地单标的/多标的产品闭环 | 使用本地 Adapter 跑通股票池、因子矩阵、选股、目标组合、调仓、T0、撮合、结果和前端 | 不依赖投研平台即可在单成员/多成员下分别跑通方向持仓和底仓＋T0 |
| C：投研平台接入 | 接入注册中心、组件 Wheel、策略 YAML、Feature Store 和模型制品 | 真实投研资产通过相同接口完成端到端回测 |

里程碑 B 是投研平台正式接入的前置条件，但里程碑 A 必须先行。不能完全脱离投研契约先设计另一套内部协议，否则里程碑 C 会演变成第二次重构。

### 1.4 一期产品与执行范围

| 项目 | 一期范围 |
| --- | --- |
| 回测对象 | 固定列表或不可变版本股票池；单标的是只有一个成员的股票池 |
| 选股 | 显式引用版本化全量通过 Selector 或投研 Selector；支持按分数选择 Top-N |
| 因子 | 开仓、普通退出、止盈、止损、时间退出和条件过滤；同职责可配置 1 至 N 个 |
| 仓位 | directional_holding 默认组合目标权重等权；core_position_overlay 按逐标的底仓与 T0 容量分配增强目标，默认使用相同额度比例且不重算底仓 |
| 策略类别 | directional_holding 与 core_position_overlay；两类均支持单标的和多标的 |
| 底仓与 T0 | core_position_overlay 按标的冻结底仓数量、底仓成本、T0 容量和日终处理策略；全部标的共享现金但额度、状态和归因互不串用 |
| 调仓 | 单一频率、固定调仓计划；根据目标组合生成确定性买卖差额 |
| 方向 | 因子系统只做多；不建设真实融券和组合做空 |
| 行情 | 标准 Bar；同一任务使用单一运行周期 |
| 成交 | 普通策略/组件决策在当前可见数据结束后形成，订单进入该标的自身下一根可交易 Bar 的开盘撮合；系统日终恢复按冻结的 T0 结算语义单独标记 |
| 账户 | 所有标的共享现金、持仓、费用和权益；PortfolioLedger 继续作为账户唯一真相源 |
| 结果 | 组合级指标为主，单标的 K 线和交易点作为下钻详情；底仓、T0、退出类型和交易成本可分别统计 |

新建 factor_system 和 strategy 的单标的/组合路径固定使用 backtest + bar_next_open；strategy 路径只接受 YAML 声明兼容的 scopeType、strategyCategory 和标准 Bar 执行能力。一期不让新组合路径进入 live 或 l2_quote。既有单标的脚本、单标的 L2 T0 和历史任务继续使用原有路由与保存时语义。

directional_holding 允许因目标组合变化而产生建仓、清仓和确定性数量调整；风险退出通常使对应标的目标权重归零。core_position_overlay 允许每个标的围绕各自底仓基准做 T，一期 T0 风险退出只结束该标的叠加层并回到底仓目标，不能清空底仓目标；账户级全仓风控如后续需要，应作为独立能力设计，不能复用普通 T0 退出组件。多标的标准 Bar 底仓＋T0 进入一期，多标的 L2 盘口组合执行留到后续。

### 1.5 一期最低可提交配置

| 配置职责 | 一期数量 | 一期规则 | 结果 |
| --- | ---: | --- | --- |
| 股票池 | 1 个，必填 | 固定列表或不可变版本；至少包含一个有效标的 | 定义候选范围 |
| 策略类别 | 1 个，必填 | directional_holding 或 core_position_overlay | 决定目标持仓、退出和核算语义 |
| Selector | 运行时 1 个，必填 | 页面可预选版本化全量通过模块；也可选择投研 Selector | 形成当前候选集 |
| 开仓/T0 触发因子 | 1 至 N 个，必填 | 标准化分数等权后与阈值比较；底仓＋T0 时用于形成叠加层交易信号 | 形成可建仓信号、T0 信号或排序分数 |
| 普通退出 | 0 至 N 个 | 标准化分数等权后与退出阈值比较 | 方向持仓总目标归零；T0 默认增强目标归零 |
| 止损 | 0 至 N 个 | 达到阈值时最高优先退出 | 方向持仓总目标归零；T0 默认增强目标归零 |
| 止盈 | 0 至 N 个 | 达到阈值时次优先退出 | 方向持仓总目标归零；T0 默认增强目标归零 |
| 时间退出 | 0 至 N 个 | 按持有 Bar 数、持有时长或指定时点判断，可配置 requiresProfit | 结束方向持仓或 T0 叠加层 |
| 条件过滤 | 0 至 N 个 | 全部满足才允许进入候选 | 不阻止风险退出 |
| 调仓计划 | 运行时 1 个，必填 | 页面预填版本化推荐计划，提交配置必须显式保存 | 决定组合决策时点 |
| 仓位模块 | 运行时 1 个，必填 | 方向持仓预选组合等权；底仓＋T0 预选按各标的可用 T0 容量等比例分配增强目标；提交配置必须显式保存 | 形成 TargetPortfolio |
| 底仓与 T0 配置 | core_position_overlay 必填 | 每个标的显式保存底仓数量、底仓成本、T0 容量和日终恢复/跨日保留策略 | 形成 BasePositionSnapshot 和 OverlaySnapshot |
| 类别约束 | 系统必填 | 方向持仓冻结最大持仓数、单标的权重上限和现金保留；底仓＋T0 冻结最大活跃 T0 标的数、单标的 overlay 数量/比例上限和现金保留 | 只约束对应类别目标，不重算固定底仓 |

directional_holding 的最低组合为：股票池、策略类别、Selector、至少一个开仓因子、仓位模块、调仓计划，以及普通退出、止损、止盈、时间退出中的至少一类。

core_position_overlay 在共通配置之外还必须提供逐标的底仓与 T0 配置、至少一个能形成 T0 买卖目标的信号，以及至少一种退出；一期 T0 风险/退出组件的 positionScope 固定为 overlay，提交 whole_position 必须拒绝。

页面可以按类别预选“全量通过、推荐调仓计划、方向组合等权”或“T0 可用额度等比例”等版本化模块，但用户保存或提交后的配置必须包含明确资产引用和参数；执行器不得在缺项时静默补齐。

一期存在两种不同的“等权”，必须分别表达：

1. **职责内因子等权**：同一职责下多个因子的标准化分数按 1/N 聚合；
2. **方向组合等权**：directional_holding 当前入选标的在组合资金中使用相同目标权重，并受最大持仓数、单标的上限和整手规则约束。

core_position_overlay 不对底仓做组合等权重算；一期默认让获得 T0 资格的标的使用相同的“可用 T0 容量比例”，再受各自额度、T+1、共享现金和整手规则约束。

投研平台已经发布的组合因子，在回测系统中仍按一个不可变因子版本处理；它内部如何组合由投研平台负责。用户在一次回测中选择多个因子形成的因子组属于回测配置，一个组合因子在组内只计为一个因子。

本方案中的“组合”有明确边界：投研侧单因子生成和可复用组合因子的生产、训练、发布不属于本次回测端建设；回测端只在一次运行内按职责临时选择、标准化和等权聚合已发布因子，不产生新的投研因子资产，也不把临时因子组回写因子库。

各职责阈值由版本化 factor_system 配置 schema 提供推荐值，页面可以预填，但用户保存或提交后的实际值必须显式存在。具体推荐值在开发联调前冻结；每次运行的阈值、Top-N、调仓计划、方向持仓约束、T0 增强约束和等权/等比例规则必须写入快照，不能因后续推荐值变化而改变历史含义。

“全量通过”“方向组合等权”和“T0 可用额度等比例”实现为用户配置中显式引用、带明确版本的策略模块，并作为实际模块写入快照。回测引擎本身不内置任何具体选股、方向判断、阈值或收益优化策略，从而继续遵守“提供通用运行能力，不内置方向性策略”的既有决定。

### 1.6 一期明确不做

一期不包含：

- 多标的 L2 盘口组合回放和逐笔成交队列；多标的标准 Bar 底仓＋T0 属于一期；
- 融券券源、保证金、借券费率、组合做空和强平；
- 人工因子权重、动态因子权重、模型加权或自动寻优；
- 风险平价、均值方差、行业中性等复杂组合优化；
- 多频率联合决策和跨市场日历；
- 动态指数成分历史、复杂规则股票池和超大规模全市场分布式回放；
- 任务运行时临时 pip install、浮动版本解析或访问公共包仓库；
- 独立部署的因子计算微服务和跨任务分布式缓存；
- 单独的 IC、RankIC、分组收益等统计因子评价产品；
- Ray 计算框架、网格搜索、参数扫描和一次提交自动展开大量回测；
- 样本外自动切分、参数平原自动分析、扣费压力矩阵、多股票池/多周期验证矩阵；
- leave-one-out、剔除最大贡献标的重跑、自动评分淘汰和自动报告生成；
- 完整 T1-T4 组件自动准入平台；一期只落实运行所必需的契约、功能、未来数据、依赖、安全和性能基础门禁；
- 实盘交易、组件市场和长任务断点续跑。

一期允许 Signal 等组件加载已经冻结的模型制品；“不做模型加权”特指不使用模型动态决定因子聚合权重或组合优化权重，不排除模型型信号本身。

### 1.7 二期及后续建设目标

一期契约稳定后逐步扩展：

1. 支持人工权重、统计模型和机器学习模型等因子聚合方式；
2. 支持动态股票池、指数成分历史、行业和风格约束；
3. 支持风险模型、组合优化、分层仓位和更复杂的调仓算法；
4. 支持多频率、多市场、多空组合和真实融券语义；
5. 在标准 Bar 多标的 T0 稳定后扩展多标的 L2 T0；
6. 建设回测实验自动化：参数网格、样本外验证、参数平原、扣费压力、多股票池/多周期验证、leave-one-out、剔除最大贡献标的复跑、自动评分淘汰和报告生成；
7. 在单机与现有任务并发不足以满足批量实验吞吐时引入 Ray，并通过任务粒度并行回测；单次回测内部仍以向量化、批量计算和确定性顺序为主；
8. 将 T1-T4 建成正式的组件自动准入与持续质量门禁；
9. 在有明确收益时引入跨任务缓存或独立计算模块；
10. 根据成交量、订单规模等数据条件引入版本化标准 Bar 冲击成本模型；
11. 根据业务需要建设独立的统计因子评价体系。

二期“自动化”特指面向用户的实验编排、批量运行、比较、归因、评分与淘汰。软件单元测试、契约测试、未来函数检查、确定性检查和性能基准是一期交付质量保障，不因自动化产品后置而取消。

## 二、总体方案

### 2.1 总体原则

本方案把多标的组合回测内核设计为独立的深模块。它只依赖稳定的股票池、因子数据、策略定义和组件解析接口，不直接依赖投研平台的传输协议、数据库或在线状态。

每个外部接入接口提供两个 Adapter：

- 本地 Adapter：使用测试股票池、固定因子数据、测试组件和测试 YAML，服务于开发、自动化测试和里程碑 B 验收；
- 投研平台 Adapter：从股票池来源、组件注册中心、内部制品库、Feature Store、模型仓库和策略中心解析真实资产。

两个 Adapter 之后的股票池解析、因子计算、组合决策、订单生成、撮合、账本和结果链路完全一致。测试不得绕过这些接口直接向引擎注入最终订单来代替因子系统闭环。

### 2.2 总体架构

~~~text
                    ┌────────────────────────────────────┐
                    │        投研平台真实资产来源         │
                    │ 股票池 / 注册中心 / 内部PyPI        │
                    │ Feature Store / 策略YAML / 模型仓库 │
                    └──────────────┬─────────────────────┘
                                   │ 投研平台 Adapter
本地股票池 / 测试因子 / 测试组件 ─┼─ 本地 Adapter
                                   ▼
                    ┌────────────────────────────────────┐
                    │       稳定资产与数据解析接口         │
                    │ UniverseProvider                    │
                    │ FactorDataProvider                  │
                    │ StrategyDefinitionProvider          │
                    │ ComponentResolver                   │
                    └──────────────┬─────────────────────┘
                                   ▼
股票池快照 → MarketSlice → 因子矩阵 → Selector/Signal
                                   ▼
                         PortfolioDecision
                                   ▼
              Category-aware TargetPortfolio / TargetPosition
                                   ▼
                    RebalancePlanner + 组合订单风控
                                   ▼
                       Batch<OrderIntent>
                                   ▼
               多标的标准Bar事件调度与逐标的成交路由
                                   ▼
                    PortfolioLedger / 统一结果模型
~~~

投研因子系统和策略 YAML 最终都进入同一 TargetPortfolio、调仓和执行链路。TargetPosition 根据 strategyCategory 表达方向持仓的 targetWeight，或底仓＋T0 的 targetBaseQuantity、targetOverlayQuantity 和 targetActualQuantity。OrderIntent 仍是撮合层识别的交易意图，但不再作为单个因子模块的直接输出；因子模块只返回契约规定的分数、状态、候选或仓位结果。

### 2.3 与现有回测引擎的关系

本方案以当前代码能力为建设基线，不把系统已经具备的能力重复列为新建项：

| 现有能力 | 当前边界 | 一期处理 |
| --- | --- | --- |
| 单标的标准 Bar on_bar 执行 | 已支持逐 Bar 回调、预热和现有成交模型 | 复用策略回调、订单和成交基础，新增组合事件时钟 |
| OrderIntent、PortfolioLedger、PortfolioSnapshot | 已支持 symbol、positionKey、方向、数量、费用和完整持仓身份 | 下沉为单标的与多标的共用内核，账本继续作为账户唯一真相源 |
| 成交与成本 | 已支持 T+1、手续费、费率配置、固定滑点、订单事件和未成交委托 | 扩展为逐标的路由、共享现金规划和组合成本汇总 |
| 单标的底仓 T0 | 标准 Bar 与 L2 已有 baseQuantity、T0 容量、T+1 可卖、日终恢复或跨日延续 | 保留既有单标的路径；把标准 Bar 语义按完整标的身份扩展到组合运行时 |
| 底仓增强归因 | 已有底仓收益、增强收益、周期指标和账户对账 | 扩展为逐标的对账后再汇总到组合级 |
| 普通任务调度 | 已有队列、多 Runner 领取、租约、心跳、取消、重试和能力匹配 | 继续承载一期单次回测；不表述为批量实验或网格搜索 |
| 快照与可追溯 | 已有策略配置、参数、运行时能力和行情快照基础 | 扩展 YAML、Wheel、股票池、Feature Store、模型和逐标的底仓快照 |
| 绩效结果 | 已有收益、回撤、年化收益、波动率、Sharpe、Sortino、胜率、盈亏比、基准和超额等指标 | 复用指标内核，补齐组合、T0、退出原因和成本分项 |
| 运行时隔离与门禁 | 已有运行时版本、能力摘要、依赖约束和隔离执行基础 | 扩展到 quantflow-contract 和组件 Wheel |

当前以下能力仍以单标的或单次任务为前提，不能仅把 symbol 改成 symbols：

- 回测请求、页面配置、行情加载和历史摘要仍以一个运行标的为主；
- BarStrategy.on_bar 每次只接收一根单标的 Bar，事件循环和待成交队列没有按 symbol 独立管理；
- 仅按 positionKey 暴露的兼容持仓映射在不同标的复用同一 positionKey 时可能覆盖；
- T0 日期状态、日初可卖量、剩余额度、底仓目标、日终恢复和增强归因仍是单 symbol 标量；
- 日终判断、权益采样和行情缺失处理尚未按全组合时钟定义；
- 现有队列可以并发运行多个普通任务，但没有“一个实验定义自动生成多个 Trial、统一汇总和质检”的父子任务模型。

一期新增组合级 PortfolioBacktestRuntime，同时承载 directional_holding 与 core_position_overlay，统一完成 MarketSlice 构造、每 Bar 风险/T0 决策、计划调仓、批次订单、逐标的下一 Bar 路由、全组合估值和逐标的日终处理。实现时将 PortfolioLedger、成交模型、费用、T+1、订单事件和单标的 T0 语义抽取为公共内核，不能复制第二套账户或撮合实现；既有单标的脚本和单标的 L2 路径保持兼容，不强制迁移。

### 2.4 多标的决策与执行顺序

组合运行时采用两个相互独立但在同一账本上合并的决策时钟：

- **每 Bar 风险/T0 时钟**：持仓标的每完成一根可见 Bar，就评估 Stoploss、TakeProfit、TimeExit、normal_exit 和 T0 信号，支持同一交易日多次 T0；
- **计划调仓时钟**：只在版本化 schedule 到点时执行 Condition、Selector、Top-N、方向开仓和组合权重调仓。

每个 MarketSlice 按固定顺序执行：

1. 交易日切换时，按标的重置当日可卖量、T0 剩余额度和日内状态；
2. 将历史待成交订单路由到对应标的自身下一根可交易 Bar；
3. 使用当前可得的逐标的最新有效标记价估值，形成只读 PortfolioSnapshot、BasePositionSnapshot 和 OverlaySnapshot；
4. 取得当前时点可用的时间序列、横截面和账户状态因子；
5. 对持仓逐标的执行退出规则，固定优先级为 Stoploss → TakeProfit → TimeExit → normal_exit；同一标的只生成一个最高优先级 ExitDecision，但保存全部命中原因；
6. 对 core_position_overlay 执行本 Bar 的 T0 信号；Selector/Top-N 只决定哪些固定底仓成员本次允许产生增强交易，不得因未入选而清掉底仓；
7. 到达计划调仓时点时，再执行 Condition、Selector、开仓判断、排序和 MoneyManager；
8. 合并同一标的的风险退出、T0 与计划调仓目标，完整评估所有标的后，由 RebalancePlanner 统一处理共享现金和组合约束；
9. 形成稳定排序的批次 OrderIntent，冻结决策追溯，并等待普通策略/组件订单进入各自标的下一根可交易 Bar；
10. 全部标的完成当日事件后，分别执行 intraday_restore 或 cross_day_carry，生成日终权益、持仓和增强归因快照。

core_position_overlay 的 Selector/Top-N 只在计划调仓时钟更新 T0EligibilitySnapshot；两个计划调仓时点之间，每 Bar T0 时钟读取最近一次已冻结快照，不在每根 Bar 重跑横截面选股。任务首次尚未形成快照时不允许新增 T0 overlay。标的失去 T0 资格时，在该计划调仓决策中生成 positionScope = overlay 的 normal_exit，使已有增强仓回到底仓目标；之后仅禁止新的增强开仓，固定底仓集合和底仓目标保持不变。

ExitRule 统一采用 evaluate(context, state) → ExitDecision 契约，并以 exitType = stop_loss | take_profit | time_exit | normal_exit 区分业务角色。TakeProfit 表达“每根已完成 Bar 结束时，扣除已知交易成本后的未实现盈利达到阈值即退出”；一期默认 profitThreshold = 0，并使用净浮盈严格大于 0 的触发条件，用户配置值仍须显式保存。TimeExit 表达持有 Bar 数、持有时长或指定时点达到条件后退出，可选 requiresProfit = true；它不能与 TakeProfit 混成同一含义。

ExitDecision 必须声明 positionScope。directional_holding 使用 whole_position；一期 core_position_overlay 的 T0 风控固定使用 overlay，只把 targetOverlayQuantity 恢复为 0、保留 targetBaseQuantity，提交 whole_position 视为越权并在回放前拒绝。overlayQuantity 可以为负，表示实际持仓低于底仓目标，不代表真实做空；targetActualQuantity 和成交后的实际总持仓不得为负。

日终估值沿用现有固定口径：某标的当天实际回放的最后一根有效 Bar 收盘价是该标的日终结算价；全部模拟成交完成后，以各持仓的日终结算价计算日终净值。权威状态确认当天无 Bar 的持仓可以沿用上一有效标记价，但必须单独记录沿用来源，且不能把它表述为当天新产生的日终结算价。

同一决策批次必须先完整评估所有标的，再统一分配资金。禁止边遍历标的边下单，否则先处理的标的会抢占现金并导致结果依赖遍历顺序。T0 卖出回款何时可用于同日其他标的买入，以及 T0 容量按卖出量、买回量还是双边累计消耗，必须在里程碑 A 冻结，不能把当前单标量实现直接广播成组合规则。

因某标的停牌或缺 Bar 时，不得把其他标的 Bar 用于该订单成交。普通策略/组件订单固定以订单标的自身下一根可交易 Bar 的开盘价为基础，并应用快照中冻结的滑点、限价和费用规则；不得改用该 Bar 的任意 OHLC 价格。

intraday_restore 产生的系统日终恢复订单是唯一例外：它沿用并版本化冻结现有 T0 结算语义，只能使用该标的自身当日最后一根有效标准 Bar 的结算价，并标记 source = system_settlement，不能伪装成普通下一开盘订单。该标的当日没有有效 Bar 时，按冻结的失败或延续规则处理，绝不能借用其他标的价格。

估值价格沿用、候选资格、订单等待或失效规则必须通过版本化执行契约冻结；正式区间最后一个普通决策产生而无法在结束日期内等到本标的下一根可交易 Bar 的订单记为区间结束未执行委托。

### 2.5 对《策略中心与组件中心架构设计方案 V1.2》中 System 编排的取舍

| 参考方案内容 | 一期处理 |
| --- | --- |
| Selector、Condition、Signal、MoneyManager、Stoploss | 保留职责思想；退出侧统一为 ExitRule 契约，并把 Stoploss、TakeProfit、TimeExit 和普通退出作为独立可选角色 |
| EngineAdapter 把 System 注册到引擎 | 由 PortfolioFactorSystem 或 StrategySystemAdapter 输出 PortfolioDecision，再统一转换为 TargetPortfolio 和批次 OrderIntent |
| EngineAction | 不直接作为现有撮合接口；只由 StrategySystemAdapter 确定性映射为 PortfolioDecision，资产来源 Adapter 不得生成 OrderIntent |
| System 自建 AccountState | 不采用；统一读取 PortfolioLedger 生成的 PortfolioSnapshot |
| 当前 Bar 计算、下一 Bar 成交 | 普通策略/组件订单保留，且“下一 Bar”严格指订单标的自身的下一根可交易 Bar；系统日终恢复按单独冻结的既有结算语义执行 |
| 组件状态 checkpoint | 一期要求状态序列化契约和任务快照；长任务断点续跑后置 |
| Ray 并行与网格搜索 | 一期不建设；二期由批量实验层通过 BatchExecutor 接入，Ray 是可替换执行实现，不进入策略 YAML、组件契约或单次回测结果契约 |
| Worker 任务时安装 Wheel | 一期和二期均不采用；使用预构建兼容环境或按哈希缓存的受控隔离运行时 |
| Qlib 在线参与回测 | 不采用；Qlib 在投研侧离线产出 Feature Store，Worker 不包含 Qlib |

一期职责到参考模块的默认映射如下，最终字段仍需在里程碑 A 与 quantflow-contract 一起冻结：

| 业务职责 | 参考模块 | 一期语义 |
| --- | --- | --- |
| 股票池与排序 | Selector | 输出候选资格和稳定排序分数 |
| 条件过滤 | Condition | 只控制新进入，不阻止已有持仓的风险退出 |
| 开仓 | Signal + role | role = entry；方向持仓形成目标权重，T0 形成目标增强仓变化 |
| 普通退出 | ExitRule + role | exitType = normal_exit |
| 调仓时点 | 策略 schedule | 决定何时产生组合决策，不作为逐标的分数 |
| 仓位/增强分配 | MoneyManager | 方向持仓输出受约束的目标权重；底仓＋T0 输出受逐标的容量与共享现金约束的目标增强数量 |
| 止损 | ExitRule + role | exitType = stop_loss，最高优先级 |
| 止盈 | ExitRule + role | exitType = take_profit；支持每根已完成 Bar 按扣费后盈利判断 |
| 时间退出 | ExitRule + role | exitType = time_exit；按持有 Bar 数、时长或指定时点判断，可要求已有盈利 |

资产来源 Adapter 只负责解析股票池、因子数据、YAML 和组件制品；PortfolioFactorSystem 与 StrategySystemAdapter 才负责把可执行结果转换为 PortfolioDecision。两类职责不得混用同一个“Adapter”名称而形成隐含调用关系。

## 三、具体建设内容

### 3.1 投研平台需要提供

本节同时包含里程碑 A 需要冻结的契约与样本，以及里程碑 C 才正式接入的生产制品和治理能力。3.1.1 至 3.1.3 定义最终正式资产契约；里程碑 A 只要求 3.1.4 的最小可运行样本和相应契约可用，不要求生产注册中心或制品仓库已经接通。里程碑 B 不依赖投研在线服务，但必须使用里程碑 A 已确认的契约和样本构建本地 Adapter。

#### 3.1.1 契约包与可执行组件

投研平台提供并版本化 quantflow-contract，至少冻结：

- Bar、MarketSlice、PortfolioSnapshot、BasePositionSnapshot、OverlaySnapshot、因子结果、SignalOutput、TargetPosition、ExitContext、ExitDecision 和状态快照的数据结构；
- Selector、Condition、Signal、MoneyManager、ExitRule 的输入、输出、生命周期和错误语义；Stoploss、TakeProfit、TimeExit 和 normal_exit 是独立可选、独立版本、独立参数、独立统计的组件角色；
- 时间可用性、预热、频率、缺失值和未来数据限制；
- 有状态组件的 get_state 与 set_state 契约；
- 契约主版本兼容规则。

退出角色使用三层固定命名映射：文档/组件角色名为 Stoploss、TakeProfit、TimeExit、NormalExit；ExitDecision.exitType 枚举为 stop_loss、take_profit、time_exit、normal_exit；策略 YAML 字段为 stopLoss、takeProfit、timeExit、normalExit。三者只能按契约映射，不能由自由文本 reason 推断。

ExitDecision 至少包含 symbol、positionKey、positionScope、triggered、exitType、targetQuantity 或 targetRatio、priority、componentId、componentVersion、tags 和 reason。组件只能读取上下文与账户快照，不能直接修改账户或下单；编排层按优先级合并后交给 RebalancePlanner。

TakeProfit 必须声明 evaluateAt、profitThreshold 和 profitBasis。“每根 K 线结束有盈利就平”属于 TakeProfit：一期采用 evaluateAt = bar_close、profitThreshold = 0，并在净浮盈严格大于 0 时触发；profitBasis 为扣除已发生成本并估算本次退出成本后的净浮盈。TimeExit 则声明 eligibleAfterBars、持有时长或指定时点，可选 requiresProfit = true；它解决“持有多久后退出”，不能替代 TakeProfit。信号 Bar 盈利不保证下一开盘实际成交仍盈利，结果以真实成交为准。

业务实现通过独立 Wheel 发布，例如 quant-comp-sel-*、quant-comp-cond-*、quant-comp-sig-*、quant-comp-mm-* 和 quant-comp-exit-*；ExitRule Wheel 通过 componentKind 明确 stop_loss、take_profit、time_exit 或 normal_exit。每个组件包应满足：

- 固定入口类或入口点，且只依赖兼容版本的 quantflow-contract；
- 不依赖回测引擎，不相互直接导入；
- 不直接访问文件、网络、数据库或系统时钟，时间只能来自运行上下文；
- 返回契约类型，不直接修改账户或执行订单；
- 声明参数 schema、支持频率、最大回看期、状态性和性能元数据；
- 通过功能、性能、未来数据、状态往返、依赖和版本规范等质量门禁。

一期保留 T1-T4 作为单次回测正确性和组件加载门禁，但不建设二期的自动准入运营平台：

| 门禁 | 一期要求 |
| --- | --- |
| T1 功能与契约 | 输入输出 schema、错误语义、边界值、状态往返和确定性通过 |
| T2 性能与资源 | 固定工作负载下耗时、内存、超时和资源上限通过 |
| T3 未来数据 | 前缀截断结果一致，组件不能访问 decisionTime 之后的数据 |
| T4 依赖与版本 | 依赖锁、禁止依赖、契约版本、Python ABI、Wheel 摘要和运行时能力兼容 |

T1-T4、工程自动化测试和未来函数门禁不属于批量回测或网格搜索，不因实验自动化后置而取消。

#### 3.1.2 策略、因子数据与模型制品

策略中心提供不可变策略 YAML，至少冻结：

- 策略 ID、版本、校验摘要和发布状态；
- runPath、scopeType、strategyCategory，以及股票池或股票池引用；
- 各模块 package、精确 version、componentKind、positionScope、参数和执行顺序；
- core_position_overlay 的逐标的底仓引用或不可变底仓表、底仓成本、T0 容量、overlaySettlementPolicy 和 T0 信号；
- stopLoss、takeProfit、timeExit、normalExit 的独立数组、逐 Bar 风险时钟和固定优先级；
- 调仓计划、运行周期、执行延迟和运行时版本；
- feature_store_version 和使用的模型版本；
- 兼容的 quantflow-contract 版本。

市场型因子由投研侧离线计算，写入版本化 Parquet Feature Store，并提供因子版本、字段、时间可用性、分区规则和内容校验摘要。回测 Worker 通过批量 Provider 或 DuckDB 等本地读取方式使用制品，不在任务中运行 Qlib。

每个因子版本必须声明唯一的计算形态：

- materialized：结果来自指定 feature_store_version 和列定义；
- runtime：逻辑来自指定组件 Wheel，可选引用冻结模型制品。

同一因子版本不能同时让 Feature Store 结果和运行时组件各算一遍并由执行端临时选择。若两者都存在，契约必须明确唯一权威来源和校验用途。

投研平台负责单因子以及可复用组合因子的生产、训练、验证、发布和保存。回测系统在一次运行内对多个已发布因子进行的职责分组与等权聚合只是临时执行配置，不生成、不发布也不回写新的因子资产。

使用模型的组件应引用模型仓库中的不可变 URI 和内容摘要；模型更新必须产生新版本，不能覆盖历史任务引用的文件。

#### 3.1.3 组件注册与制品治理

组件注册中心至少提供：

- 组件 ID、类型、包名、精确版本、发布状态和兼容契约版本；
- 参数 schema、频率、最大回看期、状态性和性能信息；
- Wheel URI、Wheel SHA-256、签名或可信来源标识；
- 版本变更说明、发布时间和历史保留状态；
- “未发布、版本不存在、制品缺失、摘要不一致、协议不兼容”等稳定错误语义。

内部 PyPI 或 Artifactory 必须保留历史不可变 Wheel。禁止用 latest、版本范围或同版本覆盖制品来执行回测。策略 YAML 中的业务资产版本和 Wheel 包版本是两层身份，均需独立冻结。

#### 3.1.4 联调前最小样本

里程碑 A 结束前，投研平台至少提供：

1. 一份可读取的 quantflow-contract 固定版本；
2. 一份版本化 UniverseSnapshot 及成员生效规则；
3. 一个 Selector、一个 Condition、一个 Signal、一个 MoneyManager，以及 Stoploss、TakeProfit、TimeExit、normal_exit 测试 Wheel；
4. 四份测试策略 YAML，分别覆盖 single/portfolio × directional_holding/core_position_overlay；其中 portfolio core_position_overlay 至少包含两个标的及不同底仓数量与成本；
5. 一份小规模 Feature Store 样本及校验摘要；
6. 一份有状态组件的状态往返示例；
7. factor_system 在 single/portfolio × directional_holding/core_position_overlay 下的四份配置样例；strategy 的四格由第 4 项四份 YAML 覆盖；
8. 预期的股票池、选择结果、方向目标权重、底仓/T0 目标、共享现金竞争、同日多次交易、退出优先级、日终恢复和组件错误样例。

这些样本用于验证本地 Adapter 是否模拟了真实契约，不能等到多标的内核完成后才首次发现双方数据模型不一致。

### 3.2 里程碑 B：本地单标的/多标的产品闭环

#### 3.2.1 稳定接口与本地 Adapter

回测系统先定义以下稳定接口：

| 接口 | 职责 |
| --- | --- |
| UniverseProvider | 按引用解析不可变股票池及成员快照 |
| FactorDataProvider | 按股票池、因子、周期和时间范围批量提供版本化因子矩阵 |
| StrategyDefinitionProvider | 按 ID 和版本解析不可变策略 YAML |
| ComponentResolver | 解析精确组件制品、入口点、摘要和运行时要求 |

每个接口先提供本地 Adapter，再提供投研平台 Adapter。组合回测模块只依赖这些接口，不感知 HTTP、数据库、内部 PyPI 或本地文件的具体实现。

本地 Adapter 必须支持真实版本号、校验摘要、缺失状态和错误场景，不能使用只返回最终 OrderIntent 的简化假实现。这样里程碑 B 验收的才是未来真实接入会走的链路。

#### 3.2.2 单标的/多标的配置契约

回测任务增加独立运行路径字段，例如 runPath = factor_system | strategy，并增加组合范围：

- scopeType = single | portfolio；
- strategyCategory = directional_holding | core_position_overlay；
- universeRef 或手工成员快照；
- 股票池版本、成员摘要和成员数量；
- 基准、运行周期、正式区间和调仓计划；
- 各职责因子、参数、阈值、Top-N 和等权聚合规则；
- directional_holding 的最大持仓数、单标的权重上限、现金保留和组合等权规则；core_position_overlay 的最大活跃 T0 标的数、单标的 overlay 数量/比例上限、现金保留和容量等比例规则；
- core_position_overlay 的逐标的 basePositions、T0 容量、T+1 可卖规则、overlaySettlementPolicy、退出 positionScope 和成本模型；
- 缺 Bar、停牌、上市前和退市后的版本化处理策略；
- executionContractVersion、结果 schema 版本和运行时能力摘要。

single 不单独维护另一套因子系统，而是由只有一个成员的 UniverseSnapshot 进入同一组合链路。既有脚本单标的回测继续走原有兼容路径，不因本方案被强制迁移。

字段路由固定为：

| runPath | scopeType | strategyCategory | mode / fillModel | 一期处理 |
| --- | --- | --- | --- | --- |
| factor_system | single 或 portfolio | directional_holding 或 core_position_overlay | backtest / bar_next_open | 进入新组件化标准 Bar 链路 |
| strategy（YAML） | single 或 portfolio | directional_holding 或 core_position_overlay | backtest / bar_next_open | YAML 声明能力兼容后进入同一新链路 |
| strategy（既有脚本） | single | 既有合法类别 | 既有合法 Bar/L2 值 | 保持原兼容链路，不强制迁移 |
| 任意新组合路径 | portfolio | 任意 | live / 任意 | 一期拒绝 |
| 任意新组合路径 | portfolio | 任意 | backtest / l2_quote | 一期拒绝，多标的 L2 后置 |

新组件化链路显式携带 strategyCategory。directional_holding 固定 allowShort = false、t0Enabled = false；core_position_overlay 固定 allowShort = false、initialPositionEnabled = true、t0Enabled = true。

core_position_overlay 为每个生效成员冻结正数 baseQuantity、baseCostPrice、显式非负 T0 容量和 overlaySettlementPolicy，且任务中至少一个标的的 T0 容量大于 0。

单成员页面可以接收现有标量字段，但提交时也必须规范化为 symbol → BasePositionConfig 的不可变快照；portfolio 禁止把一个全局 baseQuantity 或 baseCostPrice 静默广播到全部标的。

沿用现有 core_position_overlay 账户初始化口径：initialCapital 是底仓之外的独立现金，不从底仓成本中扣减；多标的初始权益为：

~~~text
initialEquity = initialCapital + Σ(baseQuantity[symbol] × baseCostPrice[symbol])
~~~

任一生效底仓成员缺少数量或成本时提交失败。负 targetOverlayQuantity 只表示实际持仓目标低于固定底仓目标，不等于真实空头；targetActualQuantity 与成交后实际总持仓不得小于 0，OPEN_SHORT、CLOSE_SHORT 和真实负目标仓位在能力声明、提交前校验和 RebalancePlanner 三层拒绝。

对于新组件化 scopeType = single 或 portfolio 标准 Bar 路径，本方案扩展《策略类别与持仓回测体系改造方案》中 core_position_overlay 仅使用单标量底仓配置和既有单标执行的边界；旧单标的标准 Bar/L2 行为、旧记录和按保存版本读取的语义继续有效。里程碑 A 必须冻结新的 resultSchemaVersion、holdingMetrics/overlayMetrics 结构和按版本回退的只读适配规则，禁止用新默认值改写或重算旧记录。

历史、对比、共享、复制和重新运行必须同时识别 runPath、scopeType、strategyCategory 与 resultSchemaVersion，不能只按股票池成员数量推断语义。

策略 YAML 是策略默认运行定义。股票池、周期、调仓计划、执行延迟和数据版本只有在 YAML 的参数 schema 明确声明为可覆盖时，页面和任务配置才允许覆盖；最终生效值、来源和覆盖前值全部写入快照。未声明为可覆盖的字段发生冲突时，任务在提交前失败，不使用隐式优先级。

新增字段必须作为完整契约贯穿默认值、页面交互、方案保存、草稿指纹、提交载荷、后端一致性校验、任务快照、历史恢复、公开结果读取和重新运行。初始资金、费用、滑点、基准和现有账户选择继续沿用当前合法配置，但必须升级为组合任务级参数并进入同一快照。

#### 3.2.3 多标的行情与事件调度

新增组合级行情调度能力：

- 行情仍由回测系统的数据源和 marketDataSnapshot 提供；Feature Store 只提供因子或特征，不能替代成交与估值行情；
- 按时间和标的稳定排序，构造同一决策时点的 MarketSlice；
- 区分当前有 Bar、停牌、缺失、尚未上市和已退市；
- 每个标的独立维护下一可交易 Bar 和待成交订单；
- 每个标的按交易日独立维护底仓目标、实际持仓、overlayQuantity、日初可卖量、T0 剩余额度和日内成交状态；
- 同一标的允许日内多次 T0，任一标的的额度消耗、部分成交、拒绝或待成交不得修改其他标的状态；
- 在策略决策前完成全部持仓标记，防止组合权益随标的遍历顺序变化；
- 日终结算在全部标的完成当日事件后发生；
- intraday_restore 分别使用各标的自身当日最后一根有效 Bar 执行系统结算；cross_day_carry 保留该标的增强偏离进入下一交易日；
- 预热期保留因子与策略状态，但禁止订单接纳、成交、费用、资金、持仓和结果事件落盘；
- 正式区间结束后的 Bar 不得用于完成任何因子或策略组件生成的订单。

沿用现有标准 Bar 时间语义：分钟 Bar 时间戳表示该 Bar 结束时间，组合决策发生在全部当前可见输入完成之后，因子 availableAt 必须小于或等于 decisionTime。下一开盘订单不得跨出用户选择的结束日期。

每 Bar 风险/T0 时钟与计划调仓时钟共用同一个 MarketSlice 和 PortfolioLedger。一个标的在某时点没有当前 Bar 时不得虚构风险判断或 T0 信号；intraday_restore 只能在确认该标的当日最后一根有效 Bar 后使用其自身结算价，整日无有效 Bar 时不得生成系统结算，也不得借用其他标的价格。其他有事件标的仍可继续执行。逐标的日终处理完成后才能汇总组合日终权益和底仓增强归因。

新组合路径沿用 warmupTradingDays 的 0 至 250、默认 0 约束。有效预热天数取用户或 YAML 配置与全部模块声明最小需求的较大值，超过上限时在回放前拒绝；按交易日历和标的实际可用交易日准备预热，停牌日不计入该标的有效预热天数。

任一在正式区间生效的成员无法取得所需有效预热日时，整个任务失败并沿用统一行情数据异常提示，不能让不同成员以不同成熟度进入横截面计算。由于现有预热 ADR 只覆盖标准 Bar 自定义策略，实施前必须同步修订 ADR，明确该语义扩展到 factor_system 和组合策略 YAML。

覆盖元数据选源继续遵守现有单一来源优先规则：新版覆盖查询成功且确认没有该标的时才读取旧版覆盖；超时或临时错误重试耗尽后终止，不切换来源掩盖故障。Worker 不通过比较交易日历、覆盖元数据和实际 Bar 的逐日集合来推断行情缺失。MarketSlice 只把权威交易状态明确标注的事件记为 KNOWN_SUSPENDED；单纯没有当前 Bar 记为 NO_EVENT，不擅自判断为停牌或数据丢失。

UniverseSnapshot 中在正式区间已生效且按契约应有行情的成员，如果整个正式区间完全没有可回放 Bar，则任务失败并列出问题标的；不能静默从分母或股票池中删除。已通过成员生效规则明确标记为尚未上市或已经退出的标的不进入当时候选集。只有权威交易状态才能把标的记为停牌或不可交易；NO_EVENT 只表示当前没有行情事件。因子 MISSING 只能由 FactorDataProvider 或因子组件按契约显式返回，不能从 Bar 缺口反推。上述状态均不得阻断无关标的事件。

页面只读取批量覆盖元数据并展示股票池可用性概览，不扫描原始 Bar，也不把元数据范围描述成执行成功保证。保存和提交不做完整行情扫描；Worker 执行阶段按上述版本化规则加载真实数据并决定是否失败。系统不得静默删除问题标的或自动缩短用户区间。

#### 3.2.4 因子计算层

新增组合级 FactorComputeSession，对外只暴露任务准备和按决策时点取得因子结果两类能力：

- 只依赖行情和固定参数的时间序列因子，在任务准备阶段按冻结数据批量计算；
- 横截面因子按 MarketSlice 或调仓时点批量计算，不能逐标的调用后再拼接；
- Feature Store 已提供的市场型因子直接批量读取和对齐，不在回测端重复运行 Qlib；
- 依赖持仓、开仓价、最高价、逐标的底仓/overlay/T0 状态或成交事件的状态因子按 symbol + positionKey + side 增量计算；按日状态再增加 tradeDate；
- 相同依赖节点在单任务内只计算一次；
- 因子结果携带 value、status、availableAt、assetVersion 和必要诊断；
- 因子只能访问当前时点及之前可见的数据，批量和横截面计算不能成为未来数据入口。

缺失按“标的 × 因子 × 时点”表达。契约允许的 MISSING 使相应职责对该标的不触发，并且不临时重新分配其余因子权重；ERROR、越界或协议不符终止任务并记录节点和标的。

#### 3.2.5 因子聚合、选股与目标组合

一期 FactorAggregator 首先提供同职责等权实现：

~~~text
标的职责分数 = 固定因子集合的标准化分数之和 / 固定因子数量
~~~

聚合前必须统一方向、范围和时间可用性。Condition 作为门控，不进入分数聚合；版本化调仓计划决定是否进入本次组合决策；仓位模块不构成开仓信号。

对于某一个标的、某一个职责，固定因子集合中任一必需因子为 MISSING 时，该职责整体保持 MISSING，不把缺失项当零，也不缩小分母或重分配权重。Condition 为 MISSING 时只视为不允许新进入，不触发已有持仓退出；已有持仓仍继续执行止损、止盈、时间退出和普通退出。

组合决策固定执行：

1. 每 Bar 风险时钟执行止损、止盈、时间退出和普通退出；同一标的同时触发时按 stop_loss、take_profit、time_exit、normal_exit 排序，只形成一份有效退出决策并保留 matchedExitTypes、componentTags 和全部原因；
2. Condition 过滤；
3. 显式配置的版本化 Selector（包括全量通过 Selector）；
4. 开仓组判断和横截面排序；外部 Selector 存在时使用其 rankingScore，否则使用开仓组分数降序；
5. Top-N 与组合约束；directional_holding 用于决定目标成员，core_position_overlay 只决定哪些固定底仓成员本次允许产生 T0 增强交易，不得把未入选解释为清空底仓；
6. MoneyManager 把建议成员、退出和类别相关目标写入 PortfolioDecision；
7. 组合约束归一化器校验并生成规范化 TargetPortfolio。

PortfolioDecision 是因子系统或策略 System 的执行中立输出；TargetPortfolio 是组合约束归一化后的引擎输入，至少包含 decisionId、decisionTime、strategyCategory、退出成员、约束版本、结构化原因，以及每个标的的 TargetPosition：

- directional_holding：targetWeight、targetActualQuantity 和 positionScope = whole_position；
- core_position_overlay：targetBaseQuantity、targetOverlayQuantity、targetActualQuantity 和 positionScope = overlay。

风险退出在 directional_holding 下通常把总目标归零，在 core_position_overlay 下只把 targetOverlayQuantity 归零而保持 targetBaseQuantity 不变。未来数学模型只替换 FactorAggregator、Selector 或 MoneyManager 的实现，不改变 PortfolioDecision → TargetPortfolio → RebalancePlanner 的稳定链路。

排名并列时使用标准化证券代码升序作为最终稳定排序键。任何并行或向量化实现都必须保持相同顺序，不能让集合迭代顺序影响 Top-N、资金分配或订单结果。

#### 3.2.6 调仓规划与订单执行

新增 RebalancePlanner，把目标组合与 PortfolioSnapshot 的差额转换为批次 OrderIntent，并统一处理：

- 卖出与买入优先级；
- 可卖数量、T+1 和停牌约束；
- 逐标的底仓目标、实际持仓、增强差额、T0 容量、日初可卖量和同日多次交易约束；
- 共享现金、费用、价格缓冲和资金预留；
- 风险退出优先、同标的目标合并，以及 intraday_restore/cross_day_carry；
- 整手与最小数量；方向持仓的单标的权重上限/最大持仓数；底仓＋T0 的单标的 overlay 上限/最大活跃 T0 标的数；
- 同一 decisionId 下订单的稳定排序和幂等键；
- 实际成交、拒绝、缩量和未执行后的状态更新。

因子计算、Selector 和 MoneyManager 不能直接修改现金、持仓或权益，也不能把期望成交当作已经成交。PortfolioLedger 继续作为账户唯一真相源。所有拒绝、丢弃、缩量、成交和区间结束未执行都必须产生版本化结果记录。

普通策略/组件订单在自身标的下一根可交易 Bar 以该 Bar 开盘价为基础，并应用冻结的滑点、限价和费用规则。严禁使用该 Bar 尚不可得的价格，也严禁用其他标的的当前 Bar 成交该订单。core_position_overlay 复用现有单标的 T0 的底仓目标、T+1 可卖、日内额度、日终恢复/跨日延续和增强归因语义，但把持仓状态扩展为按 symbol + positionKey + side 隔离，把日内状态进一步按 tradeDate 隔离；共享现金仍由 PortfolioLedger 统一维护。系统日终恢复订单按冻结结算规则处理并单独标记。

组合链路读取和更新持仓时必须使用 symbol、positionKey、side 的完整身份，日内状态至少再按 tradeDate 隔离。现有仅按 positionKey 的兼容字段以及全局 _t0_remaining 等单标量状态只供旧单标的路径使用，不得作为组合订单校验、可卖数量、T0 容量或组件状态的键。

#### 3.2.7 策略 YAML 运行路径

策略回测不再假定投研平台提供一段可以直接塞入 ScriptedBarStrategy 的完整代码。新增 StrategySystemAdapter：

1. 解析并冻结策略 YAML；
2. 通过 ComponentResolver 解析每个精确版本 Wheel；
3. 校验 quantflow-contract、Python、平台标签、runPath、scopeType、strategyCategory、逐标的底仓配置、结算策略和运行时能力；
4. 在受控运行时实例化 Selector、Condition、Signal、MoneyManager，以及独立配置的 Stoploss、TakeProfit、TimeExit 和 normal_exit；
5. 把组件输出适配为方向目标或 T0 增强目标的 PortfolioDecision，再由组合约束归一化器生成 category-aware TargetPortfolio；
6. 进入与因子系统相同的 RebalancePlanner、OrderIntent、成交和账本链路。

既有用户脚本和 ScriptedBarStrategy 保持原路径。现有脚本层已经可以在每根 Bar 自定义实现止损、止盈和固定时间退出；一期新增的是标准组件槽位、统一优先级、结构化追溯和多标的聚合，不把这些底层行为误写为从无到有。只有声明兼容对应 scopeType 与 strategyCategory 契约的投研策略才能进入新运行时；不兼容策略在回放前明确拒绝。

#### 3.2.8 前端交互

页面把“多标的”命名为“组合回测”，避免与“批量运行多个独立单标的回测”混淆。当前按组展开的配置结构继续保留，在回测范围卡中提供：

- 回测对象：单标的或组合回测；不兼容当前策略能力时禁用并说明原因；
- 策略类别：方向持仓或底仓＋长期 T0；只有策略/YAML 声明相应能力时可选；
- 单标的：继续使用现有标的搜索；
- 组合回测：使用 UniversePicker 显示股票池名称、版本、成员数量和覆盖摘要；
- 股票池来源一期支持已有版本股票池和手工组合；
- 查看或编辑成员时打开抽屉，支持搜索添加、批量粘贴、列表查看和移除；
- 已发布股票池默认只读，编辑时创建本次回测临时成员快照，不修改原版本；
- 基准继续使用单标的搜索。

选择底仓＋长期 T0 后，单标的复用当前底仓表单；组合回测使用逐标的配置表，支持批量粘贴和逐行校验 symbol、baseQuantity、baseCostPrice、T0 容量及覆盖的结算策略。页面不得把一个全局底仓数量或成本静默套用到全部标的，并应展示初始现金、总底仓市值和初始权益口径。

手工组合和已发布股票池的临时副本在保存时生成临时 universeId、成员摘要、来源和显示名称；历史任务始终读取冻结成员快照，不依赖用户后来编辑同名草稿。

页面通过批量覆盖元数据展示完整覆盖、部分覆盖和无覆盖的数量，并允许下钻查看问题标的。覆盖分类按正式区间与所需预热区间分别计算，同时展示元数据更新时间；该展示不替代 Worker 实际加载，也不得静默剔除标的或缩短区间。

因子与组合配置分为：

1. 选股与信号：Selector、开仓/T0 因子、Top-N 和职责内等权说明；
2. 退出规则：普通退出、Stoploss、TakeProfit、TimeExit 四个独立选择区，展示逐 Bar 评估、positionScope、profitBasis 和固定优先级；
3. 底仓与 T0：逐标的底仓、额度、共享现金说明，以及 intraday_restore 或 cross_day_carry；
4. 组合与调仓：方向持仓的组合等权、最大持仓数和单标的权重上限，或底仓＋T0 的容量等比例、最大活跃 T0 标的数和单标的 overlay 上限，以及共用的调仓计划。

运行前摘要必须展示并冻结股票池来源与版本、成员数量、覆盖摘要、日期周期、基准、strategyCategory、Selector、Top-N、因子与组件版本、逐标的底仓配置完整性、总底仓市值、共享现金、T0 结算策略、退出优先级、类别对应的仓位/增强约束与分配规则、成本模型、缺失数据策略、成交语义和预计计算规模。

#### 3.2.9 结果与追溯

组合回测结果首页以组合而不是单只 K 线为中心。现有总收益、最大回撤、年化收益、年化波动率、Sharpe、Sortino、胜率、盈亏比、基准和超额等指标内核直接复用，并至少补充：

- 组合净值、基准、超额、回撤和收益风险指标；
- 持仓数量、组合换手、现金比例和集中度；
- 持仓演变，以及方向持仓每次调仓前后的目标/实际权重或底仓＋T0 的 base/overlay/actual 数量；
- 标的收益贡献和费用贡献；
- 组合级与逐标的 targetBaseQuantity、actualQuantity、overlayQuantity、baseBenchmarkPnl、overlayPnl、realizedOverlayPnl、unrealizedOverlayPnl 和 T0 cycle 指标；
- grossPnl、netPnl、commission、transferFee、stampDuty、slippageCost、impactCost，以及总账户/T0、组合/标的/positionKey 的分项汇总；
- stop_loss、take_profit、time_exit、normal_exit 的 trigger、order、fill、reject、unexecuted 数量和按 componentTag 的收益/成本贡献；
- 可按标的、时间和 decisionId 过滤的交易明细；
- Selector、因子组、目标组合、订单和成交之间的精简追溯；
- 停牌、缺失和数据异常摘要。

现有佣金、过户费、印花税和固定滑点直接复用。slippageCost 由未加滑点基准价与实际成交价的差额按数量聚合；若成交价已经包含滑点，净收益对账不得再次扣除。标准 Bar 当前没有独立冲击成本模型，一期固定 impactModel = none，并单独显示 impactCost = 0、model = none，禁止把滑点改名为冲击成本；版本化非 none 冲击模型属于后续建设。

grossPnl 以未加费用和滑点的冻结基准成交价计算，explicitFee = commission + transferFee + stampDuty；一期按 netPnl = grossPnl - explicitFee - slippageCost 对账，并保留独立的 impactCost = 0 字段。PortfolioLedger 基于实际成交价形成的账户净收益必须与该拆分结果一致；任何已经体现在实际成交价中的成本都只能归因一次。

退出触发次数按 decisionId + symbol + positionKey + exitType 去重，部分成交笔数不能重复计为触发。每个标的以及组合汇总均必须在冻结容差内满足账户收益、底仓基准收益和增强收益的对账关系；费用按真实成交的 symbol、positionKey 和 tag 归属，共享现金不能被重复分摊。对账失败时任务受控失败或明确标记结果无效，不能只展示一份无法解释的净值。

用户点击某个标的后再进入该标的 K 线和买卖点详情。默认不绘制所有标的曲线，也不保存每个因子在每根 Bar 上的完整矩阵；详细轨迹作为受限诊断能力后续提供。

结果结构需要版本化，并接入子进程返回、结果归一化、持久化、历史读取、复制和共享回测链路。历史列表用股票池名称、版本和成员数量代替单一运行标的，同时保留单成员股票池的友好展示。

#### 3.2.10 运行快照与历史重放

不可变运行快照至少包含：

- 股票池 ID、版本、完整成员快照、成员摘要和成员顺序规则；
- 每个风险/T0 与调仓时点的 SelectionSnapshot、T0EligibilitySnapshot、ExitDecision 和 TargetPortfolio 摘要，包括候选、入选、资格生效区间、退出、排序键、类别相关目标、全部命中原因和 componentTags；
- 策略 YAML 原文和摘要；
- 每个组件的 ID、包名、精确版本、Wheel SHA-256、入口点和签名状态；
- quantflow-contract 版本、依赖锁摘要、Python/平台 ABI 和运行镜像摘要；
- feature_store_version、因子数据摘要和模型制品摘要；
- 因子参数、职责分组、阈值、Top-N、调仓计划和组合约束；
- strategyCategory、逐标的底仓 map、底仓成本、T0 限额与日初可卖规则、overlaySettlementPolicy，以及初始权益计算版本；
- 四类退出组件的精确版本、参数、顺序、positionScope、profitBasis、风险时钟版本和退出优先级；
- 费用、滑点和冲击成本模型版本，以及底仓/增强归因版本；
- executionContractVersion、结果 schema 版本和运行时能力摘要；
- 随机种子、数值运行时版本，以及涉及非确定模型时的确定性级别和比较容差；
- 各标的不可变行情引用、sourcePeriod、派生规则版本、正式范围、请求与实际预热范围、Bar 数和输入摘要。

任务开始后不再解析浮动版本，也不依赖投研平台在线状态。历史重放只能使用精确匹配的制品和数据；原制品或行情版本不可用、摘要不一致时明确拒绝，不能改用最新版。

多标的行情快照继续扩展既有 marketDataSnapshot JSON 并写入 backtest_run.market_data_snapshot，不为同一语义新建第二套行情快照表。读取旧任务时按保存的快照结构版本回退，不能用新的多标的默认值补算旧记录。

有状态组件必须通过 get_state 与 set_state 往返质量门禁。一期保存初始状态、必要的调仓决策摘要和最终状态用于审计，不建设运行中周期 checkpoint 或中断后续跑。

一期必须保留单次回测正确性闭环：

- 使用黄金样例对股票池、因子结果、退出决策、目标组合、订单、成交、权益和归因逐层对拍；
- 单成员组合链路与现有单标的链路在相同语义下做兼容性对拍；
- 本地 Adapter 与投研平台 Adapter 使用同一契约样例对拍；
- 使用前缀截断检查未来数据，追加未来数据不能改变截断前缀的既有决策；
- 相同快照重复执行时，选择、订单、成交和结果在冻结容差内一致；
- 决策、订单、成交和行情事件使用稳定身份，重复投递不能重复执行或重复计数；
- 账本、成交、绩效和逐标的底仓增强归因必须完成对账。

以上校验只验证用户明确提交的一次固定配置，不自动生成参数、股票池、时间区间或费用场景 Trial。

#### 3.2.11 速率、资源与安全

性能作为里程碑 B 和 C 的上线条件：

1. 股票池、组件、参数、因子数据和行情在任务准备阶段批量加载；
2. 时间序列因子向量化，横截面因子按时点批量计算，状态因子增量更新；
3. 禁止为每个标的、每个因子创建独立进程或进行网络调用；
4. 逐时点热路径禁止数据库访问、全历史切片和重复 DataFrame 构造；
5. 相同依赖节点和相同参数在单任务内共享结果；
6. 使用连续数组、固定数据类型和有效性掩码，并按最后使用时点释放中间结果；
7. 设置最大股票池规模、因子数、依赖节点数、回看期、Bar 数、预计内存和准备时间；
8. 性能基准覆盖单成员、小型组合、一期目标规模方向组合，以及多标的 T0、日内多次交易、独立风控和日终恢复工作负载，并记录准备耗时、计算吞吐、风险/T0 决策耗时、调仓耗时和峰值内存；
9. 分别记录组件冷启动、热缓存启动、Wheel 摘要校验、导入和实例化耗时。

组件 Wheel 不在任务中临时安装。运行时使用预构建、哈希锁定的兼容环境，或由受控隔离执行器按内容摘要读取本地缓存。组件运行环境默认断网、无数据库和投研凭据、使用只读制品和临时工作目录，并设置 CPU、内存、进程数、文件句柄和超时限制。

调度器只能把任务交给 quantflow-contract、组件集合、Python ABI 和执行契约均兼容的 Worker。相关摘要应进入 runtime capability，backend、Bar runner 以及未来支持该能力的 runner 必须同批发布。

一期继续复用现有队列和多 Runner 的任务级并发，但一次产品提交只生成一个单标的或多标的回测任务，不引入批次父任务、参数搜索空间、自动 Trial 展开或 Ray。多标的组合也不能为了并行而按股票拆成独立任务，否则会破坏共享现金、统一调仓和确定性语义。

### 3.3 投研平台实际接入

#### 3.3.1 资产解析与缓存

在里程碑 B 通过后，实现投研平台 Adapter：

- 从股票池来源取得精确 UniverseSnapshot、成员生效规则和内容摘要；
- 从注册中心批量解析任务所需组件和元数据；
- 从内部制品库取得精确 Wheel，并验证摘要和可信来源；
- 从策略中心取得精确策略 YAML；
- 从 Feature Store 批量读取指定版本因子数据；
- 从模型仓库取得指定模型制品；
- 将全部资产物化到任务准备区并写入快照。

资产准备阶段允许有限重试，但任务执行阶段必须离线。缓存采用内容寻址，同一摘要只保存和校验一次；缓存失效只能影响性能，不能改变结果语义。

#### 3.3.2 两条真实运行路径

因子系统路径：

~~~text
股票池版本 + 因子组件/数据版本
→ 投研平台 Adapter
→ FactorComputeSession
→ Selector / 职责聚合 / ExitRule / MoneyManager
→ PortfolioFactorSystem
→ PortfolioDecision
→ Category-aware TargetPortfolio
→ RebalancePlanner
→ Batch<OrderIntent>
~~~

策略路径：

~~~text
策略 YAML 版本
→ 投研平台 Adapter
→ ComponentResolver
→ StrategySystemAdapter
→ PortfolioDecision
→ Category-aware TargetPortfolio
→ RebalancePlanner
→ Batch<OrderIntent>
~~~

两条路径从 category-aware TargetPortfolio 起复用相同的组合约束、撮合、账本、结果和追溯；directional_holding 与 core_position_overlay 也复用同一 PortfolioLedger 和成交内核，只在目标表达、T0 状态及归因上按类别扩展。禁止因策略来源或策略类别不同而复制另一套账户或成交逻辑。

#### 3.3.3 接入失败与兼容处理

以下问题在回放前失败：

- 资产未发布、版本不存在或历史版本已不可用；
- Wheel、YAML、Feature Store 或模型摘要不一致；
- quantflow-contract、Python、ABI 或运行时能力不兼容；
- 组件依赖冲突、入口点无效或状态契约不完整；
- 组合策略声明做空能力、输出负目标权重或生成任何开空和平空动作；
- core_position_overlay 缺少逐标的底仓、成本、T0 容量、overlaySettlementPolicy 或 T0 信号，positionScope 越权，或实际总持仓目标为负；负 overlayQuantity 本身允许，不按真实做空拒绝；
- 股票池、因子频率和策略运行周期不兼容；
- 任务估算超过资源限额。

已进入执行阶段的任务不因注册中心短暂不可用而失败。投研平台发布新版本后，历史任务仍使用原快照和原制品；新版本不得改变已完成任务的展示和重放结果。

#### 3.3.4 所有权、可见范围与缓存隔离

“已发布”只表示形成不可变可运行版本，不表示向所有用户公开，也不改变原资产所有权和可见范围。解析股票池、策略 YAML、因子、模型和组件时必须携带当前组织、用户和授权上下文，并在任务创建与结果读取时分别校验权限。

任务快照可以保存完成历史重放所需的私有定义，但页面、共享回测、导出、错误日志和诊断不得向无权用户暴露 YAML 原文、模型地址、组件源码或私有参数。共享回测仍仅供有权组织成员浏览；从共享回测复制后形成由当前用户独立拥有的策略副本，并保留共享来源和原作者归属。

内容寻址缓存不能绕过权限。公共运行时和组织共用 Wheel 可以按可信制品摘要复用；私有 YAML、股票池、Feature Store 分区、模型和解密后内容必须按租户与授权范围隔离，缓存键、日志和清理流程不得泄露其他用户的资产身份。

## 四、验收标准与决策门槛

### 4.1 里程碑 A：冻结清单与契约验收

进入里程碑 B 前必须冻结：

1. quantflow-contract 的具体版本，以及一期采用的模块类型、ExitRule 角色、业务职责映射和可覆盖参数规则；
2. UniverseSnapshot、MarketSlice、因子矩阵、SelectionSnapshot、PortfolioDecision、TargetPortfolio、TargetPosition、BasePositionSnapshot、OverlaySnapshot 和 ExitDecision 的字段与状态语义；
3. 一期固定股票池和手工成员快照的 ID、版本、血缘、成员生效时点与幸存者偏差防护；动态股票池只预留扩展字段，不实现业务语义；
4. 交易日历、时区、公司行为、权威停牌状态、NO_EVENT、上市前、退市后、逐时标记价沿用和候选资格规则；不得重新定义既有日终结算价与日终净值口径；
5. Selector 与开仓/T0 分数的关系、Top-N、并列排序、调仓计划和触发时点；尤其冻结 core_position_overlay 下 T0EligibilitySnapshot 的生效区间，以及失去资格时已有 overlay 通过 normal_exit 回到底仓、但绝不清掉底仓；
6. 方向持仓组合等权的资金基数、现金保留、最大持仓数、单标的上限、整手取整及剩余资金是否重分配；底仓＋T0 的逐标的底仓 map、初始权益公式、最大活跃 T0 标的数、单标的 overlay 上限和共享现金口径；
7. 同一决策批次的卖出与买入顺序、T0 卖出回款可用时点、资金预留、价格跳空，以及 T0 容量按卖出量、买回量或双边累计的消耗口径；
8. 跨越下一个决策时点的待成交订单如何撤销、替换或净额合并，以及部分成交、拒绝、缩量和系统日终恢复如何进入下一次组合决策；
9. 开仓、普通退出、Stoploss、TakeProfit、TimeExit 的分数方向、范围、MISSING、ERROR、默认阈值、positionScope、profitBasis 和 Stoploss → TakeProfit → TimeExit → normal_exit 优先级；
10. Bar 时间戳、availableAt、每 Bar 风险/T0 时钟、计划调仓时钟、下一根可交易 Bar、日终组合时钟和正式区间结束的精确定义；
11. materialized 与 runtime 因子的资产身份、唯一权威来源和一致性校验规则；
12. Wheel 保留、签名信任根、摘要、依赖锁、Python ABI、运行镜像、隔离与第三方依赖冲突策略；
13. runPath、scopeType、strategyCategory、现有 mode 和 fillModel 的字段职责，以及 single/portfolio × directional_holding/core_position_overlay 合法矩阵；
14. 运行快照、结果 schema、executionContractVersion、随机种子、数值容差和确定性等级；
15. 基准对齐、组合收益、换手、集中度、标的贡献、退出次数、gross/net、费用、滑点，以及逐标的/组合底仓增强归因的计算和对账口径；一期冲击成本固定 impactModel = none、impactCost = 0；
16. 本地 Adapter 与投研平台 Adapter 的契约一致性数据集、比较字段和允许容差；
17. 固定性能工作负载、一期目标股票池规模和资源上限；工作负载必须包含多标的 T0、日内多次交易、独立风控和日终恢复；
18. “底仓不动”的准确含义：底仓是固定会计目标/基准而非物理锁仓，实际持仓可短时偏离，按 intraday_restore 或 cross_day_carry 结算；
19. 逐标的日初可卖量、T+1、T0 容量重置/消耗、overlay 正负、禁止真实做空，以及无本标的有效 Bar 时的处理；
20. intraday_restore 的系统订单身份、本标的结算价、成本和归因规则，以及与普通 bar_next_open 订单的边界；
21. 旧单标的标准 Bar/L2 T0、新组件化单标的标准 Bar和新多标的标准 Bar 的兼容、对拍和历史读取边界。

### 4.2 里程碑 B：本地单标的/多标的产品闭环验收

| 类别 | 验收标准 |
| --- | --- |
| 本地闭环 | 本地 Adapter 能从股票池、测试因子或测试 YAML 开始完成配置、计算、组合决策、撮合和结果展示 |
| 多标的语义 | 至少两个标的共享现金与账户，不是多个独立回测结果的简单合并 |
| 能力矩阵 | factor_system 与 strategy 两条 runPath 分别跑通 single/portfolio × directional_holding/core_position_overlay，共八种标准 Bar 组合；既有 single L2 T0 保持兼容；portfolio L2 明确拒绝 |
| 单标的兼容 | 一个成员的股票池通过相同组合链路运行，结果不存在另一套特殊因子系统实现 |
| 横截面计算 | Selector 或 Top-N 在同一时点看到完整可用候选集，结果不依赖标的遍历顺序 |
| 目标组合 | 职责内因子等权、directional_holding 的组合目标权重等权、core_position_overlay 的 T0 可用额度等比例分配分别生效，并生成确定的 TargetPortfolio |
| 资金竞争 | 多个标的同时开仓且资金不足时，按冻结规则分配，重复运行结果一致 |
| T0 状态隔离 | 逐标的底仓、成本、额度、日初可卖量、overlay 和日终策略互不串值，共享现金仍统一竞争 |
| 独立退出 | Stoploss、TakeProfit、TimeExit 和普通退出逐 Bar 执行、结构化记录；T0 默认只关闭对应标的 overlay，不清掉底仓 |
| 调仓 | directional_holding 入选集合变化时可退出旧成员并进入新成员；core_position_overlay 失去资格时用 overlay normal_exit 回到底仓且不清空底仓；两者均正确处理数量差额 |
| 成交路由 | 普通订单只在自身标的下一根可交易 Bar 使用本标的价格成交；系统日终恢复只使用自身标的冻结结算价并明确标记 |
| 缺失与停牌 | 一个标的停牌或缺 Bar 不会使用其他标的价格，也不会阻断无关标的事件 |
| 账户一致性 | PortfolioLedger 是账户唯一真相源，任何模块都不能直接修改现金或持仓 |
| 时间正确性 | 预热期无交易；因子只读取当时可见数据；区间结束后的 Bar 不承接任何因子或策略组件订单 |
| 可复现性 | 相同股票池、因子、参数、数据和执行契约重复运行，选择、订单和结果一致 |
| 归因与成本 | 逐标的及组合的账户收益、底仓基准收益、增强收益、费用和滑点完成对账；一期明确记录 impactModel = none、impactCost = 0；退出次数分层可追溯 |
| 提交粒度 | 一次用户提交只生成一个单标的或多标的回测任务，不自动展开 Trial |
| 正确性门禁 | T1-T4、未来数据检查、黄金样例对拍、事件去重、账本对账和确定性重放通过 |
| 调度复用 | 现有队列和 Runner 可并发处理普通任务，但一期不存在批次父任务、搜索空间、网格搜索或自动评分 |
| 前端 | 可以完成组合回测选择、股票池查看、覆盖摘要、因子配置、运行摘要和结果下钻 |
| 兼容性 | 既有单标的脚本、L2、历史结果和公开读取不因新默认值被重算或改写 |
| 性能 | 固定目标规模下达到里程碑 A 已冻结的耗时、吞吐和峰值内存门槛 |

至少覆盖以下工程自动化回归和发布冒烟用例。这里的“自动化”指 CI 与验收测试执行单次固定配置，不代表一期提供批量回测、网格搜索或策略质检实验产品：

1. 两个标的同一时点竞争有限现金，改变输入枚举顺序不改变最终分配；
2. directional_holding 的 Top-N 变化产生卖出旧成员和买入新成员的调仓批次；core_position_overlay 的 Top-N 变化更新 T0 资格，并将失去资格标的的已有 overlay 通过 normal_exit 回到底仓而不清底仓；
3. 某标的缺少当前 Bar 时，其待成交订单继续等待本标的下一可交易 Bar；
4. 组内必需因子 MISSING 时只使对应职责对对应标的不触发，不重分配因子权重；
5. 因子 ERROR、越界或协议不符时任务失败，并定位到标的和节点；
6. 当前时点截断数据后重新计算，截断前缀与全量运行的同一前缀一致；
7. 正式区间最后决策无法在区间内成交时记录区间结束未执行委托；
8. directional_holding 组合等权、core_position_overlay 的 T0 容量等比例目标分别经过单标的额度、整手、费用和现金约束后不出现超支；
9. 停牌持仓的估值、候选资格和交易限制符合冻结策略；
10. 一个成员股票池、多个成员股票池和旧单标的路径分别通过兼容性验证；
11. 两个标的使用不同底仓数量、成本、T0 额度和结算策略，状态与结果互不串用，初始权益符合冻结公式；
12. 两个 T0 标的竞争共享现金，改变输入枚举顺序不改变订单分配；
13. 同一标的同一交易日完成多次 T0，T+1、额度、部分成交和待单状态正确；
14. 一个标的触发 Stoploss、TakeProfit 或 TimeExit 时只关闭其 overlay，底仓目标和另一个标的状态不受影响；
15. 同一 Bar 四类退出规则同时命中时只生成一份有效退出，Stoploss 生效且全部 matchedExitTypes/componentTags 留存；
16. “持有 N 根 Bar 后且扣费后净浮盈大于 0”在 N-1/N、成本前后和下一开盘跳空场景下结果正确；
17. 两个标的最后有效 Bar 时间不同，intraday_restore 分别按自身结算；cross_day_carry 正确保留；缺 Bar 或停牌不借用另一标的价格；
18. overlayQuantity 可以为负但 actualQuantity 始终不小于 0，任何真实 OPEN_SHORT/CLOSE_SHORT 被拒绝；
19. trigger、order、fill、reject、unexecuted 分层计数，部分成交不重复计算触发次数；
20. 佣金、过户费、印花税、滑点逐成交、逐标的、T0 与组合汇总一致且不会重复扣减；impactModel = none、impactCost = 0 被单独记录；
21. 单成员新链路与现有单标标准 Bar 在相同语义下完成指标对拍，既有单标 L2 T0 快照和历史结果按旧版本读取不变；
22. factor_system 与 strategy 两条 runPath 分别覆盖 single/portfolio × directional_holding/core_position_overlay；同一冻结输入下，两条来源路径进入公共内核后的目标、订单和结果符合契约预期；
23. TakeProfit 使用 profitThreshold = 0 时，扣费后净浮盈等于 0 不触发、严格大于 0 才触发，并分别覆盖正 overlay 与负 overlay 的方向性利润计算。

### 4.4 建议实施顺序

1. 完成里程碑 A：冻结投研契约、两类 strategyCategory、category-aware TargetPosition、退出契约、版本标识和最小联调样本，并通过契约样例验收；
2. 建设 UniverseProvider、FactorDataProvider、StrategyDefinitionProvider、ComponentResolver 及本地 Adapter；
3. 建设 MarketSlice、多标的事件调度、逐标的下一 Bar 路由和组合权益采样；
4. 把现有单标的 BasePosition、T0State、T+1、OverlayAttribution 和日终结算语义扩展为按 symbol + positionKey + side 隔离，日内状态再按 tradeDate 隔离；
5. 建设 FactorComputeSession、职责内因子等权、Selector、ExitRule、PortfolioDecision、category-aware TargetPortfolio，以及方向组合等权/T0 容量等比例分配；
6. 建设 RebalancePlanner、共享现金与 T0 订单风控、完整订单事件、结构化退出、成本和底仓增强结果版本；
7. 建设前端 UniversePicker、策略类别、逐标的底仓/T0 配置、四类退出规则、运行摘要和组合/T0 结果；
8. 使用本地 Adapter 完成里程碑 B 的正确性、未来数据、兼容性和性能验收；
9. 接入股票池来源、组件注册中心、内部制品库、策略 YAML、Feature Store 和模型仓库；
10. 完成真实策略与因子资产的端到端联调、历史重放、安全隔离和性能验收；
11. 按相互依赖范围同批发布 backend、Bar runner、前端和运行时镜像，并完成新任务、历史任务和缓存命中/回源验证。

一期完成后，系统边界为：投研平台负责定义、测试、发布和保存可复现的股票池、组件、策略、因子数据与模型；回测系统负责冻结这些资产、形成单标的或多标的方向/T0 目标、生成交易意图并统一执行。投研平台接入是在不改变已验收组合语义的前提下替换资产解析实现，并补齐真实制品获取、摘要校验、缓存、隔离和兼容性处理；不得反向重构组合内核。Ray、网格搜索、批量 Trial 和策略级自动质检属于二期实验层，不回灌到一期单次回测契约。
