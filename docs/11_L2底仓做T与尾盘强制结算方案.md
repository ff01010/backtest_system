# L2 底仓做 T 与尾盘强制结算方案

## 1. 目标与范围

为 `l2_quote（基础 L2 盘口回测）` 增加单标的底仓做 T 能力，解决首根 Bar 先出现卖出信号时没有可卖持仓的问题，同时保留 A 股当日买入不可卖出的约束。

本期仅改造自定义脚本的 L2 回测。普通 `bar_close（K 线收盘价成交）` 回测不接受这些参数，避免在没有十档盘口时产生看似一致、实际不同的结果。

本期不实现融券、保证金、券源、逐笔排队或多标的组合底仓。

## 2. 已确认的业务定义

### 2.1 回测起点

- `initialCapital（初始资金）` 是独立的初始 `cash（可用现金）`，不因底仓成本而扣减。
- `baseQuantity（底仓数量）` 和 `baseCostPrice（底仓成本价）` 是回测开始前已持有的当前标的底仓。
- 底仓在启动时直接进入账户长仓；首日 `sellableQuantity（可卖数量）` 等于底仓数量。
- 底仓成本只用于持仓成本、卖出已实现盈亏和起始权益基准，不改变初始可用现金。

### 2.2 两个持仓模式

- `intraday（日内目标底仓）`：每个交易日结束时，系统将总多头仓位结算回 `baseQuantity（底仓数量）`，而非结算为零。
- `overnight（允许跨日）`：不执行尾盘调仓；实际持仓跨日保留，次日开盘前其全部数量转为可卖。

`baseQuantity（底仓数量）` 为 `0` 时，`intraday（日内目标底仓）` 与现有日内清零行为等价，保持兼容。

### 2.3 T+0 做 T 容量，不改变股票 T+1

新增 `t0Enabled（启用底仓做 T）`。它不是“当天买入股票可再次卖出”，而是一项针对底仓的单日交易容量限制。

启用时，每个交易日开始：

```text
t0AvailableQuantity（当日做T剩余额度）
  = min(baseQuantity（底仓数量）, 当日开始时的实际多头持仓)
```

每笔实际成交的 `sell_close（平多）` 或 `buy_open（开多）` 都占用同一份额度。为防止多个待成交订单超额，委托接受时先预留额度；部分成交保留已占用部分，撤单时释放未成交预留。

示例：底仓 5,000 股，当日先卖 2,000 股，再买 2,000 股：

```text
起始：position（当前持仓）= 5,000，sellableQuantity（可卖数量）= 5,000，t0AvailableQuantity（当日做T剩余额度）= 5,000
卖出：position（当前持仓）= 3,000，sellableQuantity（可卖数量）= 3,000，t0AvailableQuantity（当日做T剩余额度）= 3,000
买入：position（当前持仓）= 5,000，sellableQuantity（可卖数量）= 3,000，t0AvailableQuantity（当日做T剩余额度）= 1,000
```

因此，`sellableQuantity（可卖数量）` 仍遵守 T+1：当天买入不增加它；`t0AvailableQuantity（当日做T剩余额度）` 则限制底仓在一天内可参与的总成交量，防止同一底仓无限循环交易而放大回测收益。

未启用 `t0Enabled（启用底仓做 T）` 时，底仓仍可用于真实 T+1 卖出，但不施加上述单日做 T 容量限制。

### 2.4 尾盘结算与涨跌停

仅 `intraday（日内目标底仓）` 进行尾盘结算，目标为：

```text
position（当前持仓） < baseQuantity（底仓数量）：买入差额
position（当前持仓） > baseQuantity（底仓数量）：卖出差额
```

处理顺序：

1. 使用 `14:57` 前最后一条有效十档盘口，按现有主动成交规则尝试结算；
2. 对盘口缺边、深度不足、封板等原因留下的差额，生成 `forced_settlement（尾盘强制结算）`：涨停单边封板的补买按最后快照有效买一价，跌停单边封板的补卖按最后快照有效卖一价；双边盘口深度不足时分别按最后可见卖一/买一价；
3. 强制结算跳过盘口深度和封板限制，保证最终持仓等于底仓；成交明细必须记录 `priceSource（价格来源）` 为“尾盘涨跌停强制结算”或“尾盘盘口深度不足强制结算”，并写入告警。

强制结算按用户确定的回测假设执行，不代表真实可成交订单。买入强制结算若导致 `cash（可用现金）` 为负，允许完成以保证恢复底仓，但必须在结果中记录“尾盘强制结算导致可用现金为负”，不得静默视为正常可用资金。

## 3. 数据契约

本期尾盘结算只使用已有 `quant.tick_quote（L2 三秒十档快照表）` 的最后有效快照：买入差额使用最后可见卖一，卖出差额使用最后可见买一。若某一侧为空而另一侧有有效最优价，则该价格记录为封板强制结算价。

- 不从固定涨跌幅、代码前缀或昨收价推算价格。
- 最后快照两侧均为空仍属于数据异常，任务明确失败，不制造成交价。
- 回测结果的 `dataSnapshot（数据快照）` 已记录 quote 数据源与版本；强制结算另在成交明细中记录使用的快照时刻和价格来源。

## 4. 接口、脚本与展示契约

### 4.1 请求参数

在 `BacktestRunRequest（回测请求）`、前端参数类型、历史回测快照中新增：

- `baseQuantity（底仓数量）`：非负整数；为 0 时 `baseCostPrice（底仓成本价）` 必须为空或 0。
- `baseCostPrice（底仓成本价）`：底仓大于 0 时必填、正数、符合标的最小价格变动单位。
- `t0Enabled（启用底仓做T）`：布尔值，默认 `false`；启用时要求底仓数量大于 0。

这三项仅允许 `fillModel=l2_quote（基础L2盘口回测）`；普通 K 线回测提交时若非默认值，接口返回 422，前端禁用并说明原因。

### 4.2 脚本上下文

为自定义脚本的 `bar（当前K线及账户数据）` 增加：

- `position（当前持仓）`：当前标的全部净持仓，包含底仓和策略成交仓位。
- `strategyPosition（策略持仓）`：当前脚本自身的净持仓，保留脚本识别自己订单的能力。
- `basePosition（底仓数量）`：固定的初始底仓数量。
- `sellableQuantity（可卖数量）`：当日可按 T+1 平多的剩余数量。
- `t0AvailableQuantity（当日做T剩余额度）`：未启用做 T 时为 `null`，启用时为非负整数。

现有无底仓脚本中 `position（当前持仓）` 与原行为一致。涉及字段和成交语义变化，必须同步更新唯一手册 `docs/玄龄回测系统使用手册.md`。

### 4.3 前端与结果

- L2 参数区新增“底仓数量”“底仓成本价”“启用底仓做 T”及简短规则说明；`intraday` 文案改为“尾盘恢复底仓”，`overnight` 保持“允许跨日”。
- 首次提交、历史回填、从历史重跑、实验快照和结果上下文统一保存与恢复新参数。
- 概览显示初始可用现金、初始底仓、市值化的起始总权益；收益和回撤以 `initialCapital + baseQuantity × baseCostPrice` 为起始权益，避免把外部底仓当作免费资产。
- 信号与成交明细区分策略委托、尾盘盘口结算和尾盘涨跌停强制结算；后者显示告警与价格来源。
- 日持仓表以引擎返回的实际仓位为准，不再通过成交列表从零仓反推，确保初始底仓被正确显示。

## 5. 实施步骤

1. 建立参数与快照契约。
   - 扩展 Pydantic 请求/响应、TypeScript 类型、表单状态、校验、历史运行序列化与 L2 任务 payload。
   - 更新保存策略参数的比对集合，确保新参数变化会提示保存或明确作为运行参数记录。

2. 扩展账本初始化能力。
   - 为 `PortfolioLedger（账户账本）` 添加显式初始多头仓位初始化，使用独立的系统 `positionKey（持仓键）`（例如 `base:<symbol>`）；L2 引擎在平多时按总仓和可卖规则路由到底仓与脚本仓，使 `sell_close（平多）` 可以正确出售底仓。
   - 初始底仓不生成伪造成交记录、不扣现金；初始化后标记成本价，正确计算账户权益与卖出已实现盈亏。
   - 在 L2 worker 会话创建时传入标的、脚本持仓键和底仓参数。

3. 实现 T+1 与 T+0 做 T 容量状态机。
   - 保留并重命名内部 `_day_sellable（当日可卖数量）` 语义；首日从底仓初始化，后续交易日从上日实际长仓初始化。
   - 新增 `_t0_available（当日做T剩余额度）` 与 `_t0_reserved（待成交预留额度）`；只对多头的开多和平多订单生效。
   - 在下单接受、部分成交、撤单、日终和跨日切换中原子更新/释放额度；拒绝信息必须包含当前可卖或做 T 剩余额，便于策略排查。
   - 保证 `position（当前持仓）` 始终由账本成交结果产生，不因额度变化而直接修改。

4. 改造尾盘恢复底仓。
   - 将现有“关闭所有仓位”替换为“计算目标与实际的差额”。
   - 先在最后有效十档盘口上尝试成交；处理多档、部分成交和单边涨跌停。
   - 根据最后快照的单边封板或双边深度不足状态，对残差生成可审计的强制结算成交，并记录负现金告警。
   - `overnight` 不触发该流程；日终待成交策略单仍正常撤销。

5. 调整脚本与结果适配。
   - 在 L2 引擎向脚本提供账户快照时补充底仓、可卖量和做 T 额度。
   - 将日持仓构造改为读取每日报表的实际数量与市值，不靠 fills 从零累积。
   - 为初始权益、强制结算成交和额度拒绝补齐摘要、明细与历史展示。

6. 更新手册与验证。
   - 更新 `docs/玄龄回测系统使用手册.md` 的 L2 成交时点、底仓、T+1、做 T 容量、尾盘强制结算和非实盘提示。
   - 新增后端与前端测试，执行完整 pytest、前端现有测试与打包检查（不安装或升级依赖）。

## 6. 必测场景

1. 底仓 5,000，首根信号卖 2,000：可接受、成交后总持仓和可卖量均为 3,000。
2. 先卖 2,000 再买 2,000：做 T 剩余额从 5,000 变为 1,000；总持仓回到 5,000，当日可卖量仍为 3,000。
3. 先买后卖：当天买入不增加 T+1 可卖量；若做 T 额度不足，卖单被拒绝并带余额原因。
4. 部分成交和撤单：未成交预留额度被释放，不造成次笔订单永久不可用。
5. 次日：前日新买仓位转为可卖；做 T 容量按底仓与实际仓位重新计算。
6. `intraday`：正常盘口足够时恢复底仓；单边封板时用有效一侧最优价对剩余差额强制结算；资金不足时仍恢复且显示负现金告警。
7. `overnight`：不调回底仓、实际仓位跨日；次日可卖量正确更新。
8. 底仓为 0：旧 L2 日内清零、跨日持仓行为和无底仓脚本输出保持兼容。
9. 最后快照单边封板：使用有效一侧最优价进行封板强制结算；双边深度不足：使用对手价强制结算；双边为空：任务明确失败。
10. 信号明细、历史回测、起始权益、收益回撤和脚本字段均与底仓一致。

## 7. 自审与风险处理

| 风险 | 处理 |
| --- | --- |
| `position（当前持仓）` 原先只反映脚本持仓，底仓加入后可能误导脚本 | 底仓使用独立系统持仓键；`position（当前持仓）` 改为总仓，并新增 `strategyPosition（策略持仓）`；无底仓行为不变。 |
| 单日多笔订单可绕过做 T 上限 | 接受即预留、撤单释放，而不是仅在成交后扣减。 |
| 初始底仓没有成交记录，结果页从零反推仓位会错误 | 引擎输出初始/每日实际仓位，结果页直接读取。 |
| 固定 10% 推算涨跌停会错配科创板、创业板、ST、上市首日等 | 不推算；只使用尾盘最后有效十档快照中可观察的最优价。 |
| 强制恢复底仓与现金约束冲突 | 根据已确认目标，强制结算允许负现金，但明细和告警显式暴露这一回测假设。 |
| 强制成交被误认为真实流动性 | 使用独立成交类型与价格来源，概览告警持续展示。 |
| 已有普通 K 线回测误用新规则 | 本期限定 L2；非 L2 请求拒绝非默认底仓参数。 |
| `intraday（日内平仓）` 旧文案暗示清仓 | 前端、历史和手册统一改为“尾盘恢复底仓”；底仓为零才等价清零。 |

## 8. 实施前置条件与完成标准

完成后，L2 回测可在首根 Bar 使用底仓卖出，T+0 做 T 容量不会超额，日内模式按尾盘最后盘口并在必要时以可审计方式恢复底仓，跨日模式保持实际仓位与 T+1 可卖规则。
