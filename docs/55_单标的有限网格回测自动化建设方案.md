# 单标的有限网格回测自动化建设方案

日期：2026-09-28

实施设计补充：2026-09-29

状态：待实施

## 一、背景与结论

当前代码已经具备以下可复用的单次回测能力：

- 已保存策略及不可变发布版本；
- 通过 `STRATEGY_PARAMETERS` 声明可调整的扁平标量参数；
- 网页和开放接口对已声明参数进行单次覆盖；
- 标准 Bar 与 L2 单标的异步回测；
- PostgreSQL 任务队列、Runner、租约、取消和重试，以及已经设计并实现的用户公平与全局并发控制；
- 单次回测的配置快照、行情快照、结果、绩效指标和历史读取。

其中，37 号统一调度方案仍待服务器发布验收，49 号性能方案仍待形成正式容量基线。本方案可以基于现有代码先开发和本地验证，但这两项必须作为批量实验向普通用户开放前的上线门禁，不能把“代码中已经存在”直接写成“生产容量已经验证”。

当前缺少的不是另一套回测引擎，而是单次回测外层的实验编排能力。用户需要手工修改参数、反复提交、等待、记录结果，再自行汇总比较。该过程容易遗漏组合、混用策略版本、重复提交、超量占用资源，并且无法可靠复现一次完整搜索。

本方案优先建设“单标的有限网格回测自动化”：用户固定一份已发布策略版本及其标的、周期和撮合模型，显式提供有限参数值和实验场景；系统预览并冻结笛卡尔积，将其展开为多个相互独立的单标的 Trial，复用现有回测任务链路执行，最后通过可版本化的 EvaluationSpec 自定义过滤、排序、派生指标、分组和报告。

本方案的核心边界是：

> 自动化发生在单次回测之外，不改变策略、行情、撮合、账户、费用或结果语义。首期一个 Trial 是固定的单标有限网格点；长期一个 Trial 是某个 ExperimentStage 生成的一份普通单次回测候选。Experiment 只负责编排、调度协调和结果分析，不进入单次回测内部。

两份方案的依赖方向固定为：50 号方案先提供版本化、可独立提交的单次回测契约；本方案的实验层消费该契约并生成多个普通回测任务。实验层不能进入因子计算、组合决策、撮合或账本内部，50 号方案也不能在单次回测内复制一套批量实验状态机。

## 三、建设目标与非目标

### 3.1 建设目标

1. 用户能够从一份已发布策略版本创建单标的有限网格实验。
2. 系统能够对显式有限参数和场景进行确定性展开，并在提交前显示 Trial 数量、组合明细和资源估算。
3. 每个 Trial 复用现有单次回测校验、队列、Runner、快照和结果链路。
4. Experiment 能够汇总 Trial 状态，支持受控派发、批量取消、失败隔离和历史追溯。
5. 原始 Trial 结果保持不可变；用户可以在完成后创建多份 EvaluationSpec，反复自定义分析而不重新回测。
6. 支持参数对比、费用压力、时间区间对比、参数平原和样本内外结果对照。
7. 标准 Bar 与 L2 使用同一实验契约，但按各自能力、资源成本和合法参数执行。
8. 旧策略、旧回测任务、旧历史结果和现有单次回测入口保持兼容。
9. 首期单标策略、有限网格和现有任务队列分别作为可替换的实验对象解析器、Trial 生成器和派发实现接入，使后续因子系统、策略 YAML、多标的任务、多阶段验证和 BatchExecutor 通过扩展契约接入，而不是重写实验核心。

### 3.2 首期明确不做

首期交付不包含：

- 多标的共享现金、共享持仓或统一组合决策时钟；
- 一个 Trial 同时运行多个标的；
- 在同一 Experiment 中改变已保存策略的标的、周期、回测模式、策略类别或撮合模型；
- 把多个单标的 Trial 的收益简单相加并称为组合回测；
- 股票池组合调仓、组合贡献、leave-one-out 或剔除最大贡献标的复跑；
- 首期实际运行因子系统、策略 YAML、组件 Wheel 或投研平台资产自动化；本方案只预留其不可变资产清单、可调输入目录和单次回测编译边界；
- 随机搜索、贝叶斯优化、遗传算法、强化学习或其他自适应搜索；
- 根据中间结果自动新增参数值或扩大搜索空间；
- 平台内置综合评分自动认定“最佳策略”；
- 自动发布策略、自动修改策略、自动进入模拟盘或实盘；
- 在评价公式中执行任意 Python、SQL、JavaScript 或用户代码；
- 为批量实验改写现有回测引擎；
- 一期引入 Ray 或建设独立分布式计算平台。

## 四、核心原则

### 4.1 单次回测仍是唯一执行单元

每个 Trial 的首次 TrialExecution 必须生成一个普通 `backtest_run`；人工重试再生成新的 TrialExecution 和 `backtest_run`。每次执行都走与用户手工提交相同的服务端校验、任务排队、Runner 领取、策略隔离、行情加载、撮合、账本、结果归一化和持久化链路。

Experiment 不直接执行策略，不直接读取行情，不复制撮合或绩效计算，也不能绕过单次回测权限与资源限制。

### 4.2 结构字段固定，实验字段可变

首个版本通过 `legacy_single_strategy_v1` RunTemplateResolver 生成不可变 RunTemplateSnapshot。该快照固定以下现有单标策略结构字段：

- `configId` 与不可变 `configVersionId`；
- `scriptId`、策略代码版本、运行时版本和能力摘要；
- `symbol`、`benchmarkSymbol` 与 `timeframe`；
- `mode = backtest`；
- `accountId`、账户配置身份和 `positionMode`；
- `strategy`、`strategyCategory`、`holdingPolicy` 与 `overlaySettlementPolicy`；
- `fillModel`；
- `allowLong`、`allowShort`、`orderCash` 与 `orderPct`；
- `initialPositionEnabled`、`baseQuantity`、`baseCostPrice` 与 `t0Enabled`；
- 由脚本版本声明的 `warmupTradingDays`；
- `signalDatasetId` 及其不可变研究信号附件快照；
- 实际生效的 FeeProfile ID、版本和费率摘要。

上述字段不是兜底示例，而是 `legacy_single_strategy_v1` 的完整结构字段集合。实现新增请求字段时必须在同一改动中明确归类为结构字段或实验字段，并贯穿预览、指纹、快照、恢复和历史读取；不得因未列入集合而默认允许网格化。

Experiment 通用身份不得把 `configId`、`scriptId` 或标量 `symbol` 设计成必填顶层列。它只引用带类型和版本的 RunTemplateSnapshot；首期解析器在快照内部保存上述字段。50 号方案接入后，新的解析器可以在同一位置保存 `runPath`、`scopeType`、UniverseSnapshot、策略 YAML、组件 Wheel、Feature Store、模型制品和执行契约，而不改变 Experiment、Stage 或 Trial 的身份模型。

以下字段由首期 TunableInputCatalog 声明为可调输入，可以在当前合法范围内作为实验维度：

- `STRATEGY_PARAMETERS` 已声明的 `int`、`float`、`bool` 和 `str` 参数；
- 完整的开始/结束日期场景；
- `initialCapital`；
- `slippage`；
- `executionAlgorithm` 及其完整参数场景。

日期不能拆成独立的开始日期和结束日期后任意交叉，执行算法及参数也不能拆成可能形成非法组合的独立字段。二者都作为原子场景参与展开。

首个版本不把 `commissionRate` 作为网格维度。当前提交校验会按服务器默认 FeeProfile 覆盖请求费率，因此 Experiment 必须冻结实际生效的 FeeProfile ID、版本和费率摘要。未来若要支持佣金压力场景，必须先新增受控、可校验、可快照的 FeeProfile 覆盖契约；不得仅把不同 `commissionRate` 写入 TrialSpec 后声称已经生效。

### 4.3 输入变化与评价变化分离

- 修改 ExperimentSpec 会改变要运行的 Trial，必须创建新的实验修订并重新执行受影响的 Trial。
- 修改 EvaluationSpec 只改变已有结果的过滤、排序、分组、公式和展示，不重新运行 Trial。
- 原始 Trial 配置、快照和结果永不被评价规则改写。

### 4.4 有限、显式、可预览

系统只展开用户明确提供的有限值集合。提交前必须展示：

- 每个维度及其值；
- 规范化和去重后的 Trial 总数；
- 标准 Bar 或 L2 类型；
- 预计工作量与资源等级；
- 超限原因；
- 前若干项和尾部若干项组合预览。

未经用户确认不得开始派发任务。系统不得在运行中自行增加参数值或改变搜索范围。

### 4.5 用户公平优先于单个实验吞吐

实验 Trial 仍按当前用户身份进入现有公平调度，不获得专用高优先级，不预留全局槽位，也不能通过大量子任务或创建多个 Experiment 绕过单用户聚合并发限制。同一用户内部先保障普通手工任务的保留额度，实验任务只使用剩余额度并在多个 Experiment 之间稳定轮转。

### 4.6 冻结版本提交是前置能力

当前普通提交链路会根据 `configId` 重新读取当前策略配置，并用当前发布版本覆盖请求中的版本。该行为适合即时单次回测，但不能直接用于分批物化的 Experiment：如果用户在实验运行期间更新或重新发布策略，后续 Trial 可能错误地使用新版本。

里程碑 A 必须先增加仅供服务端实验协调器使用的冻结版本提交能力：

1. 创建 Experiment 时，在当前用户权限下读取并冻结完整策略发布版本、脚本版本、参数声明、固定结构字段、FeeProfile、研究信号附件、运行时版本和能力摘要；
2. 每次物化 Trial 时从受信任的 ExperimentRevision 快照构造请求，不再解析当前策略版本；
3. Trial 仍执行当时有效的通用请求校验、资源校验和数据加载，但不能用当前配置覆盖冻结字段；
4. 快照内容摘要进入 ExperimentSpec 和 TrialSpec 指纹；
5. 普通编辑、重新发布、重命名或归档不改变已经冻结的 Experiment；所有权撤销、管理员安全禁用或运行能力失效时停止物化新 Trial，并给出稳定原因；
6. 客户端只能引用 ExperimentRevision，不能直接提交任意策略源码或伪造冻结快照。

该能力是实验编排的可信入口，不是新的回测引擎，也不能绕过现有脚本安全校验。

### 4.7 面向 50 号方案最终态的稳定扩展边界

“单标的”和“有限网格”是首期能力门禁，不是 Experiment 核心模型的永久假设。首期必须按以下稳定边界实现：

```text
当前策略 / 未来因子系统 / 未来策略 YAML
  → RunTemplateResolver
  → RunTemplateSnapshot + TunableInputCatalog
  → ExperimentPlan + ExperimentStage
  → TrialGenerator
  → TrialSpec
  → TrialCompiler
  → 普通单次回测提交契约
  → TrialDispatcher
  → 当前任务队列 / 未来 BatchExecutor 或 Ray
  → backtest_run + 版本化结果
  → ResultMetricAdapter
  → MetricCatalog + DimensionCatalog + EvaluationRun
```

各扩展点职责固定为：

| 扩展点 | 职责 | 首期实现 | 50 号方案最终态扩展 |
| --- | --- | --- | --- |
| RunTemplateResolver | 在用户权限上下文中把实验对象解析为不可变单次运行基线和可调输入目录 | 现有已发布单标脚本策略 | `factor_system` 配置、策略 YAML 与投研资产清单 |
| TrialGenerator | 根据版本化 StageSpec 确定性生成 TrialSpec | `finite_grid_v1` | 样本外阶段、多股票池/多周期矩阵、leave-one-out、贡献剔除复跑 |
| TrialCompiler | 把运行基线和维度赋值编译为对应单次回测提交契约 | 现有单标 BacktestRunRequest | 50 号方案的 single/portfolio × factor_system/strategy 提交契约 |
| ResourceEstimator | 根据编译前后的任务定义计算预算 | 标准 Bar/L2 单标估算器 | 股票池、因子、组件、Feature Store、模型和组合规模估算器 |
| TrialDispatcher | 受控派发已编译的普通回测任务 | 现有队列的有限在途窗口 | BatchExecutor；必要时由其内部使用 Ray |
| ResultMetricAdapter | 按结果 schema 提供稳定 MetricCatalog 指标行和 DimensionCatalog 维度行 | 现有单标 Bar/L2 结果 | 组合结果、标的贡献、因子/策略追溯和归因指标 |

扩展点必须通过版本化契约和注册表选择，禁止在 Experiment 协调器中按 `if factor_system`、`if portfolio` 复制资产解析或执行逻辑。Ray 只允许成为 TrialDispatcher/BatchExecutor 的执行实现，不能进入 ExperimentSpec、策略 YAML、组件契约、Trial 指纹或单次回测结果语义。

## 五、领域模型

### 5.1 Experiment

Experiment 表示一次可追溯的自动化研究工作，拥有稳定 ID、所有者、名称、说明、当前修订、聚合状态和创建时间。首期每个 ExperimentRevision 只有一个 `finite_grid_v1` Stage，并且只接受 `legacy_single_strategy_v1` 运行模板。

Experiment 本身不持有现金、持仓、行情或回测结果，也不占用执行槽位。

同一 Experiment 同时最多存在一个活动修订。当前修订进入终态后才允许创建并切换到下一修订；旧修订的 Stage、Trial、TrialExecution、Evaluation 和状态继续独立可读，不得被新修订修改、复用或重新聚合。需要让两套配置同时运行时，用户必须复制为两个独立 Experiment。

### 5.2 ExperimentSpec

ExperimentSpec 是不可变的实验运行定义，至少包含：

- schema 版本；
- 带 `subjectType` 和精确版本的实验对象引用；
- RunTemplateSnapshot 及其内容摘要；
- 由一个或多个 ExperimentStageSpec 组成的 ExperimentPlan；
- 首期 Stage 的参数网格，以及用户自定义并冻结的数据集、资金、成本和执行场景；
- Stage 生成器及展开规则版本；
- 已知的 Stage Trial 数量、实验资源预算和预算版本；
- 失败与取消策略；
- 创建者和创建时间；
- 规范化内容摘要。

草稿可以编辑；一旦确认并开始创建 Stage 或 Trial，当前修订不可原地修改。任何输入变化产生新的 ExperimentSpec 修订，旧修订继续可读。只有当前修订已经终结时才能在同一 Experiment 中创建新修订；新修订拥有独立 Stage、Trial、执行和评价，Experiment 列表状态只聚合当前修订。首期创建时能够确定唯一 Stage 的精确 Trial 总数；未来结果驱动阶段可以只在 ExperimentPlan 中冻结生成规则和依赖，待上游不可变输出形成后再确定下游 Trial 集合。

### 5.3 RunTemplateSnapshot

RunTemplateSnapshot 是一项实验对象经过权限校验、资产解析和能力校验后形成的不可变单次运行基线。它至少包含：

- `templateType` 与模板 schema 版本；
- 原始 `subjectType`、资产 ID、精确版本和所有权上下文摘要；
- `runPath`、`scopeType`、`strategyCategory`、`mode` 和 `fillModel`；
- 固定运行输入及其来源；
- TunableInputCatalog；
- AssetManifestSnapshot；
- 单次回测提交契约版本、执行契约版本和结果 schema 版本；
- 运行时能力、资源估算器和 TrialCompiler 的兼容版本；
- 规范化内容摘要。

首期 `templateType = legacy_single_strategy_v1`，`runPath = strategy`，`scopeType = single`，AssetManifestSnapshot 保存现有策略发布版本、脚本、研究信号附件、FeeProfile、运行时和行情能力摘要。50 号方案接入后可以新增模板类型，保存 UniverseSnapshot、策略 YAML、组件 Wheel、quantflow-contract、Feature Store、模型和组合执行契约；不得把新资产回填到旧模板或用当前版本解释历史快照。

AssetManifestSnapshot 中每项资产至少使用 `assetType + assetId + exactVersion + contentDigest` 定位，并记录来源类型、可见范围摘要和物化要求。它保存可复现身份，不保存访问令牌；页面和普通 API 只返回脱敏摘要。实际私有制品由对应单次回测准备链路在授权上下文中物化，实验层不直接下载 Wheel、Feature Store 或模型文件。

如果未来某个 TunableInput 允许在多个股票池、组件、因子数据版本或其他资产之间选择，RunTemplateSnapshot 必须在实验冻结时记录全部允许候选的精确身份和摘要；Trial 只能选择这份冻结集合中的一项。不得在下游 Stage 物化时再按名称查询“最新”资产。

TunableInputCatalog 使用稳定输入 ID、类型、分组、约束、默认值来源和覆盖策略声明可实验字段。TrialGenerator 只能引用目录中的输入 ID，不能接受任意 JSON Path 修改策略 YAML、组件参数、股票池或运行快照。

### 5.4 ExperimentStage

ExperimentStage 表示 ExperimentPlan 中一个可独立生成 Trial、执行和形成输出的阶段，至少包含：

- 稳定 `stageId`、`stageIndex` 和 `stageType`；
- 依赖的 `stageId` 列表；
- 不可变 StageSpec、生成器类型和生成器版本；
- 输入 RunTemplateSnapshot 摘要，以及可选的上游 EvaluationRun 或 SelectionArtifact 摘要；
- 根据 StageSpec、生成器身份、RunTemplateSnapshot 和全部上游制品摘要计算的 `stageInputFingerprint`；
- Trial 计划数、已生成数、确定性生成游标和阶段聚合状态；
- 输出 Trial 集合摘要和生成审计信息。

首期固定创建一个无上游依赖的 `finite_grid_v1` Stage。创建请求事务只冻结 ExperimentRevision、RunTemplateSnapshot、StageSpec、生成器版本、精确 Trial 计划数、资源预算和初始生成游标，不在请求事务中插入全部 Trial。事务提交后 Experiment 和 Stage 进入 `preparing`，由协调器按 `trialIndex` 确定性分块生成 TrialSpec。

每个生成分块必须在独立短事务中完成：按冻结游标调用同版本 TrialGenerator，插入 Trial，更新已生成数、游标和增量摘要后一起提交。数据库同时约束 `(stage_id, trial_index)` 与 `(stage_id, trialFingerprint)` 唯一；协调器重启或重复扫描时从已提交游标继续，同一分块可以安全重放。只有已生成数等于计划数、集合摘要校验通过后，Stage 才从 `preparing` 转为 `queued` 并允许物化 TrialExecution。生成失败保留已提交分块并记录 `generation_blocked`，修复后从原游标续跑，不删除 Experiment 或从头展开。

Stage 不引入额外执行槽位；它只是 Trial 的来源、进度和恢复边界。

未来可以增加样本外验证、股票池/周期矩阵、leave-one-out、贡献剔除复跑或自动质检 Stage，并通过 `dependsOnStageIds` 消费已经冻结的上游输出。新增 Stage 类型是扩展生成器注册表，不得改变旧 `finite_grid_v1` 的展开和指纹语义。

### 5.5 TrialSpec

TrialSpec 是某个 ExperimentStage 生成的一项规范化单次回测定义。它必须能够通过冻结版本的 TrialCompiler 无歧义转换为对应的普通单次回测提交契约。首期转换为现有 `BacktestRunRequest`；50 号方案接入后可转换为其 factor_system 或 strategy、single 或 portfolio 单次提交契约。

TrialSpec 至少包含：

- `experimentId` 与 `experimentRevision`；
- `stageId`、Stage 生成器类型和版本；
- Stage 内稳定且连续的 `trialIndex`；
- RunTemplateSnapshot 摘要；
- 本 Trial 的规范化维度赋值；
- 编译后的单次运行输入摘要及其提交契约版本；
- 生成来源，包括可选父 Trial、EvaluationRun 或 SelectionArtifact 摘要；
- TrialSpec schema 版本；
- 确定性 `trialFingerprint`。

`trialFingerprint` 根据 RunTemplateSnapshot 摘要、`stageInputFingerprint`、Stage 生成器身份、规范化维度赋值、生成来源和单次提交契约版本计算。数据库自增 ID、创建时间、字段顺序、JSON 表示差异或重复输入值不得产生不同指纹。不同 EvaluationRun 或 SelectionArtifact 生成的候选即使最终参数相同，也必须保留不同生成来源；是否允许复用已有运行只能由独立、可审计的结果复用规则决定，不能靠指纹碰撞隐式合并。

### 5.6 Trial

Trial 是 ExperimentStage 中一个逻辑候选，与 TrialSpec 一一对应。首期它是笛卡尔积中的一个网格点；未来也可以是验证、消融或复跑阶段生成的候选。Trial 保存当前汇总状态和选定的有效执行，但不把一次运行误当作候选本身。

Trial 至少包含：

- TrialSpec 和 `trialFingerprint`；
- `materializationStatus`；
- 当前选定的 TrialExecution；
- 当前汇总状态；
- 创建时间；
- 失败、取消和重试摘要。

`materializationStatus` 只表达编排层状态：

- `pending`：尚未创建 TrialExecution；
- `materialized`：已经存在至少一个 TrialExecution；
- `cancelled_before_materialization`：取消时尚未创建执行，今后不得再物化。

`pending` 在 Experiment 聚合中计为 queued，`cancelled_before_materialization` 计为 cancelled；`materialized` 后的执行状态以选定 TrialExecution 对应的现有任务表和 `backtest_run` 为真源。Trial 不持久化可能卡死的 `creating` 中间态；协调器必须在同一数据库事务中完成 `pending → materialized`、TrialExecution、普通回测任务和额度占用，事务失败则全部回滚。实验表不复制一份可以独立漂移的任务终态。

### 5.7 TrialExecution

TrialExecution 表示 Trial 的一次人工可见执行，关联一个 `backtest_run.run_id`，至少保存：

- 执行序号；
- `run_id`；
- 创建、排队、开始和结束时间；
- 结果 schema 版本与规范化结果摘要；
- 取消或失败摘要；
- 是否被选为该 Trial 的有效执行。

现有队列在同一个 `backtest_run` 内进行的租约重领或基础设施自动重试仍属于该运行的 Attempt，不新增 TrialExecution。用户明确“重试失败项”时创建新的 `backtest_run` 和新的 TrialExecution，旧执行记录永久保留。同一 Trial 同时最多存在一个非终态 TrialExecution。

### 5.8 EvaluationSpec

EvaluationSpec 表示如何解释一批已有 Trial 结果，至少包含：

- 适用的 Experiment 修订和 Stage 范围；
- 指标目录版本；
- 展示字段；
- 过滤条件；
- 分组维度；
- 聚合规则；
- 多级排序及并列规则；
- 安全派生公式；
- 图表与报告布局；
- EvaluationSpec 版本和内容摘要。

同一个 Experiment 可以保存多份 EvaluationSpec。修改评价条件产生新版本，不覆盖旧版本，也不改变 Trial。

### 5.9 EvaluationRun

EvaluationRun 表示一次实际评价计算。它必须冻结：

- EvaluationSpec 版本；
- MetricCatalog 版本；
- ResultMetricAdapter 类型和版本；
- 每个参与 Trial 对应的 `trialExecutionId`、`run_id` 和规范化结果 SHA-256；
- 参与集合摘要；
- 评价流水线版本；
- 生成时间；
- 结构化评价输出或不可变输出制品摘要。

Trial 后续产生新的执行结果时，旧 EvaluationRun 继续读取原来的执行集合和输出。用户选择“基于最新结果重新评价”时创建新的 EvaluationRun，不原地覆盖旧结果。

### 5.10 后续 SelectionArtifact 边界

50 号方案最终态中的自动评分淘汰不能让 EvaluationSpec 直接创建或删除 Trial。后续应由版本化 SelectionPolicy 消费一个不可变 EvaluationRun，生成不可变 SelectionArtifact；下游 ExperimentStage 只引用该制品摘要生成新的 Trial。

首期不实现 SelectionPolicy、SelectionArtifact 或自动阶段推进，但 ExperimentStage 的依赖和 TrialSpec 的生成来源必须预留这些稳定引用。这样“评价事实”“候选选择”和“下游任务生成”保持分离，用户修改评分公式不会静默改写已经执行的 Trial 或自动触发未确认的新回测。

## 六、有限网格定义与展开

### 6.1 参数网格

首期 `finite_grid_v1` 参数网格只能引用 RunTemplateSnapshot 的 TunableInputCatalog 中由策略发布版本 `STRATEGY_PARAMETERS` 映射得到的稳定输入 ID。每个值必须通过目录声明的名称、类型、范围和大小校验。

示例：

```json
{
  "window": [10, 20, 30],
  "stopLoss": [0.03, 0.05],
  "enableVolumeFilter": [true, false]
}
```

同一参数的重复值在规范化后去重，并向用户展示去重前后数量。未列入网格的已声明参数使用该 RunTemplateSnapshot 保存的有效默认值。参数名到输入 ID 的映射由 `legacy_single_strategy_v1` 解析器负责，Experiment 核心不直接解析脚本或参数声明。

### 6.2 原子场景

日期、成本和执行参数使用具名场景：

```json
{
  "dateScenarios": [
    {
      "id": "development-2024",
      "role": "development",
      "startDate": "2024-01-01",
      "endDate": "2024-12-31"
    },
    {
      "id": "validation-2025",
      "role": "validation",
      "startDate": "2025-01-01",
      "endDate": "2025-06-30"
    }
  ],
  "costScenarios": [
    {
      "id": "no-slippage",
      "slippage": 0
    },
    {
      "id": "stress-slippage",
      "slippage": 0.01
    }
  ]
}
```

首个版本的 CostScenario 只改变当前链路真实支持覆盖的 `slippage`，实际佣金及其他费用来自 Experiment 冻结的 FeeProfile。一个场景内部字段必须整体校验，不能从两个场景中交叉拼接。执行算法场景必须同时冻结算法名称和完整参数；`twap` 仍只允许进入现有合法的 L2 路径。

### 6.3 确定性展开

首期 `finite_grid_v1` TrialGenerator 的展开顺序固定为：

1. 按规范字段路径排序维度；
2. 每个维度内部保留用户确认后的规范化值顺序；
3. 依次展开策略参数、日期场景、资金场景、成本场景和执行场景；
4. 对每项执行完整单次回测校验；
5. 生成连续 `trialIndex` 和稳定 `trialFingerprint`。

相同 RunTemplateSnapshot、StageSpec 和生成器版本必须得到相同 Trial 数、顺序和指纹。未来新增生成器使用自己的版本化规则，不得修改 `finite_grid_v1` 的既有输出。

### 6.4 数量与资源预算

创建首期有限网格 Stage 前必须计算：

```text
trialCount = 参数组合数
           × 日期场景数
           × 资金场景数
           × 成本场景数
           × 执行场景数
```

系统配置至少提供：

- 单个维度最大值数量；
- 单个 Experiment 最大 Trial 数；
- 单用户未完成 Trial 总量；
- 单个 Experiment 最大在途任务数；
- 标准 Bar 与 L2 分别的资源预算；
- 单个 Experiment 最大预计 Bar 数、L2 数据量或运行时间等级；
- 预览结果有效期。

具体数值必须在实现前根据 49 号性能方案的容量证据冻结，不在本方案中凭空指定。超限时创建失败并返回每个维度、Stage 总量、实验总量和资源估算，不允许静默截断组合。

### 6.5 后续 Stage 生成器扩展

50 号方案最终态需要的样本外验证、多股票池/多周期矩阵、leave-one-out、剔除最大贡献标的复跑和自动评分淘汰，不得继续向 `finite_grid_v1` 增加条件分支。每种新能力应实现独立、版本化的 TrialGenerator，并声明：

- 接受的 RunTemplate `runPath`、`scopeType`、结果 schema 和能力要求；
- 所需的静态输入、上游 Stage、EvaluationRun 或 SelectionArtifact；
- Trial 生成顺序、稳定身份、数量何时可知和资源估算规则；
- Trial 数量在生成前不可知时的冻结硬上限、最坏资源预算和超限停止规则；
- 是否需要用户在进入下一阶段前再次确认；
- 失败、取消、重试和部分输出能否继续下游阶段；
- 输出 TrialSpec 和生成审计摘要的确定性规则。

首期注册表只启用 `finite_grid_v1`，预览和创建接口遇到其他 `stageType` 必须明确拒绝，而不是保存一份无法执行的未来配置。

## 七、前端实验创建器设计

### 7.1 页面位置与入口

前端新增一级导航“自动化回测”，与现有“策略回测”和“策略广场”并列。自动化回测页面承载实验列表、新建实验、实验详情、运行进度、结果评价和报告，不把多组合创建流程塞入现有单次回测表单。

创建实验提供两个入口，但进入同一个全页面创建器：

1. 自动化回测列表页提供“新建自动化回测”，先选择当前用户有权使用且后端判定可实验的已保存策略版本；
2. 现有策略回测页在“运行回测”旁提供次级按钮“创建自动化回测”，携带当前 `configId` 和固定版本进入创建器；存在未保存的策略或结构字段修改时禁止进入，并提示先保存策略。

两个入口提交的都是带类型和版本的 `subjectRef`，不把策略页面组件或 `configId` 作为创建器内部必需依赖。50 号方案接入后，投研因子系统页和策略 YAML 页可以携带各自 `subjectRef` 进入同一个创建器；创建器通过服务端返回的 RunTemplateSnapshot 和 TunableInputCatalog 决定可展示内容，不新增另一套实验页面。

创建器必须使用独立全页面，不使用弹窗或抽屉。有限网格、原子场景、预算和权威预览需要同时核对，并且应当支持浏览器前进、后退和刷新恢复。无论首期继续使用当前页面状态导航还是引入路由，浏览器 URL 都必须能够表达实验列表、新建实验和指定实验详情，确保页面可以刷新和复制链接。

### 7.2 四步创建流程

#### 7.2.1 选择实验对象（首期为基准策略）

用户选择一份可实验的已保存策略版本。前端提交 `subjectType + subjectId + subjectVersion`，读取服务端返回的 RunTemplateSnapshot 摘要、固定结构、发布版本、代码摘要、TunableInputCatalog、AssetManifestSnapshot 摘要、FeeProfile 和运行能力，并按以下规则展示：

- 标的、周期、回测模式、策略类别、撮合模型、策略代码版本、研究信号附件和 FeeProfile 为只读结构字段；
- 结构字段需要变化时，用户必须返回策略回测页修改并保存新的策略版本，不能在实验创建器中临时覆盖；
- 只有 `STRATEGY_PARAMETERS` 明确声明的参数才能进入参数网格；没有声明参数时仍可使用日期、初始资金、滑点和合法执行算法场景；
- 从策略回测页进入时，后端返回的固定版本与入口携带的版本不一致或已经不可用，必须停止创建并要求用户重新选择，不能自动切换到最新版本。

首期仅允许 `subjectType = legacy_strategy` 且解析结果为 `scopeType = single`。未来对象类型由 Resolver 注册表和能力矩阵决定；前端不得根据对象类型自行拼接冻结资产或猜测可调字段。

#### 7.2.2 配置搜索空间

创建器按维度展示有限候选值，并实时计算仅供交互提示的理论组合数：

| 区域 | 前端交互 | 约束 |
| --- | --- | --- |
| 策略参数 | 按参数类型录入有限候选值列表，展示默认值、类型和声明约束 | 不允许新增未声明参数；重复值在规范化预览时去重 |
| 日期场景 | 逐行添加名称、开始日期和结束日期 | 每一行是一个原子场景，开始和结束日期不分别交叉组合 |
| 初始资金 | 录入有限正数候选值 | 单位和精度必须与单次回测契约一致 |
| 滑点场景 | 逐行添加完整滑点场景 | 只允许当前链路真实支持的字段和单位 |
| 执行算法 | 从当前撮合模型返回的合法算法中选择，并填写完整算法参数 | 不允许把仅适用于 L2 的算法加入标准 Bar 实验 |
| 费用 | 展示冻结 FeeProfile ID、版本和费率摘要 | 首期只读，不允许把 `commissionRate` 加入网格 |

前端理论组合数只用于尽早提醒用户。它不能作为创建依据，不能替代服务端展开，也不能通过截断候选值把超限实验静默缩小。

表单组件应优先根据 TunableInputCatalog 的类型、分组、约束和场景编辑器标识渲染。首期可以为日期、资金、滑点和执行算法提供专用编辑器，但不能把仅适用于现有脚本的参数名写成 Experiment API 的固定字段。

#### 7.2.3 服务端权威预览

用户点击“预览组合”时，前端只提交待规范化的 subjectRef 和 ExperimentPlan 草稿，不展开或提交 Trial 数组。服务端解析 RunTemplateSnapshot，并调用当前 Stage 的 TrialGenerator。预览接口至少返回：

- RunTemplateSnapshot 摘要、规范化后的固定结构、参数网格和原子场景；
- Stage 列表、权威 Trial 总数、各维度数量和确定性展开摘要；
- 预计 Bar 数、L2 数据量或运行时间等级等资源估算；
- 实验预算、当前系统硬上限、警告和阻断原因；
- 可供人工核对的头部、尾部或分层抽样 Trial 示例；
- 规范化 `specHash`、短期有效且绑定当前用户的不可猜测 `previewToken`、过期时间、预览摘要，以及预览时绑定的策略、数据、预算与能力版本。

页面必须明确区分“警告”和“禁止创建”。超过硬上限、结构版本失效、场景非法或运行能力不满足时禁止进入确认步骤；不得只显示一个总数而隐藏产生该数量的维度明细。

#### 7.2.4 确认创建并开始

最终确认页展示实验名称、可选说明、实验对象、RunTemplateSnapshot 摘要、Stage、固定结构、搜索空间、Trial 总数、资源预算、FeeProfile、在途限制和只读 FailurePolicy 摘要。主按钮固定使用“确认创建并开始”，明确该操作会创建 ExperimentRevision 和首个 ExperimentStage，并立即进入服务端 `preparing`；协调器完成确定性分块生成后自动进入排队与分批物化，不再增加“服务端草稿创建后另行启动”的生命周期。

创建成功后直接进入实验详情页。详情页先展示已冻结定义和物化进度；浏览器关闭、刷新或离开页面都不能暂停已经创建的 Experiment。

### 7.3 预览失效与创建契约

前端修改任何会进入 ExperimentSpec 指纹的字段后，现有预览立即失效，“确认创建并开始”按钮禁用，必须重新执行服务端预览。

创建请求至少携带用户填写的 ExperimentSpec、服务端预览返回的 `previewToken + specHash` 和客户端生成的幂等请求键。`previewToken` 只引用一份短期服务端预览快照，不代表创建授权永久有效，也不是服务端草稿。服务端必须重新读取权限与能力、重新规范化、重新展开并重新计算摘要：

1. `previewToken` 属于当前用户、未过期，且重新计算结果与其保存的 `specHash`、RunTemplate、数据、预算和能力摘要一致时，在一个短事务中创建 Experiment、ExperimentRevision、RunTemplateSnapshot、ExperimentStage、精确 Trial 计划数、预算和初始生成游标，不在请求事务中插入全部 Trial；
2. 策略版本、权限、能力、数据可用性或规范化结果已经变化时，返回稳定的“预览已失效”冲突，由前端保留用户输入并要求重新预览；
3. 后端不得接受客户端提交的 Trial 总数、资源估算或完整 Trial 数组作为可信创建依据；
4. 相同幂等键和相同规范化内容重复提交时返回同一个 Experiment；相同键对应不同内容时返回冲突；
5. 创建请求超时或网络结果不确定时，前端使用原幂等键查询或重试，不生成新键盲目再次创建。

创建请求事务提交前发生校验错误时不得留下部分 Experiment、Revision 或 Stage。事务提交后，分块生成的 Trial 属于可恢复的持久进度，不视为创建残留；生成失败或进程重启时按 Stage 游标续跑。事务已经成功但响应丢失时，幂等查询必须能够找回处于 `preparing` 或后续状态的既有 Experiment。

### 7.4 本地草稿

首期只提供浏览器本地草稿，不建立服务端草稿实体。创建器按用户、`subjectType`、`subjectId`、固定版本和表单契约版本隔离保存未确认输入，用于页面刷新或误关闭后的恢复。

本地草稿不属于可信快照：恢复时必须重新读取实验对象和运行能力，任何旧预览摘要一律失效，并要求重新执行服务端预览。对象版本不可用、草稿契约版本不兼容或用户主动放弃时清除草稿；创建成功后只清除对应 subject 版本的草稿，不能误删其他实验对象草稿。

草稿不得保存策略源码、账户凭据、令牌或其他敏感信息。

### 7.5 交互状态与错误呈现

- 实验对象加载失败时保留入口来源，允许返回或重新选择，不能展示一份可编辑的空结构继续创建；
- 参数和场景错误尽量定位到具体字段或行，服务端全局错误展示稳定错误码、可操作说明和关联标识，不展示内部堆栈；
- 预览中展示“理论组合数”和“服务端确认 Trial 数”，二者不一致时以后者为准，并提示规范化原因；
- 创建提交期间锁定主按钮，重复点击复用同一幂等键；只有用户修改表单形成新创建意图后才生成新键；
- 创建成功后所有停止、恢复和重试操作都在实验详情页完成，创建器不继续维护一份可能漂移的运行状态。

### 7.6 API 驱动的创建流程

完整创建流程采用 API-first 设计。前端创建器只是内部 API 的一个客户端；Experiment 的规范化、预览、创建、展开和启动不得依赖 React 组件状态、浏览器进程或任何只能从页面触发的后端分支。具有相同身份、权限和请求内容的内部 API 调用应得到与前端相同的 ExperimentSpec、Trial 数量和创建结果。

首期 API 流程固定为：

```text
读取可实验对象、RunTemplate 与能力
  → POST 预览 subjectRef + ExperimentPlan
  → 获得规范化 RunTemplate、Stage、Trial 数、资源估算、specHash 和 previewToken
  → POST 创建 Experiment（ExperimentSpec + previewToken + specHash + Idempotency-Key）
  → 获得 experimentId、revisionId、状态和权威 Trial 数
  → GET 实验状态或按原请求键找回创建结果
```

API 契约必须满足：

1. 读取、预览和创建均执行当前用户身份、实验对象及其全部底层资产的所有权和运行权限校验；
2. 预览与创建请求包含创建 Experiment 所需的全部业务输入，不读取页面本地草稿或前端派生状态；
3. 创建接口内部调用与网页相同的领域服务，成功提交事务后立即进入 `preparing`，完成分块生成后自动排队和物化，不需要再调用一个仅供页面使用的“启动”接口；
4. API 调用方不能直接创建 Trial、TrialExecution 或普通回测任务，也不能绕过预览摘要、预算和服务端展开；
5. 创建响应至少返回 `experimentId`、`revisionId`、聚合状态、权威 Trial 总数、规范化摘要和创建时间；
6. 同一 `Idempotency-Key` 的安全重试和结果找回不依赖原浏览器会话仍保持连接；
7. 首期这些接口使用现有网页登录会话，并按本方案实施级安全契约新增真正的 CSRF Token 与 Origin 校验；当前仓库尚未具备该保护，不能把 CORS 或 `SameSite=Lax` 写成已完成的 CSRF 能力；这些接口不因此自动成为对 API Key、命令行工具或外部系统开放的公共 API。

未来开放 API 或接入投研平台页面时应复用这条应用服务和创建语义，只新增独立 API Key Scope、限流、版本化外部契约、subject Resolver 和审计入口，不能复制一套不同的实验创建逻辑。

## 八、实验创建与执行流程

### 8.1 创建流程

```text
选择实验对象（首期为已发布单标策略）
  → RunTemplateResolver 冻结运行基线与可调输入目录
  → 配置 ExperimentPlan（首期为单一 finite_grid_v1 Stage）
  → TrialGenerator 规范化、校验和展开预览
  → 用户确认数量与预算
  → 短事务冻结 ExperimentSpec、RunTemplateSnapshot、ExperimentStage、精确数量与生成游标
  → 协调器确定性分块生成全部 TrialSpec
  → TrialCompiler 编译并在有限窗口内物化 TrialExecution
  → TrialDispatcher 复用现有任务队列执行
  → ResultMetricAdapter 汇总结果
  → 创建或应用 EvaluationSpec
```

前端预览只用于展示，服务端必须在确认创建时重新规范化和校验，不能信任客户端提交的 Trial 数量或组合列表。

上述流程既可由网页创建器调用，也可完全通过内部 API 完成；API 成功创建 Experiment 后，后续物化和执行不再依赖调用端保持在线。

### 8.2 分批物化

系统不得一次向普通任务队列灌入整个大实验的全部 Trial。首期 TrialDispatcher 使用现有任务队列并按以下规则维持有限在途窗口：

1. 全局调度先沿用现有用户公平规则选择用户，Experiment 不因子任务数量获得更多全局槽位；
2. 同一用户的全部 Experiment 共享一个用户级实验在途硬上限，每个 Experiment 的在途上限只是第二层更小窗口，创建多个 Experiment 不能成倍扩大额度；
3. 用户内部为普通手工回测保留可配置额度；存在普通任务时，实验只能使用剩余实验额度，并在该用户的多个 Experiment 之间按稳定 round-robin 补充；最老普通任务超过配置等待阈值时，暂停为该用户新增实验执行，直到普通任务得到领取；
4. 只为已经完成 Trial 生成、未取消、未超过冻结实验预算且当前用户仍满足系统硬上限的 Experiment 选择 `pending` Trial；
5. 物化事务按固定顺序锁定用户额度、ExperimentRevision 和 Trial，锁后重新检查取消、预算、容量和 Trial 状态，再原子占用 permit、创建 TrialExecution、普通 `backtest_run` 与 Bar/L2 任务、写入 `run_id` 并把 Trial 更新为 `materialized`；任一步失败全部回滚；
6. 普通任务创建必须提供可加入同一 Unit of Work 的事务级服务，复用调用方数据库事务；协调器不得通过 HTTP 或调用自行提交事务的普通创建接口拼接这一步；
7. `backtest_run` 或对应任务保存稳定的 `sourceType = manual | experiment` 及可空 `experimentId/stageId/trialExecutionId` 调度来源，调度器据此落实普通任务保底和实验轮转；这些来源字段不改变回测执行语义；
8. TrialExecution 终态后释放用户与实验 permit；协调器定期从 TrialExecution 和任务真源校正额度，进程崩溃不能永久占用或重复释放额度。

用户额度行或等价 advisory lock 必须把“当前未完成实验规模 + 新实验计划数”的创建校验与额度登记串行化，并把物化时的 permit 检查与占用放在同一事务中，避免两个并发创建或两个协调器同时读到旧计数后双双超限。协调器崩溃或重复扫描时，`trialFingerprint`、`active_execution_id` 的 CAS 或等价部分唯一约束、任务幂等键和数据库事务共同防止同一 TrialSpec 或 TrialExecution 被重复创建。

协调器只依赖 TrialDispatcher 接口，不直接调用特定 Runner。未来 BatchExecutor 或 Ray 接入时必须保留相同 TrialExecution、`backtest_run`、权限、公平、取消、幂等和结果语义；更换派发实现不能改变 Trial 指纹或绕过普通单次回测契约。

### 8.3 状态模型

Experiment 聚合状态定义为：

| 状态 | 含义 |
| --- | --- |
| `preparing` | 已冻结，协调器正在按游标分块生成并校验 Trial，尚不允许物化执行 |
| `queued` | 已冻结，存在待物化或已排队 Trial |
| `running` | 至少一个 Trial 正在运行，且仍有未终结 Trial |
| `cancelling` | 已停止新增物化，正在取消已创建但未终结的 Trial |
| `completed` | 所有 Trial 成功完成 |
| `partially_completed` | 至少一个 Trial 成功，且至少一个失败或取消 |
| `failed` | 没有成功 Trial，且存在失败 |
| `cancelled` | 没有运行中的 Trial，且实验由取消结束 |

ExperimentStage 使用 `waiting_dependencies`、`preparing`、`queued`、`running`、`cancelling`、`completed`、`partially_completed`、`failed` 和 `cancelled`。首期唯一 Stage 没有依赖，从 `preparing` 开始；未来下游 Stage 只有在全部依赖输出冻结且通过 StageSpec 门禁后才能进入 `preparing`，完成确定性 Trial 生成后才能进入 `queued`。

Trial 只为“尚未物化”和“取消前未物化”增加必要的编排状态；一旦物化，执行状态直接映射现有回测任务状态。Stage 状态从所属 Trial 与依赖真源派生，Experiment 当前聚合状态只从当前修订的全部 Stage 派生；历史修订保留各自终态和计数，不参与当前修订聚合。首期只有一个 Stage，因此结果与直接从 Trial 聚合一致；实现仍必须经过 Stage 层，不能把单 Stage 当作永久数据模型并绕过它。

终态判定顺序固定为：

1. Experiment 已请求取消且仍有非终态 Trial 时为 `cancelling`；
2. 未请求取消且当前 Stage 尚未完成确定性 Trial 生成时为 `preparing`；生成暂停时附加 `generation_blocked` 原因；
3. 未请求取消且至少一个 TrialExecution 为 `running` 或 `cancelling` 时为 `running`；
4. 未请求取消、没有运行中执行，但存在 `pending` 或已排队 Trial 时为 `queued`；容量阻塞只附加 `capacity_blocked` 原因；
5. 全部 Trial 成功时为 `completed`；
6. 至少一个 Trial 成功、但并非全部成功时为 `partially_completed`；
7. 没有成功 Trial，且 Experiment 已请求取消或全部终态均为取消时为 `cancelled`，同时保留取消前已经失败的数量；
8. 没有成功 Trial、没有 Experiment 取消请求且至少一个 Trial 失败时为 `failed`。

该优先级消除“部分失败后又取消”同时满足 `failed` 与 `cancelled` 的歧义。

### 8.4 失败、重试与隔离

- 默认情况下，一个 Trial 失败不终止其他 Trial。
- 单次任务内部的租约和有限重试继续使用现有机制。
- 参数非法、结构字段冲突或资源预算超限在展开阶段失败，不创建部分实验。
- 运行阶段失败必须保留 TrialSpec、TrialExecution、run_id、稳定错误分类和脱敏诊断。
- 用户重新运行失败项时，保留原执行记录并创建新的执行关联；不得把旧失败结果原地改成成功。
- 只有没有成功 Trial、没有用户取消请求且至少一个 Trial 失败时，Experiment 才进入 `failed`；取消后的终态按 8.3 节优先级判定。

### 8.5 批量取消

取消 Experiment 时：

1. 原子写入取消请求，阻止新的 Stage 进入 `preparing/queued`，并停止继续生成 Trial 和物化新执行；
2. Stage 保存取消时的计划数、已生成数和生成游标，未生成数量作为 `cancelled_before_generation` 计数保留，不再补建空 Trial 行；
3. 已生成但未物化 Trial 原子更新为 `cancelled_before_materialization`；
4. 已排队和运行 Trial 调用现有取消语义；
5. 已成功、已失败或取消竞争中先完成的结果继续保留；
6. 所有实际执行进程退出前，Experiment 保持 `cancelling`；
7. 状态最终收敛为 `cancelled` 或 `partially_completed`。

批量取消不能直接删除 `backtest_run`，也不能通过释放父状态提前释放仍由子任务占用的全局槽位。

### 8.6 实验熔断、恢复与部分评价

Experiment 采用“父实验可续跑、单个 Trial 失败隔离”的恢复模型。系统故障或服务重启不得回滚已经成功的 TrialExecution，也不得从头重新展开整个网格。

故障恢复时按数据库真源处理：

1. `preparing` Stage 从已提交生成游标继续分块生成，已经写入的 `trialIndex/trialFingerprint` 不重复插入；
2. 已成功或已经明确失败、取消的 TrialExecution 保持原终态；
3. 仍有有效任务和执行租约的 TrialExecution 继续运行；
4. 租约过期的任务由现有任务恢复与有限重试机制处理；
5. 尚未物化的 Trial 保持 `pending`，阻塞解除后从原 `trialIndex` 继续物化；
6. `trialFingerprint`、TrialExecution 活动执行约束和任务幂等键共同防止恢复扫描重复创建；
7. Experiment 聚合状态和进度从 Stage、Trial 与 TrialExecution 真源重建，不依赖协调器进程内存。

本方案只提供 Experiment 级续跑，不提供单个回测的运行中 checkpoint。某个 TrialExecution 在策略回放中途失去执行进程时，现有任务机制可以重新执行该单次回测，但必须从该 Trial 开头运行；其他已完成 Trial 不受影响。

#### 8.6.1 失败分类

| 失败类型 | 处理 |
| --- | --- |
| 创建前契约错误 | 整个 Experiment 创建失败，不产生部分网格或子任务 |
| 单 Trial 的策略、数据或业务错误 | 当前 TrialExecution 失败，默认继续其他 Trial |
| 可重试基础设施错误 | 使用现有单任务有限重试；重试耗尽后当前 TrialExecution 失败 |
| 实验协调器、backend 或 Runner 重启 | 按租约、幂等键和数据库状态恢复，不重跑已成功 Trial |
| 系统性执行错误 | 触发实验熔断，停止物化新 Trial，并记录 `execution_blocked` |
| EvaluationRun 或报告错误 | 只重试评价或报告，不重新运行 Trial |

#### 8.6.2 系统性错误识别

ExperimentSpec 冻结版本化 FailurePolicy。错误率和连续错误默认在同一 ExperimentStage 内计算；只有共享 RunTemplate、资产清单、调度器或运行时故障可以升级为 Experiment 级阻塞。首期只有一个 Stage，两种范围结果相同。以下任一条件触发对应范围的 `execution_blocked`：

1. 冻结策略版本、运行时、执行能力、数据源或必要制品被明确判定为全实验不可用；
2. 同一规范化错误指纹在三个不同 TrialExecution 上连续出现；
3. 现有任务重试已经耗尽，且 FailurePolicy 配置的最近窗口内同一错误指纹失败率达到冻结阈值；
4. 管理员通过受审计操作暂停该实验的继续派发。

错误指纹至少包含稳定错误码、ExperimentStage 类型、RunTemplate 类型、runPath、scopeType、失败阶段、执行模式和责任组件，不包含标的账号、源码、路径或动态错误文本。首期固定单一标的，某一日期场景独有的数据错误可以只失败对应 Trial；只有满足上述跨 Trial 条件时才升级为 Stage 或 Experiment 级阻塞。

除“三个连续相同错误”外，失败率窗口大小、最小样本数和阈值必须作为 FailurePolicy 配置在实现前冻结，并写入 ExperimentSpec；不得使用运行时临时默认值改变历史实验行为。

#### 8.6.3 熔断后的状态

`execution_blocked` 是停止继续派发的阻塞原因，不是新的主状态，并且必须记录 `blockScope = stage | experiment` 及对应 `stageId`：

- 已有 TrialExecution 仍在运行时，Experiment 主状态保持 `running`；
- 已请求取消时保持 `cancelling`；
- 没有运行中执行但仍有 `pending` Trial 时显示 `queued + execution_blocked`；
- 熔断前已经终结的 TrialExecution 和结果永久保留；
- 协调器不得继续物化新 Trial，也不得自动把未运行网格点标记为失败。

#### 8.6.4 恢复操作

解除 `execution_blocked` 必须满足以下一种路径：

1. 系统健康检查确认临时基础设施或数据源故障已经恢复，并按 FailurePolicy 允许自动恢复；
2. 用户在查看错误摘要后明确执行“继续未完成 Trial”；
3. 管理员解除安全或运行能力阻塞，并留下审计记录。

恢复只清除当前阻塞原因并继续原 ExperimentRevision，不修改 TrialSpec。若修复需要改变策略版本、参数网格、日期、FeeProfile、运行时或其他冻结输入，必须创建新的 ExperimentRevision，不能在原实验上打补丁。

用户还可以选择：

- 只重试明确选择的失败 Trial，生成新的 TrialExecution；
- 保留已完成结果并取消剩余 Trial；
- 不恢复执行，只对当前成功结果创建部分评价。

#### 8.6.5 部分评价

未全部完成的 Experiment 可以创建标记为 `provisional` 的 EvaluationRun，但必须冻结并展示：

- 纳入的 Stage、各 Stage 已知或冻结上限内的 Trial 总数；首期展示网格 Trial 总数；
- 成功、失败、取消、运行中、排队和未物化数量；
- 本次评价实际采用的 TrialExecution 集合与结果哈希；
- 完成比例和未纳入原因；
- `isPartial = true` 与生成时刻。

部分评价不得默认标记为最终报告，不得隐藏失败或未运行项，也不得与全量评价使用相同的完成标识。Experiment 后续恢复并产生新结果时，原 provisional EvaluationRun 保持不变；用户必须明确创建新的评价版本。

## 九、标准 Bar 与 L2 能力边界

### 9.1 统一契约

ExperimentSpec、TrialSpec、EvaluationSpec 和结果汇总对标准 Bar 与 L2 使用同一外层契约。每个实验固定一种 `fillModel`，不能在同一网格中混合 `bar_next_open` 与 `l2_quote`。

### 9.2 标准 Bar

标准 Bar 作为首个上线路径，支持：

- 已声明策略参数有限网格；
- 日期、资金和滑点场景，以及冻结的 FeeProfile；
- 当前标准 Bar 合法执行配置；
- 现有预热、下一开盘、区间结束和结果语义。

实验层不得改变预热天数、行情来源选择或区间结束未执行委托规则。

### 9.3 L2

L2 在标准 Bar 闭环通过后接入相同实验层，并额外满足：

- 每个场景继续通过现有 L2 周期、执行算法和参数校验；
- TWAP 名称与完整参数作为一个原子执行场景；
- 使用更严格的 Trial 数和在途预算；
- 提交前展示预计 L2 数据规模和资源等级；
- 不能因批量实验扩大现有 L2 能力或放松安全限制。

L2 的启用是同一方案的后续里程碑，不阻塞标准 Bar 自动化先行交付。

## 十、结果指标目录

### 10.1 原始结果不变

每个 TrialExecution 的原始结果继续由现有回测链路产生和保存。实验层只读取，不重新计算或覆盖单次回测结果；Trial 只显式选择哪一次执行用于后续评价。

当前及 50 号方案未来执行路径的结果字段不会完全一致，因此由版本化 ResultMetricAdapter 按 `runPath + scopeType + strategyCategory + fillModel + resultSchemaVersion` 把原始结果适配为稳定 MetricCatalog 指标行。实验协调器和 EvaluationSpec 不直接读取某个 Runner 的私有字段路径。

MetricCatalog 至少记录：

- 指标 ID 与显示名称；
- 数据类型和单位；
- 越大越好、越小越好或中性；
- 指标粒度 `grain`、币种、窗口语义、年化规则、基准口径和版本化 `comparabilityKey`；
- 支持的 runPath、scopeType、撮合模型、策略类别和结果 schema；
- 原始字段路径；
- 空值语义；
- 指标口径版本；
- ResultMetricAdapter 类型和版本。

`metric_catalog_v1` 固定包含以下稳定 ID：

- `totalPnl`、`finalEquity`、`totalReturn`、`annualReturn`；
- `maxDrawdown`、`maxDrawdownRate`、`annualVolatility`；
- `annualSharpe`、`sortino`；
- `completedTradeCount`、`winRate`、`profitLossRatio`；
- `benchmarkReturn`、`excessReturn`；
- `queueDurationMs`、`runDurationMs`、`resultStatus`。

手续费、过户费、印花税、滑点成本和未来组合归因只有在对应结果 schema 提供可验证口径后，才能通过新 MetricCatalog 版本加入；v1 不从成交明细临时猜算一个未冻结口径。某个 Adapter 不支持 v1 中的指标时仍返回 `null + unsupportedReason`。

某个执行路径没有提供的指标必须返回 `null + unsupportedReason`，不得按 0 参与过滤、排序、聚合或评分。

只有 `metricId + comparabilityKey` 相同的指标值才能直接跨 Trial 排序或聚合。不同本金、币种、回放区间长度、年化日历、基准、single/portfolio 粒度或结果口径导致 `comparabilityKey` 不同时，Evaluation 必须拒绝直接比较，或者要求 EvaluationSpec 显式选择一个版本化 Normalizer 先转换为同一可比较域；页面不能只因显示名称相同就把这些数值放入同一排名。

DimensionCatalog 使用稳定 dimensionId 描述可以过滤、分组和展示的维度，至少记录类型、显示名称、单位、排序规则、空值语义、适用的 templateType/stageType/runPath/scopeType 和目录版本。`dimension_catalog_v1` 固定包含 `stageId`、`stageIndex`、`stageType`、`parameter.<stableInputId>`、`dateScenarioId`、`dateRole`、`initialCapital`、`costScenarioId`、`executionScenarioId`、`fillModel` 和 `resultStatus`。未来增加 Universe、assetId、行业、组件、因子、模型或组合贡献维度时只能扩展目录；EvaluationSpec 不绑定某个 Runner 的临时 JSON key。

### 10.2 指标版本

EvaluationSpec 必须同时冻结 MetricCatalog 和 DimensionCatalog 版本。指标或维度口径升级后：

- 旧 EvaluationSpec 继续按旧版本读取；
- 新 EvaluationSpec 默认使用当前版本；
- 不得用新公式静默改写历史评价结果；
- 原始 Trial 结果不可用时明确失败，不从其他字段猜测。

## 十一、EvaluationSpec 与结果自定义

### 11.1 可自定义范围

用户可以在实验完成后定义：

- 展示哪些基础或派生指标；
- 按 Stage、实验对象、规范化维度赋值、日期角色、资金、成本或执行场景分组；
- 对指标应用过滤条件；
- 使用多级排序和稳定并列规则；
- 对分组应用计数、平均值、中位数、最小值、最大值、标准差和分位数；
- 创建安全派生指标或自定义评分；
- 选择表格、参数曲线、二维热力图和报告章节。

平台不提供一个隐含的默认“最佳策略分数”。用户可以显式保存自己的评分公式，但公式只是该 EvaluationSpec 的评价口径，不改变 Trial 事实，也不自动发布策略。

### 11.2 过滤与排序

示例：

```json
{
  "filters": [
    {"metric": "completedTradeCount", "operator": ">=", "value": 30},
    {"metric": "maxDrawdownRate", "operator": "<=", "value": 0.15}
  ],
  "sort": [
    {"metric": "annualSharpe", "direction": "desc"},
    {"metric": "totalReturn", "direction": "desc"},
    {"metric": "maxDrawdownRate", "direction": "asc"}
  ]
}
```

并列结果最终按 `trialIndex` 升序，保证重复评价结果稳定。

### 11.3 安全公式

安全公式只允许：

- MetricCatalog 中当前可用的数值指标；
- 数值常量；
- `+`、`-`、`*`、`/` 和括号；
- 白名单函数，例如 `abs`、`min`、`max` 和显式空值处理；
- 明确命名的行级派生指标，或分组后已经生成的白名单聚合指标。

禁止属性访问、动态字段、循环、递归、文件、网络、数据库、系统时间和任意代码执行。公式必须限制长度、节点数、计算时间和嵌套深度。

首期实现使用 Python `ast.parse(..., mode="eval")` 但只接受 `Expression`、数值 `Constant`、Metric `Name`、`BinOp(Add/Sub/Mult/Div)`、`UnaryOp(UAdd/USub)` 和对白名单函数 `abs/min/max/coalesce` 的直接 `Call`；任何 Attribute、Subscript、容器、比较、布尔、lambda、推导、关键字参数或未知节点立即拒绝。公式最长 1000 字符、最多 100 个 AST 节点、最大深度 20；值先转换为 `Decimal(str(value))`，计算上下文精度固定为 34，最终按指标声明精度规范化并拒绝非有限结果。不得调用 Python `eval` 执行编译结果。

除零、非有限值或缺失指标返回结构化评价错误，不产生 `NaN`、`Infinity` 或静默零值。

示例：

```text
customScore = 0.5 * annualSharpe
            + 0.3 * totalReturn
            - 0.2 * maxDrawdownRate
```

### 11.4 修改规则

- 新增、复制或修改 EvaluationSpec 不触发回测。
- 相同 EvaluationSpec 内容使用内容摘要去重。
- 每次评价保存 EvaluationSpec 版本、MetricCatalog 版本、参与 TrialExecution/run_id/resultHash 映射、集合摘要、评价流水线版本、输出快照和生成时间。
- Trial 后续完成或被重试后，不静默改变已保存评价；用户可以明确创建“基于最新结果重新评价”的新版本。
- provisional EvaluationRun 默认不能被未来 SelectionPolicy 消费；只有 EvaluationSpec 显式设置 `allowPartial = true`、冻结最小完成比例和各关键维度覆盖阈值后才能形成临时候选，而且临时候选不能解锁最终 `test` Stage。

### 11.5 确定性评价流水线

评价顺序固定为：

1. 根据 EvaluationRun 冻结的 TrialExecution 集合读取 `run_id` 和原始结果；
2. 校验每份规范化结果的 SHA-256，任何缺失或不一致使本次评价失败；
3. 通过冻结版本的 MetricCatalog 生成基础指标行；
4. 计算行级派生指标；
5. 应用行级过滤条件；
6. 按声明维度分组；
7. 依次计算声明的聚合指标；
8. 计算仅引用已生成聚合指标的分组派生公式；
9. 应用多级排序，并以 `stageIndex`、`trialIndex` 作为最终稳定键；
10. 生成结构化输出、内容摘要、图表输入和报告制品。

实现不得交换过滤与聚合顺序，也不得根据页面当前可见列改变参与计算的数据。

### 11.6 空值与统计定义

- 不支持或缺失的基础指标为 `null`；
- 普通算术遇到 `null` 返回 `null`，只有显式 `coalesce` 可以提供替代值；
- 普通过滤条件遇到 `null` 视为不通过，`is_null` 和 `is_not_null` 除外；
- 升序和降序都把 `null` 放在非空值之后；
- 聚合函数忽略 `null`，一组全部为 `null` 时结果为 `null`；
- 标准差使用样本标准差，少于两个有效值时为 `null`；
- 中位数在偶数样本时取中间两个值的算术平均；
- 分位数使用最近秩法，并把具体算法版本写入评价流水线版本；
- 除零、溢出和非有限结果生成结构化错误，不参与后续排序或评分。

这些规则同时适用于页面、导出和报告，禁止三个入口使用不同计算口径。

## 十二、参数平原与稳定性分析

### 12.1 参数平原

参数平原只对有序数值参数提供：

- 单参数曲线；
- 两参数热力图；
- 相邻显式网格点的局部统计；
- 用户选择指标的中位数、最小值、标准差和变化幅度。

“相邻”按用户提供的有序离散值定义，不在未运行的参数之间插值。三维及以上参数必须先固定或分组其他维度，不能把多维结果压成一张误导性热力图。

系统展示稳定区域及证据，不自动宣称某个参数是最优参数。

### 12.2 成本压力

首个版本的成本压力通过显式 Slippage CostScenario 实现，FeeProfile 在整个 Experiment 中固定。每个场景仍是完整独立 Trial，不允许在回测完成后简单从净收益中二次扣减来伪造成本场景。佣金压力只有在后续建立受控 FeeProfile 覆盖契约后才能加入，不能用展示层重算代替真实回测。

评价可以展示正常成本与压力成本下的指标差、相对退化和是否越过用户阈值。

### 12.3 时间稳定性

首期不自动划分训练集、验证集或最终测试集。用户可以自定义一个或多个固定 DateScenario；每个场景至少包含稳定场景 ID、名称、起止时间和顺序，并与其行情查询口径、复权口径及可用的数据版本摘要一起进入 ExperimentRevision。确认创建后，这些定义不可原地修改，全部 Trial 必须引用冻结场景，不得在物化时改用新的日期范围或“最新”数据版本。

DateScenario 可以使用以下用途标签帮助展示和分组：

- `development`：用于探索和初始参数比较；
- `validation`：用于验证开发区间得到的候选；
- `reference`：用户自定义的对照或样本外参考区间。

同一验证组内的日期范围必须顺序明确且不得重叠。用途标签只描述用户的研究意图，不自动证明数据隔离或结果无偏；首期不得把运行过全部参数组合的 `reference` 宣称为最终测试集。

首个版本允许对全部显式参数和值运行所有已确认并冻结的 DateScenario，但不会自动根据结果追加搜索。后续可以在保持“一个 Trial 对应一个普通单次回测任务”的前提下，通过新的 ExperimentStage 增加“先冻结候选、再解锁最终 test 数据集”的多阶段验证；只有未参与候选选择、且在 SelectionArtifact 冻结后才解锁的数据集才能标记为真正的 `test`。该能力不作为首个版本上线阻塞项。

## 十三、结果页面与报告

### 13.1 实验列表

实验列表至少展示：

- 实验名称、实验对象类型、名称和固定版本；
- `runPath`、`scopeType`、周期、撮合模型和简要资产范围；首期资产范围展示单一标的；
- Stage 数量、当前 Stage 和阶段进度；
- 已知 Trial 总数或冻结上限，以及成功、失败、取消、排队、运行数量；首期始终展示精确总数；
- 当前聚合状态和进度；
- 创建者、创建时间、开始时间和完成时间；
- 当前资源预算和取消入口。

### 13.2 实验详情

实验详情分为：

1. 定义：实验对象、RunTemplateSnapshot、AssetManifestSnapshot、ExperimentPlan、固定结构、网格、场景、数量、预算和快照摘要；
2. 运行：Stage 依赖与状态、Trial 状态、耗时、错误、重试和单次回测入口；
3. 结果：可配置列、过滤、分组、排序和导出；
4. 分析：参数曲线、热力图、成本压力和时间稳定性；
5. 评价：EvaluationSpec 列表、版本、公式和生成记录。

用户必须能够从任何 Trial 下钻到现有单次回测结果页面。实验页不复制全部交易明细或 K 线图。

### 13.3 报告

报告由 EvaluationSpec 驱动，至少包含：

- 实验对象、RunTemplate、资产版本和 Stage 摘要；
- 固定结构、搜索空间和 Trial 生成来源；
- Trial 完成质量和异常清单；
- 用户选择的指标表；
- 过滤、排序、评分和分组规则；
- 参数敏感性、成本压力和时间稳定性；
- 入选项及其单次回测链接；
- 数据、结果和评价口径版本。

报告不得把自定义评分表述为系统投资建议，也不得省略失败 Trial 后只展示成功结果。

## 十四、数据持久化

实现时通过新的幂等迁移新增持久化结构，不修改已执行迁移，也不在应用启动时执行 DDL。建议的逻辑实体为：

| 实体 | 核心职责 |
| --- | --- |
| `backtest_experiment_preview` | 带 TTL 的权威预览快照、版本摘要和 previewToken；不是服务端草稿 |
| `backtest_experiment` | 稳定实验身份、所有者、名称、当前聚合状态、归档时间、派发阻塞原因和恢复审计摘要 |
| `backtest_experiment_revision` | 不可变 ExperimentSpec、RunTemplateSnapshot、AssetManifestSnapshot 摘要、预算和 FailurePolicy |
| `backtest_experiment_stage` | StageSpec、依赖、生成器身份、输入/输出摘要、Trial 计数和阶段状态；首期每个修订只有一个 `finite_grid_v1` Stage |
| `backtest_experiment_trial` | 所属 stage_id、TrialSpec、生成来源、指纹、索引、物化状态、汇总状态和选定执行 |
| `backtest_experiment_trial_execution` | 每次人工可见执行与 run_id 的一对多关联 |
| `backtest_experiment_dispatch_outbox` | 当前队列或未来外部 Dispatcher 的稳定投递意图、幂等键与租约状态 |
| `backtest_experiment_user_quota` | 单用户计划额度和实验在途 permit 的事务性缓存，可从任务真源重建 |
| `backtest_experiment_asset_hold` | 冻结资产的保留关系，防止普通生命周期清理仍被 Revision 引用的版本 |
| `backtest_internal_idempotency` | 内部写操作的 owner、operation、key、requestHash 和最小响应 |
| `backtest_evaluation` | 稳定评价身份、所有者和实验关联 |
| `backtest_evaluation_revision` | 不可变 EvaluationSpec 和指标目录版本 |
| `backtest_evaluation_run` | 冻结的运行集合、结果哈希、流水线版本、完整性状态和评价输出 |
| `backtest_evaluation_export` | 异步评价表格/报告导出、租约、文件 hash、TTL 与下载审计 |

字段、约束、索引和 RLS 的实施真源见第 24 章；本节只描述领域职责。

设计要求：

- 每个 Experiment 和 Evaluation 都受当前用户所有权与 RLS 约束；
- 同一实验修订和 Stage 下 `(stage_id, trial_index)` 与 `(stage_id, trialFingerprint)` 分别唯一；
- TrialExecution 的 `run_id` 指向现有 `backtest_run`，不复制原始回测结果，并使用 `ON DELETE RESTRICT` 或等价约束阻止关联运行被普通物理删除；
- RunTemplateSnapshot、StageSpec、TrialSpec、ExperimentSpec 和 EvaluationSpec 使用版本化 JSON 保存，同时把高频查询字段规范化为列；
- Experiment 聚合计数可以缓存，但必须能够从 Trial 真源重建；
- 删除或归档策略不能破坏已存在实验及其冻结版本引用；
- 历史 ExperimentSpec 不因系统默认限额变化而被改写；
- 通用表不得要求 `configId`、`scriptId` 或标量 `symbol` 非空；这些首期字段保存在 `legacy_single_strategy_v1` RunTemplateSnapshot 中，高频查询可以建立可空投影列；
- 新增 RunTemplateResolver、TrialGenerator、TrialCompiler、TrialDispatcher 或 ResultMetricAdapter 时使用类型和版本注册，不为每类投研资产复制一组 Experiment/Trial 表。

### 14.1 归档、保留与物理清理

Experiment 一旦引用普通 `backtest_run`，该运行即进入实验保留关系。现有单次任务删除接口在发现保留关系时必须返回稳定 `409 experiment_run_retained`，不能级联删除 TrialExecution、把 `run_id` 置空或把数据库约束异常暴露为 500；不属于任何 Experiment 的历史运行保持既有删除语义。

首期用户界面的“删除实验”按归档实现：停止出现在默认列表，但保留 ExperimentRevision、Stage、Trial、TrialExecution、Evaluation、`backtest_run` 和审计信息。Experiment、Evaluation 及其子对象不得通过普通接口逐项物理删除。

需要释放存储时必须走独立、授权且可审计的“清除实验”流程。该流程在执行前解析并冻结完整依赖图，再次校验所有权、终态、保留期和法律/审计约束；随后先删除评价/导出制品并清空 Trial 的 execution 指针，再删除 TrialExecution 与实验专属 `backtest_run`，最后删除 Trial、Stage、Revision 和 Experiment。共享或仍被其他对象引用的运行不得删除。流程在同一受控事务或可恢复清理作业中执行，保存申请人、范围、原因、数量、开始/完成时间和失败位置，不复用普通单次任务删除接口。

账号删除同样必须检查尚未物化、尚无 `backtest_run` 的 Experiment，以及已有运行的保留关系；存在未清理实验时拒绝账号物理删除或显式调用同一清除流程，不能只按 `backtest_run` 是否存在判断。

## 十五、接口边界

首期提供网页内部接口，不同时扩大开放 API。首期能力包括：

| 接口能力 | 作用 |
| --- | --- |
| 读取可实验对象 | 按 `subjectType + subjectId + subjectVersion` 返回 RunTemplateSnapshot 摘要、AssetManifestSnapshot 摘要、TunableInputCatalog 和运行能力；首期只启用现有单标策略 |
| 预览实验 | 解析 subjectRef，规范化 ExperimentPlan，调用 Stage 生成器并返回数量、资源估算、版本绑定、`specHash` 与短期 `previewToken`；只保存有 TTL 的预览快照，不持久化 Experiment 或任务 |
| 创建实验 | 通过完整 API 请求携带 ExperimentSpec、`previewToken`、`specHash` 和 `Idempotency-Key`，再次校验并冻结后立即进入 `preparing` |
| 按创建请求键查询实验 | 创建响应超时或丢失时找回同一 Experiment |
| 创建新修订 | 仅当当前修订已经终结时，为同一 Experiment 冻结新的 ExperimentSpec；存在活动修订时返回稳定冲突，要求等待终结或复制新 Experiment |
| 查询实验列表与详情 | 返回聚合状态、Trial 分页和错误摘要 |
| 取消实验 | 停止物化并级联请求取消未终结 Trial |
| 归档实验 | 从默认列表隐藏已终结实验，但保留全部修订、Trial、评价、运行结果和审计关系 |
| 清除实验 | 独立授权的受审计清理作业；校验终态、保留期和依赖后清理实验专属数据，不复用普通运行删除接口 |
| 恢复受阻实验 | 校验阻塞原因与权限后继续原 ExperimentRevision |
| 重试失败项 | 为明确选择的失败 Trial 创建新执行关联 |
| 创建或复制 EvaluationSpec | 保存自定义评价规则 |
| 运行评价 | 对冻结结果集合执行安全分析 |
| 导出评价结果 | 导出表格和报告，不导出无权访问内容 |

所有写接口都必须有幂等语义。创建实验的幂等摘要至少包含用户、ExperimentSpec 规范化内容和请求键；相同键用于不同内容时返回冲突。

subject、Stage、Trial 和评价接口使用带 schema 版本的判别联合契约。新增 `factor_system`、`strategy_yaml` 或新 Stage 类型时扩展已声明的类型注册表和能力发现结果，不能增加一套平行的“投研实验 API”。

后续开放 API 若需要接入，应新增独立的实验 Scope 和稳定 snake_case 契约，不能直接暴露内部表结构，也不能默认授予现有 API Key。

## 十六、权限、安全与审计

1. 用户只能选择自己可运行的实验对象和精确版本；未来 RunTemplateResolver 解析股票池、策略 YAML、因子、组件、Feature Store 和模型时必须携带同一组织、用户与授权上下文。
2. Trial 创建和结果读取分别执行所有权校验，不能因父实验可见而绕过子任务权限。
3. RunTemplateSnapshot、AssetManifestSnapshot、ExperimentSpec、TrialSpec、EvaluationSpec 和报告不得保存账户口令、令牌或其他敏感信息；页面、导出和普通 API 不返回私有 YAML 原文、制品地址、组件源码或内部路径。
4. 评价公式使用受限解析器，不使用 `eval`、`exec` 或数据库动态 SQL。
5. 所有实验创建、取消、重试、评价保存和导出操作记录安全审计摘要。
6. 错误聚合不得把策略源码、内部路径、数据库语句或其他用户资源泄露到页面。
7. 大量 Trial 的创建、查询和导出必须分页、限流并设置响应大小上限。
8. 实验自动化只允许 `mode = backtest`，不得携带实盘账户或实盘执行授权。

## 十七、兼容与历史语义

- 现有单次回测接口和页面继续可独立使用。
- 不属于实验的历史 `backtest_run` 不需要补写 Experiment 关系。
- Trial 结果继续使用其保存时的结果 schema 和运行快照读取。
- Evaluation 通过 MetricCatalog 适配不同历史结果版本；不支持的指标明确为空。
- 单次回测结果修复或 schema 升级不得静默重算既有评价版本。
- ExperimentSpec 新版本只能影响新修订，不能给旧实验补充新的默认维度。
- 标准 Bar 与 L2 的既有成交、结算、费用和取消语义保持不变。
- `legacy_single_strategy_v1`、`finite_grid_v1` 及其 Trial 指纹算法永久按保存版本读取；未来新增对象、Stage 或执行后端不能重新解释旧实验。
- 50 号方案的单次 factor_system/strategy、single/portfolio 任务先独立通过自身契约和正确性门禁，再由新的 RunTemplateResolver 与 TrialCompiler 接入实验层；不得由实验层直接调用 UniverseProvider、FactorDataProvider 或 ComponentResolver 绕过单次任务准备。

## 十八、可观测性与容量保护

### 18.1 计算口径

本方案中的“在途 Trial”固定指已经原子物化、且当前 TrialExecution 处于 `queued`、`running` 或 `cancelling`。处于 Stage `preparing` 的计划、尚未物化的 Trial、已经终结的执行和单纯查看评价的请求不计入在途数量；其中只有现有调度定义中的 `running` 或 `cancelling` 回测占用全局执行槽位。

容量至少包含四层独立限制：单实验在途上限、单用户全部实验合计在途上限、单用户未完成实验 Trial 计划总量上限和系统全局硬上限。创建 Experiment 时必须在用户级锁内校验并登记计划额度；物化时必须在同一事务内占用用户与实验 permit。普通手工任务使用独立保留额度，不被实验 permit 吞并。

ExperimentRevision 冻结创建时适用的预算版本和数值。系统硬上限可以因运维降级而收紧；物化前若当前硬上限低于实验预算，协调器停止补充任务，并写入独立的 `capacity_blocked` 原因，不删除 Trial、不静默缩小网格，也不自动判定失败。主状态仍按 8.3 节派生：已有 TrialExecution 正在运行时保持 `running`，正在取消时保持 `cancelling`；只有没有运行中执行且仍有待物化 Trial 时才显示 `queued + capacity_blocked`。限制恢复后可以继续物化。

资源等级由版本化估算器生成：

- 标准 Bar 至少使用正式区间、预热区间、timeframe、预计 Bar 数和策略运行能力计算工作量；
- L2 至少使用区间、覆盖元数据、预计行情量、执行算法和参数计算工作量；
- 估算值只用于预算和保护，不替代 Worker 实际数据加载；
- 估算器版本和输入摘要进入 ExperimentSpec；
- 无法得到可靠估算时使用保守等级或拒绝创建，不能按最低等级放行。

### 18.2 指标

至少记录以下实验级指标：

- 创建和预览次数；
- 展开 Trial 数及被拒绝数量；
- 待物化、已排队、运行、成功、失败和取消数量；
- 从创建到首个 Trial 开始、全部完成的耗时；
- 每种 fillModel 的在途数量与吞吐；
- 每种 templateType、stageType、runPath、scopeType 和 TrialDispatcher 的数量、失败率与耗时；
- 单个实验和单用户的资源预算使用量；
- Trial 失败分类分布；
- 熔断次数、错误指纹、阻塞时长、自动/人工恢复次数；
- 评价耗时、公式错误和导出大小。

Experiment 不新增执行槽位。服务器生产并发仍由 37 号方案控制；容量数值仍由 49 号方案认证。批量实验上线前必须验证：

- 一个大实验不会让其他用户普通任务长期饥饿；
- 同一用户创建多个 Experiment 不会突破用户聚合在途上限，且普通手工任务在保留额度和最大等待门禁下不会被本用户实验长期压后；
- 协调器重复启动不会重复创建 Trial；
- 大量已完成 Trial 的汇总查询不会拖慢任务领取和历史列表；
- L2 实验不能突破已认证的数据源、内存和 Runner 容量。

未来接入 50 号方案后还必须按 RunTemplate 类型分别认证单成员因子系统、多标的组合、组件冷启动、Feature Store 读取和制品缓存负载。一个组合 Trial 始终是一个共享资金的普通回测任务，不能为提升实验吞吐而按股票拆成多个 TrialExecution。

### 18.3 上线前置门禁

标准 Bar 实验向普通用户开放前必须同时满足：

1. 37 号统一调度方案已经在目标服务器完成发布验收；
2. 49 号性能方案已经为代表性标准 Bar 实验负载冻结 Trial 上限、在途上限和生产安全并发；
3. 冻结版本提交通道通过策略更新、重新发布、归档和权限变化测试；
4. 普通单次任务与实验任务混合时的用户公平、取消和队列回落验证通过。

L2 实验还必须完成独立 L2 资源估算和容量认证。在这些门禁完成前，只能进行本地或隔离环境验证，不得把代码完成描述为生产可用。

## 十九、实施里程碑

### 19.1 里程碑 A：标准 Bar 有限网格闭环

1. 冻结 RunTemplateSnapshot、DatasetSnapshot、TunableInputCatalog、ExperimentSpec、ExperimentStage、TrialSpec、指纹和 `finite_grid_v1` 展开顺序。
2. 实现 `legacy_single_strategy_v1` RunTemplateResolver、QMT DatasetSnapshotResolver、TrialCompiler、ResourceEstimator、TrialDispatcher 和 ResultMetricAdapter，并验证受信任的冻结版本提交通道。
3. 新增 Experiment、ExperimentStage、Trial、TrialExecution 与评价持久化迁移；通用表不把 `configId`、`scriptId` 或标量 `symbol` 作为必填身份字段。
4. 实现“自动化回测”一级入口、策略页上下文入口和四步全页面创建器，前端只作为内部 API 客户端。
5. 实现可脱离页面状态完成的 API 创建链路，包括 previewToken、服务端权威预览、预览失效、数量校验、预算、短事务进入 `preparing`、确定性分块生成和幂等找回。
6. 实现版本隔离的浏览器本地草稿，恢复草稿后强制重新读取能力并预览。
7. 实现单实验与单用户聚合有限在途窗口、普通任务保底、实验 round-robin、原子 permit、TrialExecution 和普通任务同事务创建。
8. 实现失败指纹、FailurePolicy、实验熔断、恢复和协调器重启续跑。
9. 实现实验列表、详情、准备/执行进度、下钻、批量取消、归档和实验运行保留保护。
10. 跑通标准 Bar 已声明参数、用户自定义固定 DateScenario、资金和滑点场景，并冻结真实生效的数据查询口径、来源身份与 FeeProfile；运行后校验实际数据 hash。
11. 为 Cookie 写接口补齐会话绑定 CSRF Token、Origin 校验、requestId 和当前页面错误反馈，并回归全部既有写操作。

完成标志：用户能够从自动化回测列表或已保存策略进入同一个创建器，预览单一 `finite_grid_v1` Stage 后通过“确认创建并开始”立即启动实验；所有 TrialExecution 通过现有链路运行，策略在实验期间更新不会改变后续 Trial，状态和结果可完整追溯；核心编排不直接依赖现有策略页面、脚本字段或特定 Runner。

### 19.2 里程碑 B：可自定义结果评价

1. 建设版本化 MetricCatalog。
2. 实现结果矩阵、过滤、分组、多级排序和稳定并列规则。
3. 实现 EvaluationSpec 版本和安全公式。
4. 实现参数曲线、二维热力图、成本压力和时间稳定性展示。
5. 实现评价报告和导出。
6. 实现 provisional 部分评价及完成度、缺失项和非最终标识。

完成标志：同一批 Trial 可以保存和重复应用多套评价口径，不重新运行回测，也不改变原始结果。

### 19.3 里程碑 C：L2 接入与容量验收

1. 复用相同 Experiment/Trial 契约接入 L2。
2. 增加 L2 资源估算、独立预算和更严格在途限制。
3. 覆盖 immediate、合法 TWAP 场景、取消、失败和结果适配。
4. 按 49 号方案完成代表性混合负载与容量验证。

完成标志：L2 实验不会改变现有执行语义或突破生产容量，标准 Bar 普通任务、L2 普通任务和两类实验仍符合用户公平规则。

### 19.4 后续增强

以下增强不阻塞本方案完成：

- 开放 API 的实验管理与评价接口；
- 候选冻结后再运行最终 test 数据集的多阶段验证；
- 更多安全聚合函数与报告模板；
- 当现有队列有明确吞吐瓶颈时评估 BatchExecutor 或 Ray。

50 号方案达到单次回测里程碑后，按以下顺序扩展本实验层：

1. 为 `factor_system` 和 `strategy_yaml` 增加 RunTemplateResolver，把 UniverseSnapshot、策略 YAML、组件 Wheel、quantflow-contract、Feature Store、模型和执行契约冻结到 AssetManifestSnapshot；
2. 为 single/portfolio 单次提交增加 TrialCompiler 和 ResourceEstimator，但仍由 50 号方案的单次任务准备、组合内核、撮合和账本完成执行；
3. 为组合结果和归因结果增加 ResultMetricAdapter，不改变 EvaluationSpec 与 EvaluationRun 的冻结语义；
4. 增加样本外、多股票池/多周期、leave-one-out、贡献剔除复跑等版本化 ExperimentStage 和 TrialGenerator；
5. 增加 SelectionPolicy 与 SelectionArtifact，让自动评分淘汰通过不可变制品驱动下游 Stage；
6. 只有容量证据证明现有队列不足时替换或扩展 TrialDispatcher，由 BatchExecutor 选择是否使用 Ray。

多标的共享资金实验、投研因子系统自动化和组合归因的业务语义继续由 50 号方案及其后续方案承接，但接入方式是增加 Resolver、Compiler、Generator、Dispatcher 和 ResultMetricAdapter 实现，不重写 Experiment、ExperimentStage、Trial、TrialExecution、EvaluationSpec 或 EvaluationRun。

## 二十、验收标准

### 20.1 前端创建器

1. 用户可以从“自动化回测”列表或一份已保存策略进入同一个全页面创建器，策略入口能够正确绑定固定版本。
2. 存在未保存的策略或结构字段修改时不能从策略页创建实验；创建器中的结构字段始终只读。
3. 前端只能为已声明参数配置有限候选值，日期以完整原子场景录入，首期费用配置只读。
4. 任一 ExperimentSpec 输入发生变化后，旧预览立即失效，未重新预览前不能确认创建。
5. 完整创建流程可以仅通过内部 API 完成，不依赖浏览器页面状态；前端或其他内部调用方均不能提交可信 Trial 数量或完整 Trial 数组，服务端返回的规范化数量和资源估算是最终口径。
6. 创建请求超时后使用原幂等键能够找回或返回同一个 Experiment，不会因重复点击产生两个实验。
7. 本地草稿恢复后必须重新读取实验对象和运行能力并重新预览；成功创建只清除当前 subject 版本的对应草稿。
8. 用户点击“确认创建并开始”后实验立即进入 `preparing`，完成确定性分块生成后自动进入排队和有限窗口物化；关闭浏览器不会暂停实验。

### 20.2 展开与快照

9. 相同 ExperimentSpec 重复预览时得到相同 Trial 数、顺序和指纹。
10. 重复参数值规范化去重，并明确展示数量变化。
11. 未声明参数、类型错误、非有限数字和系统保留字段在创建前拒绝。
12. 非法日期、成本或执行场景不会产生部分 Experiment。
13. Trial 结构字段与冻结策略版本一致，不能覆盖 symbol、timeframe、strategyCategory 或 fillModel。
14. 每个 Trial 快照能够区分保存默认参数、本次覆盖参数和最终有效参数。
15. 创建 Experiment 后更新、重新发布、重命名或归档原策略，尚未物化 Trial 仍使用冻结版本。
16. Experiment 冻结真实 FeeProfile；不同 Slippage CostScenario 生效，但请求中伪造的 commissionRate 不会形成虚假费率网格。
17. 所有权撤销、管理员安全禁用或运行能力失效后停止物化新 Trial，并保留已有运行和稳定原因。

### 20.3 执行与调度

18. 首期每个 Trial 的首次执行只创建一个普通单标的回测任务；相同输入的结果与手工单次回测一致。
19. 基础设施自动重试保留在同一个 `backtest_run`，人工重试创建新的 TrialExecution，且同一 Trial 不会同时运行两个执行。
20. Experiment 不占用执行槽位，只有现有调度定义中的 running/cancelling 子任务占用槽位。
21. 大实验使用有限在途窗口，不一次灌满普通任务队列；同一用户的全部 Experiment 共享聚合在途上限。
22. 多用户同时提交普通任务和实验时，现有公平调度规则继续生效；同一用户内部普通任务获得保留额度，多个实验按稳定 round-robin 补充。
23. 协调器崩溃、重启或重复扫描不会重复创建相同 Trial 或 TrialExecution。
24. 一个 Trial 失败不会中止其他 Trial，Experiment 最终状态正确反映部分成功。
25. 批量取消停止新 Trial 物化，并使已创建子任务按现有取消语义收敛。
26. 取消与完成竞争时保留真实终态，迟到结果不能覆盖已接受的取消。
27. 运行中收紧系统容量时，实验以 `capacity_blocked` 原因暂停补充，恢复后继续且不丢失网格点。
28. 协调器、backend 或 Runner 重启后，已成功 Trial 不重跑，未完成 Trial 从数据库状态继续。
29. 单个 TrialExecution 中断时从该 Trial 开头重新执行，不影响其他已完成 Trial。
30. 三个不同 TrialExecution 连续产生同一错误指纹时触发 `execution_blocked`，停止继续物化。
31. 解除熔断只能继续原 ExperimentRevision；需要改变冻结输入时必须创建新修订。
32. EvaluationRun 或报告失败只重试评价链路，不创建新的回测任务。

### 20.4 结果评价

33. 原始 TrialExecution 结果在创建、修改或删除 EvaluationSpec 后保持不变。
34. EvaluationRun 冻结每个 Trial 使用的 trialExecutionId、run_id 和 resultHash；任一哈希不一致时明确失败。
35. 同一 EvaluationSpec、同一冻结执行集合和同一流水线版本重复执行得到相同输出和顺序。
36. Trial 后续重试完成时，旧 EvaluationRun 和输出快照不被静默改写。
37. 不支持或缺失指标不会被当作 0 参与计算，空值过滤、排序和聚合符合固定规则。
38. 行级公式、过滤、分组、聚合、分组公式和排序严格按冻结流水线执行。
39. 安全公式拒绝任意代码、非法字段、除零和非有限结果。
40. 修改 EvaluationSpec 不创建新的回测任务。
41. 参数平原只使用实际运行的离散网格点，不插值或伪造未执行结果。
42. 报告完整列出失败、取消和缺失结果，不只展示成功 Trial。
43. provisional EvaluationRun 明确展示总数、完成比例、失败/取消/未物化数量及 `isPartial = true`，且不会被标记为最终报告。

### 20.5 兼容与安全

44. 既有单次 Bar/L2 提交、取消、历史读取和公开接口行为不变。
45. 用户不能创建、读取、取消或评价其他用户的实验和 Trial。
46. 归档策略后已有实验仍可按冻结版本读取，但不能绕过安全禁用或所有权撤销继续物化。
47. 评价公式和报告不泄露策略源码、内部路径或其他用户数据。
48. 37 号调度与 49 号容量门禁未完成时，标准 Bar 实验不能对普通用户开放。
49. L2 未通过独立资源估算和容量门禁前不能对普通用户开放实验入口。

### 20.6 面向 50 号方案最终态的演进约束

50. Experiment、ExperimentStage 和 Trial 的通用身份不要求 `configId`、`scriptId` 或标量 `symbol` 非空；首期值通过 `legacy_single_strategy_v1` RunTemplateSnapshot 保存。
51. 首期每个 ExperimentRevision 持久化一个无依赖的 `finite_grid_v1` Stage，所有 Stage 保存 `stageInputFingerprint`，所有 Trial 保存 `stageId`、生成器版本、RunTemplateSnapshot 摘要和生成来源；未来上游 EvaluationRun 或 SelectionArtifact 摘要进入 Stage 与 Trial 指纹。
52. Experiment 核心只读取 TunableInputCatalog，不直接解析 `STRATEGY_PARAMETERS`、策略 YAML、组件 Wheel、因子配置或 UniverseSnapshot。
53. 每个首期 Trial 必须经过 TrialCompiler 和 TrialDispatcher 接口进入现有单次回测链路，协调器不得直接拼接 Runner 私有载荷。
54. ResultMetricAdapter 按冻结的执行路径和结果 schema 生成 MetricCatalog 行；EvaluationSpec 不绑定现有单标结果的私有字段。
55. 添加一个新的 RunTemplateResolver、TrialCompiler、ResourceEstimator 或 ResultMetricAdapter 时，不需要迁移或复制既有 Experiment、Stage、Trial、TrialExecution 和 Evaluation 表。
56. 添加新的 Stage 类型不会改变 `finite_grid_v1` 的展开顺序和历史 Trial 指纹；首期接口对未注册 Stage 明确拒绝。
57. 当前队列与未来 BatchExecutor/Ray 使用相同 TrialExecution、`backtest_run`、取消、幂等、公平和结果契约；切换派发实现不会改变回测语义。
58. 未来 portfolio Trial 始终对应一个共享资金的普通组合回测任务，不会被实验层按股票拆成多个独立 TrialExecution。
59. 50 号方案的本地 Adapter 与投研平台 Adapter 在单次回测层完成契约一致性验证后，实验层只消费同一 RunTemplate 和提交契约，不感知投研平台传输协议或在线状态。

### 20.7 数据集与修订生命周期

60. 用户能够自定义一个或多个固定 DateScenario；创建后其日期、顺序、用途标签、行情查询与复权口径和可用数据版本摘要均被冻结，后续物化不会改用新的范围或“最新”数据版本。
61. 首期 `development`、`validation` 和 `reference` 仅作为展示与分组标签；对全部候选运行过的 `reference` 不会被报告宣称为最终测试集，真正 `test` 只允许由候选冻结后的下游 Stage 解锁。
62. 同一 Experiment 同时最多一个活动修订；当前修订未终结时创建新修订返回稳定冲突，历史修订的 Stage、Trial、执行、评价和终态独立可读且不参与当前状态聚合。

### 20.8 创建恢复、运行保留与调度公平

63. 创建请求事务只持久化 Experiment、Revision、快照、Stage、精确计划数、预算和生成游标，并快速返回 `preparing`；大网格不会因同步插入全部 Trial 形成长事务。
64. 协调器按 `trialIndex` 分块生成 Trial，任一分块提交后重启可以从游标续跑；重复扫描不会违反 `(stage_id, trial_index)` 或 `(stage_id, trialFingerprint)` 唯一约束，全部生成并校验前不会物化执行。
65. 首期服务端状态中不存在 `draft`；未确认内容只保存在浏览器本地，服务端受理后从 `preparing` 开始。
66. Trial 从 `pending` 到 `materialized`、用户与实验 permit、TrialExecution、`backtest_run` 和 Bar/L2 任务在同一事务提交，取消或并发协调器不能生成孤儿运行或重复活动执行。
67. 关联 Experiment 的 `backtest_run` 通过普通删除接口时返回稳定 `409 experiment_run_retained`；归档不会删除结果，只有独立授权且可审计的清除流程能够按完整依赖图物理清理。
68. 同一用户并发创建多个实验时，计划额度校验和登记在用户级锁内串行化；多个协调器并发物化时也不能突破用户聚合或单实验在途上限。
69. 当同一用户同时存在普通任务和多个实验时，普通任务保留额度与最大等待门禁生效，实验在剩余额度内稳定轮转，不会通过多建 Experiment 获得更多全局槽位。

### 20.9 实施级契约

70. 预览返回绑定 owner、Spec、RunTemplate、Dataset、Capability 和 Budget 摘要的短期 `previewToken`；过期、跨用户或任一摘要变化时创建被稳定拒绝。
71. 所有写接口通过统一内部幂等记录区分安全重放、进行中操作和同键不同请求冲突，幂等记录与业务写入同一事务。
72. `canonical_json_v1` 对 Unicode、对象键、Decimal、日期、集合和有序候选具有固定测试向量；任何指纹算法升级使用新版本，不重解释历史 hash。
73. 首期 DatasetSnapshot 冻结 DateScenario 查询定义、来源身份、发布元数据摘要和 freezeLevel；同一 DateScenario 的实际数据 hash 漂移会阻塞评价，不会被报告为同一固定数据集。
74. TrialSpec 冻结 seedBundle、运行时摘要、确定性级别和容差；人工重试和基础设施 Attempt 不改变基础种子。
75. Experiment 全部子表启用并强制 RLS，owner 与 `backtest_run` 使用数据库约束闭合；跨用户 ID、Token、游标、幂等键和导出均不可探测。
76. Trial 物化通过一个 Unit of Work 原子提交 permit、TrialExecution、`backtest_run`、Bar/L2 任务和 dispatch outbox，当前自行开启事务的普通任务创建函数不被直接拼接。
77. Cookie 会话下的全部写接口通过会话绑定 CSRF Token 和 Origin 校验；CORS 与 `SameSite=Lax` 不被当作替代保护。
78. 新实验接口统一返回稳定错误码、requestId 和 retryable，未知异常不泄露源码、SQL、路径或其他用户标识。
79. MetricCatalog 使用 grain、currency、window、annualization、benchmark 和 `comparabilityKey` 建立可比较域；无 Normalizer 的跨域排序和聚合被拒绝。
80. provisional Evaluation 默认不能驱动未来 SelectionArtifact；真正 `test` Stage 只消费候选冻结后的完整合格输出。
81. 评价导出使用异步租约作业，具备幂等、取消、重试、文件 hash、TTL、下载鉴权和公式注入防护。
82. 实验功能默认关闭；开启时必须显式配置容量上限并通过配置关系校验，L2 使用独立开关和预算。
83. 协调器、评价和导出健康项、低基数指标、requestId 关联日志和核心告警均可在目标环境观测。
84. 单元、PostgreSQL 并发/RLS 集成、API、前端、故障注入、正确性、兼容和容量测试按第 29 章执行并记录真实结果。
85. 涉及提交、调度、Runner 或结果的代码完成后，通过远程普通用户最近两条样本按隔离正常链路回归；未执行时明确标记待验证。
86. 发布通过幂等迁移和 `scripts/deploy-server.sh` 同批部署相互依赖服务，实验开关分阶段开放；回滚仅停止新工作，不破坏已持久化 Experiment 和普通运行。
87. 实现同步更新 `docs/玄龄回测系统使用手册.md` 的入口、状态、错误、回测与删除行为，并提供配置、迁移和运维说明。
88. EvaluationSpec 只引用冻结 MetricCatalog 与 DimensionCatalog 的稳定 ID；未知指标、维度和判别联合类型明确拒绝，不读取 Runner 临时 JSON key。
89. 首期 Schema 的 CandidateKey 不包含 DateScenario 或执行重试身份；未来 DAG 激活、fan-in、SelectionArtifact 和失败传播通过版本化 StageTransitionPolicy 扩展，不修改历史 `finite_grid_v1` 语义。

## 二十一、风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 笛卡尔积爆炸 | 服务端预览、硬上限、资源预算、明确拒绝且不静默截断 |
| 大网格创建形成长事务 | 创建请求只冻结计划和游标；协调器确定性分块生成并可断点续跑 |
| 单个用户通过多个实验占满队列 | 单用户聚合在途硬上限、普通任务保留额度、实验 round-robin 和原子 permit |
| 重复创建 Trial 或 TrialExecution | 双唯一约束、活动执行 CAS、任务幂等键和同一 Unit of Work |
| 半途故障导致全量重跑 | 持久化生成游标与 TrialSpec、数据库恢复扫描和已完成结果保留 |
| 系统性错误持续消耗资源 | 版本化 FailurePolicy、错误指纹、实验熔断和受审计恢复 |
| 参数搜索导致过拟合 | 日期角色、样本内外对照、完整搜索空间留痕和风险提示 |
| 用户用自定义评分制造“最佳策略” | 不提供平台默认综合分数，报告明确评价口径与非投资建议 |
| 评价公式执行任意代码 | 安全表达式 AST、白名单指标与函数、资源上限 |
| Bar/L2 指标口径不一致 | 版本化 MetricCatalog、模式能力声明和 unsupportedReason |
| 策略更新导致后续 Trial 漂移 | 受信任的冻结版本提交、快照摘要和跨发布回归 |
| 人工重试覆盖旧执行 | Trial 与 TrialExecution 一对多，旧 run_id 永久保留 |
| 用户删除单次回测导致实验历史不可读 | 实验运行保留关系、普通删除稳定 409、归档和独立受审计清除流程 |
| L2 批量任务压垮数据源 | 独立预算、更小在途窗口、容量认证后启用 |
| 取消父任务但子进程仍运行 | 复用现有真正取消，子任务终结前保持 cancelling |
| 历史评价随重试或新指标变化 | 冻结 trialExecutionId、run_id、resultHash、目录版本和评价输出 |
| Experiment 被当前单标脚本字段绑死 | 使用 RunTemplateSnapshot 和 subject Resolver；通用身份不要求 configId、scriptId 或标量 symbol |
| 把所有未来自动化塞进有限网格生成器 | 首期 `finite_grid_v1` 版本冻结；新流程通过 ExperimentStage 和独立 TrialGenerator 扩展 |
| 更换 BatchExecutor 或引入 Ray 改变任务语义 | TrialDispatcher 只负责派发；TrialExecution、普通回测提交、取消、快照和结果契约保持不变 |
| 为未来扩展过度建设首期业务功能 | 只落地稳定接口、类型字段和单 Stage 持久化；不提前实现因子、组合、多阶段选择或 Ray |

## 二十二、方案边界总结

本方案完成后，系统新增的是实验层的第一个完整实现：`legacy_single_strategy_v1` RunTemplate、一个 `finite_grid_v1` ExperimentStage 和现有队列 TrialDispatcher。它把一份已发布策略版本、一个固定标的、一个固定周期和一种固定撮合模型，在显式有限参数与场景上确定性展开为多个普通回测任务，并对不可变结果使用多套自定义评价规则。

它不改变回测引擎，不形成共享资金组合，不自动发明或修改策略，也不替用户做投资决策。未来增加 50 号方案的因子系统、策略 YAML、多标的组合、多阶段质检或 BatchExecutor/Ray 时，通过新增 RunTemplateResolver、TrialGenerator、TrialCompiler、TrialDispatcher 和 ResultMetricAdapter 接入；ExperimentSpec、ExperimentStage、TrialSpec、TrialExecution、EvaluationSpec 和 EvaluationRun 的核心职责保持不变。

## 二十三、实施级 Module 与内部接口

### 23.1 Module、Interface 与 Seam

实现必须把复杂规则收敛在少量深 Module 内，路由、页面和 Runner 不能分别复制规范化、权限、状态或恢复判断。首期外部 Interface 固定为：

| Module | Interface | 隐藏的实现复杂度 |
| --- | --- | --- |
| `ExperimentApplication` | `resolveSubject`、`preview`、`create`、`createRevision`、`command`、`query` | 权限、快照、规范化、预览失效、幂等、配额和状态机 |
| `ExperimentCoordinator` | `runGenerationCycle`、`runDispatchCycle`、`runReconcileCycle` | 分块游标、租约、锁顺序、permit、熔断、取消和恢复 |
| `TrialExecutionUnitOfWork` | `materialize(trialId, dispatchAdapterType)` | Trial CAS、TrialExecution、`backtest_run`、任务、dispatch outbox 和额度原子提交 |
| `EvaluationApplication` | `saveSpec`、`run`、`export`、`query` | 结果集合冻结、指标适配、可比较域、安全公式、部分评价和制品 |

稳定 Seam 与首期、未来 Adapter 的关系为：

| Seam | 首期 Adapter | 后续 Adapter |
| --- | --- | --- |
| RunTemplateResolver | `legacy_single_strategy_v1` | `factor_system`、`strategy_yaml` |
| DatasetSnapshotResolver | 当前 QMT Bar/L2 数据源快照 | Feature Store、投研平台数据资产快照 |
| TrialGenerator | `finite_grid_v1` | 验证、消融、股票池/周期矩阵、贡献剔除复跑 |
| TrialCompiler | 当前 `BacktestRunRequest` | single/portfolio × factor_system/strategy 提交契约 |
| TrialDispatcher | PostgreSQL Bar/L2 任务队列 | BatchExecutor；必要时其内部使用 Ray |
| ResultMetricAdapter | 当前 Bar/L2 结果 | 组合、归因、因子与模型结果 |

路由只做身份取得、协议解析和结果映射；前端只调用 `ExperimentApplication`；协调器只能通过上述 Interface 推进状态。禁止页面直接计算可信 Trial 数、路由直接写实验表、协调器直接解析脚本，或 Evaluation 直接读取 Runner 私有 JSON 路径。

### 23.2 内部接口路径

首期内部接口使用现有 `/api` Cookie 会话，字段保持 camelCase。分页游标是不透明字符串，时间使用带时区 RFC 3339，金额、费率和进入身份摘要的小数使用十进制定点字符串。

| 方法与路径 | 作用 | 幂等要求 |
| --- | --- | --- |
| `GET /api/backtest/experiment-subjects/{subjectType}/{subjectId}/versions/{subjectVersion}` | 读取可实验对象、快照摘要和 TunableInputCatalog | 只读 |
| `POST /api/backtest/experiments/preview` | 权威规范化、数量和资源预览，生成短期 `previewToken` | 相同输入返回相同 `specHash`，Token 可以不同 |
| `POST /api/backtest/experiments` | 创建 Experiment、首个 Revision 和 Stage | 必须携带 `Idempotency-Key` |
| `GET /api/backtest/experiments/by-idempotency-key/{key}` | 创建响应丢失后找回当前用户的创建结果 | 只读且不可跨用户枚举 |
| `GET /api/backtest/experiments` | 游标分页查询实验 | 只读 |
| `GET /api/backtest/experiments/{experimentId}` | 返回定义、当前修订、Stage 和聚合快照 | 只读，支持 `ETag` |
| `GET /api/backtest/experiments/{experimentId}/revisions` | 分页读取历史修订 | 只读 |
| `GET /api/backtest/experiments/{experimentId}/trials` | 按 revision、stage、状态和维度筛选 Trial | 只读游标分页 |
| `POST /api/backtest/experiments/{experimentId}/revisions` | 当前修订终态后创建新修订 | 必须携带 `Idempotency-Key` |
| `POST /api/backtest/experiments/{experimentId}/cancel` | 请求取消当前活动修订 | 必须携带 `Idempotency-Key`，重复取消返回当前状态 |
| `POST /api/backtest/experiments/{experimentId}/resume` | 解除可恢复阻塞并继续原修订 | 必须携带 `Idempotency-Key` |
| `POST /api/backtest/experiments/{experimentId}/retry-failed` | 为冻结选择集创建新的 TrialExecution | 必须携带选择摘要和 `Idempotency-Key` |
| `POST /api/backtest/experiments/{experimentId}/archive` | 归档终态实验 | 必须携带 `Idempotency-Key` |
| `POST /api/backtest/experiments/{experimentId}/purge` | 创建受审计清理作业 | 首期仅管理员；必须携带 `Idempotency-Key` |
| `POST /api/backtest/experiments/{experimentId}/evaluations` | 保存 EvaluationSpec | 必须携带 `Idempotency-Key` |
| `POST /api/backtest/evaluations/{evaluationId}/runs` | 冻结结果集合并运行评价 | 必须携带 `Idempotency-Key` |
| `POST /api/backtest/evaluation-runs/{evaluationRunId}/exports` | 创建异步报告/表格导出 | 必须携带 `Idempotency-Key` |

```json
    "planVersion": "experiment_plan_v1",
    "stages": [
      {
        "stageType": "finite_grid_v1",
        "generatorVersion": "1",

          {
            "inputId": "稳定参数 ID",

          {
```

```json
    "allowed": true,

    "blockingReasons": []
  },
  "examples": []
}
```

```json

```

### 23.4 预览快照与写操作幂等

`previewToken` 对应 `backtest_experiment_preview` 中一条带 TTL 的服务端快照，至少绑定 owner、规范化 Spec、`specHash`、RunTemplate/Dataset/Capability/Budget 摘要、权威 Trial 数和过期时间。默认 TTL 为 15 分钟；创建时重新检查当前权限、安全禁用和硬上限。预览记录过期后返回 `410 experiment.preview_expired`，版本或能力变化返回 `409 experiment.preview_stale`。过期预览由后台清理，不创建 Experiment、Trial 或运行任务。

所有写操作统一使用 `backtest_internal_idempotency`，唯一键为 `(owner_user_id, operation_type, idempotency_key)`，保存 requestHash、资源类型和 ID、完成状态、HTTP 状态及最小响应。规则固定为：

1. 同一键、同一 operationType、同一 requestHash 返回首次结果；
2. 同一键对应不同 requestHash 返回 `409 idempotency.conflict`；
3. 幂等记录与业务写入位于同一事务；
4. 并发同键请求先在 owner + operation + key 作用域串行化；首个事务提交后，后续请求返回同一资源。评价、导出或 purge 等异步命令在首个短事务中创建操作资源并返回 HTTP 202，重放返回同一操作资源，不并发执行第二次；
5. 响应只保存找回所需字段，不保存策略源码、完整快照或导出内容；
6. 前端全部通过 `createBrowserUuid()` 生成键，网络结果不确定时复用原键，用户形成新操作意图时才生成新键。

### 23.5 稳定错误契约

新实验接口统一返回：

```json
{
  "error": {
    "code": "experiment.preview_stale",
    "message": "预览依据已经变化，请重新预览",
    "retryable": false,
    "requestId": "req_xxx",
    "details": {}
  }
}
```

稳定错误至少包含：

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `experiment.command_invalid` | 状态不允许该命令 |
| 403 | `auth.csrf_invalid` | CSRF Token 或 Origin 校验失败 |
| 403 | `experiment.forbidden` | 对象、实验或底层资产无权限 |
| 404 | `experiment.not_found` | 当前用户不可见或不存在 |
| 409 | `idempotency.conflict` | 同一幂等键用于不同请求 |
| 409 | `experiment.preview_stale` | Spec、资产、数据、预算或能力摘要变化 |
| 409 | `experiment.active_revision_exists` | 当前修订尚未终结 |
| 409 | `experiment.run_retained` | 普通删除命中实验保留运行 |
| 409 | `experiment.selection_changed` | 重试或评价选择集发生变化 |
| 409 | `experiment.state_changed` | 命令依据的 snapshotVersion 已过期 |
| 410 | `experiment.preview_expired` | 预览 Token 过期 |
| 422 | `experiment.validation_failed` | 字段、网格或场景不合法 |
| 422 | `experiment.metric_not_comparable` | 指标不在同一可比较域 |
| 429 | `experiment.plan_limit_exceeded` | 用户未完成计划总量超限 |
| 503 | `experiment.capacity_unavailable` | 当前能力或硬容量暂不可用 |

未知内部异常返回 `experiment.internal_error` 和 requestId；堆栈、SQL、路径、策略代码和其他用户标识只写服务端日志。

### 23.6 前端状态机

创建器状态固定为：

```text
editing
  → previewing
  → preview_ready
  → submitting
  → created
```

任一指纹输入变化使 `preview_ready → editing` 并清除 Token；预览失败回到 `editing` 且保留输入；创建失败回到 `preview_ready` 或因 Token 失效回到 `editing`。`submitting` 期间主按钮禁用，同一次请求只能发送一次。错误显示在当前步骤，不能只写入策略编辑器的通用错误区域。

详情页用单一聚合快照和 `ETag` 轮询：`preparing/running/cancelling` 初始 2 秒，连续无变化后退避到 5 秒和 15 秒，页面隐藏时降频，终态后停止。Trial 明细只使用游标分页，不按每个 Trial 单独轮询。

### 23.8 查询与命令响应

列表统一返回 `{items, nextCursor}`，默认 50、最大 200，禁止 offset 深分页。Cursor 绑定 owner、过滤条件、排序键和最后一项身份，并使用服务端签名防篡改。Experiment 列表项至少包含 experimentId、名称、subject 摘要、currentRevisionId/no、状态/reason、planned/generated/materialized/terminal 计数、更新时间和 archivedAt。详情响应在此基础上增加冻结 Spec 摘要、RunTemplate/Dataset 摘要、Stage 列表、FailurePolicy、预算、审计摘要和 `snapshotVersion`；私有源码与内部路径不返回。

Trial 分页项至少包含 trialId/index、stageId、candidateKey、维度赋值、materialization/summary 状态、selected/active execution 摘要、错误分类和单次回测链接。默认不返回完整 TrialSpec；用户展开单项时再按权限读取脱敏定义。

取消、恢复和归档请求体统一为：

```json
{
  "expectedRevisionId": "UUID",
  "expectedSnapshotVersion": 12,
  "reason": "可选、最多 500 字"
}
```

失败项重试使用冻结选择摘要：

```json
{
  "expectedRevisionId": "UUID",
  "selection": {
    "mode": "trial_ids",
    "trialIds": ["UUID"]
  },
  "expectedSelectedTrialCount": 3,
  "expectedSelectionDigest": "64 位小写 SHA-256",
  "reason": "可选、最多 500 字"
}
```

命令响应统一包含 experimentId、revisionId、status、reason、snapshotVersion、operationId、replayed 和 acceptedAt；同步完成命令返回 200，创建异步操作资源返回 202。`expectedSnapshotVersion` 不一致返回 `409 experiment.state_changed`，页面重新获取详情后再由用户确认，不自动覆盖新状态。

## 二十四、数据库实施设计

### 24.1 迁移与表职责

实现时使用下一个可用的两位递增幂等迁移编号；按当前仓库应从 `043_backtest_experiments.sql` 开始。不得修改已经执行的迁移，也不得在应用启动时执行 DDL。为控制单次迁移风险，可以按“核心实验表、评价与导出、RLS 与索引”拆成连续迁移，但同一发布批次必须完整执行。

核心表及必需字段如下，未列出的展示缓存不得成为状态真源：

| 表 | 必需字段与职责 |
| --- | --- |
| `backtest_experiment_preview` | `token`、owner、request/spec hash、规范化 Spec、RunTemplate/Dataset/Capability/Budget 摘要、权威数量、资源估算、`expires_at` |
| `backtest_experiment` | `id`、owner、名称、说明、`current_revision_id`、当前聚合状态、reason、`archived_at`、行版本、创建/更新时间 |

| `backtest_experiment_trial` | `id`、stage、`trial_index`、TrialSpec、指纹、维度投影、`materialization_status`、`active_execution_id`、`selected_execution_id`、汇总状态和时间 |

| `backtest_evaluation_revision` | EvaluationSpec、schema/MetricCatalog/Normalizer 版本、内容摘要和时间 |
| `backtest_evaluation_run` | revision、冻结执行集合、集合/结果 hash、完整性、流水线版本、状态、输出摘要和时间 |
| `backtest_evaluation_export` | EvaluationRun、格式、列与 locale 快照、状态、租约、进度、storage key、文件 hash、大小、过期时间和错误 |

ExperimentRevision、StageSpec、TrialSpec、EvaluationSpec 等版本化 JSON 使用 `jsonb` 保存；经常用于筛选的 owner、status、type、index、时间、`run_id` 和摘要必须是规范列，不能依赖大 JSON 扫描。

同批迁移还需要对既有表做加法式兼容变更：

- `auth_session` 增加可空 `csrf_token_hash` 和轮换时间；旧会话首次调用 `/api/auth/csrf` 时初始化；
- `backtest_run` 增加默认 `manual` 的 `origin_type`，以及可空 `origin_experiment_id/origin_stage_id`；历史行无需回填；
- `backtest_run` 增加 `UNIQUE (id, owner_user_id)`，供 TrialExecution 建立复合所有权外键；
- `backtest_run.request_key` 继续承载稳定 dispatchKey，普通历史请求键语义不变；
- Bar/L2 候选查询通过 `backtest_run.origin_type/origin_experiment_id` 落实普通任务保底与实验 round-robin，并建立对应部分索引。

### 24.2 主键、唯一约束与外键

数据库必须至少建立以下约束：

1. `UNIQUE (experiment_id, revision_no)`；
2. 每个 Experiment 只能有一个 `terminal_at IS NULL` 的活动 Revision，使用部分唯一索引保证；
3. `UNIQUE (revision_id, stage_index)` 与 `UNIQUE (revision_id, stage_input_fingerprint)`；
4. `UNIQUE (stage_id, trial_index)` 与 `UNIQUE (stage_id, trial_fingerprint)`；
5. `UNIQUE (trial_id, execution_no)`、`UNIQUE (run_id)` 和 `UNIQUE (dispatch_key)`；
6. `backtest_experiment_trial.active_execution_id` 是同一 Trial 唯一活动执行的数据库 CAS 点；只有该列为空才能创建人工重试；
7. `backtest_run` 增加 `UNIQUE (id, owner_user_id)`，TrialExecution 使用 `(run_id, owner_user_id)` 复合外键，保证实验 owner 与运行 owner 一致；
8. `backtest_run.origin_experiment_id/origin_stage_id` 使用可空 `ON DELETE RESTRICT` 外键；普通历史行保持 null；
9. Experiment owner 外键使用 `ON DELETE RESTRICT`；账号删除不能级联抹掉实验；
10. TrialExecution → `backtest_run` 使用 `ON DELETE RESTRICT`；普通删除接口先转换为稳定 409；
11. 内部父子表可以在受控 purge 中按依赖顺序删除，不能依赖宽泛级联绕过保留检查；
12. 所有状态、计数、hash 格式和非负数使用 CHECK 约束；计划数必须满足 `generated + cancelled_before_generation <= planned`。

`backtest_experiment.current_revision_id` 在首个 Revision 创建后于同一事务设置；外键可以使用可延迟约束或先创建 Experiment 再创建 Revision 后回填，但任何提交后的 Experiment 都必须拥有 currentRevision。

### 24.3 索引

至少建立：

- Experiment：`(owner_user_id, archived_at, updated_at DESC, id DESC)`；
- Revision：`(experiment_id, revision_no DESC)` 和活动 Revision 部分唯一索引；
- Stage 生成扫描：`(status, generation_lease_expires_at, created_at, id)`，仅覆盖 `preparing`；
- Trial 物化扫描：`(stage_id, trial_index)`，仅覆盖 `materialization_status = 'pending'`；
- Trial 状态分页：`(stage_id, summary_status, trial_index)`；
- TrialExecution：`(trial_id, execution_no DESC)`、`(run_id)`；
- dispatch outbox：`(status, lease_expires_at, created_at, id)`；
- EvaluationRun：`(evaluation_revision_id, created_at DESC, id DESC)`；
- Export：owner/created、queued、lease 和 expiry 部分索引；
- Idempotency：唯一 `(owner_user_id, operation_type, idempotency_key)` 以及 `expires_at` 清理索引；
- Preview：`expires_at` 清理索引；
- Audit：`(owner_user_id, created_at DESC)` 和 `(experiment_id, created_at DESC)`。

大 JSON 不建立通用 GIN 索引；只有真实查询证据出现后，才为明确投影增加索引。

### 24.4 RLS 与所有权闭合

Experiment、Revision、Stage、Trial、TrialExecution、AssetHold、Evaluation、EvaluationRevision、EvaluationRun、Export、Preview、Idempotency 和 Audit 全部 `ENABLE ROW LEVEL SECURITY` 与 `FORCE ROW LEVEL SECURITY`。直接带 owner 的表按 `owner_user_id = app.current_user_id() OR app.current_is_admin()`；子表通过父表 `EXISTS` 验证相同 owner，并同时配置 `USING` 与 `WITH CHECK`。

协调器使用最小权限数据库角色或受控数据库函数，只能领取和推进必要行；管理员上下文不能成为普通读取接口绕过所有权的捷径。所有插入 TrialExecution 的路径都必须经过复合所有权外键或等价受控函数。

RLS 回归必须覆盖：用户 A 无法通过 ID、runId、分页游标、幂等键、previewToken、导出 ID 或错误详情推断用户 B 的存在。

### 24.5 状态转换约束

应用层状态机与数据库约束同时生效。允许的主转换为：

```text
Experiment/Revision:
preparing → queued → running → completed | partially_completed | failed
preparing | queued | running → cancelling → cancelled | partially_completed
preparing | queued → preparing/queued + blockedReason → 原状态

Stage:
waiting_dependencies → preparing → queued → running
preparing | queued | running → cancelling
任一活动态 → 对应终态

Trial materialization:
pending → materialized
pending → cancelled_before_materialization

Dispatch outbox / Export:
queued → running → succeeded | failed
queued | running → cancelling → cancelled
running 且租约过期 → queued（attempt 未超限）| failed
```

聚合状态从真源派生；缓存计数更新必须与子状态事务同步，并提供后台一致性校验与重建命令。非法状态转换在数据库层拒绝，服务端映射为稳定冲突，不允许静默覆盖。

## 二十五、规范化、快照与确定性

### 25.1 `canonical_json_v1`

所有身份摘要使用同一 Canonicalization Module，不能在前端、路由、协调器和评价中分别实现。`canonical_json_v1` 规则固定为：

1. 先按声明的 schema 做类型转换和默认值填充，再进入规范化；
2. 字符串统一为 Unicode NFC，保留大小写和空白，除非具体字段契约声明 trim；
3. 对象键按 Unicode code point 升序；未知字段在 schema 校验时拒绝；
4. 普通数组保持顺序；声明为集合的字段先按元素规范值去重和排序；用户定义的参数候选顺序属于展开语义，去重后保持首次出现顺序；
5. 整数使用无前导零十进制；Decimal 使用非指数十进制字符串，去除无意义尾零，`-0` 归一为 `0`；
6. 身份字段禁止二进制 float，拒绝 NaN、Infinity 和负 Infinity；TrialCompiler 在单次请求边界按字段精度转换；
7. 日期使用 `YYYY-MM-DD`；时间使用 UTC RFC 3339 微秒精度并以 `Z` 结尾；
8. 布尔和 null 使用标准 JSON；
9. 输出编码为 UTF-8、无 BOM、对象分隔符无额外空白；
10. 摘要统一为小写十六进制 SHA-256，并把 `canonicalizationVersion` 写入被摘要对象。

`1` 与 `1.0` 是否相同由字段 schema 决定：int 字段两者都规范为整数 1；Decimal 字段都规范为同一 Decimal；str 字段的 `"1"` 不与数值相同。

### 25.2 摘要层级

摘要职责固定为：

```text
requestHash
  = hash(完整写请求 + operationType，不含 Idempotency-Key)

specHash
  = hash(影响 Trial 集合或运行语义的规范化 ExperimentSpec)

runTemplateDigest
  = hash(RunTemplateSnapshot + AssetManifestSnapshot + DatasetSnapshot 引用)

stageInputFingerprint
  = hash(StageSpec + generatorType/version + runTemplateDigest + 上游不可变制品摘要)

trialFingerprint
  = hash(stageInputFingerprint + trialIndex 对应的规范化维度赋值
         + TrialCompiler contractVersion + generationProvenance)

resultSetHash
  = hash(按 stageIndex/trialIndex 排序的 trialExecutionId/runId/resultHash 列表)

evaluationOutputHash
  = hash(EvaluationSpec + MetricCatalog/Normalizer/pipelineVersion + resultSetHash + 输出)
```

显示名称、说明、数据库 ID、创建时间和页面列宽不进入 `specHash/trialFingerprint`；owner 和 operationType 进入幂等作用域，但不改变相同业务 Spec 的内容摘要。

### 25.3 固定 DateScenario 与 DatasetSnapshot

首期“固定数据集”指用户自定义 DateScenario 后，系统冻结其查询定义、来源身份和可验证版本，不在每个 Trial 物化时重新选择当前默认来源。每个 DateScenarioSnapshot 至少包含：

- scenarioId、名称、用途标签、startDate、endDate；
- symbol、timeframe、adjustmentMode、正式与预热策略；
- provider、sourceDatabase、sourceTable、sourcePeriod、derivationRuleVersion；
- `qmt_ingest_runs/qmt_universe_snapshot` 等发布元数据的批次引用或创建时摘要；
- sourceFirstDate/sourceLastDate、覆盖摘要和 `datasetSnapshotSchemaVersion`；
- `formalDatePolicy`，以及 Resolver 能从发布元数据可靠确定时的 formalDates 有序摘要；否则由 Worker 从冻结来源解析并写入每次运行快照；
- `datasetFreezeLevel` 和内容摘要。

DatasetSnapshotResolver 必须遵守 ADR 0009：实际 Bar 来源是运行日期事实，不重新接入交易日历。Experiment 不复制原始 Bar；TrialCompiler 把冻结的数据快照引用写入现有 `marketDataSnapshot` 请求结构，Worker 按保存的 provider、物理来源、周期、派生规则和正式日期读取，不根据当前默认值重算。

首期当前 QMT Adapter 使用 `datasetFreezeLevel = query_definition_frozen`：冻结 DateScenario、provider、物理来源、周期、派生规则和覆盖/发布元数据摘要，不承诺为行情原始字节永久保留独立副本，也不在创建请求中扫描完整 Bar。页面和报告必须显示该级别，不能表述为内容寻址的永久数据版本。Worker 继续按 ADR 0009 从冻结来源确定实际 formalDates 和预热日期；每个 Trial 完成后保存完整 `marketDataSnapshot.hash`。同一 DateScenario 出现不一致的数据 hash 时，Stage 标记 `dataset_drift_blocked`，评价和报告不得把结果当成同一固定数据集比较，用户需要在数据稳定后创建新 Revision 重跑。

未来数据源能够按精确批次或内容摘要长期寻址时，新增 `source_version_frozen` Adapter；这只提升 DatasetSnapshotResolver 能力，不改变 Experiment、Stage 或 Trial 契约。若预览时连查询定义、来源身份或发布元数据摘要都无法冻结，仍返回 `dataset.snapshot_unavailable` 并禁止创建。

### 25.4 资产保留

创建 Revision 时按 AssetManifestSnapshot 写入 AssetHold。策略版本、脚本、研究信号附件、FeeProfile 及未来的 YAML、Wheel、Feature Store 和模型制品，在 Revision 未 purge 前不得被普通生命周期物理清除；归档只影响可见性。安全禁用或权限撤销可以阻止后续物化，但不能删除复核历史所需的摘要和已授权保留字节。

物化前再次验证 hold 和安全状态。资产在 hold 期间仍不可用时进入 `asset_unavailable` 阻塞，不改用同名最新版本。只有受审计 purge 成功后释放 hold。

### 25.5 随机性与可复现级别

TrialSpec 保存版本化 `seedBundle`：基础种子由 `SHA-256("trial-seed-v1" + trialFingerprint)` 的前 8 个字节按 big-endian 解释为无符号整数，人工重试复用同一基础种子；基础设施 Attempt 也不得改变种子。运行时按能力把它设置到 Python `random`、NumPy 及明确支持的库，并冻结数值运行时、依赖摘要、线程/并行设置、`deterministicLevel` 和 `tolerancePolicy`。

首期可复现级别为：

- `strict`：相同输入和运行环境要求规范化结果 hash 相同；
- `tolerant`：允许冻结容差内的数值差异，保存差异摘要，不允许跨容差复用结果；
- `input_deterministic_only`：运行时无法控制全部随机源，只保证输入和种子相同；禁止跨实验结果复用，也不得宣称结果可位级复现。

策略使用未声明随机源或系统时间时，预览必须警告，执行结果标记相应级别。任何未来结果复用功能都必须同时校验 Trial 指纹、数据 hash、运行时摘要和可复现级别；首期不做跨 Experiment 结果复用。

### 25.6 指标可比较域

MetricCatalog 的 `comparabilityKey` 至少由以下口径组成：metricVersion、grain、currency、capitalSemantics、windowStart/end 或 windowPolicy、annualizationCalendar、benchmarkId/version、runPath、scopeType 和 normalizerVersion。

EvaluationApplication 在过滤、排序、聚合和公式执行前构造可比较域：

1. 同一域直接比较；
2. 不同域存在已声明 Normalizer 时，先按冻结版本转换并记录来源；
3. 没有 Normalizer 时返回 `experiment.metric_not_comparable`；
4. `null/unsupported` 永不通过隐式转零进入排名；
5. provisional 评价默认不能驱动 SelectionArtifact；
6. 导出和页面复用同一评价输出，不另算一套指标。

### 25.7 后续 CandidateKey 与 StageTransitionPolicy

为避免后续多阶段验证重写 Trial 身份，首期 Schema 预留 `candidateKey` 与 `stageTransitionPolicyVersion`，但 `finite_grid_v1` 不执行自动选择。CandidateKey 标识“同一个待评价候选”，不包含 DateScenario、验证折或执行重试身份；首期由 RunTemplate 摘要加可调参数赋值、资金/成本/执行语义生成。同一 CandidateKey 可以对应多个日期或折叠 Trial，SelectionPolicy 先按 CandidateKey 聚合，再形成 SelectionArtifact。

未来 SelectionPolicy 必须冻结：输入 EvaluationRun、候选聚合方式、缺失/失败处理、最低覆盖、稳定并列、配额和输出顺序。SelectionArtifact 保存入选 CandidateKey、证据、策略版本和内容摘要，不保存可被后续修改的查询。

ExperimentPlan 在创建 Revision 时验证 DAG 无环。下游 Stage 只有全部依赖终态、所需 EvaluationRun/SelectionArtifact 已冻结且 StageTransitionPolicy 门禁通过后，才能以 CAS 从 `waiting_dependencies` 激活一次；fan-in 缺少任一输入时不得部分生成。上游之后的重试或新 EvaluationRun 不改写已激活下游 Stage，只能创建新 Revision 或显式的新 Stage 实例。取消、失败和阻塞如何向下游传播必须由版本化 StageTransitionPolicy 决定，不能由协调器临时推断。

## 二十六、协调器事务与恢复算法

### 26.1 创建事务

创建流程的数据库伪代码固定为：

```text
BEGIN
  advisory_lock(ownerId, operationType, idempotencyKey)
  replay_or_reject_idempotency(requestHash)
  SELECT preview FOR UPDATE
  validate owner, expiry, specHash, capability, budget, permission, asset safety
  SELECT user_quota FOR UPDATE
  validate and reserve plannedTrialCount
  INSERT experiment
  INSERT revision + asset holds + frozen snapshots
  INSERT stage(status=preparing, plannedCount, generatedCount=0, cursor=0)
  UPDATE experiment.currentRevisionId
  INSERT audit + completed idempotency response
COMMIT
```

幂等记录、计划额度和 Experiment 必须同成同败。创建响应发送失败不回滚已经提交的 Experiment；调用方用原键找回。

### 26.2 Trial 分块生成

多个协调器实例可以并行运行，但同一 Stage 只允许一个有效生成租约。每个循环：

```text
BEGIN
  SELECT one preparing stage
    WHERE lease expired or unclaimed
    FOR UPDATE SKIP LOCKED
  claim generation lease with attemptToken
  read immutable StageSpec and cursor
COMMIT

generate deterministic batch outside transaction

BEGIN
  SELECT stage FOR UPDATE
  verify attemptToken, lease, cursor and not cancelled
  INSERT trials in trialIndex order with ON CONFLICT identity verification
  UPDATE generatedCount, cursor, incrementalDigest, lease
  if generatedCount == plannedCount:
    verify final collection digest
    transition stage to queued
  INSERT audit
COMMIT
```

`ON CONFLICT` 只有现有行的 TrialSpec 摘要完全相同时才视为安全重放；同一 index/fingerprint 对应不同内容立即进入 `generation_identity_conflict`，不得覆盖。生成批次大小是配置，不进入 Trial 指纹；改变批次大小不能改变输出。

### 26.3 Trial 物化 Unit of Work

当前普通 `create_bar_backtest_job/create_l2_backtest_job` 自行开启事务，不能直接用于实验原子物化。实现必须提供接收现有数据库 cursor/transaction 的 `createQueuedBacktestJobInTransaction`，复用 `_create_queued_backtest_job` 的校验和写入逻辑。协调器不得通过 HTTP 回调本应用创建子任务。

锁顺序固定为 `user_quota → ExperimentRevision → Stage → Trial`，取消、物化、人工重试和终态对账全部遵守，避免死锁。物化伪代码为：

```text
BEGIN
  SELECT user_quota FOR UPDATE
  SELECT revision FOR UPDATE
  SELECT stage FOR UPDATE
  SELECT trial FOR UPDATE
  recheck revision/stage/trial status, cancel flag, asset hold, budget and permits
  require trial.activeExecutionId IS NULL
  compile frozen TrialSpec through TrialCompiler
  executionId = new UUID
  dispatchKey = "experiment:" + executionId
  INSERT backtest_run(request_key=dispatchKey, sourceType=experiment, source refs...)
  INSERT bar/l2 job using same cursor
  INSERT trial_execution(runId, dispatchKey, executionNo)
  INSERT dispatch_outbox(status=succeeded for current DB queue adapter)
  UPDATE trial SET materialized, activeExecutionId=executionId
  UPDATE quota permits
  INSERT audit
COMMIT
```

稳定 `dispatchKey` 同时写入 `backtest_run.request_key`。当前 PostgreSQL 队列 Adapter 在同一事务完成任务写入并把 outbox 标记为 `succeeded`；未来外部 BatchExecutor Adapter 仍先在本地创建 `backtest_run + TrialExecution + outbox`，由带租约的投递器至少一次发送，外部系统按 dispatchKey 幂等接收。这样切换 Adapter 不改变 Experiment Interface 或运行身份。

### 26.4 终态对账与 permit

终态对账读取 `backtest_run` 和 Bar/L2 任务真源，在同一事务中：

1. 锁定 user quota、Revision、Stage、Trial 和 TrialExecution；
2. 校验 run owner、runId 和活动 execution；
3. 冻结 result schema、规范化结果 hash、marketDataSnapshot hash、终态时间和错误摘要；
4. 成功时设置 `selectedExecutionId`；失败或取消时保留旧 selected 执行；
5. 清空 `activeExecutionId`，释放 permit，更新聚合计数；
6. 写入按 Stage 单调递增的 `terminalSequence`；
7. 重算熔断、Stage 与 Experiment 状态。

permit 释放操作使用 executionId 作为去重键；重复对账不能重复扣减。定时一致性任务从非终态 TrialExecution 和实际任务状态重算 quota，发现漂移时修复缓存计数并记录审计，不修改运行事实。

### 26.5 取消、重试与修订

取消先锁 Revision 并写 `cancel_requested_at`，然后按相同锁顺序处理 Stage 和 Trial。物化事务在拿到锁后必须重新检查取消标记，因此“取消成功后又创建新 run”不成立。已经先提交的 run 加入取消集合；未生成和未物化数量分别按 8.5 节记录。

人工重试请求必须冻结 Trial 选择集的 count + digest；事务内重新计算不一致时返回 `experiment.selection_changed`。只有 `activeExecutionId IS NULL` 且 Trial 当前选定执行终态允许重试。新 executionNo、executionId 和 dispatchKey 每次不同，但同一次重试请求的幂等键重放返回原执行集合。

创建新 Revision 时锁 Experiment 和当前 Revision；当前 Revision 未终结返回 `experiment.active_revision_exists`。新 Revision 不引用旧 Trial 行，只复用用户明确选择且仍有效的输入值；任何资产、数据、预算和能力都重新预览和冻结。

### 26.6 熔断的确定性

“连续三个相同错误”按 Stage 内持久化的 `terminalSequence` 定义，不按多个 Worker 的网络返回顺序或页面观察顺序。只有不同 TrialExecution、相同错误指纹、相邻 terminalSequence 才计为连续；用户取消、容量阻塞和安全禁用不计入策略错误连续数。

FailurePolicy 还必须冻结：阈值、观察窗口、冷却时间、最大自动恢复次数以及哪些错误类型允许自动恢复。首期默认不自动解除 `execution_blocked`；人工恢复记录操作者、原因和当时能力摘要，恢复后从原 Revision 继续。

### 26.7 估算与实际资源偏差

ExperimentRevision 冻结预计预算，但协调器同时累计实际或更新后的资源使用量。若累计实际值加剩余保守估算超过当前硬上限：

- 停止物化新 Trial，设置 `budget_blocked`；
- 已运行 Trial 默认继续完成，除非触发系统级安全停止；
- 不缩小网格、不跳过高成本 Trial、不把阻塞改写成失败；
- 用户可以取消，或由管理员调整系统容量后恢复；
- 改变 Experiment 自身预算必须创建新 Revision。

### 26.8 Evaluation 与导出作业

创建 EvaluationRun 时在事务中冻结 execution 集合、`resultSetHash`、MetricCatalog、Normalizer 和 pipelineVersion。评价 Worker 使用租约执行；失败只重试评价，不创建回测。provisional 输出保存覆盖比例、各关键维度覆盖和缺失原因。

表格和报告统一使用异步 Export 作业，复用现有信号明细导出的深 Module 模式：幂等创建、单用户并发限制、租约、取消、有限重试、进度、SHA-256、TTL 和每次下载所有权校验。导出冻结 `evaluationRunId + outputHash + format + columns + locale`；CSV/XLSX 中用户可控字符串以 `= + - @` 开头时进行公式注入转义。过期文件返回 HTTP 410，重新导出创建新作业。

## 二十七、安全、配置与可观测性实施设计

### 27.1 CSRF 与请求关联

当前仓库 Cookie 会话只有 `SameSite=Lax`，没有可供本方案复用的 CSRF Token。实施时必须先增加统一保护：

1. 登录成功响应同时返回随机 CSRF Token；服务端只在 `auth_session` 保存其 hash；
2. 页面刷新后通过 `GET /api/auth/csrf` 原子轮换 Token：服务端生成新值、替换当前会话 hash，并只在本次响应返回明文；
3. 除登录外，Cookie 会话下所有 POST/PUT/PATCH/DELETE（包括退出登录）必须携带 `X-CSRF-Token`；
4. 同时校验 `Origin` 属于配置的同源允许列表；缺少 Origin 时只允许同源 Referer，二者都缺失则拒绝；
5. API Key 路径不使用 Cookie CSRF Token，但继续执行 Scope、限流和请求审计；
6. 校验失败返回 `403 auth.csrf_invalid`，不进入业务事务。

该改造影响现有全部 Cookie 写接口，必须同批更新前端调用封装和回归现有登录、策略、回测、共享、导出写操作。CORS 只控制浏览器读取，不替代 CSRF。

所有 `/api` 和 `/api/v1` 请求都生成 requestId，并在响应头 `X-Request-Id` 与错误体返回。日志关联链固定为：

```text
requestId → experimentId → revisionId → stageId
          → trialId → trialExecutionId → runId → attemptToken
```

### 27.2 配置项与安全默认值

新增配置使用现有 `TREND_GRID_` 前缀。生产数值必须由 49 号方案容量认证后写入私有 `deploy/.env`；仓库示例不得覆盖服务器配置。

| 配置 | 安全默认值 | 规则 |
| --- | --- | --- |
| `TREND_GRID_EXPERIMENTS_ENABLED` | `false` | 总开关；关闭时接口返回能力未启用，协调器不领取新工作 |
| `TREND_GRID_EXPERIMENT_BAR_ENABLED` | `false` | 标准 Bar 门禁通过后开启 |
| `TREND_GRID_EXPERIMENT_L2_ENABLED` | `false` | 独立容量认证后开启 |
| `TREND_GRID_EXPERIMENT_MAX_TRIALS_PER_STAGE` | `0` | 功能开启时必须显式配置正数 |
| `TREND_GRID_EXPERIMENT_MAX_USER_PLANNED_TRIALS` | `0` | 功能开启时必须显式配置正数 |
| `TREND_GRID_EXPERIMENT_MAX_IN_FLIGHT_PER_EXPERIMENT` | `1` | 不得大于用户聚合上限 |
| `TREND_GRID_EXPERIMENT_MAX_IN_FLIGHT_PER_USER` | `1` | 不得突破现有用户/全局调度能力 |
| `TREND_GRID_EXPERIMENT_MANUAL_RESERVED_PERMITS` | `1` | 普通任务保留额度 |
| `TREND_GRID_EXPERIMENT_MANUAL_MAX_WAIT_SECONDS` | `60` | 超过后暂停该用户实验补充 |
| `TREND_GRID_EXPERIMENT_GENERATION_BATCH_SIZE` | `100` | 允许范围 1–1000，不影响指纹 |
| `TREND_GRID_EXPERIMENT_PREVIEW_TTL_SECONDS` | `900` | 允许范围 60–3600 |
| `TREND_GRID_EXPERIMENT_CURSOR_SIGNING_SECRET` | 无 | 功能开启时必须配置高熵服务端密钥，不记录到日志或快照 |
| `TREND_GRID_EXPERIMENT_COORDINATOR_LEASE_SECONDS` | `30` | 必须大于心跳间隔三倍 |
| `TREND_GRID_EXPERIMENT_COORDINATOR_HEARTBEAT_SECONDS` | `5` | 允许范围 1–30 |
| `TREND_GRID_EXPERIMENT_PURGE_ENABLED` | `false` | 首期默认关闭物理清理 |
| `TREND_GRID_EXPERIMENT_EXPORT_TTL_DAYS` | `7` | 只清理导出文件，不清理评价事实 |

启动校验必须拒绝：开启功能但上限为 0、未配置 cursor 签名密钥、单实验上限大于用户上限、保留额度超出当前调度能力、租约不满足心跳关系或 L2 开启但未配置独立预算。动态收紧容量只阻塞新物化，不修改历史 Revision。

### 27.3 权限与敏感信息

- 预览、创建、恢复、重试和评价时都重新校验当前用户，不把创建时权限当作永久授权；
- RunTemplateSnapshot 保存身份与摘要，不保存口令、API Key、Cookie、数据库 DSN 或可直接下载私有资产的 URL；
- 审计 detail 使用字段白名单，策略源码、YAML 原文、SQL、堆栈和绝对路径禁止进入普通审计与前端错误；
- 管理员 purge、解除熔断和容量调整必须记录操作者、原因、旧值、新值和 requestId；
- 普通用户不能通过 Trial 分页、错误聚合或指标分组推断其他用户资源；
- 自动化严格固定 `mode = backtest`，TrialCompiler 拒绝任何 live 权限、实盘账户或下单通道字段。

### 27.4 指标、日志与健康检查

Prometheus 指标只使用低基数标签：templateType、stageType、runPath、scopeType、fillModel、dispatcherType、status、reasonCode。experimentId、trialId、runId、symbol 和错误原文只进入结构化日志或 trace，不作为指标标签。

至少增加：

- `experiment_preview_total`、`experiment_create_total`；
- `experiment_generation_batch_total`、`experiment_generation_duration_seconds`；
- `experiment_generation_lag_seconds`、`experiment_oldest_pending_seconds`；
- `experiment_trial_state_count`、`experiment_in_flight_count`；
- `experiment_dispatch_total`、`experiment_dispatch_duration_seconds`；
- `experiment_quota_drift_count`、`experiment_orphan_execution_count`；
- `experiment_blocked_duration_seconds`；
- `experiment_evaluation_backlog`、`experiment_export_backlog`；
- `experiment_coordinator_heartbeat_age_seconds`。

`/api/health` 增加实验协调器、Evaluation Worker 和 Export Worker 项，返回版本、能力摘要、最后心跳和积压摘要。默认告警：心跳超过两个租约周期、孤儿/所有权不一致数量大于 0、generation cursor 连续两个租约周期无进展、quota 漂移大于 0、普通任务等待超过配置阈值、导出积压持续增长。告警只通知运维，不自动删除或重跑成功任务。

- 结果规范化链路：提供 resultHash 和 MetricCatalog Adapter 输入，不改写历史结果；
- `backend/services/auth.py` 与认证路由：会话绑定 CSRF Token；
- 新增独立协调器、评价和导出进程入口，但复用同一代码包与配置校验。

函数仍遵守不超过 50 行的职责原则；复杂 SQL 集中在 repository，状态转换集中在 application/coordinator，路由不承载业务分支。

### 28.2 前端

建议新增：

- `frontend/src/features/experiments/api.ts`：所有实验内部接口；
- `contracts.ts`：判别联合、错误码和页面模型；
- `ExperimentListPage.tsx`、`ExperimentCreatePage.tsx`、`ExperimentDetailPage.tsx`；
- `steps/SubjectStep.tsx`、`GridStep.tsx`、`PreviewStep.tsx`、`ConfirmStep.tsx`；
- `ExperimentProgress.tsx`、`TrialTable.tsx`、`EvaluationBuilder.tsx`；
- `draftStore.ts`：按用户/subject/version/schema 隔离的本地草稿；
- 对应 Vitest 测试与路由入口。

所有写请求通过统一 `sendJson` 扩展自动携带 CSRF Token、requestId 透传和当前操作生成的 `Idempotency-Key`。UUID 使用现有 `createBrowserUuid()`，不得直接调用 `crypto.randomUUID()`。提交中、失败和成功反馈必须显示在当前页面。

### 28.3 数据库与进程

- 新建幂等迁移，不修改 `001–042`；
- 协调器可以多实例部署，通过数据库租约和 `SKIP LOCKED` 协作，不依赖单进程内存 leader；
- 当前 Bar/L2 Runner 继续只领取普通任务，不识别 Experiment 表；
- Evaluation/Export Worker 不执行用户策略，只读取已经持久化的规范化结果；
- dispatch outbox、协调器和导出 Worker 都使用 attemptToken + lease，终态写入校验 token。

### 28.4 现有代码基线与改造落点

实施时以以下已核对事实为基线，不能假定能力已经存在：

- `backend/services/state_store.py::_create_queued_backtest_job` 已接受 cursor，可作为事务级创建基础；公开 `create_bar_backtest_job/create_l2_backtest_job` 会自行开启事务，实验 Unit of Work 不能直接调用后两者；
- `backtest_run.request_key` 已存在唯一约束，但当前 `_create_backtest_run_row` 没有写入该列；实验路径必须显式写 dispatchKey；
- 当前网页登录幂等把 key/hash 写入 `requested_params`，公共 `api_idempotency_record` 又绑定 `api_key_id`；二者都不能替代新的内部通用幂等表；
- 当前 `delete_backtest_run`、批量 ID 删除和筛选删除都会物理删除终态 `backtest_run`；三条路径都必须增加实验保留检查和稳定 409；
- 当前统一任务候选只按 owner 当前槽位数和 createdAt 排序，没有 manual/experiment 来源；必须先增加规范来源列，再实现用户内保底与 round-robin；
- 当前只有 `/api/v1` 自动生成 requestId，Cookie `/api` 写请求没有统一 requestId 或 CSRF Token；必须按第 27 章补齐；
- `frontend/src/utils/browserUuid.ts` 已提供非安全上下文兼容 UUID，实验前端直接复用；
- `backtest_signal_detail_export` 已提供租约、幂等、进度、TTL 和 RLS 参考，评价导出复用其模式，不复制不一致的同步导出实现。

## 二十九、测试矩阵与交付顺序

### 29.1 单元测试

至少覆盖：

- Canonicalization 的 Unicode、键顺序、Decimal、`-0`、集合与有序列表；
- spec/stage/trial/resultSet/evaluation hash 的固定向量；
- 有限网格去重、稳定顺序、数量溢出和非法场景；
- seedBundle 派生与重试复用；
- 状态转换、聚合、FailurePolicy 和 terminalSequence；
- MetricCatalog 可比较域、null、统计和安全公式；
- 各 Adapter capability 与 unsupportedReason。

### 29.2 数据库与协调器集成测试

至少覆盖：

1. 两个并发创建请求不能突破计划额度；
2. 相同幂等键同请求重放、不同请求冲突；
3. 生成进程在任意分块后崩溃可以续跑，Trial 不重不漏；
4. 两个协调器同时扫描只产生一个 TrialExecution；
5. 物化事务任一步失败不会留下孤儿 run、execution、permit 或 outbox；
6. 取消与物化竞争后不再产生新 run；
7. 终态对账重复执行只释放一次 permit；
8. 相同错误按 terminalSequence 触发熔断；
9. 用户多个 Experiment 共享聚合上限，普通任务保留额度与 round-robin 生效；
10. 关联实验的单条、批量和筛选删除全部返回稳定 409；
11. 归档不删除，purge 按依赖图清理且可从失败位置恢复；
12. 所有子表 RLS、previewToken、幂等键、游标和 runId 均不能跨用户读取；
13. DatasetSnapshot 版本不一致和实际 data hash 漂移会阻塞评价；
14. 账号删除不能绕过无 run 的 pending Experiment；
15. 配额缓存能够从任务真源重建。

数据库测试必须使用真实 PostgreSQL 特性验证部分索引、RLS、`FOR UPDATE SKIP LOCKED`、advisory lock 和事务，不用纯内存假实现替代关键并发语义。

### 29.3 API 与前端测试

至少覆盖：

- previewToken 正常、过期、跨用户、Spec 变化、能力变化和预算变化；
- 创建 201、重放 200、进行中 202及所有稳定错误体；
- CSRF Token 缺失/错误、Origin 错误和合法请求；
- 创建响应丢失后按原键找回；
- `crypto.randomUUID` 不存在时仍生成 UUID v4 并发送请求；
- 连续点击只调用一次；网络不确定时复用原键；
- 当前步骤显示错误并保留输入；
- 本地草稿按用户和 subjectVersion 隔离，恢复后强制重新预览；
- `preparing → queued → running → terminal` 页面进度、轮询退避和分页；
- 创建新修订、取消、恢复、失败项重试、归档和评价；
- 现有单次回测、策略、共享和导出接口在统一 CSRF 改造后保持可用。

### 29.4 回测正确性与兼容测试

- 同一冻结 Trial 通过实验链路和手工单次链路得到相同请求快照、成交、账本和规范化结果；
- 策略更新、重新发布、重命名或归档后，实验仍使用冻结版本；
- 历史 `backtest_run` 无 Experiment 关系时读取和删除语义保持原样；
- Bar 和 L2 分别验证合法算法、取消、租约重领、错误分类和结果适配；
- 历史结果 schema 通过旧 MetricCatalog Adapter 读取，不被新默认值重算；
- 标准 Bar 遵守 ADR 0009 的来源、正式日期和预热语义；
- 真正修改回测提交、调度、执行或结果后，按仓库规则使用远程普通用户最近两条样本通过隔离的正常 Worker 链路回归；无法执行时明确标记待验证。

### 29.5 性能与故障注入

在 49 号方案代表性负载下验证：最大允许网格预览、分块生成、多个用户/实验混合、普通任务插队、协调器重启、数据库短暂断连、Worker 租约过期、评价和导出积压。记录 p50/p95/p99 预览耗时、生成吞吐、物化延迟、普通任务最大等待、数据库锁等待、列表查询和评价耗时。

容量测试必须给出可据以填写生产配置的证据；没有证据时保持功能开关关闭。L2 单独认证，不能用标准 Bar 结果推定。

### 29.6 发布与回滚顺序

同一发布批次顺序为：

1. 备份并执行幂等迁移；
2. 发布 backend、统一 CSRF 前端兼容和新增配置，实验开关保持关闭；
3. 发布协调器、Evaluation/Export Worker，验证健康但不领取普通用户实验；
4. 发布前端入口，仍由能力开关隐藏；
5. 完成本地、集成、容量和远程普通用户样本回归；
6. 先仅管理员/测试用户启用标准 Bar，再逐步开放普通用户；
7. 独立完成 L2 门禁后再启用 L2。

修改 backend、任务调度、Runner、前端接口契约和回测运行时的相互依赖部分必须通过 `scripts/deploy-server.sh` 同批发布。发布前检查排队和运行中的 L2 任务，不能静默中断。`deploy/.env` 不得被 `.env.example` 覆盖。

回滚优先关闭 `TREND_GRID_EXPERIMENTS_ENABLED` 并停止协调器领取新工作；已经创建的普通 `backtest_run` 继续按现有语义完成或取消。数据库迁移保持向后兼容，不在紧急回滚中删除表；修复后协调器从持久化状态继续。发布后检查健康、代表性新实验、普通单次回测、历史任务、取消、删除保留和缓存回源。

### 29.7 文档与完成定义

实现改动会影响策略编辑器入口、回测提交、任务状态、错误提示和历史删除，因此同一改动必须检查并更新 `docs/玄龄回测系统使用手册.md`。完成时还必须提供：迁移说明、配置说明、接口示例、错误码清单、运维告警、容量证据、测试真实结果和未验证项；未实际执行的服务器、L2 或远程样本验证不得写成通过。
