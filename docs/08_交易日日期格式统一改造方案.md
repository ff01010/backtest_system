# 交易日日期格式统一改造方案

## 1. 背景与结论

当前系统对同一个交易日同时使用 `YYYYMMDD` 和 `YYYY-MM-DD`：前端普通回测请求、部分 API 校验和策略 Worker 使用前者；ClickHouse L2 查询和聚合 Bar 使用后者。L2 临时聚合已先后出现两类边界错误：紧凑日期无法查询 ClickHouse，ISO 日期又无法通过 Worker 的 `tradeDate（交易日）` 校验。

结论：不能继续在单个 Runner 中用字符串替换修补。应统一日期模型和服务契约：

- Python 领域逻辑使用 `date（日期对象）`。
- 前端 API、后端任务载荷、PostgreSQL JSON 快照、Runner 与策略 Worker 统一使用 ISO `YYYY-MM-DD`。
- ClickHouse 日期查询使用 ISO `YYYY-MM-DD`。
- `YYYYMMDD` 只作为旧 CSV、文件名和旧外部引擎的适配器格式，不得跨越服务边界。

本方案只处理“日期”，不改变 `datetime（日期时间）` 的毫秒精度、时区或 L2 事件排序语义。

## 2. 目标与边界

### 2.1 目标

- 一个交易日在任何 API、任务、缓存审计和 Worker 请求中只存在一种字符串格式。
- 新建回测、历史回测重跑、普通 Bar 回测和 L2 回测均接受并保存 ISO 日期。
- 在过渡期兼容旧的 `YYYYMMDD` 输入和历史任务，但不再产生新的紧凑格式任务载荷。
- 将格式转换集中到显式适配器，杜绝散落的 `replace('-', '')` 或字符串切片。

### 2.2 非目标

- 不修改 ClickHouse 原始表、L2 快照/逐笔数据和 Redis 缓存数据模型。
- 不更改交易时段、Bar 聚合规则、时间戳格式或策略 `on_bar（K线回调函数）` 接口。
- 不在本次将 PostgreSQL 中已经是 `date` 类型的行情表字段改为字符串。

## 3. 现状盘点

| 边界 | 当前格式 | 问题 | 目标格式 |
| --- | --- | --- | --- |
| 前端回测表单与默认参数 | `YYYYMMDD` | 与日期输入控件和 L2 ClickHouse 不一致 | ISO |
| `/api/backtest/*` 请求与查询参数 | `YYYYMMDD` | `app.py`、前端校验、图表接口各自校验 | ISO，过渡期兼容紧凑输入 |
| `backtest_run` 的 JSON 请求/参数快照 | 混合 | 重跑历史记录可重新引入旧格式 | 新记录 ISO；旧记录读取时标准化 |
| L2 Runner → Worker | ISO 与紧凑格式混用 | Worker 当前仅允许 `^\d{8}$` | ISO |
| ClickHouse QMT/L2 查询 | 以 ISO 最稳定 | 上游表为 `Date` / `DateTime` | ISO |
| 旧 CSV、文件名、外部旧引擎 | 紧凑格式 | 文件/数据集契约不能直接破坏 | 仅适配层转紧凑格式 |

## 4. 统一契约

### 4.1 中心日期工具

新增 `backend/date_codec.py`，集中提供：

- `parse_trading_date（解析交易日）`：接受 ISO 与紧凑格式，返回 `date（日期对象）`；拒绝无效日期。
- `format_api_date（格式化 API 日期）`：返回 ISO；所有服务边界唯一使用此函数。
- `format_legacy_date（格式化旧格式日期）`：返回紧凑格式；仅由旧 CSV、文件名和外部引擎适配器调用。
- `normalize_date_range（标准化日期区间）`：解析、比较并返回两个 ISO 日期，统一处理开始日晚于结束日的错误。

禁止业务代码直接用字符串比较、`replace`、切片或正则来转换交易日。校验和转换均委托此模块。

### 4.2 服务契约

- FastAPI 请求模型和 query 参数以 ISO 为公开规范；错误消息明确为 `YYYY-MM-DD`。
- 过渡期请求模型仍接受 `YYYYMMDD`，在进入业务层前标准化为 ISO。
- `WorkerL2DayRequest（L2交易日请求）`、`WorkerL2ChunkRequest（L2数据块请求）` 和结束交易日路径参数改为 ISO。
- L2 Bar、Quote、Trade 的 `trade_date（交易日）` 与包络 `tradeDate（交易日）` 均使用 ISO，避免同一请求体内两种格式。
- 回测结果、Redis 审计和历史详情显示 ISO；页面可按展示需要格式化，但不能改变原值。

## 5. 实施步骤

### 5.1 建立日期域与兼容输入

1. 新增中心日期工具及单元测试，覆盖闰年、非法日、ISO、紧凑格式和区间比较。
2. 在 `schemas.py` 与 API 查询参数引入统一解析，不再调用 `settings.validate_date（校验日期格式）` 作为业务入口。
3. 所有新建 `BacktestRunRequest（回测请求）` 在创建任务前保存为 ISO；包含 `requested_params（原始请求参数）`、`params_snapshot（参数快照）`、L2 job payload 和历史重跑载荷。

### 5.2 统一前端与公开 API

1. 将回测页面默认日期、输入校验、时间范围查询、数据覆盖比较和历史重跑参数改为 ISO。
2. 日期输入改为浏览器原生 `type="date"`，使浏览器输出 ISO；恢复旧记录时先标准化再放入表单。
3. `fetchBacktestTimeframes（查询回测周期）`、图表查询和历史详情相关 TypeScript 类型按 ISO 契约更新。
4. 所有 API 响应中的可表示交易日改为 ISO；如旧页面仍消费紧凑日期，在前端过渡适配器中一次性处理。

### 5.3 统一普通回测与数据适配器

1. `app.py`、`market_data.py`、`data_repository.py`、`backtest_runner.py` 接收 ISO 或 `date`，对 ClickHouse 一律传 ISO。
2. QMT 覆盖、行情状态和图表接口不再自行进行紧凑字符串比较。
3. 旧 CSV、文件名、外部中盘引擎参数等保留紧凑格式需求的位置，改为仅调用 `format_legacy_date（格式化旧格式日期）`；不得把紧凑日期返回给主流程。

### 5.4 统一 L2 任务链路

1. `TemporaryQuoteBarProvider（临时快照聚合提供方）` 继续在入口解析兼容输入，但向 ClickHouse 和输出模型仅使用 ISO。
2. `L2Runner（L2任务执行器）` 按 ISO 分组、读取行情、创建日会话、发送 chunk 和结束日会话；移除任何临时格式替换。
3. `strategy_worker.py` 与 `worker_app.py` 的日会话模型、路径校验和状态字段改为 ISO。
4. 为 Runner/Worker 的 HTTP 契约增加集成测试：一个 ISO 交易日从 `begin`、多个 chunk 到 `finish` 全程一致。

### 5.5 历史数据迁移与发布

1. 新增编号迁移，仅处理已知 JSON 字段中的 `startDate`、`endDate`、`tradeDate`；将匹配 `^\d{8}$` 的值改为 ISO。不得对任意文本字段做全局替换。
2. 迁移前统计受影响记录数，迁移后抽样核对普通回测、L2 任务和历史重跑记录。
3. 读取历史记录时保留兼容标准化，直到完成一个发布周期后再评估是否移除紧凑输入支持。
4. `backend`、`l2-runner` 与 `strategy-worker` 必须作为同一版本构建并启动，避免新旧 Worker 契约混跑。发布前不领取或先完成现有 L2 任务。

## 6. 测试与验收

### 6.1 自动化测试

- 日期工具：ISO/紧凑输入、闰年、非法日期、范围逆序。
- 后端 API：新 ISO 请求成功；紧凑格式请求在过渡期成功且保存结果为 ISO。
- 普通回测：QMT 覆盖检查、图表查询、历史重跑与导出文件名均正确。
- L2：临时 Bar 聚合、正式 Bar Provider、Quote/Trade 分页、Worker 日会话和三日回测链路使用 ISO。
- 历史迁移：仅已知字段被标准化，时间戳、策略代码、注释和其他 JSON 内容不变。
- 前端：表单默认值、日期控件、历史恢复、时间范围缓存键和 TypeScript 类型检查通过。

### 6.2 人工验证

1. 提交 `688126.SH`、2026-06-01 至 2026-06-03 的 L2 回测，确认 Runner、Worker、审计结果中交易日均为 ISO。
2. 从一条旧紧凑格式历史记录点击重跑，确认新任务保存 ISO 并能完成。
3. 提交普通 1m/5m 回测，确认既有 QMT 覆盖和图表功能没有回归。
4. 检查 Redis 临时 Bar 缓存键的日期部分为 ISO，聚合结果可命中且可回源。

## 7. 风险与回滚

- 风险：普通回测有大量历史 CSV/文件路径约定，直接全局替换会造成找不到文件。缓解：只在旧适配器输出紧凑格式，并为每个适配点写测试。
- 风险：Runner 与 Worker 分开升级会再次产生 422。缓解：Compose 统一 `--build` 启动，发布前确认三者镜像为同次构建。
- 风险：JSON 迁移误改策略文本或时间戳。缓解：仅更新白名单键，迁移前备份并记录行数，迁移脚本幂等。
- 回滚：应用代码可回退；JSON 迁移需配套反向迁移（仅 ISO 日期白名单字段转回紧凑格式）。Redis 派生 Bar 可淘汰重建，不作为回滚依赖。

## 8. 自审

- 方案没有把格式规范停留在前端或 L2，而是覆盖 API、持久化、Worker、ClickHouse 与旧文件适配器，避免下一条链路再次出现双格式。
- 方案区分了“内部日期对象”“公开 ISO 字符串”和“旧格式适配”，职责边界清楚。
- 全量统一会影响普通回测和历史重跑，实施时应先完成中心工具和兼容读取，再切换前端与 Worker，不能只修当前报错。
- 发布需要一起更新 `backend`、`l2-runner`、`strategy-worker`；若无法保证原子发布，应暂不切换 Worker 契约。
