# 信号明细页面深化方案

## 1. 目标

将“信号明细”从回测结果的交易表升级为可复核的执行账本。用户应能在一处回答：某条信号何时产生、策略给出了什么动作、为何成交或跳过、成交价格与盈亏如何形成。

页面服务于纯回测复盘，不新增模拟盘、实盘、行情订阅或委托能力。

## 2. 当前问题

- 表格已展示方向、价格、数量和盈亏，但筛选、状态和时间信息分散，逐笔复盘效率不足。
- 已跳过的信号与已成交交易缺少更强的视觉区分，跳过原因不够醒目。
- 用户需要在总览指标与单笔明细之间来回切换，难以快速判断异常交易对结果的影响。
- 在小屏幕下，宽表的阅读和筛选成本较高。

## 3. 设计方案

### 3.1 页面结构

保留“信号明细”标签页和现有导出能力，重组为三层：

1. **结果上下文条**：固定展示回测编号、策略方案、标的、周期、日期区间及成本模型；让用户明确当前查看的结果快照。
2. **筛选与摘要区**：展示总信号数、已成交、已跳过、盈利笔数、亏损笔数和胜率；筛选按“交易方向、执行状态、盈亏状态、日期分组”组织，导出操作位于同一区域。
3. **信号执行账本**：以时间为主线呈现每条记录，强调信号时间、执行时间、动作、成交状态、价格依据、数量、单笔盈亏与备注。

### 3.2 执行状态和视觉层级

| 状态 | 视觉规则 | 目的 |
| --- | --- | --- |
| 已成交 | 使用克制的青绿色状态标记 | 突出进入实际回测账本的记录 |
| 已跳过 | 使用琥珀色标记并显示原因 | 让策略信号未执行的原因可见 |
| 盈利 | 使用 A 股习惯的红色数值 | 快速识别正收益交易 |
| 亏损 | 使用绿色数值 | 快速识别负收益交易 |
| 无盈亏或不适用 | 中性灰色 | 避免制造错误的收益暗示 |

状态色只承担含义，不以大面积高饱和背景干扰表格阅读。

### 3.3 单笔信息组织

默认列按复盘顺序排列：

1. 信号时间与执行时间；
2. 信号动作、买卖方向与执行状态；
3. 成交价格、价格来源和数量；
4. 单笔盈亏与持仓后收益；
5. 跳过原因或执行备注。

保留“选择显示字段”能力。日期分组开启后，每个日期组显示当日信号数、成交数和当日已实现盈亏摘要。

### 3.4 交互与响应式规则

- 筛选条件变更后即时更新摘要和账本，不重新运行回测。
- 导出 CSV 使用当前筛选结果，并明确导出行数。
- 表格行悬停仅增强可读性；不新增会改变回测结果的编辑操作。
- 窄屏下筛选区折行，账本保留横向滚动；优先保证时间、动作、状态和盈亏列可见。

## 4. 实现边界

本阶段只调整 `frontend/src/components/BacktestPage.tsx` 中“信号明细”活跃页面及 `frontend/src/styles/global.css` 的样式层。

不修改以下内容：

- 回测引擎、交易撮合、费用和滑点计算；
- 后端 API、数据库结构、历史回测快照；
- 策略脚本接口 `on_bar(bar, state)` 与动作语义；
- 模拟盘或实盘相关功能。

## 5. 验收标准

- 用户能无需返回概览页就确认当前回测上下文和交易摘要。
- 已成交与已跳过信号可在账本中快速区分，跳过原因可读。
- 筛选、分组、字段显隐和 CSV 导出沿用现有逻辑且结果正确。
- 现有交易明细自动化测试、TypeScript 构建和差异检查通过。
- 前端容器重建后可在目标分辨率下人工复核桌面与窄屏布局。
