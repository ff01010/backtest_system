# Issue tracker：OpenProject

本仓库的需求、Bug 和实施任务统一在 OpenProject 中作为工作包管理。GitLab 仅用于代码版本管理，不使用 GitLab Issues 代替 OpenProject。

## 默认工作方式

- 当前环境未配置 OpenProject 自动写入接口时，默认只生成可直接粘贴到 OpenProject 的 Markdown，不创建或修改远程工作包。
- 生成工单前，读取当前有效的 OpenProject 工作包清单。
- 必须核对已有工作包的描述、完成内容、验证结果、验收标准和后续事项，不得只根据标题判断是否重复。
- 用户已提供工单编号或现有工作包已经实质覆盖时，不重复创建。
- 需要远程创建、更新、评论或关闭工作包时，必须由用户明确要求，并使用当时可用的受控接口。

## 创建工单

每个工单固定包含：

- 标题
- 类型
- 描述
- 完成内容
- 验证结果
- 验收标准
- 后续事项

没有实际执行或验证的内容必须标记为“待验证”。

## 获取相关工单

优先读取用户提供编号对应的完整工作包内容。没有编号时，从当前工作包清单中按工作目标、改造范围和验收内容进行实质匹配。

无法访问最新工作包数据时，应明确说明数据状态，不得虚构远程记录。

## 当技能要求发布到 Issue Tracker

默认在对话中输出可粘贴的 OpenProject 工作包内容。除非用户明确要求并提供可用的 OpenProject 写入能力，否则不得自动创建远程工作包。

## Ticket 拆分与工单记录分离

- `to-tickets` 拆出的 ticket 是实现单元，必须分开保存：每个 ticket 一个文件，写入 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，编号从 `01` 起、按依赖顺序（blockers 在前）；不得合并成单一文件，也不得只输出到对话而不落盘。
- 每个 ticket 必须包含 `Spec` 字段，指向 spec 文档的具体章节（对应哪个 Bug 或改动），让 `implement` 阶段无需人工回溯 spec。
- OpenProject 工单是记录用途：一个方案或需求是否合并成一个记录工作包，由用户决定，`to-tickets` 可询问；默认不随 ticket 拆分而拆成多个工作包。
- ticket 的拆分数量由实现边界与依赖关系决定，不代表工作包数量。
