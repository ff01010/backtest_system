# 策略完整版本与资产分页加载改造计划

日期：2026-10-15
状态：已实施；浏览器端到端写链路、远程普通用户样本回归和服务器发布待验证

## 1. 背景与问题结论

当前系统已经具备策略脚本版本和策略配置版本表，但读取、保存和前端展示仍存在三个相互关联的问题：

1. 浏览器端通过 `GET /api/strategy-configs` 一次读取当前用户的全部策略，并携带策略代码、参数等完整内容。用户存在数千至上万条策略时，请求体积、数据库读取和浏览器渲染都会显著放大，可能导致前端下拉框无法使用，并偶发经过网关返回 504。
2. 完整策略保存接口同时承载新建和更新，调用方如果在修改时继续使用新建语义，就会持续创建新的策略身份。系统不能根据“代码是否相同”猜测调用方是在新建还是更新，否则会破坏用户明确的新建和复制行为。
3. `strategy_config_version` 虽然已经存在，但早期保存链路没有保证每个已有策略都有完整策略版本。部分已有策略只有代码版本，没有包含代码和配置的完整版本号。

本次改造以用户操作作为策略身份边界：保存已有策略只更新该策略并递增完整版本；只有用户主动执行新建或复制时才创建新的策略身份。同时将策略资产读取改为轻量分页和详情按需加载，消除全量代码传输与全量 DOM 渲染。

## 2. 已确认的业务定义

### 2.1 完整策略与完整版本

用户看到的“策略”是一个完整聚合：

```text
完整策略
├── strategy_config：配置身份、参数、标的、周期等
├── user_strategy：该配置独占的脚本身份
├── user_strategy_version：不可变代码版本
└── strategy_config_version：代码与配置组合后的不可变完整版本
```

用户看到的“策略版本”指 `strategy_config_version.version_no`，其快照必须包含：

- 策略代码及其确切代码版本；
- 策略参数；
- 标的、周期、模式和基准等配置；
- 影响策略运行语义的脚本元数据。

`strategy_config.revision` 只用于乐观锁和并发修改检测，不是用户可见的策略版本号。`user_strategy_version.version_no` 只表示代码版本，也不能代替完整策略版本号。

### 2.2 三类用户操作

| 用户操作 | `config_id` | `strategy_id` | 完整策略版本 |
| --- | --- | --- | --- |
| 保存已有策略 | 保持不变 | 保持不变 | 有效内容变化时递增 |
| 新建策略 | 新建 | 新建 | 从 V1 开始 |
| 复制策略并保存 | 新建 | 新建 | 从 V1 开始 |

具体规则：

1. 用户在已有策略中修改代码后点击“保存”，仍然更新当前策略，不自动变成新策略。
2. 用户是否创建新策略仅由“新建”和“复制”操作决定，不能通过代码或配置差异推断。
3. 同一策略代码发生变化时，先在该策略内部追加代码版本，再生成新的完整策略版本。
4. 仅配置变化时，可以复用当前代码版本，但必须生成新的完整策略版本。
5. 完整快照完全一致时不创建重复完整版本；现有 `revision` 递增行为作为并发控制语义保留。
6. 两个不同策略即使代码完全相同，也不能共享可变的 `strategy_id`。

## 3. 改造范围与边界

### 3.1 本期范围

- 为缺少完整版本的已有策略补录真实的 V1 基线快照。
- 拆分浏览器端完整策略的新建与更新接口语义。
- 将策略资产列表改为轻量摘要、服务端搜索和游标分页。
- 将策略详情和版本历史改为按需读取。
- 改造策略编辑页和其他策略选择入口，避免全量加载和渲染。
- 补充数据库、后端、前端、性能和历史兼容测试。
- 同步更新 `docs/玄龄回测系统使用手册.md`。

### 3.2 明确不做

1. 不合并、删除、归档或重命名已经创建的重复策略。
2. 不为旧策略增加“需要保存”“需要另存为”或其他异常标记。
3. 不根据相同代码、相同参数或内容指纹自动合并策略。
4. 不重建迁移前已经丢失的完整版本历史；数据库没有保存的历史不能推测或伪造。
5. 不修改历史回测的代码快照、参数快照、结果或 `config_version_id`。
6. 不改变 `on_bar`、`bar`、`state`、成交、费用、仓位和风险控制语义。
7. 不通过单纯增加 Nginx 超时时间规避查询和渲染问题。
8. 不修改 `package.json`、`pyproject.toml` 或依赖版本。

## 4. 现状依据

### 4.1 已有一对一约束

迁移 `db/migrations/023_strategy_config_script_ownership.sql` 已经建立 `strategy_config.strategy_id` 的唯一归属，并通过复合外键保证配置绑定的代码版本属于自己的策略。该约束必须保留，不得为了复用相同代码而放宽。

历史提交 `b278f66` 修复过“多个配置共享同一可变策略，修改一处影响多处”的问题；本次改造必须继续满足该提交建立的一对一边界。

### 4.2 完整版本缺口

`db/migrations/002_backtest_workspace.sql` 创建了 `strategy_config_version`，但没有为后来通过旧链路保存且从未发布完整快照的配置统一补版本。因此允许出现：

```text
strategy_config 存在
user_strategy_version 存在
strategy_config_version 不存在
```

当前保存逻辑在写入代码和配置后调用发布函数。如果直接沿用该顺序处理没有版本的旧策略，修改后的内容可能被错误写成 V1，修改前的当前状态将无法恢复。

### 4.3 全量资产读取

当前 `GET /api/strategy-configs` 使用完整配置查询，包含策略代码和参数，并且不分页。前端 `BacktestPage` 首次进入时加载全部策略，再使用原生 `<select>` 渲染全部选项。策略数量达到数千或上万时，该链路同时产生：

- 数据库读取和 JSON 序列化压力；
- 网关等待时间和响应体积增长；
- 浏览器 JSON 解析、React 状态和 DOM 节点膨胀；
- 保存或归档后重新全量加载造成的重复压力。

## 5. 已有策略 V1 基线迁移

### 5.1 迁移目标

为每一条没有任何 `strategy_config_version` 的已有 `strategy_config` 创建一条真实版本记录：

```text
config_id            = 原配置 ID
version_no           = 1
strategy_version_id  = 配置当前绑定的代码版本 ID
snapshot             = 迁移时当前代码和当前配置的完整快照
```

这不是前端默认显示 V1，也不是新增一个只存数字的字段。迁移后，版本历史接口能够读取真实 V1，并能使用该快照恢复当前基线内容。

### 5.2 迁移文件与幂等规则

实施前重新确认 `db/migrations/` 的最大编号；按当前仓库状态新增：

```text
db/migrations/057_strategy_complete_version_baseline.sql
```

迁移遵循以下规则：

1. 只选择不存在任何 `strategy_config_version` 的配置。
2. 使用 `NOT EXISTS` 和 `(config_id, version_no)` 唯一约束保证重复执行不会重复插入 V1。
3. 快照绑定 `strategy_config.strategy_version_id`；如果过渡数据仍为空，则使用该配置独占策略的当前有效代码版本。
4. 找不到策略、找不到代码版本或代码版本不属于同行策略时终止迁移，不猜测代码。
5. 不更新 `strategy_config` 的名称、内容、`revision`、`updated_at`、归档状态或发布状态。
6. 不触碰已经存在任意完整版本的配置，即使其最早版本号不是 1，也不重新编号。
7. 不回填历史 `backtest_run.config_version_id`，避免把迁移时的当前状态错误绑定为过去回测的历史版本。

### 5.3 快照内容

基线快照必须与应用层 `_config_snapshot` 的结构和字段含义一致，至少包括：

- `name`
- `scriptId`
- `strategyVersionId`
- `strategy`
- `mode`
- `symbol`
- `timeframe`
- `benchmarkSymbol`
- `accountId`
- `paramsJson`
- `sharedSource`
- `paramsJson.scriptCodeHash`
- `paramsJson.scriptSnapshot`

`scriptSnapshot` 必须保存迁移时实际绑定版本的代码、名称、描述、入口类型和运行能力摘要。迁移测试应将 SQL 生成的快照与应用层快照逐字段比较，防止出现两套不兼容格式。

### 5.4 版本号解释

已有策略的完整版本统一从 V1 建立基线，但其内部代码版本可能已经是 V2、V7 或其他编号。例如：

```text
完整策略 V1 -> 绑定代码版本 V7
```

这是合法关系：V1 表示系统开始完整记录时的第一份代码与配置组合，V7 表示该策略内部当前代码版本。迁移前未保存的完整组合历史无法恢复，手册必须明确说明这一边界。

### 5.5 首次保存兜底

保存已有策略的事务增加防御性检查：

1. 锁定当前 `strategy_config`。
2. 校验所有权和 `expectedRevision`。
3. 在修改任何代码或配置前检查是否存在完整版本。
4. 如果不存在，立即用锁定后的旧内容创建 V1。
5. 再写入用户提交的代码和配置。
6. 若完整内容发生变化，生成 V2；完全一致则继续使用 V1。

正常发布顺序应保证数据库迁移先完成，因此该逻辑主要用于防止遗漏数据、测试数据库或异常环境把修改后内容误记成 V1。

## 6. 后端生命周期改造

### 6.1 服务职责

在 `backend/services/strategy_lifecycle.py` 中收拢以下操作：

```text
create_strategy(command)
update_strategy(config_id, expected_revision, command)
create_strategy_from_copy(command)
```

`create_strategy_from_copy` 可以复用创建逻辑，但调用意图必须由前端的复制状态明确给出，不能由代码指纹推导。

更新操作必须：

1. 以 `config_id` 作为外部资源身份。
2. 从数据库读取该配置独占的 `strategy_id`。
3. 不允许客户端把配置改绑到另一个 `strategy_id`。
4. 只在当前策略内部查找或创建代码版本。
5. 在同一事务中保存代码、配置和完整版本。
6. 返回最新完整策略详情及版本号，供前端直接更新状态。

### 6.2 事务顺序

更新已有策略的固定事务顺序为：

```text
锁定配置
  -> 校验用户、归属和 revision
  -> 必要时补旧内容 V1
  -> 解析或创建当前策略内部的代码版本
  -> 更新配置
  -> 生成并比较完整快照
  -> 内容变化时追加完整版本
  -> 返回同一 config_id 和 strategy_id 的最新详情
```

任何一步失败都回滚整个事务，不留下孤立代码版本或半完成配置。

### 6.3 版本生成规则

- 代码和配置均未发生有效变化：不新增完整版本。
- 代码未变、配置变化：复用代码版本，完整版本 `+1`。
- 代码变化、配置未变：追加当前策略内部代码版本，完整版本 `+1`。
- 代码和配置同时变化：两类版本均按各自规则追加。
- 代码恢复为当前策略过去出现过的内容：可以复用该策略自己的历史代码版本，但仍生成新的完整版本以记录这次组合状态。
- 其他策略存在相同指纹：不得复用其 `strategy_id` 或代码版本记录。

## 7. 接口契约

### 7.1 浏览器端写接口

新增或调整为以下明确契约：

```text
POST /api/complete-strategies
PUT  /api/complete-strategies/{config_id}
```

`POST` 表示新建，返回新的 `configId`、`strategyId`、V1 和最新 `revision`。

`PUT` 表示更新已有策略，请求必须携带 `expectedRevision`，返回原 `configId`、原 `strategyId`、当前完整版本号和新 `revision`。版本冲突返回 409，归属不一致返回 409，不存在或无权访问继续使用不泄露资源信息的既有错误语义。

为兼容发布过程中可能仍打开旧前端的浏览器，现有携带 `configId` 的 `POST` 更新形式暂时保留为兼容适配层，并复用同一个更新服务；新前端不再调用该形式。移除兼容入口不属于本次范围，应在确认旧客户端窗口结束后另行处理。

公共 API 已使用：

```text
POST /api/v1/strategies
PUT  /api/v1/strategies/{config_id}
```

本次保持其资源语义不变，并在手册中强调调用方首次 POST 后必须保存返回的 `config_id` 和 `revision`，后续修改使用 PUT。持续调用 POST 会被视为调用方明确要求新建，后端不能自动合并。

### 7.2 策略资产摘要分页

将浏览器端 `GET /api/strategy-configs` 改为轻量分页契约：

```text
GET /api/strategy-configs?limit=50&cursor=<opaque>&query=<name>
```

约束：

- `limit` 默认 50，最大 100。
- `cursor` 使用 `updated_at + id` 的不透明游标，按 `updated_at DESC, id DESC` 排序。
- `query` 只搜索当前用户策略名称，执行参数化查询，并限制输入长度。
- 默认只返回未归档策略。
- 无效游标返回 422，不退化为第一页以掩盖调用错误。

响应结构：

```json
{
  "items": [
    {
      "id": "config-id",
      "name": "策略名称",
      "scriptId": "strategy-id",
      "strategyVersionId": "code-version-id",
      "versionNo": 1,
      "revision": 3,
      "strategy": "user_script",
      "mode": "backtest",
      "symbol": "000001.SZ",
      "timeframe": "5m",
      "enabled": true,
      "updatedAt": "2026-10-15T00:00:00Z"
    }
  ],
  "nextCursor": "opaque-or-null",
  "total": 10000
}
```

摘要列表禁止返回策略代码、完整参数、运行快照或版本历史。

### 7.3 详情与版本历史

完整详情继续按 ID 加载：

```text
GET /api/complete-strategies/{config_id}
```

响应增加或明确 `versionNo`，并继续返回代码、配置、代码版本 ID 和 `revision`。

浏览器端版本历史改为分页：

```text
GET /api/strategy-configs/{config_id}/versions?limit=50&cursor=<version_no>
```

按 `version_no DESC` 返回，下一页使用最后一条版本号作为游标。具体版本详情仍通过配置 ID 与版本 ID 的归属校验读取。

## 8. 数据访问与索引

### 8.1 查询拆分

在 `backend/services/state_store.py` 中拆分：

- 摘要分页查询：不读取 `source_code` 和完整 `params`。
- 单个策略详情查询：只在用户选择策略时读取完整内容。
- 完整版本分页查询：只在打开版本历史时读取。
- 写入事务：负责基线、代码版本、配置和完整版本。

摘要查询可以对当前页使用索引化的版本号子查询，但不得使用现有包含代码正文的 `_config_query` 作为列表查询。

### 8.2 索引策略

先在至少一万条策略数据上执行 `EXPLAIN (ANALYZE, BUFFERS)`。若现有索引不能稳定支持游标分页，则在 V1 基线迁移或独立的下一个幂等迁移中增加部分索引：

```sql
CREATE INDEX IF NOT EXISTS ...
ON strategy_config (owner_user_id, updated_at DESC, id DESC)
WHERE archived_at IS NULL;
```

名称搜索索引仅在执行计划证明需要时增加。不能为了计划完整而无依据新增索引。

## 9. 前端改造

### 9.1 类型与客户端

在 `frontend/src/types/index.ts` 中区分：

- `StrategyConfigSummary`：列表摘要。
- `StrategyConfigPage`：分页响应。
- `StrategyConfig`：完整详情。
- `StrategyConfigVersionPage`：版本分页响应。

在 `frontend/src/api/client.ts` 中提供独立方法：

- 获取策略摘要页；
- 搜索策略摘要；
- 获取单个策略详情；
- 新建完整策略；
- 更新已有完整策略；
- 获取版本历史页。

### 9.2 选择器行为

将原生全量 `<select>` 改成仓库内实现的异步可搜索选择器，不引入新依赖：

1. 首次只读取 50 条摘要。
2. 输入名称后防抖查询。
3. 滚动或点击“加载更多”读取下一页。
4. 使用请求序号或取消机制丢弃过期搜索结果。
5. 选择摘要后按 `config_id` 获取完整详情。
6. 当前选中策略不在已加载页时，详情仍以固定选中项显示。
7. 显示服务端返回的 `total`，不通过当前页长度推断总数。
8. 保存或归档后局部更新或移除摘要，不重新下载全部策略。

需要审计 `BacktestPage.tsx`、`ExperimentPage.tsx` 及其他 `strategyConfigs` 消费者，避免历史回测名称、实验页面或深链接依赖“全部策略已在内存中”的旧假设。

### 9.3 新建、复制与保存状态

页面显式维护：

```text
editing  正在编辑已有策略
new      用户点击了新建
copy     用户点击了复制
```

调用规则：

- `editing` 保存调用 PUT。
- `new` 保存调用 POST。
- `copy` 保存调用 POST。
- 代码是否发生变化不参与路由选择。

复制继续采用“生成本地副本草稿，用户点击保存后创建”的现有交互。前端可以建议“原名称 副本”，但最终重名处理由后端基于用户全部策略完成，不能只扫描当前已加载的一页。

创建或更新请求进行中时禁用重复提交。请求失败必须在策略操作区域显示，不做用户不可见的自动重试。

## 11. 测试计划

### 11.1 测试层次与替换边界

| 层次 | 真实运行 | 允许替换 | 主要断言 |
| --- | --- | --- | --- |
| 数据库集成测试 | PostgreSQL、事务、约束、SQL 快照 | 不替换数据库 | 持久化事实、约束、版本顺序、幂等 |
| 后端服务/API 测试 | 生命周期服务、路由、序列化 | 可替换认证外围和不可控网络 | HTTP 契约、错误语义、所有权 |
| 前端组件测试 | 组件状态与用户操作 | 替换网络边界 | 可见列表、请求方法、加载与错误状态 |
| 浏览器验证 | 前后端及真实 DOM | 不替换核心业务链路 | 大数据量下搜索、翻页、选择和保存 |

事务、唯一约束、快照序列化和幂等迁移必须由真实 PostgreSQL 集成测试验证，不能用 Mock 代替。

### 11.2 V1 基线迁移测试

1. 无完整版本的已有策略迁移后得到真实 V1。
2. V1 快照与迁移前当前代码和配置一致。
3. 代码版本已经为 V7 时，完整策略 V1 正确绑定代码 V7。
4. 已有完整版本的策略不新增、不覆盖、不重新编号。
5. 重复执行迁移不会产生第二条 V1。
6. 孤立策略、缺失代码版本或跨策略版本引用使迁移明确失败。
7. 迁移不改变策略 ID、配置 ID、名称、`revision`、归档状态和历史回测。

### 11.3 生命周期与 API 测试

1. 新建策略产生新 `config_id`、新 `strategy_id` 和完整版本 V1。
2. 修改已有策略的代码后保存，两个 ID 不变，完整版本递增。
3. 只修改配置时复用代码版本，完整版本递增。
4. 完全相同内容重复保存不新增完整版本。
5. 复制保存产生独立的两个 ID 和 V1。
6. 相同代码的新建策略不得共享策略身份。
7. 已有策略没有完整版本时，首次更新先保存旧内容 V1，再保存新内容 V2。
8. 过期 `expectedRevision` 返回 409，先提交的数据不被覆盖。
9. 客户端传入其他策略 ID 时返回归属冲突。
10. 摘要列表不包含代码、完整参数和快照。
11. 游标分页、搜索和并发更新时间下不出现同页重复。
12. 单条详情和版本恢复仍返回完整内容。

### 11.4 前端测试

1. 首次进入只请求第一页，不调用全量详情列表。
2. 搜索输入执行防抖，过期请求不会覆盖新结果。
3. 加载更多正确合并，重复 ID 去重。
4. 选中摘要后才请求完整详情。
5. 修改已有策略无论代码是否变化都发送 PUT。
6. 新建和复制草稿保存发送 POST。
7. 保存成功后局部更新摘要和详情，不全量刷新。
8. 当前选中策略不在第一页时仍能正确显示。
9. 请求进行中重复点击不会生成多个策略。
10. 列表、详情和保存错误均有用户可见提示。
11. 保存后立即运行不会被误判为存在未保存修改。

### 11.5 性能与浏览器验证

准备至少一万条当前用户策略数据，代码长度和参数大小使用接近真实分布的生成数据，不使用生产源码作为测试固件。

验证：

- 首屏和每次追加最多渲染约定页大小的数据。
- 摘要 SQL 不读取 `source_code` 或完整参数 JSON。
- 首屏、下一页和名称搜索均记录 `EXPLAIN (ANALYZE, BUFFERS)`。
- 在本地代表性环境中，万条数据首屏和搜索响应不出现网关超时。
- 浏览器输入、翻页、选择、保存和归档保持可操作。
- 保存后不会再次产生万条完整策略下载。

## 12. 验收标准

1. 每个未归档策略都能显示真实完整版本号。
2. 原本没有完整版本的策略拥有真实 V1 快照，而不是仅在前端显示默认值。

## 15. 回滚策略

1. V1 基线迁移是只追加版本记录，不修改策略内容和历史回测；代码回滚后新增版本仍能被旧代码兼容读取。
2. 不提供删除基线版本的自动逆向迁移，避免上线后已经产生的 V2 引用失效。
3. 前端出现问题时可回退前端版本；后端在兼容期仍接受旧 POST 更新形式。
4. 分页接口出现问题时优先前向修复，不能通过恢复全量代码列表作为长期方案。
5. 只有迁移生成的快照结构或绑定关系确认错误且不能前向修复时，才在停止新写入后使用发布前数据库备份恢复。

## 16. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 修改后的内容被误记为旧策略 V1 | 迁移提前补基线；保存事务在写入前再次检查并补旧快照。 |
| 完整版本号与代码版本号混淆 | API 分别返回 `versionNo` 和 `scriptVersionNo`，手册明确两者职责。 |
| 批量补快照导致迁移时间或存储增长 | 发布前统计规模，在隔离副本演练并记录耗时与体积。 |
| 分页后当前选中策略不在首屏 | 通过详情接口单独加载，并在选择器中固定显示选中项。 |
| 复制名称只对当前页判重 | 服务端对用户全部未归档策略执行唯一名称解析。 |
| 快速搜索返回乱序 | 使用请求序号或取消机制丢弃过期响应。 |
| 深层分页性能退化 | 使用 `updated_at + id` 游标，不使用深层 OFFSET。 |
| 旧浏览器继续调用 POST 更新 | 保留兼容适配层，并让新前端统一调用 PUT。 |
| 外部调用方继续重复 POST | 手册明确 POST/PUT 契约；系统尊重显式 POST，不按内容自动合并。 |
| 重新引入多配置共享脚本 | 保留数据库唯一约束、复合外键和后端归属校验。 |

## 17. 自审与读者检查

实施前后使用以下问题检查计划和代码是否一致：

1. 一个没有完整版本的旧策略第一次修改时，旧内容和新内容分别是什么版本？
2. 修改已有策略代码时，什么条件会创建新的策略 ID？
3. 完整版本号与代码版本号是否可能不同，前端展示哪一个？
4. 相同代码的新建和复制是否仍然得到独立策略身份？
5. 策略列表是否在任何路径读取或返回代码正文？
6. 当前选择不在第一页时，页面如何加载和显示它？
7. 外部调用方应如何避免每次修改都创建新策略？
8. 迁移前缺失的完整版本历史如何处理？
9. 回滚代码后，已经补录的 V1 和后来创建的 V2 是否仍然安全？
10. 是否存在任何步骤会合并、删除或标记已有重复策略？

本计划对这些问题的答案分别是：先补旧内容 V1、修改后生成 V2；只有显式新建或复制才创建新 ID；两种版本可以不同且用户展示完整版本；新策略保持独立；列表不读取代码；通过详情接口加载；首次 POST 后持久化 ID 并使用 PUT；只以当前状态建立 V1，不伪造过去历史；版本记录继续保留；不存在历史策略清理或标记步骤。
