# 标准 Bar 行情分批读取与超时修复方案

- 状态：已实现，待发布
- 日期：2026-10-08
- 关联故障：任务 `#374`

## 1. 背景与结论

任务 `#374` 在 `bar.backtest` 阶段以 `data.bar_load_failed` 结束。经 ClickHouse 查询日志核对，本次失败不是“数据库没有数据”，而是标准 Bar 全区间查询超过客户端超时后被断开：

- 标的：`688981.SH`；
- 周期：`1m`；
- 请求区间：`2025-01-02` 至 `2025-12-31`；
- 覆盖元数据成功返回 `237` 个状态完整日期；
- 首次原始 Bar 查询运行约 `79.314` 秒后记录 broken pipe，读取约 `5,330,532` 行、`227,726,923` 字节；
- 客户端默认超时为 `30` 秒，有限重试在首次查询尚未结束时再次发起同一全年查询，形成重叠扫描；
- 重试查询运行约 `49.043` 秒后同样因客户端断开而失败。

当前查询通过 `GROUP BY bar_time` 和多列 `argMax(..., tuple(revision, ingested_at))` 选取每根 Bar 的最新版本。该逻辑适用于同一 Bar 允许存在多版本的原始表，但在上游已保证最终 Bar 唯一、干净的前提下，会带来不必要的聚合、内存和扫描开销。

本方案在不修改 ClickHouse 表、分区、索引、数据、存储介质和 Redis 的边界内，采用以下修复：

1. 标准 Bar 改为直接读取唯一的最终行，不再对原始 K 线使用 `argMax` 和 `GROUP BY`。
2. 按实际回放日期分批、串行查询，避免一次扫描全年并限制单次失败影响范围。
3. 将有限重试收敛到当前失败批次，已成功批次不重复读取。
4. 增加重复时间、越界日期和字段合法性防御，确保上游唯一性假设被破坏时明确失败，而不是静默产生错误回测结果。

## 2. 实施前提与责任边界

### 2.1 唯一性前提

本方案假定上游对已发布最终 Bar 提供以下保证：

```text
(symbol, period, adjustment, bar_time) 全局唯一
```

同时满足：

- 回测只读取 `is_final = 1` 的最终数据；
- 同一唯一键不存在多个已发布版本；
- OHLCV、时间和交易日字段已通过上游发布质量控制；
- 删除或保留 `revision`、`ingested_at` 字段均不影响上述唯一性合同。

“不再需要 `argMax`”依赖的是数据唯一性保证，而不是单纯删除 `revision` 字段。若上游仅删除字段但仍可能写入重复 Bar，本方案不得上线。

### 2.2 改造边界

本轮只修改应用侧标准 Bar 读取与相关测试：

- 不修改 ClickHouse 表结构、分区键、排序键、索引或磁盘策略；
- 不清理、重写或迁移现有行情数据；
- 不新增 PostgreSQL 迁移；
- 不引入 Redis 缓存或修改任何缓存键；
- 不修改依赖和依赖清单；
- 不改变策略回调、撮合、成交、净值、快照结构和历史结果展示语义；
- 不改变 L2 Quote 查询、撮合和摘要质量规则；
- 不恢复失败任务 `#374`，修复后通过新任务验证。

### 2.3 保留的 `argMax`

本次只移除原始 K 线查询中的 `argMax`。`qmt_ingest_runs` 等覆盖元数据表仍通过版本化状态表达某个日期的最新发布结果，其 `argMax(state, state_version)` 或等价查询必须保留。

原始 Bar 唯一性与覆盖状态版本是两个独立问题，不能因为前者已唯一而删除后者的版本选择逻辑。

## 3. 目标与非目标

### 3.1 目标

1. 任务 `#374` 的同等数据范围能够稳定完成标准 Bar 加载。
2. 单次查询只覆盖有限数量的实际行情日期，不再发起全年宽范围聚合。
3. 超时重试不与前一次全年查询形成重叠扫描。
4. 1m、3m、5m、15m、30m、45m、60m、1d 的现有来源和派生语义保持不变。
5. 正式日期、预热日期、停牌日、空数据和历史快照语义保持不变。
6. 当唯一性前提被破坏时，Worker 明确记录内部数据错误并终止任务。

### 3.2 非目标

- 不通过提高全局 HTTP 超时掩盖慢查询；
- 不建设新的行情当前态表或物化视图；
- 不将行情搬到 Redis；
- 不调整冷盘、热盘或存储层级；
- 不为追求性能改变回测输入集合；
- 不在本轮重构通用 ClickHouse 客户端或 L2 查询框架；
- 不把行情导入质量责任转移给回测 Worker。

## 4. 当前问题分析

### 4.1 全区间聚合成本过高

当前原始 K 线查询对请求日期范围内的行按 `bar_time` 分组，并分别对时间和 OHLCV 字段执行 `argMax`。对于任务 `#374`，ClickHouse 为返回约数万根目标 Bar 实际读取了约五百万行，并使用约 `165 MB` 峰值内存。

在最终 Bar 已唯一的前提下，这部分聚合既不改变结果，又增加 CPU、内存和执行时间。

### 4.2 查询范围大于实际日期集合

Worker 已从覆盖元数据得到正式日期和预热日期，但原始 Bar 查询仍使用最早日期到最晚日期的连续区间。该方式没有利用已解析的精确日期集合，也使一次失败覆盖整个任务数据范围。

### 4.3 重试粒度过大

当前 HTTP 客户端超时后对完整查询进行重试。客户端断开不代表 ClickHouse 已立即停止旧查询，因此第二次全年查询可能与旧查询重叠，进一步增加数据库负载。

单纯提高超时时间只能延后失败，不能消除高成本聚合、全年单批和重叠重试三个根因。

## 5. 目标查询模型

### 5.1 直接读取唯一最终 Bar

六个原生来源周期继续读取各自物理表，查询改为直接选择最终行：

```sql
SELECT
  qmt_time_ms AS time,
  open,
  high,
  low,
  close,
  volume
FROM qmt_history_dev.<source_table>
WHERE symbol = <symbol>
  AND period = <source_period>
  AND adjustment = 'none'
  AND is_final = 1
  AND trade_date IN (<batch_dates>)
ORDER BY bar_time ASC
SETTINGS max_execution_time = <server_timeout_seconds>
```

相较当前查询，明确移除：

- `GROUP BY bar_time`；
- 所有 `argMax`；
- 对 `revision`、`ingested_at` 的引用；
- 未参与标准化和回测的 `qmt_index` 返回列。

继续保留：

- `is_final = 1`；
- `adjustment = 'none'`；
- 来源周期和来源物理表约束；
- 按 `bar_time` 升序返回；
- 当前“不按 `quality_status` 二次筛选”的既有合同。

### 5.2 周期行为

- `1m`、`5m`、`15m`、`30m`、`60m`（物理 `1h`）、`1d` 继续直接读取原生来源。
- `3m`、`45m` 继续读取 `1m` 后按既有交易时段分桶规则派生。
- 本轮不修改分钟桶对齐、午休边界、Bar 时间语义和派生版本。

## 6. 精确日期分批读取

### 6.1 日期集合

加载入口继续以已经解析并冻结的日期为准：

```text
requested_dates = sort(unique(warmup_dates + formal_dates))
```

查询使用 `trade_date IN (...)` 精确限定每批日期，不重新推断交易日，也不将最早日期和最晚日期之间的所有自然日作为读取范围。

历史快照已保存 `formalDates`、`warmupDates` 时继续使用冻结值，不根据当前覆盖元数据重算。

### 6.2 初始批次大小

初始批次按来源周期配置：

| 来源周期 | 每批日期数 | 适用运行周期 |
| --- | ---: | --- |
| `1m` | 10 | `1m`、`3m`、`45m` |
| 其他原生周期 | 40 | `5m`、`15m`、`30m`、`60m`、`1d` |

批次按日期升序串行执行，不在单个任务内并行查询。任务 `#374` 的 237 个正式日期预计拆分为 24 个 `1m` 批次，最后一批为 7 个日期。

批次大小是应用侧性能参数，不属于回测结果语义。上线前可依据真实查询日志向下调整，但不得在没有性能证据时扩大批次。

### 6.3 空批次与整体空数据

覆盖日期可能因停牌或来源发布语义没有实际 Bar。为保持 ADR 0002、0004 和 0009 的既有合同：

- 单个批次返回空集合不立即失败；
- 所有批次合并后完全无 Bar 时，继续按 `empty_bar_data` 或现有等价内部原因失败；
- 不要求每个覆盖日期都必须返回 Bar；
- 不因为某日无 Bar 而生成策略回调或伪造数据。

## 7. 超时与重试

### 7.1 服务端先于客户端终止

每个批次查询设置 ClickHouse `max_execution_time`，确保数据库在 HTTP 客户端超时前主动终止异常慢批次。当前客户端默认超时为 30 秒，初始服务端上限按以下规则计算：

```text
server_timeout_seconds = max(1, min(25, clickhouse_timeout_seconds - 5))
```

若未来客户端超时配置不大于 5 秒，实施时必须采用不小于 1 秒且严格小于客户端超时的安全值，并补充配置边界测试，不能产生服务端上限反而晚于客户端断开的情况。
客户端超时配置必须大于 1 秒；不满足该条件时应按配置错误拒绝启动相关查询，不能生成与客户端超时相等的服务端上限。

### 7.2 批次级有限重试

- 每个批次最多执行 2 次；
- 仅对当前已有的超时、连接中断等临时错误重试；
- 已成功批次保留在内存中，不重新查询；
- 重试前使用比当前更明确的短退避，初始建议 1 秒；
- SQL、权限、字段或表不存在等确定性错误不扩大重试范围；
- 重试耗尽后继续由现有错误包装进入 `data.bar_load_failed`，管理员诊断保留原始内部原因。

本轮不修改 L2 Quote 查询的全局重试合同，也不为通用 ClickHouse 客户端引入无限重试。

## 8. 数据防御与结果不变量

批次合并后、进入派生和回放前执行以下校验：

1. `time` 可解析且严格按升序排列；
2. 来源 Bar 的 `time` 不重复；
3. 返回 Bar 的交易日期必须属于本次请求的正式或预热日期集合；
4. OHLCV 必填字段存在并满足现有数值校验；
5. 派生周期完成后仍沿用当前排序和预热计数规则。

若检测到重复时间，说明上游唯一性合同被破坏。Worker 必须按 `invalid_bar_data` 或现有等价内部原因失败，不得在应用层临时去重、取第一条、取最后一条或恢复 `argMax` 掩盖数据问题。

本轮必须保持以下不变量：

- 正式 Bar 和预热 Bar 的区分不变；
- 预热阶段只初始化状态，不产生正式交易结果；
- `marketDataSnapshot` 的来源、日期、Bar 数和输入哈希语义不变；
- 相同输入 Bar 产生的策略回调、成交和结果不变；
- 历史成功任务结果不重算，历史失败事实不改写；
- L2 Runner 复用标准化 Bar 时获得同一有序 Bar 集合。

## 11. 性能验证与验收标准

### 11.1 基准场景

使用与任务 `#374` 相同的只读行情条件验证：

```text
symbol = 688981.SH
period = 1m
startDate = 2025-01-02
endDate = 2025-12-31
formalDates = 237 个状态完整日期
```

验证不得修改生产任务、行情数据或覆盖元数据。

### 11.2 记录指标

每次验证至少记录：

- 每批日期数、耗时和返回行数；
- 总加载耗时和总 Bar 数；
- ClickHouse 每批读取行数、读取字节和峰值内存；
- 是否发生超时、重试、broken pipe 或重叠查询；
- 修复前后小样本 Bar 的时间、OHLCV、数量和排序一致性。

### 11.3 验收标准

1. 基准场景连续运行 3 次均成功完成 Bar 加载；
2. 不再出现 30 秒客户端超时和 broken pipe；
3. 不再出现两个重叠的全年原始 Bar 查询；
4. 每条 SQL 只查询一个配置批次的精确日期；
5. 返回 Bar 无重复、按时间升序，且日期不超出请求集合；
6. 固定小样本的时间、OHLCV、Bar 数和派生结果与修复前一致；
7. 多个 Worker 同时执行代表性任务时未形成持续查询堆积；
8. 标准 Bar、预热、图表预览和 L2 标准化 Bar 链路的自动化回归通过。

若 10 日期的 `1m` 批次仍接近超时，只允许继续缩小批次并重新验证；不得通过恢复全年查询或无限提高超时绕过验收。

## 13. 回滚策略

### 13.1 应用回滚

本轮不修改数据和持久化结构，可通过恢复前一版本应用镜像回滚。回滚不会要求清理 Redis 或执行数据库迁移。

### 13.2 上游字段兼容

新版直接查询不依赖 `revision` 和 `ingested_at`，因此上游暂时保留这两个字段不影响新版本运行。为保留旧版本回滚能力，建议在新版本稳定观察完成前不要物理删除字段。

如果上游已经删除字段，旧版本因仍引用 `revision`、`ingested_at` 将无法直接回滚。此时必须先恢复兼容视图或字段，再回滚应用；不得在事故中临时修改生产 SQL 绕过版本管理。

### 13.3 唯一性异常

若上线后触发重复 Bar 防御，应停止继续放量并回滚应用或修复上游唯一性。不得在 Worker 中静默去重，因为任意取舍都可能改变策略输入和回测结果。

## 14. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 上游唯一性保证与实际数据不一致 | 同一时间出现多根 Bar，回测输入不确定 | 上线前核验唯一性；运行时重复 `time` 明确失败，不静默去重。 |
| 批次过大仍超时 | 单批加载失败 | `1m` 初始 10 日期，依据查询日志只向下调优。 |
| 批次过小导致请求次数增加 | HTTP 往返和 ClickHouse 调度开销上升 | 对非 1m 周期使用 40 日期；以总耗时和数据库负载共同验收。 |
| 服务端超时设置晚于客户端 | 再次出现客户端断开和残留查询 | 服务端上限严格小于客户端超时，并补充配置边界测试。 |
| 分批后顺序或预热计数变化 | 策略状态和结果变化 | 合并后统一稳定排序，固定样本对比 Bar 与结果。 |
| 某批为空被误判为整体无数据 | 停牌或无 Bar 日期导致错误失败 | 只在全部批次合并后为空时失败。 |
| 只验证标准 Runner，遗漏 L2 复用链路 | L2 回归 | 本地 `test_l2.py` 和发布后代表性 L2 任务共同覆盖。 |
| 上游过早删除版本字段 | 旧应用无法回滚 | 稳定观察期内保留字段或兼容视图。 |

## 15. 方案自审结论

- **是否针对已确认根因**：是。直接移除无必要的版本聚合，并把全年单批改为精确日期小批次。
- **是否只靠增加超时**：否。超时仅作为批次保护，主要收益来自直接读取和缩小失败范围。
- **是否需要新表或 Redis**：否。唯一性前提成立时无需应用侧当前态表或缓存。
- **是否改变回测结果语义**：不应改变。查询目标仍是相同的最终 Bar；通过固定样本和结果回归验证。
- **是否掩盖上游数据问题**：否。重复 Bar、越界日期和非法字段均明确失败。
- **是否与 ADR 冲突**：无。方案继续以覆盖元数据和实际 Bar 日期为运行事实，保留单一 QMT 来源、冻结快照、预热隔离和空 Bar 失败合同。
- **是否覆盖发布和回滚**：是。明确 backend、bar-runner、l2-runner 同批发布、L2 任务检查和字段删除前的回滚窗口。
- **是否存在范围扩张**：无。不修改表、数据、缓存、前端、依赖、撮合和策略运行语义。
