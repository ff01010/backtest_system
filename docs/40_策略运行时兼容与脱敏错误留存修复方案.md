# 策略运行时兼容与脱敏错误留存修复方案

日期：2026-09-08
状态：本地实施完成，服务器待发布回归

## 1. 背景与问题结论

远程任务 `7473a152-7340-4d0b-93a3-64042e1df4cb` 在 L2 回放期间失败。脱敏日志确认，策略在 `_valid_slices` 中调用 Python 标准内置函数 `tuple()` 时触发 `NameError`。用户策略在普通 Python 3.12 环境中的用法合法，实际原因是平台 `_SAFE_BUILTINS（安全内置函数）` 未开放 `tuple`。

当前错误映射将所有 `NameError` 统一展示为“策略引用了未定义的变量或函数”，导致平台运行时兼容缺陷被错误归责给用户。用户即使反复修改正确代码也无法解决。

现有运行时还有两个结构性问题：

1. 平台逐项维护内置函数白名单，必然反复出现“用户使用一个正常内置函数，平台再补一个”的兼容缺口。
2. 白名单已经开放 `__import__`，策略可以导入 `builtins` 等已安装模块，因此当前白名单并不是真正的安全边界；它限制了正常语法，却不能独立阻止文件、网络或进程探查。
3. `system_error_log（系统错误日志）` 通过 `run_id` 级联关联 `backtest_run（回测记录）`。用户物理删除任务后，任务错误记录也被删除，只能依赖容器日志排查。

本方案在既有 `14_回测错误分类与前端可诊断提示方案`、`19_系统错误分类与管理员诊断日志改造方案` 和 `22_回测会话隔离与并发执行改造方案` 基础上补齐运行时契约、责任归类和脱敏统计留存，不改变策略交易与撮合语义。

## 2. 目标、范围与不做事项

### 2.1 目标

1. 策略按固定 Python 运行时使用正常内置函数，不再逐项补充 `tuple`、`enumerate`、`zip` 等常规能力。
2. 明确区分用户代码错误、平台禁止行为、平台运行时缺陷和局部变量初始化错误。
3. 平台问题不得提示用户修改策略；前端应明确告知“无需修改代码，请联系管理员”。
4. Bar、L2 和策略辅助 Worker 使用同一运行时版本、同一错误码和同一责任归类。
5. 任务物理删除后，仍保留不含源码、参数、用户和任务标识的运行环境错误统计，用于识别重复平台缺陷。
6. 不依赖 Python 函数名单承担安全隔离；安全边界由进程、容器、网络、文件系统和资源限制共同保证。

### 2.2 本期范围

- `ScriptedBarStrategy（脚本策略适配器）` 的内置函数环境与运行时版本。
- 保存校验、Bar 子进程、L2 子进程和 `strategy-worker（策略辅助服务）` 的错误转换。
- 失败任务的 `errorDetail（结构化错误详情）` 与前端错误卡片。
- 独立的脱敏运行环境错误统计及管理员聚合查询。
- 相关数据库迁移、自动化测试、使用手册和服务器发布验证。

### 2.3 不做事项

1. 不修改 `on_bar`、`on_quote`、`on_order_event` 的调用时机、参数和返回契约。
2. 不修改行情读取、撮合、费用、仓位、收益或调度规则。
3. 不保存用户策略源码、代码片段、参数、用户名、方案 ID、策略 ID、任务 ID、异常堆栈或内部地址到脱敏统计表。
4. 不把普通 Python 子进程描述为完整安全沙箱。
5. 不重算、改写或补写历史回测结果。
6. 不改变用户主动删除回测记录的物理删除语义。

## 3. 核心决策

### 3.1 正常 Python 能力与安全边界分离

策略运行时绑定固定的 Python 3.12 小版本和项目依赖镜像。内置函数环境由该固定 Python 版本提供，不再通过人工逐项列举常规安全函数。

平台可以保留明确的产品禁止项，例如 `open`、`input`、`breakpoint`、`eval`、`exec` 和 `compile`，但禁止项只承担产品契约和可复现性约束，不作为宿主机安全边界。被禁止的调用必须在保存时返回明确的策略规则错误，不能在执行阶段伪装成 `NameError`。

真正的安全边界必须由下列措施承担：

1. 一个回测任务一个独立策略子进程，任务取消或超时时可直接终止。
2. 子进程启动后不保留数据库、Redis、ClickHouse、研究中心或外部服务凭据。
3. 策略执行身份使用非 root 用户，不具备提权能力。
4. 策略可见文件系统只读且不挂载宿主机业务目录；临时目录启用 `noexec`、`nosuid` 并限制容量。
5. 策略执行环境默认无外部网络，并不能直接访问父 Runner 使用的数据库和行情网络。
6. 配置 CPU、内存、PID、整任务时限和取消宽限时间。
7. 固定运行时镜像和依赖版本，禁止策略在运行期安装包。

当前 Bar/L2 子进程已经采用 `spawn` 并清空环境变量，但仍与父 Runner 共享容器文件系统和网络命名空间。实施时必须把该限制列为真实边界，不能因为调用了 `os.environ.clear()` 就宣称已完成安全隔离。若暂时不能完成独立网络和文件系统隔离，发布说明必须明确这是兼容性修复，不是完整沙箱升级。

### 3.2 运行时版本化

新增集中定义的 `SCRIPT_RUNTIME_VERSION（策略运行时版本）`，例如 `python3.12-runtime-v2`。该版本至少覆盖：

- Python 小版本；
- 内置函数策略；
- 可导入依赖集合；
- `bar`、`quote`、`event` 和 `state` 契约版本；
- 禁止调用规则。

新任务将运行时版本写入冻结脚本快照或实验清单。历史记录没有该字段时显示 `legacy（历史运行时）`，不得用当前默认值伪造历史运行环境。运行环境发生兼容性变化时递增版本，不静默改变相同版本的语义。

### 3.3 错误责任必须由稳定规则判断

不能继续按异常类型直接判定责任。`NameError` 需要结合缺失名称、Python 标准内置集合、平台禁止集合和异常子类型分类。

| 场景 | 对外类别 | 错误码 | 前端责任说明 |
| --- | --- | --- | --- |
| Python 标准内置名称在当前运行时意外不可用 | `system_error` | `runtime.contract_missing` | 平台运行环境兼容问题，用户无需修改策略 |
| 调用了文档明确禁止的函数 | `strategy_error` | `strategy.runtime_policy_blocked` | 当前能力受平台规则限制，给出允许的替代方式 |
| 自定义名称从未定义或导入 | `strategy_error` | `strategy.undefined_name` | 用户检查变量、函数名称或导入 |
| 局部变量未在所有分支初始化 | `strategy_error` | `strategy.local_unbound` | 用户补齐初始化路径 |
| 运行时镜像、Bar、L2 或 Worker 契约版本不一致 | `system_error` | `runtime.version_mismatch` | 平台发布或调度问题，用户无需修改策略 |

`tuple` 事件应归类为 `runtime.contract_missing`，不能再返回 `strategy.runtime_error`。

## 4. 策略运行时改造

### 4.1 内置函数环境

运行时从固定 Python 版本构造完整标准内置环境，再应用少量显式产品禁止规则。实现不得继续维护“允许一个名字才可使用”的零散白名单。

保存校验和实际执行必须引用同一份运行时契约模块，禁止前端校验、后端保存校验、Bar Runner、L2 Runner 和 strategy-worker 各自维护名单。

对于禁止能力，优先在 AST 校验阶段返回受控错误；执行阶段保留同样的拒绝逻辑作为防线。禁止项不得只通过删除名称实现，否则用户只会再次看到误导性的“未定义变量”。

### 4.2 保存与提交预检

保存时执行以下检查：

1. Python 语法、回调名称与参数数量。
2. 双下划线属性和明确禁止调用。
3. 可静态确定的未定义名称、局部变量初始化和订单字面量契约。
4. 使用与 Runner 完全一致的运行时加载脚本，验证模块初始化不会因运行时能力缺失而失败。
5. 返回运行时版本，供前端保存后状态和回测提交快照使用。

静态分析不能证明所有动态分支都安全，因此运行期仍需分类错误；预检的作用是提前发现确定性问题，不得把不确定结果误报为错误。

### 4.3 Bar、L2 与 Worker 一致性

三条路径统一导入同一运行时契约：

- 标准 Bar 的 `BarStrategySession`；
- L2 的 `L2StrategySession`；
- 策略保存、预览或辅助执行使用的 `strategy-worker`。

任务领取时校验快照中的运行时版本是否为当前服务支持版本。不支持时直接返回 `runtime.version_mismatch`，不得继续执行或自动升级快照语义。

## 5. 后端错误转换

### 5.1 结构化诊断

策略子进程向父 Runner 返回内部诊断时，至少包含：

```text
exceptionType
missingName
callback
strategyLine
runtimeVersion
classification
```

`missingName` 只保存解析出的单个标识符，不携带源码行；`strategyLine` 只对当前任务的用户错误卡片可见，不进入长期脱敏统计。原始异常和堆栈继续仅用于短期容器日志或当前任务管理员诊断，不写入普通用户响应。

### 5.2 NameError 分类顺序

1. 若异常为 `UnboundLocalError`，映射为 `strategy.local_unbound`。
2. 若缺失名称属于明确禁止集合，映射为 `strategy.runtime_policy_blocked`。
3. 若缺失名称属于固定 Python 版本的标准内置集合，映射为 `runtime.contract_missing`。
4. 其余名称映射为 `strategy.undefined_name`。
5. 无法安全提取名称时保持受控的 `strategy.runtime_error`，但不得猜测责任或回显原始异常。

分类逻辑必须位于集中错误模块中，并由 Bar、L2、Worker 共用；前端不得通过中文消息或 `NameError` 字符串自行判断。

## 6. 前端提示修复

失败卡片继续消费 `errorDetail`，但根据稳定错误码显示不同责任：

### 6.1 平台运行环境问题

`runtime.contract_missing` 和 `runtime.version_mismatch` 显示：

> 回测因平台运行环境兼容问题未完成。无需修改当前策略，请提供任务编号联系管理员。

允许显示任务编号和平台支持建议，不显示 Python 堆栈、容器、内部地址或用户源码。

### 6.2 用户策略问题

- `strategy.undefined_name`：显示缺失名称、回调和行号，提示定义或导入。
- `strategy.local_unbound`：显示缺失名称、回调和行号，提示补齐所有分支的初始化。
- `strategy.runtime_policy_blocked`：明确说明平台禁止原因和替代方式，不使用“变量未定义”文案。

错误卡片标题不能只根据 `category === strategy_error` 二分；应使用错误码决定“用户可修改”或“平台需处理”的行动提示。

## 7. 脱敏运行环境错误统计

### 7.1 与现有错误日志的关系

现有 `system_error_log` 继续服务于“任务仍存在时的管理员诊断”，保持与 `backtest_run` 的级联删除关系，不保留已删除任务的源码、参数或原始堆栈。

新增独立的 `strategy_runtime_error_stat（策略运行环境错误统计）`。该表只用于识别平台运行时缺陷趋势，不关联任务、用户、方案、策略或回测结果，因此用户物理删除回测记录时不会级联删除统计。

### 7.2 最小数据模型

通过新的幂等迁移创建统计表，建议字段如下：

| 字段 | 约束 | 含义 |
| --- | --- | --- |
| `id` | 自增主键 | 内部统计记录标识，不承载业务身份 |
| `error_code` | 非空、受控枚举文本 | 仅允许运行环境错误码，例如 `runtime.contract_missing` |
| `runtime_version` | 非空、最大长度受限 | 发生错误时的固定策略运行时版本 |
| `missing_name` | 可空、Python 标识符格式、最大长度受限 | 缺失的标准内置名称，例如 `tuple` |
| `occurred_at` | 非空、服务器时间 | 错误发生时间 |

明确禁止新增下列字段：

- `run_id`、任务展示编号或其可逆映射；
- `owner_user_id`、用户名或角色；
- `config_id`、`strategy_id`、`strategy_version_id`；
- 标的、周期、日期、参数或行情信息；
- 源码、源码哈希、源码行、回调内容；
- 原始异常、堆栈、容器名、内网地址或凭据。

只有 `runtime.contract_missing`、`runtime.version_mismatch` 等平台运行环境错误写入该表。普通用户自定义变量错误不得把变量名写入长期统计；`missing_name` 仅在该名称属于固定 Python 标准内置集合时保存。

### 7.3 写入与读取权限

1. Runner 通过后端状态仓储插入受控记录，调用方不能自由提交任意错误正文。
2. 数据库启用 RLS；普通用户和普通接口无读取权限，仅管理员聚合接口可读。
3. 管理员接口默认按时间范围、错误码、运行时版本和缺失名称聚合数量，不返回用户或任务维度。
4. 前端管理员页面展示趋势和聚合次数，不提供源码或任务反查入口。
5. 统计默认保留 180 天，保留期通过服务器私有配置调整；清理只删除过期统计，不影响回测记录。

### 7.4 删除后的诊断边界

该统计可以回答“某运行时在什么时间反复缺失了哪些标准能力”，但不能在任务删除后还原某个任务的代码、参数或完整异常，也不能按已删除任务编号精确反查。这是物理删除与最小化留存共同决定的边界。

若管理员需要排查单个任务，应在用户删除前使用现有任务详情和 `system_error_log`；任务删除后只能依据脱敏统计识别重复平台问题，不能恢复已删除业务记录。

## 8. 数据库迁移与历史兼容

1. 新建下一编号的幂等迁移，不修改已执行的 `010`、`011` 等历史迁移。
2. 迁移只新增脱敏统计表、索引、RLS 策略和最小权限，不改变 `backtest_run` 与 `system_error_log` 的删除关系。
3. 不从现有容器日志或历史任务反向提取、补写统计，避免把未经分类的历史内容长期保存。
4. 历史任务缺少 `runtimeVersion` 时按 `legacy` 展示；不更新历史脚本快照。
5. 新错误码通过现有 JSON 结果字段兼容读取，不要求重写历史失败任务。

## 9. 实施步骤

### 阶段一：运行时契约与错误归责

1. 建立集中策略运行时契约模块和 `SCRIPT_RUNTIME_VERSION`。
2. 用固定 Python 标准内置环境替换逐项 `_SAFE_BUILTINS` 白名单，并保留明确产品禁止项。
3. 统一保存校验、Bar、L2 和 Worker 的运行时入口。
4. 将 `NameError` 拆分为四类稳定错误码，并修正用户提示。
5. 将运行时版本写入新任务快照和错误诊断。

### 阶段二：脱敏统计与管理员视图

1. 新建幂等数据库迁移和 `strategy_runtime_error_stat`。
2. 仅在平台运行环境错误发生时写入最小字段。
3. 增加管理员聚合查询和 180 天保留期清理。
4. 在管理员错误页面增加按错误码、运行时版本和缺失名称聚合的统计区域。

### 阶段三：隔离加固

1. 核对 Bar/L2 子进程能否读取父 Runner 的 `/proc`、文件、环境与网络服务。
2. 将策略执行身份降为非 root，并限制可见文件系统和临时目录。
3. 将策略执行网络与数据库、Redis、ClickHouse 和外网隔离。
4. 验证 CPU、内存、PID、超时和取消终止均由父 Runner 可靠执行。
5. 隔离未达标前，不把运行时描述为安全沙箱。

### 阶段四：文档、发布与观察

1. 更新《玄龄回测系统使用手册》的支持能力、禁止能力和错误责任说明。
2. 按服务器发布规则同批构建并发布数据库迁移、backend、strategy-worker、全部 Bar Runner、全部 L2 Runner 和 frontend。
3. 发布后观察 `runtime.contract_missing` 聚合；若继续出现标准内置缺失，视为发布阻断缺陷，不要求用户修改策略。

## 10. 测试与验收

### 10.1 运行时契约测试

1. 断言运行时使用固定 Python 版本的标准内置集合，不再依赖人工逐项添加常用函数。
2. 使用 `tuple`、`enumerate`、`zip`、`reversed`、`slice` 等代表性正常内置能力执行最小策略。
3. 明确禁止调用在保存阶段返回 `strategy.runtime_policy_blocked`，不返回 `NameError`。
4. 自定义未定义变量返回 `strategy.undefined_name`。
5. 条件分支未初始化局部变量返回 `strategy.local_unbound`。
6. 人工模拟标准内置能力缺失时返回 `runtime.contract_missing`，并标明用户无需修改策略。

### 10.2 Bar、L2 与前端测试

1. 相同脚本快照在普通 Bar 和 L2 中使用相同运行时版本并通过内置函数用例。
2. Bar 和 L2 子进程返回的错误码、缺失名称、回调和行号一致。
3. 前端将平台运行环境错误显示为平台责任，将真实未定义变量显示为用户策略错误。
4. 普通用户响应、浏览器控制台和任务结果中不包含原始堆栈、内部地址或凭据。
5. 历史失败任务仍按旧错误详情安全展示，不因新增字段无法读取。

### 10.3 脱敏统计测试

1. `runtime.contract_missing` 写入错误码、运行时版本、标准内置缺失名称和时间。
2. `strategy.undefined_name`、源码、参数、用户和任务编号不写入统计表。
3. 删除回测记录后，对应 `system_error_log` 继续级联删除，独立脱敏统计仍存在。
4. 普通用户无法读取统计；管理员只能读取聚合结果。
5. 超过保留期的统计可清理，未到期记录和业务回测不受影响。

### 10.4 隔离与资源测试

1. 策略无法获得数据库、Redis、ClickHouse、研究中心令牌或父 Runner 环境变量。
2. 策略无法访问宿主机业务目录或写入只读文件系统。
3. 策略无法直接连接数据库、行情网络或外网。
4. 无限循环、超大内存申请和子进程滥用分别受到时间、内存和 PID 限制。
5. 取消任务后策略子进程被终止，执行槽位按数据库终态释放。

### 10.5 远程普通用户样本回归

本改动影响策略保存、执行、错误转换和历史读取，必须按仓库规则执行远程普通用户最近两条回测样本回归：

1. 只读取得最近两条普通用户任务的冻结代码和运行快照，不输出或持久化用户源码。
2. 在隔离的正常 Bar/Worker 或 L2 执行链路中运行修改后的代码。
3. 覆盖提交、排队、领取、执行、最终结果及错误分类。
4. 至少补充一个 `tuple` 正常执行样本和一个平台运行时故障注入样本。
5. 验证完成后清理所有临时副本；远程条件不足时明确标记待验证。

## 11. 发布与回滚

### 11.1 发布前

1. 检查排队、运行中和取消中的 Bar/L2 任务；不得静默中断。
2. 在恢复的数据库副本验证新增迁移、RLS、物理删除和统计留存。
3. 核对各服务报告相同 `SCRIPT_RUNTIME_VERSION`。
4. 完成后端、前端、隔离和远程普通用户样本测试。

### 11.2 发布

通过 `scripts/deploy-server.sh` 同批发布迁移、backend、strategy-worker、全部 Bar Runner、全部 L2 Runner 和 frontend，不允许只重启某一个 Runner。发布后执行健康检查、代表性 Bar/L2 回测、失败提示检查、历史任务兼容检查和脱敏统计查询。

### 11.3 回滚

1. 运行时和错误分类可以软件回退，但已执行的数据库迁移不做破坏性逆迁移。
2. 新统计表在旧代码下保持闲置，不影响回测主链路。
3. 回退后不得删除已产生的脱敏统计；由正常保留期清理。
4. 若新运行时造成存量策略不兼容，停止新任务领取并回退所有相互依赖服务，不能只回退前端提示。

## 12. 验收标准

1. 任务 `7473a152-7340-4d0b-93a3-64042e1df4cb` 所代表的 `tuple()` 场景在 Bar 和 L2 中均可执行，不再出现 `NameError`。
2. 正常 Python 内置函数不需要逐个向平台申请添加。
3. 平台运行时缺陷、禁止行为、真实未定义名称和局部变量初始化错误具有不同稳定错误码和行动提示。
4. 平台问题明确显示“用户无需修改策略”，不再诱导用户反复修改正确代码。
5. 任务物理删除后不保留任务详情、源码、参数或原始堆栈，但管理员仍能通过脱敏统计发现重复运行环境缺陷。
6. Bar、L2、Worker 和保存预检使用同一运行时版本与错误分类。
7. 策略运行时隔离边界经过真实验证，文档表述与实际能力一致。
8. 不改变策略信号、成交、持仓、费用、净值和历史结果读取语义。

## 13. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 开放标准内置函数扩大当前运行能力 | 安全不依赖函数名单；先核对并加固进程、文件系统、网络、身份和资源隔离 |
| 禁止规则仍被动态导入绕过 | 禁止规则只作为产品契约；真正权限由容器和网络隔离阻断，不宣称 AST 是安全边界 |
| Python 或依赖升级改变策略结果 | 固定镜像、递增运行时版本、保留任务快照并执行新旧样本对照 |
| 错误继续误归责用户 | 集中分类并按固定 Python 内置集合判断；前端只依赖稳定错误码 |
| 长期统计泄露策略信息 | 只记录平台错误、标准内置缺失名称、版本和时间；无任务、用户、源码、参数和堆栈 |
| 删除任务后无法精确反查 | 明确这是物理删除边界；长期统计只支持趋势诊断，不承诺恢复单任务详情 |
| 新迁移影响生产删除链路 | 新表不引用 `backtest_run`，不修改现有外键；在生产副本先演练删除与留存 |
| 多服务运行时版本不一致 | 健康检查报告运行时版本，任务领取前校验，同批发布全部依赖服务 |

## 14. 自审结论

只补充 `tuple` 可以解决当前任务，但不能阻止下一次正常内置函数遗漏；把所有 `NameError` 继续视为用户错误也会重复误导。另一方面，仅把内置函数全部开放而不承认当前子进程仍共享 Runner 网络和文件系统，会制造虚假的安全感。

推荐一次完成三项契约：

1. 使用固定、版本化的正常 Python 运行时，停止逐项补内置函数。
2. 按责任拆分错误码和前端行动提示，平台缺陷不得要求用户改代码。
3. 用无任务关联的最小脱敏统计识别重复运行环境问题，同时保持用户回测记录的物理删除语义。

安全隔离应作为并行但不可省略的实施项，由操作系统和容器能力承担；函数名单只定义产品行为，不承担系统安全。
