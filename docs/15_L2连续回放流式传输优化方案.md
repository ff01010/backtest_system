# L2 连续回放流式传输优化方案

## 目标

在不改变用户脚本隔离边界、回放顺序、撮合规则和结果结构的前提下，减少连续三秒盘口回测中 `l2-runner` 与 `strategy-worker` 之间的 HTTP 往返次数。

## 已验证基线

- `quant.tick_quote` 的主键为 `trade_date, symbol, datetime`，单日单标的查询可命中主键。
- 13 个交易日、61,618 条快照的完整回测中，远程读取约 12.55 至 14.40 秒，原有 39 次分块 HTTP 调用约 4.06 秒。
- 时间游标分页比原有偏移分页慢，故不采用该改动。

## 设计

1. 连续回放以单个交易日为一个内部 HTTP 请求，使用 NDJSON 请求体逐块传输，不在任一进程中聚集全天快照。
2. 每条 NDJSON 记录沿用原有 `tradeDate`、`chunkNo`、`bars`、`quotes`、`trades` 结构；worker 仍以相同 `process_chunk` 调用处理，保证事件排序和策略状态语义不变。
3. runner 在生成每个数据块后续租并检查取消；worker 继续按会话、日期和块序号校验完整性。
4. 策略脚本仍只在 `strategy-worker` 中运行，不向 `l2-runner` 暴露脚本执行、数据库或 ClickHouse 凭据。
5. 性能新增 `transportMs` 与 `workerProcessingMs`，与 `sourceReadMs` 分开记录。

## 验收

1. 单元测试验证 NDJSON 解码、块序号校验及跨块策略状态保持。
2. 使用相同策略、标的和日期范围对比改造前后：订单、成交、信号、净值和收益必须一致。
3. 对比总耗时；若没有可重复的实际优化，不保留改动。
