# 历史回测信号明细批量导出方案

日期：2026-09-17
状态：已实施并完成本地验证；远程普通用户样本回归因 SSH 认证不可用待验证

## 1. 背景与问题结论

当前“信号明细”CSV 由前端根据正在查看的单条回测结果即时生成。用户必须先进入一条历史回测、打开“信号明细”，再点击导出；导出逻辑只认识当前页面中的 `result` 和信号筛选状态，后端没有信号明细导出接口，也没有批量导出任务。

“历史回测”页面已经有分页、搜索、标的筛选和行勾选，但现有勾选主要服务于批量删除，无法表达“跨页选择”或“选择当前筛选结果中的全部记录”。浏览器端也没有 ZIP 依赖。若前端逐条获取完整回测结果并在内存中打包，大批量导出会产生大量请求、重复传输和不可控的浏览器内存占用，页面关闭后任务也无法继续。

本方案在历史回测记录页面增加明确的“批量导出信号明细”能力。服务端异步任务固化选择范围，独立导出执行器逐条读取回测结果，按照现有 CSV 契约生成文件并写入 ZIP64。用户在同一页面的“信号明细导出记录”中查看进度和下载结果。

## 2. 目标、边界与不做事项

### 2.1 目标

1. 用户可以在历史回测页面手动跨页选择记录，或选择当前筛选条件下的全部可选择终态记录；系统再按第 3.1 节计算其中可导出的子集。
2. 不设置回测记录数量、信号行数或压缩包大小的业务上限；大任务通过排队、分批读取和异步执行完成。
3. 每条满足第 3.1 节资格的回测生成一个与现有导出类型、字段、顺序、取值和排序一致的 CSV；ZIP 只作为多个 CSV 的传输容器。
4. 创建、进度查看和下载入口都位于历史回测页面，并始终明确使用“信号明细”文案。
5. 页面刷新、退出页面或重新登录后，用户仍可查看自己的导出任务并下载未过期文件。
6. 历史回测列表继续只展示当前登录用户的数据；导出接口在此基础上独立校验任务和回测所有者，防止绕过页面直接构造请求。
7. 生成过程不占用 Bar/L2 回测执行槽位，不影响回测提交、撮合和结果语义。

### 2.2 已确认边界

- 内层文件继续使用 CSV，不新增 Excel、JSON 或其他明细格式。
- CSV 内容保持现有信号明细导出契约，不根据批量功能新增列、删除列或改变字段含义。
- 批量导出没有单独的信号筛选器。每条 CSV 等价于打开对应回测，将买卖方向、执行状态和盈亏状态均设为“全部”后执行现有导出。
- 支持跨页手动选择和“选择当前筛选结果中的全部可选择终态记录”，不限制为当前页或最多 50 条；最终导出数量以第 3.1 节资格判定为准。
- 下载按钮位于历史回测页面，按钮名称为“下载信号明细 ZIP”。
- 单选、多选、本页全选和当前筛选结果全选使用同一批量操作条；现有批量删除扩展为接受同一选择范围，但删除资格、确认要求和不可恢复语义不变。

### 2.3 不在本期范围内

1. 不修改回测引擎、策略运行时、撮合、费用、收益、信号或历史结果结构。
2. 不把导出任务纳入 Bar/L2 公平调度槽位，也不重新运行回测。
3. 不提供邮件、企业微信、浏览器系统通知或外部下载链接。
4. 不提供自定义 CSV 字段、字段顺序、编码、分隔符或压缩算法。
5. 不在 ZIP 中加入新的业务明细、统计报表或导出清单；任务摘要和排除原因只在页面展示。
6. 不修改 `package.json`，不引入浏览器端 ZIP 依赖。

## 3. 现有 CSV 契约

批量导出必须先把当前前端逻辑固化为可测试的导出契约。现有数据来源和转换规则如下：

1. 数据集合为 `result.trades` 与 `result.skippedSignals` 的拼接结果。
2. 按 `signalTime || time` 升序稳定排序；相同时间保持原集合中的相对顺序。
3. 默认包含已成交和已跳过信号，不应用页面临时筛选。
4. 文件使用 UTF-8 BOM，表头不加引号，数据单元格全部使用双引号包裹，内部双引号按两个双引号转义，行分隔符保持现有 `\n` 行为。
5. 字段和顺序固定为：

| 顺序 | 字段 | 现有取值规则 |
|---:|---|---|
| 1 | `signalTime` | 对 `signalTime || time` 调用现有 `formatSignalTime`：提取数字后，长度不少于 12 时输出 `YYYY-MM-DD HH:mm`，长度等于 8 时输出 `YYYY-MM-DD`，否则原样返回；空值输出 `-` |
| 2 | `executionTime` | 对 `executionTime || time` 使用相同的 `formatSignalTime` 规则 |
| 3 | `status` | `skipped` 映射为“已跳过”，其他状态映射为“已成交” |
| 4 | `direction` | 原始 `direction` |
| 5 | `side` | 原始 `side` |
| 6 | `action` | `action || direction` |
| 7 | `price` | 原始价格 |
| 8 | `priceSource` | 原值为空时使用“成交模型价格” |
| 9 | `quantity` | 原始数量 |
| 10 | `pnl` | 使用下述闭环收益规则；不适用时为空字符串 |
| 11 | `researchSignalId` | 原值为空时为空字符串 |
| 12 | `researchSignalAction` | 原值为空时为空字符串 |
| 13 | `researchSignalEffectiveAt` | 原值为空时为空字符串 |
| 14 | `note` | 原始说明文本 |

闭环收益规则固定为现有 `getClosedLoopTradePnl` 行为：`status` 有值且不等于 `filled` 时为空；底仓增强策略仅在 `cycleEffect` 为 `partial_close`、`close` 或 `reverse` 且 `realizedOverlayPnl` 是有限数值时输出该值；方向性持仓策略取 `action || direction` 转大写，动作匹配 `CLOSE|COVER|STOP|FORCE` 时输出有限数值 `pnl`，不匹配且 `pnl=0` 时为空，其余有限数值 `pnl` 原样输出。策略类别先按 `result.strategyCategory`、`result.experimentManifest.strategyCategory`、回测请求快照 `strategyCategory` 的顺序取第一个非空值；该值不属于 `core_position_overlay/directional_holding` 或三者均为空时，若请求快照 `baseQuantity>0` 或 `t0Enabled=true` 则取 `core_position_overlay`，否则取 `directional_holding`。

服务端实现前必须从当前前端函数生成固定输入和期望 CSV 字节，保存为仓库内唯一黄金样本 `shared/fixtures/signal_detail_csv_cases.json`；期望字节使用 Base64 保存，避免 JSON 文本转义或换行转换掩盖 BOM 差异。前端纯函数测试和后端序列化测试读取同一份样本；样本至少覆盖整数、小数、负数、零、科学计数法边界、空字符串、中文、逗号、双引号和单元格内换行。后端数字文本必须与 JavaScript `String(number)` 的黄金结果一致，不得直接假定 Python `str(float)` 在所有边界上等价。

### 3.1 可导出资格

一条历史回测只有同时满足以下条件才属于“信号明细可导出记录”：

1. 数据库状态为 `succeeded`；接口返回前端时该状态仍按现有映射显示为 `ok`，前端映射不是第二个资格条件。
2. 数据库 `result_json` 非空且为 JSON 对象。`NULL` 归为 `result_missing`，非对象 JSON 或归一化异常归为 `result_incompatible`。
3. 若 `fill_model=l2_quote`，先调用当前历史详情读取使用的 `normalize_l2_result(result_json, requested_params)`；其他模式直接使用现有统一结果。归一化后的 `trades` 必须为数组，`skippedSignals` 不存在时按空数组处理，存在时必须为数组。
4. 归一化后的 `trades` 与 `skippedSignals` 合计至少一条。当前单条导出在零行时按钮禁用，因此零信号回测不生成表头空文件，而是计入排除原因 `no_signal_details`。

排除原因固定为：

| 原因码 | 含义 |
|---|---|
| `run_not_succeeded` | 回测不是成功终态 |
| `result_missing` | 成功回测没有 `result_json` |
| `result_incompatible` | `trades` 或 `skippedSignals` 不符合上述兼容结构 |
| `no_signal_details` | 成交与跳过信号合计为零 |

执行器准备阶段和生成阶段必须调用同一个后端资格判定函数，不得分别实现两套条件。L2 原始结果在资格判定和 CSV 生成前必须经过 `state_store.get_backtest_run` 当前使用的同一结果归一化函数，不能直接按数据库原始 JSON 的键名判断或导出。

## 4. 用户交互设计

### 4.1 页面入口

历史回测页面顶部操作区增加固定入口：

```text
历史回测
[搜索] [标的筛选] [只看收藏]                  [信号明细导出记录]
```

“信号明细导出记录”打开页面内抽屉，不新增独立导航页面。存在 `queued/preparing/running/cancelling` 任务时显示活动数量；存在 `succeeded` 且 `last_downloaded_at` 为空的任务时显示完成标记，该标记只表示用户尚未发起过下载。

### 4.2 选择模型

页面对用户只呈现一个“已选择记录”概念。单条勾选、多条勾选、本页全选和当前筛选结果全选都进入同一个选择状态并使用同一批量操作条；`ids/filter` 只是前后端传输选择范围的内部实现，页面不得要求用户理解这两个模式。

前端内部允许使用以下两种数据表示，但不得把它们做成两套用户交互：

1. **明确 ID 集合**：单条、多条和本页全选都将对应 ID 加入集合；翻页后已选记录继续保留。表头复选框只负责把当前页可选择 ID 全部加入或移出集合，不清除其他页已选 ID。
2. **当前筛选结果集合**：当当前页可选择记录已全部选中且服务端 `selectableTotal` 大于当前已选数量时，页面显示“选择当前筛选结果中的全部 126 条”；用户点击后，前端保存筛选条件和后续取消的例外 ID，不枚举并传输全部 ID。

`GET /api/backtest/runs` 在现有分页响应中新增 `selectableTotal`，按当前关键词、标的、方案和收藏筛选统计状态为 `succeeded/failed/cancelled` 的本人记录数，不读取 `result_json`。`queued/running/cancelling` 不可选择；前端与后端使用同一显式状态集合，不能让导出逻辑依赖删除函数。

明确 ID 集合的页面选择数为去重后的 ID 数量；切换到当前筛选结果集合时，以当时的 `selectableTotal - excludedRunIds.length` 显示页面选择数。列表自动刷新造成候选集合变化时，页面数量只作选择状态提示；执行操作前后端返回的 `selectedRunCount` 才是权威数量。导出准备完成后，`totalRunCount` 表示其中满足第 3.1 节的记录数，`excludedRunCount = selectedRunCount - totalRunCount`。准备阶段二者为 `null`，页面不得用 0 代替“尚未计算”。

当前筛选包括关键词、标的、方案和“只看收藏”等服务端分页条件。用户修改任一筛选条件时，页面清除全部选择并提示“筛选条件已变化，请重新选择”，避免隐藏记录仍被批量操作；翻页和调整当前页码不清除选择。

任务创建接口在同一数据库事务中解析选择条件、校验所有者并固化任务项。任务创建后，即使页面筛选或历史列表发生变化，本次导出范围也不再变化。

### 4.3 批量操作条

只要至少选中一条可选择记录，无论来自单选、多选、本页全选还是当前筛选结果全选，都显示同一个批量操作条：

```text
已选择 126 条
[取消选择] [批量导出信号明细] [删除所选]
```

本页全选但尚未选择全部筛选结果时，在操作条上方显示二段式提示：

```text
本页 50 条可操作记录已全部选择。选择当前筛选结果中的全部 126 条
```

点击后提示改为“已选择当前筛选结果中的全部 126 条”；用户随后取消某些行时，已选择数量实时减少，重新勾选时恢复。用户不需要知道当前选择在前端保存为 ID 还是筛选条件。

导出和删除使用各自的资格判断：

- “批量导出信号明细”只处理满足第 3.1 节全部条件的记录。
- 不满足条件的本人记录仍保留为任务候选项，但不写入 ZIP；准备阶段按固定原因码汇总到排除数量，页面在准备完成后展示各原因的中文数量摘要。
- 页面在准备完成后明确提示本次导出数量和排除数量，不得静默遗漏。
- 没有选中记录时禁用“批量导出信号明细”；候选记录全部不满足导出资格时，任务以 `no_exportable_runs` 失败并展示固定提示。
- “删除所选”对四种选择方式都可用。点击后先由服务端核对选择快照，再显示“将永久删除 126 条历史回测，删除后无法恢复”；确认后按同一快照执行，不得因为选择来自当前筛选结果全选而退化为只删除当前页。

`selectableTotal` 只统计可选择记录，不扫描导出资格。前端不得根据当前页数据推算跨页可导出数量，也不新增会重复扫描完整结果的资格预览请求。第 8.1 节创建接口只固化候选记录，不读取 `result_json`；执行器准备完成后返回的 `totalRunCount` 与 `exclusionSummary` 才是本次任务的最终导出范围。

### 4.4 任务进度与下载

点击“批量导出信号明细”后，创建接口完成候选记录固化即返回任务编号，既不读取完整结果也不等待 ZIP 生成。页面先显示“正在准备信号明细：68 / 126”，准备完成后显示：

```text
正在生成信号明细：68 / 120
```

用户可以继续操作、关闭抽屉或离开页面。任务完成后，历史回测页面显示：

> 120 条回测的信号明细已生成，可在“信号明细导出记录”中下载。

导出记录抽屉包含：

| 创建时间 | 导出范围 | 选中数量 | 导出数量 | 状态 | 文件有效期 | 操作 |
|---|---|---:|---:|---|---|---|
| 2026-09-17 15:30 | 当前筛选全部 | 126 | 120 | 已完成 | 24 小时后过期 | 下载信号明细 ZIP |
| 2026-09-17 15:25 | 当前筛选全部 | 126 | 计算中 | 准备中 68/126 | -- | 取消生成 |
| 2026-09-17 15:20 | 手动选择 | 32 | 32 | 生成中 18/32 | -- | 取消生成 |
| 2026-09-17 14:50 | 手动选择 | 8 | 8 | 失败：导出存储暂不可用 | -- | 重新导出 |

状态和操作规则：

- `queued`：显示“等待生成”，允许取消。
- `preparing`：显示已核对候选回测数和选择数，导出数量显示“计算中”，允许取消；取消在当前候选资格判断完成后生效。
- `running`：显示已处理回测数和总数，允许取消；取消在当前 CSV 完成后生效。
- `cancelling`：显示“正在取消”，不重复显示取消按钮，也不再开始下一条候选或 CSV。
- `succeeded`：显示文件大小、过期时间和“下载信号明细 ZIP”。
- `failed`：按第 9.2 节固定错误文案显示原因；只有第 8.4 节列出的瞬时错误显示“重新导出”，源数据类错误提示用户返回历史列表重新选择。
- `cancelled`：不保留可下载文件，允许重新导出。
- `expired`：正常到期显示“文件已过期”；`error_code=artifact_missing` 时显示“信号明细文件不可用”。两者均禁用下载并允许重新导出。

前端在历史回测页面可见且存在 `queued`、`preparing`、`running` 或 `cancelling` 任务时每 3 秒查询一次；页面不可见或离开历史回测页面时停止轮询，重新获得焦点或打开抽屉时立即查询一次。没有活动任务时不定时轮询。下载使用浏览器正常文件下载，不把 ZIP 内容读入前端内存。

## 5. ZIP 组织与文件命名

外层文件名：

```text
信号明细批量导出_20260917_153000.zip
```

ZIP 内只建立一个固定的 `信号明细` 目录。每条 CSV 使用标的、回测冻结快照中的策略方案名称和回测编号命名：

```text
信号明细批量导出_20260917_153000.zip
└── 信号明细/
    ├── 600000.SH_均线策略_1024.csv
    ├── 600000.SH_均线策略_1025.csv
    └── 688981.SH_网格策略_1026.csv
```

内层目录名固定为 `信号明细`，CSV 基础名固定为 `<symbol>_<params_snapshot.name>_<display_no>.csv`。策略方案名称只读取回测创建时写入的不可变 `params_snapshot.name`，不得查询当前 `strategy_config`；因此方案后续改名或删除不影响文件名。回测缺少冻结方案名称属于快照契约异常，任务失败，不使用“未绑定方案”等兜底名称。标的和方案名称中的控制字符及 Windows 非法文件名字符替换为下划线，并清理首尾空格、点和下划线；中文保留。所有名称只从已固化的回测字段生成，不接受客户端提供的路径或文件名。ZIP 条目使用 UTF-8 文件名标志，外层下载名通过 RFC 5987 `filename*` 返回。打包使用 Python 标准库 `zipfile.ZipFile(..., compression=ZIP_DEFLATED, compresslevel=6, allowZip64=True)`，每个未知最终长度的 CSV 条目使用 `ZipFile.open(..., mode="w", force_zip64=True)` 逐行写入，不在内存中同时保存全部 CSV。外层文件名时间取任务 `created_at` 转为 `Asia/Shanghai` 后的 `YYYYMMDD_HHMMSS`；实际存储键仍以任务 UUID 区分，同秒创建不会互相覆盖。

ZIP 中只包含信号明细 CSV，不加入新的 README、清单或错误文件。选择摘要、排除数量和失败原因保存在任务记录并展示在页面，避免改变用户已确认的导出类型和内容边界。

## 6. 总体架构

```text
历史回测页面
    │ 创建任务 / 查询进度 / 下载
    ▼
backend API
    │ 固化选择范围、鉴权、记录任务
    ▼
PostgreSQL 导出任务与任务项
    │ 租约领取
    ▼
signal-export-runner
    │ 逐条读取 result_json
    │ 准备阶段归类可导出与排除记录
    │ 按现有契约生成 CSV
    │ 逐条写入 ZIP64 .part 文件
    ▼
共享 artifacts 卷
    │ 原子改名并记录摘要
    ▼
backend 鉴权下载
```

新增独立 `signal-export-runner` 服务，使用 backend 镜像运行 `python -m backend.signal_export_runner`。它与 backend 共享 `/runtime/artifacts` 命名卷，但不连接行情源、不调用策略 Worker，也不占用 `backtest_execution_slot`。

导出执行器采用数据库租约领取任务。一个任务由一个执行器完整生成；同一任务租约过期后允许其他实例重试。重试从新的 `.part` 文件重新生成，成功后使用原子改名替换正式文件，避免下载到损坏或半成品 ZIP。

不设置任务包含记录数或信号数的业务上限。资源控制采用：

- 每次只读取一条回测结果并完成对应 ZIP 条目后释放对象；峰值内存随单条回测结果大小增长，而不是随任务总记录数增长。
- 多个导出任务进入队列。领取候选先包含每个所有者租约已过期且未达到尝试上限的唯一 `preparing/running` 任务；没有活动任务的所有者再取其最早的 `queued` 任务。全局先按过期租约的 `lease_expires_at, id` 恢复中断任务，再按排队任务的 `created_at, id` 领取新任务；租约仍有效或正在取消的所有者不领取新任务。因此同一用户同时只运行一个导出任务，且中断任务不会被同用户的新任务越过。
- 首期部署一个 `signal-export-runner` 容器，单进程一次处理一个任务。后续可以横向增加容器，但上述数据库领取条件继续保证单用户并发为 1；该并发约束只控制资源，不限制单个任务的记录数。
- 开始生成前确认受控存储目录可写且剩余空间不少于保留水位；生成每个 ZIP 条目前再次检查。低于水位时任务以 `storage_unavailable` 失败并删除 `.part` 文件。磁盘不足属于运行条件失败，不是业务数量限制。
- 成功文件默认保留 24 小时，到期后清理文件并将任务标记为 `expired`。

配置项和首期默认值固定为：

| 环境变量 | 默认值 | 启动校验 |
|---|---:|---|
| `TREND_GRID_SIGNAL_EXPORT_POLL_SECONDS` | `2` | `0.2` 至 `10` 秒 |
| `TREND_GRID_SIGNAL_EXPORT_LEASE_SECONDS` | `90` | `30` 至 `600` 秒 |
| `TREND_GRID_SIGNAL_EXPORT_HEARTBEAT_SECONDS` | `10` | `1` 至租约秒数的三分之一 |
| `TREND_GRID_SIGNAL_EXPORT_CLEANUP_SECONDS` | `300` | `60` 至 `3600` 秒 |
| `TREND_GRID_SIGNAL_EXPORT_RETENTION_HOURS` | `24` | `1` 至 `168` 小时 |
| `TREND_GRID_SIGNAL_EXPORT_TASK_RETENTION_DAYS` | `30` | `7` 至 `365` 天 |
| `TREND_GRID_SIGNAL_EXPORT_MIN_FREE_BYTES` | `1073741824` | 不小于 `268435456` 字节 |
| `TREND_GRID_SIGNAL_EXPORT_STALE_PART_HOURS` | `1` | `1` 至 `24` 小时 |
| `TREND_GRID_SIGNAL_EXPORT_MAX_ATTEMPTS` | `3` | `1` 至 `10` 次 |

所有配置有上述安全默认值；部署脚本不得把仓库示例配置覆盖到服务器 `deploy/.env`。

## 7. 数据模型与迁移

新增幂等迁移 `040_backtest_signal_detail_exports.sql`。迁移不得修改既有迁移文件。

### 7.1 导出任务表

新增 `backtest_signal_detail_export`：

| 字段 | 说明 |
|---|---|
| `id` | 导出任务 UUID |
| `owner_user_id` | 任务所有者 |
| `selection_mode` | `ids` 或 `filter` |
| `selection_snapshot` | 创建时的筛选条件、排除 ID 和重试来源，不包含信号数据 |
| `idempotency_key`、`request_hash` | 防止创建或重试请求因网络重放生成重复任务 |
| `status` | `queued/preparing/running/succeeded/failed/cancelling/cancelled/expired` |
| `selected_run_count` | 用户选择范围内的记录数 |
| `prepared_run_count` | 准备阶段已完成资格判断的候选记录数 |
| `total_run_count` | 准备完成后的可导出记录数；准备完成前为 `NULL` |
| `processed_run_count` | 已写入 ZIP 的记录数 |
| `excluded_run_count` | 准备完成后的排除记录数；准备完成前为 `NULL` |
| `exclusion_summary` | 准备完成后按第 3.1 节原因码汇总的排除数量 JSON 对象；准备完成前为 `NULL` |
| `cancel_requested` | 是否请求取消 |
| `attempt_no`、`attempt_token` | 重试次数和本次租约令牌 |
| `worker_id`、`lease_expires_at` | 执行器和租约信息 |
| `storage_key` | 受控附件目录中的相对路径；成功前为空 |
| `download_filename` | 系统生成的下载文件名 |
| `byte_size`、`content_sha256` | 成功文件大小和摘要 |
| `error_code`、`error_message` | 对用户安全的失败分类和提示 |
| `last_downloaded_at` | 最近一次开始下载的时间；为空时显示“尚未发起下载”完成标记，不用于判断浏览器是否完整保存文件 |
| `created_at`、`started_at`、`finished_at`、`expires_at`、`updated_at` | 生命周期时间 |

表约束和索引固定为：

- `id uuid PRIMARY KEY`；`owner_user_id` 外键指向 `app_user(id) ON DELETE CASCADE`。
- `selection_snapshot` 必须为 JSON 对象；`exclusion_summary` 为空或 JSON 对象。
- `selected_run_count > 0`，其他非空计数字段均大于等于 0，`prepared_run_count <= selected_run_count`。状态为 `running/succeeded/expired`，或 `failed` 且错误码为 `no_exportable_runs` 时，`total_run_count`、`excluded_run_count` 和 `exclusion_summary` 必须非空，并满足 `selected_run_count = total_run_count + excluded_run_count`、`processed_run_count <= total_run_count`；准备期间取消、源记录消失或执行器连续中断时，这三个准备结果字段允许为空。
- 所有状态值和 `selection_mode` 使用 CHECK 约束。
- 所有者列表索引为 `(owner_user_id, created_at DESC, id DESC)`。
- `(owner_user_id, idempotency_key)` 唯一；同一键和同一请求摘要返回原任务，同一键和不同摘要返回 409。
- 增加 `(owner_user_id)` 的部分唯一索引，条件为 `status IN ('preparing', 'running', 'cancelling')`，从数据库层保证同一用户最多一个活动执行任务；领取逻辑遇到并发唯一冲突时放弃该候选并继续领取其他所有者任务。
- 新任务领取索引为 `(created_at, id) WHERE status='queued'`；租约恢复索引为 `(lease_expires_at, id) WHERE status IN ('preparing', 'running')`；过期清理索引为 `(expires_at, id) WHERE status='succeeded'`。

状态只能按下列方向转换；迁移中的状态转换触发器拒绝图外转换，执行器更新还必须同时匹配当前 `attempt_token`：

```text
queued ──→ preparing ──→ running ──→ succeeded ──→ expired
   │            │           │  └──→ failed
   │            │           └────→ cancelling ──→ cancelled
   │            ├───────────────→ failed
   │            └───────────────→ cancelling ──→ cancelled
   └──────────────────────────────────────────→ cancelled

preparing/running ──租约过期且未达到最大尝试次数──→ preparing
```

租约接管回到 `preparing` 的转换只能由后台领取函数执行，并且必须同时确认旧租约已过期；普通状态更新接口不能触发该转换。

`expires_at` 在成功完成时设置为 `finished_at + TREND_GRID_SIGNAL_EXPORT_RETENTION_HOURS`；首期默认 24 小时，失败和取消任务不设置。下载不会延长有效期。

### 7.2 导出任务项表

新增 `backtest_signal_detail_export_item`：

| 字段 | 说明 |
|---|---|
| `export_id` | 所属导出任务 |
| `ordinal` | ZIP 内稳定顺序，从 1 开始 |
| `source_run_id` | 创建任务时固化的回测 UUID |
| `display_no` | 创建任务时固化的回测编号，用于 CSV 文件名 |
| `symbol`、`start_date`、`end_date` | 创建任务时固化的文件命名信息 |
| `qualification_status` | `pending/included/excluded`；创建时为 `pending` |
| `exclusion_reason` | 被排除时填写第 3.1 节原因码，否则为空 |

任务项主键为 `(export_id, ordinal)`，`export_id` 外键指向任务表并 `ON DELETE CASCADE`，同时增加 `(export_id, source_run_id)` 唯一约束和 `(export_id, qualification_status, ordinal)` 扫描索引。手动和筛选模式都在固化候选后按 `display_no ASC, source_run_id ASC` 分配 `ordinal`，不得使用客户端传入顺序决定 ZIP 顺序。

任务项只固化候选选择、命名信息和资格结果，不复制 `result_json`。`source_run_id` 不使用会阻止历史回测删除的外键；若回测在准备完成前已删除，按 `source_changed` 使任务整体失败；若在准备完成后、ZIP 生成前被删除或结果损坏，同样整体失败且不产生可下载 ZIP，避免静默生成不完整压缩包。

任务创建使用 `REPEATABLE READ` 事务：先处理幂等键，再在同一快照内解析选择，并通过 `INSERT ... SELECT` 固化处于可选择终态的候选任务项，提交后才返回任务编号；创建阶段只读取回测 ID 和命名字段，不读取或归一化 `result_json`。序列化冲突最多自动重试 3 次，仍失败时返回 409。筛选模式必须复用历史分页的公共过滤构造器；手动模式将去重后的 ID 每 500 个一批核对所有者和固化。创建后由执行器每次读取一条候选结果并调用第 3.1 节资格函数，不得把全部 `result_json` 同时加载到内存，也不得仅用 SQL 判断 L2 原始 JSON 是否存在 `trades`。

正常页面只能从当前用户的历史回测列表产生选择，不存在跨用户选择入口。后端仍不能把页面过滤当作授权依据：明确 ID 集合中的每个 `runIds` ID 都要按当前登录用户重新查询；只要存在无法访问或不存在的 ID，就以统一 404 拒绝整次操作，不返回具体无效 ID。属于本人但状态不在 `succeeded/failed/cancelled` 的明确 ID 不得被静默忽略，公共解析器拒绝整次操作并提示选择中包含不可操作记录。导出创建接口将该错误映射为 `signal_export.selection_invalid`，选择确认和删除接口映射为 `backtest.selection_invalid`；未按当前用户查到 ID 时也分别映射为第 8.6 节对应的 `signal_export.not_found` 或 `backtest.not_found`。筛选表示中的 `excludedRunIds` 只作为本人筛选结果的集合差运算，未匹配到本人结果的值直接忽略，既不报错也不回显。不满足第 3.1 节资格的本人候选项在准备阶段计入 `excluded_run_count`，未按当前用户查询到的记录不得进入选择数、排除数或任务项。

任务表和任务项表启用并强制 RLS：任务表以 `owner_user_id=app.current_user_id() OR app.current_is_admin()` 为读写条件；任务项不重复保存所有者，其策略通过 `EXISTS` 关联任务表并使用相同所有者条件。API 层仍必须显式带 `owner_user_id=current_user_id()` 查询，不能仅依赖管理员可见性。后端收到直接构造的任务 ID 时按当前用户查询，未匹配统一返回 404，避免通过错误差异判断资源是否存在。执行器沿用现有非 HTTP 进程的管理员默认上下文，但领取、进度、完成和清理写入只能经 `state_store` 中校验 `attempt_token` 的专用函数，不提供客户端可调用的任意状态、存储路径或文件摘要更新接口。

上述所有者校验不是新增“查看他人回测”场景，也不要求增加管理员导出页面；正常历史回测页面仍只展示本人记录。它只约束用户绕过页面、直接构造 API 请求时的服务端行为。

### 7.3 导出执行器健康表

现有 `backtest_runner_health.job_kind` 只允许 `bar` 和 `l2`，本功能不得修改该约束或把导出执行器伪装成回测执行器。迁移新增独立的 `backtest_signal_detail_export_runner_health`：`worker_id varchar(128) PRIMARY KEY`、`status varchar(16)`、`current_export_id uuid NULL`、`last_error_code varchar(128) NULL`、`started_at timestamptz`、`heartbeat_at timestamptz`。`current_export_id` 外键指向导出任务并 `ON DELETE SET NULL`，状态 CHECK 限定为 `ready/running/error`，增加 `(status, heartbeat_at DESC)` 索引。该表与现有健康表策略一致：`SELECT USING (true)`，写入只允许管理员上下文；backend 健康检查只统计 30 秒内 `ready/running` 状态的新鲜心跳。

## 8. 后端接口契约

### 8.1 创建任务

```http
POST /api/backtest/signal-detail-exports
Content-Type: application/json
Idempotency-Key: 客户端生成的 UUID
```

手动选择：

```json
{
  "selection": {
    "mode": "ids",
    "runIds": ["uuid-1", "uuid-2"]
  }
}
```

筛选全选：

```json
{
  "selection": {
    "mode": "filter",
    "query": "候选",
    "symbol": "600000.SH",
    "configId": null,
    "favoritesOnly": true,
    "excludedRunIds": ["uuid-3"]
  }
}
```

响应：

```json
{
  "export": {
    "id": "export-uuid",
    "status": "queued",
    "selectedRunCount": 126,
    "preparedRunCount": 0,
    "totalRunCount": null,
    "processedRunCount": 0,
    "excludedRunCount": null,
    "exclusionSummary": null,
    "createdAt": "2026-09-17T15:30:00+08:00"
  }
}
```

候选记录数为 0 时不创建空任务，返回 422 和“当前选择中没有可处理的终态回测”。任务准备后若 `totalRunCount=0`，任务进入 `failed`，错误码为 `no_exportable_runs`，不创建 ZIP。前端每次用户主动创建生成一个 UUID 作为 `Idempotency-Key`，同一网络重试复用该键；用户再次主动导出生成新键。接口不得接受客户端提供的所有者、存储路径、文件名或进度字段。

`ids` 模式的 `runIds` 去重后不得为空；`filter` 模式只接受当前历史分页已有的 `query`、`symbol`、`configId`、`favoritesOnly` 和 `excludedRunIds` 字段，未知字段按 422 拒绝。两种模式都不设置 ID 数量或筛选命中数量的业务上限。

计算 `request_hash` 前，手动模式对 UUID 去重并排序；筛选模式对空白字符串、空值、布尔值和 `excludedRunIds` 去重排序后规范化，再使用稳定 JSON 编码计算 SHA-256。不得直接对客户端原始 JSON 文本计算摘要。

接口先用当前用户、幂等键和 `request_hash` 查询已有任务：匹配时直接返回原任务，不受此刻执行器健康状态影响；冲突时返回 409。只有确认为新请求后才检查 30 秒内执行器心跳，无可用执行器时返回 503 且不写任务。

### 8.2 统一选择下的批量删除

用户点击“删除所选”时，页面先用公共选择结构获取服务端确认快照：

```http
POST /api/backtest/runs/selection-summary
Content-Type: application/json
```

响应包含 `selectedRunCount` 和 `selectionDigest`。`selectionDigest` 固定为服务端按 `backtest_run.id ASC` 流式读取本次选择的 UUID，并对逐个 UUID 的规范 ASCII 文本及换行符计算 SHA-256；计算不读取 `result_json`，也不把全部 ID 同时加载到应用内存。页面拿到响应后才用 `selectedRunCount` 展示删除确认框。

现有批量删除接口保持向后兼容：原 `{ "runIds": [...] }` 请求及最多 100 个 ID 的既有约束继续有效；新页面统一选择流程发送与导出一致的公共选择结构：

```http
DELETE /api/backtest/runs
Content-Type: application/json
```

```json
{
  "selection": {
    "mode": "filter",
    "query": "候选",
    "symbol": "600000.SH",
    "configId": null,
    "favoritesOnly": true,
    "excludedRunIds": ["uuid-3"]
  },
  "expectedSelectedRunCount": 126,
  "expectedSelectionDigest": "sha256-hex"
}
```

`backend/schemas.py` 定义公共 `BacktestRunSelection` 联合类型，导出创建、选择确认和批量删除共同使用；`state_store` 提供唯一的选择解析函数，按当前用户、筛选条件、排除 ID 和 `succeeded/failed/cancelled` 状态解析记录。新公共选择的 `ids` 表示不沿用旧接口的 100 个 ID 业务上限，服务端去重后分批校验；`filter` 表示也不限制命中条数。

删除接口使用 `REPEATABLE READ` 事务，把本次解析出的 `backtest_run.id` 写入事务级临时表并锁定对应源记录，再按临时表计算数量和摘要；实际数量或摘要与确认快照不同则返回 `409 backtest.selection_changed`，不删除任何记录，前端保留选择并要求用户重新确认。两者一致时只通过该临时表执行删除并返回 `deleted`，不得在删除语句中再次单独解释筛选条件。因此即使确认与提交之间记录数量碰巧不变但成员发生替换，或删除事务期间又出现新的匹配记录，也不会删除用户未确认的集合。

手动 ID 模式仍逐个按当前用户核对；包含不存在或无权访问的 ID 时沿用统一 404。筛选模式始终带 `owner_user_id=current_user_id()`，不得接受客户端所有者字段。删除成功后清空选择并刷新历史分页；删除失败或数量变化时保留选择，便于用户核对后重试。

### 8.3 列表与详情

```http
GET /api/backtest/signal-detail-exports?limit=20&cursor=...
GET /api/backtest/signal-detail-exports/{export_id}
```

列表 `limit` 允许 1 至 100，默认 20；游标是服务端编码的 `(created_at, id)`，按 `created_at DESC, id DESC` 稳定翻页，响应包含 `items`、`nextCursor`、`activeCount` 和 `undownloadedSucceededCount`。`activeCount` 统计当前用户全部 `queued/preparing/running/cancelling` 任务，`undownloadedSucceededCount` 统计当前用户全部未过期、`last_downloaded_at IS NULL` 的 `succeeded` 任务，两个汇总不受当前分页游标和 `limit` 影响。列表只返回当前用户任务。详情返回状态、选择摘要、计数、文件信息、过期时间和固定错误提示，不返回服务器绝对路径、回测结果或信号内容。

### 8.4 取消与重新导出

```http
POST /api/backtest/signal-detail-exports/{export_id}/cancel
POST /api/backtest/signal-detail-exports/{export_id}/retry
```

- 取消接口幂等：排队任务直接进入 `cancelled`；已经处于任一终态时返回当前状态，不报错也不反向转换。
- `preparing` 或 `running` 任务设置 `cancel_requested` 并进入 `cancelling`；执行器完成当前候选资格判断或 ZIP 条目后停止，删除 `.part` 文件并进入 `cancelled`。
- 重试请求同样携带新的 `Idempotency-Key`；网络重试复用该键。重试克隆原任务全部候选任务项，不重新执行筛选，也不加入原任务创建后出现的新回测；新任务把所有项的资格状态重置为 `pending`，重新执行准备阶段，`selection_snapshot.retrySourceExportId` 记录来源。`cancelled` 和 `expired` 可以重试；`failed` 中只有 `storage_unavailable`、`archive_failed`、`runner_interrupted` 三类瞬时错误显示“重新导出”。`source_changed`、`result_incompatible`、`no_exportable_runs` 和 `internal_error` 不允许原任务重试，页面提示用户返回历史列表重新选择或联系管理员。`succeeded` 且未过期的任务只提供下载，不提供重试。旧任务保持原状态用于审计。

### 8.5 下载

```http
GET /api/backtest/signal-detail-exports/{export_id}/download
```

下载接口要求任务属于当前用户、状态为 `succeeded`、未过期，且文件存在并与记录中的 `byte_size` 一致。`content_sha256` 在执行器完成文件时计算，下载响应使用 `ETag: "<content_sha256>"` 强校验值，不在每次下载前重复扫描整个大文件。完整下载返回 `200 application/zip`、安全的 `Content-Disposition`、`Content-Length`、`Accept-Ranges: bytes` 和 `ETag`；单个合法字节区间返回 206 和正确的 `Content-Range`，无效区间或多区间请求返回 416。任务未完成返回 409，文件已过期返回 410，其他用户或不存在统一返回 404。文件缺失或大小不一致时，将任务标记为 `expired`、记录 `artifact_missing`，返回 410 并写入管理员诊断日志，不继续发送文件。

开始返回文件时更新 `last_downloaded_at`。该字段只用于页面提示，不作为文件完整下载的证明；用户在有效期内可以重复下载。

所有任务查询和下载响应设置 `Cache-Control: private, no-store`。访问日志不得记录选择中的回测参数、信号内容或服务器存储路径。

### 8.6 稳定错误响应

| HTTP | 错误码 | 场景 |
|---:|---|---|
| 422 | `signal_export.selection_invalid` | 选择模式、筛选字段、幂等键格式错误，或没有可处理的终态候选记录 |
| 404 | `signal_export.not_found` | 回测或导出任务未按当前用户查询到 |
| 409 | `signal_export.state_conflict` | 当前状态不允许所请求操作 |
| 409 | `signal_export.idempotency_conflict` | 同一幂等键对应不同请求 |
| 410 | `signal_export.file_unavailable` | 文件已到期、缺失或大小不一致 |
| 503 | `signal_export.runner_unavailable` | 没有 30 秒内新鲜的执行器心跳 |
| 422 | `backtest.selection_invalid` | 公共选择为空、字段无效或明确 ID 中包含不可操作状态 |
| 404 | `backtest.not_found` | 明确 ID 未按当前用户查询到 |
| 409 | `backtest.selection_changed` | 删除范围与用户确认的数量或成员摘要不一致 |

错误响应只返回稳定错误码、中文提示和请求 ID，不返回原始异常。

## 9. 导出执行器设计

### 9.1 领取与恢复

执行器每 2 秒轮询一次，使用 `FOR UPDATE SKIP LOCKED` 和第 6 节的所有者公平顺序原子领取 `queued` 或租约已过期的 `preparing/running` 任务。只有 `attempt_no < TREND_GRID_SIGNAL_EXPORT_MAX_ATTEMPTS` 的任务可以被领取；领取后增加 `attempt_no`、生成 `attempt_token` 并设置 90 秒租约。新任务进入 `preparing`，接管任务从准备阶段重新开始。执行期间每 10 秒续租并更新独立健康表。只有持有当前 `attempt_token` 的执行器可以更新进度和完成状态。租约已过期且 `attempt_no` 已达到上限的任务转为 `failed/runner_interrupted`，不再自动领取，由用户决定是否创建新重试任务。

每次轮询先把租约已过期的 `cancelling` 任务转为 `cancelled` 并登记临时文件待清理，再处理达到尝试上限的失败任务，最后领取恢复或排队任务；因此执行器在收到取消后退出也不会让任务永久停在“正在取消”。

每个新的执行尝试（首次领取或租约接管）开始时：

1. 删除该任务所有已失效尝试留下的 `.part` 文件；本次临时文件固定命名为 `{export_id}.{attempt_token}.part`。
2. 将全部候选项资格重置为 `pending`，将 `prepared_run_count`、`processed_run_count` 重置为 0，并清空导出数与排除摘要。
3. 重新执行准备阶段；准备完成且至少有一条 `included` 后进入 `running`。
4. 按 `ordinal` 从第一条 `included` 任务项生成 ZIP。
5. 成功关闭 ZIP 后计算大小和 SHA-256，原子改名到正式路径。
6. 在数据库事务中写入 `succeeded`、存储键、摘要和过期时间。

数据库完成状态写入失败时，执行器清理未登记的正式文件；数据库写入成功但响应丢失时，后续领取通过状态和 `attempt_token` 判断任务已经完成，不重复发布文件。

### 9.2 准备与逐条生成

准备阶段按 `ordinal` 逐条读取候选回测，每条使用第 3.1 节共享资格函数分类为 `included` 或 `excluded`，写入任务项资格状态；距上次持久化达到 2 秒或累计新增 20 条时更新 `prepared_run_count`，任一条件先满足即写入。每条分类后检查取消请求和租约。全部候选分类完成后，在一个事务中汇总 `total_run_count`、`excluded_run_count` 和 `exclusion_summary`：可导出数为 0 时以 `no_exportable_runs` 失败；否则状态转为 `running` 并开始创建 `.part` ZIP。准备阶段不创建 ZIP，也不把多个完整结果同时保存在内存中。

生成阶段只处理 `qualification_status=included` 的任务项，并按以下顺序执行：

1. 后台执行器使用管理员上下文领取跨用户任务，但读取源回测时 SQL 必须同时包含 `id=source_run_id AND owner_user_id=export.owner_user_id`，不能依赖管理员 RLS 绕过或进程默认用户；随后按第 3.1 节重新判定资格。
2. 读取 `trades` 和 `skippedSignals`，按照第 3 节契约构造稳定顺序。
3. 使用流式 ZIP 条目写入 BOM、表头和逐行 CSV；不先构建全部 CSV 字符串。
4. 条目成功关闭后增加内存中的处理计数；距上次持久化达到 2 秒或累计新增 20 条时更新 `processed_run_count`，任一条件先满足即写入。租约仍按 10 秒独立续租，避免大量小 CSV 造成逐条数据库写入。
5. 检查取消请求、租约所有权和剩余磁盘空间，再处理下一条。

准备阶段发现某条结果缺失、不兼容、非成功或无信号时，只按第 3.1 节排除；但候选回测已经被删除时无法完成已固化范围审计，任务以 `source_changed` 整体失败。生成阶段会再次执行资格函数：此前 `included` 的记录消失或不再满足资格时归为 `source_changed`；资格仍成立但 CSV 值无法按黄金契约序列化时归为 `result_incompatible`；ZIP 打开、写入、关闭或摘要计算失败归为 `archive_failed`，其中明确的磁盘空间不足或目录不可写归为 `storage_unavailable`；未分类异常归为 `internal_error`。任一失败都删除 `.part` 文件，不提供部分 ZIP 下载。任务错误码和页面文案固定为：

| 错误码 | 页面文案 | 页面操作 |
|---|---|---|
| `no_exportable_runs` | 所选回测中没有可导出的信号明细结果 | 返回历史列表重新选择 |
| `source_changed` | 回测记录已删除或在导出期间发生变化 | 返回历史列表重新选择 |
| `result_incompatible` | 回测结果已变化或不再符合信号明细格式 | 返回历史列表重新选择 |
| `storage_unavailable` | 导出存储暂不可用，请稍后重新导出 | 重新导出 |
| `archive_failed` | 信号明细压缩包生成失败，请重新导出 | 重新导出 |
| `runner_interrupted` | 导出执行器连续中断，请重新导出 | 重新导出 |
| `internal_error` | 信号明细导出失败，请联系管理员并提供请求 ID | 不提供原任务重试 |
| `artifact_missing` | 信号明细文件不可用，请重新导出 | 重新导出 |

错误消息可以附加系统生成的回测编号，但不得包含原始策略、信号内容、堆栈或存储路径；原始异常进入现有管理员诊断日志。

### 9.3 存储和清理

文件放在现有受控附件根目录下：

```text
/runtime/artifacts/signal-detail-exports/{owner_user_id}/{export_id}.zip
/runtime/artifacts/signal-detail-exports/{owner_user_id}/{export_id}.{attempt_token}.part
```

数据库只保存相对 `storage_key`。路径解析必须验证目标仍位于附件根目录内，禁止客户端路径参与拼接。backend 与 `signal-export-runner` 挂载同一 `quant-backtest-artifacts` 命名卷。

执行器主循环每 `TREND_GRID_SIGNAL_EXPORT_CLEANUP_SECONDS` 执行一次清理遍历；清理与生成使用不同的短事务，不持有任务生成事务或 ZIP 文件句柄：

- 删除已过期成功任务对应的 ZIP，并将状态改为 `expired`。
- 删除不存在有效 `attempt_token` 租约且文件修改时间超过 `TREND_GRID_SIGNAL_EXPORT_STALE_PART_HOURS` 的 `.part` 文件；不得只根据文件年龄删除仍有有效租约的文件。
- 删除在任务表中没有对应 `storage_key`、文件名符合本功能 UUID 规则且修改时间超过 `TREND_GRID_SIGNAL_EXPORT_STALE_PART_HOURS` 的孤立正式 ZIP，用于回收用户删除级联或数据库完成写入失败留下的文件；不得扫描或删除该功能目录以外的 artifacts。
- 清理取消、失败任务明确登记的临时文件。
- 删除文件后保留任务状态供页面查看；`expired`、`failed`、`cancelled` 任务及其任务项在终态时间超过 `TREND_GRID_SIGNAL_EXPORT_TASK_RETENTION_DAYS` 后删除。
- 删除心跳时间超过 24 小时的执行器健康行。
- 文件清理失败时记录管理员日志并重试，不把任务误报为已清理。

第 6 节列出的全部导出配置必须在 `backend/settings.py` 提供默认值和边界校验，并在服务器部署文档中逐项说明。

## 10. 前端实施设计

为避免继续扩大 `BacktestPage.tsx` 的职责，文件职责固定为：

- `frontend/src/components/SignalDetailExportDrawer.tsx`：任务列表、进度、失败原因、下载、取消和重试。
- `frontend/src/hooks/useSignalDetailExports.ts`：创建任务、活动任务轮询、页面焦点刷新和完成提示。
- `frontend/src/utils/signalDetailCsv.ts`：从当前页面导出逻辑提取的纯函数，继续服务单条导出并生成共享黄金样本。
- `frontend/src/utils/backtestRunSelection.ts`：单选、多选、本页全选、筛选结果全选、例外 ID 和公共请求结构转换；同时服务导出与删除。
- `frontend/src/api/client.ts` 和 `frontend/src/types/index.ts`：接口与类型。

`BacktestPage.tsx` 只负责把历史筛选条件、`selectableTotal` 和当前页行信息传给选择模块，并渲染二段式全选提示、统一批量操作条及导出抽屉入口。导出与删除从 `backtestRunSelection.ts` 获取同一 `BacktestRunSelection`；页面不得为某个操作维护另一套已选 ID，也不得让筛选结果全选退化为当前页操作。新页面的删除请求统一发送 `selection`，不再把当前页已选项转换为旧版顶层 `runIds` 请求；旧请求格式只用于兼容尚未更新的调用方。

用户点击创建时，`useSignalDetailExports.ts` 生成幂等键并提交当时的选择快照；接口返回前禁用创建按钮，网络重试复用同一幂等键。创建成功后清空当前选择，打开导出记录抽屉并立即查询一次任务详情；创建接口返回 422 时保留选择并显示“当前选择中没有可处理的终态回测”。任务准备后以 `no_exportable_runs` 失败时显示“所选回测中没有可导出的信号明细结果”，不自动恢复旧选择。

用户点击删除时，页面显示“正在核对删除范围”，取得第 8.2 节确认快照后再弹出确认框；确认提交期间禁用重复操作。`backtest.selection_changed` 时关闭旧确认框、保留当前选择并提示“选择范围已变化，请重新确认”，不得自动再次提交删除。

页面必须使用以下明确文案：

- `批量导出信号明细`
- `信号明细导出记录`
- `正在准备信号明细`
- `正在生成信号明细`
- `下载信号明细 ZIP`
- `信号明细文件已过期`

不得只显示含义不清的“导出”“导出记录”或“下载 ZIP”。按钮、抽屉、状态提示和无障碍名称使用相同术语。

## 12. 测试与验证计划

### 12.1 CSV 契约测试

- 普通方向性持仓和底仓增强策略生成结果与当前 CSV 黄金样本一致。
- 成交、跳过、空值、研究信号字段、中文说明、逗号、双引号和换行正确转义。
- 信号时间、执行时间、相同时间稳定排序和 UTF-8 BOM 保持一致。
- 普通平仓收益、增强策略关闭效果和不适用收益为空字符串。
- 无信号回测按 `no_signal_details` 排除，不生成 CSV，与现有单条导出按钮禁用行为一致。
- 单条现有导出在买卖方向、执行状态和盈亏状态均为 `all` 时，与批量 ZIP 中对应 CSV 的字节完全一致。

### 12.2 数据与权限测试

- 手动 ID 去重，跨页选择不会丢失。
- 新公共选择的明确 ID 超过 100 条时仍可用于导出确认和删除确认，并按固定批次核对所有者与状态；旧版顶层 `runIds` 请求仍保持原有最多 100 条约束。
- 历史分页 `selectableTotal` 与相同筛选下 `succeeded/failed/cancelled` 的本人记录数一致，不读取 `result_json`。
- 筛选全选与历史分页的关键词、标的、方案、收藏筛选结果一致。
- 导出创建、删除确认和批量删除对同一 `BacktestRunSelection` 解析出相同候选 ID；删除数量或成员摘要变化时返回 409 且不删除任何记录。
- 创建任务时固化选择范围；后续筛选变化不改变任务项。
- 创建接口不读取 `result_json`；大范围选择在固化候选后返回，资格归类由执行器完成。
- `failed`、`cancelled` 和结果缺失或不兼容的成功回测被计入排除数量；`queued`、`running`、`cancelling` 不属于可选择集合，既不进入选择数也不进入排除数。
- 准备期间 `totalRunCount/excludedRunCount` 返回 `null` 而不是 0；全部候选不合格时任务以 `no_exportable_runs` 失败且没有 ZIP。
- 历史回测列表和信号明细导出记录继续只返回当前登录用户的数据。
- 绕过页面直接向接口提交未按当前用户查询到的回测 ID，或访问未按当前用户查询到的导出任务 ID 时，统一返回 404，不暴露具体 ID 是否存在或所属关系。
- 不存在和无权限资源均返回 404，不泄露资源归属。
- 迁移重复执行安全，RLS、索引和状态约束生效。

### 12.3 执行器测试

- 多条同标的、同方案回测在同一 `信号明细` 目录中生成，并通过回测编号避免文件名冲突。
- 策略方案改名或删除后，CSV 文件名仍使用回测冻结快照中的 `params_snapshot.name`。
- 使用至少 200 个任务项的仪器化数据源，断言生成下一条前已释放上一条结果对象，执行器没有累计保存全部 CSV 或全部结果。
- 测试中临时降低 `zipfile.ZIP64_LIMIT`，验证 `allowZip64=True` 和每条 `force_zip64=True` 后压缩包可完整打开，任务不因传统 ZIP 边界被截断。
- 心跳、租约过期、执行器退出和其他实例接管后从干净 `.part` 文件恢复。
- 两个执行器并发领取时，部分唯一索引和领取逻辑保证同一用户最多一个 `preparing/running/cancelling` 任务。
- 取消请求在当前条目完成后停止，临时文件被清理。
- 回测被删除、结果损坏、磁盘不足和摘要失败时不产生部分可下载文件。
- 成功文件原子发布，大小和摘要正确；过期后文件删除并显示 `expired`。

### 12.4 前端测试

- 单选、多选、本页全选和筛选结果全选始终显示同一个批量操作条，均可执行“批量导出信号明细”和“删除所选”。
- 本页全选只增减当前页 ID且保留其他页选择；二段式提示可以切换到全部筛选结果，取消单条形成例外 ID，重新勾选可恢复。
- 批量操作条使用 `selectableTotal` 显示精确跨页选择数，不用分页 `total` 或当前页数量猜测。
- 修改任一筛选条件时清除全部选择并提示原因，单纯翻页不清除选择。
- 删除前显示“正在核对删除范围”，确认框展示服务端精确数量；服务端返回 `backtest.selection_changed` 时不删除、保留选择并要求重新确认。
- 新页面四种选择方式发起删除时都提交同一个 `selection` 结构，不调用只携带当前页 ID 的旧版请求。
- 活动任务轮询、焦点刷新、完成提示和未下载标记正确。
- 抽屉展示状态、进度、文件大小、有效期和安全错误原因。
- 只有成功且未过期任务显示“下载信号明细 ZIP”。
- 页面刷新和重新登录后仍可看到所属用户的导出记录。
- 四种选择方式下的批量导出和批量删除均操作完整选择范围；历史分页、收藏、搜索和单条信号明细导出不回退。

### 12.5 集成与人工验证

1. 手动选择不同页的多条普通 Bar、L2 和增强策略回测，生成 ZIP 并逐个核对 CSV。
2. 使用测试数据创建至少 120 条匹配记录，在 50 条/页下执行筛选全选，确认 120 条均进入任务而不是只导出当前页。
3. 使用可回收测试记录验证单选、多选、本页全选和筛选结果全选均能执行删除；筛选结果全选删除 120 条而不是当前页 50 条。
4. 在删除确认后增删一条匹配测试记录，确认摘要变化导致 409、零删除且必须重新确认。
5. 创建至少 120 条任务项且未压缩 CSV 总量超过 64 MiB 的任务后刷新、退出页面再返回，确认任务继续执行、进度可恢复且下载入口仍存在。
6. 生成中取消一次任务，确认不提供残缺文件；随后重新导出成功。
7. 安全测试绕过页面直接请求未按当前用户查询到的导出任务 ID，确认返回 404；页面本身不提供跨用户记录入口。
8. 对上述大任务下载完整 ZIP，并从非零偏移发起 Range 请求，核对 `206`、`Content-Range`、`Content-Length`、ETag、文件名和解压完整性。

### 12.6 远程普通用户样本回归

本改动读取历史回测完整结果并新增导出权限链路。完成本地自动化测试后，按仓库规则通过只读查询取得远程服务器普通用户最近两条有效回测的保存代码和运行快照，在隔离的正常导出执行器链路中生成并下载 ZIP，核对：

- 两条回测均由所属普通用户创建导出任务并成功生成。
- CSV 与该用户现有单条导出在买卖方向、执行状态和盈亏状态均为 `all` 时一致。
- 绕过页面直接请求未按当前用户查询到的任务 ID 时返回 404。
- 临时样本、ZIP 和查询结果验证后清理，不写入仓库、测试固件、文档、对话或持久日志。

生产普通用户样本只做只读选择解析和导出回归，不调用批量删除；四种选择方式的删除及摘要变化保护使用本地可回收测试记录验证，禁止为验证本功能删除生产历史回测。

远程不可访问、有效样本不足两条或环境无法挂载导出存储时，必须标记“远程普通用户样本回归待验证”并说明原因。

## 13. 发布与兼容性

本功能直接改动 migrate、backend、新增的 signal-export-runner 和 frontend。现有 `scripts/deploy-server.sh` 会在每次标准发布中统一重建 strategy-worker、backend、bar-runner、l2-runner 和 frontend，因此本次仍必须沿用脚本现有的“关闭提交入口、等待运行中回测排空、迁移、统一重建、健康检查、重新开放入口”流程，不得以“导出不影响策略执行”为由跳过 Bar/L2 任务检查或只手工重启部分服务。

发布顺序：

1. 检查 artifacts 卷空间、数据库备份状态和当前发布健康状况。
2. 执行幂等迁移，确认任务表、任务项表和 RLS 生效。
3. 将 `signal-export-runner` 加入脚本统一 `docker compose up -d --build` 服务列表；Compose 健康检查执行 `python -m backend.signal_export_runner --healthcheck`，验证数据库连接和 artifacts 根目录可写。
4. 执行器启动后每 10 秒更新独立健康表；backend `/api/health` 返回 `signalExportRunner.healthy`，任务创建接口在没有 30 秒内新鲜心跳时返回 503，不创建长期无人领取的任务。
5. 发布 frontend，验证历史回测页面入口和接口兼容。
6. 创建一条小型普通用户导出任务，完成生成、下载、解压和内容核对。
7. 创建跨页筛选全选任务，验证异步进度、刷新恢复和任务记录。
8. 验证旧历史任务读取、单条 CSV 导出、批量删除、收藏和 Bar/L2 回测运行不受影响。

数据库新增表和接口均为增量能力，不修改历史 `result_json`，不重算旧任务。旧前端不会调用新接口；新前端遇到尚未发布接口时应显示功能暂不可用，不影响查看和运行回测。

导出文件存放在持久化 artifacts 卷，backend 或前端发布不会删除已成功且未过期的文件。回滚应用版本时不得删除新增表或附件目录；待任务过期后由兼容清理逻辑处理。

## 14. 风险与处理

| 风险 | 处理 |
|---|---|
| 大任务耗尽浏览器内存 | 浏览器只创建任务和下载文件，CSV 与 ZIP 均在服务端逐条生成 |
| 大任务占用回测执行能力 | 使用独立 signal-export-runner，不占用 Bar/L2 执行槽位 |
| 磁盘空间不足 | 开始和生成过程中检查空间，使用 `.part` 文件，失败后定向清理 |
| ZIP 超过传统格式限制 | 启用 ZIP64，不设置业务数量或文件大小上限 |
| 执行器重启产生损坏文件 | 租约接管后从干净 `.part` 文件重建，关闭并校验后原子发布 |
| 跨页全选与筛选范围不一致 | 复用历史分页同源过滤条件；修改筛选时清除旧全选状态；创建时事务化固化 |
| 筛选全选删除范围在确认后变化 | 删除前生成服务端数量和成员摘要；提交时事务内重新核对，不一致则零删除并要求重新确认 |
| 选择中包含不可导出记录 | 创建时固化全部终态候选，执行器准备阶段逐条归类；任务记录展示排除数量及原因，ZIP 只写入可导出记录 |
| 生成期间历史回测被删除 | 任务以 `source_changed` 整体失败，不发布部分 ZIP；原任务不允许重试，页面提示返回历史列表重新选择 |
| CSV 前后端口径分叉 | 建立黄金样本，前后端运行相同契约用例，任何字段变化必须同步更新 |
| 文件路径或结果跨用户泄露 | RLS、所有者条件、安全路径解析、鉴权下载及统一 404 |
| 过期文件长期占用空间 | 默认 24 小时有效期，执行器持续清理并对失败清理重试告警 |
| 任务数量很多影响公平性 | 多任务排队、按所有者公平领取、同一用户同时只运行一个任务 |

## 15. 验收标准

1. 历史回测页面提供“批量导出信号明细”和“信号明细导出记录”，不存在含义不清的通用导出文案。
2. 单选、多选、本页全选和当前筛选结果全选使用同一个选择概念和批量操作条；四种方式均可执行“批量导出信号明细”和“删除所选”，操作完整选择范围而不是仅当前页。
3. 用户可以跨页手动选择，也可以选择当前服务端筛选条件下的全部可选择终态记录；创建接口固化候选后返回，执行器准备完成后准确给出可导出数量和各类排除数量，导出不限制为当前页或 50 条。
4. 筛选结果全选删除前展示服务端确认的精确数量；确认后成员发生变化时返回 409 且零删除，不会删除未经确认的记录。
5. 批量任务不设置回测记录数、信号行数或 ZIP 大小的业务上限，大任务能够排队并异步生成。
6. 每条满足第 3.1 节资格的回测在 ZIP 中对应一个 CSV；零信号回测继续不可导出；现有 CSV 的类型、编码、字段、顺序、取值、排序和闭环收益口径保持不变。
7. ZIP 内只有一个 `信号明细` 目录，CSV 按“标的_冻结方案名称_回测编号”命名，可以正常解压且不覆盖文件。
8. 用户离开或刷新页面后任务继续执行，重新进入历史回测页面可以查看进度并下载未过期结果。
9. 历史回测列表和导出记录抽屉仍只展示当前用户的数据；导出和删除接口不依赖前端过滤，所有资源 ID 均按当前用户重新查询，未匹配时统一返回 404。
10. 取消、失败、执行器重启、历史记录变化和磁盘不足均不会留下可下载的部分 ZIP。
11. 成功文件默认保留 24 小时，过期状态和重新导出入口清楚，临时文件与过期文件能够回收。
12. 导出执行器不占用 Bar/L2 回测并发槽位，现有回测提交、运行、历史读取、收藏、删除和单条 CSV 导出不回退。
13. 数据库迁移、backend、signal-export-runner 和 frontend 可以通过 `scripts/deploy-server.sh` 同批发布，并完成本地及远程普通用户样本验证。
