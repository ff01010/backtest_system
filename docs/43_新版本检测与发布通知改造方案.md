# 新版本检测与发布通知改造方案

日期：2026-09-12
状态：本地实现完成，待服务器迁移与发布验收

## 1. 背景与问题结论

当前系统发布新功能后，已经登录或长期保持页面打开的用户无法主动得知版本变化，只能通过刷新页面、他人通知或偶然发现界面变化获知。现状存在以下问题：

1. `/api/health` 只返回回测执行器健康状态、策略运行时版本和能力摘要，不表达应用发布版本，也没有面向用户的更新内容。
2. frontend 构建过程没有注入本次部署的构建标识，浏览器无法判断当前页面和服务器是否来自同一提交。
3. 系统没有发布记录、当前生效发布和用户已读回执，无法实现一次提醒、跨设备去重及历史更新记录。
4. `scripts/deploy-server.sh` 能在迁移、服务重建、Runner 和应用健康检查完成后判断发布成功，但没有在该时点激活用户通知。
5. 策略管理页面已经能够识别未保存修改；若版本弹窗直接强制刷新，可能造成用户策略代码和参数丢失。
6. 单纯比较 Git 提交哈希不能判断先后顺序，也无法正确处理重复部署、回滚和同一提交重新构建。

本方案新增独立的发布通知模块，将“构建是否变化”“本次发布向用户说明什么”和“用户是否已经确认”分开管理。模块通过小接口封装版本识别、发布激活、权限、已读判断和回滚语义，前端只负责查询通知状态、展示和确认。

## 2. 目标、范围与不做事项

### 2.1 目标

1. 新版本成功发布后，已登录用户无需重新登录即可收到更新提示。
2. 弹窗展示用户可理解的版本、发布时间、功能更新和必要操作，不直接暴露内部提交细节。
3. 当前有效公告对同一用户只主动弹出一次，并在不同浏览器和设备间共享已读状态。
4. 页面持续打开时能够检测到新发布；页面重新登录或重新获得焦点时及时补检。
5. 版本检测失败不得阻断登录、策略编辑或回测操作。
6. 刷新前识别未保存策略，避免因更新提示造成用户内容丢失。
7. 发布通知只在数据库迁移、相关服务重建、最终健康复检和部署状态 CAS 全部成功后激活。
8. 正确处理重复部署、静默发布、回滚和发布通知撤回，不产生错误或重复提醒。
9. 保留可查询的历史更新记录，用户关闭弹窗后仍可再次查看。

### 2.2 本期范围

- 应用构建标识和发布标识定义。
- 发布说明清单及校验规则。
- 发布记录、当前生效发布和用户回执的数据模型。
- 查询通知状态、确认已读和读取历史发布记录的后端接口。
- 登录后检测、页面恢复检测、定时检测、更新弹窗和更新记录入口。
- 未保存策略识别与刷新保护。
- frontend、backend、Nginx 和发布脚本的版本传播与激活流程。
- 自动化测试、迁移验证、服务器发布验证和回滚验证。

### 2.3 不在本期范围内

1. 邮件、短信、企业微信、浏览器系统通知或移动端推送。
2. 按部门、用户组、灰度租户或功能开关做复杂受众分流。
3. 由系统自动把全部 Git 提交信息原样生成用户公告。
4. 强制用户立即升级；只有明确标记为 `mandatory` 的兼容性或安全发布可以阻止继续使用。
5. 修改策略执行、撮合、行情、费用、仓位、收益和历史回测结果语义。
6. 引入 WebSocket 或 SSE。首期采用低频条件请求，避免为低频发布事件增加长连接运维复杂度。

## 3. 核心设计决策

### 3.1 区分构建标识、发布记录和运行时版本

系统使用三个不同概念：

| 概念 | 示例 | 职责 |
| --- | --- | --- |
| `buildId（构建标识）` | Git 完整提交 SHA | 判断浏览器 frontend 与当前 backend 是否属于同一份应用代码。 |
| `releaseNo（发布序号）` | `27` | 数据库单调递增编号，用于发布历史排序，不参与 Git 拓扑判断。 |
| `clientCompatibilityVersion（客户端兼容版本）` | `3` | 单调递增整数，只在旧 frontend 不允许继续操作时递增，用于强制门禁。 |
| `strategyRuntimeVersion（策略运行时版本）` | `python3.12-runtime-v3` | 表达策略 Python 和量化依赖能力，不作为应用新版本通知依据。 |

Git SHA 是不透明标识，禁止用字符串大小或截断值判断新旧。页面是否过期只比较 `clientBuildId != serverBuildId`；用户是否需要弹窗由当前有效公告和用户回执决定；强制刷新门禁比较客户端兼容版本，不能被“已读”状态解除。普通和静默部署沿用当前兼容版本，只有经评审的 `mandatory` 发布才能递增它。

### 3.2 发布成功后才激活通知

发布说明可以随代码提前进入服务器，但只有在以下条件全部满足后才能成为当前部署状态：

1. Git 更新完成且工作区干净。
2. 数据库迁移成功。
3. backend、strategy-worker、Bar Runner、L2 Runner 和 frontend 按既有发布流程完成重建。
4. ClickHouse 连通性、交易日历和应用健康检查通过。
5. frontend 实际入口资源、backend 内建元数据和所有对外服务实例报告相同 `buildId`。
6. 发布说明清单的 `buildId` 与实际部署提交一致。

`scripts/deploy-server.sh` 对“拉取、构建、迁移、重建、检查、激活”全过程持有部署互斥锁，并在现有 `wait_for_application` 成功后执行最终复检和带代际 CAS 的幂等激活。任何前置步骤失败时保持上一部署状态，不向用户报告尚未成功上线的功能；若新服务已经切换但激活失败，新的回测提交门禁保持关闭，修复激活或回退服务后才能重新开放。

### 3.3 发布说明必须显式维护

自动检测部署版本不等于自动生成用户说明。每次需要通知用户的发布都提交结构化发布说明，文案描述用户可以看到或使用的变化，不直接复制内部提交标题、路径、漏洞细节或故障堆栈。

允许 `notifyUsers=false` 的静默发布。静默发布仍更新 `serverBuildId`，但不产生主动弹窗；适用于只调整日志、内部部署或无用户行为变化的修复。

### 3.4 服务器回执是已读事实源

用户回执存入 PostgreSQL，以支持跨设备去重。浏览器 `localStorage` 只用于当前设备的请求防抖和短暂故障降噪，不得作为发布已读的唯一依据。

普通发布只有在用户点击“知道了”或“稍后刷新”后写入回执。弹窗刚渲染时不自动标记已读，避免页面关闭、网络中断或遮挡导致用户实际未看到内容却永久失去提示。`acknowledged` 仅表示用户看过公告；`upgradeRequired` 表示当前页面因强制发布必须刷新，两者是独立状态。

### 3.5 首期采用轮询与页面恢复检查

发布是低频事件，首期不建设长连接。前端在登录后、页面重新可见和固定间隔触发条件请求；后端使用 ETag 或等价版本令牌减少无变化响应开销。

### 3.6 更新提示不得破坏用户工作

普通和重要发布不得自动刷新页面。检测到策略存在未保存修改时，“刷新页面”按钮必须变为保护流程，明确要求先保存策略或继续留在当前页面。

仅 `mandatory` 发布可以阻止继续操作，但仍必须显示未保存内容警告。首期不实现自动保存策略草稿；若产品要求强制升级同时零丢失，需要另立可靠草稿持久化需求。

`mandatory` 只是已加载 frontend 的交互控制，不能替代后端兼容设计或安全校验。发布通知首次上线前的旧页面无法理解该级别，因此后端接口仍应保持向后兼容；若未来必须拒绝旧客户端写操作，应另行设计可验证的客户端兼容契约。

### 3.7 只主动提示当前有效公告

首期产品语义是“展示最新有效公告”，不是可靠消息队列。新的通知发布会替代旧公告成为当前有效公告；尚未看到旧公告的用户只看到新公告，发布文案必须能够概括自上一个公开版本以来仍然有效的用户变化。静默部署默认保留当前有效公告，因此不会令尚未确认的公告消失；回滚和撤回必须显式指定保留、替换或清空公告。若未来要求每条公告必达，应另建公告队列和投递游标，不能复用当前指针假装实现。

## 4. 总体架构

```text
Git main 提交 + 发布说明清单
              ↓
scripts/deploy-server.sh
  生成 buildId 并注入 frontend/backend
              ↓
迁移、重建、应用与 Runner 健康检查
              ↓ 成功后
ReleasePublisher（发布激活命令）
              ↓
PostgreSQL：发布记录 + 当前部署状态 + 用户回执
              ↓
GET /api/releases/status?clientBuildId=...
              ↓
ReleaseNotificationManager（前端发布通知模块）
  登录检查 / 页面恢复检查 / 定时检查
              ↓
更新弹窗、刷新保护、更新记录
```

### 4.1 后端模块

新增 `backend/services/release_notifications.py`，对业务调用方提供最小接口：

```python
def get_release_status(client_build_id: str) -> dict[str, Any]: ...

def acknowledge_release(release_id: str) -> dict[str, Any]: ...

def list_published_releases(limit: int, cursor: str | None) -> dict[str, Any]: ...
```

版本查询、当前部署与公告解析、用户回执和权限处理都位于模块实现内部。`backend/app.py` 只负责 HTTP 参数和响应映射，不重复编写数据库判断。

发布状态管理使用不依赖目标应用运行进程的独立 `release-admin` 工具镜像。正常发布使用 `quant-backtest-release-admin:<完整 Git SHA>` 不可变标签，使工具代码、公告清单和目标构建一一对应；首次验证成功后建立 `quant-backtest-release-admin:recovery-v1` 恢复基线，后续日常发布不得覆盖。即使回滚到尚无通知模块的旧 backend，也能使用恢复基线切换部署状态：

```text
release-admin bootstrap --build-id <sha> --client-version <n> --deployment-id <uuid>
release-admin activate --manifest <path> --build-id <sha> --deployment-id <uuid> --expected-generation <n>
release-admin activate-silent --build-id <sha> --client-version <n> --deployment-id <uuid> --expected-generation <n> (--keep-notice | --no-notice)
release-admin withdraw-notice --release-id <uuid> --deployment-id <uuid> --expected-generation <n>
release-admin rollback --build-id <sha> --client-version <n> --deployment-id <uuid> --expected-generation <n> (--release-id <uuid> | --no-notice)
```

所有命令只在可信部署环境使用，不暴露为 HTTP 接口；必须在单个事务中锁定部署状态、校验预期代际并做 CAS，成功时只输出一行 JSON，校验失败或状态冲突时以非零状态退出。`bootstrap` 仅允许在状态表为空时插入初始行，重复调用只有全部参数一致才幂等成功。`rollback --release-id` 必须校验公告已发布且 buildId 与目标回滚构建一致，禁止按最大发布号猜测；`--no-notice` 则显式清空公告。发布记录不可原地修订，文案修正必须提交新的 manifest，从而产生新的 Git SHA 和新发布记录。

### 4.2 前端模块

新增 `ReleaseNotificationManager`，对页面只暴露：

```typescript
type ReleaseNotificationManagerProps = {
  clientBuildId: string;
  clientCompatibilityVersion: number;
  hasUnsavedStrategy: boolean;
  isStrategySavePending: boolean;

```

模块内部负责触发时机、请求去重、弹窗状态、已读确认、重试和刷新动作。`App.tsx` 不直接维护轮询计时器或发布状态细节。

## 5. 发布说明清单

### 5.1 文件位置与结构

新增固定文件：

```text
deploy/release-manifest.json
```

示例：

```json
{
  "schemaVersion": 1,
  "version": "2026.09.12",
  "clientCompatibilityVersion": 3,
  "title": "回测能力更新",
  "summary": "新增北交所回测和常用量化计算能力。",
  "highlights": [
    "支持北交所股票搜索与标准 Bar 回测",
    "支持 TA-Lib 等常用量化计算库",
    "优化策略保存失败提示"
  ],
  "level": "normal",
  "notifyUsers": true
}
```

`buildId` 不由开发者手工填写，由发布脚本读取服务器当前 `git rev-parse HEAD` 后传入。`publishedAt` 由服务器激活事务生成，避免使用开发机器时间。

### 5.2 基于 Git 提交生成草稿

发布说明不直接复制原始 Git 日志。合并发布 MR 前执行：

```bash
python scripts/generate_release_manifest.py --base origin/main --target HEAD
```

生成模块读取指定提交范围、排除 merge commit，将 `feat` 归入功能更新、`fix` 归入问题修复，并默认忽略 `docs`、`test`、`refactor`、`chore`、`build`、`ci` 和 `perf`。提交正文可用 `Release-Note: <用户文案>` 覆盖标题、用 `Release-Note: skip` 排除公开条目、用 `Release-Level: important|mandatory` 显式提升公告等级。没有用户可感知条目时生成静默发布。生成结果必须人工审核并随 MR 提交，服务器不调用外部 AI，也不在部署时公开未经审核的提交内容。

### 5.3 校验规则

- `schemaVersion` 首期只能为 `1`。
- `version` 长度不超过 32，只用于展示，不参与顺序判断。
- `clientCompatibilityVersion` 为大于等于 1 的整数；普通、重要和静默发布必须等于当前服务器要求值，只有 `mandatory` 发布可以恰好递增 1，禁止跳号或回退时隐式猜测。
- `title` 长度为 1–128。
- `summary` 长度不超过 1000。
- `highlights` 为 1–20 条，每条不超过 300；静默发布允许为空。
- `level` 只能为 `normal`、`important` 或 `mandatory`。
- `notifyUsers` 为布尔值。
- `mandatory` 必须 `notifyUsers=true`、递增客户端兼容版本，并要求发布说明写明刷新原因。
- 发布命令收到的 `buildId` 必须为 40 位小写十六进制 Git SHA。

`manifestDigest` 为清单规范化 JSON 的 SHA-256：UTF-8 编码、对象键按字典序排序、数组顺序保留、不转义非 ASCII 字符、逗号和冒号外不保留空白、末尾不含换行；等价于 Python `json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":"))` 的字节结果。摘要覆盖清单全部字段，不覆盖由部署时生成的 buildId、发布时间和发布序号。

清单无效或与实际构建不一致时，应用代码发布可视为已运行，但发布脚本整体返回失败且不得激活通知；运维需修正清单或明确执行静默激活，不能自动发布不完整文案。

## 6. 数据库设计

新增幂等迁移 `db/migrations/027_app_release_notifications.sql`。本地首次验证 027 后发现需要收紧数据库写入边界，因此未回改已执行迁移，另以 `028_release_notification_write_boundary.sql` 撤销直写权限并补齐受控函数、独立发布角色和激活审计。

### 6.1 应用发布表

```text
app_release
  id uuid PRIMARY KEY
  release_no bigint GENERATED ALWAYS AS IDENTITY UNIQUE
  build_id char(40) NOT NULL
  manifest_digest char(64) NOT NULL
  version varchar(32) NOT NULL
  client_compatibility_version integer NOT NULL
  title varchar(128) NOT NULL
  summary text NOT NULL DEFAULT ''
  highlights jsonb NOT NULL DEFAULT '[]'
  level varchar(16) NOT NULL
  notify_users boolean NOT NULL DEFAULT true
  status varchar(16) NOT NULL
  published_at timestamptz
  withdrawn_at timestamptz
  created_at timestamptz NOT NULL DEFAULT now()
  UNIQUE (build_id)
  UNIQUE (id, build_id)
```

约束：

- `level IN ('normal', 'important', 'mandatory')`。
- `client_compatibility_version >= 1`。
- `status IN ('published', 'withdrawn')`；草稿只存在于 Git 中的 manifest，不预先写数据库。
- `published` 必须存在 `published_at` 且没有 `withdrawn_at`；`withdrawn` 必须同时保留 `published_at` 和 `withdrawn_at`。
- `mandatory` 必须同时满足 `notify_users=true`。
- `build_id`、`manifest_digest` 格式以及 `highlights` 的数组类型、数量、元素类型和长度同时由数据库约束与命令层校验。
- 同一构建只能对应一份不可变公告；相同 buildId 和相同摘要重复执行为幂等成功，相同 buildId 和不同摘要必须拒绝。文案修正需提交新 manifest 并产生新 Git SHA，不提供同构建公告替换。
- 发布表撤销物理删除权限，回执外键使用 `ON DELETE RESTRICT`，发布和回执只允许通过受控函数写入，以保留审计事实。

### 6.2 当前部署状态表

```text
app_deployment_state
  singleton_key boolean PRIMARY KEY DEFAULT true CHECK (singleton_key)
  current_build_id char(40) NOT NULL
  required_client_version integer NOT NULL
  current_notice_id uuid REFERENCES app_release(id) ON DELETE RESTRICT
  activation_kind varchar(16) NOT NULL
  deployment_id uuid NOT NULL UNIQUE
  generation bigint NOT NULL
  activated_at timestamptz NOT NULL
```

使用单行部署状态表而不是根据最大 `release_no` 推断当前公告。`current_build_id` 始终记录实际生效构建；`current_notice_id` 是独立的当前有效公告，可以属于此前仍被当前构建包含的通知发布；`required_client_version` 是当前服务器允许写操作的最低客户端兼容版本。静默部署默认保留公告和兼容版本，回滚和撤回必须显式指定公告，回滚还必须显式传入目标镜像内建兼容版本。数据库约束要求 `activation_kind IN ('release', 'silent', 'rollback')`、`required_client_version >= 1`、`generation >= 0`；受控函数进一步保证非空 `current_notice_id` 只能指向 `status='published' AND notify_users=true` 的记录。`activation_kind` 供前端选择提示文案，`generation` 每次成功切换递增，结合 `deployment_id` 拒绝旧部署最后激活。

迁移只幂等创建空的单例表，不伪造 buildId。首次上线在提交入口关闭状态下，由部署脚本读取新镜像的真实 buildId 和客户端兼容版本并执行 `release-admin bootstrap`，再执行正常激活；后续迁移不改写该行。应用角色的 `INSERT`、`DELETE` 和直接 `UPDATE` 权限全部撤销，只有受控数据库函数可更新。约束只能保证“最多一行”，因此 bootstrap 后的启动检查和发布命令必须验证“恰好一行”；bootstrap 前发布状态接口固定返回 `503 release.state_unavailable`。

### 6.3 用户回执表

```text
app_release_receipt
  release_id uuid NOT NULL REFERENCES app_release(id) ON DELETE RESTRICT
  user_id uuid NOT NULL REFERENCES app_user(id) ON DELETE CASCADE
  acknowledged_at timestamptz NOT NULL DEFAULT now()
  client_build_id varchar(64) NOT NULL DEFAULT ''
  PRIMARY KEY (release_id, user_id)
```

确认操作使用 `INSERT ... ON CONFLICT ... DO NOTHING`，重复点击、请求重试和多个标签页同时确认都保持幂等。发布记录禁止物理删除，账号按既有隐私删除流程移除时允许级联清理该账号回执。`release_no` 只在激活事务真正插入公告时分配，不提供提前创建草稿的日常流程，因此序号与发布时间顺序一致；历史游标仍使用 `(published_at, release_no)`，避免同一时间戳和并发查询时重复或遗漏。

### 6.4 权限与 RLS

- 应用每个数据库事务沿用现有连接管理，在事务开始后通过 `SET LOCAL` 写入当前用户 ID、角色和管理员标记，事务结束后自动清除；连接池复用用例必须验证 A 用户上下文不会泄漏到 B 用户。
- 普通用户只能读取 `status='published' AND notify_users=true` 的发布记录，并只能读取、写入自己的回执；静默部署不创建 `app_release` 用户公告。
- 管理员可以读取全部回执用于发布覆盖率诊断，但首期前端不建设覆盖率报表。
- API 应用角色不拥有发布表、部署状态表的直接写权限。发布管理工具使用独立最小权限数据库角色，只能执行受控函数；表 owner 不作为运行角色，也不依赖 superuser/BYPASSRLS。
- 新表显式启用并强制 RLS；受控函数使用固定 `search_path`、校验调用角色并记录操作者、deploymentId、旧代际和新代际。
- 迁移只负责 DDL、约束、索引、RLS、受控函数和授权；应用启动时不得执行 DDL。

## 7. 后端接口设计

### 7.1 查询当前发布状态

```text
GET /api/releases/status?clientBuildId=<build-id>&clientCompatibilityVersion=<n>
```

需要 Cookie 登录会话，不对开放回测 API Key 暴露。

响应：

```json
{
  "serverBuildId": "3e4f2fe30f2776019636f50c65a7514d516b90cf",
  "requiredClientCompatibilityVersion": 3,
  "clientOutdated": true,
  "activationKind": "release",
  "presentationMode": "release_notice",
  "acknowledged": false,
  "unread": true,
  "upgradeRequired": false,
  "release": {
    "id": "uuid",
    "releaseNo": 27,
    "version": "2026.09.12",
    "title": "回测能力更新",
    "summary": "新增北交所回测和常用量化计算能力。",
    "highlights": [
      "支持北交所股票搜索与标准 Bar 回测"
    ],
    "level": "normal",
    "publishedAt": "2026-09-12T15:30:00+08:00"
  }
}
```

规则：

1. `serverBuildId` 来自 backend 镜像内建元数据；启动时校验容器运行时配置与内建值一致，模块再验证它与 `app_deployment_state.current_build_id` 一致，不从请求、公告行或策略运行时推测。
2. `clientOutdated = clientBuildId != serverBuildId`。只有编译期 `clientBuildId='dev'` 的本地前端跳过轮询；生产 backend 不接受自身 buildId 为 `dev`，查询参数为 `dev` 时返回 `clientOutdated=false` 且不提供通知，避免开发页面连接生产环境时误提示。
3. `acknowledged` 仅表示当前用户已经确认当前有效公告；`unread = release != null AND NOT acknowledged`。
4. `upgradeRequired = clientCompatibilityVersion < requiredClientCompatibilityVersion`，与 buildId 和 `unread` 无关。用户确认公告、换设备或重新打开页面都不能解除门禁；普通/静默后续部署不会意外继承新的强制刷新，旧于最低兼容版本的页面则持续受控。
5. `presentationMode` 明确取 `mandatory_gate`、`release_notice`、`version_mismatch`、`rollback_mismatch` 或 `none`，优先级固定为：`upgradeRequired` 时使用 `mandatory_gate`；否则回滚且构建不一致时使用 `rollback_mismatch`；否则存在当前有效公告时使用 `release_notice`；否则只要构建不一致就使用 `version_mismatch`；其余为 `none`。`release_notice` 仅在 `unread=true` 时主动弹出，`version_mismatch` 只显示顶部非弹窗状态。前端不得根据 SHA 或空字段自行猜测语义。
6. 无部署状态或部署状态与 backend 构建不一致时返回 `503` 和稳定错误体 `{"detail":{"code":"release.state_unavailable","message":"版本通知暂不可用"}}`，不返回 ETag；前端静默降级，不阻断主功能。
7. 支持 `If-None-Match`。ETag 为 `current_build_id`、`required_client_version`、`activation_kind`、`current_notice_id`（可空）、公告摘要和状态、`notify_users`、当前用户回执是否存在的规范化组合摘要，不包含原始用户 ID。任一指针、兼容版本、撤回状态或回执变化都会生成新值。
8. `304` 没有响应正文；前端仅在内存中保留与 ETag 对应的最近成功响应，ACK、退出登录和切换用户时清空。个性化响应不得写入共享 `localStorage`。
9. 所有接口时间使用带时区的 RFC 3339 格式。

### 7.2 确认发布通知

```text
POST /api/releases/{releaseId}/acknowledge
```

请求体为 `{"clientBuildId":"<40位SHA或dev>"}`，不接受用户 ID。后端始终使用当前登录用户，并校验目标发布已发布、允许读取且仍是当前有效公告。确认事务先锁定部署状态再写回执，避免撤回与确认竞态；重复确认返回成功，不创建重复记录。`clientBuildId` 只用于诊断记录，不参与身份或权限判断。

响应：

```json
{
  "acknowledged": true,
  "releaseId": "uuid"
}
```

### 7.3 查询历史更新记录

```text
GET /api/releases?limit=20&cursor=<opaque-cursor>
```

- 只返回 `status='published' AND notify_users=true` 且未撤回的记录。
- 发布记录只在激活事务中创建，`release_no` 因而代表发布时间顺序；按 `(published_at DESC, release_no DESC)` 分页。
- cursor 为不透明值，前端不能自行拼装数据库偏移。
- 首期最多返回 50 条，避免公告内容无限增长。

### 7.4 健康接口扩展

`/api/health` 增加：

```json
{
  "applicationBuildId": "3e4f2fe30f2776019636f50c65a7514d516b90cf",
  "clientCompatibilityVersion": 3
}
```

该字段供部署健康检查验证 frontend/backend 构建一致性，不代替登录后的发布通知接口，也不返回发布文案或用户已读状态。它必须读取镜像内建元数据，不能只信任可被容器环境覆盖的值。

## 8. 构建标识传播

### 8.1 发布脚本

在 `git pull --ff-only origin main` 成功后计算：

```text
release_build_id=$(git rev-parse HEAD)
```

发布脚本将其作为本次命令的局部变量，通过显式 `export APPLICATION_BUILD_ID` 或 Compose `--env-file` 临时文件传入，不能假定未导出的 shell 变量会参与 Compose 插值。临时文件权限设为仅当前用户可读并在退出时清理；不得写入或覆盖 `deploy/.env`。

### 8.2 backend

- `deploy/Dockerfile.backend` 声明 `ARG APPLICATION_BUILD_ID=dev` 和客户端兼容版本参数，把它们写入镜像 label 和镜像内只读 `/app/build-info.json`。
- `backend/settings.py` 读取 `TREND_GRID_APPLICATION_BUILD_ID`，默认 `dev`，并校验生产值格式。
- backend 启动时比较运行时设置、镜像 label 对应的内建文件和生产格式，不一致则健康检查失败。
- backend 镜像复制发布说明清单，使容器内发布命令读取的是与镜像一起构建的内容，而不是服务器工作区可能变化的文件。

### 8.3 frontend

- `deploy/Dockerfile.frontend` 声明 `ARG VITE_APPLICATION_BUILD_ID=dev` 和 `ARG VITE_CLIENT_COMPATIBILITY_VERSION=1`。
- Vite 构建期将两个值写入编译期常量。
- frontend 镜像构建完成后生成只含 buildId、客户端兼容版本和入口资源摘要的 `/build-info.json`，供发布脚本核对；该文件不得包含环境变量或内部配置。
- 前端构建标识是编译期常量，不能运行时从 backend 覆盖，否则无法判断旧页面与新服务器是否不同。
- 最终检查必须请求实际对外 `index.html`，解析其入口 bundle，并核对该 bundle 内容中的编译期 buildId/摘要与 `/build-info.json` 一致，不能只比较两个可被同时误配的旁路字段。

### 8.4 Docker Compose

backend 和 frontend build args 都取同一个 `APPLICATION_BUILD_ID` 和经 manifest 校验的客户端兼容版本。backend 容器环境同时获得该值；strategy-worker、Bar Runner 和 L2 Runner 不参与用户界面版本比较，除非后续需要在统一发布诊断中展示其应用构建标识。

## 9. 前端检测与交互设计

### 9.1 检测时机

用户认证成功并进入 `Workspace` 后挂载发布通知模块：

1. 首次挂载立即查询。
2. `visibilitychange` 从隐藏变为可见时查询。
3. 窗口重新获得焦点且距离上次查询超过 60 秒时查询。
4. 页面持续可见时每 5 分钟查询一次。
5. 同一时刻最多存在一个查询；后续触发合并，避免焦点和定时器造成并发请求。
6. 页面卸载时取消请求和定时器。

接口遇到 `401` 时沿用现有登录失效处理；网络、`5xx` 或无效响应只记录一次可诊断日志，并按最长 15 分钟退避，不能弹出与版本无关的错误或阻断工作区。

### 9.2 弹窗内容

弹窗至少包含：

- “发现新版本”标题；
- 用户可见版本和发布时间；
- 发布标题、摘要和更新点；
- “知道了”按钮；
- `clientOutdated=true` 时显示“刷新使用新版本”按钮；
- 关闭后仍可从顶部“更新记录”入口重新打开。

普通发布允许通过关闭按钮退出，关闭动作等同“知道了”并提交回执；重要发布要求用户显式点击“知道了”或“稍后刷新”，不允许点击遮罩误关闭；强制发布不显示普通关闭入口。任何级别都不在弹窗刚渲染时自动标记已读。

普通或重要公告确认后但尚未刷新时，不再重复主动弹窗，顶部持续显示“有新版本”状态，直到 `clientBuildId` 与 `serverBuildId` 一致。`mandatory` 即使已经确认，只要 `upgradeRequired=true` 就持续显示不可绕过的工作区门禁。

发布标题、摘要和更新点按纯文本渲染，不支持任意 HTML；即使发布清单内容异常，也不得通过 `dangerouslySetInnerHTML` 注入页面。

### 9.3 未保存策略保护

`BacktestPage` 已有 `versionDirty`，但该状态当前封装在页面内部，也没有独立的保存中状态。改造时补充保存中状态，并通过回调向工作区暴露最小事实：

```typescript
onWorkspaceSafetyStateChange(state: {
  hasUnsavedStrategy: boolean;
  isStrategySavePending: boolean;
}): void
```

同时由 `BacktestPage` 注册最小命令式保存动作 `onRequestStrategySave(): Promise<boolean>`：复用现有保存校验和错误展示，成功且 dirty 已清除时返回 `true`，失败或取消返回 `false`。不得把草稿指纹、策略代码或整个表单状态提升到 `App.tsx`。状态回调只在两个布尔值实际变化时触发，避免表单输入造成工作区无意义重渲染；强制门禁覆盖工作区时通过该动作提供“保存策略”按钮，不依赖用户穿透遮罩操作底层页面。

刷新规则：

| 状态 | 行为 |
| --- | --- |
| 无未保存策略 | “刷新使用新版本”直接执行 `window.location.reload()`。 |
| 有未保存策略、普通或重要发布 | 阻止刷新，提示先保存策略；保留弹窗和当前编辑内容。 |
| 有未保存策略、强制发布 | 只允许“保存策略后刷新”或经二次确认“放弃修改并刷新”；不得进入其他页面或发起新回测。 |
| 正在保存策略 | 禁用刷新和放弃按钮，等待保存成功或失败；成功且 dirty 清除后仍由用户点击刷新，不自动刷新。 |

为避免浏览器原生刷新绕过保护，实施时必须复用 `versionDirty` 增加 `beforeunload` 提示；该提示只在存在未保存修改时注册。强制门禁只保留策略保存、退出登录和明确放弃修改后刷新所需操作，不能用公告回执解除；浏览器刷新失败或仍加载旧 bundle 时，重新查询后继续保持门禁。

### 9.4 已读时机与多标签页

- “知道了”和“稍后刷新”先提交回执，成功后关闭普通主动弹窗；强制门禁不因回执关闭。
- “刷新使用新版本”先提交回执；请求失败时仍允许用户刷新，但不在本地持久化待确认发布 ID。新页面会依据服务器未读状态再次提示，避免同一浏览器切换账号后把 A 用户回执误写给 B 用户。
- 使用 `BroadcastChannel` 通知同源其他标签页某发布已经确认；不支持时依赖下次服务器查询。
- 多标签页并发确认由数据库唯一约束保证幂等。

### 9.5 首次上线限制

在发布通知功能首次上线之前已经打开的旧页面没有检测代码，因此无法被新功能主动唤醒。只有至少加载过一次具备通知能力 frontend 的页面才能检测后续发布，无法按“第几次发布”保证覆盖；该限制必须写入首次发布验收记录，不能误报为缺陷。

## 10. Nginx 缓存策略

为保证页面刷新后取得新入口文件，同时保留带哈希静态资源的缓存收益：

```text
/index.html 和 SPA fallback
  Cache-Control: no-cache

/build-info.json
  Cache-Control: no-cache

/assets/*（Vite 带内容哈希文件）
  Cache-Control: public, max-age=31536000, immutable

/api/releases/status
  由 backend 返回 Cache-Control: private, no-cache
  强制 Vary: Cookie
  使用 ETag 条件请求
```

不使用 `no-store` 禁止所有浏览器缓存，因为状态接口可以通过私有 ETag 安全重验证；响应必须同时带 `Cache-Control: private, no-cache` 和 `Vary: Cookie`，Nginx/CDN 必须显式关闭该路径的代理缓存，`401`、`403`、`503` 同样不得共享缓存。验收时用两个用户交替覆盖 `200/304`、退出重登和会话切换，防止已读状态混用。

## 11. 发布、重复部署与回滚语义

### 11.1 正常发布

1. 在修改服务器工作区前由外层 `flock` 进程取得主机级部署锁。锁覆盖拉取到最终开放入口全过程，禁止部署、回滚、撤回并发运行。
2. 拉取 main；若 `scripts/deploy-server.sh` 发生变化，在同一把锁内重新执行新脚本，再校验 `deploy/release-manifest.json` 并计算 `buildId`。
3. 按现有流程关闭新提交入口、排空任务、执行迁移并重建相关服务。
4. 构建 `quant-backtest-release-admin:<buildId>`，验证其镜像 label、客户端兼容版本和镜像内公告清单摘要与目标工作区一致；恢复基线不存在时才建立 `recovery-v1`，禁止覆盖既有恢复基线。
5. 请求实际对外 `index.html` 及其入口 bundle，验证 frontend 编译期 buildId 和资源摘要。
6. 完成 Runner、ClickHouse 和代表性应用健康检查；激活前立即对实际流量入口做最后一次 buildId 复检，缩小检查与激活之间的 TOCTOU 窗口。
7. 首次上线若状态表为空，先用目标镜像的真实 buildId 和兼容版本执行一次 `bootstrap`；随后使用独立 `release-admin` 执行 `activate`，携带 `deploymentId` 和 bootstrap 后读到的 `expectedGeneration`。事务锁定单例行，只有代际仍匹配时才创建/复用发布、更新构建、最低兼容版本和公告指针并递增代际。
8. 再次查询当前部署状态，确认代际、公告、文案和 `buildId` 正确后，才重新开放提交入口并释放部署锁。

相同 `buildId` 和相同摘要重复执行时不新增发布号、不清空用户回执；CAS 冲突、实际构建变化或激活失败时禁止覆盖当前状态。当前只支持单部署主机，使用固定绝对路径文件锁防止脚本并发，数据库代际 CAS 仅用于拒绝崩溃恢复后的过期激活，不能替代跨主机编排锁。未来扩容前必须先引入全局部署编排，并检查所有实际接流量实例，而不是只命中一个健康实例。

提交门禁只阻止新建回测、策略执行等写入型任务，已经运行的 Worker 任务继续按排空规则完成，健康检查和运维接口保持可用。门禁由发布脚本通过 Nginx 受控配置/标记启停，并在 `trap` 中遵循“仅激活成功或服务已完整回退后开放”，不能因脚本异常退出而自动放开。

### 11.2 相同提交重复部署

- 相同 `buildId`、相同发布内容：复用原发布，不重复弹窗。
- 相同 `buildId`、不同发布内容：默认拒绝，避免同一构建身份对应不同用户承诺。
- 若必须修复已发布文案，提交修正后的 manifest 形成新的 Git SHA，再按正常发布流程激活；不支持同一 buildId 创建公告修订，也不复制旧回执。

### 11.3 静默发布

`notifyUsers=false` 时不创建用户公告，使用 `activate-silent` 更新 `current_build_id` 和代际。默认 `--keep-notice` 保留上一有效公告，使尚未确认公告不会被随后的内部部署吞掉；如果该公告已不再适用，部署者必须显式使用 `--no-notice`。静默部署不会进入普通用户历史列表，其构建切换进入既有部署审计日志。

### 11.4 回滚

回滚脚本使用与正常发布相同的全流程锁、提交门禁、最终健康复检和代际 CAS。旧版本服务健康后，使用稳定的独立 `release-admin rollback` 把 `current_build_id` 切换为实际目标 buildId，并显式传入 `--release-id` 或 `--no-notice`；禁止根据最大发布号或 buildId 隐式猜测公告。

- 回滚到用户已确认过的旧版本时不再次弹出该旧发布。
- 浏览器 build 与回滚后的 server build 不一致时，`activationKind=rollback`、`presentationMode=rollback_mismatch`，不把旧发布描述为“更新版本”，文案固定为“当前页面版本与服务器不一致”。
- 若需要告知用户某功能因故回退，应另行发布一条新的运维公告记录，不能篡改旧发布说明或清空旧回执。
- 回滚到通知能力上线前的镜像时，由保留的独立 `release-admin` 镜像完成状态切换；目标旧 backend 没有新健康字段时，改用镜像 label、部署时留存的 Git SHA 和对外静态资源校验。通知功能首次上线把所有旧镜像的兼容版本定义为基线 `1` 并记录在部署审计中，不能临时猜测；首次上线前必须实际演练。
- 回滚激活失败时保持提交入口关闭并继续修复，不能让数据库当前部署状态长期指向与实际服务不一致的构建。

### 11.5 撤回通知

撤回只隐藏错误公告，不回滚代码。`withdraw-notice` 取得同一部署锁，在事务中锁定部署状态；若目标仍是当前公告，则将 `current_notice_id` 置空并递增代际，`current_build_id` 保持不变。历史公告和用户回执保留审计，不物理删除。用户已打开被撤回弹窗后再确认时，接口返回 `409 release.notice_stale`；前端立即重新查询并关闭或替换旧弹窗，不能永久重试。

## 12. 兼容性与失败处理

1. 旧 frontend 不调用新接口，backend 新增接口不会改变现有页面行为。
2. 新 frontend 遇到旧 backend 返回 `404` 时静默关闭通知能力，不影响其他功能。
3. 发布状态接口异常时保留当前页面，不自动刷新，不显示全局系统故障。
4. 用户确认接口失败时弹窗保留可重试状态；若公告已撤回导致 `409 release.notice_stale`，则立即重新查询而非继续重试旧公告；刷新动作按 9.4 的本地补偿规则处理。
5. 数据库没有部署状态或 buildId 不一致时，发布脚本保持提交门禁关闭；已运行页面的通知查询可静默降级，通知读取故障不得扩大为策略或回测执行故障。
6. 用户被禁用或会话过期后不能查询或写入回执。
7. 现有历史回测、策略版本和任务队列不读取发布通知表，不需要数据回填或结果重算。
8. 新表和接口只保存发布文案、构建标识与已读时间，不保存用户策略、回测参数或其他敏感内容。

## 14. 实施步骤

### 阶段一：版本和数据契约

1. 确定发布说明 JSON Schema、buildId 校验和三种通知级别语义。
2. 新建幂等迁移及 RLS，验证全新数据库和已存在数据库重复执行。
3. 扩展启动迁移完整性检查；只验证新表和必要约束存在，不在应用启动时执行 DDL。
4. 实现发布通知后端模块、受控数据库函数和独立发布管理工具。
5. 增加状态、确认和历史查询接口测试。

退出条件：可以在本地数据库登记、激活、确认和回滚发布；普通用户无法操作他人回执或写发布记录。

### 阶段二：构建和发布链路

1. 将同一 Git SHA 注入 backend 和 frontend。
2. 扩展健康接口和 frontend 构建标识验证方式。
3. 修改发布脚本，增加全流程锁、提交门禁、最终健康复检和 CAS 激活。
4. 覆盖无效清单、构建不一致、重复/并发部署、TOCTOU 和激活失败。

退出条件：发布失败不产生通知；发布成功后数据库当前指针和实际运行构建一致。

### 阶段三：前端检测与交互

1. 实现发布通知管理模块、弹窗和更新记录抽屉。
2. 接入登录、页面恢复、焦点和五分钟条件检查。
3. 从 `BacktestPage` 提升最小未保存事实，完成刷新保护。
4. 实现多标签页确认同步、退避和接口失败降级。

退出条件：普通发布只弹一次，跨设备已读一致，未保存策略不会因刷新丢失。

### 阶段四：发布和回滚验收

1. 本地完成后端、前端、迁移、Nginx 和发布脚本验证。
2. 发布前按既有流程排空回测任务。
3. 同批发布 backend 和 frontend；本改造不改变 Runner 契约，但既有脚本仍会重建相关服务，发布前不得中断活动任务。
4. 使用普通用户和管理员分别完成首次提示、确认、跨设备和历史记录验证。
5. 模拟相同提交重复部署和回滚，核对当前指针、页面提示和用户回执。

退出条件：服务器端完整验收通过，回滚后实际构建、健康响应和当前部署状态一致。

## 15. 测试矩阵

### 15.1 后端与数据库

- 新迁移从空库执行成功，并可连续重复执行。
- 首次迁移后状态表为空且接口稳定返回 503；`bootstrap` 后恰好一行，重复 bootstrap 幂等，参数冲突时拒绝。
- 应用和普通管理员不能插入、删除或直接更新部署状态行。
- 同一 buildId 重复激活不新增发布号。
- 同一 buildId 使用不同内容时拒绝。
- 普通用户读取当前已发布通知成功。
- 使用真实生产应用数据库角色验证 FORCE RLS：普通用户不能读取已撤回公告、内部部署审计或他人回执。
- 连接池复用时事务结束会清理用户 GUC，A 用户上下文不会泄漏到 B 用户。
- 普通用户只能确认自己的回执。
- 多次确认和并发确认只生成一条记录。
- 管理员和部署命令权限符合预期。
- 发布激活、静默部署、撤回和回滚写入既有审计日志，且不包含敏感部署配置。
- 两个部署以及部署与回滚/撤回并发执行时，旧操作不能覆盖较新代际。
- 回滚能把当前构建和公告指针切到目标状态，不依赖最大发布号。
- ETag 在发布或回执变化时更新，无变化时返回 `304`。
- 无部署状态、当前公告撤回和数据库异常返回稳定错误契约。

### 15.2 前端

- 登录后未读发布弹窗出现。
- 已读发布不再次主动弹出，但可在更新记录查看。
- 页面恢复和超过阈值的窗口聚焦会触发检查。
- 五分钟轮询不会与聚焦请求并发。
- 多标签页确认后其他标签关闭相同弹窗。
- 普通发布可稍后处理，重要发布不能误点遮罩关闭。
- 旧页面和新 server build 不一致时显示刷新提示。
- 未保存策略存在时刷新被阻止，策略内容保持不变。
- 策略保存进行中时刷新和放弃按钮禁用。
- 通知接口 `404`、`5xx`、超时和无效响应不影响工作区。
- `mandatory` 已确认但未刷新、跨标签页或跨设备时仍由 `upgradeRequired` 保持门禁。
- 用户刷新到 mandatory 兼容版本后再发生同兼容版本的静默部署，不会被错误地再次强制；仍低于最低兼容版本的旧页面继续受控。
- 公告打开期间被撤回时收到 stale 冲突并关闭或替换弹窗。
- `304` 不解析正文，ACK、登出和切换用户后清理个性化 ETag 内存缓存。
- 浏览器级验证 `beforeunload` 和真实 reload，不只依赖组件单测。
- 组件卸载后不再更新状态或遗留定时器。

### 15.3 构建、Nginx 与部署

- frontend 和 backend 镜像获得完全相同的 40 位 buildId 与客户端兼容版本。
- `/build-info.json` 只返回 buildId 和入口摘要，且与实际 `index.html` 引用的 bundle 编译常量一致。
- 开发环境默认 `dev` 不产生误提示。
- `index.html` 会重新验证，带哈希 assets 长期缓存。
- 发布状态响应不被不同用户共享缓存。
- 健康检查失败时发布命令不执行。
- 激活前健康检查通过但随后实例变化时，最终复检/CAS 阻止开放提交入口。
- 激活失败后提交入口保持关闭，修复或服务回退后才重新开放。
- 发布说明清单无效时通知不激活并返回明确失败。
- 相同提交重复部署不重复通知。
- 回滚后 `/api/health`、当前部署状态和实际 frontend buildId 一致。
- 回滚到通知能力上线前镜像时，独立发布管理工具仍可完成状态切换。
- A 通知后紧接 B 静默部署仍保留 A；两个通知快速连续发布时只主动展示最新有效公告。
- 两个用户交替请求、条件请求、登出和重新登录不会发生代理缓存串号。

### 15.4 既有功能回归

- 登录、退出和会话失效行为不变。
- 策略新建、编辑、保存、复制和回测不受影响。
- 有无未保存修改的既有判断保持一致。
- 标准 Bar 和 L2 回测任务提交、排队、领取及结果读取不受影响。
- 前端类型检查、Vitest、正式构建和后端全量 pytest 通过。

1. 发布前确认 queued、running、cancelling 任务已按脚本规则排空。

7. 使用普通用户 B 登录，确认该用户仍能独立收到通知。
8. 保持策略未保存修改，验证刷新被阻止且代码、参数不丢失。
9. 模拟相同提交重复部署，确认不重复生成发布或清空回执。
10. 在可控环境完成一次回滚演练，确认页面提示为版本不一致且当前部署状态正确。

13. 演练激活失败，确认新提交入口保持关闭且已有运行任务不被通知模块影响。

## 17. 回滚方案

### 17.1 软件回滚

1. 取得与正常部署相同的全流程锁，关闭新的页面和公开 API 回测提交，并记录当前部署代际。
2. 按既有规则等待活动回测任务结束。
3. 回退 backend 和 frontend 到目标镜像；若既有发布脚本同批处理 Runner，继续遵守全排空要求。
4. 服务健康并完成最终构建复检后，使用保留的独立工具执行 `rollback --build-id <target-sha> --deployment-id <uuid> --expected-generation <n> --release-id <uuid>`；无适用公告时必须改传 `--no-notice`。
5. 核对前后端 buildId、数据库指针和实际页面一致后恢复入口。

### 17.2 数据回滚

新增表为旁路通知数据，不影响交易和历史结果。软件回滚时不删除新表、不执行破坏性逆迁移、不删除用户回执。旧版本不读取这些表，可以安全保留。若发布记录文案错误，使用撤回或替代记录，不直接修改历史已发布事实。

## 18. 验收标准

1. 成功发布一个 `notifyUsers=true` 的新 build 后，已加载通知能力的在线页面在五分钟内发现新版本。
2. 新登录用户立即看到未读发布内容。
3. 当前有效公告对同一用户只主动提示一次，并跨设备共享已读状态；快速连续公告按“最新公告折叠”规则处理。
4. 不同用户的回执完全隔离。
5. 同一提交重复部署不重复通知。
6. 发布健康检查失败、清单无效或构建标识不一致时不激活通知。
7. 回滚后当前部署状态与实际运行构建一致，不把旧版本错误描述为新版本；回滚到通知功能上线前镜像的演练通过。
8. 页面存在未保存策略时不会因更新操作丢失代码或参数。
9. 通知查询失败不影响登录、策略编辑和回测。
10. 普通、重要和强制发布的关闭与刷新行为符合本方案；强制门禁不因确认回执解除。
11. 用户可以通过顶部入口查看历史更新记录。
12. HTML 与发布状态缓存策略正确，不发生旧入口文件长期缓存或跨用户已读状态泄漏。
13. 数据库迁移幂等，真实应用角色下的 RLS、连接池上下文隔离、唯一约束和并发确认测试通过。
14. 后端全量测试、前端 Vitest、TypeScript 类型检查和生产构建通过。
15. 服务器完成普通用户、多设备、重复/并发部署、激活失败、回滚及代表性回测验证。

| 重复部署重复弹窗 | 用户被频繁打扰 | buildId 唯一、清单摘要一致性校验、幂等激活、保留原回执。 |
| 并发部署后旧构建最后激活 | 部署指针和实际服务错位 | 主机级全流程锁、数据库 generation CAS 和 deploymentId 审计。 |
| 回滚仍指向新发布 | 页面提示与实际能力不一致 | 单行部署状态、独立发布管理工具、显式公告参数和回滚后复检。 |
| 强制刷新丢失策略 | 用户代码和参数丢失 | 提升最小 dirty 状态、强制 beforeunload、保存后手动刷新或二次确认放弃。 |
| 用 localStorage 保存已读 | 换设备重复提示或清理缓存后重现 | PostgreSQL 回执为事实源，localStorage 只做临时补偿。 |
| 轮询增加后端压力 | 长期开页产生无效请求 | 五分钟间隔、焦点节流、单请求合并、正确索引、连接池容量和并发压测；ETag 只作为网络优化。 |
| 响应被共享缓存 | A 用户已读状态泄漏给 B 用户 | private/no-cache、Vary Cookie、反向代理不缓存用户响应。 |
| 发布文案泄露内部信息 | 暴露路径、漏洞或部署细节 | 结构化清单、长度校验、用户语言审查，不自动复制全部提交。 |
| 首次上线无法唤醒旧页面 | 首次发布覆盖不完整 | 明确只有加载过通知代码的页面可被检测，通过现有渠道提醒旧页面刷新。 |
| 通知模块故障阻断业务 | 用户无法进入回测系统 | 前端失败降级，通知接口不参与回测提交和执行。 |

## 20. 方案自审

1. 本方案没有把策略运行时版本误作应用版本，避免量化依赖不变但 frontend 已更新时漏报。
2. 发布通知激活位于最终健康复检之后，并由部署锁和代际 CAS 保护，解决提前通知和并发旧部署覆盖问题。
3. 当前构建和公告指针独立保存，不以最大发布号推断，因此覆盖了静默部署、公告撤回和回滚场景。
4. buildId、发布文案和用户回执职责分离，同一提交重复部署不会重复提示，跨设备也能稳定去重。
5. 前端模块只接收 buildId 和未保存事实，版本检测复杂度没有扩散到 `App.tsx` 和策略表单。
6. 方案复用现有 `versionDirty`，不在全局复制策略代码或参数，降低敏感内容和状态同步风险。
7. 轮询使用条件请求并在失败时退避；数据库负载仍依靠索引、连接池容量和并发压测控制，未把 ETag 误当作免查询缓存。
8. 数据库变更采用新幂等迁移并保留历史，不在应用启动时执行 DDL。
9. 发布、重复部署、静默发布、回滚和撤回均定义了明确语义，没有只覆盖理想正常发布。
10. 首期不引入 WebSocket、邮件或复杂受众规则，改造集中在发布通知目标内。
11. 方案明确第一次上线无法通知此前已打开的旧页面，避免形成无法兑现的覆盖承诺。
12. 改造不触碰策略执行、撮合和历史结果，但服务器发布仍需遵守队列排空与同批重建的既有规则。
13. 独立审阅后补齐了首次版本回滚、强制门禁、公告折叠、RLS 身份上下文、ETag 状态机和共享缓存隔离；实现阶段不得把这些约束降级为仅靠前端判断或人工约定。
