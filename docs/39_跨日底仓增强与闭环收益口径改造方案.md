## 0. 方案摘要

当前问题不是账户总收益公式错误，而是成交归属与闭环定义不完整：当策略当日买入的股票受 T+1 限制不可卖时，引擎可能实际卖出可卖的初始底仓；结果层却仍把这笔成交解释为策略仓位的平仓，并以底仓成本计算 realizedPnl（已实现损益）。因此总现金和总持仓可以正确，但“本次做 T 收益”“闭环胜率”和策略内部持仓可能互相对不上。

本方案采用“双账本、一个事实源”的设计：

1. accountLedger（账户事实账）继续记录真实现金、实际持仓、成交费用和账户权益，是 accountPnl（账户总收益）的唯一事实源。
2. overlayAttributionLedger（增强归属账）只解释实际持仓相对 targetBaseQuantity（目标底仓数量）的偏离，计算底仓增强的已实现收益、未实现收益和完整周期。
3. 底仓增强不再被固定为“必须当日补回”，增加 overlaySettlementPolicy（增强仓结算规则）：intraday_restore（日内恢复）或 cross_day_carry（允许跨日）。
4. 一次完整增强周期从 overlayQuantity（增强仓位）由 0 变为非 0 开始，到再次回到 0 结束；分批补回在各自成交日确认已实现收益，完整周期仅在最后恢复为 0 时完成。
5. directional_holding（方向性持仓）继续使用单一净仓语义，不借用底仓增强的闭环和收益口径，也不再通过隐藏的“先策略仓、再底仓”回退改变订单归属。

### 0.1 业务流转图

~~~mermaid
flowchart TD
  A[策略输出订单] --> B[撮合与 T+1 校验]
  B --> C[产生唯一实际成交 Fill]
  C --> D[accountLedger 账户事实账]
  C --> E{strategyCategory 策略类别}
  D --> F[现金 + 实际持仓 + 市值]
  F --> G[accountPnl 账户总收益]
  E -->|directional_holding| H[单一净仓与方向性收益]
  E -->|core_position_overlay| I[overlayAttributionLedger 增强归属账]
  I --> J[overlayQuantity = actualQuantity - targetBaseQuantity]
  J --> K[部分恢复：当日确认 realizedOverlayPnl]
  J --> L[回到 0：完成一个 completedCycle]
  J --> M[任务结束仍非 0：形成 openCycle 并按市价估值]
  G --> N[收益核对]
  I --> N
  N --> O[accountPnl = baseBenchmarkPnl + overlayPnl]
~~~

## 1. 问题原因

### 1.1 当前实际行为

以任务 ea9c78d9-0609-4ca8-a21e-fd40f1f6635a 的第二次平仓为例：

- 当日策略买入 1,200 股，成交加权价约为 47.5837；
- 随后卖出 1,200 股，成交价为 49.45；
- 因当日买入股票不可卖，撮合实际使用了回测开始前已持有、当日可卖的底仓；
- 结果中的 4,452.7366 元，是按底仓成本 45.71 元计算的账户会计已实现损益；
- 若把这一买一卖解释为一次增强操作，扣除实际费用后的增强收益约为 2,193.7656 元。

这两个数不是谁算错了，而是回答了不同问题：前者回答“账户卖出的库存相对其历史成本赚了多少”，后者回答“这次增强操作相对保持底仓不动多赚了多少”。当前页面把两者都叫作交易收益，才造成预期冲突。

### 1.2 当前闭环并不是真正闭环

当前 L2 结果层主要按每一条 realizedPnl（已实现损益）非零的成交统计胜负。分批平仓可能被算成多笔胜负，跨日未恢复的增强仓也没有生命周期记录。因此它不能回答：

- 昨日卖出 1,200 股、今日买回 600 股，今日是否有已实现增强收益；
- 今日再次卖出 300 股后，它属于新周期还是原周期；
- 最后一次补回时，完整周期的总收益应显示在哪一天；
- 任务结束仍未补回的仓位应如何进入收益和胜率。

## 2. 改造目标与边界

### 2.1 目标

1. 支持底仓增强策略跨日偏离并在后续交易日分批恢复目标底仓。
2. 保证账户事实、每日收益、部分恢复收益和完整周期收益四种视角可以相互核对。
3. 标准 Bar 与 L2 使用相同的仓位归属、周期边界和指标公式；差异只保留在成交模型。
4. 严格遵守 A 股 T+1；“底仓增强”不等于当天买入股票可以再次卖出。
5. 保持历史任务及其结果快照不可变，新口径只用于新任务或用户主动重跑的任务。
6. 页面明确区分账户收益、底仓基准收益和增强收益，不再以一个“收益”字段表达多个含义。

### 2.2 不在本方案范围

- 不实现真实融券、券源、保证金、借券成本或净空头仓位。
- 不改变策略代码决定 action（交易动作）和 quantity（下单数量）的职责。
- 不按“最近一次成交”进行主观配对，也不允许用户手工挑选哪两笔成交组成闭环。
- 不重算、覆盖或迁移历史回测结果。
- 不修改行情数据维护和行情版本机制。

## 3. 已确认的核心决策

### 3.1 策略类别与结算时点分离

strategyCategory（策略类别）决定仓位业务语义；overlaySettlementPolicy（增强仓结算规则）只决定增强仓是否必须日内恢复。

| strategyCategory（策略类别） | 仓位语义 | 可选结算规则 |
| --- | --- | --- |
| directional_holding（方向性持仓） | 单一净仓；初始持仓也是方向性库存的一部分 | 沿用 holdingPolicy（持仓规则） |
| core_position_overlay（底仓增强） | 围绕固定目标底仓产生正、负增强仓位 | intraday_restore 或 cross_day_carry |

不得再用 baseQuantity（底仓数量）、t0Enabled（启用底仓做 T）或 holdingPolicy（持仓规则）反推策略类别。

### 3.2 底仓增强使用有符号偏离量

对每个 symbol（标的），定义：

actualQuantity（实际持仓数量） = 账户当前真实多头数量

targetBaseQuantity（目标底仓数量） = 回测开始时配置且在任务内固定的基准持仓数量

overlayQuantity（增强仓位） = actualQuantity - targetBaseQuantity

| overlayQuantity（增强仓位） | 含义 |
| --- | --- |
| 大于 0 | 持仓高于目标底仓，属于正增强仓 |
| 等于 0 | 已恢复目标底仓，没有未完成增强周期 |
| 小于 0 | 已卖出部分底仓但尚未全部补回，属于负增强仓 |

负增强仓只表示相对目标底仓少持有，不表示真实融券或账户净空头。必须保持 actualQuantity（实际持仓数量）大于等于 0。

### 3.3 每日收益与完整周期分别记录

- 部分恢复在实际成交日确认 realizedOverlayPnl（已实现增强收益）。
- 完整周期只有在 overlayQuantity（增强仓位）回到 0 时才完成。
- 已经在前几日确认的部分收益不得移动到周期完成日，也不得重复计入。
- 任务结束仍未回到 0 的周期是 openCycle（未完成周期），按最后有效行情计算 unrealizedOverlayPnl（未实现增强收益），但不进入闭环胜率。

### 3.4 一个实际成交，只记一次事实

每个 Fill（成交）只能在 accountLedger（账户事实账）中出现一次。overlayAttributionLedger（增强归属账）引用该 Fill 的唯一标识进行策略归属，不复制现金或持仓变动。这样可以避免同一成交同时被算作底仓平仓和策略平仓。

## 4. 持仓与归属模型

### 4.1 两层账本

| 层级 | 职责 | 不负责 |
| --- | --- | --- |
| accountLedger（账户事实账） | 现金、实际持仓、T+1 可卖量、成交费用、账户权益 | 判断一笔成交属于哪个增强周期 |
| overlayAttributionLedger（增强归属账） | 目标底仓偏离、增强成本、部分恢复收益、周期状态 | 修改现金、制造成交或绕过 T+1 |

accountLedger（账户事实账）始终为最终事实。归属账若与账户账无法对账，任务必须以可诊断错误结束，不能静默选择其中一个结果。

### 4.2 增强仓状态机

| 变动前 | 实际成交 | 变动后 | 周期效果 |
| --- | --- | --- | --- |
| 0 | 买入 | 正数 | 新建正增强周期 |
| 正数 | 买入 | 更大正数 | 增加正增强仓 |
| 正数 | 卖出且未到 0 | 较小正数 | 部分恢复，确认部分收益 |
| 正数 | 卖出至 0 | 0 | 确认剩余收益，完成周期 |
| 0 | 卖出 | 负数 | 新建负增强周期 |
| 负数 | 卖出 | 更小负数 | 增加负增强仓 |
| 负数 | 买入且未到 0 | 较大负数 | 部分恢复，确认部分收益 |
| 负数 | 买入至 0 | 0 | 确认剩余收益，完成周期 |

如果一笔成交跨过 0，必须按数量拆成两个归属片段：第一段关闭旧周期至 0，第二段按相反方向新建周期。实际 Fill 仍只有一条，其费用按两个归属片段的数量比例确定性分摊，分摊尾差归入最后一个片段。

### 4.3 周期唯一键

completedCycle（已完成周期）使用系统生成的 cycleId（周期编号），其范围至少包含：

symbol（标的） + strategyExecutionId（策略执行编号） + cycleSequence（周期顺序号）

同一标的同一时刻只能有一个当前增强周期。周期不按自然日切断，也不按“最近成交”重新配对。

## 5. 成交、T+1 与策略状态

### 5.1 撮合顺序

1. 策略按原接口输出订单。
2. 引擎按真实现金、实际持仓、sellableQuantity（可卖数量）、涨跌停和成交模型校验并撮合。
3. 成交写入 accountLedger（账户事实账）。
4. 只有已成交数量进入 overlayAttributionLedger（增强归属账）；拒单和未成交部分不得改变增强仓。
5. 引擎把实际成交、实际净仓和增强仓状态回传策略，不用订单意图假装已经成交。

### 5.2 T+1 规则

- 回测开始前持有的底仓在首个交易日可卖。
- 每个交易日开始时，前一交易日及更早买入且仍持有的数量进入 sellableQuantity（可卖数量）。
- 当日买入不增加当日 sellableQuantity（可卖数量）。
- 同日先买 600 股再卖 300 股时，只要账户仍有至少 300 股此前已持有且可卖的库存，卖出可以成交；它会使 overlayQuantity（增强仓位）再次向负方向增加。
- cross_day_carry（允许跨日）只取消日终强制恢复，不放宽 T+1、资金或真实持仓约束。

### 5.3 方向性持仓隔离

directional_holding（方向性持仓）采用一个净仓事实，不再维护“脚本仓位卖不出时，静默切到底仓仓位”的归属回退：

- 启用初始持仓时，它就是方向性策略的起始净仓和成本基础；
- 平多订单减少真实净多仓，并按账户成本产生会计已实现损益；
- 未启用初始持仓时，当日买入受 T+1 限制，不能通过虚拟底仓完成当日平多；
- 方向性结果不生成底仓增强 cycleId（周期编号），也不使用 overlayPnl（增强收益）评价策略。

策略自定义 state（策略状态）若记录 holdQty（策略自记持仓），仍必须以成交回报更新；平台同时提供实际仓位字段。引擎不得因为订单被部分成交或改变了库存来源，就把原始委托数量全部回报为已平仓。

## 6. 收益口径与对账公式

### 6.1 账户总收益

accountPnl（账户总收益）是唯一总账结果：

accountPnl = endingCash + endingMarketValue - initialEquity

其中：

initialEquity（起始权益） = initialCapital（初始现金） + targetBaseQuantity × baseCostPrice（底仓成本价）

dailyAccountPnl（每日账户收益）按相邻交易日收盘权益差计算，第一日相对起始权益计算。它包含持仓市值变化、已实现交易收益和全部实际费用。

### 6.2 底仓基准与增强收益

底仓基准表示“整个回测期间始终持有目标底仓、不做任何增强交易”的表现：

baseBenchmarkPnl（累计底仓基准收益） = targetBaseQuantity × (currentMarkPrice - baseCostPrice)

dailyBaseBenchmarkPnl（每日底仓基准收益） = targetBaseQuantity × (当日收盘价 - 上一估值价)

overlayPnl（增强策略收益） = accountPnl - baseBenchmarkPnl

必须满足：

accountPnl = baseBenchmarkPnl + overlayPnl

### 6.3 已实现与未实现增强收益

正增强仓使用包含开仓费用的加权买入成本；卖出恢复时，以扣除卖出费用后的净卖出金额减去所关闭数量的加权成本，确认 realizedOverlayPnl（已实现增强收益）。

负增强仓使用扣除开仓卖出费用后的加权净卖出价；买入恢复时，以所关闭数量的加权净卖出金额减去包含买入费用的实际买入成本，确认 realizedOverlayPnl（已实现增强收益）。

未完成仓位按最后有效估值价计算 unrealizedOverlayPnl（未实现增强收益），不预扣尚未发生的未来平仓费用。

在每个估值时点必须满足：

overlayPnl = cumulativeRealizedOverlayPnl + unrealizedOverlayPnl

由于单笔最低佣金和跨零分摊可能产生小数尾差，统一采用账本最小货币精度，并把分摊尾差归入最后一个片段；禁止通过模糊容差长期吞掉差额。

### 6.4 账户会计收益与增强归属收益并存

底仓被卖出时，accountLedger（账户事实账）可以按 baseCostPrice（底仓成本价）产生 accountRealizedPnl（账户会计已实现损益）；但它不等于本次增强操作已经完成。

结果中必须分别保留：

- accountRealizedPnl（账户会计已实现损益）：用于解释账户库存成本；
- realizedOverlayPnl（已实现增强收益）：用于评价底仓增强操作；
- completedCyclePnl（完整周期收益）：一个已完成增强周期内各次 realizedOverlayPnl 的总和。

页面不得再用同一个“闭环收益”标签展示 accountRealizedPnl（账户会计已实现损益）。

## 7. 跨日示例

假设初始 actualQuantity（实际持仓数量）等于 targetBaseQuantity（目标底仓数量），忽略价格和费用，只看数量与收益确认时点：

| 日期 | 成交 | overlayQuantity（成交后增强仓位） | 收益处理 | 周期状态 |
| --- | --- | ---: | --- | --- |
| 第 1 日 | 卖出 1,200 | -1,200 | 只产生开仓费用和未实现增强收益，不产生价差型已实现增强收益 | 周期 A 打开 |
| 第 2 日 | 买入 600 | -600 | 对 600 股确认第 2 日 realizedOverlayPnl | 周期 A 未完成 |
| 第 2 日 | 再卖出 300 | -900 | 增加负增强仓，更新加权净卖出价 | 周期 A 未完成 |
| 第 3 日 | 买入 800 | -100 | 对 800 股确认第 3 日 realizedOverlayPnl | 周期 A 未完成 |
| 第 N 日 | 买入 100 | 0 | 对最后 100 股确认当日 realizedOverlayPnl | 周期 A 完成 |

因此：

- 第 2 日有已实现增强收益，因为已经恢复了 600 股；
- 第 2 日再次卖出 300 股不会新建周期，因为增强仓尚未回到 0；
- 第 3 日有 800 股对应的已实现增强收益；
- 完整周期总收益在第 N 日形成一条 completedCycle（已完成周期）记录，但前面各日的收益不搬到第 N 日；
- 若回测在第 3 日结束，周期 A 仍为 openCycle（未完成周期），剩余 100 股按最后行情进入未实现增强收益，不进入胜率。

## 8. 请求与快照契约

### 8.1 新增字段

core_position_overlay（底仓增强）新增：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| overlaySettlementPolicy（增强仓结算规则） | enum | intraday_restore 或 cross_day_carry |
| targetBaseQuantity（目标底仓数量） | 正整数 | 新任务显式保存；首版可由 baseQuantity 归一化得到 |

兼容字段处理：

- baseQuantity（底仓数量）暂时保留为外部字段，后端在请求边界归一化为 targetBaseQuantity（目标底仓数量）。
- t0Enabled（启用底仓做 T）对新建底仓增强任务由类别派生，不再参与类别推断；历史任务继续按快照读取。
- holdingPolicy（持仓规则）继续服务方向性持仓；底仓增强是否跨日只读取 overlaySettlementPolicy（增强仓结算规则）。
- 新底仓增强任务必须启用初始持仓，且底仓数量和成本价均大于 0。

### 8.2 完整链路

新增字段必须同时进入：默认值、前端表单、方案保存、草稿指纹、回测提交载荷、strategyParams（策略参数）、后端已保存方案一致性校验、运行快照、任务队列载荷、Worker 输入、历史恢复和公开回测读取。

保存后立即运行不得被误判为“存在未保存修改”。Redis 或本地缓存中若持久化了请求或结果结构，必须递增缓存命名空间。

## 9. 结果数据契约

### 9.1 summary（结果摘要）

新增或明确以下字段：

| 字段 | 含义 |
| --- | --- |
| accountPnl | 账户总收益 |
| accountRealizedPnl | 账户库存成本口径的已实现损益 |
| baseBenchmarkPnl | 固定目标底仓基准收益 |
| overlayPnl | 相对固定底仓的增强收益 |
| realizedOverlayPnl | 累计已实现增强收益 |
| unrealizedOverlayPnl | 期末未实现增强收益 |
| completedCycleCount | 已完成增强周期数 |
| openCycleCount | 期末未完成增强周期数 |
| winningCycles | 盈利周期数 |
| losingCycles | 亏损周期数 |
| breakevenCycles | 持平周期数 |
| cycleWinRate | 完整周期胜率，平局不进入分母 |
| resultSchemaVersion | 结果结构版本，值为 3 |
| tradeMetricVersion | 交易指标版本，值为 3 |

保留 totalPnl（总收益）作为 accountPnl（账户总收益）的兼容别名；两者不一致时任务结果无效，禁止前端自行挑选。

### 9.2 trades（成交明细）

每条成交至少增加：

- fillId（成交编号）；
- positionKey（持仓键）；
- inventorySource（库存来源）：directional_net、base_delivery 或 overlay_inventory；
- cycleId（周期编号，可空）；
- cycleEffect（周期效果）：open、increase、partial_close、close 或 reverse；
- overlayQuantityBefore（成交前增强仓位）；
- overlayQuantityAfter（成交后增强仓位）；
- accountRealizedPnl（账户会计已实现损益）；
- realizedOverlayPnl（本次已实现增强收益）；
- totalFee（本次实际总费用）及费用分项。

若一个 Fill 跨过 0，trades（成交明细）保留一条事实成交，并附 attributionSegments（归属片段）数组说明关闭旧周期与打开新周期的数量、费用和 cycleId（周期编号）。

### 9.3 cycles（增强周期）

新增 cycles（增强周期）数组：

- cycleId（周期编号）、symbol（标的）、direction（增强方向）；
- openedAt（开始时间）、closedAt（完成时间，可空）；
- openedQuantity（周期累计建立数量）、closedQuantity（累计恢复数量）、remainingQuantity（剩余数量）；
- realizedPnl（已实现周期收益）、unrealizedPnl（未实现周期收益）、netPnl（当前周期净收益）；
- fillIds（关联成交编号）；
- status（周期状态）：open 或 completed。

### 9.4 dailyHoldings（每日持仓与收益）

每日记录至少增加：

- targetBaseQuantity（目标底仓数量）；
- actualQuantity（实际持仓数量）；
- overlayQuantity（增强仓位）；
- sellableQuantity（当日实际可卖数量快照）；
- dailyAccountPnl（每日账户收益）；
- dailyBaseBenchmarkPnl（每日底仓基准收益）；
- dailyOverlayPnl（每日增强收益）；
- dailyRealizedOverlayPnl（当日已实现增强收益）；
- unrealizedOverlayPnl（当日收盘未实现增强收益）；

## 10. 前端展示

### 10.1 参数区

底仓增强策略显示“增强仓结算规则”：

- 日内恢复：继续执行尾盘恢复目标底仓；必要的强制结算假设沿用现有告警。
- 允许跨日：日终只撤销未成交委托，不自动恢复底仓，增强仓和周期状态延续至下一交易日。

选择允许跨日时，页面明确提示：允许跨日不改变 T+1，任务结束未恢复仓位会按最后行情计入未实现增强收益，但不计入闭环胜率。

### 10.2 结果概览

结果页分为三个清晰区域：

1. 账户表现：总收益、总收益率、权益曲线、回撤。
2. 底仓基准：固定目标底仓的收益与收益率。
3. 增强表现：增强收益、已实现增强收益、未实现增强收益、完整周期数、未完成周期数和周期胜率。

不得用“第二笔交易收益”这种依赖明细顺序的文案。应使用“周期 A 当前收益”或“成交 X 本次已实现增强收益”。

### 10.3 明细与图表

- 成交明细同时展示账户会计已实现损益和本次已实现增强收益，并提供简短口径说明。
- 新增增强周期表，支持展开查看组成成交；未完成周期以明显状态标识。
- 持仓图同时绘制 targetBaseQuantity（目标底仓数量）水平线、actualQuantity（实际持仓数量）和 overlayQuantity（增强仓位）。
- 每日收益图可切换账户、底仓基准、增强三条序列；默认不把三种收益相加显示。

## 12. 日终与任务结束处理

### 12.1 intraday_restore（日内恢复）

沿用现有目标底仓恢复流程，但所有系统生成成交也必须先进入账户事实账，再进入增强归属账。恢复完成后 overlayQuantity（增强仓位）必须为 0，并完成当日周期。

若使用强制结算价格或导致负现金，必须保留现有可审计告警；强制结算产生的周期收益不得被标记为真实可成交表现。

### 12.2 cross_day_carry（允许跨日）

日终不恢复目标底仓：

- 撤销当日未成交委托并释放预留；
- 保存实际持仓、T+1 库存日期、增强仓加权价格和 openCycle（未完成周期）；
- 次日按真实库存日期重建 sellableQuantity（可卖数量）；
- 周期延续，不因换日重新编号或清零成本。

### 12.3 任务结束

任务结束时不得伪造补回成交。未完成周期按最后有效估值价计算未实现增强收益，写入 openCycle（未完成周期）和告警提示。只有用户选择 intraday_restore（日内恢复）时，才按该模式已定义的尾盘恢复规则产生系统结算成交。

## 13. 历史兼容与迁移

1. 历史任务及其 JSON 结果保持原样，不在读取时补算周期。
2. 没有 resultSchemaVersion = 3 的任务显示“历史收益口径”，并继续读取其原字段。
3. 历史 core_position_overlay（底仓增强）任务默认解释为 intraday_restore（日内恢复），但不回写数据库或结果文件。
4. 历史 directional_holding（方向性持仓）任务若存在底仓回退成交，只按已冻结结果展示，并标识旧版归属口径；只有主动重新运行才使用新语义。
5. 方案保存或任务表如需新增持久化字段，必须新增幂等数据库迁移，不修改已执行迁移。
6. 结果文件、任务载荷和缓存均带显式版本；缓存命名空间升级后，旧缓存只能失效回源，不能改变历史结果。

## 16. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 账户收益正确但增强收益无法对账 | 每日和期末强制执行两条等式；失败即任务错误并保留诊断字段 |
| 账户库存成本与增强归属再次混用 | 字段命名强制区分 accountRealizedPnl 与 realizedOverlayPnl，页面不共用标签 |
| 分批恢复被算成多个周期 | 周期只由增强仓从 0 离开并再次回到 0 决定 |
| 跨日时成本或周期被日切清空 | openCycle、加权价格和库存日期进入日终状态快照并覆盖恢复测试 |
| 一笔成交跨零导致费用重复 | 实际 Fill 唯一；归属片段按数量分摊同一笔费用，尾差只落一次 |
| 方向性策略行为被底仓增强改造污染 | 两类策略在请求校验和引擎归属入口显式分支，方向性不创建增强账 |
| 强制尾盘成交抬高策略质量 | 单独标识系统结算，页面告警，质量指标可排除或单独统计 |
| 新旧任务结果混读 | 显式结果版本、历史兼容分支、缓存命名空间升级，不读取时重算 |
| 多服务版本不一致 | 相关服务同批部署并在启动和任务载荷中校验结果版本支持范围 |

## 17. 验收标准

1. 底仓增强可显式选择日内恢复或允许跨日；允许跨日时不在日终制造补回成交。
2. 昨日卖出、今日分批买回、今日再次卖出、后续继续买回的序列始终按有符号增强仓正确延续。
3. 每次部分恢复均在实际成交日确认 realizedOverlayPnl（已实现增强收益）；只有增强仓回到 0 才增加 completedCycleCount（已完成周期数）。
4. 任务结束未恢复的增强仓进入 unrealizedOverlayPnl（未实现增强收益）和 openCycle（未完成周期），不进入周期胜率。
5. accountPnl（账户总收益）仍由现金和实际持仓市值计算，并能与底仓基准及增强收益逐日、期末对账。
6. 方向性持仓不生成增强周期，不再通过隐藏仓位回退造成策略仓和账户仓语义分裂。
7. T+1、资金、费用、涨跌停和实际可卖量约束不因跨日增强而放宽。
8. 标准 Bar 与 L2 对相同成交序列产出相同的增强仓、周期和收益口径。
9. 新结果字段、前端类型、方案保存、任务快照、历史恢复和公开读取完整一致。
10. 历史任务不重算、不改写，旧结果可查看且明确标识历史口径。
11. 自动化测试覆盖第 14 节全部场景，部署后完成代表性新回测与历史兼容验证。

## 18. 自审结论

本需求合理，且不应通过修改某一笔交易的“预期收益”来局部修补。局部把底仓成本替换为最近一次买入价，会在跨日、分批恢复、再次卖出和一笔成交跨零时产生新的歧义，也无法解释账户总账。

推荐实施本方案：保留账户事实账作为总收益真值，以目标底仓为基准建立独立增强归属账；每日收益按实际日期确认，完整周期按增强仓归零确认。这样既符合底仓增强策略的经济含义，也不会改变方向性持仓的正常跨日逻辑。

本方案实施后，docs/11_L2底仓做T与尾盘强制结算方案.md 中“底仓增强只能日内恢复”的约束，以及 docs/28_闭环交易胜率与交易质量指标改造方案.md 中尚未区分账户已实现损益与增强已实现收益的部分，由本方案替代；docs/36_方向性持仓可选初始底仓方案.md 中方向性初始仓位的单一净仓语义继续有效。
